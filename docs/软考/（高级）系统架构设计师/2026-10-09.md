## 今日核心概念

### 1. 云原生与Kubernetes高级调度
定义：基于容器、服务网格、微服务、不可变基础设施和声明式API构建的云原生应用体系，Kubernetes作为容器编排的事实标准，通过控制平面（API Server/Scheduler/etcd/Controller Manager）与工作节点（kubelet/kube-proxy/容器运行时）协同，实现应用的自动化部署、扩缩容与自愈。
关键要点：
- Pod是最小调度单位，底层通过CRI容器运行时接口对接containerd或CRI-O
- 调度器采用两级过滤：Predicates（节点筛选）+ Priorities（打分），影响调度的关键因素包括资源requests/limits、节点亲和性、污点与容忍、拓扑分布约束
- 控制器模式是核心思想，Deployment→ReplicaSet→Pod三层通过Label Selector维持期望状态
- HPA基于CPU/内存/自定义指标（如QPS）做水平扩缩容，VPA做垂直资源调整，Cluster Autoscaler做节点级弹性
- 高级调度特性：拓扑分布约束（pod topology spread constraints）实现多可用区均匀分布，反亲和性（pod anti-affinity）避免单点故障，优先级调度（PriorityClass）保障核心业务SLO
- 考试高频考点：Deployment滚动更新策略（maxUnavailable/maxSurge）、StatefulSet有序部署、DaemonSet节点级守护

### 2. 分布式事务与最终一致性
定义：在分布式微服务环境下，跨多个服务或数据源的数据一致性保障机制，由于CAP定理约束，强一致性（Consistency）与可用性（Availability）不可兼得，多数业务场景选择最终一致性（Eventual Consistency）。
关键要点：
- 两阶段提交（2PC）通过Prepare+Commit两阶段保证强一致，但存在协调者单点与同步阻塞问题，适合数据库XA事务
- 三阶段提交（3PC）引入CanCommit预阶段与超时机制降低阻塞，但实现复杂且仍不能完全避免不一致
- TCC模式（Try-Confirm-Cancel）将业务逻辑拆为三阶段，由业务代码实现补偿，适合资金类强一致场景
- Saga模式分为编排式（Orchestration，中央协调器）与编舞式（Choreography，事件驱动），通过补偿事务实现最终一致
- 本地消息表 + 定时任务实现最终一致性的经典方案：业务操作与消息写入同库，扫描未发送消息投递到MQ
- RocketMQ事务消息采用Half Message + 回查机制，弥补本地消息表扫描延迟
- 软考常考：Saga补偿设计、本地消息表原理、MQ事务消息与最大努力通知三种方案对比

### 3. 高可用架构与容灾设计
定义：通过冗余设计、故障检测、自动切换等机制保障系统持续提供服务能力，衡量指标包括可用性SLO（如三个9=99.9%年停机8.76小时、四个9=99.99%年停机52分钟）、RTO（恢复时间目标）与RPO（数据恢复点目标）。
关键要点：
- 主备复制（Master-Slave）通过binlog同步实现读写分离，故障时VIP漂移，RTO通常分钟级
- 主主复制（Master-Master）双向同步提升写入能力，但需解决写冲突与自增ID问题
- 同城双活两个机房同时对外服务，数据库通过同步复制（如PXC、MGR）保持强一致
- 异地多活通过单元化（Set化）将用户按ID哈希路由到不同地域，跨地域异步复制，接受秒级RPO
- 限流是保障高可用的关键防线：令牌桶（允许突发）、漏桶（平滑流出）、滑动窗口（精确控制QPS）
- 熔断（Circuit Breaker）三态转换：Closed→Open→Half-Open，防止雪崩向依赖服务扩散
- 降级策略：读降级（返回缓存或兜底数据）、写降级（异步化或丢弃）、功能降级（关闭非核心模块）
- 考试必背：限流算法四象限对比、Sentinel/Hystrix熔断器原理、异地多活Set化设计原则

### 4. 性能优化与可观测性
定义：通过压力测试、性能分析、参数调优等手段提升系统吞吐与响应速度，同时建立Metrics（指标）、Logging（日志）、Tracing（追踪）三位一体的可观测性体系，实现故障快速定位与根因分析。
关键要点：
- 性能优化三阶段：基准测试（Baseline）→ 瓶颈定位（Profiler）→ 优化实施（CPU/内存/IO/网络分层调优）
- 数据库优化金字塔：SQL改写（避免SELECT *、合理JOIN）→ 索引优化（最左前缀、覆盖索引）→ 表结构（范式/反范式）→ 架构（读写分离、分库分表）
- 缓存设计三大问题：缓存穿透（布隆过滤器/空值缓存）、缓存击穿（分布式锁/逻辑过期）、缓存雪崩（随机过期/多级缓存）
- 缓存一致性经典方案：Cache Aside（先DB后Cache，先更新DB再删Cache）、Read/Write Through、Write Behind
- OpenTelemetry统一Metrics/Logs/Traces采集，通过OTLP协议上报，Jaeger/Tempo做分布式追踪
- Prometheus Pull模式采集指标，Grafana可视化，AlertManager按SLO规则告警
- APM（应用性能监控）通过字节码插桩（Java Agent）采集调用链与慢SQL，SkyWalking/CAT是典型代表
- 软考案例分析常考：性能问题排查步骤（自上而下：网络→应用→DB→底层）、缓存与DB一致性保证

### 5. 安全架构与零信任模型
定义：以"从不信任，持续验证"（Never Trust, Always Verify）为核心的安全架构范式，替代传统基于网络边界的防御模型，对每一次访问请求进行身份认证、权限校验与风险评估，覆盖网络、应用、数据全栈。
关键要点：
- 零信任三大技术支柱：SDP（软件定义边界，隐藏资产）、IAM（统一身份与访问管理）、MSG（微分段）
- NIST零信任架构八大核心组件：策略引擎（PE）、策略管理器（PA）、CDN、PE与PA协同的持续诊断与缓解
- OAuth 2.0四种授权模式：授权码（最安全，Web应用）、隐式（已弃用）、密码（仅可信应用）、客户端凭证（服务间调用）
- OIDC（OpenID Connect）在OAuth 2.0基础上增加ID Token实现身份认证，JWT是Token常用格式
- SPIFFE/SPIRE为工作负载提供加密身份（SVID），解决传统TLS仅认证通信不认证服务身份的问题
- SBOM（软件物料清单）+ SLSA供应链安全四级：Level 1基础追溯、Level 2完整性签名、Level 3防篡改构建、Level 4双人审计
- 数据安全：传输加密（TLS 1.3）、存储加密（KMS信封加密）、密钥分权（KMS Key与DEK分离）、脱敏（动态遮罩）
- 软考必考点：零信任与传统边界防护差异、OAuth 2.0四种模式适用场景、SBOM在软件供应链合规中的作用

## 案例分析题

**题目**：
某互联网金融公司推出"秒级放贷"产品，要求P99响应时间≤500ms，峰值QPS 5万，可用性99.99%（年停机≤52分钟），并通过等保三级认证。系统采用微服务架构，包含用户中心、风控引擎、征信查询、账户服务、贷款核心、还款服务6个核心模块。风控引擎需实时调用央行征信与第三方反欺诈接口（响应时间200ms~3s不等），贷款核心要求强一致的资金账务处理。系统上线后频繁出现：①大促期间风控线程池打满导致贷款申请被拒；②征信查询接口超时拖垮整个风控链路；③单库单表账户表数据量过亿导致查询缓慢；④异地机房切换时部分用户出现资金重复放款异常。

请回答：
1. 针对问题①，请给出至少3种线程池优化与隔离方案
2. 针对问题②，请设计完整的熔断降级+超时控制+兜底数据体系
3. 针对问题③，请设计账户表的分库分表方案并说明扩容策略
4. 针对问题④，请分析异地多活场景下资金一致性保障方案

**参考答案**：

**问题1：线程池优化与隔离方案**
- 线程池隔离：按业务重要性分级，风控引擎独立线程池（核心线程50，最大200，队列1000），与征信查询、反欺诈查询使用独立线程池，避免一个慢调用耗尽所有线程
- 信号量隔离（Semaphore）：对第三方依赖（征信、反欺诈）使用信号量限流，并发上限控制为30，超出直接快速失败
- 舱壁模式（Bulkhead）：每个外部依赖一个独立线程池，类似船舶水密舱室，单舱漏水不影响全船
- 动态线程池：根据QPS自适应调整核心线程数，配合Prometheus监控线程池活跃度
- 异步化：风控校验全链路异步化，主线程只做入口校验与结果汇总，耗时操作（反欺诈深度分析）转入MQ异步处理

**问题2：熔断降级+超时控制+兜底数据体系**
- 超时控制：风控调用第三方统一设置超时（征信500ms、反欺诈800ms），使用Sentinel或Resilience4j的TimeLimiter
- 熔断器配置：滑动窗口20个请求，错误率超50%熔断10秒，Half-Open状态放行3个探测请求
- 降级策略：
  - 征信接口降级：返回本地缓存的近7天查询结果（覆盖90%重复申请），缓存无则跳过征信
  - 反欺诈接口降级：返回基于规则引擎的本地反欺诈判定（覆盖80%场景），标注"非实时反欺诈"标识
  - 极限降级：风控引擎完全不可用时，进入"白名单+小额授信"应急模式
- 兜底数据：所有外部依赖返回FallbackResult包含reason字段，下游根据reason决策（如reason=TIMEOUT则放款金额降为50%）
- 重试策略：仅对幂等读操作重试，最多2次，指数退避（100ms、500ms），不重试非幂等写操作
- 监控告警：熔断Open/Close状态变更、第三方调用P99超过300ms触发告警

**问题3：账户表分库分表方案**
- 分片键选择：以user_id为分片键，账户查询95%场景基于用户ID，可避免跨分片查询
- 分片策略：64个分片（8库×8表），按user_id取模分散到8个物理库，单表数据量控制在2000万以内
- 路由方案：客户端分片（ShardingSphere-JDBC）部署在贷款核心服务，无中心化Proxy，延迟低
- 数据迁移：使用ShardingSphere的弹性伸缩能力，从8库扩到16库，零停机扩容流程：
  1. 双写阶段：新库启用，代码同时写新旧两套表
  2. 全量迁移：使用DTS工具将旧库数据迁移到新库，按user_id取模分布
  3. 数据校验：比对新旧库数据，差异数据修复
  4. 切读阶段：读流量按灰度比例切到新库（1%→10%→50%→100%）
  5. 下线旧库：保留30天后清理旧库
- 索引优化：账户表联合索引（user_id, account_type），覆盖余额查询场景
- 冷热分离：历史账户（6个月无交易）迁移到OSS+Elasticsearch，活跃账户保留在线库

**问题4：异地多活资金一致性保障**
- 异地多活选型：采用同城双活（同城RPO=0，RTO秒级）+ 异地灾备（异步复制，RPO分钟级）方案，避免异地多活数据冲突复杂度
- 单元化设计：将用户按user_id哈希分为多个Set（如同城A单元、同城B单元），同用户所有操作路由到同一单元，避免跨单元调用
- 资金账务强一致：账户表主库采用PXC（Percona XtraDB Cluster）或MySQL Group Replication同步复制，保证同城双中心RPO=0
- 防重复放款：放款操作通过Redis分布式锁（SETNX + Lua脚本）锁定user_id+order_id，锁粒度按用户+业务单号
- 幂等设计：放款流水号全局唯一（雪花算法 + 单元标识），数据库unique索引兜底，重复请求直接返回原结果
- TCC补偿：贷款发放采用TCC模式，Try阶段冻结额度、Confirm阶段实际扣减、Cancel阶段释放冻结，任何一阶段失败自动反向补偿
- 故障切换演练：每月一次主备切换演练，验证RTO<30秒，账务对账脚本15分钟内完成数据校验
- 监控对账：实时对账（每分钟核对两个机房账务总额）、日终对账（T+1凌晨全量核对）、差错处理（人工调账工单）

**踩分要点**：
- 线程池隔离要答出"按业务分级"+"信号量/Semaphore"+"舱壁模式"三个层次，单答"加线程"不给满分
- 熔断降级要形成完整体系：超时→熔断→降级→兜底→重试→监控六环缺一不可
- 分库分表必须说明分片键选择依据、扩容策略、索引设计三部分，仅答"分8个库"不够深入
- 异地多活资金一致性是高频考点，必须区分同城双活（RPO=0）与异地多活（RPO>0）的不同方案
- 强调可观测性：所有方案必须配套监控指标（线程池活跃度、熔断状态、QPS/P99、对账差异）
- 等保三级合规要点：数据传输加密、敏感信息脱敏、操作审计日志保留6个月以上
- "踩坑"提示：线程池不要共用，分布式锁必须有唯一键+超时机制，分库分表后跨库JOIN要反范式化
