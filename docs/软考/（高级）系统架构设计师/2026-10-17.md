# 系统架构设计师 第61次学习（2026-10-17）

## 今日核心概念

### 1. 微服务架构演进与Service Mesh服务网格
定义：Service Mesh是处理服务间通信的专用基础设施层，通过Sidecar代理将业务逻辑与服务治理解耦。

关键要点：
- 演进路径：单体应用→SOA面向服务→微服务→服务网格→无服务器Serverless
- 架构组成：数据平面（Sidecar代理如Envoy，处理实际流量）+ 控制平面（Istiod，管理配置与策略）
- 核心能力：流量管理（灰度发布、路由、限流、重试）+ 安全（mTLS双向认证授权）+ 可观测性（指标日志追踪三大支柱）+ 策略（访问控制、限流规则）
- 代表实现：Istio（控制面基于Envoy）+ Linkerd（轻量Rust实现）+ Consul Connect
- Sidecar模式优势：业务无侵入、多语言支持、关注点分离

### 2. 分布式事务解决方案体系
定义：在分布式环境下保证跨服务数据一致性的多种模式与协议集合。

关键要点：
- 强一致性方案：2PC两阶段提交（协调者+参与者+Prepare+Commit阶段）+ 3PC三阶段（CanCommit+PreCommit+DoCommit，解决2PC协调者单点阻塞）
- 最终一致性方案：TCC（Try-Confirm-Cancel三阶段，业务侵入强）+ Saga（长事务拆分+补偿）+ AT模式（自动补偿，Seata实现）+ 可靠消息最终一致（本地消息表+MQ投递）+ 最大努力通知
- Saga两种实现：编排式Orchestration（中心协调器集中调度）+ 编舞式Choreography（事件驱动，无中心节点）
- 选型依据：业务一致性等级要求 + 性能容忍度 + 系统复杂度 + 资金安全约束
- 资金场景首推TCC/Saga强一致，非资金场景优先MQ最终一致

### 3. CQRS读写分离架构
定义：命令查询职责分离（Command Query Responsibility Segregation），将写模型与读模型分离的架构模式。

关键要点：
- 核心思想：写路径走领域模型保证强一致，读路径走专用读模型优化查询性能
- 实现三种层级：共享数据库读写分离（最简）+ 数据库分离（写库+读库，通过CDC同步）+ 事件驱动（写后发事件，读模型订阅事件）
- 适用场景：读写比例严重失衡（读多写少10:1以上）+ 复杂查询报表需求 + 多视图多端展现
- 核心优势：性能优化（读写独立扩展）+ 扩展性强 + 关注点分离 + 架构清晰
- 核心代价：复杂度显著提升 + 数据同步延迟（最终一致窗口期）+ 维护成本增加

### 4. Event Sourcing事件溯源
定义：以事件为存储核心，通过回放事件流重建聚合状态的架构模式。

关键要点：
- 核心思想：不存储当前聚合状态，存储导致状态变化的不可变事件流
- 事件四要素：不可变性 + 全序性 + 业务语义完整 + 可重放回放
- 配套机制：快照Snapshot（定期保存聚合状态避免无限重放）+ 事件存储Event Store + 投影器Projector订阅事件构建读模型
- 核心优势：审计天然完整 + 时间旅行任意版本回溯 + 与事件驱动架构天然契合
- 核心代价：架构复杂 + 即时查询困难（需重放） + 事件版本升级兼容（Upcasting机制）
- 与CQRS天然搭配：写端事件溯源 + 读端物化视图投影

### 5. 云原生12要素方法论
定义：The Twelve-Factor App，构建可移植、可扩展、可部署SaaS应用的12条方法论原则。

关键要点：
1. 基准代码：一套基准代码多部署，单一仓库
2. 依赖：显式声明依赖，隔离运行环境
3. 配置：配置与代码分离，环境变量统一注入
4. 后端服务：把数据库缓存MQ当作可替换附加资源
5. 构建发布运行：严格三阶段分离，单向不可回退
6. 进程：无状态共享进程，通过进程模型横向扩展
7. 端口绑定：自包含服务，通过端口对外暴露HTTP
8. 并发：通过进程模型横向扩展应对负载
9. 易处理：快速启动优雅终止，对抗故障
10. 开发生产等价：保持环境一致性，缩小差距
11. 日志：日志作为事件流统一采集
12. 管理进程：一次性管理脚本作为进程运行

### 6. API网关与BFF（Backend For Frontend）模式
定义：API网关统一处理南北向流量的入口组件，BFF为不同前端定制后端的适配层模式。

关键要点：
- API网关六大核心能力：统一鉴权（JWT/OAuth2/OpenID Connect）+ 流量管控（限流熔断降级）+ 动态路由 + 服务聚合编排 + 协议转换（REST/gRPC/WebSocket）+ 全链路监控
- 网关选型：Nginx（高性能反向代理）+ Kong（OpenResty可扩展）+ Spring Cloud Gateway（Java生态）+ APISIX（云原生+多协议）
- BFF核心思想：每种前端（Web/iOS/Android/小程序）单独构建后端聚合层，按需聚合微服务
- BFF核心优势：前端体验定制化（多端差异屏蔽）+ 减少端到端请求数 + 后端服务彻底解耦
- 与API网关关系：API网关是基础设施级横切关注点，BFF是业务级前端聚合层，二者正交共存

## 案例分析题

**题目**：某电商平台日均订单量300万笔，秒杀场景峰值20万QPS。原来采用单体架构，订单服务、库存服务、支付服务、积分服务耦合严重，性能瓶颈突出，数据库单点压力大。系统改造要求如下：
（1）订单创建涉及订单库写入、库存扣减、支付预扣、积分赠送四个步骤，任一失败需回滚
（2）双11大促需支撑20万QPS，库存不能超卖
（3）需要支撑订单全程追溯，包括创建、支付、发货、退款的状态变更历史
（4）读写比例约100:1，运营报表实时性要求高

请基于微服务架构思想，设计该电商订单系统的整体架构，说明：
a) 微服务拆分粒度与依据
b) 分布式事务解决方案
c) 库存防超卖设计
d) 订单状态追溯方案
e) 高并发读优化方案

**参考答案**：

a) **微服务拆分粒度与依据**：采用领域驱动设计DDD进行限界上下文划分。订单核心域拆分为订单服务、库存服务、支付服务、积分服务、物流服务五个微服务，依据：
- 业务边界清晰（订单履约全链路五环节）
- 数据归属独立（各自有专属数据库，互不直访）
- 高内聚低耦合（接口通过OpenAPI/Protobuf定义，内部实现透明）
- 团队规模匹配（每个团队负责2-3个服务，康威定律）
- 基础设施层独立：API网关、统一认证中心、配置中心Nacos、注册中心、可观测性平台

b) **分布式事务解决方案**：库存扣减+支付预扣采用TCC强一致（资金场景），订单写入+积分赠送采用可靠消息最终一致（业务场景）。具体设计：
- 订单-库存-支付链路：TCC三阶段。Try阶段冻结库存+预扣支付额度；Confirm阶段订单创建成功落库；Cancel阶段解冻并返还额度
- 订单-积分链路：积分服务订阅订单创建MQ消息，消费失败重试+人工兜底。MQ选RocketMQ，开启事务消息保证本地事务与消息发送原子性
- 配套Seata框架统一管理TCC与AT两种模式，配置中心下发事务分组

c) **库存防超卖设计**：Redis预扣库存+数据库乐观锁双保险双层防护。
- 第一层Redis原子预扣：秒杀入口Redis DECR原子操作，库存不足直接返回失败；Lua脚本保证判断库存与扣减原子性
- 第二层数据库乐观锁：SQL执行`UPDATE stock SET count = count - #{num} WHERE sku_id = #{id} AND count >= #{num}`，受影响行数为0即超卖失败
- 库存同步管道：库存变更异步写MySQL Binlog，Canal订阅同步到Redis维持一致
- 大促预留专属Redis集群与库存分桶（按SKU hash分散热点）

d) **订单状态追溯方案**：Event Sourcing事件溯源。
- 订单聚合根持久化不可变事件流：OrderCreatedEvent、OrderPaidEvent、OrderShippedEvent、OrderCompletedEvent、OrderRefundedEvent等
- 事件存储采用MySQL事件表，字段含aggregate_id、event_type、event_data（JSON）、version、created_at
- 定期Snapshot快照（每100个事件做一次）加速状态重建，避免无限回放
- 投影器Projector将事件流投影到订单查询视图与运营报表视图
- 任意时刻时间旅行：通过version截断事件回放还原历史状态，天然满足审计追溯需求

e) **高并发读优化方案**：CQRS读写分离 + 多级缓存 + 专用读模型三位一体。
- 读写链路分离：写库MySQL主库承担订单写入，读库MySQL从库+MyCAT/ShardingSphere读写分离中间件承担普通查询
- 多级缓存链：L1 Caffeine本地缓存（热点订单TTL 30秒）+ L2 Redis集群（订单详情TTL 5分钟）+ L3 CDN（静态化资源）
- 读模型专用化：复杂查询视图走Elasticsearch（支持全文检索、复杂聚合、即时排序），通过Canal订阅MySQL Binlog准实时同步（毫秒级延迟）
- 运营实时报表：数据ETL到ClickHouse/Doris列式存储，运营大屏通过Flink实时计算订单金额、笔数、转化漏斗等指标

**踩分要点**：
- 第(1)问必须答出TCC与可靠消息的差异边界（资金强一致 vs 业务最终一致），体现场景化选型能力
- 第(2)问必须答出Redis预扣+数据库乐观锁双保险，并解释双保险的必要性（Redis单点风险兜底+数据库最终一致性）
- 第(3)问必须答出Event Sourcing的事件表结构设计+Snapshot机制+时间旅行原理
- 第(4)问必须答出CQRS读写分离架构+多级缓存分层+专用读模型（ES/ClickHouse）选型
- 加分项：DDD限界上下文作为拆分依据、统一可观测性平台（Metrics+Log+Trace）、云原生K8s部署、Sentinel限流防雪崩
