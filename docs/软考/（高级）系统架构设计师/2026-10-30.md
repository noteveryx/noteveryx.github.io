## 今日核心概念

### 1. 流式计算引擎与批流一体架构

定义：流式计算是对无界数据流进行持续增量计算的计算范式，输出延迟在毫秒到秒级；批流一体（Unified Batch & Streaming）指用同一套引擎、同一套 SQL 语义、同一套存储底座同时处理有界批数据与无界流数据。

关键要点：
- **流计算三要素**：无界数据流、增量计算（每条记录只处理一次，结果持续更新）、低延迟输出。**批计算三要素**：有界数据集、全部数据一次算完、任意延迟
- **四大引擎对比**：
  - **Flink**：真正的流批一体，原生支持事件时间与 Watermark，状态丰富（键控状态 + 算子状态），内置 CEP 库，支持异步 IO，端到端精确一次语义最成熟。**延迟最低（毫秒级）、生态最全、成本最高**
  - **Spark Structured Streaming**：本质是微批（Micro-batch），默认批次 100ms~数秒，生态最全（SQL、ML、GraphX 复用批侧代码），**适合既有 Spark 资产与 SQL 复杂场景**
  - **Kafka Streams**：无独立集群的轻量库，与 Kafka 分区天然绑定，本地状态存储 RocksDB，**适合中小规模流处理与 Kafka 已有团队**
  - **Storm**：老牌 Tuple 原生 API，延迟低但生态弱、无 SQL、精确一次语义弱，**新项目不推荐**
- **批流一体的三条落地路径**：
  - **以流为批**：Flink 批模式把离线文件当作有界流读取，SQL 语义与流作业一致（批流一套 SQL）
  - **以批为流**：Spark Structured Streaming 直接查批表，用"长表 + 水位标记"模拟增量
  - **双引擎 + 统一湖仓**：批侧 Spark、实时侧 Flink CDC，共写 Iceberg / Hudi / Paimon 湖仓，靠 ACID 事务与 Schema Evolution 保证一致
- **湖仓一体（Lakehouse）**：Iceberg（开放表格式、隐藏分区、支持 Schema Evolution 与 Time Travel）、Hudi（主键索引、更新删除能力强）、Paimon（原 Flink Table Store，国内湖仓主流）。**底座能力决定上层批流能否共读共写**
- **实时数仓标准链路**：业务库 MySQL → CDC（Debezium / Canal / Flink CDC）→ Kafka → Flink 实时计算 → 实时数仓（ODS/DWD/DWS/ADS）→ OLAP 引擎（Doris / StarRocks / ClickHouse）→ 大屏、风控、特征库
- **选型口诀**：超低延迟 + 复杂事件 + 复杂状态 → Flink；SQL/机器学习/批侧复用 → Spark；已有 Kafka 且规模不大 → Kafka Streams

### 2. 复杂事件处理（CEP）与事件模式匹配

定义：CEP（Complex Event Processing）是在事件流上识别具有时间约束与组合关系的事件模式的技术，例如"同一账户 5 分钟内 3 次小额试探性查询后 1 分钟内发生大额转账"，是 Flink CEP、流式规则引擎的核心能力。

关键要点：
- **事件模式四要素**：事件类型（Type）、顺序关系（严格 / 宽松 / 混合）、数量约束（within 时间窗内 exactly / at least / optional 几次）、时间约束（within 5 minutes）
- **模式分类**：严格顺序（a→b→c 必须相邻）、宽松顺序（a→b 或 b→a）、混合模式（条件组合 + 分支）、迭代模式（同一事件多次出现，如连续 3 笔金额递增）
- **匹配语义三型**：严格连续（strict contiguity，中间不可插入他事件）、非严格连续（non-strict contiguity，允许跳过）、宽松连续（relaxed contiguity，允许跳过且允许重复）。**考试常考：默认严格连续，写错会漏报**
- **常用算子**：within（时间窗约束）、followedBy（宽松后继，可跳过）、followedByAny、notFollowedBy（否定，"未发生"类风险规则必备）、beginBy、skip / take（跳过与截断）、where（自定义过滤条件）、withinEach（按子流分组计数）
- **内部机制**：CEP 用 **NFA（非确定有限自动机）** 维护部分匹配状态，含开始状态、循环状态、终止状态；终止前超时未完成的匹配可通过 **侧输出（Side Output）** 捕获，用于旁路告警或补数
- **与邻近技术区分**：CEP 面向无界流的**时间窗模式识别**；状态机面向**会话生命周期流转**；Drools 面向**业务规则决策**；流式数仓面向**度量聚合**。四者可组合而非替代
- **规则治理三件套**：规则 DSL 化（规则中心配置下发，避免改代码发版）、规则版本与时间旅行回放、规则效果评估（命中率、误报率、人工复核率、产出价值）
- **告警风暴治理四步**：规则分级（高危自动阻断 / 中危人工复核 / 低危仅记录）→ 同类同主体时间窗聚合去重 → 置信度阈值与模型预筛前置 → 命中后自动生成核查任务并将核查结论反哺规则（闭环迭代）

### 3. 时间语义、乱序处理与 Watermark

定义：Watermark 是流处理中表示"事件时间推进进度"的机制，Flink 依据它触发窗口计算并判定数据迟到；正确的时间语义是实时计算结果可重现、可审计的前提。

关键要点：
- **三种时间**：事件时间（Event Time，事件实际发生时刻，**最符合业务语义**）、处理时间（Processing Time，处理时刻，简单但结果不可重现）、摄取时间（Ingestion Time，采集时刻）
- **Watermark 定义**：W(t) 表示"预计不会再有事件时间 ≤ t 的数据到达"。Flink 采用**周期性水位线**（按 autoWatermarkInterval 定期计算）与**空闲源标记**（idleness，避免单一慢分区拖住全局水位线）
- **乱序四大来源**：多源异构采集、网络抖动与重试、上游缓冲批量发送、业务系统自身写入无序
- **乱序三级应对**：
  - 提高水位线延迟（容忍更多乱序，代价是延迟上升）
  - **允许迟到（allowed lateness）+ 侧输出通道**（迟到数据进侧输出走修正 / 补数通道，是生产主流做法）
  - 事件时间重排序缓冲（需全量排序，代价高，仅适用于短窗口）
- **窗口四型**：滚动窗口（Tumbling，如每 1 分钟）、滑动窗口（Sliding，如每 1 分钟统计最近 5 分钟）、会话窗口（Session，按不活动间隔切分，用户行为分析常用）、全局窗口（Global，触发式，单例聚合）
- **确定性收益**：使用事件时间 + 水位线后，**同一输入必得同一结果**，这是实时与离线双跑对账、审计追溯、故障复算的前提
- **三大坑**：水位线推进过慢 → 检查点阻塞与状态膨胀；水位线设定过激 → 迟到数据被静默丢弃；只在 Flink 侧改事件时间而上游埋点不带时间戳 → 口径失真
- **权衡三角**：延迟、准确性、资源占用，三者不可同时最优，方案评审必须明确取舍与 SLA 承诺

### 4. 流式状态管理与容错一致性

定义：流式状态是引擎为完成增量计算而维护的中间数据；容错一致性指故障重启后作业能恢复到"不丢不重"的语义。

关键要点：
- **状态两分类**：**算子状态**（Operator State，list / union list / broadcast，无 key 依赖）与**键控状态**（Keyed State，value / list / map / reduce，按 key 分区，**是并行度扩展的基础**）
- **状态后端（State Backend）**：堆内（HashMap / On-heap，快但容量受限）、RocksDB（本地磁盘，容量大、支持增量落盘，大状态首选）、Paimon 分层存储（Tiered，冷热分层）、混合型（热数据堆内 + 冷数据 RocksDB）
- **三大容错机制**：**Checkpoint**（周期性一致性快照，依赖屏障对齐 barrier；反压严重时用非对齐检查点 unaligned checkpoint）、**Savepoint**（手工触发、停机升级、回滚到指定版本）、**WAL / 元数据存储**（增量日志 + HDFS 或元数据服务）
- **增量 Checkpoint**：只上传新增与变更的 keygroup，避免全量重传，是大状态场景的必选项，可显著缩短快照时间
- **一致性语义三级**：至多一次（At-most-once，**丢数据**）、至少一次（At-least-once，**重复数据**）、精确一次（Exactly-once，**不丢不重**）
- **端到端精确一次（EOS）三前提**：
  1. **源可重放**（Kafka 位点手动提交、CDC 有 binlog 位点，故障可从位点重放）
  2. **状态与位点原子对齐**（Checkpoint 屏障保证算子状态快照与 source 位点一致）
  3. **Sink 幂等或支持事务**（主键 upsert、唯一索引去重，或两阶段提交 2PC）
- **两阶段提交（2PC）**：预提交（pre-commit）→ 状态快照与事务一并提交（commit），Kafka 事务型 Sink 即此机制
- **状态膨胀三因**：窗口过长、键基数过高（如身份证号 / 卡号）、TTL 缺失。**对策**：状态 TTL + 窗口收敛 + 增量 Checkpoint + RocksDB + 状态访问优化 + 监控（状态大小、checkpoint 时长、失败率）
- **反压（Backpressure）**：下游处理不过来时上游自动减速的自我保护机制。根因通常在下游：慢节点、外部系统写入慢、GC 停顿、数据倾斜。**对策**：异步 IO、批量写入、热点 key 打散、扩容并行度、优化 Sink 批量与压缩
- **数据倾斜三解法**：加盐打散 + 两阶段聚合、广播小维表、预聚合后再关联

### 5. 实时指标体系与流式数仓落地

定义：实时指标体系是在流式计算之上构建的秒级刷新度量体系，配套实时数仓分层与在线特征库，并与离线口径严格对齐。

关键要点：
- **指标三层延续**：原子指标（不可再分）→ 派生指标（原子 + 逻辑 + 周期 + 范围）→ 复合指标（组合计算）。**实时与离线必须共用同一套指标定义，否则大屏与财务报表打架**
- **双跑校验是上线前置条件**：同一指标在离线（T+1）与实时并行计算，设置容差（如 0.1%~0.5%），差异超阈值自动告警并可回溯差异明细
- **实时数仓分层**：ODS（Binlog 落地）→ DWD（明细清洗、维度关联）→ DWS（主题宽表、多窗口聚合）→ ADS（应用层、指标、特征）
- **维表关联三法**：Flink CDC 维表 changelog 流（一致性最好）、异步 IO 查询 HBase / Redis（维表小而稳定）、**广播状态**（小维表全量下发到各 TaskManager，读最快）
- **Lookup Join 陷阱**：事实流与维表流时间不一致导致关联错乱 → 正确做法是按**事件时间取对应维表版本**（维表 changelog 带版本时间戳），而非"取最新值"
- **维表 TTL 与热更新**：维表快照需定期刷新，TTL 过短造成反复回源、过长造成关联过期，经验值与量级相关
- **在线离线特征一致性**：训练与推理特征必须同源计算，配合特征版本号与回填校验，防止"训练服务偏斜"
- **结果存储选型**：Doris / StarRocks（实时 OLAP，明细 + 聚合）、ClickHouse（超高压缩分析）、Elasticsearch（检索）、HBase（海量点查）。写入放大敏感场景优先 OLAP 列存
- **高基数与生命周期**：维度高基数导致 join 放大与内存压力，需做分区、预聚合与冷数据归档

## 案例分析题

**题目**：

某市医疗保障局为强化基金监管，建设"医保基金智能监管平台"。原系统基于 MySQL 数据库 + Spring Batch 定时批处理，每小时执行一次离线规则，结算数据主要来自 30 余家定点医院 HIS 与 200 余家定点零售药店 POS 网关，通过 Kafka 汇聚到数据平台。改造方案采用 Flink + Kafka + Flink CEP 构建实时风控链路：Flink CDC 订阅业务库 Binlog 与 POS 网关流，Coffee/规则引擎定义 30 余条风险规则，命中后写入 Kafka 风险主题，下游对接人工审核系统、稽核系统与领导驾驶舱。

上线运行两周后，业务部门反馈如下：

（1）领导驾驶舱"当日基金支出"与财务系统月度对账差异巨大，且每日 8:00 前差异最大，财务部门认为是实时平台数据不准，险些要求回退离线方案。

（2）CEP 规则上线后告警量由日均约 200 条暴涨至日均 5 万条，人工审核系统队列严重积压，审核人员反映大量告警内容高度相似，属于同一患者同一医生的连续开药被逐条推送。

（3）作业运行 2~3 小时后频繁重启，TaskManager 进程被操作系统 OOM Killer 杀死，Checkpoint 持续超时，且日志中出现大量 "Checkpoint expired before completing" 告警。

（4）下游"重点人员画像系统"反馈同一笔药品结算在监管平台出现一次、在画像系统出现两次，人工去重后画像结果被污染。

（5）驾驶舱"药品销量 TOP10"每 10 分钟才刷新一次，业务人员反馈刷新过慢，且与业务库自行统计的 TOP10 榜单不一致，某药品在榜单中同时出现两个不同排名。

3. 请分析问题（3）产生的原因，并给出解决方案。
4. 请分析问题（4）产生的原因，并给出解决方案。
5. 请分析问题（5）产生的原因，并给出解决方案。
6. 请给出该平台实时化改造整体上"指标一致性"与"精确一次语义"两条链路的验收方法。

**参考答案**：

**问题（1）：时间语义与水位线配置不当导致跨天错分**

原因分析：
- 方案中未明确时间语义，若作业采用 **处理时间（Processing Time）** 计算"当日"窗口，则凌晨集中入库的夜间结算数据会按"到达引擎的时刻"被划入当日，导致同一笔费用在财务系统（按业务发生日归属）与实时平台（按处理时刻归属）归集到不同日期，差异集中在每日 8:00 前的批量入库高峰，与现象完全吻合。
- 另外，POS 网关存在网络抖动与批量补传，事件时间与到达时间偏差较大，采用处理时间还会放大偏差。
- 差异"巨大"还说明缺少与财务口径的对账机制，错误无法被及时发现。

解决方案：
- 统一采用**事件时间（Event Time）** 计算业务窗口，窗口按业务发生日切分（Session / 滑动日窗 + 事件时间语义），以"费用发生时间"而非"入库时间"归属日期。
- 设置**周期性 Watermark**，依据上游实际到达延迟分布设定容忍乱序的延迟阈值（建议按 POS 延迟 P99 分布取值并定期复核）。
- 对凌晨批量结算设置**允许迟到（allowed lateness）**，迟到的日终数据在窗口关闭后更新输出，同时通过**侧输出通道**将迟到明细投递到补数 / 修正流，保证最终一致。
- 财务口径需与业务口径显式对齐：跨日结算、退费冲正、医保基金与个人自付分摊规则要在事件模型中显式建模，不依赖默认值。
- 建立**离线与实时双跑对账**：同一指标在 T+1 离线与实时并行计算，按日比对差异并设置容差阈值，超阈值自动告警与追溯。
- 补充：结算数据在进入 Flink 前应带可靠的业务时间戳（POS 端以业务发生时间上报，不能用网关接收时间替代），这是事件时间可信的前提。

**问题（2）：CEP 规则缺少分级、去重与效果评估，形成告警风暴**

原因分析：
- 规则库中 30 余条规则均为同一告警等级，未按风险后果分级，高危阻断类与低危提示类混在一个队列。
- CEP 模式缺少**抑制 / 合并机制**：同一患者同一医生短时间内的连续行为被逐条匹配推送，产生大量高度相似告警。
- 规则以**代码硬编码**方式实现，调整阈值或新增场景必须改代码发版，缺少规则灰度与效果度量。
- 缺少**命中后核查结论的回流**，误报规则长期不下线，规则库只增不减。
- "连续开药"这类场景本身是正常诊疗行为，若未区分合法连续诊疗与异常行为，属于规则设计缺陷而非纯粹运维问题。

解决方案：
- **规则分级**：按风险后果分为阻断类（自动拦截 / 暂停结算）、复核类（人工审核）、观察类（仅记录与统计），不同等级走不同通道与不同 SLA。
- **告警收敛三招**：设置去重键（患者 ID + 医生 ID + 规则 ID + 滚动时间窗）做窗口内合并；同主体多规则命中做聚合为一条案件；短时间重复告警做抑制与升级（连续命中次数达阈值才推送）。
- **规则 DSL 化 / 规则中心**：规则参数（阈值、时间窗、次数、排除名单）配置化下发，支持灰度、回滚与版本管理，避免每次调整都发版。
- **规则效果闭环**：统计命中率、误报率、人工复核通过率、案件查处率，定期下线无效规则；对误报原因分类（规则逻辑、数据质量、合法例外）分别处理。
- **例外与白名单机制**：对合法连续诊疗（如同一医生同一病种复诊）、慢性病长处方、特殊疾病备案等建立可维护的例外清单，规则命中前先过白名单。
- **引入模型前置**：在规则引擎之前增加轻量模型或统计特征做粗筛，只有高风险样本才进入 CEP 规则匹配，降低无效计算与无效告警。

**问题（3）：状态膨胀 + 检查点超时导致作业不稳定**

原因分析：
- CEP 规则普遍使用较长的时间窗（分钟级甚至更长），且**键控状态以身份证号 / 医保卡号这类高基数为 key**，单个 key 对应的状态对象多、生命周期长，状态总量持续膨胀。
- 状态未配置 **TTL**，已结束的模式匹配状态与窗口状态无法回收。
- Checkpoint 采用**全量上传**，状态大导致快照传输与提交时间超过配置超时，触发 "Checkpoint expired before completing"，连续失败后作业重启；重启又从初始状态重放，进一步放大负载。
- 关键指标缺失：状态大小、Checkpoint 时长与失败率、GC 时间、反压水位无监控，故障无法定位。

解决方案：
- **状态治理三步**：为所有键控状态配置 TTL 并与业务窗口长度对齐；缩短规则时间窗到业务可接受的最小长度；避免把大对象直接塞入状态，改存标识与必要摘要。
- **增量 Checkpoint**：开启增量快照，只上传变更 keygroup，配合 RocksDB State Backend 与异步增量落盘，显著缩短快照时间。
- **状态后端与资源配置**：大状态场景从 RocksDB 起步，调整 state backend 内存与磁盘配置、增大 TaskManager 内存并调大 `taskmanager.memory` 比例，必要时启用 Paimon / 分层存储做冷热分离。
- **Checkpoint 参数调优**：提高快照间隔与超时时间、启用非对齐检查点（unaligned checkpoint）应对反压场景下的对齐阻塞、配置 tolerable failure 容忍连续失败避免立即重启。
- **反压与倾斜排查**：确认是否由下游写入慢或热点 key 引起，采用异步 IO + 批量写入 + 热点打散 + 两阶段聚合，必要时扩容并行度与 Slot。
- **可观测性建设**：监控状态大小趋势、Checkpoint 时长 / 失败率 / 耗时分布、背压水位、GC 与容器被杀次数，建立阈值告警；同时配置作业重启策略与状态 Savepoint 便于快速恢复。
- 补充：作业重启后应从最近成功的 Checkpoint 恢复，避免从最早位点全量重放造成雪崩。

**问题（4）：Sink 端不满足幂等或事务要求，导致重复消费**

原因分析：
- 下游画像系统为至少一次（At-least-once）语义下的重复消费：Kafka 消费位点提交与业务数据写入**不是原子操作**——若业务写入成功而位点提交失败（或进程在两步之间崩溃），重启后会重复消费同一条消息。
- 典型错误做法：在消费循环里先写库后提交 offset 且不做幂等控制；或采用"先提交 offset 再写库"，则会丢数据。
- 画像系统缺少业务唯一键去重与覆盖策略（应按业务主键 upsert 而非 insert），导致同一结算多条记录并存，画像被污染。

解决方案：
- **端到端精确一次三前提落地**：
  1. 源可重放：Kafka 手动提交位点，位点随 Checkpoint 一并提交，保证故障可从一致位点重放；
  2. 状态与位点对齐：Flink Checkpoint 屏障保证算子状态快照与源位点一致；
  3. Sink 幂等或事务化：画像系统改为**按结算单号 + 医保卡号做主键 upsert**（或加唯一索引 + 冲突更新），使重复写入产生同样结果。
- 对必须严格事务的场景（如写入外部关系型数据库）使用**两阶段提交 Sink**；对 ES 等不支持事务的场景，采用幂等写入 + 下游定期对账去重。
- **对账兜底**：建立实时平台与画像系统的定期对账任务，发现重复与缺失自动修复。
- 明确区分"消息重复"与"业务重复"：消息层可去重，业务层仍需幂等设计，二者不可互相替代。

**问题（5）：维表关联方式与数据倾斜问题**

原因分析：
- "每 10 分钟才刷新"：TOP10 榜单走了批量刷新或小时间窗聚合链路，而非实时增量更新；也可能是聚合结果写 Doris 时未采用流式写入，导致刷新周期被拉长。
- "同时出现两个不同排名"：**维表关联错乱**。若采用 Flink CDC 维表 changelog 流但关联时直接取"最新值"而非按事件时间取对应版本，药品规格、剂型、院区等维度的历史版本会与事实错配，同一药品在不同结算单上被关联到不同维度，产生重复分组。
- 也可能是**双流 join 未做状态 TTL**导致同一药品的旧版本与新版本同时保留在状态中，聚合时同一药品被拆成两个分组；或**数据倾斜**（爆款药品占据绝大部分流量）导致部分聚合延迟，榜单刷新滞后。
- 与业务库不一致：实时侧统计口径（是否含退费、是否按医保支付额、是否按结算日）与业务库口径不同。

解决方案：
- **维表版本化关联**：维表变更以 changelog 流接入，按**事件时间取对应维表版本**（lookup 时带版本时间戳），保证任意时点事实关联到当时有效的维度数据。
- **状态 TTL 收敛**：双流 join 与维表缓存均设置 TTL，过期维表版本及时淘汰，避免历史版本滞留造成重复分组。
- **写入方式改造**：Doris / StarRocks 侧采用 **Stream Load / Routine Load 流式写入**并按主键聚合模型（Unique Key / Aggregate Key）实时 upsert，避免定时批量覆盖导致 10 分钟延迟。
- **倾斜治理**：对爆款药品、头部机构做两阶段聚合（加盐打散后合并）或单独打标旁路处理；小维表（药品目录、科室）用广播状态，读取最快。
- **口径统一**：明确 TOP10 统计口径——是否含退费冲正、按结算日还是开单日、金额取医保支付额还是全口径；把口径写入指标字典并与业务库统计脚本对齐。
- **双跑校验**：榜单类结果同样纳入实时与离线双跑对账，差异超阈值告警。

**问题（6）：两条链路的验收方法**

指标一致性验收：
- 建立**双跑对比机制**：选取核心指标（当日基金支出、结算笔数、TOP10 榜单、异常检出数）在离线与实时两侧并行计算，按日（必要时按小时）比对，设定容差（建议金额类 0.1%、计数类 0.5%）。
- 建立**指标字典与口径卡**：每个指标登记统计口径、时间周期、数据范围、计算逻辑、责任人、来源表与血缘关系，作为对账争议的唯一裁决依据。
- 建立**差异归因流程**：差异超阈值时自动下钻到明细，按维度（日期、机构、药品、结算类型）定位差异来源，区分口径差、迟到差、维表差与缺陷。
- 建立**关键报表人工抽样复核**：每日抽取若干笔结算做端到端穿透核对（源系统 → Binlog → Kafka → Flink → 结果库 → 大屏）。
- 验收结论需给出连续多日（建议 ≥ 15 个自然日，含月末与月初）的稳定性达标数据，而非单日抽样。

精确一次语义验收：
- **故障注入测试**：在 Flink 作业处理过程中 kill -9 TaskManager、断开 Kafka Broker、重启下游数据库、制造反压与网络分区，验证任务能自动恢复且结果无重复无丢失。
- **位点与状态一致性核查**：确认故障恢复后 source 位点与算子状态一致（对比 Checkpoint 中记录的位点与实际恢复位点）。
- **端到端唯一性校验**：以结算单号（业务主键）为键，对实时结果库做唯一性约束与重复计数校验，重复数必须为 0；对画像系统做同样的唯一性核查。
- **重复注入测试**：人为向 Kafka 重复投递相同业务事件，验证结果库因幂等设计不产生重复记录。
- **Sink 事务性验证**：检查 Sink 写入是否支持两阶段提交或幂等 upsert；关闭自动提交位点确认位点提交时机与数据写入的原子性设计。
- **对账兜底机制验证**：模拟下游数据缺失与重复，验证对账任务能发现并自动修复，且修复记录可追溯。

**踩分要点**：

问题（1）
- 答"使用事件时间（Event Time）而非处理时间（Processing Time），窗口按业务发生日切分"得 2 分
- 答"设置 Watermark / 允许迟到（allowed lateness），迟到数据走侧输出或修正通道"得 2 分
- 答"凌晨批量入库导致按处理时间归属错日，与差异集中在 8:00 前现象吻合"得 1 分
- 答"统一跨日结算 / 退费冲正 / 基金与个人自付分摊等财务口径"得 1 分
- 答"建立离线与实时双跑对账并设容差阈值"得 2 分
- 只答"改用事件时间"而缺少迟到处理与对账，最多 2 分
- 答"回退离线方案"或"实时方案不适合实时财务统计"为错误方向，扣分

问题（2）
- 答"规则分级（阻断 / 复核 / 观察）"得 2 分
- 答"同主体同规则在滚动时间窗内去重合并 / 告警聚合与抑制"得 2 分
- 答"规则参数配置化（规则中心），避免硬编码与频繁发版"得 1 分
- 答"建立规则效果评估与误报下线机制、核查结论回流闭环"得 2 分
- 答"白名单 / 合法例外场景（同一医生同一病种复诊）处理"得 1 分
- 答"模型前置粗筛降低无效匹配"得 1 分
- 混淆"限流"与"告警收敛"不得分；只答"加机器提升处理能力"为治标，扣分

问题（3）
- 答"键控状态键基数过高（身份证 / 卡号）+ 窗口过长 + 无 TTL 造成状态膨胀"得 3 分
- 答"开启增量 Checkpoint + RocksDB State Backend"得 2 分
- 答"调优 Checkpoint 超时与间隔、启用非对齐检查点、容忍连续失败"得 2 分
- 答"配置状态 TTL、缩短窗口、状态对象瘦身"得 2 分
- 答"建立状态大小 / Checkpoint 时长 / 反压 / GC 的监控告警"得 1 分
- 答"作业重启从最近成功 Checkpoint 恢复"得 1 分
- 只答"加内存、加机器"而无状态治理，不得分

问题（4）
- 答"至少一次语义 + 位点提交与业务写入非原子导致重复消费"得 2 分
- 答"端到端精确一次三前提：源可重放、状态与位点对齐、Sink 幂等或两阶段提交"得 3 分
- 答"下游按业务主键 upsert / 唯一索引幂等写入"得 2 分
- 答"实时与下游定期对账去重"得 1 分
- 答"消息层去重不能替代业务层幂等"得 1 分
- 答"直接关掉重试 / 关掉幂等校验以消除重复"为错误方案，扣分

问题（5）
- 答"维表关联未按事件时间取版本（直接取最新值）导致关联错乱，出现重复分组"得 3 分
- 答"双流 join 与维表缓存未设 TTL，旧版本滞留"得 2 分
- 答"改用流式写入 + 主键聚合模型实时 upsert，解决 10 分钟刷新延迟"得 2 分
- 答"爆款药品数据倾斜治理（加盐 + 两阶段聚合 / 广播小维表）"得 1 分
- 答"统一统计口径（是否含退费、按结算日、金额口径）并与业务库对齐 + 双跑对账"得 2 分
- 只答"加个定时任务刷新"不得分

问题（6）
- 指标一致性验收：答"离线与实时双跑 + 容差阈值 + 指标字典口径卡 + 差异归因下钻 + 连续多日稳定性数据"得 3 分
- 精确一次验收：答"故障注入测试（kill 进程 / 断 Broker / 断连数据库）+ 位点状态一致性核查 + 业务主键唯一性校验 + 重复消息注入测试 + Sink 事务性验证 + 对账兜底"得 4 分
- 仅写"人工检查日志无 ERROR"或"上线观察一周无异常"得分极低

**常考陷阱**：
1. 认为"用了 Flink 就是流批一体" —— 忽略湖仓底座与双引擎口径统一，批侧仍用另一套逻辑，指标必然打架
2. 认为"Watermark 设置得越大越准" —— 越大延迟越高、状态驻留越久，必须与业务 SLA 一起权衡
3. 认为"只要有 Checkpoint 就不会重复" —— Checkpoint 只解决状态恢复，Sink 不幂等照样重复
4. 认为"CEP 能替代规则引擎" —— CEP 解决时间窗模式识别，业务决策仍需规则引擎与模型配合
5. 认为"告警越多越安全" —— 告警风暴会导致真实风险被淹没，是可用性风险而非安全收益

## 记忆口诀

**引擎选型口诀**
真流批一体选 Flink，SQL 生态复用选 Spark；已有 Kafka 用 Streams，老牌 Storm 别新用。

**时间语义口诀**
事件时间定口径，处理时间不重现；Watermark 定进度，迟到走侧输出；三窗滚动滑会话。

**CEP 模式口诀**
类型定事件，顺序定连续，within 定时限，量词定几次；notFollowedBy 定否定，NFA 维护半状态。

**状态容错口诀**
键控状态管并行，算子状态管广播；TTL 管收敛，增量快照管体积；反压查下游，倾斜加盐打散。

**精确一次口诀**
源要能重放，状态位点齐，Sink 要幂等；三者齐备才 EOS，两阶段提交保原子。

**告警治理口诀**
规则要分级，同类要合并，例外挂白名单；命中要回流，误报要下线。

**实时数仓口诀**
CDC 进 ODS，明细进 DWD，主题出 DWS，应用看 ADS；维表按版本取，倾斜两阶段。

**实时化四板斧**
事件时间保证口径，幂等 Sink 保证不重，状态收敛保证稳定，双跑校验保证一致。

**一句话总纲**
实时链路三大风险：**口径错、语义松、状态胖**；对策分别是事件时间 + 双跑校验、幂等 + 两阶段提交、TTL + 增量 Checkpoint。
