## 今日核心概念

### 1. RESTful 设计的六条约束

REST（Representational State Transfer，Roy Fielding 2000 博士论文提出）的六条约束是**架构约束，不是风格指南**——**只要有一条不满足，就不是 REST**。

| 约束 | 内容 | 违反的后果 |
|---|---|---|
| **C1 客户端—服务器** | 分离关注点，客户端不关心服务端实现 | 客户端与服务端强耦合，无法独立演进 |
| **C2 无状态（Stateless）** | **每次请求包含处理该请求所需的全部信息**，服务端不存会话 | 有状态则无法负载均衡、无法水平扩展、故障转移困难 |
| **C3 缓存（Cacheable）** | 响应必须**隐式或显式**标明是否可缓存 | 无法有效利用 HTTP 缓存，网络开销剧增 |
| **C4 统一接口（Uniform Interface）** | 组件间通过标准接口交互，**与实现解耦** | 客户端需了解服务端内部细节，耦合上升 |
| **C5 分层系统（Layered System）** | 组件只感知相邻层 | 无法插入网关、缓存、负载均衡等中间层 |
| **C6 按需代码（Code-on-Demand）**（可选） | 服务端可下发扩展功能 | — |

**关键认知：C2 无状态是微服务架构的技术前提，不是理想。** 一旦服务端保存会话（Session in Memory），就会出现：负载均衡后用户被转到另一节点导致掉线、扩容时新节点没有会话、节点宕机后会话全丢。

**无状态的三种实现方式**：
1. **Cookie 承载**（最简单，但 Cookie 有大小限制 4KB 且有安全风险）
2. **Token 承载**（JWT，最常用）
3. **分布式会话存储**（Redis，严格说这是"有状态但状态外置"，介于两者之间）

**JWT 的三个必知风险**：
- **无法撤销**：签发后在有效期内一直有效，必须配短有效期 + 刷新令牌（Refresh Token）机制
- **无法主动变更内容**：载荷是签名的而非加密的，JWT 里的内容是可读的（Base64 不是加密）
- **密钥泄露即全面失守**：需支持密钥轮换（kid 机制）

### 2. HTTP 方法语义与幂等性

**这是 API 设计最常考、也最容易出错的地方。**

| 方法 | 语义 | 安全（不改变状态） | 幂等 | 典型用途 | 常见误用 |
|---|---|---|---|---|---|
| **GET** | 查询资源 | **是** | **是** | 读取列表/详情 | **用 GET 做删除/提交**（最严重） |
| **POST** | 创建子资源 / 非幂等操作 | 否 | **否** | 创建、复杂查询、提交 | 用 POST 做幂等重试（会重复创建） |
| **PUT** | **整体替换**资源 | 否 | **是** | 全量更新 | 期望部分更新 |
| **PATCH** | **部分更新**资源 | 否 | **是**（设计良好的话） | 局部修改 | 用它做全量替换 |
| **DELETE** | 删除资源 | 否 | **是** | 删除 | 重复调用返回 404 造成误判 |

**关键认知（三条）**：

1. **GET 必须安全（safe）且幂等（idempotent）**。**用 GET 触发"取消订单""付款""删除"，会导致爬虫、浏览器预取、链接预览、代理缓存全部误触发**——这是真实生产事故的高频来源。

2. **幂等不等于相同响应。** 幂等的定义是：**同一请求执行 1 次和执行 N 次，对服务器状态的最终影响相同**。DELETE 第一次返回 204，第二次返回 404，**状态影响相同，仍是幂等的**。很多人在这里理解错。

3. **PUT 与 PATCH 的区别在语义而非技术**：PUT 是"用这个表示替换它"，PATCH 是"用这个文档的部分内容修改它"。**PUT 若带部分字段，语义上是把未提及的字段置空**，这几乎总是 bug。

**幂等键（Idempotency Key）**：对必须幂等的 POST 操作，客户端生成唯一键（UUID），服务端记录键与结果的映射，重复请求直接返回首次结果。**这是支付、下单、消息投递的标配。**

### 3. 状态码的正确使用

| 码 | 含义 | 关键要点 |
|---|---|---|
| **200** | 成功 | **PUT/PATCH 成功用 200（带响应体）** |
| **201** | 已创建 | **必须带 Location 头**指向新资源 |
| **204** | 成功但无内容 | **DELETE 成功用 204** |
| **400** | 请求语法错误 | 语义不对应，用 422 |
| **401** | 未认证 | **"你是谁"**，应配合 `WWW-Authenticate` 头 |
| **403** | 已认证但无权限 | **"你知道是谁，但不让做"** |
| **404** | 资源不存在 | **也用于"故意不告诉你资源是否存在"（防枚举）** |
| **409** | 冲突 | **并发冲突、状态机冲突（如重复取消）** |
| **412 / 428** | 前置条件失败 / 必须带条件头 | **乐观锁的载体**（If-Match） |
| **422** | 语义正确但业务规则不满足 | **校验失败的标准码** |
| **429** | 限流 | **必须带 Retry-After 头** |
| **500** | 服务器内部错误 | **不要在响应体里泄露堆栈** |
| **503** | 服务不可用 | **熔断降级时返回，配合 Retry-After** |

**最常见的三个错误**：
1. **401 与 403 混用**。语义完全不同：401 是"你没证明你是谁"，403 是"我知道你是谁，但你的权限不够"。前端据此决定是跳登录页还是弹无权限提示。
2. **业务失败全用 200 + body 里写 code**。**这会破坏 HTTP 缓存与重试语义**，也让网关、监控、SDK 无法正确处理。**正确做法是业务错误用 4xx/5xx + 统一错误体。**
3. **500 里带堆栈**。**堆栈泄露是信息泄露漏洞**（泄露类路径、框架版本、内部结构）。对外只给错误码和 traceId，堆栈进内部日志。

### 4. API 版本演进策略

**版本策略的选择，本质是在"兼容性成本"和"演进自由"之间做取舍。**

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **URI 版本** | `/v1/users`、`/v2/users` | **直观、易调试、易灰度** | URI 语义污染 | 开放 API、对外服务 |
| **Header 版本** | `Accept: application/vnd.api+json;version=2` | URI 干净 | 调试不直观，工具链支持弱 | 内部服务 |
| **查询参数版本** | `/users?version=2` | 简单 | **不优雅，易被忽略** | 不推荐 |
| **无版本 + 兼容性演进** | 靠字段可选、语义兼容 | **最优雅** | **要求极高，一旦破坏无法挽回** | 内部服务、长期稳定的 API |

**关键认知：版本化的真正目的是"给破坏性变更留出路"。**

**不破坏兼容性的变更（无需升版本）**：
- **新增可选字段**（响应新增字段，客户端应忽略未知字段）
- **新增接口**
- **放宽约束**（原本必须填的字段变可选）
- **新增枚举值**（需谨慎，客户端通常有 switch-case 穷举）

**破坏性变更（必须升版本）**：
- 删除/重命名字段
- 字段类型或含义改变（如把字符串 ID 改成数字）
- **收紧约束**（原本可选变必填）
- **修改状态码语义**
- **改变分页方式或默认排序**

**最阴险的破坏性变更：修改字段的含义。** 比如 `amount` 从"分"改成"元"，字段名类型都没变，**所有旧客户端会静默算错钱**。这类变更必须升版本，且必须通知所有调用方。

**API 版本策略的建议**：
- **对外 API**：URI 版本 + **明确的废弃策略**（公告 → 迁移期 → 下线）
- **内部 API**：**优先"无版本 + 兼容演进"**，用契约测试守住兼容
- **废弃三步法**：① 响应头标记 `Deprecation` 与 `Sunset` 日期 ② 监控各调用方的使用情况 ③ 到期下线
- **最关键的一步是第②步**：**不监控调用方使用情况的废弃，等于突然断供。**

### 5. API 契约驱动开发（Contract First）

**契约优先（Contract-First）** 的核心思想：**先定义接口契约（OpenAPI/Protobuf），再实现服务端与客户端。**

**为什么必须契约优先**：
1. **并行开发**：服务端与客户端可同时开工，不必等一方完成
2. **接口即文档**：契约文件自动生成文档，**不会出现文档与实现不一致**
3. **Mock 驱动**：可基于契约自动生成 Mock，前端不依赖后端进度
4. **兼容性可验证**：见下

**契约测试（Contract Testing）** 的核心机制：
- **消费者驱动契约（Consumer-Driven Contract, CDC）**：**由消费方定义期望，提供方验证**
- 工具：**Pact**（最主流）、Spring Cloud Contract
- **提供方在 CI 中跑消费者契约测试**，任何破坏兼容的改动会**立即导致构建失败**

**关键认知：契约测试是"兼容性的自动化守卫"。** 没有它，"不要破坏兼容性"只是一句口号，靠人 review 必然漏。

**OpenAPI 与 Protobuf 的选型**：

| 维度 | OpenAPI（REST） | Protobuf（gRPC） |
|---|---|---|
| 描述语言 | JSON/YAML，**人可读** | 二进制，**人不可读** |
| 传输 | HTTP/1.1、HTTP/2 | HTTP/2 |
| 调试 | 浏览器、curl 直接调 | 需 grpcurl 工具 |
| 浏览器支持 | **原生支持** | 需 gRPC-Web 代理 |
| 性能 | 一般 | **高（二进制 + 长连接）** |
| 适用 | **对外 API、浏览器端** | **内部服务间调用** |

**常见错误：对内对外都用 gRPC**。内部服务用 gRPC 完全合理，**但对外必须提供 REST/JSON 端点**，否则浏览器、第三方、开放平台接入全部受阻。**这正是 API 网关的核心职责之一——协议转换。**

### 6. 接口治理：限流、熔断、降级、超时、重试

**这五个是服务韧性设计的核心，必须理解它们的分工与配合。**

| 机制 | 解决的问题 | 作用位置 | 关键参数 |
|---|---|---|---|
| **超时（Timeout）** | **调用方无限等待** | 客户端/服务端 | **连接超时、读取超时** |
| **限流（Rate Limiting）** | **流量超过承载能力** | 网关/服务入口 | QPS、并发数 |
| **熔断（Circuit Breaking）** | **下游已经挂了还在打** | 调用方 | 失败率阈值、熔断时长 |
| **降级（Degradation）** | **资源不足时保证核心功能** | 各层 | 兜底数据、功能开关 |
| **重试（Retry）** | **瞬时故障自愈** | 调用方 | 次数、退避策略、幂等性 |

**最关键的认知：五者的执行顺序不能乱。**

**正确的调用链保护顺序**：
```
请求进入 → 限流（超出直接拒绝，不进业务）→ 调用下游
                                          ↓
                              设置超时（必须有，兜底）
                                          ↓
                              调用失败 → 熔断器判断
                                          ↓
                    熔断打开 → 快速失败 + 触发降级（返回兜底）
                                          ↓
                    未熔断 → 有限次重试（指数退避 + 抖动）
                                          ↓
                              重试仍失败 → 返回降级结果
```

**三个必须讲清的技术点**：

1. **超时是所有其他机制的前提。** **没有超时，重试会雪崩，熔断永远不会触发（因为请求都卡着，不返回就统计不到失败）**。**熔断依赖失败率统计，而超时是让请求"失败"而非"挂着"的唯一手段。** 这是最高频的考点。

2. **重试必须配指数退避 + 抖动（Exponential Backoff with Jitter）**。固定间隔重试会在下游恢复瞬间形成**同步重试风暴**。抖动是必需的，不是可选的。

3. **重试必须保证幂等**。**对非幂等操作重试 = 重复下单、重复扣款。** 这就是幂等键存在的意义。

**限流算法**：

| 算法 | 特点 | 适用 |
|---|---|---|
| **固定窗口计数器** | 实现最简单 | 允许突发的场景 |
| **滑动窗口日志** | 精确，**内存开销大** | 精确限流 |
| **滑动窗口计数器** | 折中，**工业界主流** | 通用 |
| **漏桶（Leaky Bucket）** | **强制平滑输出**，不允许突发 | 保护下游 |
| **令牌桶（Token Bucket）** | **允许一定突发**，**最常用** | API 网关 |

**关键区别**：**令牌桶允许攒令牌后一次放行（突发），漏桶强制匀速出水（平滑）**。**保护下游服务用漏桶，保护自身入口用令牌桶。**

**熔断器三状态**：
- **Closed（关闭）**：正常放行，统计失败率
- **Open（打开）**：直接失败，快速返回
- **Half-Open（半开）**：**放少量请求试探**，成功则关闭，失败则重新打开

**Half-Open 状态是最容易被忽略的**——没有它，熔断器打开后只能靠定时器恢复，**恢复是盲的**；有了它，恢复是**被验证过的**。

### 7. API 网关的职责边界

| 职责 | 说明 | 是否适合放在网关 |
|---|---|---|
| **路由与转发** | 按路径/规则分发 | 适合 |
| **认证鉴权** | 统一认证、Token 校验 | 适合 |
| **限流熔断** | 统一入口管控 | 适合 |
| **协议转换** | REST 与 gRPC 互转 | 适合 |
| **接口聚合** | 聚合多个后端为一个接口（BFF） | 适合 |
| **业务逻辑** | 复杂的业务规则处理 | **不适合** |
| **数据库访问** | 直接读写业务库 | **绝对不适合** |

**关键认知：网关是"边缘关注点"（Edge Concerns）的集中地，不是业务逻辑的堆放地。** 业务逻辑下沉到服务，**网关一旦承载业务，就会变成新的巨石**，且每次业务变更都要动网关，所有服务一起发布。

**BFF（Backend for Frontend）模式**：为不同前端（Web、App、小程序）分别建后端层，各自聚合所需接口。好处是各端点的接口形状可以按端优化，不必强求统一。代价是 BFF 数量增加、逻辑可能重复。

## 三个常考陷阱

### 陷阱一：认为"加了 API 网关就不用管服务内部的限流熔断"

**错。** 网关只能做**入口侧**的管控，**服务之间的调用（东西向流量）完全绕不过网关**。

真实链路：网关 → 订单服务 → 库存服务 → 支付服务。**订单服务调用库存服务时的熔断，网关管不了。** 每一个可能发起调用的服务都必须自己做超时与熔断。

**另一个更隐蔽的问题：网关自身的限流阈值是全局的，而某个下游服务的实际承载能力是局部的。** 全局阈值必须按各下游的服务能力**分配配额**，否则会出现"网关总流量没超，但库存服务已经被打垮"。

### 陷阱二：把"返回 200 + body 里写错误码"当成接口设计

**错，破坏了三层语义。**

1. **破坏 HTTP 缓存**：GET 返回 200 会被缓存，包括错误响应
2. **破坏重试语义**：客户端 SDK 通常按状态码判断是否重试，**5xx 会重试、200 不会**，但实际上错误也需要重试
3. **破坏可观测性**：网关、APM、监控按状态码统计，**所有错误都算成功，可用性指标完全失真**

**正确做法**：**业务错误用 4xx/5xx 表达，配合统一错误响应体**：

```json
{
  "code": "ORDER_ALREADY_PAID",
  "message": "该订单已完成支付",
  "traceId": "abc123...",
  "timestamp": "2026-10-27T10:00:00+08:00"
}
```

**注意 code 用业务码而 message 用人类可读文案**——客户端按 code 判断，界面显示 message。

### 陷阱三：认为"版本化是接口设计的万金油"

**错，且会掩盖真正的设计问题。**

**滥用版本化的后果**：
1. **版本碎片化**：v1/v2/v3 并存，**维护成本指数上升**，且**没人敢删老版本**
2. **逃避设计**：**该好好设计的接口用"再加个版本"糊弄**，结果两个版本的语义都不清晰
3. **客户端懒升级**：老版本长期不弃用，**新特性无法统一推广**

**正确原则**：
- **能兼容演进就不升版本**（新增可选字段是最常见的合法演进）
- **升版本前先问**：这个变更真的破坏兼容吗？能不能用"新增字段 + 保留旧字段"实现？
- **版本要有生命周期**：每个版本都要有明确的废弃时间表，**没有下线计划的版本等于永久负担**

### 陷阱四：以为"重试能解决所有下游问题"

**错，重试是把双刃剑。**

**重试的四种危害**：
1. **放大流量**：下游已经过载，重试让流量变成 2 倍、4 倍，**直接把"有点慢"变成"彻底挂"**
2. **掩盖真问题**：下游持续性故障（如参数错误、契约不匹配）时重试 100 次也修不好，**只是延迟了暴露时间**
3. **破坏幂等**：对非幂等操作重试 = 重复扣款/重复下单
4. **耗尽上游资源**：**重试占用的线程、连接不会被释放**，上游自己也会被拖垮

**重试的适用前提（四条全满足才重试）**：
1. **操作幂等**（或带幂等键）
2. **错误可重试**（网络超时、5xx 可重试；4xx 参数错误、401 认证失败**不可重试**）
3. **有退避与抖动**
4. **有次数上限，且有全局熔断兜底**

**一句话**：**重试解决的是"瞬时故障"，熔断解决的是"持续故障"。对持续故障重试，是把问题放大而不是解决。**

## 案例分析题

### 案例 1 — 某市政务服务平台的 API 治理失效

**题干**：某市政务服务平台由 8 个微服务构成，统一通过 API 网关对外提供接口。上线 8 个月后，运维与业务部门反馈了大量问题。

**接口与版本状况**：
- 对外开放 3 个版本：v1（原始申报）、v1.1（新增 2 个可选字段）、v2（材料项从 12 项减至 6 项）
- **v1 至今仍有 12 个第三方系统调用**，其中 3 个是市民服务 App
- v2 上线 7 个月，**仅有 2 个调用方**，且这两个调用方同时还在调用 v1 的部分接口
- 平台的 OpenAPI 文档**更新于 v2 上线前，此后未再修改**

**运行状况**：
- 网关配置限流：**全局 QPS 2000**，无按服务分配配额
- 报告服务（调用库存服务、档案服务、第三方短信服务）在**每日上午 9:30 准时出现 3 分钟超时**
- 平台运维查监控发现：**网关入口 QPS 峰值为 1800（未超限）**，**报告服务自身 CPU 峰值 42%**
- 排查发现：报告服务的 P99 响应时间为 **8.2 秒**，而其三个下游的 P99 分别为 0.4 秒、0.3 秒、**7.9 秒**
- 团队在调用档案服务时**配置了 500ms 超时 + 3 次重试（固定间隔 200ms）**；调用短信服务**未配置超时**
- 一次故障复盘：上午 9:30 短信服务响应变慢时，报告服务因未设超时而**线程池在 5 分钟内被占满**，导致**报告服务完全不可用**，且**重试机制把档案服务的正常请求也拖垮**（档案服务 P99 从 0.4 秒涨到 3.1 秒）

**团队争论焦点**：架构师 A 认为"应该给每个下游配置独立熔断器和独立限流配额"；架构师 B 认为"网关统一限流就够了，重试应该改成指数退避加抖动"；架构师 C 认为"根本问题是第三方短信服务不可控，应该直接去掉短信功能"。

**问题**：
1. 指出该平台在 API 设计与治理上的六个具体问题，并分析根因与影响。
2. 逐条评价 A、B、C 三位架构师的观点。
3. 设计该平台的接口版本与废弃策略，以及针对报告服务的韧性改造方案。

**参考答案**：

### 问题 1 — 六个问题、根因与影响

| 问题 | 表现 | 根因 | 影响 |
|---|---|---|---|
| **1. 版本策略失效，多版本长期并存** | v1、v1.1、v2 三版本共存 7 个月，v2 几乎无人用 | **未区分"兼容演进"与"破坏性变更"**：v1.1（新增可选字段）本应作为 v1 的兼容演进而非新版本；v2（材料项从 12 减到 6）本可通过"**废弃字段保留 + 新增字段 + 服务端按新逻辑校验**"逐步实现，而非整体另起版本。更根本的问题是缺少版本生命周期管理机制。 | **维护成本上升**（同一业务逻辑三套代码）；**新特性无法统一推广**（v2 的 6 项材料优化对 12 个调用方中的 11 个无效）；**网关路由与鉴权逻辑复杂度上升** |
| **2. 未做废弃管理，老版本无法下线** | v1 有 12 个调用方，无人推动迁移 | **缺少"废弃三步法"**，尤其是**缺少调用方使用情况监控**——不知道谁在用、用多少、迁移难度多大。更关键的是：第三方系统不在本单位控制范围内，迁移需要协调成本，若无倒逼机制就永远不会迁。 | **技术债永久化**；**安全漏洞修复必须同时修三个版本**（v1 至今仍在被调用） |
| **3. 文档与实现脱节** | OpenAPI 文档停留在 v2 上线前 | **契约未作为开发的强制输入**，而是事后补的"文档"。**文档不来自契约，就一定与实现脱节。** | **第三方接入方按旧文档开发，集成失败**；**接口变更无预警** |
| **4. 网关统一限流无下游配额** | 全局 QPS 2000，入口峰值 1800 未超限，但下游已过载 | **限流阈值是全局的，而服务承载能力是局部的。** 1800 QPS 中**报告服务占比可能只有 200，其余 1600 冲击的是其他服务**——**全局不超限，不代表任何一个下游不超限**。**这是"限流粒度错误"，不是"限流没做"。** | **局部过载**（报告服务被非关键请求挤占）；**故障扩散**；**无法做容量隔离** |
| **5. 客户端侧防护缺失** | 短信服务未配超时；档案服务用 500ms 超时 + 固定间隔重试 | **两个方向都错**：①**无超时**——请求无限等待，**线程被长期占用**，这是 5 分钟内线程池占满的直接原因；②**超时设置不合理**——档案服务 P99 是 0.4 秒，设 500ms 意味着**正常波动就会被判失败**（P99 之外的 1% 请求被误杀），**触发无意义重试**；③**固定间隔重试**——失败时形成同步重试，且**无抖动** | **线程池耗尽 → 服务完全不可用**；**重试放大流量 → 拖垮正常下游**（档案服务 P99 从 0.4 秒涨到 3.1 秒）；**这是典型的级联故障** |
| **6. 缺少契约驱动与兼容性守卫** | 无契约测试；v1 至今被调用说明"改接口"没人拦 | **无 OpenAPI 契约作为开发输入**，**无消费者驱动契约测试（Pact）**。**"不要破坏兼容性"仅靠人 review，必然漏。** | **破坏性变更可能直接上线**；**v1 长期存在正是这个机制的缺失结果** |

**贯穿性根因**：**该平台的 API 治理停留在"网关配置 + 文档编写"的工具层面，没有建立"契约定义 → 契约验证 → 版本生命周期 → 废弃倒逼"的完整治理链条；同时客户端侧的韧性防护（超时/熔断/退避）被完全忽略，把风险全部推给下游。**

### 问题 2 — 评价三位架构师

**架构师 A（"给每个下游配置独立熔断器和独立限流配额"）：**
**结论：方向正确，但表述不完整，且优先级排序有误。**

- **正确的部分**：①**独立熔断器**是必须的——**熔断器必须是"每个被调用关系"一个，而不是"每个服务"一个**。因为不同下游的可靠性与容量不同，档案服务挂了不应影响短信服务的调用。②**独立限流配额**正确识别了问题的本质：**全局限流不能替代按下游的容量分配**。
- **不完整的部分**：**A 漏掉了最根本的一步——超时**。**没有超时，熔断器永远不会正确触发**（请求挂着不返回，失败率统计不到）。**先设超时，再设熔断，最后才是限流配额。**
- **优先级问题**：A 直接跳到熔断和限流，**跳过了"去掉无谓重试"和"修正错误超时值"这两件成本最低、见效最快的事**。

**架构师 B（"网关统一限流就够了，重试改指数退避加抖动"）：**
**结论：部分正确，但有一个明确的错误。**

- **正确的部分**：**重试改指数退避 + 抖动是完全正确的**，且这是本次故障放大链的直接原因。**固定间隔重试在失败时形成同步重试风暴，而抖动是打破同步的必要手段。**
- **明确错误**：**"网关统一限流就够了"是错的。** 网关只能管**南北向**（外部进内部），**东西向流量（服务间调用）绕不过网关**。报告服务调档案、短信服务**完全在网关管辖之外**。**恰恰是这次故障中拖垮档案服务的那股重试流量，是网关管不到的。**
- **B 也漏了超时**：没有超时，重试机制本身就不安全——**请求挂住时重试逻辑根本不会被触发，反而线程先被占满**。

**架构师 C（"第三方短信服务不可控，应该直接去掉短信功能"）：**
**结论：不可接受，属于用回避问题的方式解决不擅长的问题。**

- **逻辑错误**：短信服务不可控是**客观事实**，但这正是**韧性设计要处理的核心场景**，不是删除功能的理由。去掉短信等于放弃业务能力，且**短信是政务场景的法定通知渠道**（办件结果通知、到期提醒），去掉会直接引发合规问题。
- **混淆了"消除依赖"与"管控依赖"**：**在分布式系统中，消除外部依赖通常不可行**（第三方支付、短信、实名认证、地图服务都是刚需）。**工程界的正确姿势是"降级"而非"删除"**：短信发不出时，**通知降级为"站内消息 + 办件状态页展示 + 到期未读提醒"**，**核心业务（提交、查询、流转）不受影响**。
- **C 的方案有严重副作用**：去掉短信后，**办件结果通知的送达率要求无法满足**，且**用户不知情会引发投诉**。**这是把一个技术问题升级为业务与合规问题。**

**综合结论与正确优先级**：

```
第 1 优先（立即，成本最低）：
  ① 所有外部调用必须设超时（档案服务超时从 500ms 改为 P99 的 2~3 倍，如 1.5s）
  ② 短信服务补上超时（按其 P99 历史值设定）
  ③ 去掉固定间隔重试，改为指数退避 + 抖动，且仅对 5xx/超时重试
第 2 优先（本周）：
  ④ 按下游加独立熔断器（每个被调用关系一个）
  ⑤ 网关按下游分配限流配额，报告服务独立配额
  ⑥ 对非关键下游做降级（短信降级为站内消息）
第 3 优先（两周内）：
  ⑦ 全面做调用链梳理，形成《外部依赖清单》，每个依赖标注：是否关键、超时值、熔断策略、降级方案
第 4 优先（一个月内）：
  ⑧ API 版本生命周期治理 + 契约测试
```

**一句话**：**A 说对了方向但跳过了前提，B 说对了一半但断言错了，C 回避了问题。真正的答案是"先超时、再熔断、后退避、最后降级"，且这四件事一条都不能少。**

### 问题 3 — 接口版本与废弃策略 + 报告服务韧性改造方案

#### 3.1 API 版本与废弃策略

**第一步：立即冻结版本扩散**

- **暂停新增 API 版本**（新需求一律在当前主版本上以兼容方式实现）
- **对 v1.1 做回溯判定**：v1.1 只是新增了 2 个可选字段，**属于完全兼容的变更**。**应将 v1.1 合并回 v1**（v1.1 的接口即 v1 接口的当前形态），**下线 v1.1 这个版本标签**，**从三个版本减为两个**。这一步零成本、立即见效。
- **对 v2 做保留判定**：材料项从 12 减到 6 是**破坏性变更**（响应结构删字段），**保留 v2 独立版本是合理的**。

**第二步：把版本演进规则写进规范（防止再犯）**

| 变更类型 | 处理方式 | 是否升版本 |
|---|---|---|
| 新增可选字段（响应） | 直接在当前版本实现，**客户端须忽略未知字段** | **否** |
| 新增接口 | 直接新增 | **否** |
| 放宽约束（必填变可选） | 直接调整 | **否** |
| 新增枚举值 | 直接新增，**但须提前公告且客户端做兜底** | **否（谨慎）** |
| 删除/重命名字段 | 保留旧字段（标记 deprecated）+ 新增新字段，**双写一个过渡周期** | **是** |
| 字段类型或含义改变 | 只能升版本 | **是** |
| 收紧约束 | 只能升版本 | **是** |
| **修改字段含义（如单位变更）** | **只能升版本，且必须书面通知所有调用方** | **是（最严格）** |

**第三步：对 v1 制定强制废弃计划（带倒逼机制）**

**这是本题的关键——"没有倒逼机制的废弃等于没有废弃"。**

1. **明确时间表**：
   - T+0（方案批准后 1 个月内）：响应头加 `Deprecation: true` 与 `Sunset: <v1 下线日期>`
   - T+0 起：**v1 与 v2 双跑**，v1 维护**只修致命缺陷，不加新功能**
   - T+3 个月：v1 进入"**仅应急维护**"
   - T+6 个月：**v1 下线**
2. **建立调用方使用监控（倒逼的技术基础）**：
   - 网关按 **调用方 AppID + 接口 + 时间窗** 统计调用量，**形成《v1 调用方活跃度报表》**
   - 每周自动推送：**"您正在使用将于 X 日下线的 v1 接口，当前调用量 Y 次/日，请于 Z 日前完成迁移"**
   - **报表同时推送给对方单位的信息化负责人**（不只是技术对接人）——**这一招能显著提升迁移响应速度**
3. **提供迁移降低成本的工具**（**推动迁移的最好方式是让迁移比不迁移更省事**）：
   - 提供**一键迁移指引文档 + 字段差异对照表**
   - 对调用量小的调用方，**由平台团队主动代为改造**（补贴式迁移）
   - 考虑**在网关侧为 v1 调用方做协议适配**，把 v1 请求转成 v2 内部调用，**让调用方无感完成迁移**。**这是本案例最有效的招：迁移成本从调用方转移到平台方，平台方有动力做得更好。**
4. **设置"最后手段"**：
   - v1 下线前 1 个月，若仍有调用方未迁移，**由市局信息中心发正式函件**要求限期迁移
   - **明确"下线例外"的审批权归局领导**，避免逐个求情

**第四步：把契约纳入开发流程（防止再出现新版本失控）**

- **接口定义统一以 OpenAPI 3.0 文件为准**，该文件是**代码仓库中的受控资产**，走 Code Review
- **CI 中加入契约校验**：后端实现与 OpenAPI 不一致时**构建失败**
- **引入消费者驱动契约测试（Pact）**：每个消费方定义期望契约，提供方在 CI 中验证，**破坏兼容的改动直接被拦截**
- **所有内部服务的接口变更必须先改契约文件**，再改实现

#### 3.2 报告服务韧性改造方案

**改造原则：先消除放大机制，再建立隔离，最后才是降级兜底。**

**第一层：修正客户端调用配置（立即执行，1 天内）**

| 下游 | 现状 | 改造后 | 理由 |
|---|---|---|---|
| **档案服务** | 超时 500ms，固定间隔重试 3 次 | **超时 1.5s**（约为其 P99 的 3 倍）；**重试 2 次，指数退避 200ms 到 400ms + 抖动 ±50%**；**仅对连接失败/超时/5xx 重试** | 原 500ms 超时会把 P99 之外的 1% 正常请求误判为失败，触发无意义重试 |
| **短信服务** | **无超时** | **超时 3s**（第三方 P99 通常远高于内部服务）；**重试 2 次，指数退避 500ms 到 1s + 抖动**；**熔断阈值：失败率 > 50% 持续 30 秒则熔断，熔断 60 秒后半开试探** | 无超时是线程池占满的直接原因 |
| **库存服务** | 未提及 | **超时 1s，熔断失败率 50%/30s** | P99 0.4s，余量充足 |
| **新增：所有调用统一使用 OpenTelemetry SDK** | — | **埋点 + TraceId 贯穿**，**每次调用记录耗时、结果、重试次数** | 没有数据就没法定超时值 |

**第二层：为每个下游配置独立熔断器（3 天内）**

**熔断器配置要点**：
- **每个"被调用关系"一个独立熔断器**（报告服务调档案一个，调短信一个）
- **熔断打开时**：**快速失败 + 立即走降级**，不要等重试
- **Half-Open 状态必须实现**：熔断 60 秒后半开放 5% 流量试探，**成功则关闭，失败则重新打开并延长熔断时长**（指数退避）
- **熔断必须配监控指标**：熔断打开次数、打开时长、Half-Open 成功率

**第三层：网关按下游分配限流配额（1 周内）**

- **废弃单一的全局 QPS 2000**，改为**按下游服务的实际承载能力分配配额**
- **报告服务**独立配额，按其压测容量设定（**并预留早高峰冗余**）
- **关键路径与非关键路径分离**：报告服务为**非关键路径**（超时只是报告延迟，不影响办件提交），**应给予独立的、较低但明确的配额**，**绝不能与非关键路径共享配额导致被挤占**
- **配额使用 Token 桶**（允许一定突发），**下游保护用漏桶**（强制平滑）
- **超限返回 429 + Retry-After**，不排队

**第四层：建立降级方案（1 周内）**

| 下游 | 降级策略 | 用户感知 |
|---|---|---|
| **短信服务** | 降级为"站内消息 + 办件状态页展示 + 到期未读提醒" | **办件结果仍可查，仅通知方式变化**（可接受） |
| **档案服务** | 降级为"返回最近一次缓存的档案快照 + 标记'数据截至 X 时'" | **有轻微延迟，但功能可用** |
| **库存服务** | 降级为"提示库存系统维护中，请稍后重试" | **可直接重试**（库存查询是强一致的，不宜给假数据） |

**降级的关键原则**：**降级必须返回"标识清楚的降级结果"，绝不能返回看似正常的假数据。** 政务系统里"看起来正常但实际是默认值的数据"，比明确报错危害大得多。

**第五层：建立外部依赖清单与持续治理（2 周内）**

- **《外部依赖清单》**：逐条列出所有外部依赖，标注：**是否关键业务、超时值、熔断策略、降级方案、责任联系人、供应商 SLA**

## 记忆口诀

- 口诀 1：**REST 六约束**——客户分离、无状态、可缓存、统一接口、分层、按需代码。**缺一条就不是 REST。**
- 口诀 2：**无状态是前提不是理想**——服务端存 Session 就没法水平扩展。
- 口诀 3：**JWT 三坑**——不能撤销、内容可读、密钥轮换。
- 口诀 4：**GET 必须安全幂等**——用 GET 干删除，爬虫预取全误触发。
- 口诀 5：**幂等看状态不看响应**——DELETE 二次返回 404，仍是幂等。
- 口诀 6：**PUT 替换、PATCH 局部**——PUT 带部分字段会把其余置空。
- 口诀 7：**401 问身份、403 问权限**——前端据此跳登录还是弹无权限。
- 口诀 8：**别用 200 装错误**——破坏缓存、重试、监控三层语义。
- 口诀 9：**500 别带堆栈**——堆栈是信息泄露漏洞。
- 口诀 10：**版本只为破坏性变更而设**——新增可选字段是合法演进，不升版本。
- 口诀 11：**改含义最阴险**——分改元，旧客户端静默算错钱。
- 口诀 12：**废弃三步**——公告、监控调用方、到期下线。**第二步最关键，不监控等于断供。**
- 口诀 13：**契约先于实现**——OpenAPI 是受控资产，CI 校验不一致就构建失败。
- 口诀 14：**Pact 守兼容**——消费者定期望，提供方验证，破坏兼容直接拦。
- 口诀 15：**超时是一切前提**——没超时，熔断不触发、重试雪崩。**先超时再熔断。**
- 口诀 16：**重试要退避加抖动**——固定间隔会造同步重试风暴。
- 口诀 17：**重试必须幂等**——非幂等重试等于重复扣款。
- 口诀 18：**令牌桶允许突发，漏桶强制平滑**——保护自己用桶，保护下游用漏。
- 口诀 19：**半开状态别省**——没有它，熔断恢复是盲的。
- 口诀 20：**网关管南北不管东西**——服务间调用绕过网关，各自都要熔断。
- 口诀 21：**全局限流管不了局部**——要按下游能力分配配额。
- 口诀 22：**网关不装业务**——装了就是新巨石。
- 口诀 23：**重试治瞬时，熔断治持续**——对持续故障重试是把问题放大。
- 口诀 24：**降级要给降级标识**——假数据比明确报错危害大。
- 口诀 25：**废弃要倒逼**——监控调用方 + 网关代改 + 正式函件，三管齐下。
