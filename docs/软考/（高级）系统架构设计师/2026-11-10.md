## 今日核心概念

### 1. 存储引擎的两条技术路线：B+树与LSM树

定义：存储引擎是数据库中负责数据物理组织、索引维护、并发控制与持久化的核心模块，其技术路线的分歧集中在一个根本矛盾上：**随机读性能与顺序写吞吐之间的取舍**。B+树路线以原地更新换取强随机读性能，LSM树路线以顺序写加后台归并换取高写入吞吐与低成本存储。

关键要点：
- **B+树索引结构**：非叶节点仅存键与指针形成多路平衡树，叶节点串成有序链表。三个决定性性质——树高低（3-4 层即支持千万级到亿级数据）、数据有序、范围扫描高效。范围查询可通过叶链顺序扫描完成，是 B+树相对哈希索引的关键优势。
- **B+树的代价在写**：单条记录的插入或删除可能触发页分裂或页合并，导致随机写与页级争用。InnoDB 采用"聚簇索引 + 变更缓冲"缓解——二级索引的更新先写变更缓冲，在页需要加载时再合并，避免立即随机 IO。
- **LSM树结构**：多层有序的 SSTable（不可变排序表）+ 内存 MemTable + WAL（预写日志）。写入路径为"写 WAL → 写 MemTable → MemTable 满则刷为 SSTable → 后台归并"。写入是纯追加，天然适配顺序存储介质与高吞吐写入场景。
- **LSM树的三项固有代价**：
  - **写放大（Write Amplification）**：一次用户写入被放大为多次物理写（MemTable 刷盘、层级归并、重写），通常放大系数在 10 至 50 之间。
  - **读放大（Read Amplification）**：一次查询可能需要查询多层，需检查 Bloom Filter、块缓存与布隆过滤器后才能确定数据在哪一层。
  - **空间放大（Space Amplification）**：多层数据未归并完成前存在冗余，空间占用高于逻辑数据量。
- **三大放大系数的相互制约**：增大 MemTable 与块大小可降低写放大，但会增加读放大；增大 Bloom Filter 假阳性率与位数组可降低读放大，但降低写放大效果；布隆过滤器过大会带来缓存压力。工程上的本质是**在三项放大之间寻找可接受的平衡点**，不存在三者同时最优的配置。
- **适用场景判据**：读多写少、需要复杂范围查询与多表关联（OLTP）→ B+树；写多读少、日志与时序类追加写、LSM 天然契合顺序写（OLAP、时序数据库、日志存储）→ LSM树。
- **现代融合路线**：多数新一代数据库采用混合方案——LSM 负责写入路径，另有独立的 B+树索引或读优化结构（如 RocksDB 的 Column Family 与 Block Cache、TiDB 的 RaftTree、ClickHouse 的主表 MergeTree 与跳数索引）。

### 2. MVCC 多版本并发控制与可见性判断

定义：MVCC（Multi-Version Concurrency Control）通过为每行数据保留多个版本，使读操作无需加锁即可读取到符合其事务隔离级别的版本，从而实现"读不阻塞写、写不阻塞读"的并发控制目标；其核心机制是**事务可见性判断**——给定一个事务的快照版本，要确定它应当看到哪一行版本。

关键要点：
- **版本链机制**：每行除业务字段外，隐藏字段包括事务标识（创建该版本的事务号）与回滚指针（指向上一版本）。更新一行时生成新版本，新版本回滚指针指向旧版本，形成按事务号递减排列的版本链。
- **Read View（读视图）判定四要素**：创建 Read View 时记录四个边界——当前活跃事务集合中最小事务号（低水位）、最大事务号（高水位）、创建者自身事务号、活跃事务集合快照。这是可见性判断的全部输入。
- **可见性判定规则**：版本的事务号小于低水位则可见；大于等于高水位则不可见（是未来事务）；落在低水位与高水位之间则需查活跃事务集合，**若该事务仍活跃则不可见（否则会出现脏读）**，若已提交则可见。
- **两种典型实现路径**：
  - **快照读（一致性读）**：通过 Read View 读取某一时刻的一致性快照。MySQL InnoDB 在可重复读隔离级别下，同一事务内的多次快照读共享同一个 Read View；在读已提交隔离级别下，每次快照读都创建新的 Read View，因此能看到期间其他事务已提交的数据。
  - **当前读（最新读）**：读取最新版本，**不通过 Read View**，直接读取最新已提交版本并加锁。更新语句、删除语句、锁定读语句属于当前读。**当前读不走版本链，而是直接在最新版本上操作并加锁**——这是最常被误解的知识点。
- **长事务的危害（必须写进案例）**：一个长事务的 Read View 会阻止旧版本被清理，使版本链不断增长，形成"历史版本堆积"，导致 undo 空间暴涨、查询性能下降、二级索引膨胀。这是生产环境最常见的 MVCC 故障模式。
- **治理手段**：设置事务超时阈值与空闲超时（idle_in_transaction_session_timeout）、限制长查询、监控长事务列表与 undo 空间使用率、定期清理孤儿事务。
- **MVCC 的代价**：多版本共存带来存储开销与清理开销（purge 线程）、读写路径判断复杂度上升，且**MVCC 不解决写写冲突**——写写冲突仍由锁机制处理。

### 3. 事务隔离级别与并发控制机制

定义：事务隔离级别定义并发事务之间的可见性规则，是并发控制与数据正确性之间的权衡旋钮。四种标准隔离级别对应不同的脏读、不可重复读、幻读三类并发异常允许程度。

关键要点：
- **四种隔离级别与异常容忍度（核心记忆表）**：
  - 读未提交：允许脏读、不可重复读、幻读。
  - 读已提交：不允许脏读，允许不可重复读与幻读。
  - 可重复读：不允许脏读与不可重复读，允许幻读（标准定义层面；但 MySQL InnoDB 通过间隙锁在很大程度上避免了幻读）。
  - 可串行化：三类异常全部禁止，等价于串行执行，代价是并发度最低。
- **MySQL 的特殊实现**：InnoDB 在可重复读隔离级别下通过**间隙锁（Gap Lock）**与**next-key lock（记录锁 + 间隙锁）**抑制幻读；快照读不加锁，当前读加锁。因此同一事务中"快照读"与"当前读"可能看到不同数据——这一现象是高频考点，也是实际开发中的困惑来源。
- **锁类型谱系**：
  - **共享锁（S）**与**排他锁（X）**：读读兼容、写写与读写互斥。
  - **意向锁（IS、IX）**：表级标记，用于快速判断表上是否有行锁，避免逐行检查。
  - **记录锁**：锁定索引记录本身。
  - **间隙锁**：锁定索引记录之间的间隙，阻止插入新记录，用于防止幻读。
  - **next-key lock**：记录锁 + 间隙锁的组合，是可重复读下的默认加锁单位。
  - **元数据锁（MDL）**：保护表结构，事务未提交时其他事务的 DDL 会被阻塞。
- **死锁的四个必要条件**：互斥、持有并等待、不可剥夺、循环等待。破坏任一即可预防，而数据库实际采用的是**死锁检测与自动回滚**（代价低但会牺牲一个事务）。
- **死锁排查三步**：查看死锁日志或监控中的死锁记录定位涉及的事务与 SQL → 分析加锁顺序是否一致 → 统一访问顺序或缩短事务、降低隔离级别、加合适索引（**索引缺失会加锁范围扩大，是死锁的重要诱因**）。
- **MVCC 与锁的分工**：读靠 MVCC 免锁，写靠锁互斥，二者配合构成完整的并发控制。

### 4. 查询优化器的代价模型与执行计划

定义：查询优化器是数据库中基于统计信息与代价模型，为查询选择最优执行计划的组件；执行计划是优化器决策的具体体现，包含访问路径、连接顺序、连接算法与物理算子。架构师的职责不是"写好查询"，而是**读懂执行计划、识别错误的代价估算、给出结构性优化方案**。

关键要点：
- **优化器三阶段**：逻辑优化（基于代数法则改写查询，如子查询展开、谓词下推、连接交换）、物理优化（选择具体算子与访问路径）、代价估算（基于统计信息计算各候选计划代价并择小）。
- **代价模型的两类代价**：CPU 代价与 IO 代价。传统系统偏重 IO，现代优化器引入 CPU 代价、内存代价、网络代价与并行度代价；**列存系统（如 ClickHouse）的 IO 代价权重显著低于行存系统**，这是不同数据库优化策略差异的根源。
- **统计信息是优化的地基**：表行数、列直方图、选择率估计、索引统计信息。**统计信息过期是"同样的 SQL 昨天快今天慢"的第一原因**。关键手段是定期收集统计信息（ANALYZE）、对大表与高基数列提高采样精度、对倾斜数据使用直方图而非均匀分布假设。
- **基数估算误差是计划劣化的主因**：估算行数与真实行数相差一个数量级以上时，优化器几乎必然选错连接顺序。识别方法是对比执行计划中的估算行数与实际行数，**偏差超过 10 倍即应视为估算失效**。
- **连接算法选择**：嵌套循环连接（内表被驱动表适合小结果集或索引驱动）、哈希连接（等值连接，适合大表等值连接）、归并连接（需要两侧有序，适合范围连接与排序输出）。**连接顺序与连接算法的组合空间巨大，是优化器搜索的主要目标**。
- **关键执行计划算子与风险信号**：
  - 全表扫描在大表上出现是首要风险信号。
  - 索引扫描的过滤性差（扫描行数远大于返回行数）说明索引选择错误或缺少更优索引。
  - 排序算子出现在大结果集上且未利用索引有序性，说明可优化为索引有序扫描。
  - 临时表或物化算子出现在本应流式处理的查询中，通常是谓词下推失败或连接顺序不当的信号。
- **分页深翻（Deep Pagination）问题**：使用大偏移量的分页查询（OFFSET 100000）需要扫描并丢弃前十万行，代价随页码线性增长。**正确做法是基于游标的键集分页（Keyset Pagination）**，用上一页最后一条记录的主键做游标条件，代价与页码无关。

### 5. 存储引擎性能诊断与慢查询治理

定义：慢查询治理是一套从发现、归因、优化到固化的闭环机制，其核心不是"逐条优化 SQL"，而是**建立分层的可观测体系与结构性的数据访问规范**，把优化成果沉淀为约束。

关键要点：
- **慢查询日志的三个关键配置项**：长查询阈值（决定记录哪些查询）、是否记录未使用索引的查询、采样率。**只按执行时间设阈值会漏掉"执行快但扫描行数巨大"的隐患查询**，因此应同时设置扫描行数阈值。
- **全表扫描的判定不能只看类型**：应结合实际扫描行数与表总行数的比例、小表全扫属正常、超过阈值才是问题。
- **索引使用的四条黄金法则**：
  - 最左前缀原则：复合索引的顺序决定可用性，跳过最左列则无法使用该索引。
  - 避免在索引列上做函数运算与隐式类型转换（索引失效）。
  - 区分度原则：区分度低的列（如性别、状态）单独建索引价值有限，复合索引中应把区分度高的列放在前面。
  - 覆盖索引：用索引本身覆盖查询所需列，避免回表，显著降低 IO。
- **索引的代价必须一并评估**：每个索引都占用存储、拖慢写入、增加优化器搜索空间与选择错误的可能。**索引不是越多越好，需定期清理零使用率索引与重复索引**。
- **治理闭环五步**：发现（慢日志与调用链埋点）→ 归因（区分 SQL 写法、索引缺失、统计信息过期、数据倾斜、硬件瓶颈）→ 优化（改写、增索引、改统计信息、调参数、拆表或分区）→ 固化（写入数据库开发规范并纳入代码评审与上线检查）→ 复测（回归验证并纳入监控看板）。
- **结构性优化优先于语句级优化**：当单表已到亿级且增长持续时，应考虑分库分表、按维度分区、冷热分离、归档策略、读写分离；**语句级优化在数据量跨过量级阈值后收益急剧衰减**。
- **读写分离的一致性陷阱**：主从延迟导致的读己之写不可见、跨分片事务与全局唯一 ID、以及"写后立即读"场景必须路由主库或引入强制读主策略。

## 案例分析题

**题目**：

某省级政务服务大数据中心的统一数据服务平台承载全市 42 个委办局的共享数据，日均提供 3000 万次数据查询、1200 万次数据写入。平台采用主从架构（1 主 2 从），存储层使用某开源关系型数据库。近期运维监控发现以下现象：

一、每日凌晨 1:00 至 4:00 期间，从库 CPU 利用率持续 95% 以上，主库 CPU 利用率仅 30% 至 40%，主从延迟在高峰时段达到 180 秒，业务侧频繁反馈"刚提交的数据查不到"。

二、平台运维人员为提升查询性能，对一张日均新增 200 万行的流水表新增了 8 个索引，此后写入 TPS 从 1.2 万下降至 6000，同时该表在每日凌晨批量统计报表任务运行时出现大量超时。

三、客服工单系统表，工单量 800 万行，运维人员通过执行计划发现其中一条查询全表扫描、扫描行数 89 万行、返回行数 12 行、耗时 6.8 秒。检查发现该查询条件为"工单状态 = 已办结 AND 创建时间 > 某日期"，而状态字段的区分度仅为 3%。

四、客服工单分页查询采用"SELECT * FROM 工单 ORDER BY 创建时间 DESC LIMIT 1000000, 100"，用户翻到第 500 页时查询耗时从 200 毫秒上升至 15 秒，用户普遍反馈"越翻越慢"。

五、数据库管理员反馈：某批量报表作业使用"SELECT COUNT(*) FROM 工单 GROUP BY 创建日期"查询耗时 47 分钟。开启长事务监控后发现，该报表作业开启事务后先执行分组查询、随即在同一事务内执行一系列 UPDATE 与 DELETE，全过程未提交，导致该事务的 Read View 长期存在，undo 表空间从 120 GB 增长至 460 GB，磁盘告警。

六、架构师在评审会上提出，将工单表的"状态"字段从"待受理/处理中/已办结/已关闭"改造为独立的状态字典表并建立关联，理由是"字段只有四个值，不符合第三范式，应该做规范化改造"。数据组提出异议：改造涉及 800 万行数据迁移、十余个应用系统的接口改造，且工单表查询已出现性能问题。

**问题**：

1. 针对现象一，判断主从延迟与"查不到刚提交数据"的根因，给出具体的架构层与数据库层改造措施。
2. 针对现象二，分析索引增加后写入性能下降与报表任务超时的机理，给出索引治理的完整方案。
3. 针对现象三，分析该查询走全表扫描的根因，给出优化的具体步骤与预期收益。
4. 针对现象四，说明深分页问题的成因并给出改造方案。
5. 针对现象五，说明长事务与 undo 膨胀的因果链，给出即时处置与长效治理措施。
6. 针对现象六，对架构师的规范化建议作出技术判断，并给出更合理的改造路径。

**参考答案**：

### 第1问：主从延迟与读己之写不可见（9 条）

**根因判断**

1. **主从延迟的成因是写入集中 + 只读扩容方式单一**：凌晨 1:00 至 4:00 是业务批处理与报表的高峰，1200 万次日均写入中相当比例集中在该时段，主库单线程（或有限并行度）回放重做日志追不上从库应用速度，从库 CPU 被打满至 95%，延迟累积至 180 秒。
2. **读写分离策略缺失导致读流量全部落在从库**：从库 CPU 95% 而主库仅 30% 至 40%，说明大量读请求也被路由到从库，进一步挤占从库回放资源，**形成"读越多、从库越慢、延迟越大、读被路由到从库更多"的正反馈恶化循环**。
3. **"查不到刚提交数据"是典型读己之写不可见**：读请求走从库，从库回放未追平时读到旧版本。在可重复读隔离级别下，如果读操作采用快照读，会进一步锁定旧快照，问题更持久。
4. **缺少强制读主机制与延迟感知路由**：系统未设置延迟阈值熔断，也未对"写后立即读"场景路由主库。

**改造措施**

5. **读写分离改为延迟感知的动态路由**：设置主从延迟阈值（如 1 秒），超过阈值时自动将普通读请求切回主库；针对写后立即读场景提供"强制读主"标记或基于会话的读主窗口。
6. **从库并行回放与并行复制**：启用并行回放（并行度按 CPU 核数设定）与并行复制，从根本上提升回放速度；同时评估半同步复制，在对数据一致性要求高的业务上保证主库提交前至少一个从库已接收。
7. **读写分离的路由规则改为业务分级**：报表类查询走从库并可进一步走离线数仓或物化视图；在线交互查询在延迟超阈值时回落主库；将高频轻量查询通过缓存前置。
8. **拆分批处理与在线流量的资源**：凌晨批处理使用独立从库组或独立实例，与在线读隔离，避免资源争抢；批处理写任务错峰或限速。
9. **建立延迟可观测与自动处置**：监控主从延迟、复制线程状态、从库应用位置落后量，设置延迟告警与自动摘除故障从库的机制；出现持续延迟时自动降级并告警。

### 第2问：索引增加的写入代价与报表超时（10 条）

**机理分析**

1. **索引是写放大的主要来源**：每增加一个索引，每次插入与更新都需同步维护该索引的 B+树结构，产生额外随机写、页分裂与空间消耗。8 个索引意味着单行写入的维护成本成倍增加，这是写入 TPS 从 1.2 万降至 6000 的直接原因。
2. **索引挤占缓冲池**：大量索引页占据有限的内存池，导致热点数据页与索引页频繁换页，读取性能同步恶化，形成"写入变慢 + 读取变慢"的双输。
3. **优化器搜索空间膨胀**：候选索引组合数量呈指数增长，优化器单次查询的编译时间上升，在批处理高频执行时成为额外开销。
4. **报表任务超时的机理**：一是新增索引使表页数激增，批量统计需要扫描的物理数据量显著扩大；二是写入压力下缓冲池换页加剧，统计任务在统计信息过期的情况下选择了低效计划；三是统计任务与写入任务争抢 IO 与 CPU。

**索引治理方案**

5. **立即评估并清理冗余索引**：导出全部索引的使用统计（使用次数、扫描行数、覆盖列），识别零使用索引、被复合索引覆盖的单列索引、前缀重复索引（复合索引左侧列已有独立索引），评估后下线，确认前先在备库验证业务无依赖。
6. **按业务查询模式重建索引**：以真实慢查询与高频查询为依据，确认工单表真正需要的访问路径，典型为"创建时间 + 状态 + 部门"复合索引，并考虑将常用查询列纳入覆盖索引以避免回表。
7. **建立索引设计规范**：规定复合索引列序遵循区分度优先与最左前缀匹配；禁止对低区分度单列建索引；新建索引必须附带预期被哪些查询使用的说明，并在评审中确认。
8. **把索引变更纳入变更控制**：新增索引须评估对写入 TPS、存储空间、缓冲池命中率与优化器编译时间的影响，形成量化基线对比（变更前后 TPS、延迟、空间占用三项指标），经评审后执行。
9. **错峰执行批量变更与统计任务**：将报表与索引维护任务安排在写入低谷，或对批量统计走独立的分析型副本，避免与在线写入争抢资源。
10. **建立索引健康度巡检**：每月输出索引清单与使用率报告，自动标记零使用索引、膨胀索引、低区分度索引，交由评审决定下线，形成索引生命周期的常态治理。

### 第3问：全表扫描根因与优化（8 条）

**根因分析**

1. **复合条件中低区分度列主导了访问路径**：状态字段仅 3% 区分度，优化器估算"经状态索引过滤后仅剩 24 万行"，成本估算低于全表扫描 89 万行加过滤，因此判定走状态索引更优——但实际选择的是全表扫描，说明该状态字段**没有可用索引**或已有索引因选择性差被优化器排除。
2. **统计信息陈旧或未收集**：优化器对"创建时间 > 某日期"的选择率估算失真，导致扫描行数估算（89 万）与实际严重偏离，这是判定基数估算失效的直接证据。
3. **缺失以创建时间打头的索引**：真正的区分度高的过滤条件是时间范围，而索引列序把低区分度列放在了前面，无法走范围扫描。

**优化步骤与预期收益**

4. **第一步，核实统计信息新鲜度**：立即收集表与索引统计信息（重新分析），确认统计时间戳，并检查状态列与创建时间列的直方图与选择率估算值是否与实际分布吻合。若估算值与实际偏离超过 10 倍，须先修正统计而非改索引。
5. **第二步，创建以高区分度列打头的复合索引**：建立"创建时间 + 状态"复合索引（创建时间为主列、状态为次列），若业务查询普遍附带部门或工单类型，再按查询模式追加为第三列。
6. **第三步，改写查询以利用索引**：条件中时间范围置于最前并使用与索引匹配的类型（避免在索引列上套函数、避免隐式类型转换）；若业务允许，将部分过滤下推为等值条件。
7. **第四步，考虑覆盖索引与返回列裁剪**：当前返回列范围大时应避免全列返回；工单列表页仅返回列表所需列时，可将列表列并入索引尾部形成覆盖索引，消除回表。
8. **预期收益**：走索引范围扫描后，扫描行数应从 89 万降至与时间范围匹配的量级（按实际业务分布通常在万级以内），配合覆盖索引可消除回表，整体耗时可从 6.8 秒降至百毫秒以内。**收益须以改造后的实际执行计划与压测数据验证，不能以估算代替结论**。

### 第4问：深分页改造（7 条）

**成因分析**

1. **大偏移量分页的本质是无效扫描与丢弃**：语句 LIMIT 1000000, 100 要求数据库定位到第 1000001 行后开始输出 100 行，定位过程必须完整扫描并丢弃前 100 万行，代价随页码线性增长，用户翻到第 500 页即对应约 50 万行的无效扫描，这与"越翻越慢"的现象完全吻合。
2. **叠加因素**：若排序字段"创建时间"无合适索引，还会叠加一次排序，代价进一步放大；即便有索引，排序字段若存在相同值，排序稳定性问题还会导致翻页时记录重复或遗漏。

**改造方案**

3. **采用键集分页（游标分页）**：把分页条件改为"创建时间 < 上一页最后一条记录的创建时间 AND (创建时间 = 该值 AND 主键 < 该记录主键)"，并使用主键或（时间 + 主键）组合作为游标，数据库直接从游标位置向后扫描固定条数，**代价与页码无关，恒定为百行量级**。
4. **配套索引**：建立"创建时间 + 主键"的复合索引，确保游标定位可走索引有序扫描，避免排序算子介入。
5. **保留总数查询的独立实现**：总数统计仍需一次全量或近似估算，可改用独立统计表、计数器或近似值分页，避免每页都付出精确总数代价。
6. **处理跳转需求**：键集分页不支持跳转到任意页码，这是其固有取舍。若业务强依赖任意页跳转，可采用"分段锚点 + 二分定位"方案，预先在分段边界记录锚点值，跳转时先二分定位到最近锚点再做小范围偏移扫描，代价从线性降为对数级。
7. **接口改造与兼容**：前端交互改为"上拉加载"或"上一页下一页"模式，接口传游标而非页码；已在改造的工单接口需同步改造应用系统，并在灰度期监控慢查询数与数据库 CPU 变化。

### 第5问：长事务与 undo 膨胀（8 条）

**因果链**

1. 报表作业显式开启长事务 → 2. 事务内先执行分组查询创建 Read View → 3. 同一事务内执行大量 UPDATE 与 DELETE → 4. 事务长期未提交，Read View 持续存在 → 5. 被修改行的旧版本无法被清理（因可能仍被该快照读取） → 6. 版本链持续增长 → 7. undo 表空间从 120 GB 膨胀至 460 GB → 8. 磁盘空间告警，且历史版本堆积使历史版本查询与二级索引维护性能同步下降。

**即时处置**

2. **立即终止或强制回滚长事务**：定位到具体的会话与作业，优先通过终止会话释放资源；恢复磁盘水位。
3. **分段提交改造作业**：将报表作业改为小批次处理，每批独立提交，避免单个事务跨越整个作业。
4. **将统计类查询移出写事务**：分组统计应在只读会话或独立只读实例上执行；写操作单独以短事务提交，避免快照跨写操作长期存活。
5. **临时收紧长事务限制**：设置空闲事务超时与会话级最大执行时长，对超限会话自动告警或断开。

**长效治理**

6. **建立长事务与 undo 监控**：监控最长事务时长、活跃长事务数量、undo 表空间使用率与增长速率，设置三级告警阈值（如使用率 60% 预警、75% 严重、85% 紧急），并配置自动清理策略。
7. **设置参数级防护**：配置空闲事务超时、最大事务时长、单事务最大 undo 空间占用上限，超限即拒绝或告警。
8. **为历史版本堆积场景建立容量模型**：估算峰值并发长事务数 × 单事务平均 undo 增量 × 保留周期，据此规划 undo 表空间容量与独立表空间，避免默认配置在突增场景下被打爆。

### 第6问：规范化改造的技术判断（9 条）

**对架构师建议的判断**

1. **结论：不建议按"符合第三范式"的理由做这次改造，理由不成立，应予否决并给出替代方案**。
2. **第一条理由，第三范式针对的是非主属性对码的传递依赖，不是针对"取值种类少"**：状态字段是"工单状态"这一实体的属性，其取值来自业务枚举而非从其他实体派生，不构成传递依赖。将其拆为字典表是为了**参照完整性统一与多语言扩展**，属于可选的工程优化，而非范式要求。用第三范式为由拆分，会形成"为满足理论而承担迁移成本"的典型误判。
3. **第二条理由，成本收益严重倒挂**：需迁移 800 万行数据、改造十余个应用系统接口，风险覆盖全部工单相关业务；而工单表已存在查询性能问题，在数据量与访问模式未稳定前做大规模结构变更，会引入新的性能与稳定性风险。
4. **第三条理由，规范化的收益方向与当前痛点相反**：拆表后每次查询工单状态需要多一次连接，在当前已存在全表扫描与深分页问题的表上增加连接开销，与优化目标冲突。

**更合理的改造路径**

5. **先解决性能问题，再评估结构优化**：按第 3 问与第 4 问的方案完成索引与分页改造，将工单表的访问路径稳定下来，再基于新的性能基线判断字典表拆分的实际收益。
6. **优先采用低风险的结构优化**：在工单表上以"状态编码 + 应用层字典"或"保留原字段 + 增加状态名称的冗余列（由应用或触发器维护）"的方式实现状态取值的统一维护与展示一致性，**不动表结构、不迁移数据、不改接口**。若确需字典表，采用"新增字典表 + 增加冗余列 + 双写过渡 + 存量数据离线回刷"的渐进路径，避免停机迁移。
7. **为字典表设定引入门槛**：仅在出现真实需求时引入——需要多语言展示、需要按状态配置流程规则或权限、需要与主数据体系统一编码、或需要状态相关的统计分析维度。**以门槛约束改造冲动，避免为规范而规范**。
8. **接口层兼容策略**：如最终必须改造，通过在数据访问层引入统一的状态枚举映射与兼容视图，使十余个应用系统的接口改造收敛为一处变更，改造可分批灰度。
9. **架构师的正确职责表述**：架构师对表结构的技术判断本身没有错误，错误在于**把理论规范直接等同于工程必做项，绕过了成本收益评估与实施风险评估**。资深架构师的做法是——承认规范方向合理，量化改造成本与收益，评估收益是否覆盖成本与风险，再决定做、延后做还是以更低成本的方式做等价目标。

### 踩分要点

1. **第1问必须区分"主因"与"加剧因素"**：主因是回放能力不足与应用负载不匹配，加剧因素是读流量全部落在从库形成的正反馈。只答"主从延迟"不得分。
2. **第1问的改造措施必须落到具体机制**：并行回放、半同步复制、延迟阈值熔断、强制读主、业务分级路由，缺一即为措施笼统。
3. **第2问必须答出"索引是写放大主因"与"索引挤占缓冲池"两条机理**，只写"索引影响写入"属浅层。
4. **第2问的治理方案要体现生命周期管理**（使用率统计、零使用索引下线、月度巡检、变更前量化基线），这是资深架构师视角。
5. **第3问必须点出"低区分度列主导访问路径"与"统计信息陈旧导致基数估算失效"两条**，且要给出"先修统计再改索引"的顺序判断。
6. **第3问的预期收益必须给量化区间并说明以实际执行计划验证**，写"性能大幅提升"不得分。
7. **第4问必须解释清楚"扫描并丢弃"这一机理**，并给出键集分页的具体条件改写形式；只说"用游标"不给条件写法不得分。
8. **第5问必须写出完整因果链（长事务 → Read View 存活 → 旧版本不可清理 → 版本链增长 → undo 膨胀）**，并区分即时处置与长效治理。
9. **第6问是本卷的"观点辨析"题，必须给出明确结论并说明理由**，且必须指出"第三范式针对传递依赖而非取值种类少"这一知识点，答成"都可以，看情况"为负分。
10. **全卷通用**：所有性能结论必须区分"估算值"与"实测值"，出现"预计可提升数倍"而无口径说明的表述会被扣分；改造方案必须含灰度、回滚与监控三项配套。

## 记忆口诀

1. **两条路线一句话**：**B+树随机读强、LSM 顺序写强**，选型本质是"读写比与访问模式"的取舍。
2. **B+树三性质口诀**：树高低、数据有序、叶链相连——**有序是范围查询的通行证**。
3. **LSM 三放大口诀**：写、读、空间三放大——**放大与放大此消彼长，无三者兼优的配置**。
4. **MemTable 与块大小口诀**：**调大降写放大、增读放大**，调 Bloom Filter 反向——记住方向就不会记反。
5. **适用判据口诀**：读多写少用 B+树，写多读少用 LSM——**OLTP 走 B+树，时序日志走 LSM**。
6. **MVCC 核心一句话**：**读靠版本链免锁，写靠锁互斥**，MVCC 不解决写写冲突。
7. **Read View 四要素口诀**：低水位、高水位、自身事务号、活跃集——**四要素齐全才判得准可见性**。
8. **可见性口诀**：小于低水可见、大于高水未来、中间看活跃——**在活跃集里就是不可见**。
9. **快照读与当前读口诀**：**快照走 Read View，当前读直接读最新并加锁**——更新删除锁定读全属当前读，最易记混。
10. **隔离级别表口诀**：读未全允许、读已禁脏读、可重禁不可重、串行全禁——**幻读靠间隙锁在可重读下被压住**。
11. **锁谱系口诀**：共享排他意图、记录间隙、next-key、元数据——**间隙加 next-key 是可重读下的默认单位**。
12. **长事务危害口诀**：**快照不死、旧版不消、undo 暴涨**——长事务是 MVCC 生产故障第一诱因。
13. **死锁四条件口诀**：互斥、等待、不抢、循环——**破坏任一可预防，数据库选检测回滚**。
14. **死锁排查三步口诀**：查死锁记录、比对加锁顺序、统一访问顺序——**索引缺失扩大锁范围是重要诱因**。
15. **优化三阶段口诀**：逻辑改写、物理选路、代价估算——**统计信息是地基**。
16. **统计信息口诀**：**"昨天快今天慢"先查统计**，直方图应对倾斜，大表提高采样精度。
17. **基数误差口诀**：**估算与实际差十倍，连接顺序必选错**。
18. **执行计划风险信号口诀**：大表全扫、过滤性差、大结果集排序、物化临时——**四个信号四个根因**。
19. **深分页口诀**：**大偏移要扫描并丢弃，代价随页码线性涨**。
20. **深分页解法口诀**：**键集分页代价恒定**，索引保有序，任意跳页用锚点二分。
21. **索引四黄金法则口诀**：最左前缀、禁函数隐转、区分度列前、覆盖免回表——**索引有成本不是越多越好**。
22. **慢查治理五步口诀**：发现、归因、优化、固化、复测——**不固化到规范就白做**。
23. **结构性优化口诀**：**语句级优化在数据量跨量级后收益急剧衰减**，该分表就分表。
24. **第三范式口诀**：**针对非主属性对码的传递依赖，不是针对取值种类少**——字典表拆分是工程选择而非范式要求。
25. **改造判断三问口诀**：**收益覆盖成本吗、风险可控吗、有更低成本等价方案吗**——三问不过就否决。
26. **全卷信条**：**先归因再开方，估算与实测必须分清，改造必带灰度回滚与监控**。
