## 今日核心概念

### 1. 排队论基本模型与肯德尔记号

定义：排队论是研究"随机到达—排队等待—服务完成"这一类随机服务系统的数量关系与性能指标的数学理论，是性能工程与容量规划的理论地基。系统架构师用它回答三个问题：系统还能撑多久、瓶颈在哪里、扩容要扩多少。

关键要点：

- **排队系统三要素**：到达过程（客户如何来到）、服务过程（单服务台多快）、排队规则与系统容量（先来先服务/优先级/拒绝准入/有限缓冲）。
- **肯德尔记号 A/S/c/K/N/D**：A 为到达间隔分布，S 为服务时间分布，c 为服务台（并发处理能力）数量，K 为系统最大容纳数，N 为排队规则，D 为服务台工作方式。记法中三个分布符号是考点核心：M 表示泊松（随机）到达或指数服务，D 表示确定性（固定），G 表示一般（任意）分布。
- **六个基本度量**：到达率 λ、有效到达率 λe（扣除被拒绝的部分）、服务强度 μ、服务台利用率 ρ、系统内顾客数 L、队列中顾客数 Lq、顾客逗留时间 W、顾客等待时间 Wq。核心恒等式：λ = L/W = Lq/Wq，W = Wq + 1/μ（单服务台）。
- **稳定性条件**：ρ = λ/(c·μ) < 1。这是排队系统"会不会雪崩"的分水岭；ρ ≥ 1 意味着到达速率已超过处理能力，队列长度随时间线性甚至超线性增长，等待时间趋于无穷，表现为超时、502、重试风暴。
- **性能悬崖**：M/M/1 下 W = 1/(μ−λ)。λ 取 μ 的 50% 时 W = 2/μ；取 90% 时 W = 10/μ；取 95% 时 W = 20/μ。利用率从 50% 提到 95%，吞吐只增加 90%，但平均响应时间放大 10 倍。这是"扩容不如削峰"的数学依据，也是容量规划把利用率上限卡在 0.6~0.7 的直接理由。
- **在架构中的映射**：线程池=有限服务台排队，数据库连接池=共享资源排队，消息中间件=带缓冲的排队削峰，HTTP 请求队列=系统边界处的准入控制。

### 2. 经典排队模型 M/M/1 与 M/M/c

定义：M/M/1 表示泊松到达、指数服务、单服务台的排队模型；M/M/c 表示同一分布假设下的多服务台模型。两者是容量估算中最常用的封闭解模型。

关键要点：

- **M/M/1 核心公式**：ρ = λ/μ；L = ρ/(1−ρ)；Lq = ρ²/(1−ρ)；W = 1/(μ−λ)；Wq = ρ/(μ−λ)。注意 Lq 与 L 的关系 Lq = ρL，是判断"队列比处理中任务还多"的直观依据。
- **M/M/c 的两个修正项**：服务台不忙概率 P0 需按 c 阶求和计算；等待概率按爱尔朗 C 公式求得。含义是：c 增大到某个临界点后，继续增加服务台的收益急剧下降——新增的资源更多是"减少排队"而非"提升吞吐"。这是"扩容到某个点后收益递减"的量化表述。
- **临界服务台数判据**：当 λ/μ 明显大于 c 时，c 的最优区间应落在 λ/μ 与 c = λ/μ + 1.5√(λ/μ) 之间；超出该区间，增加服务台对等待时间的改善迅速衰减。多实例部署数规划应据此留出合理余量，而不是简单按总吞吐除以单实例。
- **M/M/1 假设的工程偏差**：真实系统服务时间更接近确定分布（请求体量固定、处理路径固定），因此真实系统的排队时延通常优于 M/M/1 的预测；反之若服务时间方差很大（长尾），实际表现会劣于模型预测。考试中遇到"模型预测与实测不符"的情形，标准答法是"检查服务时间分布与变异系数假设是否成立"。
- **利用率与并发的换算**：单实例理论吞吐 = c×μ（c 为并发处理能力，如连接池大小），实际可用吞吐应乘以利用率折减系数（一般取 0.6~0.7），由此得"所需实例数 = 目标峰值吞吐 /(单实例理论吞吐 × 0.6)"。

### 3. M/G/1 与 Pollaczek-Khinchine 公式

定义：Pollaczek-Khinchine（P-K）公式给出了"一般服务时间分布"条件下排队等待时间的期望值，是把排队论从理想模型推向工程现实的桥梁。

关键要点：

- **P-K 公式**：Wq = λ·(E[S²] + (E[S])²) / (2c(1−ρ))。整理后 Wq = (λ·(E[S])²·(1+C²)) / (2c(1−ρ))，其中 C² = Var(S)/(E[S])² 称为**变异系数**。
- **变异系数的工程含义**：C² = 0 表示服务时间完全确定（最好），C² = 1 表示服务时间服从指数分布（最差的泊松同源场景），C² > 1 表示服务时间波动比指数分布还大（长尾场景）。公式清晰表明：在 λ、μ 不变的前提下，降低服务时间的方差能直接压缩排队时延。
- **三个降延迟的杠杆**：一是降低 ρ（扩容、限流、削峰使到达更平滑）；二是降低 C²（把长尾的个体请求聚合成批处理、把同步串行改异步并行、用缓存削掉慢路径）；三是降低 E[S]（优化慢查询与外部依赖）。扩容只作用于第一个杠杆，其余两个是架构手段。
- **排队论与"平滑度"的关系**：到达越突发（λ 的方差大），系统越接近"到达集中瞬间"，有效 ρ 峰值被拉高，排队时延被放大。因此把请求导入消息队列后按固定速率消费，等价于把到达分布从泊松改造成接近确定分布，是在不改硬件的前提下降低排队时延。
- **下界与上界**：D/G/1 是同等均值下的最优情况（服务时间完全确定），M/M/1 是常规参照。工程判断题常用"实测排队时延落在下界与上界之间"来验证改造收益是否合理。

### 4. 利特尔定律与排队系统在软件架构中的映射

定义：利特尔定律（Little's Law）指出：在一个稳定的排队系统中，系统内顾客数 L = 到达率 λ × 平均逗留时间 W。它不依赖具体的服务分布，只要求系统长期稳定，因此是架构设计中最好用的一条通用公式。

关键要点：

- **三形态表述**：L = λW（系统内人数）、Lq = λWq（排队人数）、λ = L/W。三者等价，题目常给两个求第三个。
- **架构落点一：容量反推**。并发数 = 吞吐 QPS × 平均响应时间 RT。若已知平均 RT 为 0.2 秒、峰值 3000 QPS，则需要支撑的并发量约为 600。线程池大小、连接池大小、Web 服务器并发连接数都由此推导，并应叠加 1.5~2 倍的突发系数。
- **架构落点二：资源池定容**。线程池过小 → 排队时延上升、CPU 利用率反而低（线程在等 IO 时被占用但未产生吞吐）；线程池过大 → 上下文切换开销与内存占用上升，并放大下游数据库的并发冲击。经验公式在应用层是"连接池 = 单实例核心里程碑吞吐 × 单请求平均占用时长"，再乘安全系数。
- **架构落点三：定位瓶颈的判据**。若某个环节的到达速率已接近其处理能力（ρ ≥ 0.9），该环节即为瓶颈，此时在其上游扩容毫无收益；正确做法是在上游削峰或在旁路做缓存与异步化。
- **架构落点四：拒绝优于排队**。无界队列会把"快速失败"变成"漫长等待"，进而触发上游客户端重试，形成重试风暴。正确做法是在系统边界做限流与有界排队：队列有长度上限、等待有超时上限、超限即快速拒绝并返回可重试标识。
- **常见误区**：利特尔定律描述的是稳态长期平均关系，用它推断"瞬时并发"必然偏差；用它做容量规划时，必须以稳定态为前提，系统已处于 ρ ≥ 1 的发散状态时该公式不成立。

### 5. 性能与容量规划方法论

定义：容量规划是把业务目标（峰值请求量、SLO 响应时间、可用性目标）转换为硬件与架构资源投入的完整方法；性能工程则在此基础上保障系统在真实负载下达成质量属性。

关键要点：

- **三种估算方法**：基准测量法（压测单实例得到吞吐-响应曲线）、排队论模型法（用到达率与服务时间推导所需服务台数与并发）、比例外推法（按线性假设由已知规模推算，前提是未触达瓶颈且扩展性近似线性）。
- **峰值到达率的获得**：先算日均请求量与业务分布折算的峰值时段请求量，再乘峰值系数（政务、金融类系统常取 3~5），最后做季度或年度增长预留。错误做法是直接用日均值做规划。
- **分层容量模型**：按接入层→应用层→缓存层→数据库层逐层测算，单层瓶颈即全链瓶颈。容量报告必须给出每层的理论上限、当前实测值与利用率百分比。
- **瓶颈定位四步法**：分层阶梯加压（找到拐点）→ 观察各层资源曲线（CPU、内存、IO、连接池等待）→ 用排队论反推各环节 ρ（ρ ≥ 0.9 即瓶颈）→ 定位到单点后再做横向与纵向对比（区分容量瓶颈与延迟瓶颈）。
- **性能测试五类**：基准测试（单点性能上限）、负载测试（预期业务负载下的表现）、压力测试（找到拐点与极限）、稳定性测试（长时间运行查内存泄漏与资源劣化）、容量测试（为扩容决策提供数据）。架构题常问"如何证明新架构优于旧架构"，标准答法是同负载同数据量的对照压测，并同时观察吞吐、P99、错误率、资源利用率四组指标。
- **SLO 与利用率的耦合**：给定 P99 时延目标，实际上就是给可用利用率设了上限（利用率越接近 1，时延长尾越陡）。因此容量规划不能脱离 SLO 单独做，扩容后的稳态利用率必须回落到安全区间，否则加机器只是把雪崩时间推后。
- **治理闭环**：目标（SLO）→ 测量（压测与监控）→ 定位（瓶颈与排队论建模）→ 改造（扩容/削峰/缓存/异步/降级）→ 复核（回归压测与容量模型更新）→ 常态化（容量周报、阈值告警、预案演练）。

## 案例分析题

**题目**：某省政务服务网"惠企政策兑现"平台上线补贴申报功能。平台由 12 台应用服务器组成，每台 8 核 16G，Web 容器线程池 200，数据库连接池 50，后端为单主 MySQL 集群并带 1 只只读副本；"资格核验"为核心同步接口。开放申报首日高峰，系统出现如下现象：

1. 入口层 502/504 错误率一度达 23%，平均响应时间 1.8 秒，P99 达 11 秒；
2. 应用日志显示 Web 容器线程池长期 200/200 满载，任务排队长度持续超过 2000 且不回落；
3. 数据库慢查询日志显示"资格核验"单次平均 620ms、P99 达 3.1 秒；主库 CPU 92%，连接池等待时间升高；
4. 运维两次将应用节点扩容至 24 台，错误率未下降，主库 CPU 反而升至 97%。

已知：申报总量 120 万件，开放窗口 6 小时，其中 70% 集中在前 2 小时。

**问题**：

1. 依据排队论分析该系统的稳定性与性能瓶颈，说明为什么"扩容应用节点"没有效果。
2. 改造后仅保留 3000 TPS 的同步受理能力，其余转为异步处理。请用利特尔定律与排队论计算所需的应用实例数、数据库连接数与异步消费能力，并说明计算前提。
3. 提出架构改造方案（不少于 5 项），并说明每一项分别作用于排队论的哪个杠杆（利用率 ρ、变异系数 C²、平均服务时间 E[S]、准入控制）。
4. 设计性能测试方案与上线准入准出指标，说明如何证明改造有效。
5. 指出该方案遗留的风险并给出复核机制。

**参考答案**：

**问题 1**

峰值到达率计算：70% × 120 万 = 84 万件集中在 7200 秒内，平均 1167 TPS；政务类系统峰值系数取 4，峰值约 4700~4800 TPS。

单实例有效服务能力：单实例数据库连接池 50，核验接口单次 620ms，受连接池约束的单实例吞吐 = 50 / 0.62 ≈ 80.6 TPS；12 实例合计约 968 TPS。

利用率：ρ = 4800 / 968 ≈ 4.96，远大于 1，系统处于发散状态。M/M/1 排队时延公式 W = 1/(μ−λ) 在 λ > μ 时无解，即等待时间趋于无穷。表现为线程池排队长度持续增长不回落（对应队列中顾客数 Lq 无界）、大量请求超时、入口层出现 504。

瓶颈定位：数据库连接池 50 < Web 线程池 200，说明实际并发上限被数据库连接数钳制为 50，线程池中另有 150 个线程处于等待数据库连接的空闲占用状态；主库 CPU 92% 表明数据库层 ρ 同样处于高位。

扩容无效的三个原因：
- 扩容只作用于下游资源，未解决上游到达率超出系统能力 4.96 倍的根本矛盾；数据库连接池与主库 CPU 才是瓶颈，应用层扩容反而增加数据库并发连接压力，主库 CPU 由 92% 升至 97%，排队恶化；
- 扩容后单实例有效吞吐受连接池 50 限制，节点数从 12 增至 24 理论上限也仅由 968 升至 1936 TPS，仍不足 4800 TPS 的 41%；
- ρ ≈ 4.96 属发散区，扩容幅度不足一个数量级时无法跨过稳定性阈值，只能略微推迟雪崩到来时间。

结论：该问题是"系统能力与到达率结构性失配 + 瓶颈层次错配"，属必须先削峰解耦、再谈扩容的典型场景。

**问题 2**

改造后同步受理链路只承担表单校验、幂等判重与受理落库，单条平均 15ms。

应用实例数：单实例受理能力 = 50 / 0.015 ≈ 3333 TPS；按安全利用率 0.6 折减可用吞吐 ≈ 2000 TPS；峰值同步受理 3000 TPS → 需 3000 / 2000 = 1.5 台，向上取整并预留单节点故障，按 1.5 倍余量取 4~5 台。

数据库连接数：由利特尔定律，同步受理并发数 = λW = 3000 × 0.015 = 45 个在途请求；异步核验按批量 100 条/次、单批 1.2 秒处理，单 worker 批吞吐 = 100/1.2 ≈ 83 批/s，在途批数 = 83 × 1.2 ≈ 100 批并发，对应连接占用 100（每批一条连接）。合计在途连接约 145，按 1.5 倍突发系数取约 220 条连接；再按实例分摊（5 台应用实例）得每实例连接池不低于 45，考虑连接池必须小于数据库最大连接数上限，最终以"连接池 45~60 + 数据库侧按实例数与总量双约束"为准。

异步消费能力：需在可承诺的时延窗口内消化 84 万件。取消息队列积压上限 50 万件、消化速率 4800 件/秒，从满积压到清空需 104 秒；若承诺"受理后 10 分钟内出结果"，则消费能力需求 = 84 万 / 600 秒 = 1400 件/秒，建议按 4800 件/秒配置以留出积压重放余量。

计算前提（必须写明，否则不得分）：
- 到达过程近似泊松或取更保守的峰值系数；服务时间服从指数分布且变异系数按实测值 C² 修正（P99 3.1 秒显著高于均值 620ms，说明 C² 远大于 1，需用 P-K 公式而非 M/M/1 公式估算排队时延）；
- 系统处于稳定态（ρ < 1），不处于发散区，否则利特尔定律不适用；
- 单实例吞吐在压测中实测得到，而非理论推算；压测数据需包含长时间稳定性数据；
- 数据库连接数受实例数与最大连接数双约束，且需为运维与故障切换预留连接。

**问题 3**

改造方案与所作用的杠杆：

1. 入口限流与有界排队（令牌桶 + 令牌桶突发量与队列长度双上限，超限快速返回可重试标识）：作用于准入控制，把"无限等待"变为"显式拒绝"，并把 λ 削到 ρ < 1 的安全区。禁止无界队列与自动重试风暴。
2. 受理与核验解耦，异步化（受理接口只做校验与落库，核验走消息队列异步执行，结果通过短信/站内信与主动查询返回）：作用于利用率 ρ 与变异系数 C²，把同步链路的 λ 压到服务能力以下，同时把到达分布从突发改造成近似确定分布，消费端按固定速率拉取。
3. 批量核验与慢 SQL 治理（"资格核验"改为批量接口 100 条/批，一次连接查多批，620ms 降至 60ms 量级；对核验涉及的资格表补齐覆盖索引、消除 N+1 查询与全表扫描）：作用于平均服务时间 E[S] 与变异系数 C²，单请求耗时的方差同时收窄，P99 从 3.1 秒降至百毫秒级。
4. 读写分离与热点治理（资格核验走只读副本，报表类查询全部下沉副本，读写路由按业务分级；申报热点字段用本地缓存 + Redis 多级缓存挡在数据库之前）：作用于到达率与 E[S]，把读流量从主库剥离，使主库只承载受理落库写流量。
5. 主从半同步与读写一致性策略（受理落库改为主从半同步复制，副本可读延迟设阈值；受理后需立即读己之写的场景强制读主，其余读副本）：作用于服务时间与可靠性，避免扩容后主库 CPU 进一步被同步压力推高。
6. 同步链路限流降级与熔断（令牌桶限流，队列有界；核验接口对下游工商、税务等外部系统加熔断与降级兜底数据，超时预算按剩余时延链路反推）：作用于准入控制与 E[S]，防止外部依赖抖动传导为全链路雪崩。
7. 削峰填谷与预约制（申报高峰前 2 小时开放预处理通道做资格预热、把 70% 的集中流量引导为"预约提交 + 定时生效"）：作用于到达率，把峰值系数从 4 降到 1.5 以内，是本方案收益最大的一项。
8. 弹性伸缩与自动扩缩容（HPA 基于队列长度与 CPU 双指标，而非仅 CPU；配置 PDB 与反亲和避免节点同时驱逐）：作用于利用率 ρ，通过自动增实例把 ρ 稳定压在 0.6~0.7。

四项杠杆与措施对应关系：

| 杠杆 | 含义 | 对应措施 | 可观测指标 |
|---|---|---|---|
| 利用率 ρ | 到达率与服务能力之比 | 异步化解耦、批量核验、削峰填谷、弹性伸缩 | 各层线程池/连接池占用率、队列长度、DB CPU |
| 变异系数 C² | 服务时间方差 | 批量聚合、缓存削慢路径、固定速率消费 | P99/P50 比值、单请求耗时分布 |
| 平均服务时间 E[S] | 单次处理耗时 | 索引优化、消除 N+1、连接池调优、缓存 | 平均耗时、慢查询数 |
| 准入控制 | 是否允许进入系统 | 限流、有界排队、快速拒绝、熔断降级 | 拒绝率、限流触发次数、超时率 |

**问题 4**

性能测试方案：

- 基准测试：单实例压测受理接口，得出吞吐-响应曲线，确认单实例有效吞吐与拐点，作为容量模型的输入而非直接采用理论公式。
- 负载测试：按 4800 TPS 峰值与 3000 TPS 稳态两档分别加压，观察 P99 时延与错误率是否满足 SLO。
- 压力测试：阶梯加压（每档 500 TPS）直到错误率超 1% 或 P99 超时上限，记录拐点，作为限流阈值与自动扩容阈值的依据。
- 稳定性测试：连续 8 小时以上运行峰值负载，观察内存泄漏、连接数漂移、消息积压曲线、慢查询增量。
- 容量测试：以 1 倍、1.5 倍、2 倍峰值三档做阶梯验证，给出"能支撑多少业务量"的结论。
- 对照验证：改造前后同负载、同数据量、同机器配置做对照压测，同时记录吞吐、P99、错误率、资源利用率四组指标，避免只比 QPS。

上线准入准出指标：

准入（压测全部满足才放行）：峰值 4800 TPS 下 P99 ≤ 500ms、错误率 ≤ 0.1%、主库 CPU ≤ 60%、线程池与连接池占用率 ≤ 70%、消息端到端时延 P99 ≤ 3 秒、受理成功率 100%。
准出（灰度期实时监控，任一项越界即回滚）：错误率 > 0.5% 持续 1 分钟、主库 CPU > 75% 持续 3 分钟、消息积压增速超过消费速率、P99 超过准入值 50%、限流拒绝率 > 20%。
灰度策略：按 1% → 5% → 20% → 50% → 100% 五档逐级放量，每档观察不少于 30 分钟并与准入指标逐项比对。
证明有效的判据：同负载下 P99 由 11 秒降至 500ms 以内、错误率由 23% 降至 0.1% 以内、主库 CPU 由 92% 降至 60% 以内、消息积压可在承诺时延窗口内清空；且改造后有效吞吐达到改造前稳定吞吐的 3 倍以上。

**问题 5**

遗留风险与复核机制：

- 风险一：削峰措施依赖用户配合，若高峰集中度未按预期下降，λ 仍超 ρ 安全区。对策：保留令牌桶硬限流作为兜底，限流阈值按实测到达率动态调整；定期复核峰值系数假设。
- 风险二：异步化后"受理成功但核验失败"的数据不一致。对策：受理单与核验任务建立状态机（待核验/核验中/成功/失败/人工介入），失败任务进入补偿队列并由人工工单兜底；对账任务按日核对受理数与核验完成数。
- 风险三：外部依赖（工商、税务）不可控，熔断降级后使用兜底数据会产生结论偏差。对策：兜底数据单独打标并标注"待复核"，不得直接用于发放；熔断阈值与降级数据保质期需评审确认。
- 风险四：批量核验改变单条失败定位粒度。对策：批量内保留单条结果码，失败单独立重试，禁止整批回滚。
- 风险五：弹性伸缩依赖指标准确性，队列长度指标在瞬时高峰下可能滞后。对策：采用 CPU + 队列长度 + 在途请求数三指标，任一触发即扩容；配置最小副本数兜底，避免冷启动无实例可用的雪上加霜。
- 风险六：数据库读写分离后主从延迟造成读己之写不可见。对策：受理后 T+0 内关键查询强制读主；设置从库延迟阈值（建议 200ms）告警，超阈值自动降级为全部读主。
- 风险七：容量模型基于压测环境，与生产数据分布差异导致预测偏差。对策：生产上线后用真实流量做一次影子压测或灰度实测，反向修正模型参数。

复核机制：

- 每周输出容量周报：实际到达率、各层 ρ 估算、实际 P99 与准入值偏差、扩容次数与触发原因。
- 每月复核一次容量模型参数（单实例吞吐、服务时间分布、变异系数），模型偏差超过 20% 时触发重算。
- 每季度做一次全链路故障演练与限流演练，验证限流阈值、降级开关、扩容触发与回滚脚本可用。
- 每半年做一次架构评审，评估是否需要引入单元化、多活或本地化部署；新业务上线前必须重跑容量测算并纳入准入。
- 建立架构适应度函数自动校验：对外暴露"提交接口 P99 ≤ 500ms""主库 CPU ≤ 60%""消息积压增速 ≤ 消费速率""连接池占用 ≤ 70%"四条，任一不达标即阻断发布。

**踩分要点**：

1. 峰值到达率必须由总量与时间分布推导并乘峰值系数，直接用日均值规划是常见的错误扣分点。
2. 稳定性判据 ρ = λ/(c·μ) < 1 必须写出；ρ > 1 时队列发散、等待时间趋于无穷，这一句是本题核心得分点。
3. 必须指出线程池 200 大于连接池 50 的层次错配，说明实际并发被数据库连接数钳制，这是"扩容无效"的直接原因。
4. "扩容无效"要答出三层原因：瓶颈不在应用层、扩容幅度不足一个数量级、并发增加反而推高主库 CPU。
5. M/M/1 与 M/M/c 的公式要能正确使用：单服务台用 M/M/1，多服务台用 M/M/c，并指出 c 增大存在收益递减临界点。
6. 利特尔定律应用题必须写出三式关系，并明确"并发 = λ×W"要叠加突发系数。
7. 计算必须列出前提假设（泊松到达、指数服务、稳态、单实例吞吐由压测实测），否则即使数字对也会扣分。
8. 排队时延不能只用 M/M/1 公式，因为题目给出 P99 3.1 秒远高于均值 620ms，必须提到变异系数 C² 大于 1、应用 P-K 公式。
9. 改造方案每项都要对应到具体杠杆（ρ、C²、E[S]、准入控制），只罗列技术名词不得分。
10. 必须包含"异步化 + 削峰"两项，二者缺一则无法把 λ 从 4800 降到 3000 以下的同步能力范围，逻辑不闭环。
11. 必须明确"拒绝优于排队"与"禁止无界队列 + 禁止无限重试"，这是排队论在高并发架构中最常考的落点。
12. 性能测试要答出五类测试（基准、负载、压力、稳定性、容量）与准入准出双指标，缺"准入准出"或缺"稳定性测试"各扣一处分。
13. 必须用同负载同数据量的对照压测来证明改造有效，并同时给出吞吐、P99、错误率、利用率四组指标。
14. 风险部分必须落到数据一致性（受理与核验状态机与对账）、外部依赖降级数据保质期、读己之写一致性三个具体点，不能泛泛写"可能有风险"。
15. 复核机制必须含量化阈值与自动校验（适应度函数阻断发布），这是架构治理类问题的评分落点。

## 记忆口诀

1. 排队三要素：客户怎么来、服务有多快、排队的规矩定。
2. 肯德尔 A/S/c/K/N/D：三个分布看 M/D/G，服务台数是关键。
3. M 是随机、D 是定、G 是任意，六度量要背全。
4. 稳定判据 ρ<1，ρ 到 1 雪崩来。
5. M/M/1：ρ=λ/μ，L=ρ/(1−ρ)，W=1/(μ−λ)。
6. 利用率 50% 快如飞，95% 时延放大十倍。
7. M/M/c 有临界点，加到 λ/μ 加 1.5 倍根号就够，再多是浪费。
8. P-K 公式：C² 是变异系数，指数分布最差是 1。
9. 降延迟三杠杆：降 ρ、降 C²、降 E[S]，扩容只管第一个。
10. 利特尔三式 L=λW，Lq=λWq，λ=L/W。
11. 并发数 = 吞吐乘响应，线程池连接池都由它定。
12. 瓶颈判据 ρ 大于 0.9，下游扩容白搭上游忙。
13. 无界队列是大忌，拒绝优于排队。
14. 连接池小于线程池，是层次错配的信号。
15. 削峰填谷把到达变确定，等于降了 C²。
16. 性能五类测：基准、负载、压力、稳定、容量。
17. 准出指标四组：吞吐、时延、错误率、利用率。
18. 受理成功核验失败，靠状态机与对账兜。
19. 降级数据必打标，兜底不用来发放。
20. 写完读主读副本，读己之写不能等。
21. 容量模型每季度校，偏差过二成就重算。
22. 适应度函数做门禁，不达标就断发布。
