## 今日核心概念

### 1. 软件架构风格与分布式通信
定义：软件架构风格是描述软件系统高层次组织与结构的通用模式，规定组件类型、连接件类型、约束与语义；分布式通信是微服务与云原生架构下服务间协作的核心机制。

关键要点：
- 经典架构风格：管道-过滤器（Pipe-Filter，编译器）、分层架构（Layered，MVC三层架构）、客户端-服务器（C/S）、浏览器-服务器（B/S）、事件驱动（EDA，发布订阅）、微服务（Microservices）
- 微服务九大特性：单一职责+独立部署+技术异构+去中心化数据+轻量通信+DDD限界上下文+容错+演进+自动化
- 微服务 vs SOA 区别：微服务去中心化无ESB总线、服务粒度更细（200-2000行）、独立部署、DevOps强协同；SOA有ESB企业服务总线、服务粒度粗、共享数据库
- 服务间通信三大模式：同步调用（REST/gRPC/Thrift，阻塞等待）+异步消息（Kafka/RabbitMQ/RocketMQ，松耦合）+事件驱动（EDA，发布订阅）
- 同步 vs 异步通信权衡：同步调用强一致但耦合高、易雪崩；异步消息解耦但调试复杂、消息丢失风险
- 服务发现三种方式：客户端发现（Eureka+Ribbon，客户端负载均衡）+服务端发现（K8s Service+DNS，服务端代理）+服务注册中心（Consul/Nacos，自带健康检查）
- API 网关六大职责：路由转发+统一鉴权+限流熔断+协议转换（REST/gRPC/WebSocket）+灰度发布+监控埋点
- 服务间调用链路过长问题：N+1问题（一次请求调用多个服务）、雪崩效应（慢调用拖垮整条链路）
- 微服务反模式：分布式单体（拆服务不拆数据库）+共享数据库（多服务共写一库）+同步链路过长+数据一致性失控
- 微服务适用边界：业务复杂度高+团队规模50+人+变更频繁+独立扩展要求高；不适用：初创MVP、简单CRUD、小团队

### 2. 分布式一致性与共识算法
定义：分布式一致性是指在分布式系统中多个节点对某个值达成一致的过程；共识算法是保证分布式系统对某决策达成一致的协议机制。

关键要点：
- CAP 理论三选二：一致性Consistency（所有节点同一时刻看到相同数据）+可用性Availability（每个请求都得到响应）+分区容错性Partition tolerance（网络分区仍能运行）
- CAP 实战选择：P 是分布式系统必选项（无法避免网络故障），故实际在 C 和 A 间权衡
- CP 系统：HBase、Redis Cluster、ZooKeeper、Etcd，强一致放弃部分可用性
- AP 系统：Cassandra、CouchDB、Eureka、Couchbase，牺牲强一致保可用性
- BASE 理论：基本可用 BA（允许损失部分功能）+软状态 S（数据存在中间态）+最终一致 E（经过一段时间数据达到一致）
- 强一致 vs 最终一致：强一致写后立即读到最新值；最终一致允许中间态但保证收敛
- 共识算法三剑客：Paxos（最经典难懂，Lamport 提出）+Raft（易懂，Leader+Follower+Candidate 三角色）+ZAB（ZooKeeper 专用）
- Raft 算法三阶段：Leader 选举（投票过半）+日志复制（Append Entries 心跳）+安全性（任期 Term 单调递增、Leader 完整日志）
- Raft 日志一致性：Leader 强制 Follower 复制自己的日志条目，处理日志不一致（Term+Index）
- Paxos 算法两阶段：Prepare 阶段（提议者申请多数接受）+Accept 阶段（接受者承诺接受）；Multi-Paxos 优化（选出一个 Leader 简化后续）
- ZAB 协议两模式：恢复模式（Leader 崩溃后选主）+广播模式（Leader 广播消息，Follower 确认）
- 分布式锁三大实现：Redis（SETNX+过期时间，Redisson 看门狗自动续期）+ZooKeeper（临时顺序节点）+数据库（唯一索引）
- 分布式 ID 生成方案：UUID（128位无序，碰撞概率极低）+Snowflake 雪花算法（1位符号+41位时间戳+10位机器+12位序列）+Leaf 号段模式（美团）+Redis INCR
- 拜占庭将军问题：在不可信环境下（含恶意节点）达成一致的难题；比特币 PoW 工作量证明是解决方案

### 3. 分布式事务解决方案
定义：分布式事务是协调多个分布式节点上的数据操作保持 ACID 特性的机制；解决方案是在一致性、性能、复杂度之间权衡的不同策略。

关键要点：
- 分布式事务核心难题：CAP 定理决定了分布式系统无法同时满足 C+A+P；事务在多个节点执行时面临网络分区、节点故障等不确定性
- 强一致分布式事务：两阶段提交 2PC（Prepare 准备+Commit 提交，阻塞协议，强一致但单点故障）；三阶段提交 3PC（CanCommit+PreCommit+DoCommit，增加超时机制但仍不完美）
- TCC 补偿事务：Try（预留资源）+Confirm（确认提交）+Cancel（撤销释放）；业务侵入性强，性能好，落地框架 ByteTCC/TCC-Transaction
- Saga 长事务模式：拆分大事务为多个本地事务+补偿事务；两种协调方式 Orchestration（编排式，中央协调器）+Choreography（链式，事件触发）
- Seata 分布式事务框架：阿里开源；支持 AT 模式（自动补偿，业务侵入低）、TCC 模式、Saga 模式、XA 模式
- AT 模式原理：基于 undo_log 表实现自动补偿，业务 0 侵入；通过全局锁实现读已提交
- 本地消息表（最终一致）：业务表与消息表同库写入，通过定时任务扫描发送；适合异步场景
- 可靠消息最终一致：RocketMQ/Kafka 事务消息（Half 消息+Commit/Rollback）+幂等消费；适合异步解耦场景
- 最大努力通知：允许偶发失败，业务方自行补偿；适合对一致性要求低的场景（如支付回调）
- 分布式事务选型：强一致场景（资金/库存）选 TCC 或 Seata AT；最终一致场景（订单同步）选本地消息表或可靠消息
- 幂等性设计：所有写入操作携带业务唯一键，通过唯一索引或 Redis 去重表防重；分布式事务必做
- 金融级分布式事务：蚂蚁金服 OceanBase（蚂蚁自研+TPC-C 霸榜）+TiDB（PingCAP，兼容 MySQL 协议）

### 4. 数据一致性与分布式锁
定义：数据一致性是分布式系统中多个数据副本保持一致的特性；分布式锁是协调分布式节点互斥访问共享资源的机制。

关键要点：
- 副本一致性三大模型：强一致性（写入后所有副本立即同步）+弱一致性（不保证何时一致）+最终一致性（保证一段时间后一致）
- 副本一致性三大协议：NWR 协议（N 个副本 W 个写入 R 个读取，W+R>N 保证强一致）；Quorum 机制（多数派写入）；Paxos/ZAB 共识
- 数据同步三大模式：同步复制（写入主库后同步等待从库确认，强一致性能差）+异步复制（写入主库后立即返回，从库异步同步，性能高但可能丢数据）+半同步复制（至少一个从库确认后返回，折中）
- 分布式锁三大属性：互斥性（任何时刻只有一个客户端持有锁）+死锁避免（lock + 过期时间自动释放）+容错性（Redis 节点故障锁仍可用）
- 分布式锁三大实现对比：
   * Redis：性能高（亚毫秒），但存在主从切换丢失锁风险；Redisson 框架提供看门狗自动续期
   * ZooKeeper：可靠性高（基于 ZAB 共识），临时顺序节点实现，但性能略低（毫秒级）
   * 数据库：实现简单但性能最差（毫秒到秒级），不推荐生产环境高并发场景
- Redis 分布式锁实现要点：SETNX（SET if Not eXists）+ EX 过期时间 + 唯一 Token（防误删）；释放锁时需校验 Token
- Redisson 看门狗机制：默认 30 秒续期一次，自动续期防止业务未完成锁已过期；任务完成后手动释放
- ZK 分布式锁实现：临时顺序节点 + Watch 机制；最小序号节点获锁，其余节点 Watch 前一个节点
- 数据库分布式锁：唯一索引 + FOR UPDATE；性能差但实现简单，适合低并发场景
- 分布式锁常见坑：锁过期业务未完成（看门狗续期）、误删他人锁（Token 校验）、Redis 主从切换锁丢失（RedLock 多节点半数）
- 分布式锁选型：性能优先选 Redis（容忍极低丢失率）；强一致优先选 ZK；简单场景选数据库

### 5. 微服务网关与流量治理
定义：微服务网关是微服务架构的统一入口，负责请求路由、鉴权、限流、监控等横切关注点；流量治理是通过限流、熔断、降级等手段保障系统稳定性的工程实践。

关键要点：
- API 网关核心功能：路由转发（动态路由+灰度路由）+统一鉴权（OAuth 2.0+JWT）+限流熔断（Sentinel/Hystrix）+协议转换+监控埋点
- 主流 API 网关：Spring Cloud Gateway（Spring 生态，WebFlux 响应式）+Kong（基于 Nginx，高性能）+APISIX（Apache，云原生）+Zuul（Netflix，老牌但性能一般）
- 限流四大算法：计数器（固定窗口/滑动窗口，简单但边界问题）+令牌桶（Token Bucket，平滑限流）+漏桶（Leaky Bucket，强制匀速）+滑动日志（精确但内存大）
- 限流五大维度：QPS 限流（每秒请求数）+并发限流（同时处理数）+关联限流（资源A限流时B也被限流）+IP 限流+合作方限流
- 熔断器三状态：Closed（关闭，正常）+Half-Open（半开，试探恢复）+Open（断开，直接失败）
- 熔断器关键参数：错误率阈值（默认 50%）、窗口时间（10s）、恢复时间（5s 等待）、最小请求数（10个）
- Sentinel vs Hystrix：Sentinel（阿里开源，规则化配置+实时监控+多语言）；Hystrix（Netflix，已停更，进入维护）
- 熔断 vs 降级 vs 限流区别：熔断（服务故障自动断开）+降级（牺牲非核心功能保核心）+限流（限制流量防过载）
- 灰度发布五大策略：按比例灰度（1%→10%→50%→100%）+按用户灰度（VIP/特定用户）+按地域灰度（试点城市→全国）+按版本灰度（v1/v2 并行）+按合作方灰度
- 蓝绿部署 vs 灰度发布：蓝绿（两套环境，瞬间切换，回滚快但资源翻倍）；灰度（金丝雀 Canary，逐步放量，风险小）
- 流量染色与全链路压测：通过 HTTP Header 传递流量标识（如 gray=blue），影子表存储压测数据，影子库屏蔽真实数据影响
- 服务降级三大策略：返回默认值（缓存预热数据）+返回兜底数据（简化版业务数据）+排队等待（公平调度）
- 限流降级配置中心：Nacos/Apollo/Spring Cloud Config；规则动态下发，无需重启服务

## 案例分析题

**题目**：
某互联网出行平台"迅行"启动下一代订单中台重构项目，将原单体订单系统拆分为微服务架构。系统日均订单量 800 万单，峰值 QPS 达 12 万，重要促销期间 QPS 可达 50 万。系统要求可用性 99.99%（年宕机≤52 分钟），P99 响应时间≤500ms。

项目当前面临挑战：
1. 原有单体订单系统代码 200 万行，新人接手困难，需求变更平均需 3 周才能上线；
2. 订单数据库 MySQL 单库日均 1.2 亿次写入，CPU 持续 90%，连接池经常打满；
3. 司乘两端分别通过 APP/小程序调用接口，调用方有司机端、乘客端、客服端、第三方合作渠道（高德、曹操、T3 等 30+ 家）；
4. 订单创建涉及订单服务、支付服务、计价服务、优惠券服务、司机调度服务、营销服务、风控服务等 8+ 个服务调用；
5. 业务要求强一致：支付成功后必须生成订单，且不能重复扣款；
6. 营销活动期间 30% 流量集中在大额优惠券发放，频繁触发库存超卖；
7. 等保三级合规要求客户敏感信息（手机号、身份证）脱敏存储与传输；
8. 第三方合作渠道接入平均耗时 1.5 个月，新渠道接入需修改多处代码。

请作为系统架构设计师回答：
(1) 请设计微服务拆分方案（含领域划分、服务治理、数据拆分）；
(2) 请设计订单创建流程（含分布式事务、限流、降级、链路追踪）；
(3) 请给出数据库性能优化与多级缓存方案。

**参考答案**：

问题一：微服务拆分方案

一、领域划分（基于 DDD 限界上下文）：
1. 订单中心域：
   - 订单创建服务（订单生命周期管理：创建/支付/取消/退款/完成）
   - 订单查询服务（CQRS 读写分离，Elasticsearch 二次索引）
   - 订单状态机服务（OrderStateMachine：未支付→已支付→已完成→已退款）
2. 支付中心域：
   - 支付服务（聚合支付：微信/支付宝/银联/钱包）
   - 退款服务（支持原路退+钱包退）
   - 对账服务（每日与第三方对账）
3. 计价与优惠域：
   - 计价服务（动态计价：起步价+里程费+时长费+远途费+动态调价）
   - 优惠券服务（优惠券发放/核销/库存管理）
   - 营销活动服务（满减/折扣/抽奖/限时活动）
4. 调度与履约域：
   - 司机调度服务（订单派单/抢单/改派）
   - 运力服务（司机位置/状态管理）
   - 履约跟踪服务（行程记录/轨迹回放）
5. 客户域：
   - 用户服务（乘客信息管理）
   - 司机服务（司机信息/资质/车辆）
   - 风控服务（反欺诈/信用评估/异常订单识别）
6. 通知域：
   - 推送服务（APP 推送/短信/邮件）
   - 消息中心（IM 消息/系统通知）
7. 平台域：
   - API 网关（统一入口/路由/鉴权）
   - 配置中心（Nacos 统一配置）
   - 监控中心（SkyWalking 全链路追踪）
8. 数据域：
   - 数据同步服务（Canal 监听 binlog 同步 ES）
   - 数据分析服务（订单统计/司机画像）

二、技术栈统一：
1. 服务框架：Spring Boot 3.x + Spring Cloud Alibaba（Nacos + Sentinel + Seata + SkyWalking）
2. 服务通信：内部 gRPC（高性能低延迟，ProtoBuf 序列化）+ 外部 RESTful（OpenAPI 3.0 标准化）
3. 服务治理：
   - 注册中心：Nacos（服务注册+配置中心+健康检查）
   - 熔断限流：Sentinel（QPS 限流+并发限流+关联限流+熔断降级）
   - 分布式事务：Seata AT（默认）+TCC（资金场景）+Saga（长事务）+本地消息表（最终一致）
   - 链路追踪：SkyWalking（全链路调用追踪+性能分析）
   - 配置中心：Nacos（动态配置推送）
4. API 网关：Spring Cloud Gateway（WebFlux 响应式编程）
   - 路由转发（按合作方/按版本/按地域）
   - 统一鉴权（OAuth 2.0 + JWT + 双向 mTLS）
   - 限流（合作方维度/IP 维度/接口维度）
   - 灰度发布（按合作方灰度+按版本灰度）

三、数据拆分（分库分表）：
1. 拆分维度：
   - 订单库（按用户 ID 哈希分 256 库 × 16 表 = 4096 表）
   - 支付库（按订单号哈希分 32 库 × 8 表 = 256 表）
   - 司机库（按司机 ID 哈希分 64 库 × 8 表 = 512 表）
   - 乘客库（按用户 ID 哈希分 64 库 × 8 表 = 512 表）
   - 计价库（按订单号哈希分 32 库 × 8 表）
   - 优惠券库（按活动 ID + 用户 ID 分库分表）
2. 拆分中间件：ShardingSphere-JDBC（客户端轻量级）/ ShardingSphere-Proxy（代理端统一接入）
3. 拆分键选择三原则：高频查询字段、数据均匀分布、避免跨分片事务
4. 跨分片查询方案：
   - ER 表绑定（订单主表+订单明细表同分片）
   - 数据冗余（订单宽表复制查询字段）
   - Elasticsearch 二次索引（异步同步构建）
   - 应用层组装（聚合多个分片查询结果）
5. 读写分离：MySQL 1 主 8 从，ShardingSphere 路由读从库；主从延迟敏感业务强制走主库

四、数据一致性方案：
1. 强一致场景（订单创建+支付扣款）：Seata AT 模式（自动补偿） / TCC（Try-Confirm-Cancel）
2. 最终一致场景（订单状态同步/物流回传）：本地消息表 + RocketMQ 可靠消息 + 幂等消费
3. 跨服务长事务（订单+支付+调度+营销）：Saga 模式（编排式 Orchestration）+ 补偿子事务
4. 幂等性设计：所有写入操作携带业务唯一键（订单号/支付单号），通过唯一索引或 Redis 去重表防重

五、安全合规：
1. 等保三级五技术：物理环境+通信网络+区域边界+计算环境+管理中心
2. 数据加密：传输 TLS 1.3 + 存储 AES-256 + 敏感字段 SM4 国密 + 密钥管理 KMS/HSM
3. 数据脱敏：身份证/手机号/银行卡/地址静态脱敏 + 动态脱敏（API 返回前处理）
4. 访问控制：RBAC + ABAC 双层 + 字段级权限 + 合作方资源隔离
5. 审计日志：API 调用/数据库操作/管理操作全留痕，保留≥180 天，防篡改

问题二：订单创建流程设计

一、订单创建链路设计（8 步走）：
1. 第一步：API 网关接收请求
   - 路由到订单服务（Spring Cloud Gateway）
   - 鉴权（JWT Token 验证）
   - 限流（合作方维度 QPS 限流）
   - 监控埋点（生成 TraceId）
2. 第二步：风控服务前置校验
   - 乘客风险评分（黑名单/异常行为检测）
   - 司机风险评分（服务分/合规状态）
   - 风险等级评估（高/中/低）
   - 高风险订单直接拦截，返回错误码
3. 第三步：计价服务计算价格
   - 起步价+里程费+时长费+远途费+动态调价
   - 优惠券预校验（用户优惠券列表筛选可用券）
   - 营销活动叠加（满减/折扣/限时活动）
   - 返回最终价格明细
4. 第四步：订单服务创建订单（Seata AT 分布式事务起点）
   - 生成全局唯一订单号（Snowflake 雪花算法）
   - 写入订单主表（status=待支付）
   - 写入订单明细表
   - 写入优惠券占用记录（防止重复使用）
   - 写入营销活动使用记录
   - Seata AT 全局事务注册
5. 第五步：调用支付服务
   - 拉起支付（微信/支付宝/银联/钱包）
   - 等待用户支付
   - 支付回调：判断全局事务状态
6. 第六步：支付成功后调用其他服务
   - 司机调度服务（订单派单/抢单）
   - 优惠券服务（核销）
   - 营销服务（活动标记完成）
   - 通知服务（推送用户/司机）
7. 第七步：订单状态更新（Seata AT 事务提交）
   - 订单状态：待支付→已支付→已调度→已接驾→已完成
   - 全局事务提交
   - 写入订单日志（操作流水）
8. 第八步：返回订单创建结果
   - 返回订单号+支付结果+预计到达时间
   - 监控埋点（上报业务 KPI）
   - 日志记录（请求+响应+耗时）

问题三：数据库性能优化与多级缓存方案

一、数据库性能优化：
1. 慢查询治理：
   - 开启慢查询日志（slow_query_log，阈值 1s）
   - 识别 TOP 10 慢 SQL（SHOW PROCESSLIST）
   - SQL 优化：避免 SELECT *、避免函数转换、避免深分页（LIMIT 1000000,10 → 游标分页）
   - 索引优化：补充缺失索引、删除冗余索引、复合索引最左前缀
2. 索引设计：
   - 主键索引（订单 ID/支付流水号）
   - 唯一索引（业务唯一键防重）
   - 普通索引（高频查询字段：用户 ID、司机 ID、状态、时间）
   - 复合索引（WHERE + ORDER BY 联合索引）
   - 覆盖索引（避免回表查询）
3. 数据库架构优化：
   - 分库分表：256 库 × 16 表（4096 表），按用户 ID 哈希分片
   - 读写分离：MySQL 1 主 8 从（4 主 32 从集群）；ShardingSphere 路由读从库
   - 主从延迟解决：强制走主库（关键业务）+ 监控主从延迟（seconds_behind_master < 1s）
   - 数据库连接池：HikariCP（maxPoolSize=核心数×2）
4. 大表优化：
   - 历史订单归档（3 个月前订单迁移到 TiDB）
   - 冷热数据分离（热数据 MySQL + 冷数据 TiDB/OSS）
   - 定期 ANALYZE TABLE（更新统计信息）
   - OPTIMIZE TABLE（整理碎片）
5. 引入 TiDB：
   - 海量订单数据（PB 级）
   - OLAP 分析（订单统计/司机画像）
   - 兼容 MySQL 协议（应用无侵入）
   - HTAP 混合负载

二、多级缓存架构：
1. 三级缓存架构：
   - L1 本地缓存：Caffeine（纳秒级，几 GB 上限）
   - L2 分布式缓存：Redis Cluster（毫秒级，TB 级）
   - L3 持久化：MySQL + TiDB（10 毫秒级）
2. 缓存策略：
   - Cache Aside 旁路缓存（最常用，应用维护缓存）
   - Read/Write Through 读写穿透（缓存层维护数据库）
   - Write Behind 异步写入（性能最高但可能丢数据，金融慎用）
3. 缓存场景：
   - 用户信息（乘客/司机基本信息）：本地缓存 + Redis
   - 订单信息（订单详情）：Redis Cluster 50 节点
   - 优惠券信息（优惠券模板）：本地缓存
   - 计价规则（起步价/费率）：本地缓存
   - 营销活动（活动配置）：本地缓存 + Redis
   - 司机位置（GeoHash）：Redis GEO（5 秒过期）
4. 缓存一致性方案：
   - Cache Aside 先更 DB 再失效缓存（高一致性）
   - 延迟双删（删除缓存 → 更新 DB → 延迟 500ms 再删缓存）
   - binlog 订阅（Canal 监听 binlog 异步失效缓存）
   - 版本号 CAS（强一致场景）
5. 缓存三大问题：
   - 缓存穿透：布隆过滤器（拦截不存在的 key）+ 空值缓存（缓存 null 值短 TTL）
   - 缓存击穿：分布式锁（只允许一个线程回源）+ 逻辑过期（不设 TTL 后台异步刷新）
   - 缓存雪崩：TTL 随机化（基础 TTL + 随机偏移 60s）+ 多级缓存兜底 + 熔断降级
6. 缓存预热：
   - 系统启动时加载热点数据到本地缓存
   - 运行时定时刷新（每 5 分钟刷新一次热点数据）
   - 营销活动预热（提前加载活动配置到所有节点）
7. 缓存命中率优化：
   - L1 命中率 95%+（本地缓存热点数据）
   - L2 命中率 90%+（Redis 缓存常用业务数据）
   - L3 命中率 1%（数据库兜底）
   - 整体命中率 99.99%，数据库 QPS 降低万倍

三、热点数据识别与处理：
1. 热点识别：
   - 实时监控（Redis 监控 TOP 100 热点 key）
   - 历史数据分析（订单热点时段+热点用户+热点司机）
   - 业务预测（促销活动前提前预热）
2. 热点处理：
   - 多级缓存（本地+Redis+DB）
   - 限流保护（单 key 限流防击穿）
   - 数据分片（热点 key 分散到多个分片）
   - 异步加载（提前异步加载避免同步等待）

四、数据库连接池调优：
1. HikariCP 调优：
   - maximumPoolSize：核心数 × 2（CPU 密集型）/ 核心数 × 4（IO 密集型）
   - minimumIdle：核心数 × 1
   - connectionTimeout：30 秒（默认 30s）
   - idleTimeout：10 分钟
   - maxLifetime：30 分钟（小于数据库 wait_timeout）
   - validationTimeout：5 秒
   - connectionTestQuery：SELECT 1（验证连接可用）
2. Druid 调优：
   - initialSize：10
   - minIdle：10
   - maxActive：50
   - maxWait：60 秒
   - validationQuery：SELECT 1
   - testWhileIdle：true
   - testOnBorrow：false
   - testOnReturn：false

五、SQL 优化实战：
1. 案例 1：订单查询慢 SQL
   - 原始：SELECT * FROM orders WHERE user_id=? AND status=? ORDER BY create_time DESC LIMIT 20
   - 问题：缺少复合索引（user_id, status, create_time）
   - 优化：添加复合索引 → 查询时间从 800ms 降至 5ms
2. 案例 2：深分页查询慢
   - 原始：SELECT * FROM orders WHERE user_id=? ORDER BY create_time DESC LIMIT 100000, 20
   - 问题：OFFSET 100000 需要扫描 100020 行
   - 优化：游标分页 WHERE create_time < ? LIMIT 20 → 查询时间从 5s 降至 10ms
3. 案例 3：COUNT(*) 大表统计慢
   - 原始：SELECT COUNT(*) FROM orders WHERE create_time > ?
   - 问题：全表扫描
   - 优化：使用 Redis 计数器（订单创建时 INCR，订单取消时 DECR）

## 记忆口诀

微服务九大特性口诀：「单职独部技异数、轻重容进自」
- 单一职责+独立部署+技术异构+去中心化数据+轻量通信+容错+演进+自动化+自治

微服务 vs SOA 口诀：「微去心、SOA 总线」
- 微服务去中心化无 ESB；SOA 有 ESB 企业服务总线

微服务拆分四大策略口诀：「业能领事组扩展」
- 业务能力拆分（DDD）+领域事件+组织架构（康威定律）+可扩展性维度

服务发现三方式口诀：「客服注」
- 客户端发现（Eureka+Ribbon）+服务端发现（K8s Service+DNS）+注册中心（Consul/Nacos）

API 网关六职责口诀：「路鉴限协灰监」
- 路由+鉴权+限流+协议转换+灰度+监控

微服务反模式口诀：「分布式单体」
- 拆服务不拆数据库仍是单体思维

服务通信三大模式口诀：「同异事」
- 同步调用（REST/gRPC）+异步消息（Kafka/RabbitMQ）+事件驱动（EDA）

CAP 口诀：「P 是命，C 和 A 二选一」
- 分区容错 P 必选，实际在一致性 C 和可用性 A 间权衡

CP vs AP 系统口诀：「CP HB RC ZK，AP Cass EU CB」
- CP：HBase/Redis Cluster/ZooKeeper；AP：Cassandra/Eureka/CouchDB

BASE 口诀：「基本可用软状态，最终一致是方向」
- BA+S+E，三件套

强一致 vs 最终一致口诀：「强即时写、终会收敛」
- 强一致写后立即读到最新；最终一致保证收敛

共识算法三剑客口诀：「Pax Raft ZAB」
- Paxos（经典难懂）+ Raft（易懂，Leader+Follower+Candidate）+ ZAB（ZK 专用）

Raft 三阶段口诀：「选日安」
- Leader 选举+日志复制+安全性（任期 Term 单调递增）

Paxos 两阶段口诀：「Pre Acc」
- Prepare 阶段（提议者申请多数接受）+ Accept 阶段（接受者承诺接受）

ZAB 两模式口诀：「恢广」
- 恢复模式（Leader 崩溃后选主）+ 广播模式（Leader 广播 Follower 确认）

分布式锁三实现口诀：「Redis ZK 数据库」
- Redis（SETNX+过期时间+Token，Redisson 看门狗）+ ZK（临时顺序节点）+ DB（唯一索引）

分布式 ID 四方案口诀：「U 雪花 Leaf Redis」
- UUID（无序）+ Snowflake（1+41+10+12）+ Leaf 号段（美团）+ Redis INCR

分布式事务五方案口诀：「2PC 3PC TCC Saga Seata」
- 两阶段+三阶段+TCC（Try-Confirm-Cancel）+ Saga（编排式+链式）+ Seata（AT/TCC/Saga/XA 四模式）

Seata 四模式口诀：「AT TCC Saga XA」
- AT（自动补偿，0 侵入）+ TCC（业务侵入，强一致）+ Saga（长事务）+ XA（数据库 XA 协议）

TCC 三步口诀：「Try Confirm Cancel」
- Try（预留资源）+ Confirm（确认提交）+ Cancel（撤销释放）

Saga 两协调口诀：「编编排」
- Orchestration（编排式，中央协调器）+ Choreography（链式，事件触发）

本地消息表口诀：「业务消息同库写、定时扫发送」
- 业务表与消息表同库写入，通过定时任务扫描发送

幂等性口诀：「唯一键+去重表防重」
- 所有写入操作携带业务唯一键（订单号/支付流水号），通过唯一索引或 Redis 去重表防重

副本一致性三大协议口诀：「NWR Quorum 共」
- NWR 协议（N 副本 W 写入 R 读取，W+R>N）+ Quorum 多数派 + 共识算法（Paxos/Raft/ZAB）

数据同步三模式口诀：「异半全」
- 异步复制（性能高可能丢）+ 半同步复制（折中）+ 全同步复制（强一致性能差）

分布式锁三大属性口诀：「互死容」
- 互斥性（任一时刻只有一个客户端持有）+ 死锁避免（lock+过期时间）+ 容错性（节点故障锁仍可用）

Redisson 看门狗口诀：「30秒续期」
- 默认 30 秒自动续期一次，业务完成后手动释放锁

Redis 分布式锁实现口诀：「SETNX EX Token 校验删」
- SETNX（SET if Not eXists）+ EX 过期时间 + 唯一 Token（防误删）+ 释放锁校验 Token

限流四算法口诀：「计令漏滑」
- 计数器（固定/滑动窗口）+ 令牌桶（Token Bucket，平滑）+ 漏桶（Leaky Bucket，匀速）+ 滑动日志（精确）

限流五维度口诀：「QPS 并关 IP 合作」
