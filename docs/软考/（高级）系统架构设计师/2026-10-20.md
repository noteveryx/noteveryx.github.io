# 系统架构设计师 · 第63次学习（2026-10-20）

主题：架构风格与模式、架构决策记录、遗留系统演进、架构治理与技术雷达、模块化单体与微服务权衡

## 今日核心概念

### 1. 架构风格与架构模式

定义：架构风格（Architectural Style）是构件与连接件在系统中的**组织范式**，描述"系统由什么构成、构件如何交互"的结构性约定；架构模式（Architectural Pattern）是风格的具体化，给出可复用的**问题—解决方案对**，并附带约束、后果与适用条件。风格偏"语法规则"，模式偏"带代价的完整方案"。

关键要点：
- 经典风格七类：管道—过滤器（Pipe-Filter，每个过滤器职责单一、输出即下一个输入，如编译器流水线、日志采集清洗链路）、分层（Layering，严格自上而下或允许反向调用，如网络七层、三层架构）、客户机—服务器（C/S）、发布—订阅（Pub-Sub，发布者与订阅者通过中介解耦，支持异步、可变订阅关系，是事件驱动架构的骨架）、模型—视图—控制器（模型承载数据与规则、视图负责呈现、控制器处理输入，派生自交互式界面）、微服务（Microservices，独立部署、独立数据、按业务能力划分）、事件溯源（Event Sourcing，以不可变事件序列作为唯一事实来源，状态由事件重放得出）、微内核（Microkernel，核心最小化、插件化扩展，如操作系统与浏览器）。
- 风格选择即质量属性取向：管道—过滤器利于可重用与可维护但控制流分散；分层利于变更隔离与团队分工但可能造成跨层调用与性能损耗；发布—订阅利于解耦与异步削峰但引入最终一致性与链路排查成本；事件溯源利于审计回溯但存储与查询复杂度上升。
- **架构风格与质量属性的映射关系是高频考点**：要求"高可用、易扩展、弱耦合、可审计"→ 优先事件驱动/发布—订阅 + 服务化；要求"强一致、严格事务"→ 集中式分层 + 单一事务边界；要求"批流一体、低成本存储"→ 管道—过滤器 + 湖仓分层。
- 常见误区：把技术栈（如是否用某个框架）当成架构风格；把架构模式当成"套路照搬"，忽略模式自带的后果（约束与权衡）。

### 2. 架构决策记录与架构原则

定义：架构决策记录（Architecture Decision Record，ADR）是**一份轻量文档**，记录某项重要架构决策的上下文背景、候选方案、最终选择、后果影响与状态（提议中／已接受／已废弃／已替代），用于保留决策的推理链条，避免后人重复讨论、推翻无据。架构原则是一组**可判定的约束语句**，为后续设计提供统一裁决依据。

关键要点：
- 架构原则必须"可判定"：写"系统应具备高可用性"无效，写"单可用区故障时核心交易链路不丢单、RTO 不超过 30 秒、RPO 为零"才是可判定原则。
- ADR 典型结构：标题（一句决策）、状态、上下文与问题、备选方案及取舍、决策结论、正面与负面后果、关联决策编号；一份决策一张单，便于检索与回溯。
- 决策类型：技术选型类（关系库与文档库取舍）、边界划分类（哪些业务留在单体、哪些拆分）、质量属性优先级类（一致性优先还是可用性优先）、数据策略类（读写分离、分库分表、冷热分层）、安全合规类（等保三级、商用密码改造）。**架构评审的争议多数不是技术之争，而是优先级排序之争**。
- 原则落地机制：原则写入《架构规范》并在设计评审、代码扫描、流水线检查中作为准入门禁；原则随架构演进修订，但修订本身必须走决策记录，避免"悄悄改原则"。
- 常见考点：ADR 不替代设计文档，它记录的是"为什么这么选"；一个决策被替代时，新记录应"引用并取代"旧记录，旧记录状态改为"已替代"而非直接删除。

### 3. 遗留系统演进策略

定义：遗留系统演进策略是在**不停机、不中断业务**的前提下，逐步把老系统替换为新架构的一组工程手段组合，核心矛盾是"业务不能等"与"架构必须改"。

关键要点：
- 五大策略：
  - **绞杀者模式**（渐进替换）：在老系统外围建立新系统，通过路由层把流量按功能、租户、用户逐步切到新实现，新功能只在新系统上做，老代码随迁移完成自然腐化下线。适合边界清晰的模块，周期长但风险最低。
  - **防腐层**（隔离层）：在遗留系统与新模型之间加一层转换与适配，把两套不一致的领域模型、编码规则、接口语义隔离开，防止外部概念污染核心域，也防止遗留的坏模型扩散。防腐层是**隔离而非翻译全量**，只暴露新系统所需能力。
  - **双写与数据同步**：新旧系统同时写入，靠变更数据捕获或消息订阅保持一致，再以对账校验修正；迁移期必须有"幂等 + 校验 + 修复"三件套，双写必须处理循环依赖与失败补偿。
  - **抽象分支**：对同一业务在主干上分叉出一条独立演进路径（维护双版本），成熟后合并或替换主干；代价是长期双维护。
  - **重构式替换**：离线一次性重写替换，风险最高，一般只适合边界极清晰且规模可控的模块，通常配合并行运行与数据校验工具。
- 绞杀者的实施要点：先做**流量入口统一**（网关路由），再按"低风险功能 → 高频核心功能 → 长尾功能"排序；每次切换必须可秒级回滚；老系统下线前完成数据归档与审计留痕。
- **迁移判据**：当某功能的读写已全部由新系统承载、老库表已无调用方、且可删除整段代码而业务无感时，方可下线。常见错误是"切了流量就删库"，导致回滚无路。
- 迁移期的双写一致性只能做到"最终一致"，对外承诺 SLA 时必须显式区分：哪些场景允许秒级延迟，哪些场景必须同步双写成功。

### 4. 架构适应度函数与技术雷达

定义：架构适应度函数（Fitness Function）是把**架构质量属性变成持续自动校验的规则**，在构建流水线中反复执行，用"可执行指标"守住架构约束，防止架构腐化；技术雷达（Tech Radar）是按**采用决策分区**对技术项进行分类的可视化工具，用于统一技术选型态度。

关键要点：
- 适应度函数两类：**静态校验**（依赖分析检查禁止模块间越层调用、接口契约一致性、数据库访问规范）与**动态校验**（压测指标响应时间、故障注入验证降级生效、混沌演练验证恢复时间、可观测性指标埋点覆盖率、依赖漏洞扫描）。例：某订单服务禁止直连他人数据库，流水线自动扫描代码并阻断。
- 技术雷达四个分区：**采用区**（已验证、鼓励使用）、**试验区**（有前景、限场景试点）、**评估区**（值得研究、暂不进生产）、**暂缓区**（淘汰，不再新增、逐步下线）。同时标注"领域维度"（技术／工具／平台／语言）与"环（Ring）"的推进。
- 雷达使用纪律：任何技术进入采用区必须经过真实生产验证与团队能力评估；暂缓区的技术必须给出下线计划与例外审批，否则雷达形同虚设。
- 架构治理配套：**架构中心团队**（制定规范、评审、沉淀模板与资产，不直接承接业务开发）、**架构评审机制**（新系统立项评审、重大变更评审、定期架构体检）、**技术资产复用**（脚手架、中间件、通用组件库）。
- 康威定律与逆康威设计：组织沟通结构决定系统架构；同时用平台化、中台化、通用能力沉淀来**逆向影响组织**，减少重复造轮子。

### 5. 模块化单体与微服务权衡

定义：模块化单体（Modular Monolith）是**单一部署单元、内部按严格边界模块化**的系统：一次构建、一次发布，但模块之间只能通过显式接口通信、数据归属唯一，禁止跨模块直接访问表；微服务是"独立部署 + 独立数据 + 围绕业务能力自治"的分布式形态。两者是连续谱上的不同取舍点，不是非此即彼的对立。

关键要点：
- 模块化单体优势：本地调用延迟低、事务天然一致、部署与调试简单、分布式复杂度归零；前提是**模块边界靠强制机制守住**（构建期依赖检查、表访问权限、接口发布契约）。
- 微服务必要条件：团队已拆分到需要独立交付节奏、存在明显的容量差异热点、必须有独立可用性边界的核心链路；没有这三者，拆分只会把代码耦合换成网络耦合，联调和一致性成本更高。
- 典型演进路径：**单体 → 模块化单体（先理边界）→ 服务化拆分（后拆部署）**。跳过第一步直接"微服务改造"，往往导致拆分依据是"表结构"而非"业务能力"，形成分布式单体。
- 判断健康度：模块化单体看**依赖方向是否单向、是否存在跨模块直连表**；微服务看**是否退化为分布式单体**（服务间共享库表、接口无版本、发布需联动、故障相互拖累）。
- 服务粒度准则：一个服务对应一个清晰的业务能力或限界上下文；对齐组织（团队能完整拥有该服务的开发、发布、运维），避免出现"一个服务三团队共同改"。

## 案例分析题

**题目**：

某省政务服务"一网通办"平台建成于2018年，为单体架构（Java + 单库单表），承载全省2000万注册用户、日均80万办件量。业务逐年增长，暴露三类问题：一是办件高峰期（月初、季末集中申报）系统卡顿，扩容只能整库主机升级，成本高；二是近三年新增 27 个垂直领域应用，全部直连老库，共 150 多张表被多方读写，任何一次表结构变更需通知十几次，发布一次超过 6 小时；三是原厂商已停止维护，老代码无人能改。

现计划用两年时间完成架构升级，替换为微服务架构，但要求**业务不中断、老数据不能丢、新旧可回退**。请你作为总架构师回答：
1. 改造过程中你会选用哪些架构风格与架构模式？分别解决什么问题？
2. 说明从现有单体到微服务的具体演进路线，列出阶段划分与每阶段的回退方案。
3. 设计用于守住架构约束的"架构适应度函数"，至少给出四条。
4. 针对 27 个垂直应用的接入，说明你如何避免产出"分布式单体"。

**参考答案**：

**1. 架构风格与模式选择**

- 数据写入与状态记录：引入**事件溯源风格**，把"办件受理、材料变更、审批流转"记录为不可变事件流，落入消息中间件与事件存储，天然支撑审计回溯（政务强审计要求），也便于后续重放生成新视图。这是应对"27 个应用直连老库"的核心手段——**读模型可以多份、唯一事实来源只有一个**。
- 服务间协作：主体采用**发布—订阅事件驱动风格**，垂直应用订阅办件事件而非同步调用老系统，实现松耦合与异步削峰，避开高峰时段同步链路的耦合瓶颈；跨服务强一致场景（如扣费、缴费）保留同步调用并配合补偿。
- 单体内部：先做**分层风格**（接入层／应用层／领域层／持久层），领域层禁止跨模块直连下层，为后续拆分"留好缝"，这是抽丝剥茧式拆分的必要前置。
- 遗留对接：采用**微内核风格 + 防腐层**，在老库前建立防腐层，把老系统的 150 张表、老编码规则、老接口语义收敛为面向领域的稳定契约，垂直应用只面向防腐层编程，不再感知老模型。
- 入口治理：网关统一入口，按**业务能力/租户/垂直应用**做流量路由，是绞杀者模式落地的控制点。

**2. 演进路线（阶段划分 + 回退）**

- 阶段一（0-3个月，缝合期）：代码内分层，强制模块依赖方向（构建期校验）；建立全链路可观测与统一日志链路；对 150 张表做资产登记，标注读写方、责任人；引入防腐层，老系统只允许通过防腐层对外。此阶段不改业务，老库仍为唯一事实来源。**回退**：无业务变更，纯工程手段，直接回退分支。
- 阶段二（3-9个月，双轨期）：办件受理主链路采用**双写 + 事件订阅**：老系统仍是权威源，同时把关键领域事件投递到消息中间件；在新系统侧**建立独立只读视图库**供垂直应用消费，老系统零改造即可供给数据。**回退**：关停事件订阅消费者，回到直连老库模式，视图库可随时重建。
- 阶段三（9-15个月，切流期）：按"低风险功能 → 高频核心功能 → 长尾功能"排序，用网关逐功能、逐租户灰度切流，每批切流前跑数据一致性对账（双写差异率、办件状态一致性校验）。此阶段老库对应模块转为只读或停写。**回退**：网关路由规则秒级回切到老系统；老库保持可写窗口期内数据双向补偿。
- 阶段四（15-18个月，下线期）：完成全量功能切流、老库模块归档与历史数据入仓、审计留痕具备后，才下线老代码与老表；对外只保留归档查询能力。**回退**：此阶段起仅支持向前修复，不支持回切（须在切换前与业务方书面确认）。
- 全程约束：任何阶段不满足一致性对账与性能基线，立即中止本批切流；禁止一次性全量切换。

**3. 架构适应度函数（四条以上）**

- 静态一：依赖方向校验——构建期扫描，领域层不得直接依赖持久层，模块间只允许通过公开接口依赖；越层调用直接阻断流水线。
- 静态二：数据库访问规范——任何服务不得直接连接他人数据库，扫描代码中的数据源配置与连接串，命中即失败；新服务建库必须走评审与登记。
- 动态三：事件契约校验——事件结构向后兼容检查（新增字段可选、禁止删除与改类型），Schema 注册中心在发布时自动比对，破坏性变更阻断发布。
- 动态四：可观测性指标——核心链路埋点覆盖率不低于 95%，链路追踪采样率与日志完整率达标，未达标不允许进入切流批次。
- 动态五：容量与弹性——核心服务在双十一级峰值压测下 P99 响应时间与错误率达标；单可用区故障演练下核心链路 RTO ≤ 30 秒、RPO 为零，未达标不予发布。
- 动态六：降级熔断有效性——定期故障注入验证熔断、降级、限流真实生效，而非只配置未验证。
- 动态七：安全合规——等保三级要求项与商用密码使用合规扫描、依赖组件漏洞扫描（高危必须阻断）。

**4. 防止"分布式单体"的具体做法**

- 按**业务能力与限界上下文**切分，而不是按表切分；切分前先输出领域划分文档并评审，确认每个服务的业务语义、数据归属与负责人。
- **数据归属唯一**：每个服务独占自己的库与表，通过事件或查询接口对外提供数据；禁止跨服务直连、禁止共享库表。
- **契约先行**：所有对外接口与服务间事件必须版本化并登记，接口变更走评审与兼容期，禁止无版本改造。
- **契约化替代同步依赖**：垂直应用以订阅事件为主，减少跨服务同步调用链，避免一个垂直应用故障拖垮主链路。
- **独立交付验证**：以"能否单服务独立发布而不需联动"作为验收标准；无法独立发布的合并回同一服务。
- **组织对齐**：一个服务对应一个可完整负责其开发、发布、运维的团队，避免多团队共改导致耦合。

**踩分要点**：
- 阅卷常按踩分点给分，以下关键词必须出现：**事件溯源 / 不可变事件、发布—订阅 / 事件驱动、松耦合、防腐层、绞杀者、双写与一致性对账、灰度切流与秒级回滚、数据归属唯一、模块化单体先行、适应度函数（静态与动态）、技术雷达分区、康威定律、分布式单体判别标准、契约版本化**。
- 只写"采用微服务"不给分的，必须说明**为什么选、解决了哪个具体问题**（如削峰解耦、审计回溯、数据归属治理）。
- 演进路线的分值点在于"分阶段 + 每阶段有回退方案 + 不停机不停业务"，只列技术清单最多得一半分。
- 适应度函数只写"代码审查""单元测试"这类通用项不加分，必须写成**可执行、可阻断**的具体规则（含指标与阈值）。
- 常见失分：忽略审计与信创等保合规要求、忽略老系统原厂停止维护带来的知识流失风险、遗漏停写老库前的一致性校验与归档。

## 记忆口诀

**架构风格口诀**：管道过滤走流水线，分层叠罗汉，客户端服贴得紧；发布订阅解耦妙，微服独立各自跑，事件溯源溯无漏，微核插件小而巧。

**决策记录口诀**：一决策一档案，状态五态记清楚（提议／接受／废弃／替代／复审），替代不删旧，只述不再议。

**遗留演进口诀**：先缝后绞再绞后绞——先分层缝合，后防腐隔离，再绞杀切流，末下线归档；绞杀三原则：路由统一、低风险先行、灰度秒回；双写两件套：幂等校验与补偿对账。

**治理口诀**：雷达四区采用试评停，适应度函数两条腿——静态门禁管依赖，动态演练管指标；康威定律组织定架构，逆康威设计靠平台。

**粒度口诀**：模块化单体先理边界，服务化拆分看三必要——交付节奏、容量热点、可用边界；跳过模块边界直接拆微服务，拆出分布式单体最难救。
