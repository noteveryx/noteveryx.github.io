## 今日核心概念
### 1. DDD 战略设计（Strategic Design）
定义：从业务全景出发划分问题域，识别核心域、支撑域、通用域，划定限界上下文（Bounded Context），在上下文之间定义明确的协作关系（Context Map），避免"大泥球"架构。
关键要点：
（1）子域三分类：核心域（业务核心竞争力，企业自研）、支撑域（自研或外包但非核心）、通用域（建议采购 SaaS，如短信、邮件、支付）。
（2）限界上下文：语义的边界，同一名词在不同上下文中含义不同（如"商品"在库存上下文指 SKU，在订单上下文指交易快照）。
（3）上下文映射七种：共享内核（Shared Kernel）、客户-供应商（Customer-Supplier）、防腐层（Anti-Corruption Layer，ACL）、开放主机（Open Host Service，OHS）、发布语言（Published Language）、合作（Partnership）、各行其道（Separate Ways）。
（4）ACL 防腐层：上下文之间通过 DTO 转换器隔离，防止外部模型侵入核心域；本质是"领域翻译官"。

### 2. DDD 战术设计（Tactical Design）
定义：在限界上下文内部构建战术构件，包括实体、值对象、聚合根、领域服务、领域事件、仓储，把业务逻辑封装在领域层而非贫血的 Service 类里。
关键要点：
（1）实体（Entity）：有唯一标识（ID）+ 生命周期可变状态，标识跨时间稳定。
（2）值对象（Value Object）：无标识、不可变（创建即确定）、可替换（关注属性而非身份），如金额、地址、时间段。
（3）聚合根（Aggregate Root）：一致性边界，外部对聚合内对象的访问必须经过聚合根；一笔事务只能修改一个聚合。
（4）领域事件（Domain Event）：用过去时态命名（如 OrderPlaced），解耦跨聚合协作；落地通过事件总线或 MQ。
（5）领域服务（Domain Service）：跨聚合业务逻辑（不属于任何单一实体）。
（6）仓储（Repository）：聚合根级别的持久化抽象，聚合内部对象不单独暴露 Repo。

### 3. CQRS 命令查询分离
定义：将读写模型解耦为命令端（Command，写模型，强一致）和查询端（Query，读模型，最终一致），通过领域事件或消息中间件异步同步数据。
关键要点：
（1）适用场景：读写比例严重失衡（如 1:100）、查询维度复杂多变、性能要求差异大（写强一致读高并发）。
（2）读模型可异构：MySQL 写 + Elasticsearch 全文检索 + ClickHouse 实时分析，每个读模型按查询形态定制。
（3）同步延迟：通常毫秒到秒级，对应最终一致性；下单秒付场景应使用同步事务避免用户感知。
（4）风险：数据漂移、幂等补偿、版本回滚处理复杂。

### 4. 事件溯源 Event Sourcing
定义：不保存对象的当前状态，而是保存所有领域事件组成的"事件流"，通过重放事件得到当前状态，事件是事实的不可变记录（Event as Fact）。
关键要点：
（1）事件不可变（Immutable）：发生过的事不可修改，仅可追加；天然审计、合规、追溯。
（2）聚合根从事件流"投影"出当前状态：state = reduce(events)。
（3）快照（Snapshot）：定期保存状态加速重放，避免每次从零拉取。
（4）配合 CQRS：写端事件追加，读端通过 Projection 物化视图。
（5）挑战：schema 演进（事件升迁 Upcasting）、事件版本管理、删除与隐私（GDPR 被遗忘权的折衷是"资金账户重置事件"而非删除）。

### 5. 微服务拆分原则与反模式
定义：将单体应用按业务边界拆分为独立部署、独立演进的小服务；拆分要"恰到好处"，过细变成分布式单体。
关键要点：
（1）三大拆分维度：业务（按限界上下文）、质量（性能瓶颈模块单独拆、变更频繁模块单独拆）、团队（康威定律，团队边界对齐服务边界）。
（2）拆分反模式：分布式单体（强耦合、链式调用、共享数据库）、纳米服务（10 行代码也独立部署，运维地狱）、绞杀者模式缺失（直接重写爆炸）。
（3）拆分方法：绞杀者模式（Strangler Fig，逐步用新服务替换老接口）、领域事件先行（先解耦通信再拆库）、领域共创（事件风暴 EventStorming 工作坊）。
（4）服务粒度判断：单一职责 + 独立可部署 + 团队规模（两 pizza 团队）+ 性能要求差异化。

### 6. Saga 长事务与分布式事务
定义：跨多个微服务/聚合根的业务一致性通过 Saga 编排实现，本地事务 + 补偿事务，最终一致性替代 ACID 强一致。
关键要点：
（1）两种实现：编排式（Orchestration，集中式协调器 Send/Reply 易理解但耦合高）、协调式（Choreography，去中心化基于事件但流程分散难调试）。
（2）补偿策略：可补偿事务（如取消订单退款）+ 关键事务不可补偿（如已发货）；后者要前置风控+幂等重试。
（3）幂等三要素：唯一业务键（订单号）、状态机（避免重复处理）、结果缓存。
（4）适用边界：跨服务强一致要求高、补偿成本高、调用链路短的场景应改回 TCC 或本地消息表，避免滥用 Saga。

### 7. 微服务可观测性三大支柱（关联 10-12 OTel 主题）
定义：Metrics（指标）、Logs（日志）、Traces（追踪）三者通过统一 TraceID + 关联 ID（CID、SpanID、ParentSpanID）打通，形成完整诊断链。
关键要点：
（1）日志：结构化（JSON 字段，含 trace_id/span_id/user_id/level）；ELK / Loki / 阿里云 SLS。
（2）指标：RED 方法（Rate 请求率 + Errors 错误率 + Duration 时延）+ USE（Utilization 资源使用率 + Saturation 饱和度 + Errors 错误数）+ 业务黄金指标。
（3）追踪：调用链、慢请求根因定位、依赖拓扑自动生成。
（4）关联：每条请求入口生成 trace_id，沿 HTTP Header（traceparent W3C Trace Context）向下穿透；日志里写 trace_id，指标标签写 service + endpoint，反向定位效率极高。

## 案例分析题
**题目**：某电商平台日均订单 800 万，促销日峰值 5000 万，业务包括订单、商品、营销、库存、支付、物流六大领域。当前为单体应用（Java + Spring + Oracle），性能瓶颈集中在订单与库存，每年双 11 都因热点商品超卖引发客诉。CTO 决定采用微服务架构，要求：
（1）每个促销日不能超卖，库存扣减强一致；
（2）订单状态变更与下游物流、积分、营销解耦；
（3）服务出现部分故障时不影响下单主链路；
（4）数据隔离严格，不能跨服务直接访问对方数据库；
（5）平均团队 8 人，共 5 个团队负责不同领域。

请用 DDD + 微服务架构思想给出方案，需覆盖：子域划分、限界上下文、聚合根设计、关键流程（如下单、库存扣减、订单取消）的协作方式、一致性策略、可观测性方案，并指出至少 3 个常见的反模式及规避方法。

**参考答案**：
一、子域划分（DDD 战略）
- 核心域：订单、商品、营销（核心竞争力自研）
- 支撑域：库存、支付、物流
- 通用域：账号、消息推送（采购 SaaS）

二、限界上下文与上下文映射
- 订单上下文（聚合根：Order，实体：OrderItem / OrderStatus，值对象：Money / Address）
- 库存上下文（聚合根：Stock，实体：StockLog；ACL 防腐层将商品 SKU 翻译为本上下文内部 ProductID）
- 商品上下文（聚合根：Product，提供 OHS 开放主机 + Published Language，订单上下文仅依赖商品 API 不直连库）
- 上下文映射：订单→库存（Customer-Supplier + ACL）、订单→商品（OHS）、订单→营销（事件驱动）

三、订单聚合根设计
- 聚合根：Order（订单号 + 生命周期状态机 + 商品列表 + 金额）
- 实体：OrderItem（商品项）、PaymentRecord（支付记录）
- 值对象：Money（金额）、Address（收货地址）、CouponDiscount（优惠折扣）
- 领域事件：OrderPlaced（已下单）、OrderPaid（已支付）、OrderCancelled（已取消）、InventoryReleased（库存释放）

四、关键流程
1. 下单流程（编排式 Saga）
   - Step1：订单上下文本地事务创建订单（状态=已下单、预留库存引用号）
   - Step2：发布 InventoryReserveRequested 事件，库存上下文本地事务预占库存 → 发布 InventoryReserved
   - Step3：订单上下文订阅 InventoryReserved → 更新订单状态为已确认
   - 补偿：5 分钟内未收到 InventoryReserved 触发订单自动取消 + 释放预占（T+5 min 定时扫描）
2. 库存扣减（强一致）
   - Redis Lua 原子脚本（Lua 脚本包含 GET + DECR + 写流水三步，单线程执行）：KEYS=[stock:sid:{skuId}]，预占成功后落 MySQL 流水表，异步同步到库存聚合根；促销日 99 个分片抵消热点 key
3. 订单取消流程
   - 调用库存上下文回滚预占库存；调用营销上下文扣减已使用优惠券；调用支付上下文发起退款；任一步失败进入"挂起订单"队列人工补单

五、一致性策略
- 强一致（Redis Lua + MySQL 流水）：库存预占、退款
- 最终一致（事件溯源 + MQ）：订单状态流转、营销积分发放、物流通知
- 读模型 CQRS：订单写 MySQL + 同步 Canal 写 ES 供商家后台搜索；用户订单历史用 ClickHouse 多维分析

六、可观测性方案
- 统一 TraceID：使用 OpenTelemetry SDK 自定义 Injector，traceparent Header 沿 Spring Cloud Gateway → Sentinel → OpenFeign → RocketMQ Producer → Consumer 整条链路透传
- 日志：Logback JSON 编码器，含 trace_id / span_id / order_id / sku_id，P99 慢查询 200ms 上报
- 指标：Prometheus + Grafana，RED 三个指标（订单 QPS、错误率、P99 时延）+ USE 资源指标（Tomcat 线程池活跃数 + DB 连接池使用率 + JVM 老年代使用率）+ 业务指标（订单创建成功率 / 超卖次数 / 支付转化率）
- 告警：SLO 99.95%，错误预算耗尽 50% 自动降级（关闭非核心路由）

七、反模式规避（至少 3 个）
1. 分布式单体：禁止服务之间共享数据库（通过账号权限隔离 + Schema 隔离）；禁止跨服务长链路同步调用（>2 跳改用 MQ 事件）
2. 纳米服务：聚合根颗粒度为单元，单聚合根 200~500 行代码，独立部署但不必每个实体一服务
3. 绞杀者模式缺失：以订单服务为试点先拆，先解耦通信（MQ 替换 RMI）再拆库；新老系统并存 6 个月逐步切流
4. 过度 Saga：库存扣减与下单放在同一聚合根或共享 saga，对账改为本地事务 + 异步写日志

**踩分要点**：
- 写出核心/支撑/通用三类子域并准确分类；
- 限界上下文中给出聚合根、实体、值对象；
- 库存强一致必须出现 Redis Lua 原子脚本；
- 编排式 Saga + 补偿机制 + 防悬挂订单策略；
- TraceID 贯穿 + RED 指标 + 错误预算；
- 反模式：分布式单体、纳米服务、过度 Saga、缺乏 ACL；
- 加分：Saga vs TCC vs 本地消息表的取舍；
- 加分：CQRS 在订单/商家后台的读模型分层。

## 记忆口诀
**DDD 战略四件套**：子域三分类（核心支撑通用），限界上下文划清，映射七招看场景，ACL 防腐不可少。

**子域三字诀**：核（核心域自研）、支（支撑域轻自研）、通（通用域买 SaaS）。

**战术六宝**：实值聚服事仓（实体、值对象、聚合根、领域服务、领域事件、仓储）。

**聚合根规则**：外访问必经根，单事务改一根，根内不变对外严。

**CQRS 读写诀**：写强一致读高并发，事件总线串两端，读模型按查询形态建。

**事件溯源四特性**：事件即事实、追加不可改、状态由重放投影、快照加速重放。

**Saga 两式选择**：编排易理解耦合高，协调去中心流程散；短链补偿成本低用 Saga，关键不可补偿换 TCC。

**拆分两反**：分布式单体（共享库+链式调用）、纳米服务（十行代码也拆服务）。

**防腐层原则**：外部模型不进门，DTO 转换做翻译，Context 之间 ACL 是城墙。

**可观测三柱口诀**：指标看趋势、日志看细节、追踪看路径；三柱靠 TraceID 串。

**超卖双保险**：DB 行锁 + Redis Lua 原子；缓存预占库存，异步落流水。
