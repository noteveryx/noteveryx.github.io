## 今日核心概念

### 1. CAP 定理的精确辨析与一致性模型谱系

定义：CAP 定理是 Gilbert 与 Lynch 提出的分布式系统设计约束，用于回答"当网络分区发生时，系统必须在一致性与可用性之间做出取舍"这一根本问题；一致性模型谱系则是描述"多副本数据在并发读写下对外呈现何种可观察语义"的分级体系，从线性一致性一路递减到最终一致性，中间还有会话保证这一工程上最常用的档位。

关键要点：
- **三个性质的严格定义**：Consistency 在 CAP 中特指**线性一致性**（所有副本在同一时刻对外表现一致），不是 ACID 里那个指"事务完整性"的 C；Availability 的严谨含义是"每个请求在有限时间内收到一个非错误响应"，即"系统繁忙/降级提示"也属于不可用；Partition Tolerance 指系统在网络分区（部分节点互相不可达）下仍能继续按既定规则正确运行。
- **"三选二"是通俗化误传**。P 不是可选项——分布式系统必然存在分区可能，真实决策发生在分区发生的那一刻：**牺牲 C**（转异步复制，允许读到旧值）或**牺牲 A**（拒绝请求、进入只读降级或直接报错）。在无分区的正常时段，C 与 A 是可以兼得的。
- **常见误区清单**（案例题高频陷阱）：
  1. 把 CAP 的 C 与 ACID 的 C 混为一谈——前者是副本一致性，后者是事务原子性/完整性，二者判定对象不同。
  2. 把"三选二"当成选型结论——真实选型是"分区发生时的行为选择"，而绝大多数互联网系统选的是**牺牲 C 保 A**。
  3. 把"最终一致"当作"没有一致性"——最终一致仍是明确的一致性模型，有收敛保证；不可接受的是"不收敛"。
  4. 忽略 Availability 与可用率指标的区别——CAP 的 A 是语义定义，SLA 的 99.99% 是工程指标，二者不可互相推导。
- **PACELC 扩展**（Daniel Abadi）：若发生 Partition 则在 A 与 C 间取舍，**否则（Else）**在 Latency 与 Consistency 间取舍。它解释了为什么正常网络下强一致读的代价很高——多数系统在没有分区时就已经选择了低延迟的弱一致读写，正是为了把关键路径的延迟压到最低。
- **一致性模型谱系（由强到弱）**：
  - **线性一致性**：全局存在单一操作顺序，且尊重"真实时间"先后（客户端 A 的写完成后客户端 B 的读必须能看到）。
  - **顺序一致性**：存在全局单一顺序，但不强制尊重实时先后（并发操作可交换）。
  - **因果一致性**：有因果关系的操作保持因果序（先发消息后发评论，评论不能先显示），并发无关操作可乱序。
  - **最终一致性**：无新写入后各副本最终收敛到同一值。
  - **会话保证（Session Guarantees）**：把一致性约束限定在单个会话内，工程上最常用，包含**单调读、单调写、写后读（Read-Your-Writes）、因果一致性保证**四项。
- **弱一致性的业务后果必须能说清**（答题时体现"技术—业务"映射）：写后读不满足 → "提交后刷新看不到"的投诉与重复提交；单调读不满足 → 翻页出现"已消失"的记录、购物车数量倒退；因果一致性不满足 → "消息已发但评论不显示""回复早于原帖"；最终一致不保证 → 多端数据长期不一致、指标与明细对不上。
- **实现代价**：线性一致写需要多数派确认（延迟至少含多数派 RTT），会直接压缩吞吐上限；线性一致读可通过 **ReadIndex / Lease 读**（先向 Leader 确认领导权与提交位点，再本地读）避免每次读都走多数派写，兼顾一致性与读扩展。
- **考点提示**：问"CAP 中 C 与 ACID 中 C 有何区别""分区发生时你的系统怎么取舍"时，标准答法是——CAP 的 C 限定副本线性一致，ACID 的 C 指事务约束不被破坏；本系统在分区时选择牺牲一致性（关键交易走多数派强一致，非关键读走本地副本）以保可用性，并用对账与补偿闭环最终收敛。

### 2. 分布式共识算法：Paxos、Raft 与脑裂治理

定义：共识（Consensus）是指在存在节点故障与网络分区的条件下，让一组副本对一系列日志或值的顺序达成一致的分布式计算问题；Paxos、Raft、ZAB 等共识算法是分布式数据库、配置中心、选主服务与协调服务的核心机制，其作用是**在不确定的网络中，用多数派换取"不会做出两个相互冲突的决定"**。

关键要点：
- **共识三属性**：Agreement（无冲突，不允许两个进程决定不同的值）、Validity（被决定的值必须是某个提议者提出的合法值）、Termination（在多数派存活且网络最终恢复的前提下算法必须终止）。
- **FLP 不可能结论**：异步系统中只要存在一个节点可能失效，就不存在"总能在有限步内达成一致"的确定性算法。工程解法三条：引入**超时假设**（把无响应视为故障）、**随机化**（打破对称性）、**部分同步假设**（网络最终会恢复）。这条结论直接决定了共识算法的设计取向——**安全性优先于活性**：宁可暂时不可用，也不产生冲突决定。
- **多数派（Quorum）原则**：设总副本数 N=2F+1，则最多容忍 F 个节点故障；写操作需至少 ⌊N/2⌋+1 确认，多数派写成功；强一致读需读取至少 ⌊N/2⌋+1 个副本（或用 ReadIndex）。**R+W>N 且 R+W>N 且 R+W>N**——标准表述是读写副本数之和不小于总副本数（更严格的隔离性要求是 R+W>N，即读集与写集交集可能为空），这是保证读己之写与单调读的经典条件。多数派机制本身即"防双主"的第一道防线：分区时少数派无法凑齐多数派，因此无法提交写入。
- **Paxos 核心**：两阶段 Prepare/Promote，角色为 Proposer / Acceptor / Learner；Multi-Paxos 通过选出唯一 Leader 复用 Phase 1 达成稳态优化；活性靠 Leader 选举与虚拟节点兜底。
- **Raft 核心（当前主流，需掌握细节）**：
  - 三大组件：Leader Election、Log Replication、Safety。
  - 关键术语：**任期（Term）单调递增**、日志条目、commitIndex、lastApplied。
  - 选举限制：每个任期最多一个 Leader；候选人日志必须至少与 Leader 日志一样新（比较 lastLogTerm 优先、再比 lastLogIndex）才能当选。
  - 提交规则：Leader 必须**先在当前任期提交至少一条日志**，才能间接提交旧任期的日志（这是 Raft 安全性最容易被忽略的一条，也是"Leader Completeness"成立的前提）。
  - 日志匹配性质与状态机安全：一旦某条日志被提交，之后任何 Leader 的该位置及之前的日志必须与之相同。
  - 日志压缩：快照（Snapshot）+ InstallSnapshot，解决日志无限增长与重启回放过慢。
- **ZAB（ZooKeeper）**：Leader + 恢复（Recovery）+ 广播（Broadcast）三阶段；提供的是**顺序一致性**（读到最新或某个此前版本），不保证线性一致；写需 quorum；会话（Session）与临时节点是其最独特的抽象。
- **脑裂（Split-Brain）治理的三个层次**：
  1. **多数派机制**（共识层）：少数派自动失去写能力，这是根本防线。
  2. **外部仲裁**：Redis 用哨兵/仲裁节点，Kafka 用 Controller 多数派，非共识组件通过第三方仲裁确定唯一主。
  3. **栅栏令牌（Fencing Token）**：领导权每次变更令牌单调加一，下游存储（数据库、对象存储、支付网关）拒绝携带旧令牌的请求——这是**旧主尚未感知自己已被罢免**场景下的唯一可靠防线。纯租约（Lease）方案依赖"时钟漂移有界"这一不严谨假设，工程上不可单独依赖租约。
- **非共识场景的等价手段**：数据库选主（VIP 漂移、keepalived、ProxySQL）与共识的区别在于——数据库选主常靠"超过 N 秒无心跳则切换"的超时判断，若旧主网络分区但仍能对外服务，就会出现双写；因此数据库层通常叠加 **GTID / 事务位点 / 冲突检测** 或由上层强制"写入口只认当前主"。
- **考点提示**：问"为什么 Raft 提交必须多数派""如何防止脑裂导致双写"时，标准答法——多数派保证任意两个多数派相交，从而不可能同时产生两个互不冲突的提交；防双写须三层：多数派仲裁 + 唯一写入入口 + 下游 Fencing Token/幂等校验。

### 3. 复制拓扑与读写一致性策略

定义：复制是通过在多个节点保存数据副本来获得可用性、读扩展与容灾能力的机制；复制拓扑描述副本的角色与数据流向（单主、多主、无主/仲裁），读写一致性策略描述在从副本读取时如何保证客户端看到的数据符合业务预期——这是"高可用架构"与"数据可信"之间的分界线。

关键要点：
- **三类复制拓扑**：
  - **单主复制（一主多从）**：写入只进主库，从库按异步或同步复制跟随。优点：简单、冲突天然避免；缺点：主库单点、写扩展受限（可用并行回放/组复制缓解）。
  - **多主复制（Active-Active）**：多个节点均可写，需解决冲突。典型：MySQL Group Replication、TiDB 多可用区、多活消息队列。
  - **无主/仲裁复制（Leaderless）**：任意节点可写，靠版本向量与冲突合并保证收敛，典型：Dynamo 系、Cassandra、Riak；配合 hinted handoff 与反熵（anti-entropy）完成数据修复。
- **三种复制模式**：**同步复制**（强一致、延迟高、可用性差）、**异步复制**（性能好、存在数据丢失窗口）、**半同步/组复制**（在两者之间折中，RPO≈0 但不绝对，严格场景仍需对账）。
- **复制延迟的六大成因**（"从库读到旧数据"排查清单）：网络 RTT、批量提交间隔（group commit）、大事务与大批量 redo 未刷盘、单复制线程瓶颈、从库并行重放能力不足或被大查询阻塞、磁盘 IO 争用与 binlog 格式/位点问题。
- **读写分离的六个经典坑**：
  1. 写后读不一致（用户提交后立即查询读到旧值）。
  2. 延迟导致的业务误判（余额、库存、审批状态机判错）。
  3. 故障切换后旧主未回切或角色混乱，造成双写或写入丢失。
  4. 缺少延迟监控，故障切换时才发现复制断裂。
  5. 报表与大查询拖垮从库，反噬主库（延迟放大）。
  6. 运维层面 binlog 位点/GTID 丢失造成复制中断未被发现。
- **读一致性策略清单（按代价从低到高）**：
  - **会话粘性（Sticky Session）**：最省事，但节点重启/漂移即失效，且负载不均。
  - **读己之写（Read-Your-Writes）**：会话级记录写入位点/版本，比对后再读。
  - **单调读（Monotonic Reads）**：会话内不读到比先前更旧的值，需记录会话已读到的最大版本/GTID。
  - **因果一致性**：会话级保证因果链（常通过版本向量判定依赖）。
  - **强一致读**：读走 Leader，线性一致，代价最高。
  - **ReadIndex 读**：请求经 Leader 确认当前提交位点后本地读，兼得线性一致与读扩展，是 NewSQL 的主流做法。
- **多主冲突解决三路线**：
  - **LWW（Last-Write-Wins）**：按时间戳，简单但会静默丢更新，适合可覆盖型数据（如状态展示）。
  - **向量时钟 / 版本向量**：检测并发冲突，交由应用或业务补偿处理，适合需要保留冲突证据的场景。
  - **CRDT（收敛型数据结构）**：从数据结构层面保证副本最终收敛（计数器、G-Set、PN-Counter、OR-Set），适合协同类场景；代价是元数据膨胀与语义复杂。
  - **业务补偿**：订单状态机、库存"预占—确认—释放"、金额对账冲正——这是政务与医保结算场景真正依赖的兜底手段。
- **跨机房写模式三选一（必须明确回答）**：
  1. **主库在 A 机房，B 机房异步从库只读**：性能最好，RPO>0，需接受灾备数据丢失窗口。
  2. **半同步 / 仲裁强一致**：写延迟受跨机房 RTT 约束（同城 1-2ms 可接受，异地需权衡），RPO=0。
  3. **单元化（Cell）**：数据按分片划分"归属单元"，每个单元独立读写，跨单元弱一致，路由层按用户/分片键路由到 home 单元——这是大规模多活（尤其异地多活）的唯一可行解，因为跨地域强一致写在物理上不可持续。
- **考点提示**：案例题问"用户提交后立刻查询显示未提交""主从切换后同一单据处理两次"时，答法必须落到：延迟成因逐条定位 + 读一致性策略选型（会话保证/读己之写/粘性读/强一致读四种给场景）+ 切换期的"旧主只读、唯一写入口、按 GTID 追平"三重管控 + 幂等与对账兜底。

### 4. 数据分片：分片键设计、一致性哈希与在线再平衡

定义：分片（Sharding / Partitioning）是按规则把数据水平切分到多个存储节点的技术，用来突破单节点的容量与吞吐上限；分片键是决定数据分布与请求路由的核心设计要素，其选型的正确性对系统性能的影响远大于任何中间件调优。

关键要点：
- **垂直分片 vs 水平分片**：垂直分片按字段/业务模块拆表，治"宽表"与"写冲突"，收益有限且最终仍要走向水平分片；水平分片按行拆，治容量与吞吐，是分片的主形态。
- **分片键设计四条准则**：
  1. **覆盖高频查询**——路由后不应再广播，否则每次查询变成 N 个分片并行扫。
  2. **分布均匀**——避免热点，单分片数据量与流量占比应在可接受偏差内。
  3. **不跨分片事务**——尽量让一个业务事务落在一个分片内，避免分布式事务。
  4. **路由稳定**——不随业务规则变化而大规模迁移，变更需可规划、可停机或可双写。
- **典型错误分片键**：时间/自增 ID（尾端写入集中，热点落在最后一个分片）、低基数枚举（状态、性别、少量大客户，分片严重倾斜）、与查询条件不一致的分片键（跨片查询泛滥）。
- **一致性哈希（Consistent Hashing）**：把节点与数据映射到环上，节点增删只影响其相邻区间，避免传统取模（N 取模）扩容导致的全量数据迁移；**虚拟节点（VNode）**解决物理节点较少时的负载倾斜；工程实现通常再叠加"副本因子"——副本沿环顺时针放置，故障时自动迁移。
- **Range 分片 vs Hash 分片**：Range 利于范围查询与排序，但易产生尾端写热点；Hash 分布均匀、路由 O(1)，但范围查询需并行扫全部分片再归并，归并成本与深分页是主要痛点。生产上常用"Hash 为主 + 时间分区辅助裁剪"的混合策略。
- **跨分片查询五类解法**：分片键路由（命中即单分片）、广播表（字典类小表冗余到每个分片）、绑定表（关联表使用同一分片键）、异写索引/第二索引（ES 等旁路检索，带来最终一致与双写一致性问题）、分布式聚合（各分片返回部分结果后归并，注意全局排序与深分页的正确性）。
- **全局唯一 ID**：雪花算法（时间戳 + 机器位 + 序列，趋势递增、可单机发号）、号段模式（数据库发号器批量取号，避免单点瓶颈）、Redis INCR（需持久化与高可用）、UUIDv7（时间有序、无中心依赖）。要求：唯一、趋势递增（利于索引写入与范围查询）、不可预测（对外暴露场景需防枚举）、高可用。
- **在线再平衡（Resharding）五步法**：① 目标分片提前建表/建索引；② 全量迁移历史数据（离线快照 + 增量 CDC 追平）；③ **双写 + 校验**（按主键计数、关键字段校验和、抽样业务比对）；④ **灰度切流**（按比例路由读流量，观察错误率/延迟/双写差异后再全量）；⑤ 停旧写、保留回滚窗口。每一步都要有幂等保障与明确的准出指标。
- **扩容的两种含义必须分清**：**水平分片扩容**解决总容量与总吞吐（需要再平衡）；**副本扩容/读写分离**解决单分片读压力（无数据搬迁）。多数"慢"的问题应先判断是容量型还是并发型。
- **考点提示**：案例给"单表 8 亿行、按时间范围查询、扩容后写入集中在单节点"，标准答法——分片键选业务主键（如结算单号/参保人 ID + 路由因子）而非时间；时间作为二级分区维度；扩容走在线再平衡五步；跨期统计走离线数仓/预聚合而非在线强一致查询。

### 5. NewSQL 与分布式数据库选型

定义：NewSQL 是兼具关系模型与事务能力、同时具备水平扩展能力的数据库品类，通过在存储层引入分布式共识与多副本强一致、以智能分片与智能路由隐藏分布细节，实现"像单机一样使用、可水平扩展"的目标，是应对手工分库分表痛点的主要替代路径。

关键要点：
- **传统方案的三难困境**：**应用层分库分表**（分片逻辑、跨片事务、跨片 join 全部下沉到应用，改造与运维成本高）、**读写分离 + 缓存**（只能缓解读压力，无法突破单写上限，且引入延迟与一致性问题）、**纯 NoSQL**（放弃强事务与灵活查询，模型迁移代价大）。
- **NewSQL 三条技术路线**：
  1. **共享存储型**：依赖分布式文件系统/共享块设备或共享日志（AWS Aurora、阿里云 PolarDB 高版本），计算与存储分离，对外兼容 MySQL 协议，运维简单、强一致，但深度依赖特定存储厂商与特定硬件形态。
  2. **分片复制层型**：TiDB（自研分布式事务层 + Raft 复制 + RocksDB 存储）、CockroachDB（Range 分片 + 事务）、YugabyteDB（DocDB + Raft）。水平扩展能力强，支持在线扩容与跨机房多副本。
  3. **分支路线**：Percona/XtraDB Cluster、国产 GaussDB、OceanBase 等，在既有内核上叠加分布式能力，兼容性与迁移成本友好。
- **必须掌握的关键能力与其代价**：
  - **分布式事务**：两阶段提交、TCC、以及基于 Raft 时间戳/乐观并发的方式（Percolator 式）；代价是跨分片事务延迟高、冲突多，是典型热点。
  - **全局二级索引**：需处理跨分片唯一性与一致性，实现代价直接带来**写放大与延迟抖动**，是 NewSQL 选型时最该压测的指标。
  - **在线扩容与负载均衡**：数据分裂（split）与自动再平衡是持续能力，不是上线时的开关。
  - **多副本强一致**：多数派写 + Raft/半同步；可用性降级模式（只读、Learner 副本）影响故障时的可用区间。
  - **时钟依赖**：部分实现使用本地时间戳作为事务顺序，必须配套 NTP/PTP 与时钟漂移监控。
- **选型六维度**：数据模型契合度、事务与一致性要求、写入扩展方式、运维复杂度（组件数量、扩缩容、版本升级、备份恢复）、成本（硬件/许可/云费用）、生态与工具链（监控、慢 SQL、备份、CDC、BI 工具）、信创与国产化要求、可运维性（故障定位是否依赖厂商黑盒）。
- **重要边界**：**NewSQL 不会替你选分片键**——分片键仍决定单表热点与跨片事务比例；选型评审必须同时评审分片键设计。
- **现实中没有单一数据库**：政务与医保类平台的典型组合是——NewSQL/分库分表（交易与结算）、Redis（缓存与会话）、ES（检索与日志分析）、Kafka（CDC 与异步解耦）、对象存储（影像与票据附件）、MPP（报表分析）、向量化存储（AI 检索）。选型题的本质是"业务负载特征驱动的组合设计"。
- **考点提示**：问"为什么不再继续手工分库分表而改用 NewSQL"时，六条标准答案——① 消除应用层分片与跨片事务的改造成本；② 支持多机房多副本与跨机房强一致/单元化；③ 在线扩缩容与负载自动均衡；④ 统一 SQL 入口降低开发与运维门槛；⑤ 更好的可观测与故障定位；⑥ 避免自研分片中间件带来的长期技术债。

## 案例分析题

**题目**：某省医疗保障局现有医保结算系统采用"一个主库 + 两个从库"的 MySQL 主从架构，部署在单一机房，主库负责全部写请求，从库承担查询与报表。近期暴露三类问题：

第一，业务量在月末集中爆发，从库读取到最新数据的平均延迟达到 3~5 秒，导致"参保人缴费后立即查询显示未到账"、"经办人员核销时查不到待遇记录"，引发大量投诉与重复缴费。

第二，机房一次网络抖动触发了主从切换，切换后系统出现两个现象：一是部分已经成功的结算单在切换后消失，财务对账出现差额；二是切换期间部分参保人被提示"重复提交"，实际是同一个结算单被处理了两次。

第三，运维团队为排查问题，尝试用"先查从库、查不到再查主库"的方案做读修复，但上线后发现仍有脏读，且改造后主库压力上升明显。

现架构师提出改造方案，请回答以下问题：

**问题 1（6 分）**：请分析上述三类问题产生的根本原因，并说明"从库读到旧数据"与"切换后数据丢失"在机制上的本质区别。

**问题 2（8 分）**：请设计改造后的数据架构与读写策略，至少覆盖分片方案、主从复制模式、读一致性策略和故障切换机制四个方面，并说明关键取舍理由。

**问题 3（6 分）**：请针对问题 3（读修复方案上线后仍有脏读、主库压力上升）给出修正方案，并说明为什么"读不到再查主库"这种方案存在并发竞态问题。

**问题 4（5 分）**：请为该系统设计一套可自动检查的架构适应度函数（Fitness Function），至少给出 4 条，并说明每条规则检查什么、失败后的处理动作。

### 参考答案

**问题 1（6 分）**

三类问题的根因分别如下：

第一类（读旧数据）根因是**复制延迟 + 读写分离策略缺失**。MySQL 主从默认是异步复制，主库 binlog 落盘后异步传给从库，从库 SQL 线程回放后才可见，因此存在复制延迟；延迟来源包括网络 RTT、批量提交间隔、大事务与大批量 redo 未刷盘、单个复制线程瓶颈、从库并行重放能力不足、报表大查询占用从库 IO 与 CPU。叠加应用层"全部写主库、全部读从库"的固化路由，读请求在延迟窗口内必然读到旧值。投诉集中出现在月末峰值期，与批量结算大事务、并发上升直接相关。

第二类（数据丢失）根因是**异步复制的数据丢失窗口 + 切换时旧主未及时降级**。主库向从库异步复制，主库已确认提交但尚未传到从库的这段数据，在主库宕机、切换到从库时即永久丢失；而切换瞬间旧主若因网络分区仍能接受写入（未收到 fencing 信号），就会形成脑裂双写，进一步放大数据不一致。

第三类（读修复方案）的根因是**方案本身是应用层的"点查补救"而非一致性保障**：只对特定查询路径做补偿，未覆盖全部读路径；且引入了读放大——每次未命中都要再打一次主库，热点键下主库 QPS 被成倍放大。

**"读旧数据"与"切换后数据丢失"的本质区别**（本题核心得分点）：

| 维度 | 读旧数据（复制延迟） | 切换后数据丢失 |
|---|---|---|
| 数据是否丢失 | 未丢失，主库存在，只是从库尚未回放 | 确实丢失，主库已不可用且未复制到新主 |
| 一致性类型 | 最终一致性在收敛过程中的正常中间态 | 破坏了持久性（Durability）与 RPO 承诺 |
| 可恢复性 | 延迟回放完成后自然收敛 | 需靠 binlog 恢复、异地备份或对账补录人工修复 |
| 根因层次 | 读写策略与同步时序 | 复制模式（RPO）与切换/仲裁机制 |
| 治理手段 | 读一致性策略（粘性/会话保证/读己之写/强一致读） | 同步或半同步复制、GTID 追平、备份与对账补录、防脑裂 fencing |

一句话：**读旧数据是"最终一致尚未到达"，数据丢失是"最终一致永远无法到达"**；前者靠一致性策略收敛，后者靠持久性设计避免。

**问题 2（8 分）**

**（一）分片方案**

- 现状问题：单库写入成为瓶颈，且"参保人—结算单—缴费记录"三大表数据量最大、增长最快。
- 选型结论：按**参保人 ID（或医保个人编号）作为分片键**做水平分片，采用一致性哈希 + 虚拟节点，以分库分表（RANGE 或 HASH 策略二选一，HASH 更均衡、RANGE 利于按时间范围查询但需防尾端写热点）落地；结算单表按参保人 ID 路由，保证同一参保人的结算单、缴费记录、待遇记录落在同一分片，使绝大多数业务事务为**单分片本地事务**，从根本上消除跨片分布式事务。
- 全局唯一 ID：采用雪花算法或号段模式发号，保证趋势递增、全局唯一、可按 ID 反解分片。
- 查询路由：绝大多数查询带参保人 ID，直接路由单分片；跨分片的统计类查询下沉到离线数仓（ODS/DWD/ADS）或 MPP，不打在在线库上。

**（二）主从复制模式**

- 从"异步复制"改为**半同步复制 + 强一致关键路径**：核心结算写入走半同步（主库等待至少一个从库 ACK 才向客户端返回成功），把 RPO 从"秒级丢失"压到 RPO=0；非关键写入（流水日志、统计打点）走异步。
- 跨机房采用**单元化（Cell）**：按参保人 ID 哈希将数据划分为若干归属单元，每个单元独立承担读写，单元内采用多副本强一致，跨单元弱一致，路由层按参保人 ID 路由到其 home 单元。这样避免跨地域强一致写的物理不可行问题，同时保留同城双活的可用性收益。
- 说明取舍理由：强一致跨地域写在网络 RTT 上不可持续（异地 RTT 30~80ms，直接串行化写会击穿吞吐），所以单元化 + 同城强一致 + 异地弱一致是唯一可落地的路径。

**（三）读一致性策略**

按业务分类选择，而不是一刀切：

1. **写后立即读场景**（参保人缴费后查状态、经办核销查待遇）：采用**会话级保证**——会话建立时记录写入位点/版本，读请求携带该位点；路由层优先路由到已同步的副本，未达位点则降级读主库。同时对写后读关键路径使用**强制读主库**策略（该类请求占比可控，不会压垮主库）。
2. **非关键查询场景**（历史明细、列表查询）：允许读从库，采用**单调读**保证会话内不回退。
3. **报表与大查询场景**：走独立的只读副本组或离线数仓，绝不与在线从库混用，避免大查询拖慢复制回放、放大延迟。
4. **缓存策略**：热点字典与待遇标准等可缓存数据走 Redis，缓存仅作加速不做唯一数据源；采用**逻辑过期 + 互斥重建**防缓存击穿，**随机 TTL + 集群化过期**防雪崩，缓存空值短 TTL + 参数校验防穿透。

**（四）故障切换机制**

- 切换触发：基于心跳与 GTID 复制延迟的仲裁，而非单纯超时；设置**最大容忍延迟阈值**，超过则判定不可切换。
- 切换安全性：切换前检查新主已接收到的 GTID 位点，确认无未复制事务；对新主加 **fencing token**，旧主恢复后即使仍持有 IP/VIP 也无法接受写入（写入口校验令牌版本号或租约）。
- 切换后动作：新主短暂**只读或按白名单放行关键写**（等待旧主恢复或确认数据边界），由应用层做幂等（业务幂等键 + 唯一约束）避免重复处理；对切换前窗口内的数据做**对账补录**，保证财务不出现差额。
- 日常防护：读写分离只读副本默认开启 `super_read_only`、禁止本地写，防止"从库被误写"造成不可逆的数据分叉。

**（五）其他关键取舍说明**

- 同步复制不能全量开启：全量半同步会使写延迟翻倍并降低可用性，故只对关键交易链路启用。
- 不采用"读写分离 + 缓存"作为唯一扩展手段：它无法解决单写上限，必须配合分片。

**问题 3（6 分）**

**"读不到再查主库"的并发竞态问题**：该方案存在 TOCTOU（检查-使用）时间差。在两次查询之间，另一个事务可能正在修改该行——若修改事务先于第二次查询提交，第二次查询读到的是新值，与第一次读到的旧值组合在一起，就会**把"旧值→新值"或"旧值→另一个更新值"误判为不一致**，导致不必要的回源，甚至把并发的合法更新当成脏数据告警；同时在延迟窗口内该方案**无法保证读到的一定是最新值**（两次查询都可能读到同一个旧值）。本质上，"读旧值再回查主库"只能提高命中率，不能提供任何一致性保证。

**修正方案**：

1. **改用位点/版本判定而非值比较**：读请求携带客户端已读到的位点（GTID/版本号/时间戳），由路由层或数据库层判定"副本是否已追平该位点"；追平则直接返回副本，未追平则路由主库。这把"值比较"变为"时序判定"，消除竞态。
2. **会话级一致性标签**：在会话上下文或用户维度记录最近一次写位点，读请求必须满足"已读位点 ≥ 会话写位点"才允许返回副本结果；不满足直接走主库强一致读。
3. **关键路径强制读主 + 限流保护**：对缴费状态、核销等强一致诉求接口，直接走主库并设置独立线程池与限流，防止主库被打垮；主库承载"关键强一致读 + 全部写入"，副本承载"非关键读"。
4. **缓存一致性改造**：缓存只做加速，命中后仍需校验位点（缓存值与位点一起存储），位点过期即回源；禁止用缓存承担唯一一致性职责。
5. **主库压力治理**：读写比例治理、慢查询与报表隔离、连接池与并发控制、读写分离流量比例可配置灰度，避免"全量回查主库"形成雪崩式回源。

**问题 4（5 分）**

以下 6 条适应度函数可自动检查，任选 4 条作答并写清检查内容与失败动作：

| 编号 | 规则（可自动检查） | 检查内容 | 失败处理 |
|---|---|---|---|
| F1 | 核心交易接口的复制延迟 P99 必须 ≤ 200ms | 监控从库 seconds_behind_master 与端到端延迟分位 | 告警 + 降级：核心读切主库 + 排查大事务与慢查询 |
| F2 | 任何单库单表数据量不得超过容量水位 60% | 巡检各分片行数与磁盘使用率 | 触发分片扩容与再平衡工单 |
| F3 | 业务库（除临时表）禁止出现未走路由的直连写 | 扫描应用连接配置与数据库审计日志 | 阻断并告警，防止绕过唯一写入口 |
| F4 | 关键写接口幂等：同一幂等键重复提交必须返回首次结果 | 自动化回归测试 + 生产抽样校验 | 阻断发布 + 补数据修复 |
| F5 | 切换演练必须满足 RPO=0、RTO≤5min | 每季度故障演练自动校验切换时长与数据丢失行数 | 演练不通过则冻结生产变更并整改 |
| F6 | 缓存命中率 ≥ 80% 且空值缓存比例 < 1% | 监控命中率与空值/穿透流量 | 告警 + 优化预热与空值策略 |
| F7 | 全库禁止跨分片事务比例 ≤ 1% | 从链路追踪聚合事务涉及的分片数 | 立项整改分片键或引入本地事务表 |

作答要点：**适应度函数必须可自动化、可量化、有明确阈值与失败后的处置动作**，而不是"要提高可用性"这类无法检查的表述。

### 踩分要点

1. **问题 1 的核心得分点是"本质区别"**：必须点出"读旧数据是最终一致尚未收敛、数据丢失是最终一致永远无法到达"，并从"是否丢失、能否自愈、根因层次、治理手段"至少三个维度展开。只答"一个是延迟、一个是宕机"得分低。
2. **根因要分层作答**：复制延迟必须答出至少四条具体成因（网络、提交间隔、大事务、并行回放不足、大查询干扰），不能只说"主从有延迟"。
3. **问题 2 四个方面缺一不可**：分片、复制模式、读一致性、故障切换。任何一块缺失按缺项扣分。
4. **分片键理由必须写出**：为何选参保人 ID（同一业务主体同分片、消除跨片事务、查询可路由），并给出全局 ID 方案与跨片查询的兜底路径（离线数仓）。
5. **读一致性必须分类给策略**，且至少写出"写己之写/单调读/强一致读/会话粘性"中的三种并说明各自适用场景；笼统答"提高一致性"不得分。
6. **跨机房强一致必须点明物理不可行**，从而推出单元化（Cell）方案——这是拉开区分度的高分点。
7. **故障切换必须写 fencing 与幂等**：只写"用哨兵/仲裁"不够；要写出"旧主如何被隔离""重复处理如何避免""差额如何补"。
8. **问题 3 必须点名竞态本质**：TOCTOU + 值比较无法保证最新；正确解法是位点/版本判定与会话级一致性标签。"改用加锁""加长超时"不是得分答案。
9. **主库压力上升必须正面回应**：限流、线程池隔离、读写比例灰度、报表与慢查询分离、缓存一致性改造，五答其三即可。
10. **问题 4 每条适应度函数必须三元齐备**：可自动检查的规则表述 + 检查对象 + 失败处置动作。只写"可用性要达到 99.99%"不给检查方式与失败动作，不得分。
11. **全卷通用提示**：本案例三条失分重灾区——① 把 CAP 的 C 与 ACID 的 C 混用；② 认为"最终一致 = 不一致"；③ 认为"上缓存就能解决读延迟"。阅卷老师最反感这三类表述。

## 高频陷阱速查

**陷阱一**：把 CAP 的"一致性"当作 ACID 的"一致性"——CAP 的 C 指副本线性一致，ACID 的 C 指事务约束不被破坏，答题时混淆直接扣分。

**陷阱二**：认为"三选二"是选型结论——分区容忍是分布式系统必选项，真实决策是"分区发生时保 C 还是保 A"，多数互联网系统保 A。

**陷阱三**：把"最终一致"等同于"没有一致性"——最终一致是有收敛保证的一致性模型，不可接受的是"不收敛"。

**陷阱四**：认为"上了缓存就能解决读延迟"——缓存只做加速不做唯一数据源，且会带来击穿/雪崩/穿透三坑与缓存一致性问题。

**陷阱五**：认为"同步复制能保证不丢数据"——同步复制在主库故障、复制中断时仍可能丢最后一段；RPO=0 必须叠加持久化策略、备份与对账。

**陷阱六**：把"主从切换"当成"自动无缝"——切换必然带来写入口变化、旧主隔离、重复提交与数据边界问题，必须有 fencing、幂等与对账补录三件套。

**陷阱七**：认为"分库分表之后就万事大吉"——跨片事务、跨片 join、全局 ID、再平衡、热点治理五件事一件都不会消失。

**陷阱八**：认为"NewSQL 能自动解决分片"——分片键仍由人设计，选错分片键，再强的分布式引擎也救不了热点表。

**陷阱九**：跨机房场景仍写"两地三中心强一致跨地域写"——异地 RTT 30~80ms，跨地域强一致写不可持续，必须走单元化。

**陷阱十**：适应度函数写成"系统要更稳定""可用性要更高"——没有阈值、检查方式与失败处置动作，就不是可执行的适应度函数。

**陷阱十一**：把"读写分离"当成"没有一致性问题"——应用层必须显式声明每类读的一致性等级（会话保证/单调读/最终一致/强一致），并在接口契约中写明。

**陷阱十二**：忽略"从库被误写"——只读副本必须启用 `super_read_only` 并纳入巡检，一旦从库产生本地写入，数据分叉不可逆。
