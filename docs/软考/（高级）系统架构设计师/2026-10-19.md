## 今日核心概念
### 1. 微服务架构（Microservices）
定义：将单体应用按业务边界拆分为一组小型自治服务，每个服务独立部署、独立伸缩、独立演进，围绕业务能力组织，服务间通过轻量级协议（HTTP/REST、gRPC、消息队列）通信，拥有独立的数据库（Database per Service）。
关键要点：
（1）核心特征：单一职责（One Bounded Context One Service）、独立部署（Independent Deployability）、去中心化（Decentralized Governance，每个服务可选用不同技术栈）、去中心化数据（每个服务独享数据库）、基础设施自动化（CI/CD 必配）、容错设计（Failure Isolated，避免级联雪崩）、可观测性集中（Tracing 跨服务透传 TraceID）。
（2）九大特性（依据 Lewis & Fowler 2014）：组件化 + 按业务组织 + 去做中心化治理 + 做轻量级通信 + 去做中心化数据 + 基础设施自动化 + 容错设计 + 可观测 + Smart Endpoint Dumb Pipe（智能端点+傻管道）。
（3）服务拆分三原则：业务边界（按 DDD 限界上下文）、团队规模（Two-Pizza Team，每个微服务对应一个小组）、可独立交付（独立 CI/CD、独立版本号）。
（4）反模式：分布式单体（Distributed Monolith，服务拆了但库共用、链路耦合）、纳米服务（Nanoservice，过度拆分导致运维成本爆炸）、共享内核反模式（多个服务共用同一代码库导致发布耦合）。

### 2. API 网关（API Gateway）
定义：系统对外的统一入口，承担路由转发、协议转换、认证授权、流量管控、可观测等非业务横切关注点，避免业务服务重复造轮子，本质是"门面模式 + 责任链"的网关化落地。
关键要点：
（1）核心能力：路由（Path/Header/Method 匹配转发）、认证鉴权（OAuth 2.0、JWT、API Key 解码校验）、限流熔断（Sentinel/Hystrix 规则集中下发）、协议转换（REST↔gRPC、HTTP↔WebSocket）、缓存（热点响应 Redis 边缘缓存）、灰度发布（按 Header/UserID 路由到不同版本）、聚合编排（BFF 模式聚合多个下游服务）。
（2）网关 vs 反向代理：Nginx 反向代理只做 L7 转发和负载均衡；API Gateway 多出鉴权、流控、协议转换、业务编排等能力。
（3）BFF（Backend For Frontend）：按前端形态拆出专属网关，Web BFF / Mobile BFF / 第三方 BFF，避免一个通用网关被多端需求绑架。
（4）部署模式：嵌入式 SDK（如 Spring Cloud Gateway）、独立 Sidecar（Envoy+Kong）、云原生 Ingress（K8s Nginx Ingress、Traefik、APISIX）。

### 3. 服务发现与配置中心（Service Discovery & Config Center）
定义：服务注册中心记录所有可用服务实例的元数据并提供健康检查，客户端通过服务名动态发现可用节点；配置中心集中托管全环境配置，支持动态推送与版本回滚，两者常合并实现（如 Nacos）。
关键要点：
（1）两种模式：客户端发现（Eureka + Ribbon，客户端集成负载均衡器，自主选择实例）和服务端发现（Consul + Nginx/Envoy，网关层或 LB 做负载均衡）。
（2）注册中心核心能力：服务注册（Instance 元数据含 IP/Port/Metadata/TTL）、健康检查（心跳+探针 TCP/HTTP/gRPC）、服务订阅（Watcher 推送变更）、集群同步（Gossip 协议保证 AP）、元数据管理（版本号、灰度标签、机房区域）。
（3）配置中心四要素：环境隔离（dev/test/staging/prod）、动态推送（WebSocket 长连接主动刷新）、灰度发布（按 IP/标签灰度推送）、版本回滚（配置版本号 + 一键回退）。
（4）CAP 取舍：Eureka AP（高可用优先，注册短暂不一致可容忍）、Zookeeper CP（强一致优先，写失败立即报错）、Nacos AP/CP 可切换（默认 AP，集群模式下 CP）。

### 4. 分布式链路追踪（Distributed Tracing）
定义：在分布式请求经过的每个服务节点上记录调用信息（TraceID、SpanID、ParentID、操作名、开始时间、耗时、状态），通过统一 TraceID 串联，形成完整调用链视图，定位性能瓶颈与故障根因。
关键要点：
（1）核心概念：Trace（一次完整请求调用链，唯一 TraceID）、Span（一次具体操作调用，有 SpanID+ParentID）、Baggage（跨服务透传的键值对上下文）、SpanContext（TraceID+SpanID+采样标志的传播头部）。
（2）三大支柱 Metrics+Logs+Traces：Metrics 聚合指标（QPS/P99/错误率）、Logs 离散事件（INFO/ERROR 日志）、Traces 调用链路（Trace 拓扑），OTel 统一规范。
（3）采样策略：全量采集成本爆炸，采用头部采样（Head-Based 入口 1/1000 决策）或尾部采样（Tail-Based 收集完链路上报再决策，精准但延迟），结合错误全采+慢链路全采。
（4）OpenTelemetry：可观测性统一规范（OpenTracing+OpenCensus 合并），提供 SDK + 自动探针 + Collector + 协议（OTLP），对标 Jaeger/SkyWalking/Zipkin，主流趋势。

### 5. 云原生十二要素（The Twelve-Factor App）
定义：Heroku 联合创始人 Adam Wiggins 提出的 SaaS 应用开发方法论，定义云原生应用应遵循的十二条最佳实践，是微服务+容器化+K8s 部署的事实标准。
关键要点：
（1）代码基线（Codebase）：一份代码库多次部署，告别环境漂移。
（2）依赖（Dependencies）：显式声明依赖（requirements.txt/pom.xml/package.json），禁止依赖系统全局包。
（3）配置（Config）：配置与代码分离，环境变量注入，禁止配置硬编码。
（4）后端服务（Backing Services）：数据库/缓存/MQ 视为可挂载资源，通过 URL 寻址接入。
（5）构建/发布/运行（Build/Release/Run）：严格三阶段分离，不可手工改动运行时代码。
（6）进程（Processes）：应用是无状态进程，状态外置到 Redis/DB。
（7）端口绑定（Port Binding）：应用自带 HTTP 端口，不依赖外部 Web 容器。
（8）并发（Concurrency）：通过进程模型横向扩展，不靠线程。
（9）易处理（Disposability）：进程可快速启动+优雅退出（SIGTERM 时排空请求后再杀进程）。
（10）开发/生产等价（Dev/Prod Parity）：环境差异最小化（Docker 镜像同套环境过三阶段）。
（11）日志（Logs）：日志视为事件流，stdout 输出到 ELK/Loki 集中采集，禁止写本地文件。
（12）管理进程（Admin Processes）：一次性管理任务（如数据迁移）走与主进程独立的环境同步执行。

## 案例分析题
**题目**：
某电商平台为应对双十一流量洪峰，将订单系统从单体拆分为微服务架构，包含：用户服务、商品服务、库存服务、订单服务、支付服务、物流服务。系统上线后出现以下问题：
（1）用户下单提交时偶发失败，研发追踪发现是链路上的支付服务调用超时引起雪崩；
（2）营销活动日高峰期监控告警，问题出现 30 分钟后工程师才感知到根因；
（3）前端 PC 端与移动端请求字段差异大，网关适配代码冗长且经常改一处全部回归；
（4）配置变更需要重启所有服务才能生效，每次大促前配置改动引发大量变更工单。
问题：
① 请结合微服务架构理论，分析上述四类问题的根因，并给出每个问题的架构级解决方案（至少 2 条）；
② 请画出修复后的下单链路时序图，说明核心服务的协作关系（文字描述亦可）。

**参考答案**：
① 问题逐条分析：
（1）"支付超时引起雪崩"根因：服务间调用没有隔离保护，一个非核心依赖异常拖垮主链路；下单提交属强链路（核心流程），支付属弱链路（可异步补偿）。
   解决方案：A. 引入熔断器（Resilience4j/Sentinel）熔断支付服务，降级为"挂单状态=待支付"+MQ 异步补偿；B. 引入超时（HTTP 2s+gRPC 1s）+ 重试（带幂等键最多 2 次）+ 线程池隔离（支付服务专用 ThreadPool，独立于订单主链路）。
（2）"30 分钟才发现根因"根因：监控告警颗粒度不足，仅有机器级指标（CPU/内存）缺少业务链路级 SLO 告警。
   解决方案：A. 接入 OpenTelemetry 统一采集三支柱指标（Red Metrics：Rate/Errors/Duration），按 P99 延迟+错误率双维度告警；B. 引入 APM（SkyWalking/Pinpoint）+ 告警分级（一级告警=资损型，二级=体验型）；C. 配置链路追踪全量错误日志自动归档到 ELK/Jaeger 一键跳转。
（3）"网关适配代码冗长"根因：单一通用网关适配多端需求，PC/移动/第三方共用一份路由配置导致改一端影响全部。
   解决方案：A. 引入 BFF 模式拆分 Web BFF/Mobile BFF/Partner BFF 三套网关，各管各的请求/响应模型；B. 在 BFF 层引入 GraphQL（按需取字段，前端要啥取啥，避免字段冗余）；C. 抽取通用 Adapter 工厂（通过 Header 中 deviceType 路由到不同 Adapter 链）。
（4）"配置变更需重启服务"根因：配置耦合在代码或文件里，没有独立的动态配置中心。
   解决方案：A. 引入 Nacos/Apollo 配置中心，配置变更通过长连接实时推送（WebSocket+版本号幂等），版本回滚一键完成；B. 配置中心按环境隔离+灰度发布+审计日志；C. 配合 @RefreshScope/@ConditionalOnProperty 注解实现配置热更新无需重启。

② 修复后下单链路时序图（文字描述版）：
前端 →（HTTPS）→ API 网关（鉴权+限流+路由） → 订单 BFF（聚合校验） →（并行调用）→ 用户服务（核对身份+收货地址）+ 商品服务（核对价格+规格）+ 库存服务（Redis Lua 原子预扣，失败回滚）
→ 订单服务（创建订单，落库前发领域事件） → 消息总线（RocketMQ 事务消息） → 支付服务（异步监听订单创建事件，唤起支付+自动确认收货超时关单）
→ 物流服务（监听支付成功事件，调用三方快递 API 创建运单）
→ 全链路 TraceID 串联，三支柱指标上报 OTel Collector → 异常时熔断器立刻降级，最终告警在 1 分钟内通过企业微信告警群触达。

**踩分要点**：
（1）熔断+降级+超时三件套是微服务可用性保障标配，必须答出熔断器（Sentinel/Resilience4j/Hystrix 命令式编程）或线程池隔离/信号量隔离。
（2）可观测性三大支柱 Metrics+Logs+Traces 必须答到，且要明确说明 OpenTelemetry 是统一规范。
（3）BFF 模式不要答"网关拆分"这种模糊表述，要点出"按前端形态拆 Web/Mobile/第三方三套"。
（4）配置中心必答"动态推送+版本回滚+环境隔离+灰度发布"四件套，缺一扣 0.5 分。
（5）时序图要体现异步解耦（MQ 事务消息），不能画全部同步链路。

## 记忆口诀
微服务九特性：单部去数可容，端点要轻巧，业务按限界，团队两 Pizza，故障必隔离。
API 网关七能力：路由鉴权限流熔断，协议转换缓存灰度，BFF 拆端聚合。
CAP 三选二：Eureka AP 高可用，Zookeeper CP 强一致，Nacos 切换两相宜，分布式系统不可三角替。
云原生十二要素：代码基线显式依，配分三阶分离运，并发进程易处置，开发生产等价齐，日志事件流外部十一。
限流四算法口诀：令牌桶（削峰填谷）、漏桶（匀速）、计数器（固定窗）、滑动窗（防双倍突刺），适用场景要分清；其中令牌桶允许一定程度的突发流量，漏桶则强制恒定流出速率。
熔断三态：关闭（CLOSED，正常）、打开（OPEN，直接拒绝）、半开（HALF_OPEN，放少量试探），状态机靠统计窗口滑动切换，超阈值（错误率 50%/调用数 10/10s）开熔断，超时窗口后转半开。
