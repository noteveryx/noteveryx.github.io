## 今日核心概念

### 1. 高并发架构总体思路与容量规划
定义：高并发架构是指系统在单位时间内承载海量请求的能力设计，通过分层解耦、缓存前置、异步削峰、水平扩展、读写分离、流量治理六大手段，把集中式压力转化为分布式能力，核心指标为 QPS、TPS、RT（响应时间）、并发数与吞吐量。
关键要点：
- 六大手段：**分层**（接入层、应用层、服务层、数据层各司其职）、**缓存**（把 80% 的读引到内存）、**异步**（同步转异步，用消息队列削峰填谷）、**拆分**（垂直拆分按业务、水平拆分按数据）、**扩展**（无状态服务加机器即可扩容）、**治理**（限流、熔断、降级、隔离）。
- 容量规划流程：明确业务指标（日活、峰值 QPS）→ 换算单机容量（按压测数据推算）→ 计算所需机器数（含 1.5–2 倍冗余）→ 定期全链路压测验证。
- 性能与可用性指标：QPS（每秒查询数）、TPS（每秒事务数）、RT（响应时间，关注 P95/P99 而非均值）、并发数（同时处理请求数）、成功率。
- 利特尔法则：并发数 = QPS × 平均响应时间；用于估算线程池大小与连接池容量。
- 分层原则："**上游能做的不下沉，能用缓存的不查库，能异步的不同步，能合并的不逐次**"。
- 高并发不等于高性能：前者解决"同时很多人来"，后者解决"单个请求快"，但二者共享同一套优化手段。

### 2. 缓存架构与缓存一致性
定义：缓存是在访问速度差异悬殊的两级存储之间加入的高速缓冲区，通过把热点数据放到内存，降低后端数据库压力、缩短响应时间；多级缓存通常由客户端缓存、CDN 缓存、反向代理缓存（Nginx）、分布式缓存（Redis）、本地缓存（Caffeine）组成。
关键要点：
- 缓存更新四策略：Cache Aside（旁路更新，最常用）、Read/Write Through（读写穿透）、Write Behind（写回，异步刷盘）、Refresh Ahead（提前刷新）。
- **缓存三大坑**：**缓存穿透**（查询不存在的数据，请求全部打到数据库）——解法：布隆过滤器、空值缓存、参数校验；**缓存击穿**（热点 key 过期瞬间大量请求涌入）——解法：互斥锁重建、逻辑过期、热点永不过期；**缓存雪崩**（大批 key 同时过期或缓存服务宕机）——解法：过期时间加随机扰动、多级缓存、集群高可用、熔断降级兜底。
- Cache Aside 一致性：**先更新数据库、再删除缓存**（而非更新缓存），配合延迟双删（更新库 → 删缓存 → 延迟 500ms 再删一次）降低并发不一致概率。
- 强一致方案：分布式锁串行化、订阅 binlog（Canal）异步淘汰缓存、写请求走同一队列。
- 热点 key 处理：本地缓存 + Redis 多副本（key 加随机后缀打散到多个分片）、读写分离、热点探测（JDK 自带或第三方热点探测上报）。
- Redis 高可用三态：主从复制（读写分离）、哨兵（Sentinel，自动故障转移）、集群（Cluster，16384 槽位分片，横向扩展）。

### 3. 数据库高并发与分库分表
定义：数据库高并发是通过读写分离、分库分表、索引优化、连接池调优、分布式 ID 等手段，把单库单表的压力分散到多个数据库与数据表，突破单机存储与并发上限的架构设计。
关键要点：
- 读写分离：主库写、从库读，主从复制（异步/半同步）；注意**主从延迟**导致的数据不一致，关键业务"写后立即读"强制走主库。
- 垂直拆分：按业务域拆库（用户库、订单库、商品库）；垂直拆表：把大字段（文本、二进制）拆到扩展表。
- 水平拆分：按分片键把同一张表的数据分散到多个库/表。**分片算法**四类：范围分片（易扩容、易热点）、哈希分片（分布均匀、扩容需迁移）、一致性哈希（扩容影响小）、路由表（灵活可控、需维护）。
- 分片键选择原则：**高基数、分布均匀、查询高频、尽量避免跨片**（订单场景常用 user_id 或 order_id）。
- 分库分表后的新问题：跨库 JOIN（改为应用层聚合或宽表冗余）、分布式事务（TCC/Saga/本地消息表）、全局唯一 ID、跨库分页、跨库排序。
- 分布式 ID 方案：UUID（无序、占空间）、数据库自增（单点瓶颈）、号段模式（批量取号，性能好）、Snowflake 雪花算法（时间戳 + 机器号 + 序列号，趋势递增）、Redis INCR。
- 存量数据迁移：双写（新老库同时写）→ 数据同步对账 → 灰度切读 → 切写 → 下线老库。

### 4. 流量治理：限流、熔断、降级与削峰
定义：流量治理是在系统入口与关键链路上对流量进行识别、整形、隔离与保护的技术体系，含限流（拒绝超额流量）、熔断（故障服务快速失败）、降级（牺牲非核心保核心）、隔离（资源池划分）与削峰（异步缓冲）五类手段。
关键要点：
- **限流四算法**：计数器（简单，有临界问题）、滑动窗口（平滑，解决临界）、漏桶（恒定速率流出，强行整形）、令牌桶（恒定速率生成令牌，允许突发，最常用）。
- 限流粒度：单机限流（Guava RateLimiter）、分布式限流（Redis + Lua 原子化）、网关层限流（Nginx / Spring Cloud Gateway / Sentinel）、集群限流。
- **熔断三态**：关闭（正常放行）→ 打开（快速失败，不调用下游）→ 半开（放少量请求试探，成功则恢复关闭）。
- **降级策略**：读降级（返回缓存或默认值）、写降级（异步落库）、功能降级（关闭非核心模块）、限流降级（排队或提示稍后再试）。降级原则："**保核心、舍非核心；保读、舍写；保老用户、舍新功能**"。
- **隔离手段**：线程池隔离（不同服务用不同线程池，避免相互拖垮）、信号量隔离、集群隔离（按租户/业务分集群）、机房隔离。
- **削峰填谷**：消息队列异步化（RocketMQ / Kafka），把瞬时高峰写入队列，消费者按自身能力匀速消费；配合本地消息表与幂等消费保证不丢不重。
- 秒杀架构五层漏斗：**CDN 静态化 → 前端限流（答题/按钮置灰）→ 网关限流（令牌桶）→ 服务层 Redis 预扣减库存 → 消息队列异步下单**。核心思想是"**把流量挡在离用户最近的地方**"。

### 5. 高并发下的一致性与幂等设计
定义：分布式系统在并发、分区、延迟条件下，无法同时满足一致性（C）、可用性（A）、分区容错性（P）三者，即 CAP 定理；BASE 理论（基本可用、软状态、最终一致）是 CAP 在高并发场景下的工程折中。幂等是指同一请求执行一次与执行多次产生的结果相同。
关键要点：
- CAP 三选二：分布式系统必然存在分区（P），故实际是在 C 与 A 之间取舍；**CP**（如 ZooKeeper、Etcd，强一致但可能不可用）、**AP**（如 Eureka、Cassandra，高可用但可能读到旧数据）。
- BASE 理论：Basically Available（基本可用，允许降级）、Soft state（软状态，允许中间态）、Eventually consistent（最终一致）。它是 ACID 的柔性替代。
- 最终一致性实现：可靠消息最终一致（本地消息表 + MQ + 消费重试）、最大努力通知、TCC（Try-Confirm-Cancel）、Saga（长事务拆分为本地事务链 + 补偿）、对账补偿（T+1 全量对账 + 差异工单）。
- **幂等四方案**：唯一索引（数据库兜底）、Token 机制（提交前申请、提交时校验并删除）、状态机（只允许合法状态跃迁）、分布式锁（串行化执行）。
- 幂等三要素：**全局唯一标识**（业务流水号 / 请求 ID）+ **去重存储**（Redis / DB 唯一键）+ **过期策略**（防止存储无限增长）。
- 高并发场景的一致性取舍：库存扣减用 Redis 预扣 + 异步落库（允许短暂不一致），订单支付用 TCC 或本地消息表（要求最终一致），账户余额用强一致（宁可牺牲可用性）。

## 案例分析题

**题目**：某电商平台"双十一"大促系统，日均订单 200 万单，2026 年"双十一"预计峰值下单 QPS 达到 12 万，瞬时峰值可达 20 万，是日常峰值的 40 倍。系统现有架构为：Nginx 负载均衡 → 单体 Java 应用集群（部署 40 台 8C16G）→ MySQL 主从（1 主 3 从）+ Redis 主从（1 主 2 从）。大促历史数据显示：2025 年"双十一"0 点开抢瞬间，系统在 30 秒内出现大面积超时，库存超卖 340 单，支付回调重复入账 12 笔，商品详情页 QPS 达到 8 万导致 Redis CPU 打满；数据库连接池被打满后，主从延迟从 200ms 飙升至 15s。业务方要求 2026 年实现"零超卖、零重复入账、核心链路可用性 99.99%、峰值 20 万 QPS"。

**问题：**

1. 分析现有架构在大促场景下的主要瓶颈与风险。
2. 设计整体高并发架构方案，说明分层设计与六大手段的具体应用。
3. 针对"商品详情页 Redis CPU 打满"，设计多级缓存与热点 key 治理方案。
4. 针对"库存超卖与数据库压力"，设计库存扣减方案并说明如何保证不超卖。
5. 针对"支付回调重复入账"，设计幂等方案。
6. 设计流量治理方案（限流、熔断、降级、隔离、削峰），并给出大促保障的组织措施。

**参考答案**：

**1. 主要瓶颈与风险分析**

- **接入层瓶颈：** 单层 Nginx 承担全部入口流量，缺乏边缘静态化与 CDN 卸载；20 万 QPS 静态资源请求（图片、JS）与动态请求混合进入源站。
- **应用层瓶颈：** 单体应用混部，商品、订单、库存、支付共用一个进程与线程池，任一模块慢都会拖垮全局，缺乏隔离；40 台 8C16G 按峰值 20 万 QPS 计，单机需承载 5000 QPS，若无缓存与异步，单机难以支撑。
- **缓存层瓶颈：** Redis 单主 2 从，容量与 CPU 均有限；热点商品 key 集中在一个分片，导致单节点 CPU 打满；无本地缓存，所有请求穿透到 Redis。
- **数据层瓶颈：** 单库单表存储 200 万单/日的数据量，主从延迟在大流量下放大至 15s，读从库可能读到"未支付"的脏读；连接池被打满后请求排队，形成雪崩式连锁反应。
- **一致性风险：** 库存扣减与支付回调缺乏幂等设计，导致超卖 340 单与重复入账 12 笔。
- **容量与压测风险：** 未做全链路压测，容量基线不清；无自动扩缩容；缺乏降级预案与演练。

**2. 整体高并发架构方案（分层 + 六手段）**

- **分层设计：**
  - **接入层：** CDN（静态资源、图片、视频全量卸载）+ WAF + 多级 Nginx 集群（DNS 轮询/LVS 四层负载 → Nginx 七层）+ API 网关（路由、鉴权、限流、灰度）。
  - **应用层：** 按业务域拆分微服务（商品服务、库存服务、订单服务、支付服务、优惠券服务），无状态化，支持横向扩容；使用容器化 + K8s HPA 自动扩缩容。
  - **缓存层：** 多级缓存（CDN → Nginx 本地缓存 → 应用本地缓存 Caffeine → Redis 集群）。
  - **数据层：** MySQL 分库分表（订单按 user_id 哈希分 32 库 256 表）+ 读写分离 + 热点数据 NoSQL 化（库存、购物车用 Redis）。
  - **异步层：** RocketMQ 集群承担削峰填谷，MQ 前置到下单链路，异步创建订单与扣减积分、发券。
- **六大手段落地：**
  - **分层：** 如上五层各司其职，层间异步解耦。
  - **缓存：** 商品详情、库存快照、用户信息全部前置缓存，目标缓存命中率 ≥99%。
  - **异步：** 下单只做"Redis 校验+预扣减+写 MQ"，返回用户"排队中"，后端异步消费生成订单；支付成功后的积分、优惠券、通知全部异步。
  - **拆分：** 垂直拆服务、水平拆数据；大促前对核心链路做"独立部署、独立扩容"。
  - **扩展：** 无状态服务一键扩容至 400 台；Redis 从主从升级为 Cluster 集群。
  - **治理：** 全链路限流（网关 + 单机 + 分布式）、熔断降级、资源隔离、预案演练。

**3. 多级缓存与热点 key 治理**

- **多级缓存设计：**
  - **第一级 CDN：** 商品详情页静态化（页面模板 + 商品数据渲染后的 HTML/JSON），TTL 60s，卸载 70% 以上流量。
  - **第二级 Nginx 本地缓存：** 对热点商品详情做 proxy_cache，TTL 5–10s。
  - **第三级应用本地缓存：** Caffeine 缓存热点商品（Top 1%），TTL 3–5s，容量上限按 2 万条控制。
  - **第四级 Redis Cluster：** 全量商品数据，主数据 30 分钟过期 + 主动刷新。
  - 逐级过滤后，最终到 MySQL 的读请求可降至 <1%。
- **热点 key 治理：**
  - **热点探测：** 接入层与 Redis 侧埋点统计 key 访问频次，每分钟输出热点榜单（如 JD 热点探测方案）。
  - **key 打散：** 热点 key 加随机后缀（`item:12345:0~9`）分散到 10 个分片，读取时随机取一个；读取后本地缓存合并。
  - **本地副本：** 热点数据下沉到应用本地缓存，Redis 只做回源。
  - **副本扩容：** 为热点商品单独建立 Redis 副本集群，配置多主多从。
  - **降级兜底：** 库存、价格等强实时字段走独立链路，商品描述、评价等非核心字段降级为静态或省略。
- **容量保障：** Redis Cluster 至少 6 主 6 从，32G 内存规格，单分片 CPU 水位控制在 60% 以内。

**4. 库存扣减方案（不超卖）**

- **方案总原则：Redis 预扣 + 异步落库 + 幂等校验 + 对账兜底。**
- **第一层：前端限流。** 商品页按钮置灰 + 答题/验证码 + 每人限购数量限制，从源头降低无效请求。
- **第二层：Redis 预扣库存（核心）。** 大促前把库存预热到 Redis；扣减使用 **Lua 脚本保证原子性**（判断库存 ≥ 购买量 → 扣减 → 返回结果），避免"查了再扣"的并发窗口；同时用 `DECRBY` 与库存判断在同一脚本内完成。
- **第三层：计数器兜底。** Redis Cluster 使用分片计数器，同一商品固定分片避免跨片事务；对超卖风险极高的爆款，采用"Redis 库存 + 数据库唯一约束"双保险。
- **第四层：消息队列异步下单。** 预扣成功即写 MQ 并返回用户"排队中"；消费者按能力匀速消费，创建订单并落库，避免数据库瞬时写入高峰。
- **第五层：数据库唯一约束 + 版本号。** 订单表以 `order_no` 建立唯一索引；库存表采用 `update stock set num = num - #{qty} where sku_id = ? and num >= #{qty}`（条件更新 + 影响行数判断），即使 Redis 失效也不会超卖。
- **第六层：对账与回补。** 定时任务比对"Redis 扣减总量 vs 数据库订单总量"，差异自动生成工单；未支付订单超时后归还 Redis 库存（同样走 Lua 原子操作 + 幂等标记）。
- **超卖根因反思：** 去年 340 单超卖源于"先查后扣"非原子操作与 Redis 主从切换期间的库存丢失，必须改用原子脚本并把 Redis 升级为 Cluster 且开启 AOF 持久化。

**5. 支付回调幂等方案**

- **幂等三要素落地：** 全局唯一标识 = 渠道支付流水号 + 商户订单号；去重存储 = Redis SETNX + 数据库唯一索引双保险；过期策略 = Redis 24 小时过期，数据库永久保留。
- **具体实现：**
  - **第一步 校验签名：** 验证回调来源真实性，防止伪造回调。
  - **第二步 幂等前置校验：** 以"商户订单号 + 渠道流水号"为 key 执行 `SETNX`，设置 TTL 24 小时；若 key 已存在，直接返回成功（不重复处理）。
  - **第三步 数据库唯一约束兜底：** 支付流水表对 `(order_no, channel_trade_no)` 建唯一索引；即使 Redis 失效，重复插入也会被数据库拒绝。
  - **第四步 状态机校验：** 订单状态只允许 `待支付 → 支付中 → 已支付` 单向跃迁，重复回调因状态不合法被拒绝。
  - **第五步 分布式锁：** 对同一订单加 Redis 分布式锁（Redisson），保证同一订单的回调串行处理。
  - **第六步 异步通知：** 入账成功后通过 MQ 异步触发发货、积分、通知，且消费侧同样实现幂等（消费幂等表）。
  - **第七步 对账兜底：** 每日与支付渠道 T+1 全量对账，发现少账补单、多账挂起人工核实。
- **12 笔重复入账根因：** 支付渠道回调重试（网络超时后重发）时未做幂等，直接执行了入账逻辑；本次通过"SETNX + 唯一索引 + 状态机"三重防护彻底解决。

**6. 流量治理方案与组织保障**

- **限流：** （1）网关层令牌桶限流（按 IP、用户、接口维度，20 万 QPS 阈值，超出返回 429）；（2）应用层 Sentinel 单机限流（按接口 QPS 阈值，保护单机）；（3）分布式限流（Redis + Lua，控制全局总入口）；（4）热点商品单独限流（限制单商品 QPS 上限）。
- **熔断：** 对下游依赖（库存服务、支付服务、风控服务）配置熔断器，错误率超 50% 或 RT 超 500ms 触发打开，快速失败保护调用方；半开状态试探恢复。
- **降级：** 制定分级降级预案——一级降级关闭商品页评价与推荐、二级降级关闭积分与优惠券展示、三级降级非核心业务只读、四级降级仅保留下单与支付。降级开关通过配置中心（Nacos/Apollo）动态推送，秒级生效。
- **隔离：** 线程池隔离（每类服务独立线程池，核心业务线程池预留 30% 余量）、集群隔离（大促核心链路独立部署集群）、机房隔离（多可用区部署，同城双活）。
- **削峰：** RocketMQ 承载峰值流量，队列积压监控告警；设置消息 TTL 与死信队列；消费端按 3 倍峰值能力配置，并支持动态扩容消费实例。
- **容量与演练保障：** 大促前完成全链路压测（影子库 + 影子表，压测流量打标隔离）、单机压测标定容量基线、故障演练（Chaos Engineering，模拟 Redis 宕机、MQ 延迟、DB 主从切换）、限流熔断阈值实压校准。
- **组织保障：** 成立大促保障指挥部（总指挥 + 各域负责人），建立"**值班表 + 值守大屏 + 应急预案手册 + 一键降级开关 + 15 分钟故障上报机制**"；分时段封网（大促前 24 小时冻结变更）；大促后进行复盘（故障复盘 + 性能复盘 + 容量复盘），沉淀经验教训入库。
- **监控与可观测：** 全链路追踪（TraceId 贯穿）、Metrics（QPS/RT/错误率/缓存命中率/队列积压）、日志集中（ELK）、告警分级（P0 电话 + P1 短信 + P2 企业微信），核心指标 1 分钟粒度监控。

**踩分要点**：
- 第 1 问须覆盖接入层、应用层、缓存层、数据层、一致性、容量压测六个方面，不能只答"数据库压力大"。
- 第 2 问须体现五层分层（接入/应用/缓存/数据/异步），并把六大手段逐条对应落地。
- 第 3 问必须写出四级缓存（CDN/Nginx/本地/Redis）+ 热点探测 + key 打散 + 本地副本，缺一不可。
- 第 4 问必须强调 **Lua 原子脚本** 与 **数据库条件更新（num >= qty）** 双保险，并说明异步落库与对账回补。
- 第 5 问必须写出幂等三要素（唯一标识/去重存储/过期策略）与至少三种实现（SETNX、唯一索引、状态机）。
- 第 6 问须覆盖限流、熔断、降级、隔离、削峰五类技术手段 + 压测演练 + 组织保障 + 监控可观测。

## 记忆口诀

**高并发六手段**：分层解耦、缓存前置、异步削峰、读写拆分、水平扩展、流量治理。

**利特尔法则**：并发 = QPS × RT，算线程池先算这个。

**高并发四原则**：上游能做的不下沉，能用缓存的不查库；能异步的不同步，能合并的不逐次。

**缓存更新四策略**：旁路（Cache Aside）、穿透（Read/Write Through）、写回（Write Behind）、预刷新（Refresh Ahead）。

**缓存三大坑**：穿透查空库（布隆+空值缓存）、击穿热点失效（互斥锁+逻辑过期）、雪崩大批过期（随机 TTL + 多级缓存）。

**Cache Aside 口诀**：先更库、再删缓存，延迟双删保平安；更新缓存不如删缓存，删了自然回源来。

**Redis 三态**：主从做读写分离，哨兵管自动切换，Cluster 靠 16384 槽做分片。

**分片算法四类**：范围、哈希、一致性哈希、路由表。

**分片键四原则**：高基数、分布匀、查询频、少跨片。

**分库分表五难题**：跨库 JOIN、分布式事务、全局 ID、跨库分页、跨库排序。

**分布式 ID 五法**：UUID 无序、自增单点、号段批量、Snowflake 趋势递增、Redis INCR。

**限流四算法**：计数器有临界、滑窗更平滑、漏桶恒速率、令牌桶允许突发（最常用）。

**熔断三态**：关闭放行、打开快失败、半开试探恢复。

**降级四原则**：保核心舍非核心，保读舍写，保老舍新，保支付舍其他。

**隔离三招**：线程池隔离、信号量隔离、集群/机房隔离。

**秒杀五层漏斗**：CDN 静态化 → 前端限流 → 网关令牌桶 → Redis 预扣减 → MQ 异步下单。

**CAP 三选二**：分区必有（P），在 C 与 A 之间选；CP 强一致（ZK/Etcd），AP 高可用（Eureka/Cassandra）。

**BASE 三要素**：基本可用、软状态、最终一致。

**最终一致五法**：本地消息表、最大努力通知、TCC、Saga、对账补偿。

**幂等四方案**：唯一索引兜底、Token 机制、状态机跃迁、分布式锁。

**幂等三要素**：全局唯一标识 + 去重存储 + 过期策略。

**不超卖双保险**：Redis Lua 原子预扣（判断与扣减同脚本），MySQL 条件更新（num >= qty 判影响行数）。
