## 今日核心概念
### 1. Service Mesh 服务网格
定义：一种把微服务间的通信、流量管理、安全、可观测性等"非业务"能力从应用进程中剥离出来，下沉到独立的网络代理层（Sidecar）的架构模式。业务进程只关心业务逻辑，跨服务的所有"管道"由基础设施统一接管。
关键要点：
- Sidecar 边车模式：与业务 Pod 一对一部署的代理（Envoy），拦截所有出入口流量，业务无感知
- 控制面（Control Plane）vs 数据面（Data Plane）：Pilot/istiod 配置下发，Envoy 执行转发
- 核心能力：流量路由（金丝雀、A/B、镜像）、熔断限流、mTLS 安全、可观测性、策略灰度
- 代表实现：Istio（功能最全）、Linkerd（轻量 Rust）、Consul Connect、Envoy 原生
- 与传统 SDK 方式（Spring Cloud）对比：业务零侵入、语言无关，但多一跳延迟与运维复杂度

### 2. Envoy 与 xDS 协议
定义：Envoy 是 Lyft 开源的高性能 C++ L7 反向代理，作为 Service Mesh 数据面事实标准；xDS（LDS/RDS/CDS/EDS）是 Envoy 与控制面之间的动态配置发现协议族。
关键要点：
- LDS：Listener 发现，定义监听端口与过滤器链
- RDS：Route 发现，配置路由规则（路由到哪个 Cluster）
- CDS：Cluster 发现，定义上游服务集群
- EDS：Endpoint 发现，订阅具体实例 IP 与负载权重
- 优势：动态配置无需重启、增量推送 xDS、最终一致性，比 Nginx reload 平滑

### 3. OpenTelemetry 可观测性三支柱
定义：OpenTelemetry（CNCF 统一标准）整合了 Metrics、Logs、Traces 三大可观测性支柱，提供厂商中立的采集、传输、SDK 规范，取代 Zipkin/Jaeger/OTel 三足鼎立。
关键要点：
- Metrics 指标：Counter/Gauge/Histogram，定时聚合，低成本，适合监控告警
- Logs 日志：离散事件，结构化 JSON，排查现场，但量大成本高
- Traces 链路：跨服务调用树，TraceID/SpanID 串联，定位慢调用根因
- 三者关系：Trace 锚定请求链，Metric 看趋势，Log 看细节，需统一关联 ID
- OTLP 协议：基于 gRPC/HTTP 的标准化传输协议，告别厂商私有采集器

### 4. 多云与混合云架构
定义：将业务部署跨多个公有云（AWS+Azure+阿里云）或混合私有云+公有云的架构模式，避免厂商锁定、提升可用性、满足合规与数据主权要求。
关键要点：
- 多云 vs 混合云：多云=多家公有云；混合云=私有云+公有云互通
- 挑战：网络互联（专线/SD-WAN）、统一身份（IAM 联邦）、数据迁移与同步、应用跨云部署
- 抽象层：Terraform/Pulumi IaC 统一编排、Kubernetes 跨云一致运行时
- 适用场景：灾备双活、地理合规（数据不出境）、避免厂商绑定、成本套利
- 常见误区：以为多云 = 高可用，实际反而放大复杂度与故障域

### 5. 云原生安全与零信任深化
定义：在云原生环境下，以"永不信任、始终验证"为核心，对每一次访问请求进行身份认证、授权、最小权限控制的安全架构范式。
关键要点：
- 三大原则：Never Trust / Always Verify / Least Privilege
- 关键技术：SPIFFE/SPIRE 工作负载身份、mTLS 全链路加密、OPA/Kyverno 策略即代码、SBOM 制品签名
- 4C 安全模型：Code/Container/Cluster/Cloud 四层纵深防御
- 供应链安全：SLSA 框架、Cosign 镜像签名、Sigstore 密钥透明
- 与传统边界安全对比：不再依赖网络位置（内/外网），而是身份+上下文+设备信任度

## 案例分析题
**题目**：
某互联网电商平台日均订单 5000 万，2024 年完成容器化与微服务拆分后遭遇三大瓶颈：
① 微服务数量突破 800 个，业务团队反馈 Spring Cloud Gateway 网关成为性能瓶颈，链路追踪断层，无法定位跨服务慢调用；
② 大促期间频繁因某商品详情服务故障引发雪崩，传统 Hystrix 线程池隔离已无法精细化控制；
③ 安全团队要求所有 Pod 间通信强制 mTLS，但 SDK 改造涉及 30+ 语言栈成本过高。

请结合云原生架构，给出该平台下一阶段架构演进方案，并说明每项技术选型的核心理由。

**参考答案**：
瓶颈①网关性能+链路追踪→引入 Istio 服务网格替代 Spring Cloud Gateway，Envoy 数据面处理东西向流量，Jaeger/Tempo 接管分布式追踪，通过 OpenTelemetry SDK 统一埋点，业务零改造解决跨服务慢调用定位。
瓶颈②雪崩与精细化流量控制→基于 Istio 的 DestinationRule 配置熔断（连接池/连续错误数/异常检测），结合 Envoy 的流量镜像与故障注入做混沌演练，配合 K8s HPA+Istio 的请求速率限流实现大促态弹性。
瓶颈③mTLS 全链路加密→启用 Istio 的 STRICT mTLS 模式，由 istiod 统一签发 SPIFFE 身份证书，所有 Pod 间通信自动加密，业务进程无需改造证书管理，30+ 语言栈一次性覆盖。
补充可观测体系：Prometheus 采集 Metrics、Loki 聚合 Logs、Tempo/Jaeger 存储 Traces，三者通过 TraceID 关联；Grafana 统一看板。
演进收益：业务团队专注业务、可观测性全景化、安全合规达成、跨语言统一治理。

**踩分要点**：
- 必须点出"Sidecar 数据面 + 控制面"是 Service Mesh 替代 Spring Cloud 网关的核心
- mTLS 必须提到 SPIFFE 身份与零信任理念，不能只说"加密通信"
- 雪崩治理要区分"传统 Hystrix 已过时"与"Istio 熔断配置（connectionPool/异常检测）"
- 可观测性三大支柱（Metrics/Logs/Traces）必须三件齐全且说明关联机制
- 大促场景要提及"流量镜像、混沌工程、限流熔断三件套"
- 强调"业务零侵入、语言无关"是 Mesh 选型相对于 SDK 方案的核心优势

## 记忆口诀
服务网格三件套：边车代理 Envoy 跑，控制面是 istiod，安全治理一并包。
xDS 四兄弟：L 听 R 路由 C 集群 E 端点，动态配置全靠它。
可观测三支柱：M 看趋势 L 看现场 T 看链路，统一 TraceID 串。
零信任三原则：不信任、常验证、最小权，身份代替网络边界。
多云四挑战：网络通、身份通、数据通、应用通，IaC 统一编排。
4C 安全模型：代码、容器、集群、云，四层纵深守供应链。
