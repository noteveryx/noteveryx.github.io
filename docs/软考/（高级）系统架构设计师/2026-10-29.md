## 今日核心概念

### 1. 维度建模体系与总线矩阵

定义：维度建模（Dimension Modeling）以"业务过程"为中心组织数据，用一张事实表记录度量值、用若干张维度表提供分析视角，将数据组织成星型 / 雪花型 / 星座型结构，支撑多维切片、钻取与聚合分析。

关键要点：
- **三要素**：业务过程（Business Process，如"订单支付"）、事实表（Fact Table，存度量值）、维度（Dimension，存分析角度）
- **粒度（Granularity）是维度建模的第一设计决策**：粒度一旦确定不可更改，事实表行数 = 业务事件数 × 粒度。**先定粒度，再定维度，最后定事实**
- **三种表结构**：
  - 星型（Star Schema）：维度表全部反范式冗余，事实表只存代理键与外键。**join 少、查询快，但维度表冗余、存储大**
  - 雪花（Snowflake）：维度表继续拆分规范化，减少冗余省空间，**join 层数增加、查询性能下降**
  - 星座（Constellation）：多个事实表共享同一套一致维度，实现跨主题交叉分析
- **总线矩阵（Bus Matrix）**：横向列出一致性维度、纵向列出业务过程，交叉点标记事实表。它是 Kimball 路线的设计蓝图，也是多个数据集市整合、避免"指标打架"的唯一抓手
- 建模流程：选定业务过程 → 声明粒度 → 确定维度 → 确定事实与度量 → 分配代理键 → 判断维度退化 → 校验一致性维度

### 2. 事实表类型与维度表设计要点

定义：事实表按加载时机与生命周期分为事务事实表、周期快照事实表、累积快照事实表三大类；维度表按功能分为一致维度、退化维度、冗余维度、拆分维度等。

关键要点：
- **事务事实表**：每发生一次业务事件写一行（订单明细）。**只插不改不删**，性能最好，需按周期分区与归档
- **周期快照事实表**：按固定周期（月末 / 每周）记录状态存量（账户月末余额）。**可加性受限**：余额属半可加，可跨维度加、不可跨时间加
- **累积快照事实表**：以业务实体生命周期为粒度，每个关键里程碑更新同一行（订单：下单→支付→发货→签收）。**行数固定、字段稀疏**，需设"未完成"标志位
- **可加性三型**：完全可加（金额、数量，可沿所有维度求和）、半可加（余额、库存，只能跨部分维度求和）、不可加（毛利率等比率，必须存分子与分母，不能存平均值）
- **维度表要点**：
  - 一致维度（Conformed Dimension）：被多个事实表共享，保证跨主题口径统一
  - 退化维度（Degenerate Dimension）：只存在于事实表中、不在维度表中的属性（如订单号），不参与 join
  - 冗余维度：把低基数常用属性（性别、年龄段）直接冗余进事实表，**用空间换 join 性能**
  - 拆分维度：把宽维度拆成多个窄表（日期维拆年 / 月 / 日），降低单表宽度
- **代理键（Surrogate Key）**：维度表主键用无业务含义的自增 / 雪花 ID，业务主键作为自然键另存。**解决业务主键变更导致事实表关联断裂的问题**

### 3. 缓慢变化维（SCD）六种处理策略

定义：缓慢变化维（Slowly Changing Dimension）指属性值随时间变化但变化频率低的维度，如客户等级、客户地址、事项状态定义。SCD 是保证历史事实可被正确解释的核心机制。

关键要点：
- **Type 1 覆盖更新**：直接 UPDATE 新值覆盖旧值。**不保留历史，历史事实被污染**，仅适用于纠错类属性（如录错手机号）
- **Type 2 新增行**：旧行保留 + 插入新行，附加有效起止时间（Valid_From / Valid_To）与版本号或当前标志位。**可还原任意历史时点状态，是金融、政务场景默认选择**
- **Type 3 新增列**：保留"当前值列 + 上一个值列"。仅适合变化极少且需前后对比的属性，**列会持续膨胀，不推荐**
- **Type 4 历史表**：主维表只存当前值，另建维度历史表记录全部变更，介于 Type 1 与 Type 2 之间
- **Type 5 不处理**：历史与当前保持一致，适用于维度从不变化
- **Type 6 组合**：Type 2 + Type 3 同时实现，既保留明细历史又支持当前 / 上期对比
- 工程要点：Type 2 的时间区间采用**左闭右开** `Valid_From <= 业务时间 < Valid_To`，避免边界重复计数；海量维度用拉链表（Zipper Table）实现增量更新

### 4. 数据仓库分层架构与指标体系

定义：数据仓库分层按加工深度划分数据资产层次（ODS → DWD → DWS → ADS + DIM）；指标体系是对业务度量的标准化定义与口径管理机制。

关键要点：
- **ODS 操作数据层**：贴源存储，保持与业务库结构一致，不做清洗，只做落地与增量抽取
- **DWD 明细层**：清洗、去重、统一编码与标准化，做**维度退化**（常用维度属性打平冗余进明细表），是全链路数据基座
- **DWS 汇总层**：按主题 + 维度 + 时间窗口轻度汇总（宽表），面向多场景复用
- **ADS 应用层**：面向具体报表、大屏、接口的结果表与数据集市
- **DIM 维度层**：一致性维度公共层，独立管理代理键与缓慢变化维
- **指标体系三层**：**原子指标**（不可再分，如"支付订单数"）→ **派生指标**（原子指标 + 计算逻辑 + 时间周期 + 业务范围，如"日均支付订单数"）→ **复合指标**（多个派生指标组合，如"客单价 = 支付金额 / 支付订单数"）
- **指标口径三要素**：统计口径 + 时间周期 + 业务范围。跨部门数据打架的根因通常**不是技术而是口径未统一**，因此必须建"指标字典 / 指标平台"，做到一指标一编码一责任人
- 快照与拉链选择：需按周期重算状态存量用周期快照表；需取任意历史时点状态用拉链表

### 5. 数据治理、数据质量与数据资产管理

定义：数据治理是对数据资产管理行使权力和控制的活动集合（参考 ISO/IEC 38500 与 DCMM 数据管理能力成熟度模型），涵盖组织、制度、流程、技术四个要素，目标让数据资产"找得到、看得懂、用得准、管得住"。

关键要点：
- **元数据三分**：技术元数据（库表结构、字段类型、同步任务）、业务元数据（业务定义、指标口径、数据责任人）、管理元数据（分级分类、权限、合规要求）。**业务元数据缺失是数据仓库最大的隐性成本**
- **数据血缘**：表级、字段级、任务级、报表级的上下游依赖关系，是变更影响评估与故障根因定位的基础
- **数据质量六维度**：完整性、准确性、一致性、及时性、有效性、唯一性；对应六类核查规则——空值率、值域与格式、跨系统对账、更新延迟、枚举合法性、重复键检查
- **数据安全分级分类**：依据《数据安全法》《个人信息保护法》与行业要求，划分一般数据 / 重要数据 / 核心数据，以及个人信息、政务数据等类别；落实三权分立（数据 Owner / Steward / Custodian）与最小必要授权
- **数据资产入表**：财政部《企业数据资源相关会计处理暂行规定》（2024 年 1 月 1 日起施行）允许符合条件的数据资源作为无形资产或存货入表，前提是**预期经济利益很可能流入且成本能可靠计量**，这是数据治理由"成本中心"转向"利润中心"的关键节点
- **治理组织**：数据 Owner（业务负责人定口径）、数据 Steward（数据管理员定标准）、数据 Custodian（数据运维保运行）、数据安全官（合规与分级），四角色分工是 DCMM 八个能力域的落地基础

## 案例分析题

**题目**：某市"一网通办"政务数据仓库建设项目。现状：全市 11 个委办局自建业务系统共 263 个业务库，同一事项在不同委办局口径不一致，跨部门综合报表平均出具周期 3 天，一线窗口人员无法自助查询"一件事一次申请"的关联数据。市大数据局决定建设统一数据仓库，要求：一网通办驾驶舱数据每日更新，核心指标口径全市唯一，事项办理全链路可追溯，同时满足等保三级与数据分类分级要求。

**【问题1】（6分）** 请设计该项目的数据仓库分层架构，说明 ODS、DWD、DWS、ADS、DIM 五层各自的职责，并给出本项目各层的具体内容设计。

**【问题2】（6分）** 本项目应采用 Inmon 路线还是 Kimball 路线进行建模？说明理由，并至少给出 2 个本项目的一致维度示例。若采用 Kimball 路线，请说明总线矩阵的作用与画法。

**【问题3】（6分）** 委办局的"办件状态"定义随政策调整会发生变化（例如原"受理即办结"改为"送达即办结"）。为保证历史报表口径可追溯，请设计缓慢变化维处理策略，说明选用类型、字段设计与边界处理方式。

**【问题4】（6分）** 请设计本项目的指标体系：给出至少 2 个原子指标、2 个派生指标、1 个复合指标，并说明保证全市口径唯一的机制。

**【问题5】（6分）** 从数据治理角度，说明本项目在数据质量、数据分类分级、元数据与血缘、数据资产入表四个方面的建设要点与落地举措。

**【参考答案】**：

**问题1（数据仓库分层架构）**
- 采用 ODS → DWD → DWS → ADS 分层，外加独立 DIM 维度层，共五层。
- **ODS 操作数据层**：11 个委办局 263 个业务库通过 CDC / 定时抽取落地区，按源系统分库分表存放，**保留原始结构不做清洗**，只做幂等去重与增量标记；保留 3 年历史用于追溯。
- **DWD 明细层**：统一清洗规则（去重、空值处理、主数据代码映射）、统一编码（事项编码、办件状态码、行政区划码），对"办件""申请""人员""法人"四类核心实体做明细标准化；实施维度退化，将办件状态名称、事项名称、行政区划名称等高频属性直接冗余到明细表，减少后续 join。
- **DWS 汇总层**：按"时间 + 区域 + 事项 + 部门"轻度汇总，形成受理量、办结量、办结时长、一次办结率等主题宽表，供驾驶舱与跨部门报表复用。
- **ADS 应用层**：面向一网通办驾驶舱、领导决策大屏、窗口自助查询、一件事联办等具体场景构建结果表与数据集市，直接对接前端接口。
- **DIM 维度层**：独立维护日期、行政区划（省-市-区-街道）、事项、办件状态、委办局、部门、人员等一致性维度，统一分配代理键。

**问题2（建模路线与一致维度）**
- **以 Kimball 维度建模为主路线、Inmon 思想为辅的混合策略**。理由：本项目业务过程清晰（受理、办结、送达、评价）、上线时限紧、且需快速响应"一件事"跨部门联办，Kimball 自底向上按业务过程建维度模型见效快、贴近业务人员认知；同时引入 Inmon 的统一企业数据模型思路用于维度标准化与指标口径管理，弥补 Kimball 跨主题一致性弱的短板。
- **一致维度示例**：① 行政区划维度（被办件量、办结时长、事项分布等多个事实表共用）；② 事项（事项编码）维度；③ 办件状态维度；④ 时间维度；⑤ 委办局 / 部门维度。
- **总线矩阵**：横轴为一致性维度（时间、行政区划、事项、状态、部门、人员），纵轴为业务过程（受理、办结、送达、评价、超期办件），交叉格填入对应事实表名（如"受理"×"时间"×"行政区划"= 办件受理事实表）。作用：① 规划各数据集市的事实表与维度表归属，避免重复建模；② 识别未覆盖的维度组合与缺口；③ 保证各数据集市共用同一套一致维度，是跨部门指标口径统一的架构前提。

**问题3（缓慢变化维策略）**
- 选用 **SCD Type 2（新增行 + 有效期）**。理由：政策调整后必须能按业务发生时间还原当时生效的状态口径，否则历史报表被"追溯性篡改"，无法作为审计与考核依据；Type 1 会污染历史，Type 3 列膨胀且只能保留有限历史，Type 4 需多表关联查询且不利于主表 join。
- 字段设计：办件状态维度表增加代理键（状态代理键）、自然键（状态码 + 状态名称 + 版本号）、`valid_from`（生效时间）、`valid_to`（失效时间）、`is_current`（当前标志位）、`policy_ref`（关联政策文号），**历史行只读不更新**。
- 边界处理：有效区间采用**左闭右开** `[valid_from, valid_to)`，即 `valid_from <= 业务时间 < valid_to`；对当前行 `valid_to` 置为最大值（如 9999-12-31）。这样政策生效当日的办件只会命中一行，避免边界重复统计。事实表存**状态代理键**而非状态码，保证与维度版本严格对应。
- 实施要点：政策生效前需跑批提前加载新版本行并关闭旧行有效期；采用拉链表（Zipper Table）按日增量合并，避免每次全量重刷；建立政策文号与状态版本的映射关系作为一致性稽核规则。

**问题4（指标体系与口径统一）**
- **原子指标（不可再分）**：① 办件受理量（按确认受理的办件记录计数）；② 事项办结量（按产生办结结果的办件记录计数）；③ 超期办件数。
- **派生指标（原子指标 + 逻辑 + 周期 + 范围）**：① 一次办结率 = 一次办结的办件数 / 办件受理量（统计周期：日 / 月 / 年；业务范围：全市或按行政区划）；② 平均办结时长 = 办结总时长 / 办结量（按自然日或工作日两种口径分别计算并分别命名，不混用）；③ 超期率 = 超期办件数 / 办件受理量。
- **复合指标（多个派生指标组合）**：① 跨部门联办率 = 涉及两个及以上部门联办的办件数 / 办件受理量；② 一件事一次办结率 = 一次办结的办件数 / 关联事项平均数。
- **口径统一机制**：① 建立**指标字典 / 指标平台**，一指标一编码（建议"域_主题_业务过程_口径版本"命名）、一名称定义、一统计口径（分子分母、是否含退件、是否去重）、一时间周期定义、一业务范围（全市 / 区域 / 部门）、一责任人；② 指标定义下沉到 DWD / DWS 层统一计算，**禁止在 ADS 层或前端临时计算**，杜绝"同名不同义"；③ 口径变更走版本化管理（新编码或新版本号 + 生效日期），历史数据按原口径保留、不可覆盖；④ 建立跨部门指标委员会（业务 Owner 主导）与发布审核流程，指标上线需评审；⑤ 建立指标一致性稽核规则（同一指标在不同报表取值比对、与权威系统对账），纳入数据质量监控告警。

**问题5（数据治理建设要点）**
- **数据质量**：按完整性、准确性、一致性、及时性、有效性、唯一性六维度建立指标卡与稽核规则集——完整性核查办件关键字段非空率；准确性核查办件状态码与字典匹配、与源系统对账；一致性核查"办结量"在市级与委办局口径下的差异率；及时性核查数据到达时延（当日增量 6:00 前入库）与日更任务成功率；有效性核查值域、格式与枚举合法性；唯一性核查办件编号重复。规则实现为调度任务 + 质量看板 + 阈值告警 + 问题工单闭环（发现→派单→根因整改→复检），并对核心指标设置质量不达标时的数据发布熔断。
- **数据分类分级与安全**：依据《数据安全法》《个人信息保护法》及政务数据相关要求，将数据划分为一般数据 / 重要数据 / 核心数据，并按个人信息、重要信息、业务数据分类；建立**数据分类分级清单与目录**，逐表逐字段标注敏感级别；落实三权分立与最小必要授权，对个人身份、联系方式等敏感字段做脱敏 / 加密 / 行列级权限，核心库与大数据平台分离部署并接入统一身份认证（依托政务外网统一认证体系），实现"以用途定范围"的数据授权与用完即收的临时授权机制，满足等保三级要求。
- **元数据与血缘**：建设统一元数据管理平台，采集**技术元数据**（库表结构、字段类型、任务依赖、同步链路）、**业务元数据**（指标字典、事项口径、业务定义、数据责任人）与**管理元数据**（分级分类、权限、合规要求）；实现字段级血缘（从源系统字段 → DWD → DWS → ADS → 报表 / 接口），支撑"一件事一次申请"全链路溯源与影响分析；建立数据地图按业务域—主题—表—字段—指标五级导航，并明确每个数据资产的责任人。
- **数据资产入表**：梳理符合条件的数据资源清单，依据财政部《企业数据资源相关会计处理暂行规定》（2024 年 1 月 1 日起施行）判断能否作为**无形资产**（自用类）或**存货**（对外交易类）入表，前提是能够带来预期经济利益且成本能可靠计量；配套建立数据资源台账（数据资源识别、确权、成本归集、收益分摊、减值与处置），将数据加工投入从期间费用转为资产，为数据要素市场化与持续投入提供激励。**注意：入表不改变数据安全合规义务，须同步完成分类分级与合规评估。**

**踩分要点**：
- **问题1**：分层缺一扣分；必须写清"ODS 不清洗、DWD 清洗 + 维度退化、DWS 轻度汇总、ADS 面向场景、DIM 统一代理键"五个要点，每点 1 分左右。**答"ODS/DW/DM 三层"不给分**，本项目必须体现 DIM 维度层与 DWD 维度退化两个加分点。
- **问题2**：只答"Kimball 好"不给分，必须给**理由**（业务过程清晰、上线时限、跨部门口径统一需求）+ **2 个以上一致维度** + **总线矩阵的三个作用**。只写 Inmon 或只写 Kimball 单一路线且无权衡分析，最多给一半分。
- **问题3**：核心踩分点是**必须答 Type 2 并说明选型理由**（历史可还原、审计需要），以及**有效期的左闭右开边界处理**和**事实表存代理键而非状态码**。只写"用 Type 2 存历史"而无字段设计，最多 3 分；答 Type 1 或 Type 3 且无理由说明，扣 3-4 分。
- **问题4**：原子 / 派生 / 复合三层各写够数量且给出计算公式；**必须写口径统一机制**（指标字典、一指标一编码、口径变更版本化、计算下沉 DWS 而非 ADS、稽核对账），仅列指标不给机制，本问最多 6-8 分。注意"平均办结时长"必须说明工作日 / 自然日口径不能混。
- **问题5**：四个方面（质量、安全、元数据血缘、入表）**每点都要落到"机制 + 举措"两层**，只写名词不给手段不加分。质量维度要能对应到六类稽核规则；安全要提到**三权分立 + 最小必要 + 分类分级清单**；血缘要强调**字段级**（表级不够）；入表要写出**适用前提（经济利益很可能流入 + 成本可靠计量）与无形资产 / 存货两条路径**，并点明**入表不豁免安全合规义务**。
- **通用踩分提醒**：案例题答案要"分点编号 + 先结论后展开"，每问开头用加粗一句话给出结论（如"采用 Type 2 缓慢变化维"），阅卷按点给分，避免大段文字；涉及数据必须给出可计算的量化目标（如非空率 ≥ 99.5%、对账差异率 ≤ 0.1%、数据 6:00 前入库）。
