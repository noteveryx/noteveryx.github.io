## 今日核心概念

### 1. 软件构件与构件模型

定义：软件构件（Component）是具有明确接口、可独立部署、可独立复用、可被组合的封装软件单元；构件模型（Component Model）规定了构件的接口规范、部署形态与组装规则，是构件能够被第三方开发、部署和复用的基础规范体系。

关键要点：
- **构件的三大核心特征**：**接口明确**（对外只暴露契约，内部实现完全隐藏）、**独立部署**（可单独装入运行单元）、**可复用**（可被多个系统组装引用）。**构件 ≠ 类**：类只在编译期复用、依赖同一语言与进程；构件在运行期复用，可跨语言跨进程，粒度更大
- **构件模型的五大要素**：**接口规范**（提供接口 / 需求接口，IDL 或类型签名）、**封装**（实现隐藏）、**实现**（内部算法与数据）、**部署**（打包与配置）、**组装规则**（构件之间如何连接）
- **经典构件模型对比**：
  - **COM / DCOM**：微软组件对象模型，进程内 + 跨进程（DCOM），以接口指针与引用计数为核心，COM+ 补齐事务与安全服务；适合 Windows 体系与遗留 .NET 系统集成
  - **EJB（企业 JavaBeans）**：企业级 Java 构件规范，三类 Bean——**Session Bean**（有状态 / 无状态，承载业务逻辑）、**Message Bean**（异步消息处理）、**Entity Bean**（实体持久化映射，EJB 3.x 已移除）；容器提供事务、安全、并发、生命周期等**容器托管服务**，是"应用服务器 = 构件容器"模式的代表
  - **.NET 构件模型**：以**程序集（Assembly）**为部署单元，CLR 提供统一类型系统与运行时，**强名称签名**保证唯一性与版本绑定
  - **CORBA 构件模型**（ORB + IDL + IIOP）：真正的**跨厂商跨语言**分布式构件规范，构件可在不同厂商的对象请求代理上互操作
- **构件 vs 服务 vs 模块三者辨析（高频考点）**：**模块**是编译期划分、不能独立部署；**构件**可独立部署、强调二进制级复用与接口契约；**服务**是网络可达的能力单元、强调松耦合与运行时治理。**构件是"部署与复用单元"，服务是"通信与治理单元"**，现代微服务本质是"带远程调用契约的构件"，但构件更强调可组合性与版本治理
- **构件粒度权衡**：粒度过粗 → 复用率低、牵一发动全身、无法独立演进；粒度过细 → 组合开销、接口爆炸、依赖地狱。**推荐粒度 = 一个构件承担一个可独立描述的业务能力或技术关注点**，并在评审中明确"不变核心、变化外围"
- **架构视角的构件价值**：构件化把"重复造轮子"变成"复用资产沉淀"，是组织级架构资产（Architecture as Asset）落地的最小载体，也是**架构治理从图纸走向代码**的关键抓手

### 2. 基于构件的软件工程（CBSE）与软件复用层次

定义：基于构件的软件工程（Component-Based Software Engineering）是**以构件的开发、构件库的建立和构件的组装为核心**的软件工程方法，把"从零编写代码"转变为"从构件库中选取、适配、组装构件"，核心收益是缩短交付周期、降低开发成本、统一质量基线。

关键要点：
- **CBSE 三要素（必背）**：**构件库（Repository）** + **构件开发（Development）** + **构件组装（Composition/Assembly）**。三要素中**构件库是基础，组装是核心活动**，构件开发阶段必须考虑"未来如何被复用与组装"
- **复用三个层次（必背）**：
  - **黑盒复用（Binary / 构件级复用）**：直接复用已编译的二进制构件（.jar / .dll / 容器镜像），**不接触源码**，效率最高，是 CBSE 的主战场
  - **白盒复用（源码级复用）**：拿到源码做裁剪修改，复用率最高但**耦合最深、后续演进困难**，只建议在内部强管控代码中采用
  - **灰盒复用（设计级复用）**：复用设计方案与接口契约，用不同技术栈重新实现，**在"框架替换、跨语言迁移、国产化适配"场景中最常用**（例如国产数据库/中间件替换时按原设计契约重新实现）
- **构件组装的三大方式（必背）**：
  - **顺序组装（Sequential Assembly）**：用**连接件（Connector）**把构件的输出接到下一个构件的输入，形成处理链
  - **层次组装（Hierarchical Assembly）**：把构件组织成**调用树**，上层构件调用下层构件（分层架构的装配形态）
  - **叠加组装（Overlay Assembly）**：在不改源码前提下**覆盖/替换**某些构件（如替换数据库驱动、替换日志实现），实现**可插拔与可替换**，代价是必须定义清晰的覆盖点与扩展契约
- **软件产品线（SPL）与特征建模**：产品线不是多个独立产品，而是**共享核心资产的一族产品**。核心概念——**特征（Feature）**、**特征依赖与约束**、**变体点（Variation Point）**、**变化点（Variation Point Realization）**、**可选特征 / 强制特征 / 变体特征**；特征树的**可选性（optional）**、**强制性（mandatory）**、**可选组（alternative / or-group）**、**多选组（and-group）**是特征依赖必考四类。**变体点实现方式**：绑定（BIND）、派生（DERIVE）、组合（COMPOSE）
- **复用的收益与代价（架构评审必答）**：收益 = 交付周期缩短、成本下降、质量基线统一、重复缺陷减少；代价 = **学习与选型成本、版本冲突与升级地狱、供应链安全风险、许可证合规风险、过度抽象导致的性能损耗与调试困难、架构僵化**。**结论：复用不是越多越好，应按"业务能力稳定度 × 复用收益"矩阵分级复用**

### 3. 构件库建设与构件治理

定义：构件库（构件仓库）是集中存放、检索、评价、分发构件资产的受控基础设施；构件治理是一套围绕"入库—评审—发布—升级—淘汰"的制度与技术机制，决定构件复用是资产还是负债。

关键要点：
- **构件检索方法三型**：**刻面分类（Faceted Classification）**（多维正交分类法，如"语言=Java / 领域=政务 / 架构风格=事件驱动 / 质量等级=生产可用"，最常用）、**属性分类（Attribute Classification）**（按预定义属性值组织）、**关键词 / 全文检索**（灵活但精度低）。**选构件库先看分类法，再看功能**
- **构件评价维度（选型清单）**：**功能适配性**（是否覆盖需求）、**非功能质量**（性能、可靠性、安全、可维护性、可移植性）、**接口契合度**（是否需改造）、**维护活跃度**（社区规模、版本节奏、响应速度）、**许可证合规**（开源许可是否允许商用与闭源分发）、**依赖与漏洞**（传递依赖数量、已知 CVE）
- **版本治理三件套**：
  - **语义化版本 SemVer**：`主版本.次版本.修订号`——**主版本变更 = 不兼容变更，破坏契约，次版本 = 向后兼容新增功能，修订号 = 向后兼容的缺陷修复**
  - **兼容性三型**：**向后兼容**（新版本兼容老数据/老调用方）、**向前兼容**（老版本能识别新数据）、**完全兼容**。**微服务契约演进默认只允许向后兼容**
  - **弃用策略（Deprecation）**：标记弃用 → 公布替代方案与迁移窗口 → 到期下线，**禁止静默升级**，破坏性变更必须走**并行期 + 双写双读 + 灰度切流**
- **构件库治理的"入库准出"清单**：源代码与构建可复现、许可证与版权清晰、单元与集成测试覆盖率达标、静态扫描与依赖漏洞扫描通过、安全评审与等保合规确认、**SBOM（软件物料清单）**自动生成、**构件签名与来源校验（Sigstore / Cosign 类）**、制品不可变与可追溯
- **架构资产化运营指标**：构件复用率（被引用构件数 / 总构件数）、**构件平均被引用数（扇出复用度）**、构件版本分叉数（同一能力存在多版本说明治理失效）、平均修复时长、构件导致的线上故障归因占比
- **常见反模式**：**"构件坟场"**（入库多、复用少，只当代码备份）、**"依赖地狱"**（传递依赖冲突、版本漂移）、**"静默升级"**（自动拉最新版本引发线上故障）、**"过度抽象"**（把业务逻辑塞进通用构件，导致无法定制）

### 4. 集成中间件与通信中间件选型

定义：中间件（Middleware）是位于应用与操作系统、网络、数据库等基础资源之间的**公共支撑软件层**，屏蔽底层差异并提供通信、数据管理、事务、目录、安全等通用能力；集成中间件是其中面向异构系统互操作的部分，是分布式架构的"隐形骨架"。

关键要点：
- **中间件五大类（教材主干）**：
  - **数据库中间件**：ODBC / JDBC 驱动、连接池、ORM 支持；解决"应用与数据库解耦 + 连接复用"
  - **远程过程调用中间件（RPC）**：**CORBA（IDL + ORB + IIOP，跨语言跨厂商）**、DCOM、Dubbo / gRPC（HTTP2 + Protobuf）、Java RMI。**特征：同步、位置透明、接口强契约**
  - **面向消息中间件（MOM）**：Kafka / RocketMQ / RabbitMQ / ActiveMQ；**提供发布订阅、点对点、消息持久化、削峰填谷、异步解耦、事件广播**
  - **事务中间件**：XA / 2PC、TCC、Saga、本地消息表 + 事务消息；解决**跨资源一致性**
  - **分布式对象 / 服务网格 / 边缘中间件**：CORBA 中间件、Istio（Sidecar + xDS）、CDN / 边缘计算节点（把计算与数据推到靠近用户处）
- **同步 RPC vs 异步消息 选型对比（高频考点）**：
  - **同步 RPC**：**强一致即时语义、低延迟**、调用链清晰；**缺点**：故障沿调用链放大、需处理超时与雪崩、可用性依赖被调方
  - **异步消息**：**削峰、解耦、广播、可重放、故障隔离**；**缺点**：**最终一致**、链路追踪需自建、排查链路变复杂
  - **决策规则**：**查询类、要求即时结果、下游强依赖 → 同步；写链路、跨域解耦、峰值不均、需广播或重放 → 异步**；混合模式（同步查 + 异步写 + 事件驱动）是主流
- **消息中间件的可靠性五要素（生产必备）**：
  - **持久化 + 多副本**：消息落盘、集群多副本（主从 / 多可用区），防 Broker 单点
  - **确认机制（ACK）**：生产端确认 + 消费端手动 ACK，失败不确认触发重投
  - **重试 + 死信队列（DLQ）**：可重试次数上限，超限进死信并告警，**避免无限重试打垮系统**
  - **幂等消费**：消费端按业务唯一键去重（唯一索引 / 状态机 / 去重表），**因为"至少一次"投递必然重复**
  - **顺序性保证**：全局有序代价极高，生产上用**分区有序**（同一业务键固定分区）实现局部有序
- **消息可靠性四大经典问题与对策**：**消息丢失**（三段确认：生产确认 → Broker 落盘 → 消费确认；配合事务消息 / 本地消息表）、**消息重复**（幂等 + 去重表）、**消息乱序**（分区有序 + 业务侧版本号 / 状态机过滤）、**消息积压**（扩容消费者 + 限流 + 死信 + 降级；排查堆积消费能力与生产速率差）
- **分布式中间件带来的新问题**：调用链变长导致**可观测性成本上升**（必须全链路 TraceID 贯穿）、**本地事务与远程调用的原子性**（需最终一致方案）、**中间件本身成为共享瓶颈**（需限流、隔离、多集群）

### 5. 构件组装集成与遗留系统演进策略

定义：构件组装集成是把独立构件通过接口与连接件装配成目标系统的过程；对既有系统的接入则需要"组装 + 适配"两类手段组合，核心目标是在**不停机、不失控**的前提下完成能力替换。

关键要点：
- **集成层次五级（由低到高）**：**文件级集成**（共享文件交换，耦合最松但一致性最差）→ **数据库级集成**（共享库表，最易形成"共享数据库反模式"）→ **API 级集成**（接口调用，行业主流）→ **消息级集成**（事件解耦，异步解耦程度最高）→ **数据级 / 分析级集成**（面向分析与决策的数据共享）
- **遗留系统接入五策略及风险**：
  - **直接改造重构**：风险最高、周期长，适合核心且有把握的核心系统
  - **绞杀者模式（Strangler Fig）**：在旧系统外围建新系统，逐步"绞杀"旧功能，**适合边界清晰的子系统**
  - **防腐层（Anti-Corruption Layer）**：新系统侧建适配层，把遗留模型翻译为新模型，**隔离污染、防止旧模型扩散，是遗留集成的首选**
  - **门面/适配器（Facade / Adapter）**：统一接口 + 包装器实现，最轻量
  - **数据同步双写对账**：CDC / ETL 双向同步 + 定期对账补偿，适合数据迁移与多系统并存期
- **契约测试保障组装正确性**：消费者驱动契约（Consumer-Driven Contract）——**提供方定义并发布契约，提供方桩服务（Provider Stub） + 消费方本地桩（Consumer Stub）双向验证**，**在 CI 阶段阻断不兼容变更**，是把"组装"从人工联调变成**可自动化验证**的关键
- **灰度与流量治理**：影子流量（Mirror，把真实流量复制给新版本但丢弃响应，用于压测与回归）、金丝雀（少量流量）、蓝绿（两套环境整体切换，回滚秒级）、A/B 分流、**流量染色**（按标记路由，保证同一次用户请求在全链路落到同一版本，是分布式追踪与灰度一致性的基础）
- **组装失败的典型根因与对策**：
  - **接口语义不一致**（同名不同义、单位 / 时区 / 编码差异）→ 契约测试 + 统一数据字典
  - **版本不兼容**（上下游依赖版本漂移）→ 依赖锁定 + 兼容性矩阵 + 受控升级
  - **隐式耦合**（跨构件直接访问数据库表）→ 架构守护测试（ArchUnit 类）禁止跨层直连
  - **性能悬崖**（串行化调用链叠加）→ 并行化 + 异步化 + 缓存 + 超时预算（Timeout Budget）
  - **职责边界模糊形成分布式单体**→ 以数据所有权划分限界上下文，禁止跨服务直连数据库

## 案例分析题

**题目**：

某市政务服务管理局现有"一网通办"平台，运行 6 年，主体是一套基于 .NET Framework 的单体应用（Windows Server + Oracle 数据库 + 自研工作流引擎），数据库存储了全市 40 余万家企业、800 余万人的办件与审批数据。原由集成商 A 独家维护，源码、构建脚本、构件制品全部封闭在集成商 A 内部，管理局只能拿到发布包。

2026 年该市启动"政务服务中台"建设，要求：18 个月内建成市级构件库与统一集成中台，支撑 6 个新建业务子系统（政策兑现、企业画像、办件批联合、容缺受理、信用监管、政策直达）复用能力；统一消息中心为跨部门协同提供异步通道；原单体在不停机的前提下分批迁移。

架构现状存在以下问题：
1. 60% 的代码为重复实现，例如工作流审批、表单渲染、消息通知、附件预览在多个系统中被反复开发，质量参差；管理局无构件库，构件全靠"从集成商 A 采购"。
2. 迁移过程中出现"共享数据库反模式"：新系统直接读写老库表，导致老库无法下线，改造无法收敛。
3. 统一消息中心上线后，消费端积压严重，峰值时段积压消息量超过 8000 万条，部分关键审批消息延迟 40 分钟；期间还发生过 3 次"重复投递导致办件被重复办结"的严重事故。
4. 集成商 A 提出方案：建议管理局一次性购买其全部既有构件并整体切换，理由是"复用最彻底、风险最小"，但报价高、且构件为封闭二进制、后续无法自主演进。

请回答：

**问题 1（8 分）**：针对本项目的复用目标，请从构件模型与复用层次角度给出架构建议，并说明 CBSE 的三要素在本项目中分别对应哪些具体工作。同时指出集成商 A 方案的三个主要风险。

**问题 2（8 分）**：为避免"共享数据库反模式"并支撑单体平滑迁移，请设计目标集成架构：给出接入层次选择、遗留系统接入策略、契约保障机制，以及灰度与回滚方案。

**问题 1（8 分）**

架构建议：

- **构件模型选择**：政务中台面向新建 6 个子系统，属**异构技术栈并存、跨厂商交付**场景，建议以 **.NET 构件模型（程序集 + 强命名 + 契约接口）** 承接存量 Java / .NET 混合资产，统一采用 **IDL / OpenAPI + 版本化契约** 作为跨语言接口规范；对确需跨语言跨厂商集成的部分按 **CORBA 风格的对象契约**（或 gRPC + Protobuf）定义，避免直接依赖对方 SDK。
- **复用层次选择**：新建 6 个子系统优先采用**黑盒复用（构件级 / 二进制复用）**——以构件库中的工作流引擎、表单引擎、消息通知 SDK、附件预览服务作为黑盒依赖；确需深度定制的（如特殊审批流程）采用**灰盒复用（设计级复用）**，保留原设计契约、由新团队用统一技术栈重新实现，**明确禁止白盒级源码级修改**（否则将丧失构件独立性、造成升级地狱）。
- **构件粒度原则**：以"一个构件 = 一个可独立描述的业务能力或技术关注点"为准，工作流 / 表单 / 消息 / 附件 / 组织权限统一沉淀为平台级构件；各业务子系统只编排不重造。

CBSE 三要素在本项目中的对应：

- **构件库**：建设"市级政务构件库"，完成存量资产盘点（识别 6 类重复实现）、构件化改造、统一入库评审与版本发布，并对接构件登记与依赖分析（SBOM）。
- **构件开发**：对工作流引擎、表单引擎、消息通知、附件预览等高价值重复资产进行构件化重构（解耦、去业务耦合、接口契约化、自动化测试覆盖），并建立构件版本流水线（构建 → 测试 → 扫描 → 签名 → 发布）。
- **构件组装**：以"构件库 + 组装规范"支撑 6 个子系统的搭建，明确组装方式：流程类走**顺序组装**、平台分层走**层次组装**、可替换部件（数据库驱动 / 消息实现 / 日志）走**叠加组装**。

集成商 A 方案的三个主要风险：

1. **不可自主演进、供应商锁定**：构件为封闭二进制，版本节奏、缺陷修复、路线规划完全由集成商 A 决定，管理局丧失架构主导权，后续需求变更成本不可控。
2. **整体切换的爆炸半径过大**：一次性切换无法做增量验证与灰度，故障时回滚成本高、回滚窗口长，与"不停机分批迁移"要求直接冲突。
3. **复用边界与质量不可控**：整体接管意味着把原系统的历史耦合、封闭实现一并继承，重复实现问题并未解决，且缺少构件级质量门禁与契约测试，后续演进仍依赖原厂。

**问题 2（8 分）**

目标集成架构设计：

- **接入层次选择**：以 **API 级集成为主干**（同步查询与写操作）、**消息级集成为解耦通道**（跨部门协同、事件广播）、**数据级集成仅用于分析类场景**（只读视图 / 湖仓同步），**明确禁止新系统直连老库表**；对确需读取历史数据的场景，通过**数据服务 / 只读视图 + CDC 同步**提供数据出口。
- **遗留系统接入策略**：
  - 对单体中的工作流、表单等能力：抽取为构件 + 建**防腐层**，由防腐层负责老模型到新模型的翻译与协议适配（防腐层是隔离旧模型扩散的关键）；
  - 对尚未迁移的存量业务功能：采用**门面 / 适配器 + 绞杀者模式**，按业务域逐个"绞杀"（新功能在老系统外建，逐步接管，老功能关闭后老库字段再下线）；
  - 迁移过渡期历史数据与办件状态：用 **CDC + 对账补偿**保证双写一致，最终以**单向切换 + 存量对账校验**收敛。
- **契约保障机制**：
  - 统一契约规范（OpenAPI / Protobuf + 语义化版本 + 错误码字典 + 统一数据字典），禁止返回 200 携带业务错误码；
  - **消费者驱动契约测试**：提供方发布契约 → 契约测试在 CI 阶段阻断不兼容变更 → 契约仓库版本化留存；
  - **架构守护测试**：以自动化规则禁止跨服务直连数据库、禁止绕过防腐层、禁止跨限界上下文共享表。
- **灰度与回滚方案**：
  - **流量染色**标识用户 / 办件批次，保证同一请求全链路版本一致；
  - **影子流量**：真实流量镜像到新链路（丢弃响应），用于性能回归与数据比对；
  - **金丝雀**：按 1% → 5% → 20% → 50% → 100% 逐级放量，每级设置观察窗与成功率 / 延迟 / 业务一致性闸门；
  - **蓝绿双栈 + 秒级回切**：老系统保持可承接流量，回滚以路由切回为主，不做数据回滚（数据迁移走"只向前兼容 + 补偿"策略）；
  - 数据库变更遵循**扩展—收缩（Expand-Contract）**：先加新字段兼容读，再双写校验，最后下线旧字段，保证任意时刻向前回滚可用。

**问题 3（10 分）**

根因分析与治理措施：

**（1）可靠投递**
- 根因：消息可靠性只做到"发送即忘"，生产端到 Broker、Broker 落盘、消费确认三段任一失败即丢消息；Broker 单副本故障造成消息不可用。
- 措施：
  - **三段确认链**：生产端同步 ACK（失败落本地消息表 / 重试）+ Broker 同步刷盘或副本确认 + 消费端手动 ACK；
  - **事务消息 / 本地消息表**保证"本地事务与发消息"原子性，避免事务已提交但消息未发；
  - **Broker 多副本 + 多可用区部署**，消费端在分区重新分配（Rebalance）时正确处理位点，避免漏消费；
  - 消费端失败按"**有限重试 + 死信队列**"处理，超限入 DLQ 并告警，不做无限重试。

**（2）幂等消费**
- 根因：至少一次投递语义导致重复消息；消费端未做业务幂等，"办件被重复办结"即由此产生。
- 措施：
  - 消费端按**业务唯一键**（办件流水号 + 环节码）建**唯一索引 / 去重表**，重复消息直接返回成功不重复推进状态；
  - 状态机式推进：只允许"待办 → 在办 → 办结"单向跃迁，重复到达时依据当前状态判定为**幂等空操作**；
  - 用**全局唯一业务单号 + 数据库唯一约束**兜底，而非依赖应用层先查后写（存在并发窗口）；
  - 消息体携带**事件 ID 与版本号**，消费端按版本号做顺序与去重校验。

**（3）顺序性**
- 根因：多分区多消费者并行消费，跨分区无序；重试消息重投导致"旧消息后到"倒序。
- 措施：
  - 以**业务键分区**（同一办件 / 同一申请单固定分区），实现**局部有序**，放弃代价极高的全局有序；
  - 消费端引入**版本号 / 状态前置校验**，对"状态已推进但事件版本落后"的消息直接丢弃或补偿；
  - 重试消息不跨分区乱序回灌，或采用延迟队列按原序重放。

**（4）积压治理**
- 根因：峰值生产速率远超消费能力（消费组并发不足 / 单条处理耗时长 / 下游数据库成为瓶颈 / 分区数不足导致消费并发受限），且缺少背压与限流，积压持续放大。
- 措施：
  - **水平扩容消费者**并同步扩容分区数（分区数是消费并发上限，扩消费者不扩分区无效）；
  - **识别瓶颈**：下游数据库慢查询、连接池耗尽、外部接口 RT 过长，采用**批量写、批量读、连接池调优、慢 SQL 治理**；
  - **生产端限流与背压**：生产者侧令牌桶限流，超阈值落本地暂存或降级，防止继续压垮链路；
  - **积压水位告警 + 自动扩容预案**，并对关键消息启用**优先级队列**（审批类优先于通知类）；
  - 应急可**转储大促型旁路**（先落文件 / 库表再回灌）保核心链路，事后批量回放；
  - 治理效果以**消费滞后（Lag）曲线**、**端到端延迟 P99**、**积压恢复时长**持续监控，并纳入 SLO。

**问题 4（8 分）**

构件库治理制度要点：

- **入库准出清单**：源代码与构建可复现（同一源码产出同一制品）、**许可证与知识产权清晰**（开源许可类型登记，是否允许商用 / 闭源 / 修改分发）、接口契约完备并通过契约测试、单元与集成测试覆盖达标、静态代码扫描与**依赖漏洞扫描**无高危、**SBOM 自动生成**、构件**签名与来源可验证**、文档与运维手册齐备、性能与容量基线数据齐备。
- **版本与兼容性策略**：统一**语义化版本**规范；**破坏性变更必须提升主版本**并走"并行期 + 双写双读 + 灰度切流 + 弃用公告"流程；维护**上下游兼容性矩阵**；构件库中同一构件**只保留一个当前生产主版本**，禁止多版本长期并存（版本分叉数纳入考核）；禁止自动静默升级，升级须经依赖影响分析。
- **供应链与许可证合规**：建立**可信构件源白名单**与私有制品库；制品**不可变**、按摘要寻址并留存全量审计日志；对高危构件定期复扫并执行**应急替换 / 降级下线流程**；对外交付前完成开源组件**许可证义务核对**（是否要求声明、是否要求开源、是否存在传染性条款）。
- **权限与责任**：设立**架构委员会 / 构件治理组**，明确构件 Owner（业务归口）与 Maintainer（技术归口），构件升级、废弃、替换须 Owner 与架构委员会双签。
- **持续运营**：构件版本、依赖关系、SBOM 全量可追溯；定期清理无引用构件与僵尸依赖，防止"构件坟场"。

度量指标（至少 4 项）：

1. **构件复用率** = 被两个及以上系统引用的构件数 / 构件总数（衡量广度）；
2. **构件平均被引用数（复用扇出度）** = 构件被引用次数总和 / 构件数（衡量深度，识别核心资产）；
3. **平均交付周期缩减率** = 采用构件前后的需求交付周期对比（衡量业务收益）；
4. **缺陷密度对比** = 复用构件内部缺陷密度 vs 新开发模块缺陷密度（衡量质量收益）；
5. **构件版本分叉数**（同一能力存在多个在用版本数，越低越好，衡量治理有效性）；
6. **重复实现下线率**（原 60% 重复代码的实际收敛比例）；
7. **依赖漏洞平均修复时长（MTTR）** 与高危漏洞存量；
8. **构件导致的线上故障占比**（按故障根因归集到构件的比例）。

**问题 5（6 分）**

- **复用层次**：采用**灰盒复用（设计级复用）**。原因：适配国产数据库与国产芯片平台时，厂商提供的中间件、驱动、运行时与原厂 API 不兼容，无法直接复用二进制（黑盒复用不成立）；若走白盒源码级改造则会造成大规模分叉与后续升级困难。正确做法是**按原设计契约重新实现**：保持对外接口契约（OpenAPI / Protobuf）与业务语义不变，内部实现替换为国产技术栈。属于**叠加组装**范畴——通过定义清晰的**抽象层 / 适配点（适配器 + 防腐层）**，在不改业务构件契约的前提下替换底层运行时、数据库驱动、消息实现。
- **双轨运行**：
  - 新旧栈**并行承载流量**，按流量比例（1% → 10% → 50% → 100%）逐步切换；
  - 数据层采用**双写 / CDC 同步 + 双向对账**，设定对账周期与差异容忍阈值，差异自动补偿（以新栈为准做幂等重放，保留全量对账流水）；
  - 消息通道**双写双订阅**，新旧消费端按同一业务唯一键做幂等去重，保证结果一致；
  - 切换期间保留**统一抽象层的双实现**，通过配置或服务发现完成流量切换，**不修改上层业务构件**，回滚即切回旧实现。
- **一致性校验**：
  - **影子流量比对**：真实请求同时打到新旧链路（丢弃新链路响应），逐笔比对业务结果与关键字段；
  - **数据对账**：行数比对、主键集合比对、关键指标（金额 / 状态 / 计数）汇总比对；
  - **性能与容量校验**：同等流量下的 RT、吞吐、资源占用对比，达成等价或更优才允许放量；
  - **一致性标准**：对账差异率低于设定阈值且连续 N 个周期稳定，方可进入下一放量阶段；
  - 全过程留痕，形成**迁移一致性审计报告**作为验收依据。

- 版本与兼容（2 分）：语义化版本 + **破坏性变更提主版本 + 并行双写灰度流程** + 兼容性矩阵 + 禁止静默升级 + 版本分叉治理。
- 供应链与责任（1 分）：私有制品库 / 白名单源 / 不可变制品 / 审计日志 + 架构委员会与 Owner 双签。
- 度量指标（2 分）：**至少 4 项**，每项写清计算口径。答"提升复用率"不给口径只给 0.5 分；只写"复用率、覆盖率"两项不得满分。

**问题 5（6 分）**
- 复用层次（2 分）：**必须答"灰盒 / 设计级复用"**，并说明"黑盒不成立（API 与运行时不兼容）"与"白盒不可取（造成分叉与升级困难）"。答"黑盒"或"白盒"直接扣 1—2 分。
- 组装方式（1 分）：**叠加组装 / 抽象层与适配点**，并强调"不改上层业务构件契约"。
- 双轨运行（2 分）：双写 / CDC + 对账 + 双写双订阅 + 幂等去重 + 配置切流可秒回滚。
- 一致性校验（1 分）：影子流量比对 + 数据行数与关键指标对账 + **差异率阈值与连续 N 周期稳定**的放量门槛 + 审计报告。答"人工抽查"不得分。

**全卷通用踩分提示**

1. **先答"为什么"再答"怎么做"**：每个措施后面补一句它解决的具体风险，阅卷老师按踩分点给分，没有因果链的措施容易被判为"堆砌术语"。
2. **区分"架构手段"与"技术产品"**：答"用 Kafka""用 Redis"只能得极少分，必须写成"通过**消息中间件的持久化 + 手动 ACK + 死信队列**保证至少一次投递并配合**消费端幂等**实现业务恰好一次"。
3. **强调取舍**：每一问都补一句权衡（如"放弃全局有序换取吞吐，以分区有序满足业务要求"），这是架构师与实施者的区分点。
4. **数据迁移必答向前兼容**：回滚方案只写"切回旧版本"而没交代库表结构变更的，不得满分。
5. **术语务必用准**：CBSE 三要素、复用三层次、组装三方式、契约测试、灰度四类、语义化版本、SBOM、SLI/SLO —— 名称写错按未答处理。

## 记忆口诀

**构件三特征口诀**
接口明确可部署，封装内部不外泄；构件独立于类，跨语言跨进程。

**构件模型五大类口诀**
COM 管进程内，EJB 有容器，.NET 靠程序集，CORBA 走 ORB，构件模型定契约。

**CBSE 三要素口诀**
有库才能选，有件才能用，组装才是核；构件开发要为复用而设计。

**复用三层次口诀**
黑盒拿二进制，白盒改源码，灰盒留契约换实现；国产化适配用灰盒。

**组装三方式口诀**
顺序用连接件，层次成调用树，叠加做替换；可插拔靠叠加。

**特征建模口诀**
特征树四型记：必选可选与或组，多选一起成组用；变体点三实现：绑定派生加组合。

**构件库检索评价口诀**
刻面多维最好用，功能非功兼容度；许可活跃度漏洞数；版本 SemVer 分主次。

**兼容性口诀**
主版本破契约，次版本加功能，修订号改缺陷；破坏变更先并行，双写灰度再切换。

**中间件五类口诀**
数据库管连接，RPC 管同步，MOM 管异步，事务管一致，网格管流量。

**同步异步选型口诀**
查要即时用同步，写要解耦用消息；峰值不均需削峰用消息，需广播重放也用消息。

**消息可靠五要素口诀**
持久多副不丢，ACK 确认不漏，有限重试死信兜，幂等去重不重办，分区有序不乱序。

**消息四大经典问题口诀**
丢：三段确认加事务；重：唯一键加状态机；乱：分区有序加版本；积：扩分区扩消费者加限流。

**集成五层次口诀**
文件库表 API 消息，分析数据最末端；共享数据库是反模式，新系统禁直连老库。

**遗留接入五策略口诀**
绞杀者外建新，防腐层隔污染，门面适配最轻量，双写对账保过渡，直接改造风险高。

**契约与灰度口诀**
契约测试卡 CI，守护测试禁越层；染色同链路一致，影子比对新旧，金丝雀逐级放量，蓝绿秒级回切。

**治理度量口诀**
复用率看广度，扇出度看深度，分叉数看治理，MTTR 看修复，重复下线看收益。

**灰度回滚口诀**
先加后减双写期，只向前兼容不回滚数据；路由切回就是回滚。

**一句话总纲**
构件化落地三件事：**边界要清晰（一个构件一件事）、契约要可测（不兼容变更进不了主干）、演进要受控（版本不静默升级、废弃有窗口）**；集成中间件落地三件事：**语义要对齐（契约 + 字典）、交付要可靠（确认 + 幂等 + 死信）、变更要可退（染色 + 影子 + 金丝雀 + 蓝绿）**。
