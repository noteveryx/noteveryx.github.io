**主题**：AI 大模型应用架构 —— RAG 增强生成、Agent 编排、推理优化与成本治理

---

## 今日核心概念

### 1. 大模型应用架构的四层全景

```
┌─────────────────────────────────────────────┐
│  L4 应用层：对话助手 / 数字人 / 智能客服      │  ← 业务价值与体验
├─────────────────────────────────────────────┤
│  L3 编排层：Agent 循环 / 工作流 / 多轮记忆     │  ← 智能性的来源
├─────────────────────────────────────────────┤
│  L2 能力层：RAG 检索 / 工具调用 / 微调 / 提示   │  ← 准确性的来源
├─────────────────────────────────────────────┤
│  L1 推理层：公有云 API / 私有化部署 / 推理引擎   │  ← 性能与成本
└─────────────────────────────────────────────┘
```

**架构设计的核心判断**：**大模型应用 90% 的工程问题不在模型层，而在 L2 和 L3。** 模型能力是给定的，工程价值在于"如何把一个概率性的、不可控的组件，包成一个可控的、可交付的系统"。

### 2. RAG（检索增强生成）架构深度

#### 2.1 RAG 的本质

**RAG = 用检索替代记忆**。它解决的是大模型三大固有缺陷之一：**知识时效性与知识幻觉**。

- 大模型的参数里存储了训练截止时的知识，且无法保证准确（幻觉）
- RAG 在生成前先检索相关文档片段，把它们作为上下文塞进提示词，让模型"开卷考试"

#### 2.2 文档处理流水线

```
原始文档 → 解析(Parse) → 切分(Chunk) → 嵌入(Embed) → 索引(Index)
                                                              ↓
用户提问 → 查询改写 → 向量检索 + 关键词检索 → 重排序(Rerank) → 组装上下文 → LLM 生成 → 引用溯源
```

#### 2.3 切分策略（Chunking）——最影响效果但最少被重视的环节

| 策略 | 做法 | 适用 | 问题 |
|---|---|---|---|
| **固定长度切分** | 按字符/token 数硬切 | 通用基线 | **切断语义**，一句话被腰斩 |
| **递归字符切分** | 按分隔符优先级递归切（段落→句子→字符） | 通用，改动最小 | 仍可能切断表格与列表 |
| **按结构切分** | 按 Markdown 标题层级 / HTML 章节 | 文档结构清晰 | 结构混乱的文档失效 |
| **语义切分** | 按相邻句向量相似度找"语义断点" | 语义连贯性要求高 | 计算成本高，阈值难调 |
| **父子块索引** | 小块用于检索，大块用于喂给 LLM | **长文档问答最佳实践** | 需维护块父子关系 |

**关键原则**：
1. **块大小与召回的权衡**：块越小，召回越精确但上下文越碎（信息不足）；块越大，信息越全但噪声越多。**经验值：中文 300-500 字，英文 200-300 词，并保留 10-15% 重叠**
2. **重叠（Overlap）不可省**：没有重叠，任何落在切分点上的问题都会丢失
3. **表格是最大陷阱**：合并单元格表格按字符切分会彻底碎片化。**正确做法是把表格转成"一记录一段落"的 Markdown**——这一条在政务知识库实践中已被反复验证
4. **分隔符设计**：中文文本优先用 `\n`（段落级）作为一级分隔符，避免用标点作为主分隔符导致句子过碎

#### 2.4 检索增强的四个关键决策

**① 检索模式选择**

| 模式 | 机制 | 适用 | 延迟 |
|---|---|---|---|
| **朴素 RAG** | 向量检索 Top-K → 塞进提示 | 单文档问答，语料小 | 最低 |
| **HyDE** | 先让 LLM 生成"假想答案"，用假想答案去检索 | 用户提问模糊时召回率高 | 中（多一次 LLM） |
| **混合检索** | 向量 + BM25 关键词，RRF 融合 | **生产默认选择** | 低 |
| **多路召回 + Rerank** | 多路召回 Top-50 → Cross-Encoder 重排 → Top-5 | 语料大、精度要求高 | 中高 |
| **GraphRAG** | 构建实体关系图谱后做图遍历 | 跨文档关联推理（如"A 项目的预算受 B 政策影响"） | **高** |

**为什么混合检索是默认**：向量检索擅长语义相似，但对**专有名词、编号、日期、人名**这类"精确匹配"反而不可靠。BM25 恰好相反。政务场景里"112 号文件""京政办发〔2024〕15 号"这类查询，向量检索几乎必然失败。

**② Rerank 的不可替代性**

- **向量检索（双塔/Bi-Encoder）**：query 和 document **分别**编码，预先算好所有文档向量，检索时只算 query 向量 → 快，但 query 与 doc 之间**没有交互**
- **Rerank（Cross-Encoder）**：query 与 document **拼在一起**送入模型做交互式评分 → 准，但必须对每个候选逐一计算 → 慢

**标准做法**：双塔粗召回 Top-50 → Cross-Encoder 精排 Top-5。**这一层通常能带来 10-20 个百分点的准确率提升，成本却只增加几百毫秒。**

**③ 上下文组装的三条铁律**

1. **上下文中必须包含"不要什么"**：明确告诉模型"以下资料与问题无关时，请回答资料中未提及"
2. **编号 + 引用**：每个片段编号，要求模型在答案中标注引用编号，便于溯源与幻觉检测
3. **顺序敏感**：**"丢失在中间"（Lost in the Middle）是 LLM 的已知缺陷**——长上下文中，位于中间部分的信息被引用的概率显著低于开头和结尾。**因此最重要的片段要放在开头和结尾**

**④ 幻觉检测与兜底**

- **引用验证**：答案中的每个引用编号必须能在检索结果中找到对应片段，否则视为幻觉
- **置信度阈值**：Rerank 分数低于阈值时，返回"未找到相关资料"而非强行生成
- **拒答机制**：这是 RAG 系统**最容易被忽略但最影响可信度**的设计

### 3. Agent 架构与工具调用

#### 3.1 Agent 的本质

**Agent = LLM + 工具 + 循环 + 记忆**。核心机制是 **ReAct（Reasoning + Acting）**循环：

```
用户问题 → LLM 思考(Thought) → 决定调用工具(Action) → 工具返回结果(Observation)
                                              ↑                    ↓
                                              └──── 继续思考 ───────┘
                                                    （直到得出答案）
```

#### 3.2 Function Calling 的工程要点

```json
{
  "name": "query_tender_info",
  "description": "根据招标编号查询招标公告详情",
  "parameters": {
    "type": "object",
    "properties": {
      "tender_id": {"type": "string", "description": "招标编号，如 11000023210200012345"}
    },
    "required": ["tender_id"]
  }
}
```

**五条工程要点**：
1. **description 是给模型看的，不是给人看的**——必须写清"什么时候该用、什么时候不该用、边界在哪"，模型完全依赖它做工具选择
2. **参数必须有描述与示例**——尤其是枚举值与格式要求
3. **工具数量控制在 20 个以内**——超过后模型选择准确率断崖式下降
4. **工具返回值要精简**——大段原始数据会挤占上下文，应该返回结构化摘要 + 可选详情 ID
5. **错误信息要可读可自愈**——返回 `"错误：日期格式应为 YYYY-MM-DD"` 而非 `"400 Bad Request"`，模型才能自我修正

#### 3.3 Agent 的四种模式与适用

| 模式 | 结构 | 适用 | 风险 |
|---|---|---|---|
| **单次调用** | 一次 prompt 一次生成 | 分类、摘要、改写 | 低 |
| **链式（Chain）** | 固定顺序多步 | 数据处理流水线 | 低，可预测 |
| **路由（Router）** | 分类器分发到不同专家 | 多领域客服 | 低 |
| **ReAct Agent** | 自主循环决策 | 复杂查询、多工具协作 | **高（可能死循环）** |

**ReAct Agent 必须有的三个防护**：
- **最大步数上限**（如 10 步）
- **工具白名单**（禁止调用危险工具）
- **成本预算**（累计 token 上限 + 累计费用上限）

#### 3.4 多 Agent 协作模式

- **Supervisor（主管型）**：一个主 Agent 分派任务给多个子 Agent 并汇总（最常用、最可控）
- **Sequential（顺序型）**：固定顺序依次传递
- **Parallel（并行型）**：多个 Agent 并行处理不同方面，最后聚合（如分别查政策、查流程、查案例）

**不要一开始就上多 Agent。** 单 Agent + 好工具 + 好提示词能解决 80% 的问题，**多 Agent 会带来 3 倍成本、5 倍调试难度，只换来最后 20% 的效果**。

### 4. 推理层优化与成本治理

#### 4.1 影响成本与延迟的四个旋钮

| 旋钮 | 降低成本 | 代价 |
|---|---|---|
| **模型选择** | 小模型/蒸馏模型处理简单任务 | 复杂任务质量下降 |
| **提示词长度** | 精简上下文、去冗余示例 | 可能损失关键信息 |
| **RAG 召回数** | Top-5 而非 Top-20 | 召回率下降 |
| **输出长度** | 限制 max_tokens、用简洁指令 | 内容可能不完整 |

#### 4.2 模型路由（Model Routing）

**核心思路：不是所有请求都需要最强模型。**

```
用户请求 → 意图分类/难度评估
  ├── 简单（分类、翻译、短摘要）→ 小模型（如 7B 级）
  ├── 中等（常规问答、代码补全）→ 中等模型
  └── 复杂（多步推理、长文分析）→ 大模型
```

**实践数据**：合理路由可使综合成本降低 50-70%，而对用户可感知的质量下降很小。这是**投产前必须做的第一项优化**。

#### 4.3 缓存策略（三层）

1. **语义缓存（Semantic Cache）**：对用户问题做向量检索，命中相似问题（相似度 > 阈值）直接返回历史答案。**注意：涉及实时数据、个性化内容时禁用**
2. **前缀缓存（Prefix/Prompt Cache）**：把不变的提示词前缀（如系统提示 + 固定文档）缓存 KV，只重算变化部分。**Anthropic/OpenAI 均已支持自动前缀缓存**
3. **结果缓存**：对确定性查询（如静态知识）缓存最终结果，设置合理 TTL

### 5. 评估体系（Evals）——大模型应用成熟的标志

**大模型应用最难的不是做出来，是证明它好。**

#### 5.1 三层评估

| 层次 | 评估对象 | 方法 | 频率 |
|---|---|---|---|
| **单元级** | 单次调用/RAG 检索 | 标注集 + 精确率/召回率 | 每次提交 |
| **端到端** | 完整回答 | LLM-as-a-Judge + 人工抽检 | 每日/每周 |
| **线上** | 真实用户反馈 | 点赞率、追问率、复制率、放弃率 | 持续 |

#### 5.2 LLM-as-a-Judge 的实施要点

- **必须先与人工标注对齐**：先用 100-200 条人工标注数据校准 Judge，验证 Judge 与人工的一致性（Cohen's Kappa > 0.7 才可用）
- **成对比较优于绝对打分**：让模型判断"A 比 B 好"比让它打 1-10 分稳定得多
- **评估维度分离**：准确性、完整性、相关性、简洁性、安全性分别评，不要合成一个总分

#### 5.3 线上四大指标（最能反映真实体验）

- **点赞/点踩率**
- **追问率**（用户追问说明首答不完整——**最被低估的指标**）
- **复制率 / 引用率**（说明答案可用）
- **放弃率**（用户看完就走了——说明答案无用）

## 三个常考陷阱

### 陷阱一：以为"换个更大的模型"能解决 RAG 效果问题

**错，而且是最贵的错。** 检索不准时换大模型，只会得到"**基于错误资料的、更流畅的错误答案**"，且幻觉更难被发现。

**排查顺序永远是**：先看检索结果对不对 → 再看切分是否合理 → 再看重排是否生效 → 最后才考虑换模型。

### 陷阱二：忽略"丢失在中间"现象

**长上下文中，位于中间部分的信息被模型引用的概率显著低于开头和结尾。** 这个现象在 2023 年由 Liu 等人在 Stanford 的 *"Lost in the Middle: How Language Models Use Long Contexts"* 中系统验证。

**实践对策**：
- 最重要的片段放**最前面**（先给结论，再给依据）
- 关键约束放**最后面**（如"仅依据以下资料回答"）
- 超过 20 个片段时，考虑做**递归摘要**而非简单堆叠

### 陷阱三：把 Agent 的"自主性"当成优点

**自主性越高，系统越不可预测。** 生产环境必须把 Agent 当作一个**不可信的、可能犯错的下属**来设计：每一步都要校验、每一步都要有兜底、每一步的花费都要设上限。

**永远不要让 Agent 自主执行不可逆操作**（删除数据、转账、发外部通知），这类操作必须有人类确认环节（Human-in-the-Loop）。

## 案例分析题

### 案例 1 — 政务知识库智能体的准确率困境

**题干**：某市政务服务局建设"政策问答数字人"，接入 RAGFlow 平台，用 Redis + Milvus 作为向量存储，LLM 使用某国产大模型。上线后业务部门反馈：

- 简单的政策条文问得准（"办理时限是几天"答得对）
- **涉及多部门协同的问题经常答错或答不全**（如"异地就医报销需要哪几个部门审批"）
- **涉及数字的问题容易出错**（如"2025 年起门诊报销比例调整为多少"，模型答了一个 2023 年的数字）
- 用户追问率高，业务部门认为是模型不够智能

技术团队排查后给出了三个判断：
1. "chunk_size 设为 512 token，delimiter 是 `。`，效果一般，建议改成 1024"
2. "向量检索 Top-5，考虑加 rerank"
3. "建议换一个参数量更大的模型"

**问题**：
1. 针对三类问题，分别指出最可能的根因。
2. 技术团队的三个建议中，哪些有效、哪些无效、哪些有害？请逐一评判。
3. 请给出一个改进方案（分检索层、生成层、评估层三部分）。

**参考答案**：

**问题 1 — 三类问题的根因**：

**第一类：多部门协同问题答错/答不全 —— 根因是"单文档检索的局限"**
- 多部门协同问题的答案天然**分散在多份文件中**（医保文件说报销流程、卫健文件说转诊政策、医保局文件说异地备案）
- 朴素 RAG 只做单次向量检索，**Top-5 往往全部来自同一份文件**，另一份关键文件根本没被召回
- 加上 chunk 按 `。` 切分后单块很短，语义被切碎，检索精度进一步下降
- **本质问题：缺失回答需要多跳推理与跨文档聚合的能力，单次 RAG 结构上做不到**

**第二类：数字类问题出错 —— 根因是"时效性与幻觉"**
- 政策数字随时间变化，模型参数里的知识停留在训练截止时
- RAG 检索到了旧版本文件（比如 2023 年的文件排在 2025 年文件之前，或向量检索没有"时间"维度）
- **更隐蔽的问题：模型在检索结果之外，用参数里的旧知识"补"了一个看起来合理的数字**
- 这不是"模型不够智能"，而是"**检索没有按时间过滤 + 没有强制引用约束**"

**第三类：追问率高 —— 这是症状不是病因**
- 追问率高说明首答不完整或不确定，根源在前两类问题。**不要把"追问率高"当成独立问题去优化交互**

**问题 2 — 三个建议的评判**：

| 建议 | 评判 | 理由 |
|---|---|---|
| **chunk 512→1024，delimiter `。`** | **部分无效，有害** | 块变大确实能保留更多上下文，但**用 `。` 作为主分隔符本身是错的**——中文句子被切得过碎，语义单元被打散。正确做法是：块大小可提到 600-800，**但主分隔符应改为 `\n`（段落级），句号只作为次级分隔符**。这个建议"改了症状没改病因"，且改的方向部分有害 |
| **向量检索 Top-5 加 rerank** | **有效，且是最高性价比的改进** | Rerank（Cross-Encoder）能显著提升"候选片段排序"的准确性，且成本低。但**必须强调：先要确保 Top-K 召回的候选里确实包含正确文档**。若正确文档在 Top-20 之外，rerank 也救不回来。建议**召回 Top-20-30 → rerank → 取 Top-5**，而不是只用 Top-5 |
| **换更大参数量模型** | **无效（针对上述问题）且成本最高** | 三个问题**没有一个是模型能力不足导致的**：①②是检索层问题，③是结果问题。**换大模型只会让错误答案更流畅、更有说服力，幻觉更难被发现**，同时成本翻倍、响应变慢。**这是最需要驳回的方案** |

**问题 3 — 改进方案（三层）**：

#### 检索层改进

1. **重新设计切分策略**
   - 主分隔符改为 `\n`（段落级），次级为 `。`；块大小 600-800，overlap 15%
   - **对表格类文件单独处理**：转为"一记录一段落"的 Markdown 格式，不与其他内容混切
   - **采用父子块索引**：小块（200 字）用于召回，大块（完整章节）用于喂给 LLM，兼顾精度与完整性

2. **混合检索 + 重排**
   - 向量检索 Top-30（语义）+ BM25 Top-30（关键词，用于"112 号文件""京政办发〔2024〕15 号"这类精确匹配）
   - RRF（Reciprocal Rank Fusion）融合两路结果 → Cross-Encoder Rerank → 取 Top-5-8

3. **增加时间维度过滤**
   - 文档元数据中增加 `effective_date`（生效日期）与 `status`（现行/已废止）
   - 检索时**硬过滤**：优先返回 `status=现行` 且 `effective_date ≤ 当前日期` 的文件
   - 若同一政策有多版本，**只召回现行版本**，废止版本仅用于对比说明

4. **处理多跳问题——元问题路由**
   - 建立"问题类型识别"前置环节：判断问题是否需要跨文档聚合
   - **简单问题**（单文件可答）→ 走标准 RAG
   - **复杂问题**（需多部门/多文件聚合）→ 走**两阶段检索**：先做子问题拆解（最多 3 个子问题），每个子问题独立检索，最后聚合
   - 投入产出比最高的折中方案，成本远低于全量 GraphRAG

#### 生成层改进

1. **强制引用约束**
   - 上下文中每个片段编号，提示词明确要求"回答中必须标注引用编号"
   - 后处理校验：答案中的编号若不在检索结果中 → 判为幻觉，触发重试或降级

2. **检索置信度阈值与拒答**
   - Rerank 分数低于阈值（如最高分 < 0.35）→ 直接返回"未检索到相关政策，请咨询 XX 部门"，**不强行生成**
   - 这一条对政务场景是**刚性的**——宁可说不知道，不能编政策

3. **数字类问题的专项约束**
   - 提示词中明确："**涉及数字、比例、时限、金额时，必须逐字引用原文，不得推算或估算**"
   - 结构化输出：把从原文抽取的条款（文件号 + 条款号 + 原文 + 生效日期）作为独立字段返回，前端单独展示

4. **模型路由与上下文优化**
   - 简单问答（占 70%）用小模型，复杂多跳（占 30%）用大模型
   - 开启前缀缓存，系统提示与固定政策背景文档部分不重复计费
   - 关键片段置首置尾，规避"丢失在中间"

#### 评估层改进

1. **建立分层标注集（最优先、成本最低、见效最快）**
   - 从业务咨询记录中抽取 300 条真实问题（覆盖简单/复杂/数字/政策已废止四类）
   - 由业务部门人工标注标准答案与引用来源
   - **这套标注集是后续所有优化的裁判标准**，没有它，任何"调 chunk_size""换模型"的改动都无法判断是好是坏

2. **指标体系（四类分别度量，不要合并）**
   - 检索层：**Recall@5**（正确片段是否被召回）、MRR
   - 生成层：**答案正确率**、**引用准确率**（标注的引用是否真的支持答案）、**幻觉率**
   - 端到端：**一次解决率**（= 1 − 追问率）
   - 分问题类型统计，**重点监控复杂问题与数字问题两类**

3. **LLM-as-a-Judge 先校准后使用**
   - 先用 100 条人工标注与 Judge 结果对比，Cohen's Kappa ≥ 0.7 才允许自动评估
   - 用成对比较而非绝对打分

4. **上线后持续监控**
   - 线上指标：点踩率、追问率、引用点击率、无答案率
   - **建立"低分样本回流"机制**：用户点踩与人工纠错的问题自动进入标注集，形成迭代闭环

## 记忆口诀

- 口诀 1：**四层架构**——应用、编排、能力（准确）、推理（成本）。工程价值在 L2/L3。
- 口诀 2：**检索先于生成**——排查问题先看召回对不对，最后才换模型。
- 口诀 3：**切分四要点**——块 600-800、重叠 15%、主分隔 `\n`、表格转段落。
- 口诀 4：**混合检索打底**——向量抓语义、BM25 抓编号；政策类提问数字与文号靠 BM25。
- 口诀 5：**召回 30 精排 5**——rerank 前必须给足候选，否则救不回来。
- 口诀 6：**中间会丢**——重要片段置首置尾，超 20 块做递归摘要。
- 口诀 7：**拒答要敢用**——分数不够就说没有，政务场景绝不允许编政策。
- 口诀 8：**工具二十上限**——description 写给模型看，错误信息要可自愈。
- 口诀 9：**Agent 三防护**——步数上限、工具白名单、费用预算；不可逆操作必须人工确认。
- 口诀 10：**先建标注集**——没有裁判标准，所有优化都是盲改。
- 口诀 11：**模型路由省半**——简单问题走小模型，综合成本可降 50-70%。
- 口诀 12：**追问率最诚实**——它直接等于 1 − 一次解决率，比满意度更真实。
