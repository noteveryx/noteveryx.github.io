# （高级）系统分析师 · 第56次学习（2026-10-27）

**主题**：系统可观测性与可维护性工程 —— SLI/SLO/错误预算、分布式追踪、故障模式分析（FMEA）与可靠性设计

---

## 今日核心概念

### 1. 可观测性的三支柱与"可观测 ≠ 可监控"

**这是现代系统架构中最重要的认知升级。**

| 支柱 | 回答的问题 | 典型技术 |
|---|---|---|
| **Metrics（指标）** | 有多少、趋势如何 | Prometheus、VictoriaMetrics、OpenTelemetry Metrics |
| **Logs（日志）** | 具体发生了什么 | ELK、Loki、OpenTelemetry Logs |
| **Traces（链路追踪）** | 这一条请求经历了什么 | OpenTelemetry、Jaeger、Zipkin |

**可监控（Monitoring）**：**预先知道要监控什么**，针对已知故障模式设置告警。典型：CPU 超 80% 报警。

**可观测性（Observability）**：**不预设假设，仅通过系统输出的信号推断系统内部状态**。这是控制论里 observability 概念的直接移植——**你不需要知道系统内部有多少个状态变量，只要能观测输出，就能判断内部状态。**

**关键区别（高频考点）**：

| | 监控 | 可观测性 |
|---|---|---|
| 前提 | **已知**故障模式 | **未知**故障模式 |
| 回答 | "有没有出问题" | "**为什么会出问题**" |
| 手段 | 预设规则与阈值 | 统计推断与关联分析 |
| 适合 | 稳定系统的已知问题 | 复杂/微服务/分布式系统 |

**关键认知**：**传统监控回答"发生了什么"，可观测性回答"为什么会发生"。** 这也是为什么在微服务架构下可观测性成为刚需——**微服务下可能出现的故障组合是指数级的，没法全部预先枚举。**

### 2. SLI / SLO / SLA：三层服务目标体系

**这是 SRE 的核心，也是最容易混淆的考点。**

| 概念 | 全称 | 含义 | 归属 |
|---|---|---|---|
| **SLI** | Service Level Indicator | **服务级别指标**——对服务水平的**度量**，是数字 | 内部技术指标 |
| **SLO** | Service Level Objective | **服务级别目标**——对 SLI 的**目标值** | 对内承诺 |
| **SLA** | Service Level Agreement | **服务级别协议**——**对外的合同承诺**，有法律效力 | 对外合同 |

**关键区分（三句话）**：
1. **SLI 是"现在是多少"，SLO 是"承诺要到多少"**。
2. **SLO 是内部目标，SLA 是对外承诺**。**SLA 的违约要赔钱，SLO 未达成通常不赔。** 通常 **SLA 比 SLO 宽松**（对外承诺要留有余地）。
3. **只有 SLI 可以度量，SLI 不可度量就无从谈 SLO。**

**常见指标选型（政务系统的典型 SLI）**：

| 维度 | SLI 示例 | 说明 |
|---|---|---|
| **可用性** | 成功请求数 / 总请求数 | 最常用，但**必须明确"成功"的定义** |
| **延迟** | P99 响应时间 ≤ 500ms | **要用分位数，不能用平均值** |
| **正确性** | 数据校验通过率、错误率 | 政务系统尤其重要 |
| **吞吐** | TPS、并发连接数 | 容量规划用 |
| **新鲜度** | 数据延迟 ≤ 5 分钟 | 数据类系统必备 |
| **完整性** | 事件丢失数 = 0 | 消息队列/对账场景 |

**关键认知**：**SLO 选指标时，"成功"必须可判定。** "服务正常"这种不可判定的定义会让 SLO 失去约束力。

### 3. 错误预算（Error Budget）与"可靠性工程化"

**错误预算是 SRE 最重要的一招——它把"要不要发布"这个争论变成可以计算的决策。**

**核心公式**：

```
错误预算 = (1 - SLO) × 总请求数
```

**示例**：SLO = 99.9% 可用性，月请求量 1 亿次 → 错误预算 = 0.1% × 1 亿 = **10 万次错误**。

**关键认知（本题核心）**：**错误预算耗尽 = 停止发布新功能，专心修稳定性。** 这条规则的意义在于：

1. **把"稳定性"从"做好事"变成了"可消耗的预算"**。SLO 不是不能碰的天花板，是**允许消耗的资源**。
2. **用预算余额替代争论**。"这个功能能不能上"从"我觉得能上/不能上"变成"**预算还剩 3.2%，上这个功能预估消耗 0.5%，可以上**"。
3. **当预算耗尽**，组织自动进入**"修复模式"**（reliability mode），此时所有资源投向稳定性，不接受新需求。**这条规则之所以有效，是因为它不需要谁来判断"稳定是否重要"——它用数字自动触发了行为改变。**

**预算分配的三种策略**：

| 策略 | 说明 | 适用 |
|---|---|---|
| **全部发布（Release）** | 有预算就发 | 迭代快、风险低 |
| **部分发布（Canary）** | 灰度放量，按比例消耗预算 | **默认推荐** |
| **冻结（Freeze）** | 预算耗尽，冻结发布 | 稳定性优先 |
| **分配（Allocation）** | 预算预先切给各团队 | 多团队自治 |

**陷阱：把错误预算当"可以随便花的额度"**。**错误预算不是许可，是上限。** 真正的用法是：**用预算余额决定"能不能承担这个风险"，而不是"敢不敢冒这个险"。**

### 4. 分布式追踪：Trace / Span / Context 传播

**核心概念**：

| 概念 | 定义 |
|---|---|
| **Trace** | 一次完整的请求链路，**全局唯一 ID（TraceId）** |
| **Span** | 链路中的一个**工作单元**（如一次 RPC、一次数据库查询） |
| **Parent Span / Child Span** | 调用关系构成**树形结构** |
| **Context Propagation** | 跨服务传递 TraceId 的机制 |
| **Baggage** | 随请求传递的**业务上下文键值对** |

**三种跨进程传播方式（高频考点）**：

| 方式 | 做法 | 优缺点 |
|---|---|---|
| **Header 注入（推荐）** | HTTP Header 携带 `traceparent`（W3C Trace Context 标准） | **跨服务、跨语言、跨中间件通用** |
| **RPC 框架拦截器** | 通过 OpenTelemetry SDK 自动注入 | 透明，但**只覆盖支持的框架** |
| **消息队列属性** | 把 TraceId 放入消息属性 | **异步场景必需**，Kafka/RabbitMQ 需显式配置 |

**关键认知**：
1. **异步场景是追踪的最大断点**。消息队列、线程池、批处理中的 Span 关联必须显式处理，**否则链路会断成碎片**。
2. **采样要分级**：通常头部请求（高延迟、报错）100% 采样，正常请求按比例采样。**全量采样成本不可接受。**
3. **TraceId 必须贯穿业务日志**。**追踪与日志不打通，排查时就得在两个系统间来回切换**，这是很多团队"有链路追踪但仍然排查困难"的根本原因。

**性能提示：Span 数量爆炸是常见事故**。每个 Span 都有创建/序列化/网络开销，一个请求产生上千个 Span 会拖垮系统。**必须控制 Span 粒度。**

### 5. 可维护性工程：可观测性的最终目的

**可观测性不是为了监控而监控，它的目的是"缩短故障恢复时间"和"支撑变更"。**

**可维护性的四个核心指标**：

| 指标 | 定义 | 意义 |
|---|---|---|
| **MTTR（平均修复时间）** | 从故障发生到恢复的平均时长 | **衡量可维护性的核心指标** |
| **MTTD（平均检测时间）** | 从故障发生到被发现 | 靠告警与追踪 |
| **MTBF（平均故障间隔）** | 两次故障之间的平均时间 | 靠可靠性设计 |
| **变更失败率** | 导致故障的变更占比 | **衡量变更质量** |
| **部署频率 / 变更前置时间** | 交付速度的两项 | DevOps 四项指标 |

**关键认知：可维护性的三个支柱是"可观测 + 可部署 + 可回滚"。**

**三者缺一不可**：
- 只有可观测没有可回滚 → 知道出问题了，但改不回来
- 只有可回滚没有可观测 → 能改回来，但不知道该改什么
- 都没有 → 只能靠人守

**变更失败率与部署频率的组合判断（DevOps 四项指标的经典用法）**：

| 部署频率 | 变更失败率 | 状态 | 改进方向 |
|---|---|---|---|
| 高 | 低 | ** Elite** | 保持 |
| 高 | 高 | 危险区 | **改测试与回滚** |
| 低 | 低 | 保守区 | **改自动化流水线，提频** |
| 低 | 高 | 危险区 | **改测试质量** |

### 6. 可靠性设计：FMEA 与失效模式分析

**FMEA（Failure Mode and Effects Analysis）是工程上最经典的可靠性分析方法。**

**五个步骤**：
1. **识别功能模块**（自上而下拆解）
2. **识别失效模式**（每个功能可能怎么坏）
3. **分析影响**（对系统/用户的影响程度 S：Severity）
4. **分析原因与现有控制**（为什么会坏 O：Occurrence，是否已被检测 D：Detection）
5. **计算风险优先级数 RPN = S × O × D**，排序并制定改进措施

**RPN 的局限（重要考点）**：**RPN 相乘会把不同维度的重要性混在一起**，例如 S=9/O=1/D=1 的 RPN=9，可能比 S=5/O=9/D=9 的 RPN=405 更危险（后者虽然单项指标低，但发生率与不可探测性都很高）。**现代做法是同时看严重度 S 的独立门槛**——**S=9 或 10 的项无论 RPN 多低都必须处理。**

**FMEA 在软件架构中的变体**：
- **失效模式 = 服务的降级形态**（不响应、返回错误、返回脏数据、超时）
- **软件特有失效**：**级联故障（Cascading Failure）**——一个服务的失败触发下游连锁失败
- **必须设计"降级矩阵"**：每个依赖故障时，上层的行为是什么

## 三个常考陷阱

### 陷阱一：把"可观测性"当成"监控的升级版"

**错，这是概念性误解。**

**监控是"我预设了要监控什么"，可观测性是"我不预设，通过信号反推内部状态"。**

**判断题的标准**：如果你的所有告警规则都是"某指标超过某阈值"，那你有监控，可能没有可观测性。**可观测性的标志是：能回答"这个我没预料到的问题是怎么回事"。**

**常见误解**：以为装了 Prometheus + Grafana + ELK 就是可观测性。**没有关联分析（Metrics ↔ Logs ↔ Traces 打通）、没有分布式追踪、没有能回答"为什么慢"的工具，就不是可观测性。**

### 陷阱二：把 SLO、SLA、SLI 混用，或用平均值代替分位数

**错。**

1. **SLA 是对外合同，SLO 是对内目标，SLI 是度量。** 三者错位会导致"内部天天报警但从未违约"的尴尬，或"对外赔了钱但内部不知道"。

2. **延迟必须用分位数（P95/P99），不能用平均值。** **平均值 200ms 可能是"190 个请求 10ms + 10 个请求 1900ms"的混合**，用户体感极差但平均值看起来很好。**SLO 若基于平均值制定，等于给尾部体验挖坑。** 业界通行做法是 **SLO 用 P99，容忍度基于 P99 计算**。

### 陷阱三：把错误预算当成"可以随便花的性能额度"

**错。**

**错误预算是"可以消耗的"而不是"随便花的"。** 两个关键点：

1. **错误预算是上限，不是目标。** 预算耗尽就冻结发布，不存在"反正还有 5%，多上几个功能"。
2. **"多消耗预算"本身是坏消息**。错误预算消耗速度快，说明**质量问题在恶化**。健康的状态应该是"预算消耗缓慢，因为错误少"。

**最常见的错误用法**：把错误预算当成"发布节奏的调节阀"，错误预算快用完了就赶发功能填坑——**方向完全反了。** 预算快用完的唯一正确反应是**减少发布、加强修复**。

### 陷阱四：认为"链路追踪能替代日志"

**错，两者不可互相替代。**

- **链路追踪回答"请求走了哪些路径、每段花多久"**——宏观结构
- **日志回答"这一段里具体发生了什么"**——微观细节

典型场景：追踪显示"数据库查询耗时 3 秒"，**但为什么慢？** 这要看那条 SQL 的执行日志、参数、慢查询日志、锁等待情况。**没有日志，追踪只能告诉你"哪里慢"，不能告诉你"为什么慢"。**

**正确做法：TraceId 贯穿日志，日志中携带 TraceId，可从追踪跳到日志，再跳回追踪。** 这个"双向跳转"能力才是可观测性的完整形态。

## 案例分析题

### 案例 1 — 某省政务服务平台"半夜告警，人喊上班"

**题干**：某省政务服务网平台采用微服务架构，部署在 8 个节点上，对外提供统一办事入口和统一身份认证。运维团队 6 人，实行 7×24 小时值班。

上线半年后，团队负责人向CIO汇报了三组数据：

1. **告警数量**：日均告警 **847 条**，其中**有效告警仅 12 条**（占 1.4%），其余 835 条为重复、抖动或已知可忽略的告警。值班工程师平均每人每班要处理 141 条告警。
2. **故障统计**：过去 6 个月共发生 **23 次影响可用性的故障**，其中 **19 次**的检测依赖"用户投诉或拨打客服热线"，**仅 4 次**由监控告警提前发现。**MTTD（平均检测时间）中位数为 47 分钟**。
3. **用户体验**：客服工单中 **62%** 反馈"提交后页面卡住"或"转圈很久"，但平台团队从监控看，**服务器 CPU 平均利用率仅 28%，内存 45%，无任何资源瓶颈指标异常**。业务方要求平台方"扩容解决卡顿"。

补充信息：
- 平台团队 3 个月前上线了一套监控平台，采集了 800+ 指标，配置了 180 条告警规则。
- 团队曾尝试用"直接在告警里查日志"的方式排查，但**日志分散在 8 个节点的本地磁盘，且未按请求 ID 串联**。
- 一次故障复盘发现：某次"用户大面积无法登录"，实际原因是**认证服务的数据库连接池配置过小**，在早高峰时耗尽连接。**而当时的监控只有"数据库 CPU 使用率"这一个指标，CPU 使用率始终正常。**
- 运维负责人提出："我们准备上 APM 全链路追踪系统，把 8 个节点都串起来。"

**问题**：
1. 指出该团队在可观测性建设上的五个具体问题，并分析根因。
2. 对于"CPU 正常但用户觉得卡"这一现象，说明可能的技术原因并给出排查思路。
3. 评价"直接上 APM 全链路追踪"这一方案是否充分，若不充分请补全。
4. 为该平台设计一套完整的 SLO 体系与错误预算使用机制。

**参考答案**：

### 问题 1 — 五个问题与根因

| 问题 | 现象 | 根因 |
|---|---|---|
| **1. 告警噪音失控** | 日均 847 条、有效仅 1.4% | **三个叠加根因**：①**告警规则过多且未分级**（180 条规则几乎无优先级区分，缺少"紧急/重要/提示"的告警分层）；②**缺少告警收敛与抑制机制**（无去重、无抖动抑制、无同源告警聚合）；③**缺少"可行动性（Actionability）"标准**——告警规则按"指标越界"而非"是否需要人动手"设计。**告警的检验标准应当是"收到后是否必须立刻有人做点什么"，不是"指标有没有越线"。** |
| **2. 缺乏真正的可观测性，只有监控** | 只能发现已知指标越界 | **本质上是监控而非可观测性**：180 条规则全是"某指标 > 阈值"，**没有任何跨信号的关联分析**，无法回答"这个没预料到的问题是怎么回事"。表现为两次典型失误：①**认证服务连接池耗尽未被检测**（只监控了 CPU，而连接池耗尽的正确指标是**活跃连接数、等待队列长度、连接获取耗时、连接池饱和度**）；②**19/23 次故障靠用户投诉发现**。 |
| **3. 三支柱未打通，日志不可用** | 日志分散在 8 个节点本地磁盘，未按请求 ID 串联 | **缺少两个基础能力**：①**集中式日志采集**（未部署日志汇聚）；②**缺少统一的请求标识（TraceId）贯穿**。结果是**告警发生后无法定位到具体请求**，排查只能靠猜。**这是"有监控但排查不了"的根本原因。** |
| **4. 缺少 SLO 与错误预算，稳定性无法管理** | 无度量口径、无投入产出权衡 | **没有定义任何 SLI/SLO**，因此：①无法判断"当前可用性到底多少"；②无法用错误预算把"要不要发布"变成可计算的决策；③23 次故障每次都靠"人肉救火"而非"制度化改进"。**稳定性完全依赖人力投入，必然不可持续。** |
| **5. 故障后无系统性复盘与改进闭环** | 19 次故障靠热线发现，且同类问题重复发生 | **缺少故障复盘机制（无故障类型分类、无 MTTR 统计、无改进项跟踪）**。这导致组织**永远在处理"当前这一场火"，从不减少"下一场火的成因"**。典型证据：连接池配置过小这一类问题在其他服务中大概率同样存在，但无复盘就无从排查。 |

**补充根因（贯穿性）**：**该团队的"可观测性建设"停留在"部署监控平台 + 配告警规则"的工具层面，没有建立"从用户症状到系统内部状态"的推理链条。** 这正是可观测性与监控的本质差距。

### 问题 2 — "CPU 正常但用户觉得卡"的原因与排查思路

**这类现象的根因几乎从不在资源总量上，而在资源的使用方式、排队、级联与前端感知上。**

**可能的技术原因（按发生概率排序）**：

1. **下游依赖饱和（最常见）**。本服务 CPU 正常，但它调用的下游（数据库连接池、Redis 连接数、第三方接口、认证服务）**已达饱和**，请求在**排队等待**而非在计算。**排队等待不消耗本服务 CPU**——这是"CPU 正常但慢"的第一大原因。典型：连接池 20 个连接、并发 200 个请求 → 180 个请求在等连接，CPU 却在 25%。
2. **线程池/协程池耗尽**。Web 容器（如 Tomcat）线程池被打满，**新请求在队列里排队**，表现为响应时间飙升但 CPU 不高。**Tomcat 的 `maxThreads` 被打满是国内最常见的一类故障。**
3. **级联故障与重试放大**。下游变慢 → 本服务超时重试 → 流量放大 N 倍 → 下游更慢 → **形成正反馈雪崩**。此时**总 CPU 可能确实不高，但延迟成倍增长**。
4. **锁等待**。数据库行锁/表锁等待不消耗应用 CPU。典型症状：**CPU 低但接口慢 + 数据库活跃连接数高 + 存在长事务**。
5. **前端感知与网络层**。后端很快但**首字节慢**（TTFB 高），瓶颈在网络、CDN、TLS 握手、或**前端 JS 渲染/接口瀑布（串行请求）**。**"转圈很久"常常是前端发起 5 个串行接口，每个 300ms，合计 1.5 秒。**
6. **GC 停顿**。Java 类应用频繁 Full GC 会造成周期性长尾延迟，**而 CPU 平均值可能完全正常**（甚至不高，因为 GC 用的是多核）。需看**GC 暂停时间分布**，不是看 CPU。
7. **慢查询**。单条 SQL 无索引导致全表扫描，单次耗时数秒，**CPU 可能确实不高**（IO 等待），但用户感知是"卡住"。

**排查思路（按可观测性成熟度递进）**：

**第一步：先定位是"哪一段"慢，而不是"整体慢"。**
- **引入 APM 分布式追踪**，按 TraceId 拆出各段耗时：网关 → 认证 → 应用 → 数据库 → 缓存 → 外部接口
- **看 P99 而非平均值**——用户投诉的"卡"几乎都是尾部
- **用火焰图（Flame Graph）看线程状态**：大量线程在 `WAITING`（等锁/等连接）还是 `RUNNING`（真在算）？**这一步就能区分"算不过来"和"在等"。**

**第二步：若定位到等待，查等待的对象。**
- 数据库：查**连接池饱和度、活跃连接数、等待队列、慢查询、锁等待**
- 应用：查**线程池活跃数/队列长度**、连接池配置
- 下游：查**下游自身的 P99 与错误率**

**第三步：查是否有放大机制。**
- 统计**超时率与重试次数**，看是否形成重试风暴
- 查**熔断降级是否生效**（未熔断的必然雪崩）

**第四步：查感知层。**
- 前端接口瀑布图、TTFB 分解、CDN 命中率

**对该案例的具体结论**：团队"扩容解决卡顿"的建议是**错误的**——**CPU 28% 说明瓶颈不在计算资源**，扩容只会增加节点数、分散连接池、**让问题更难定位**，且成本翻倍。**正确动作是：先上链路追踪定位卡在哪一段，看是连接池饱和还是线程池打满，再对症处理（调大连接池、加缓存、异步化非关键调用、前端并行请求）。** 事实上，从补充信息看，**认证服务连接池配置过小**极可能就是这个问题的答案。

### 问题 3 — 对"直接上 APM 全链路追踪"的评价

**结论：必要，但远不充分。单上 APM 追踪无法解决本案例的核心问题。**

**它能解决的**：
- 问题 2 的"定位是哪一段慢"——**这是 APM 最大的价值，本案例确实需要**
- 提供跨服务的调用拓扑，发现级联故障路径
- 为 MTTD 提供技术基础（异常调用链自动告警）

**它解决不了的（五点）**：

1. **解决不了告警噪音问题。** 上完追踪，**847 条告警一条不少**，因为噪音来自**告警规则设计**与**缺少告警收敛机制**，与有没有追踪无关。**必须同步做告警分级、去重、抑制、聚合和可行动性重构。**

2. **解决不了"检测缺失"。** 连接池耗尽的检测**不依赖追踪**，而依赖**正确的指标埋点**（连接池饱和度、等待队列、连接获取耗时）。**必须补齐应用与中间件层的 RED 指标。** 追踪是"事后定位"工具，SLO 驱动的告警是"实时检测"工具，两者不能互相替代。

3. **解决不了日志不可用问题。** 追踪告诉你"数据库查询花了 3 秒"，**但为什么慢**要看日志。**必须同时做日志集中化与 TraceId 贯穿。**

4. **解决不了"19 次靠投诉发现"这个流程问题。** 这需要的是 **SLO 驱动的合成监控与拨测**（从用户视角主动探测），而不是被动等告警。**合成监控（Synthetic Monitoring）是本案例最该补的一环。**

5. **解决不了复盘与改进闭环。** 需要建立**故障分类统计 + MTTR 跟踪 + 改进项跟踪 + 错误预算封顶机制**这套制度。

**补全方案（正确的建设顺序）**：

**第一阶段（打地基，2 周）**：
- 部署**集中式日志采集**（Filebeat/Fluent Bit → Elasticsearch/Loki），**统一日志格式**
- **引入 TraceId 并贯穿全链路**：网关生成/透传 TraceId，**所有应用日志、数据库审计日志、消息队列消息属性全部携带 TraceId**
- 补齐**基础指标**（RED + 中间件关键指标：连接池、线程池、GC、慢查询、缓存命中率）
- **建设合成监控**：从外部网络按真实用户路径做拨测（登录、查询、提交），**主动发现"用户感知到但服务器指标正常"的问题**

**第二阶段（治理告警，2 周）**：
- **告警分级重构**：P1（立即呼叫，需人工介入且有明确 SOP）/ P2（工作时间处理）/ P3（工单记录），**180 条规则按此重新归类**
- **告警收敛**：同源去重、抖动抑制、时间窗口聚合、依赖抑制（**下游挂了不重复报上游**）
- **每条告警必须绑定 Runbook**（处置手册），无 Runbook 的告警一律降级或删除
- **告警有效性周复盘**，无效告警进"整改池"

**第三阶段（引入追踪，2-4 周）**：
- 部署 **OpenTelemetry + APM 后端**（Jaeger/Tempo）+ **Service Map**（服务拓扑）
- **异步链路打通**：Kafka/RabbitMQ 消息属性携带 TraceContext，线程池任务显式传递 Context
- **采样策略**：错误请求 100%、高延迟请求 100%、正常请求按比例
- **Span 粒度管控**，防止 Span 爆炸

**第四阶段（制度化，1 个月）**：
- 建立 **SLO 与错误预算**（见问题 4）
- **故障复盘机制**：无指责复盘（blameless postmortem）、故障类型分类、MTTR 统计、改进项跟踪至关闭
- **把"是否发布"与错误预算余额绑定**

**一句话**：**APM 解决"看得见"，SLO 与告警治理解决"管得住"，复盘机制解决"不再犯"。三者缺一，稳定性都建不起来。**

### 问题 4 — SLO 体系与错误预算机制设计

#### 4.1 SLI 选型（针对该政务平台的特点）

| 维度 | SLI 定义 | 目标值建议 | 说明 |
|---|---|---|---|
| **可用性** | 成功请求数 / 总请求数（**"成功"= HTTP 2xx + 业务状态码正常 + 数据校验通过**） | 99.9% | 政务平台高可用要求；**必须把"业务状态码正常"纳入成功定义**，否则数据错误不算故障 |
| **延迟（关键接口）** | 办事查询、提交、支付三类核心接口的 **P99** 响应时间 | 提交类 ≤ 800ms；查询类 ≤ 500ms | **用 P99，不用平均值** |
| **延迟（登录）** | 统一身份认证 P99 | ≤ 300ms | 认证是所有业务的入口，单独设更严的 SLO |
| **正确性** | 业务数据一致性校验通过率 | ≥ 99.99% | **政务系统的"可用但错"比"不可用"更严重**，必须单列 |
| **数据新鲜度** | 事项库、办件状态数据从产生到可查的延迟 | ≤ 1 分钟 | 保证"数据不一致"类投诉可解释 |
| **吞吐** | 峰值 TPS 承载能力 | 满足早高峰 3 倍冗余 | 容量规划用 |
| **合成探测可用性** | 拨测成功率（用户视角） | ≥ 99.5% | **比内部指标更贴近用户感知**，是"CPU 正常但用户卡"的唯一可靠探测器 |

**必须补充的关键点**：**"可用但错"必须被计入失败。** 政务平台最危险的故障不是系统挂了，而是**系统正常响应但数据错了**（如多扣费、办件状态错乱）。若 SLI 只统计 HTTP 错误码，这类故障完全不可见。

#### 4.2 SLO 目标设定方法

**不能拍脑袋定，要用"用户可感知"倒推：**

1. **先定用户可感知的底线**：如"办事人提交材料后，10 秒内必须看到明确结果（成功或失败）"。这是**用户旅程 SLO**，比单个接口 SLO 更接近真实体验。
2. **用历史数据校准**：统计过去 3 个月的真实 P99 分布，**SLO 设在比当前水平略好、且技术上可达的位置**。**一步定到位（从 99% 直接定 99.99%）会导致 SLO 从第一天起就违约，团队直接放弃。**
3. **分阶段提升**：第一阶段 99.5% → 第二阶段 99.9% → 第三阶段 99.95%，每阶段稳定一个季度再提升。**这是错误预算能落地的关键节奏。**
4. **关键接口与普通接口分级**：登录、提交、支付**必须最严**；后台查询、内部管理可宽松。**一套 SLO 覆盖所有接口是最常见的错误。**

#### 4.3 错误预算的计算与使用机制

**计算示例**：
- 月请求量按 1 亿次计（其中核心写操作 2000 万次）
- 可用性 SLO 99.9% → 月错误预算 = 1 亿 × 0.1% = **10 万次**
- 正确性 SLO 99.99% → 错误预算 = 1 亿 × 0.01% = **1 万次**（**数据错误的预算比可用性严格 10 倍**）

**使用机制（写成可执行规则）**：

| 预算消耗状态 | 规则 | 强制动作 |
|---|---|---|
| **消耗 < 50%** | 绿灯 | **正常发布节奏**，可上中大型功能 |
| **消耗 50%–80%** | 黄灯 | **限制发布规模**，新功能需项目集/架构评审确认风险；**优先偿还技术债** |
| **消耗 80%–100%** | 橙灯 | **仅允许缺陷修复与紧急安全补丁上线**，冻结所有新功能；**启动稳定性专项** |
| **消耗 = 100%** | 红灯 | **完全冻结发布**，全团队转入可靠性模式；**SLO 达成率纳入部门考核** |

**三条配套规则（缺一不可）**：

1. **"冻结发布"必须由数字自动触发，不由领导拍脑袋。** 预算耗尽即冻结，不需要争论"现在到底稳不稳"。**这就是错误预算最核心的价值——它把一个价值判断变成了一个算术判断。**

2. **预算被"用完"是坏消息，要追责。** 预算消耗过快说明**质量问题在恶化**。必须复盘：**是哪个变更引入了问题？是哪类缺陷没被拦住？** 绝不能把"预算用完"当成"发布太多"来解释——**发布多不是问题，错误多是问题。**

3. **预留"不可抗力"额度与"重大变更"豁免机制。** 例如 3·15 前的集中保障期、重大政策上线日，**允许临时超预算，但必须登记并在事后复盘**。**没有豁免机制，团队会为了不超预算而压制必要的紧急修复——这比超预算更危险。**

#### 4.4 配套的度量看板与复盘节奏

- **每日**：错误预算消耗率、Top 10 错误类型、合成探测结果
- **每周**：告警有效性复盘（无效告警整改闭环）、MTTR 统计
- **每月**：SLO 达成报告（按接口、按 SLO 分别算）、故障类型分布与趋势、**错误预算超支的复盘**
- **每季度**：SLO 目标值是否需要调整（**该升的升、该降的降**——长期达不到的 SLO 应该重新审视而不是硬撑）

**最后一条至关重要**：**SLO 是用来改进的，不是用来考核的。** 一旦把 SLO 达成率直接和个人绩效强绑定，团队的第一反应必然是**把 SLO 定得极松**、或者**出问题时隐瞒**。**正确做法是：SLO 用于约束发布节奏和驱动改进；个人绩效看过程指标（复盘质量、改进项闭环率、值班响应）。**

## 记忆口诀

- 口诀 1：**监控问"有没有"，可观测问"为什么"**——预设故障是监控，陌生故障才需要可观测。
- 口诀 2：**三支柱要打通**——指标看趋势、日志看细节、追踪看路径，缺一排查就断。
- 口诀 3：**SLI 是数、SLO 是目标、SLA 是合同**——**SLA 赔钱，SLO 不赔。**
- 口诀 4：**延迟用分位数**——平均值 200ms 可能藏着 1.9 秒的尾巴。**SLO 必用 P99。**
- 口诀 5：**错误预算是上限不是许可**——耗尽就冻结发布，不是"还有就多上点"。
- 口诀 6：**预算耗尽自动触发行为**——把"要不要发布"从争论变成算术。
- 口诀 7：**预算耗太快是坏消息**——说明质量在恶化，不是发布太多。
- 口诀 8：**TraceId 贯穿日志**——追踪说"哪里慢"，日志说"为什么慢"，**双向跳转才算完整**。
- 口诀 9：**异步是追踪最大断点**——MQ 与线程池必须显式传递 Context。
- 口诀 10：**排队不耗 CPU**——"CPU 正常但慢"第一嫌疑是连接池饱和或线程池打满。
- 口诀 11：**告警看可行动性**——"收到必须立刻动手"才是告警，"指标越界"不是。
- 口诀 12：**告警四件配套**——分级、去重、抑制、Runbook，缺一就还是噪音。
- 口诀 13：**可用但错最危险**——政务系统的数据正确性 SLO 要比可用性严 10 倍。
- 口诀 14：**SLO 别一步到位**——分阶段提升，稳一个季度再升，**否则从第一天就违约**。
- 口诀 15：**SLO 不用于个人考核**——用于管发布和驱动改进；考核用过程指标。
- 口诀 16：**合成监控补位**——用户感知与内部指标背离时，拨测是唯一可靠探测器。
- 口诀 17：**可维护性三支柱**——可观测 + 可部署 + 可回滚，缺一不可。
- 口诀 18：**FMEA 看 S 的独立门槛**——RPN 相乘会掩盖高严重度项，**S=9 以上必须处理**。
