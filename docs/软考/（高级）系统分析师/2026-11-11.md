# 系统分析师 · 第 66 次学习（2026-11-11）

## 今日核心概念

### 1. 遗留系统数据迁移与双写一致性工程化

定义：遗留系统数据迁移与双写一致性工程化，指在不停用老系统的前提下，将业务数据从旧有存储结构平稳搬迁到新系统，并通过"双写 + 校验 + 切流 + 回滚"四段式工程手段，保证迁移期间新老两侧数据始终可核对、最终一致、随时可退的技术体系。

关键要点：

- 四阶段生命周期：评估（存量盘点与依赖分析）→ 准备（通道建设与映射建模）→ 执行（迁移试跑与双写校验）→ 切换（金丝雀放量与回滚兜底）。
- 双写三种模式：同步双写（强一致、延迟叠加、失败即阻断）、异步双写（最终一致、需幂等与补偿）、事件驱动双写（CDC 捕获旧库变更 → 消息 → 新库消费，推荐用于存量系统改造）。
- 一致性校验三步法：抽样核对（按主键分层抽样，量级建议万分位）、总量比对（行数、金额、数量、状态分布四类聚合校验）、差异归因（差异分类为漏写、延迟、乱序、覆盖、脏数据五类并分别定位）。
- 差异窗口三段耗时：捕获延迟（CDC/日志解析）、投递延迟（MQ 积压）、应用延迟（消费与幂等处理），优化时先测出三段各自占比再动手。
- 灰度切流三金丝雀：按流量比例（1%、5%、20%、50%、100%）、按租户/机构维度、按数据实体维度；每级放量需设置观察窗口与回滚阈值。
- 回滚红线四指标：差错率超阈值、时延 P99 超基线、峰值 CPU/内存越界、业务部门书面叫停；任一触发即切回旧系统主写通道。
- 不可逆变更清单六动作：旧库停写、旧表下线、旧字段清除、索引重建、字符集转换、时间戳精度调整；每项必须先有备份与独立回滚脚本。

### 2. CDC 变更数据捕获与增量同步

定义：CDC（Change Data Capture，变更数据捕获）是通过读取数据库事务日志（如 MySQL binlog、Oracle redo log、PostgreSQL WAL）实时或准实时获取数据变更事件的技术，是新旧系统间增量同步、双写校验与事件溯源的基础设施。

关键要点：

- 三种捕获模式：日志捕获（对源库零侵入、性能最好、主流方案）、轮询触发器（实现简单但性能差、锁竞争大、仅适合小表）、消息中间件捕获（需改造业务写库路径，侵入性中等）。
- 三类数据载体：行级（携带全部列，回放简单、带宽大）、列级（只带变更列，需保留最后镜像表）、日志事件（携带事务边界与顺序号，语义最强）。
- 三大工程难题：顺序性（同一主键变更必须有序）、幂等性（重复投递不产生副作用）、一致性快照（事务内多表变更的原子可见性）。
- 顺序性保障三招：按分片键单分区有序、目标端做版本号/时间戳去重与丢弃过期版本、全局序列号兜底。
- 幂等三件套：唯一键约束（数据库兜底）、幂等表/去重表（记录消息 ID）、业务状态机判定（只允许合法状态跃迁）。
- 源库影响控制三招：独立日志流通道、批量拉取与限流、避开高峰并设置断点续传位点。
- 关键延迟来源：日志刷盘频率（commit 到日志落盘的间隔）、位点采集轮询间隔、投递批量大小与压缩率。

### 3. 影子流量与金丝雀发布验证

定义：影子流量是指将真实生产请求复制一份（镜像流量）发送到新系统处理但丢弃其返回结果，只采集并比对两套系统的输出差异，以在不影响用户的前提下验证新系统行为；金丝雀发布则是将真实小比例流量切到新系统，观察真实用户反馈后逐级放量。

关键要点：

- 影子流量三大用途：性能压测（不占生产资源）、行为差异比对（响应字段/业务结果一致性）、数据回归验证（存量数据在新系统的读取渲染是否一致）。
- 影子流量的三大风险：影子请求产生副作用（写入、发消息、扣费，必须通过打桩/影子库/标记位拦截）、隐私与合规风险（复制个人数据需脱敏并限定范围）、资源挤占（镜像流量占用新系统产能，需限流）。
- 差异比对三类：状态码与 HTTP 层差异、业务字段语义差异（含空值与默认值处理）、时序与数量差异（如返回列表条数、排序规则）。
- 金丝雀放量五级阶梯：1% → 5% → 20% → 50% → 100%，每级观察窗口不低于一个业务峰值周期；不可跳级。
- 金丝雀四指标看板：错误率、响应时延（分位值）、业务转化/办件量、饱和度（CPU/内存/连接池）；设硬阈值与软阈值双线。
- 回滚三档时长目标：一键切回（分钟级）、流量比例回滚（秒级）、版本回退（重建镜像）；前者需蓝绿或双写通道常备。
- 影子与金丝雀的分工：影子解决"行为是否一致"，金丝雀解决"用户是否接受"，两者不可互相替代。

### 4. 数据迁移校验与双端一致性兜底

定义：迁移校验是指在新旧系统并行期间，通过总量核对、抽样比对、规则校验、日志追踪四种手段持续验证两侧数据一致性，并据此决定放量、暂停或回滚的常态化工程机制。

关键要点：

- 四类校验手段：总量校验（行数、金额、数量、状态分布）、抽样校验（随机抽样 + 关键字段全字段比对 + 边界值样本）、规则校验（校验和、哈希、聚合值、余额对账）、链路校验（业务流水端到端回溯）。
- 抽样三原则：随机性（避免只取首尾）、覆盖性（覆盖新建/修改/删除/边界四类记录）、分层性（按数据量、租户、时序分层）。
- 差异五分类归因：漏写（事件未产生或被过滤）、延迟（在窗口内尚未到达，属可接受差异）、乱序（旧版本覆盖新版本）、覆盖（新系统写覆盖了旧系统值）、脏数据（源端本身有问题）。
- 可接受差异与不可接受差异的界定：以业务时间窗为界，窗口外差异不可接受；窗口内差异需在 SLA 约定时限内收敛。
- 兜底三机制：对账批处理（每日定时跑差异比对并出报表）、异常补偿队列（差异自动生成补偿任务）、人工核查通道（提供差异明细查询与一键重放）。
- 迁移完成的判定标准：连续 N 天差异率低于阈值、差异全部归因闭环、业务方签署确认、观察期无新增异常。

### 5. 遗留系统现代化四象限与改造策略选型

定义：遗留系统现代化四象限，指以"业务重要性"与"系统可改造性"两个维度，把遗留系统划分为核心且难以改造、核心且易于改造、非核心且难以改造、非核心且易于改造四类，并针对每一类匹配差异化的改造路径。

关键要点：

- 四象限策略矩阵：核心+难改（绞杀者模式渐进替换 + 双写过渡）、核心+易改（原地重构或分层改造 + 领域模型重塑）、非核心+难改（保留原系统 + 防腐层隔离 + 功能冻结）、非核心+易改（直接下线并迁移数据至轻量服务）。
- 防腐层（ACL）定位：在新系统与遗留系统之间设置稳定接口层，屏蔽遗留接口变动，使遗留系统可随时替换。
- 功能冻结与遗留清单：一旦确定保留系统，立即冻结新需求并登记遗留功能清单，避免"边留边改"的成本黑洞。
- 技术债盘点四维度：代码债、数据债、架构债、运维债；每项估算治理成本与收益，排出优先级。
- 风险隔离三原则：不引入新架构债（改造不得比原系统更脆）、不破坏业务连续性（关键路径必须可回滚）、不做大爆炸式替换（除非系统极小且可停机窗口充分）。
- 决策输出物：现代化路线图（分阶段目标 + 里程碑 + 量化指标）、迁移矩阵（系统—模块—改造策略—责任方—时间）、风险登记册与应对清单。

## 案例分析题

**题目**：

某市社保经办服务平台改造。原系统为"经办前置子系统 + 待遇发放子系统"两套老旧应用，分别运行在两台物理机上，数据库为 Oracle 11g；新系统采用 Java 微服务架构、MySQL 8.0 集群。项目组制定方案：将两个子系统数据迁移至新平台，迁移期间新旧系统并行运行。为保证数据一致，方案设计"双写"：应用层在写老库的同时调用新库接口写入新库。

上线三个月后出现以下情况：

1. 待遇发放子系统日均处理补贴发放 12 万笔。改造期间，老库对"待发放"表写入后，新库偶尔查不到对应记录，出现"办件成功但新系统无数据"的现象，人工核查发现两库差异约 1800 条。进一步排查发现，应用在写老库成功、写新库失败时，异常被 catch 后仅记录日志，未做补偿，运维通过定时脚本每日拉取差异并人工补录。

2. 财务对账发现，某批次共 5 万笔补贴中，有 137 笔金额在新库中为 0.01 元级别，而老库为正常金额（约 800 元）。分析为改造代码中新增的"金额精度转换"逻辑使用了 double 类型进行累加。

3. 新系统上线后，老系统仍被多个科室使用并持续产生新需求，业务部门要求"新系统上线后再也不回老系统"。同时新系统按"经办—审核—发放"三阶段流程重构了业务模型，与老系统的"经办—发放"两阶段不一致，两边数据无法直接对应。

4. 数据同步链路采用应用层双写 + 每日定时脚本补录，运维统计显示同步差异修复依赖人工，日均人工补录耗时约 3 小时，且存在补录重复导致个别记录重复发放的风险。

5. 切流计划：先按机构维度切 1 个试点机构，观察 2 周后逐步放量至全量。运维提出上线后回滚需要在 30 分钟内切回老系统主写通道，但当前架构中老库写入路径未被统一收口，散落在多个服务中。

问题：

1. 请指出该方案在双写一致性设计上的主要缺陷（至少 4 条），并说明各自应采取的改进措施。

2. 针对现象 1 和现象 2，请分别分析根本原因，并给出对应的技术解决方案。

3. 请设计替换该双写 + 人工补录方案的新同步机制，说明其技术选型理由与关键实现要点。

4. 请针对问题 3 的"业务模型不一致"和"老系统持续新增需求"，分别给出治理措施。

5. 请评估问题 5 的切流方案与回滚设计，指出风险并提出改进后的分阶段放量与回滚方案。

**参考答案**：

**问题 1：双写一致性设计的主要缺陷与改进措施**

缺陷一：双写顺序为"先老库后新库"，且新库写失败被 catch 后仅记日志不补偿，形成静默丢写。
改进：改为"以新库为权威源 + 老库为影子"或引入可靠消息；写失败必须进入补偿队列并重试，禁止吞异常；引入事务性发件箱（Transactional Outbox）或在写库与发消息间使用可靠事件机制。

缺陷二：应用层双写在同一次业务操作中跨两个数据存储，无法保证原子性，存在部分成功的不一致窗口。
改进：改用事件驱动同步（数据库变更捕获 CDC），将新库写入交由订阅端异步完成，业务事务只保证本地事务原子性；或采用分布式事务（TCC/Saga）但成本高，仅用于强一致关键路径。

缺陷三：缺乏任何一致性校验机制，仅靠人工发现。
改进：建立自动化对账体系——每日定时批量比对总量（行数、金额、状态分布）、按主键抽样全字段比对、关键表校验和对账，输出差异报表并自动生成补偿任务。

缺陷四：差异修复依赖人工脚本补录，存在重复补录与重复发放风险。
改进：以消息 ID 或业务流水号建立幂等控制（唯一键约束 + 幂等表 + 状态机判定），补偿动作走幂等接口；差异闭环由补偿队列自动完成，人工仅处理异常例外。

缺陷五：同步链路是"推"模式（应用写时推），老系统侧对遗留机构产生的变更无法感知，覆盖不全。
改进：改为"拉 + 推"结合，以 CDC 捕获老库全部变更作为兜底通道，确保同步不遗漏任何写入来源。

缺陷六：双写顺序导致读偏斜（read skew）。在切换前若以新库为查询源，可能读到不完整数据。
改进：切换期采用老库为查询源、新库只写；或引入"就绪标记 + 版本可见性"控制，仅在数据追平后才对某机构开启新库读。

**问题 2：现象 1 与现象 2 的根因与方案**

现象 1（老库有、新库无，约 1800 条）根因：
- 直接根因：应用层双写顺序错误 + 新库写失败被静默吞掉（catch 后只记日志），导致部分写入从未到达新库。
- 机制根因：跨库双写不具备原子性，且没有重试与补偿机制；双写点分散在多个业务方法中，遗漏难以发现。
- 次生根因：差异发现依赖人工每日拉取，时效滞后，导致差异持续累积。

解决方案：
- 同步机制重构：以老库为源引入 CDC 捕获 binlog/redo 变更，作为最终一致的兜底同步通道；应用层双写降级为低时延的快速通道（可选）。
- 写失败处理：失败必须抛至统一异常处理器，进入持久化重试队列（指数退避 + 死信队列），死信由人工介入但需有工单闭环。
- 幂等：以业务流水号 + 源库主键建唯一索引，重复投递使用 upsert 或状态机判定。
- 顺序保证：按主键/机构维度分区有序投递，目标端以版本号或更新时间戳丢弃过期版本。
- 校验兜底：每日自动全量比对 + 分层抽样，差异自动生成补偿任务，人工只做例外审核。
- 存量修复：对已存在的 1800 条差异做一次性回补，以 CDC 位点重放 + 补偿任务双通道，并做重复发放核查。

现象 2（金额 0.01 元级别）根因：
- 直接根因：使用 double 浮点类型表示与累加金额，二进制浮点无法精确表示十进制小数，存在舍入误差；尤其在经过多次类型转换（如 String→double→BigDecimal 转换链中先入 double）后产生精度丢失。
- 加剧因素：金额在老库为 DECIMAL(18,2)，新库字段定义或应用层反序列化环节出现类型不匹配；累加场景下误差逐笔放大。

解决方案：
- 金额一律使用 BigDecimal（或长整型以最小单位"分"存储），禁止 double/float；字符串与金额互转必须走 BigDecimal 且显式指定 scale 与 RoundingMode，建议统一 RoundingMode.HALF_UP。
- 明确字段与映射规范：数据库 DECIMAL(18,2)，应用层 BigDecimal，序列化用字符串而非常规数字，防前端/JSON 精度丢失；建"金额类型"代码规范并做静态检查与单测覆盖。
- 补偿方案：对已产生的 137 笔异常，以老库金额为权威源比对修复，并回溯该批次全部 5 万笔做全量金额核对，防止误差未暴露的部分。
- 校验常态化：把"金额类字段逐笔比对"加入每日差异对账，且此类差异直接判定为不可接受差异，触发告警并阻断切流。

**问题 3：新的同步机制设计与选型理由**

方案：事件驱动 + CDC 为主的应用层双写兜底架构。

组件与职责：
- 变更捕获层：CDC 组件以日志订阅方式捕获老库（Oracle 11g redo log / 非归档日志）变更，解析为行级变更事件；或若老库无法改造（无 logminer 权限、版本受限），退化为"应用层可靠事件发件箱 + 定期批量抽取对账"的组合。
- 事件总线层：引入消息中间件（Kafka 或 RocketMQ），按主键/机构分片保证同键有序；开启消息持久化与多副本。
- 幂等与消费层：新库消费端以"业务流水号 + 源主键"唯一键实现幂等 upsert；采用状态机判定，只接受合法状态跃迁；记录消费位点支持断点续传。
- 校验对账层：每日 T+1 全量比对（行数、金额、状态分布、哈希抽样）+ 实时抽样；差异分类归因（漏写/延迟/乱序/覆盖/脏数据），自动生成补偿任务。
- 补偿层：差异补偿走幂等补偿接口，支持一键重放；死信队列 + 人工工单闭环。

选型理由：
- CDC 相比应用层双写：对源库零侵入（不需改老系统全部写路径）、可捕获所有写入来源（含遗留机构的后台脚本与直连操作）、不增加老库应用事务耗时、性能稳定。
- 事件驱动相比同步 RPC 写：新库不可用不阻塞老系统主流程，故障隔离；削峰填谷，支撑搬迁期双倍写入压力。
- 消息中间件选 Kafka/RocketMQ 而非数据库轮询：支持高吞吐、分区有序、持久化重放、位点管理。
- 保留应用层双写作为低时延快速通道而非唯一通道：兼顾切换前的新库查询时延要求，同时不作为一致性唯一保障。

关键实现要点：
- 顺序性：同主键分区有序；目标端以版本号/时间戳比对，丢弃过期版本（解决乱序覆盖）。
- 幂等：数据库唯一键为最终防线，幂等表辅助，业务状态机三重保障。
- 一致性快照：CDC 需处理事务边界，保证同一事务内多表变更的原子可见性；必要时保留事务 ID。
- 延迟控制：监控"捕获—投递—应用"三段耗时，分别治理（日志刷盘频率、位点轮询间隔、消费批量与并发），把端到端延迟控制在秒级。
- 源库保护：独立日志流通道、限流、避开高峰、位点续传。
- 存量回补：以位点重放历史变更 + 一次性全量抽取补齐 1800 条与 137 笔异常，校验后关闭回补通道。

**问题 4：业务模型不一致与老系统持续新增需求的治理**

业务模型不一致（"经办—审核—发放"三阶段 vs "经办—发放"两阶段）：
- 建模映射：建立"老系统功能—数据实体—新系统阶段"三维映射表，明确老"经办"在新模型中如何映射到"经办+审核"两阶段的拆分规则（谁填、谁审、审核结论如何回写老库或替代）。
- 数据模型重构：在新库引入"业务主表 + 阶段实例表"（阶段化/状态机建模），使老的一条记录可展开为新模型下的多条阶段记录；建立老 ID 到新 ID 的映射表（ID 映射服务），保证双向可查。
- 接口防腐：在新系统侧增设 ACL 防腐层，向老系统暴露"按老口径的聚合视图接口"，老系统无需理解新模型；反向由同步通道把新阶段结果翻译回老库字段格式。
- 流程与权限对齐：对新增的审核环节明确责任岗、时限、驳回回退路径；若老系统不承载审核职能，则在过渡期由新系统单独承载并向老库写回汇总状态。
- 过渡期数据唯一性：约定过渡期以新库为权威源写、老库只读镜像（或反之，须全局一致），避免双主写入导致模型映射歧义。

老系统持续新增需求：
- 立项阶段明确"遗留系统清单"并冻结功能：对确认为保留的老系统立即停止新增功能开发，需求一律转至新平台改造实现，走统一需求池与版本规划。
- 设置需求"收口闸门"：新增需求评审时必须回答"为什么不放新系统"，特殊情况需架构治理委员会审批；老系统需求只允许缺陷修复与合规类强制变更。
- 债务登记与偿还计划：对老系统做功能—使用部门—使用频次盘点，把"无人使用/低频"的功能列入下线清单，随迁移分批下线（功能下线即数据清理，可直接减少迁移范围）。
- 技术隔离与安全网：老系统只读化（关键流程迁移后转只读）、加 ACL 与监控告警、保留完整操作审计，便于在满足业务连续性前提下安全下线。
- 组织机制：设立架构治理委员会与架构合规评审（ADR 强制留痕），把"不再回老系统"从口号变成流程卡口。

**问题 5：切流与回滚方案评估及改进**

对现方案的评价（风险点）：
- 只按机构维度单级切 1 个机构后直接放量全量，缺少中间阶梯与观察窗口，风险暴露过快。
- 观察期仅 2 周，未覆盖完整业务周期（月底批量结算、季度社保基数调整、年度医保报销高峰），峰值场景未验证。
- 回滚要求 30 分钟内切回，但老库写入路径未收口、散落多服务，实际上难以在 30 分钟内完成切换，回滚承诺不可落地，属"不可执行的回滚方案"。
- 未定义放量阈值与自动回滚触发条件，依赖人工判断，切流过程缺少可度量的门禁。
- 切换期读写源未明确（老库写、新库已写、双主？），存在双主写冲突与读偏斜风险。

改进后的分阶段放量方案（阶梯式 + 门禁化）：
- 阶段零（准备）：完成同步链路验证与存量回补；差异率连续 3 天低于 0.01% 且金额类差异为 0；完成全链路压测与故障演练（CDC 中断、消息积压、新库不可用）；建立老库写入口收口（统一写入代理/单一写入服务），保证回滚可秒级执行。
- 阶段一（影子验证）：不切流，镜像真实流量到新系统，比对响应与业务结果，连续 3 个完整业务周期无重大差异。
- 阶段二（金丝雀）：按流量比例 1% → 5% → 20% → 50%，每级观察不少于 5 个工作日且必须覆盖一次月度批量结算峰值；每级设观察窗口与四指标看板（错误率、P99 时延、业务办件量、饱和度）。
- 阶段三（机构灰度）：按机构维度逐批放量，每批 3~5 个机构，保留原试点机构作为对照组，用于识别机构特有的业务差异。
- 阶段四（全量与老库只读化）：全量后保留老库可写回退窗口 2 个月，期满转只读，随后下线。

回滚方案（三层兜底）：
- 第一层（秒级·自动）：以"主写开关 + 流量权重开关"配置化控制，切回老库主写并把新库写入降级为影子；要求开关在管理后台一键操作，不依赖重新发布。
- 第二层（分钟级·预案）：老库写入统一收口至单一代理，切回只需改路由；预先准备数据补差脚本（切回后把新库期间产生的增量同步回老库），确保老库数据不缺。
- 第三层（小时级·重建）：镜像版本回退与数据库版本回滚（DDL 不可逆项须提前准备反向脚本）。

触发回滚的硬红线（任一命中即自动回滚）：差错率 > 0.1% 或出现任一金额类差异、办件成功率下降 > 0.5 个百分点、P99 时延 > 基线 1.5 倍、饱和度（CPU/连接池）> 85% 持续 10 分钟、业务部门书面叫停。

**踩分要点**：

1. 问题 1 必须答出"双写顺序与静默吞异常""跨库无原子性""缺一致性校验""人工补录非幂等""老库侧变更漏捕获（覆盖不全）""读偏斜"等具体缺陷，答"缺少事务""缺少补偿"等空话不得分；每条缺陷须配一条对应改进措施，缺陷与措施必须一一对应。
2. 现象 1 根因要点：先写老库后写新库、写失败仅记日志不重试不补偿、跨库双写无原子性、差异靠人工发现导致时效滞后。方案要点：CDC 或可靠事件作为最终一致通道、重试与死信队列、幂等（唯一键/幂等表/状态机）、有序投递与版本去重、自动对账与差异补偿闭环。
3. 现象 2 根因必须明确指出 double/float 二进制浮点无法精确表示十进制小数、金额经多次类型转换精度丢失、累加场景误差放大。方案要点：统一 BigDecimal（推荐以"分"为单位的长整型存储）、禁止 double、显式 scale 与 RoundingMode、字符串序列化防 JSON 精度丢失、137 笔修复并对该批次 5 万笔做全量金额回溯、全量核对结果纳入对账常态化。
4. 问题 3 得分点：CDC（binlog/redo 日志订阅）零侵入与全来源捕获优势、事件总线分区有序与削峰、幂等唯一键兜底、对账层四类校验、补偿层一键重放、延迟三段（捕获/投递/应用）分别治理、存量 1800 条与 137 笔的回补路径（位点重放 + 一次性全量抽取）。注意答题时"CDC"与"应用层双写"的角色定位不要颠倒。
5. 问题 4 得分点：业务模型不一致——阶段化/状态机数据建模、老新 ID 映射表、ACL 防腐层向老系统暴露聚合视图、反向写回老库字段格式、过渡期唯一权威源与读写源约定；老系统新增需求——遗留清单与功能冻结、需求评审收口闸门与例外审批、功能盘点下线清单、老系统只读化与审计留痕、架构治理委员会与 ADR 流程卡口。
6. 问题 5 得分点：指出现方案缺少阶梯与观察窗口、未覆盖完整业务周期、回滚 30 分钟不可落地（写路径未收口）、缺少放量阈值与自动回滚条件、切换期读写源与双主风险；改进方案须体现影子验证 → 金丝雀 1%/5%/20%/50% → 机构灰度 → 全量 → 老库只读化的阶段划分，每级设观察窗口与四指标看板，回滚分自动/预案/重建三层并含"切回后增量回补老库"步骤，硬红线阈值要写出具体数值。
7. 通用踩分：答案中要出现具体技术名词（CDC、Outbox、幂等表、位点重放、ACL、BigDecimal、RoundingMode、金丝雀、影子流量、ADR、状态机、唯一索引、死信队列），并把每条措施落到"谁做、何时做、如何验证"；只罗列原则不给落地方案的，通常只能得一半分。
8. 通用踩分：金额类差异一律判为不可接受差异并触发阻断切流，是本题隐含的关键判断点，必须写出来。

## 记忆口诀

1. 迁移四段：评估准备执行切，影子金丝雀保平安。
2. 双写四型：同步最严异步松，事件驱动最通用，双写兜底靠补偿。
3. CDC 三模式：日志捕获最主流，轮询触发伤性能，中间件捕获改代码。
4. CDC 三载体：行级省心带宽大，列级轻量要镜像，日志事件语义最强。
5. CDC 三大难：顺序、幂等、快照。
6. 顺序三招：分片有序、版本去重、序列兜底。
7. 幂等三件套：唯一键、幂等表、状态机。
8. 源库护三招：独立通道、批量限流、断点续传。
9. 校验四手段：总量、抽样、规则、链路。
10. 抽样三原则：随机、覆盖、分层。
11. 差异五分类：漏写、延迟、乱序、覆盖、脏数据。
12. 差异三段耗：捕获、投递、应用。
13. 兜底三机制：对账批处理、补偿队列、人工核查。
14. 影子三用途：性能压测、行为比对、数据回归。
15. 影子三风险：副作用、隐私合规、资源挤占。
16. 金丝雀五阶梯：一五二十五十百，逐级不跳。
17. 金丝雀四看板：错误率、时延、办件量、饱和度。
18. 回滚三档：一键切回、比例回滚、版本回退。
19. 影子比行为，金丝雀比体验，缺一不可。
20. 金额铁律：BigDecimal 显 scale，double 绝对禁止；字符串传输防 JSON 丢精度。
21. 精度事故先回溯同批全量，再补单笔。
22. 迁移四象限：核心难改绞杀易改重构，非核心易改下线难改隔离。
23. 四象限配招：防腐层隔离、只读化、功能冻结。
24. 技术债四维：代码债、数据债、架构债、运维债。
25. 双写缺陷六条：顺序错、无原子、缺校验、人工补、改动散、会读偏。
26. 幂等三防线：唯一键兜底、幂等表辅助、状态机判定。
27. 乱序丢旧不丢新：目标端版本号比对，丢弃过期。
28. CDC 选型口诀：老库不侵入、来源全覆盖、新库可异步、存量位点重放。
29. Outbox 适用：本地事务 + 可靠事件，不能丢不能重。
30. 写库与发消息：本地事务表兜底，不要分布式锁硬扛。
31. 存量大迁移：位点重放 + 一次性全量抽取，双通道补齐。
32. 老库补录：差异自动生成补偿任务，人工只管例外。
33. 切流阶梯：影子 → 金丝雀 → 机构灰度 → 全量 → 只读。
34. 金丝雀观察窗：不少于一月结算峰值。
35. 灰度必留对照：试点机构当参照系。
36. 回滚红线四：差错率、办件率、P99、饱和度。
37. 阈值数值化：0.1% 差错、0.5pp 成功率、1.5 倍 P99、85% 饱和。
38. 回滚三前提：写路径收口、开关一键化、增量回补脚本。
39. 切回不是就完：新库增量必须回灌老库，否则老库缺数据。
40. 双主不共存：过渡期唯一权威源，读写源写一次写清。
41. 模型不一致三件：阶段化建模、ID 映射、ACL 聚合视图。
42. 新模型回老库：字段格式翻译 + 汇总状态回写。
43. 审核新环节：责任岗、时限、驳回回退三明确。
44. 老系统不接新需求：功能冻结 + 需求收口闸门。
45. 例外要走：架构治理委员会审批 + ADR 留痕。
46. 老功能三盘：使用部门、使用频次、遗留清单。
47. 无用功能随迁下线，迁移范围自然缩小。
48. 老系统最终态：只读化 + 审计留痕 + 可安全下线。
49. 迁移完成四证：差异率达标、差异闭环、业务签署、观察期无异常。
50. 金额差异零容忍，直接阻断切流不商量。
51. 差异别凭感觉，窗口外差异即不可接受。
52. 延迟可容忍但要收敛，SLA 内不收敛就是故障。
53. 采样别只取首尾，随机分层才见真问题。
54. 覆盖四类记录：新建、修改、删除、边界值。
55. 同步三防：漏写防、延迟测、覆盖防。
56. 采集尽量日志源，触发器轮询只做小表应急。
57. 事务内多表变更，注意 CDC 事务边界保原子可见。
58. 顺一致不等于实时，看三段耗时定位瓶颈。
59. 灰度看四指标，单看错误率会漏时延退化。
60. 影子请求必须打桩，副作用拦截是底线。
61. 观察窗要覆盖月末、季末、年度高峰。
62. 不可逆变更六动作：停写、下线、清字段、重索引、改字符集、调精度。
63. 每项不可逆先备份、先写反向脚本。
64. 蓝绿是回滚底气，金丝雀是放量底气。
65. 影子打桩、金丝雀放量、机构灰度切流、只读收官、老库下线——五步一条线。
66. 方案先问三件事：一致性谁保证、失败谁补偿、差异谁发现。
67. 三问答不上来，方案必有洞。
68. 迁移是工程不是搬运，校验与回滚同权重。
69. 一切不可逆变更清单化、脚本化、可审批。
70. 遗留系统现代化四问：要不要留、怎么改、何时切、怎么退。
