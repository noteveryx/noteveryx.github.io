## 今日核心概念

### 1. Serverless 无服务器架构总论与服务形态判据

**定义**：Serverless 是一种架构范式而非某项具体技术：应用开发者只提交业务逻辑（函数、代码或声明式配置），服务器选型、操作系统、运行时、打补丁、扩缩容、负载均衡与计费全部由平台托管，用户按"请求次数 × 资源用量 × 执行时长"付费。"无服务器"指的是**运维责任从用户团队转移到平台方**，而不是真的没有服务器——平台方以另一种形式接管了原先由系统分析师承担的容量规划、故障处置与补丁管理职责。

**关键要点**：

- **三种服务形态**：FaaS（函数即服务，用户交付函数代码，事件驱动、毫秒级启动）、BaaS（后端即服务，用户直接使用托管的数据库、对象存储、消息队列、认证、密钥服务，只写业务代码）、SaaS（软件即服务，用户只做配置与租户运营）。三者是**责任边界递进关系**：IaaS 用户管操作系统，PaaS 用户管应用与数据，FaaS 用户只管函数代码，BaaS 用户只管业务数据，SaaS 用户只管配置。
- **适用判据（六条同时满足才考虑 FaaS）**：① 由事件或请求触发，非常驻进程；② 流量波动大、峰谷比高（政务场景的申报日、集中推送、突发舆情是典型）；③ 单次执行时间短（通常分钟级以内）；④ 执行单元可水平拆分且无强状态依赖；⑤ 有明显的"空闲期资源浪费"可被消除；⑥ 团队愿意接受平台约束与托管运维模式。
- **明确不适用场景**：长时任务（超出平台执行时长上限）、需要常驻长连接的协议服务、有强顺序/强事务要求的复杂流程编排、大吞吐持续稳定负载（固定成本反而更优）、对毫秒级确定性延迟极敏感的同步核心链路、需要独占硬件或特定内核特性的场景。
- **与容器 / 微服务的关系**：Serverless 不是替代关系，而是**部署粒度与扩缩容策略的更激进一端**。容器是"部署单元 + 声明式编排 + 水平副本"，FaaS 是"部署单元 + 事件绑定 + 按需零副本"。二者共享同源技术底座（不可变制品、隔离运行时、声明式期望状态、自动伸缩），因此**混合架构是工程常态**：常驻容器承载核心同步链路与长连接服务，FaaS 承载事件密集、流量波动大、可容忍冷启动的外围能力。
- **四种落地形态**：公有云托管 FaaS、私有化 / 专有云 FaaS（OpenFaaS、Kubeless、Knative）、边缘 FaaS（把函数下沉到边缘节点，就近处理）、多云 FaaS（跨云统一运行时标准）。
- **责任边界话术（答题加分）**：Serverless 消除了"管理服务器"的工作量，但把风险转嫁为"依赖平台规范"——因此架构师必须从"设计部署拓扑"转向"设计事件契约、状态边界、超时与重试策略、失败隔离、流量护栏"，能力要求没有降低，只是换了战场。
- **与等保 / 责任共担的关系**：云上 FaaS 责任共担模型中，平台方负责物理设施、虚拟化、宿主机与运行时底座的安全，用户方仍负责函数代码、业务数据、身份权限、依赖组件与应用配置的安全，**责任不因"无服务器"而转移**。

### 2. 函数计算运行机制与冷启动治理

**定义**：函数计算的核心机制是"以调用为单位分配执行环境、用完即毁（可选保留一段时间以复用）"。一次请求的生命周期为：事件到达 → 鉴权与路由 → 调度分配执行环境 → 运行时初始化 → 加载用户代码与依赖 → 建立外部连接 → 执行函数 → 响应返回 → 环境回收或进入保温状态。**冷启动**就是其中"分配环境 + 运行时初始化 + 代码与依赖加载 + 连接建立"这一段未命中复用环境时的额外耗时。

**关键要点**：

- **冷启动的三段分解（定位问题的第一刀）**：① 平台冷启动（调度分配、实例创建、沙箱/隔离环境准备，通常几十至几百毫秒）；② 运行时冷启动（语言运行时启动，如 JVM 启动、Node 运行时引导，JVM 常常是最大头）；③ 应用冷启动（业务代码初始化、SDK 客户端构造、配置与密钥读取、数据库与缓存连接建立）。**三段的治理手段完全不同，必须先分段测量再优化**。
- **实例复用与保温机制**：平台通常保留已初始化实例一段时间（保温），后续调用直接复用，从而消除运行时冷启动。保温期越长、预置实例越多，冷启动越少，但**常驻实例产生常驻成本**，这是"延迟"与"成本"的直接权衡。
- **预置并发（Provisioned Concurrency）**：为关键函数提前保留一定数量的已初始化实例，调用时无需冷启动，代价是预置实例无论是否被调用都计费。**适合核心同步接口，不适合所有函数**——正确用法是只对关键路径上的少数函数开启，其余靠代码瘦身与保温复用。
- **内存与 CPU 的绑定关系**：多数 FaaS 平台按"内存规格"计费并按比例分配 CPU（如内存 2048MB 对应约 1 vCPU 级别的配额，具体比例以平台为准）。因此**调优的第一杠杆是内存**：内存给小了 CPU 被限流、函数变慢；内存给大了成本线性上升。正确做法是依据实际 CPU 使用曲线选择规格，而不是"给大点保险"。
- **应用侧冷启动优化的六个动作**：① 依赖包最小化（剔除无用依赖、避免把整个 SDK 打包进来）；② 延迟加载（把非关键依赖放到首次真正需要时再 require/import）；③ 运行时选型（JVM 需开启分层编译与 AppCDS/类数据共享，Node 需裁剪 polyfill）；④ **客户端单例化**（数据库连接池、HTTP 客户端、SDK 实例放在模块级全局变量中复用，避免每请求重建）；⑤ 密钥与配置缓存（不每次请求调用密钥管理服务）；⑥ 自定义运行时 / 定制镜像预置依赖（把依赖装在镜像层，避免每次下载）。
- **连接建立是被低估的冷启动来源**：跨网络访问数据库、缓存、第三方 API 时，TLS 握手 + 认证往返可能超过代码执行时间。治理手段包括**长连接保活**（平台支持的连接复用机制）、**同可用区同 VPC 部署**（降低网络 RTT）、**预热脚本在保温实例启动时预建连接**。
- **超时与并发模型**：必须显式设置函数超时（防止实例被长时间占用而拖垮平台或产生意外费用）；并发模型需按平台语义理解（单实例串行处理 vs 单实例多请求并发），它直接决定扩容时的实际吞吐。
- **指标化衡量**：不要只看"平均响应时间"，要看冷启动占比（冷启动请求数 / 总请求数）、初始化时长分解（平台通常能给出 Init Duration 与 Runtime Duration 分段）、首字节时延与总时延比值。

### 3. 事件驱动集成、函数编排与幂等一致性

**定义**：Serverless 架构的骨架是"事件源 → 事件总线 / 消息中间件 → 函数（订阅者）"。函数之间不直接调用，而由事件解耦；一次业务办理由多个事件触发多个函数顺序或并行推进。**由于消息中间件通常只保证"至少一次"投递，函数必须设计为幂等**，否则重复消费会造成重复扣费、重复发证、重复推送。

**关键要点**：

- **事件源五类**：消息队列消息、对象存储事件（上传即触发解析）、数据库变更捕获（CDC / 流）、外部 Webhook 与 API 网关、定时器 / 调度触发。每类事件源对应不同的可靠性与重放语义。
- **事件契约（Schema）设计**：事件包含事件标识（唯一 ID）、事件类型、事件版本、数据负载（业务数据）、发生时间、来源（生产者标识）、追踪标识（贯穿全链路）；**事件 Schema 必须版本化**，向后兼容演进，禁止随意改字段语义；破坏性变更必须新版本 + 双写 / 灰度。
- **幂等三件套**：① 唯一幂等键（业务单号 + 事件 ID 的组合，保证同一业务事件重复投递被识别）；② 去重存储（Redis / 数据库唯一索引，键值 + TTL 控制存储规模）；③ 状态机前置校验（处理前判断业务状态是否已推进到目标态，已推进则直接返回成功）。**幂等键必须由业务方提供或用事件 ID + 业务主键组合生成，不能用随机 UUID 重新生成**。
- **失败处理三件套**：重试策略（指数退避 + 最大次数 + 是否区分可重试异常与不可重试异常）、死信队列（多次失败后进入并人工/自动介入）、**补偿而非回滚**（Serverless 场景多用 Saga 补偿，因为流程已跨函数推进无法真正回滚）。
- **函数编排（编排型 vs 事件型）**：编排型（由一个编排器显式定义步骤、并行、选择、循环、异常处理，如 Step Functions 类能力）适合流程清晰、步骤有依赖的场景；事件型（事件驱动各订阅者自治）适合松耦合、可独立演进的场景。**选择判据：流程分支是否可预知、是否需要全局状态视图**。实践中两者可混用：主干用编排保证顺序，旁支用事件解耦。
- **状态管理三条铁律**：① 函数保持无状态，状态外置到数据库 / 对象存储 / 键值存储；② 长会话交互式场景不适合纯 FaaS，应回到常驻服务或采用会话状态外置方案；③ 跨函数的业务状态用**状态机**表达而不是散落在各函数内部，避免出现"状态只存在于某个函数的内存里"的不可恢复局面。
- **批处理与流处理落地**：定时触发 + 分片参数并行（注意幂等键要含分片与批次号）；事件时间与处理时间的区分、窗口（水位线）与迟到数据处理、背压机制。政务场景的批量政策推送、材料批量识别属于典型批处理。

### 4. Serverless 安全体系与合规责任划分

**定义**：Serverless 改变了攻击面与责任边界：平台接管了补丁管理与宿主机隔离，用户仍需对自己的代码、数据、权限、依赖与配置负责。安全设计的核心命题是"**最小权限 + 零信任访问 + 不可信输入 + 审计留痕**"，其中"执行角色（函数运行时的身份）"是新的关键管控点。

**关键要点**：

- **执行角色与最小权限**：每个函数绑定独立的执行角色，只授予该函数实际需要的资源权限（如只读某个对象存储桶前缀、只往某个主题投递消息）；**禁止使用拥有全量管理权限的共享角色**；高权限操作（部署、改密钥、扩缩容）由流水线或人工在控制面完成，不授予函数运行时。角色与函数的绑定关系需纳入配置审计。
- **密钥与凭证管理**：统一由密钥管理服务托管并由平台自动注入 / 轮转临时凭证，**禁止把密钥硬编码在代码、镜像层、环境变量明文或代码仓库中**；代码仓库启用推送前扫描，防止密钥泄漏；轮转周期与应急吊销流程明确。
- **应用层防护**：入参严格校验与类型约束、防命令注入与模板注入、**防服务端请求伪造（出站调用必须有目标白名单，函数不应能任意访问内网元数据服务）**、临时目录与文件系统隔离、依赖锁定版本并持续扫描漏洞、敏感字段在日志中脱敏、函数日志中严禁打印密钥与个人敏感信息。
- **网络隔离**：生产函数挂载到专有网络（VPC）内访问数据库与缓存；**默认关闭公网出站**，确需外呼的按域名 / 端口白名单放行；内网数据库不暴露公网入口；跨租户与跨环境的网络路径物理或逻辑隔离。
- **配额与抗滥用**：并发上限、调用频率上限、超时上限、内存上限是**防止被恶意触发耗尽配额与费用**的第一道闸门；对外暴露的 Webhook 入口必须做签名校验与防重放；对关键函数配置熔断与降级返回。
- **审计与合规**：函数调用日志、配置变更审计、权限变更审计需集中留存并设留存期限；**等保 2.0 云计算安全扩展要求**下，用户方在应用层承担的责任项包括身份鉴别、访问控制、安全审计、数据完整性与保密性、备份恢复；平台方的 IaaS / PaaS 侧措施需在合规材料中引用其已通过的测评结论。答题要点是**写清"哪一类责任在哪一方"**，而不是笼统写"云平台负责安全"。
- **常见攻击路径与对策**：伪造事件源注入（→ 事件签名与来源校验）、混淆代理（→ 严格的资源级权限而非账户级权限）、依赖投毒（→ 私有源与版本锁定）、资源耗尽（→ 配额与费用告警）、敏感数据泄漏（→ 日志脱敏与最小数据集）。

### 5. Serverless 成本模型、可观测性治理与架构决策方法

**定义**：Serverless 的成本模型是"按量计费 + 三要素定价"——调用次数、内存规格与执行时长的乘积、以及由此派生的并发规模。其成本结构与传统服务器完全不同：没有固定的服务器摊销，但**函数调用放大（一次业务触发 N 个函数）与冷启动开销（预置实例与更长执行时间）都会放大成本**。可观测性方面，短生命周期的执行环境使传统的"进程内埋点 + 长驻监控"模型失效，必须改用**以平台原生 Trace 为主干、以业务埋点为补充**的方式。

**关键要点**：

- **计费三要素与两个隐藏成本**：① 调用次数（一次用户操作触发 5 个函数即 5 次计费）；② 内存 × 时长（内存翻倍、时长翻长，费用近似四倍）；③ 由此派生的预置并发常驻成本。隐藏成本是**跨函数数据传递成本**（函数间反复调用、反复拉取大对象、数据在数据库与函数之间来回搬运）与**重复初始化成本**（每次冷启动都重新建连接、重新读配置）。
- **成本优化的五个动作**：按 CPU 实际曲线选内存规格（而不是凭经验给大）；**合并过碎的小函数**（减少调用次数与网络往返）；把大对象改用引用传递（传对象存储键而非文件内容）；引入缓存层降低下游调用；对可预测的稳定负载用常驻容器更省（**成本模型必须按负载曲线选择，而非按技术时髦程度选择**）。
- **可观测性三个维度**：指标（调用次数、错误率、限流次数、执行时长分布、冷启动次数与时长、并发数）；日志（结构化输出、集中采集、脱敏、按 trace ID 关联）；追踪（平台原生 Trace 上下文在事件与调用间传递，保证一次业务跨越 5 个函数仍可还原完整链路）。
- **Serverless 可观测性的三个特殊难点**：① 执行环境短命，进程内 Agent 不可靠；② 事件异步化后因果链跨越时间与进程，需要上下文传播；③ 冷启动使时长分布呈双峰，**只看平均值会掩盖问题，必须看分位数（P50 / P95 / P99）与冷启动单独维度**。
- **架构决策四步（ADR 化）**：① 业务特征画像（触发方式、峰谷比、时延敏感度、状态复杂度、合规约束、预算）；② 候选方案列举（常驻容器 / FaaS / 混合 / 事件驱动常驻服务）；③ 质量属性权衡（延迟、吞吐、可用性、成本、运维复杂度、可移植性、供应商锁定风险）；④ 决策与验证（选定方案 + 明确"什么指标在什么阈值下说明决策错了"，如"冷启动占比超过 30% 则回退为预置并发或常驻"）。
- **五个常见陷阱**：供应商锁定（事件源、身份、API 均为专有）、调试链路长（本地复现难，需提供本地模拟与统一事件格式）、冷启动不可控（平台调度与运行时版本变化会改变时延）、长任务限制（异步模式有时长与内存上限）、计费模型理解偏差（按日志量、出口流量、并发同时计费的项目容易被漏算）。
- **与 11-06 云原生主题的衔接关系**：容器与函数是同一技术谱系的两个端点——容器管"进程级声明式编排与弹性"，函数管"事件级按需实例化与零闲置成本"；选型不是二选一，而是**按业务特征做切分**。

## 案例分析题

**题目**：

某省"一网通办"平台承载全省政务服务事项申报，涉及 210 个部门系统。近期运维与业务部门反映三类问题：

1. **通知推送严重延迟**：平台每月 1 日、15 日为社保、医保、公积金集中申报截止日，8:00—10:00 消息推送量是平日的 25 倍。通知中心当前由 6 台虚拟机承载常驻的 Java 推送服务，平峰期 CPU 利用率不足 4%，高峰期消息积压最长 3 小时，事后统计发现约 18% 的推送消息最终超时作废，窗口期提醒未送达引发多起群众投诉。

### 问题 1 答案：适用性判别与总体架构建议

**（1）三类能力的适用性判别**

| 能力 | 结论 | 判别依据 |
|---|---|---|
| 通知推送（对外发送短信 / 站内信 / 邮件） | **适合 FaaS** | 事件驱动、峰谷比 25 倍、空闲期资源浪费严重、执行时间短（秒级）、对毫秒级确定性延迟不敏感但对积压时长极敏感；改后空闲时段可降至近零成本，且能瞬间应对流量洪峰 |
| 电子材料 OCR 与要素抽取 | **适合 FaaS（异步批处理 + 定时触发）** | 计算密集、执行时间可预测但耗时长、可按文件分片并行、无强状态依赖；但需注意长任务需走异步模式并做分片 |
| 人工补录插队调度 | **适合事件驱动调度** | 由"人工提交事件"触发独立处理流，不再需要手工重启服务切换任务，天然解决插队问题 |
| 办件状态流转 / 审批主链路 | **不适合 FaaS** | 强状态依赖、流程有严格顺序与事务一致性要求、涉及核心业务数据与资金类校验，宜保留常驻微服务（Spring Boot / 工作流引擎） |
| 统一身份认证与权限判定 | **不适合 FaaS** | 长连接、常驻状态、低延迟要求严格、涉及会话一致性 |
| 敏感数据落库与共享交换 | **谨慎使用** | 可用 FaaS 做前置脱敏与校验，但数据主权与授权逻辑应留在常驻服务，避免事件总线成为数据越权通道 |

**（2）总体架构建议：混合架构，按"业务特征"切分而非按"技术偏好"切分**

- **常驻层（微服务 / 容器）**：办件主流程引擎、统一认证、事项规则引擎、数据库访问代理与数据交换授权——承载强状态、有事务一致性要求的核心链路。
- **函数层（FaaS）**：消息推送、短信 / 站内信 / 邮件模板渲染与发送、OCR 与要素抽取、附件格式转换与校验、报表与统计、数据脱敏与前置校验、对外 Webhook 接入——承载事件密集、流量波动大、可容忍冷启动的外围能力。
- **事件总线（消息中间件）**：作为两层之间的解耦纽带，同时承担削峰填谷（吸收申报日洪峰）、重试与死信、多订阅者广播（一次材料入库事件同时触发 OCR、风险校验、通知三类函数）三项职责。**"一次业务动作触发一次事件、事件被 N 个函数各自订阅"，是混合架构下降低调用成本与耦合的关键设计。**
- **削峰填谷的直接收益**：申报日洪峰不再直接冲击常驻服务，而是先入消息队列由函数按自身并发能力消费，队列积压成为缓冲而非超时作废，可把推送及时率从 82% 提升到 99% 以上。

**（3）"无服务器"带来的实质变化**

- **责任转移而非消失**：服务器选型、操作系统补丁、运行时升级、扩缩容由平台承担；但"事件契约设计、状态边界划分、超时与重试策略、幂等与失败隔离、流量护栏与费用护栏、故障降级预案"这些**原由运维承担一部分、现在必须由架构师显式设计**的工作量上升。
- **能力重心迁移**：从"画部署拓扑、算机器配置"迁移到"定事件模型、定幂等键、定失败语义、定可观测指标"。
- **风险形态变化**：从"机器挂了就整机不可用"变为"单函数失败可隔离但级联依赖会放大"，**函数越多、扇出越大，级联故障与配额打满风险越高**，因此必须配套超时、重试上限、死信与降级。
- **合规责任不变**：应用层安全（代码、数据、权限、审计）仍由用户方全责，等保测评不会因为"用了云函数"而降低要求。

### 问题 2 答案：冷启动分段定位与分层治理

**（1）分段定位方法（先用数据定位段，再对症下药）**

- **第一步：区分"冷"与"不冷"**：平台运行指标中分别取冷启动请求（初始化时长字段大于阈值）与复用请求（命中保温实例）的响应时长分布；**若仅冷启动请求慢，则问题在初始化环节；若冷热请求都慢，则问题在函数体逻辑或下游依赖**，不要在冷启动上浪费时间。
- **第二段：平台冷启动**：看调度分配与实例创建耗时，通常在百毫秒级；该段一般属于平台内部机制，可通过**跨可用区调度规避、避免冷可用区、私有网络端到端同可用区部署**改善，用户侧可控空间有限。
- **第三段：运行时冷启动**：重点看语言运行时启动时长；**JVM 平台的函数，冷启动大头往往是 JVM 启动 + 类加载**，治理手段为开启分层编译（快速启动但运行期稍慢）、使用类数据共享（CDS / AppCDS）、精简依赖包、避免在静态初始化中做重活。
- **第四段：应用冷启动**：看初始化时长中的业务初始化部分，重点排查三类"隐形重活"：① **每次调用都新建数据库连接 / HTTP 客户端 / SDK 实例**（应改为模块级单例 + 连接池 + 长连接保活）；② 每次调用都从密钥管理服务读密钥、每次都拉取配置中心配置（应缓存 + 设置合理过期 + 支持热更新）；③ 依赖包中包含大体积无关 SDK 造成加载耗时（应延迟加载 / 裁剪）。
- **第四步：外部连接建立耗时**：把"发起请求到收到首个字节"的网络耗时单独剥离，识别 TLS 握手、跨可用区路由（应确保函数与数据库、缓存、消息队列同可用区同 VPC）、长连接保活未开启等。
- **定位结论表**：平台冷启动（用户侧基本不可控，仅能规避）→ 运行时冷启动（换运行时 / 开启分层编译 / 类数据共享）→ 应用冷启动（依赖瘦身、延迟加载、单例化、缓存密钥与配置）→ 连接建立（长连接、同可用区、预热脚本）。**必须先测出四段的量级占比，再决定投入方向**，否则容易把时间花在只占 5% 的环节上。

**（2）分层治理方案（自上而下四层）**

- **第一层：架构层——削峰与错峰**
  - 洪峰流量先入消息队列，函数按自身并发上限消费，把"瞬时并发"转化为"排队等待"，**队列长度成为可观测、可控的缓冲**。
  - 申报截止日的前一天做"预生成与预渲染"：模板渲染结果提前算好并缓存到对象存储，高峰期只做发送动作；同理，提示类消息提前一天排程。
  - 区分优先级通道：截止提醒类消息走独立的高优先级队列与独立函数配额，**避免被普通通知淹没**。
  - 引入"过期时间"语义：过期消息直接丢弃并记录原因，不再无限堆积。
- **第二层：平台配置层——预置并发与保温策略**
  - 对关键路径函数（推送主函数）开启**预置并发**，按高峰预估并发量配置，代价是预置实例无论是否被调用都计费；建议仅覆盖高峰窗口的思路（定时预置 + 高峰后释放）比全天常驻更经济。
  - 调整保温时长与保温实例数，把"复用率"作为核心指标跟踪；**保温实例数不足是复用率低的直接原因**。
  - 提高单实例并发度：若单实例可并发处理多请求，则相同并发需求所需实例数下降，冷启动被摊薄；但单实例并发过高会推高延迟，**必须用 P99 而非平均值评估**。
  - 升级运行时版本以获得更快的初始化（平台通常在版本发布说明中给出冷启动改善幅度）。
- **第三层：代码层——应用侧冷启动六动作**
  - 依赖瘦身与延迟加载；JVM 侧开启分层编译与类数据共享；客户端单例化与连接池；密钥配置本地缓存（带过期与热更新）；把非必要初始化移出模块加载阶段；**把"读取全局配置、查数据库、请求第三方接口"这类重活从每次调用改为定时预热 + 缓存**。
- **第四层：观测层——用指标闭环验证**
  - 核心指标：冷启动请求占比、冷启动初始化时长 P95、保温实例复用率、并发数、错误率、限流次数、单次业务调用链上的函数总时长。**目标是让"高峰 5 秒"回落为"高峰 P95 < 800 毫秒、99% 的通知在截止前送达"**。

**（3）预置并发与代码瘦身的适用场景与代价对比**

| 维度 | 预置并发 | 代码瘦身（依赖裁剪 / 延迟加载 / 单例化 / 运行时调优） |
|---|---|---|
| 解决的问题 | 消除"平台冷启动 + 运行时冷启动"，即实例准备与语言运行时启动 | 消除"应用冷启动"，即业务初始化与依赖加载；并降低单次执行的资源消耗 |
| 适用场景 | **少量关键路径函数、时延敏感、调用量可预估**（如推送主函数、支付回调）；不适合长尾低频函数（预置常驻成本远超收益） | **所有函数**，尤其是长尾低频函数（无预置时靠代码瘦身把冷启动压到可接受范围） |
| 成本代价 | 常驻实例按秒或按并发配额计费，**不调用也计费**；并发配得过高造成浪费，配得过低仍会冷启动；本质是"用钱买时间" | 不产生额外直接费用，反而因单次执行更快、内存更省而**降低成本**；代价是投入研发与治理时间，且需持续维护防止依赖回涨 |
| 风险 | 若平台调度或运行时版本变化导致初始化变慢，预置实例也受影响；配额被平台限流时无法保证 | 优化不当可能破坏功能正确性（延迟加载引发空指针、缓存过期导致读到旧配置），必须有测试与回滚机制 |
| 组合用法 | 对 3—5 个关键函数开启预置并发，其余函数靠代码瘦身 | 全部函数都做，作为基础工程规范纳入代码评审与流水线门禁 |

**结论**：**代码瘦身是基础盘，预置并发是尖峰武器**。正确顺序是先把代码层与架构层做到位，再对确实无法满足时延要求的少数函数用预置并发补位，而不是一上来就给所有函数开预置并发。

### 问题 3 答案：事件契约、幂等、失败处理与状态管理

**（1）事件契约（Schema）治理**

- **统一事件信封结构**：事件标识（全局唯一，用于去重与追踪）、事件类型（业务语义）、事件版本、数据负载、发生时间（业务事件产生时间，非处理时间）、生产者标识（来源系统）、追踪标识（贯穿整条链路）、幂等键（业务单号 + 事件标识组合）。
- **版本化与兼容策略**：事件 Schema 纳入版本管理；新增字段必须可选且带默认值；**禁止改变已有字段语义**；破坏性变更必须发布新版本事件类型，旧版本消费者保留过渡期；采用"生产者双发（旧版本 + 新版本）→ 消费者逐步迁移 → 下线旧版本"三步走。
- **契约即代码**：事件 Schema 用结构化定义文件维护并纳入版本库，**在流水线中做兼容性校验**（新增必填字段、字段类型变更、字段删除会导致不兼容，直接阻断合并）；生产者与消费者以同一份契约为准。
- **敏感数据最小化**：事件负载中不直接放身份证号全文等敏感字段，改为**引用（指向数据库中的记录标识）**，需要时由消费方凭权限回查，从源头上避免"消息总线成为数据泄露面"。

**（2）幂等机制**

- **幂等键设计**：由**业务主键 + 事件标识**组合生成（如"办件号 + 材料ID + 动作类型"），保证同一业务动作的重复投递被识别；**严禁使用随机 UUID**，否则重复投递会生成不同键，幂等失效。
- **去重存储**：Redis 去重键 + TTL（覆盖业务允许的最长重试窗口即可，TTL 过长浪费存储、过短会失效），或数据库唯一索引（强一致、代价较高，适合核心落库动作）。
- **状态机前置校验**：处理前读取业务状态，若已推进到目标态则直接返回成功（幂等第二道防线）；**这是防止"重复入库、重复发证"最有效的手段**，因为它基于业务事实而非技术痕迹。
- **写操作的最终防线**：落库时用唯一约束或乐观锁（版本号）保证"重复插入"在数据库层被拒绝；**应用层判断与数据库约束必须双保险**，应用层判断可能被并发穿透。
- **"通知发了两遍"的专项治理**：发送前先落"发送记录"（唯一键 = 业务标识 + 通知类型 + 通知轮次），再调发送渠道；**若外部渠道无幂等能力，则只能靠"先落记录再发送 + 记录状态机"来实现"至多一次"的效果**，并接受极端情况下"已发但记录未落"的丢失风险（可通过对账补偿）。
- **去重与业务的边界**：**"恰好一次"在分布式系统中不可保证**，工程目标应是"至少一次投递 + 业务效果恰好一次"，靠幂等与状态机实现效果层面的恰好一次。

**（3）失败处理**

- **重试策略**：指数退避 + 抖动（避免重试风暴）；区分**可重试异常**（网络超时、限流、依赖暂时不可用）与**不可重试异常**（参数非法、业务规则不满足、权限不足），后者直接进入死信，避免无效重试放大成本。
- **重试上限与熔断**：单函数重试次数上限（如 3 次）+ 退避时长上限；依赖方熔断防止级联；**函数调用链的级联深度要设上限**，否则一个慢依赖会沿扇出放大成雪崩。
- **死信队列**：多次失败后进入死信队列，保留原始事件与失败原因、失败次数、时间；提供人工重放与自动重放两种入口，重放同样走幂等机制。
- **超时与隔离**：每个函数设置超时上限；**"部分材料处理到一半状态丢失"的根因通常是超时被中断后状态未落库**，对策是分步落状态（收到即落"处理中"、完成落"已完成"），并设计**断点续跑**（按材料 ID 跳过已完成项）。
- **补偿优先于回滚**：跨函数流程一旦推进到外部系统（如已发短信、已写库），无法真正回滚，只能补偿（发冲正通知、标记冲正记录）；因此在设计期就要识别"不可逆动作"并为其设计补偿动作与人工兜底。

**（4）状态管理**

- **函数无状态，状态外置**：业务状态统一存放在数据库（或专用状态存储），函数实例内存中不保留跨调用状态；函数重启、实例回收不影响业务进度。
- **状态机表达流程**：材料处理状态建议为"已接收 → 识别中 → 抽取完成 → 校验通过 / 校验驳回 → 已入库"，每个状态迁移都落库并记录操作者与时间戳，**任何时刻都能从数据库还原完整进度**，这是解决"处理到一半状态丢失"的根本办法。
- **分片与并行**：批量任务按材料 ID 哈希或范围分片，每个分片是一个独立的可重入单元；分片任务的状态以"分片号 + 批次号"为幂等键的一部分；**批次号必须唯一**，否则重跑批次会与历史批次混淆。
- **定时任务转事件**：把"夜间批处理 + 人工插队"改为"定时事件 + 人工事件"，两类事件进入同一队列但用不同优先级；**任务调度由平台的事件驱动能力承担，取代手工重启切换任务的做法**。
- **状态一致性与可观测**：状态迁移写入审计日志（谁在何时把状态从 X 改到 Y），配合追踪标识可还原"一条材料在 5 个函数间的完整流转链路"，这既是排障能力，也是等保审计的证据链。

### 问题 4 答案：安全整改与责任划分

**（1）三条整改问题的具体措施**

**问题一：执行身份权限过大**

- **执行角色最小化**：每个函数绑定独立执行角色，权限精确到资源级而非账户级（例如只允许读取对象存储中 `tmp/ocr/` 前缀、只允许向 `topic.ocr-result` 投递消息、只允许查询 `ocr_task` 表的特定字段）。
- **拆分角色类型**：只读角色（读配置、读对象）、写入角色（写结果、写日志）、管理角色（部署、扩缩容、改密钥）分离，**函数运行时只持前两者，管理角色只授予流水线与人工操作者**。
- **禁止共享高权限角色**：禁止新建"管理员"类角色并挂到多个函数；角色与函数的绑定关系纳入配置基线并定期审计（清单化：函数 → 角色 → 权限项 → 资源范围）。
- **权限收敛技术手段**：启用执行角色的权限边界（Permissions Boundary）做二次约束；对能访问敏感数据源的函数额外施加标签级访问条件；跨账号访问必须显式授权角色而非全通。
- **高危操作外移**：创建 / 删除函数、修改环境变量与密钥、开启公网访问、调整配额与预置并发等操作，**全部移出函数运行时可执行范围**，通过控制面流水线 + 审批完成。

**问题二：日志留存不足**

- **集中化采集**：函数运行日志（平台 stdout / stderr）与业务日志统一接入日志中心，禁止写入函数本地文件系统（实例回收即丢失），也禁止长期写入对象存储形成"影子日志"。
- **留存期限对齐合规要求**：按等保与行业主管部门要求设定留存期限（通常不少于 6 个月，涉及重要业务与个人信息处理的按更长要求），**冷热分层存储**（热层 30 天内可全文检索，冷层长期归档并保证可解密调阅）。
- **完整性保护**：日志启用传输加密、访问控制（审计日志只有审计角色可读且只增不改）、定期备份；**防止攻击者通过"删日志"抹除痕迹**，日志账号与业务账号分离。
- **完整性补充**：同时留存**调用链审计**（调用者身份、函数名、触发事件标识、请求参数摘要、返回码、耗时）与**配置变更审计**（谁在何时改了函数代码、内存、超时、配额、角色绑定、密钥引用），二者结合才能还原"发生了什么"与"是谁改的"。
- **检索与告警**：设置关键审计事件的实时告警（角色权限变更、公网开启、密钥读取异常、批量导出日志），并定期做日志覆盖度核对（是否所有函数都在采集、是否有静默失败的采集通道）。

**问题三：个人敏感信息出现在日志中**

- **日志内容分级与白名单**：默认日志只记录"标识 + 结论 + 耗时"，**不记录请求体与响应体**；确需记录时按字段白名单，并建立"日志字段登记台账"（谁、什么字段、为什么必要、保存多久）。
- **脱敏与不可逆处理**：身份证号、手机号、银行卡号、姓名、住址、生物特征等按规则脱敏（保留前 3 后 4 或哈希），**日志中永不出现完整值**；脱敏在日志 SDK 的输出层统一实现，避免依赖各业务方自觉。
- **密钥与凭证绝对隔离**：日志中禁止出现密钥、令牌、密码、连接串；一旦发现密钥出现在日志中，按安全事件流程处置（立即吊销并轮换密钥，清理历史日志，排查该密钥对应的调用记录）。
- **栈与异常信息治理**：异常堆栈中可能携带 SQL 参数、请求 URL 与响应体，须在日志框架层做过滤与截断；对外错误返回只返回错误码与追踪标识，不返回内部细节。
- **链路追踪同步治理**：Trace 属性中的业务字段同样受脱敏规则约束，**不要把敏感字段直接作为 Trace 标签**，否则在链路平台上扩散。
- **存量治理**：对历史日志做一次抽样扫描（正则匹配身份证 / 手机号模式），发现即清理并追溯问题代码；对涉及个人信息的分析类日志，须有合法依据与告知，且纳入个人信息保护影响评估。

**（2）等保责任共担模型中的责任划分**

- **平台方（云服务商）责任**：物理机房与基础设施安全（电力、温控、防火防水）、虚拟化与hypervisor 安全、宿主机操作系统安全与补丁、云平台自身组件安全、**云服务管理平台的安全（管理面与数据面隔离）**、IaaS / PaaS 层面的访问控制与安全审计、**提供符合国家标准的云服务并配合完成等保测评（提供其已测评结论作为引用材料）**、提供安全配置基线与加固建议。
- **用户方责任（云上应用系统）**：应用代码安全（无后门、无漏洞、及时修复）、**身份鉴别与访问控制（含执行角色与权限最小化）**、应用层数据安全（分类分级、加密、脱敏、完整性保护）、**安全审计与日志留存（应用与配置变更审计）**、入侵防范与恶意代码防范、**备份与恢复（含业务数据备份与应急响应）**、个人信息保护与合规（告知同意、最小必要、影响评估）、供应链安全（依赖组件漏洞治理）、**安全管理制度与人员管理**。
- **判定原则（答题要点）**：**"平台做过等保"不等于"我的应用过了等保"**。用户方必须针对应用层控制项逐条自查并提供证据，包括：应用架构与部署文档、权限矩阵与角色清单、审计日志样本与留存策略、数据加密与脱敏方案、漏洞扫描与修复记录、应急演练记录、备份恢复演练记录、个人信息保护制度与评估报告。测评机构在云上场景采取"以平台方测评结论 + 用户方应用层自查证据"组合取证的方式。
- **答题通用表述模板**：控制项 → 责任方 → 技术措施 → 证据材料（截图 / 日志 / 报告 / 记录）→ 整改闭环。四列缺一不可，尤其是"证据材料"这一列，直接决定得分。

### 问题 5 答案：成本模型、可观测性、架构决策记录与锁定规避

**（1）成本测算模型**

- **计费三要素**：总费用 ≈ Σ（调用次数 × 单次调用基础费）+ Σ（并发实例数 × 预留时长 × 实例费率）+ Σ（执行时长 × 内存规格单价）+ 附加项（出站流量、日志量、对象存储、消息队列、数据库、第三方 AI 服务调用）。
- **单次业务成本放大模型**：设一次业务动作触发 K 个函数，其中 J 个需要跨函数传递数据，则单次业务成本 = K × 单函数基础调用费 + J × 数据传递成本（函数间调用、重复拉取大对象、数据库往返）。**K 越大放大越严重，这是"把函数切得太碎"的核心代价。**
- **峰值与均值成本**：FaaS 成本取决于峰值并发而非平均值，因此必须用**并发模型**（到达率 λ 与平均服务时间 S，估算并发数 ≈ λ × S，考虑峰谷比 25 倍与批量到达特性）而非日均请求量来测算。
- **预置并发成本**：预置实例数 × 常驻时长 × 实例费率，须单独列为成本项并给出优化（仅高峰窗口预置、按时段启停）。
- **成本对照测算**：与常驻方案对比时，常驻成本 = 峰值所需实例数 × 实例单价 × 运行时长（受最小副本与资源规格约束）；FaaS 成本 = 调用量 × 单价 + 预置成本。**结论应按负载曲线给出**：峰谷比大、负载波动剧烈 → FaaS 显著更省；负载平稳且持续高水位 → 常驻更省（无冷启动、无调用次数税）。
- **敏感性分析**：分别测算"调用次数增长 3 倍""内存规格提升 50%""预置并发翻倍"对总成本的影响，识别成本敏感因子并优先治理（通常调用次数与数据传递成本是最大敏感项）。

**（2）成本优化措施**

- **减少调用次数 K**：合并职责过碎的小函数；一次事件处理完多个动作后再发事件（"事件合并 / 批量投递"）；用消息队列批量消费替代逐条触发。
- **降低单次执行成本**：按 CPU 实际曲线选内存规格（内存与时长近似相乘，规格给大一档成本翻倍）；压缩依赖包与镜像体积（影响初始化与内存占用）。
- **消除数据搬运成本**：传引用而非传数据（大对象放对象存储，事件里只放键）；函数间避免"查库→写库→再查库"的往返；引入缓存层降低下游调用次数；结果聚合后再落库。
- **降低重复初始化成本**：客户端单例化、连接复用、配置与密钥缓存（既降成本又降冷启动）。
- **配额与费用护栏**：设置并发上限、超时上限、调用频率上限、预算告警与自动熔断；**这是防止"函数被错误调用或循环触发"导致费用失控的必要闸门**，也是等保与财务合规的要求。
- **定期成本复盘**：按函数维度出成本报表，识别"调用量高但价值低"的函数并下线或合并；用单位业务量成本（如每万次推送成本）替代总量作为考核指标。

**（3）面向 Serverless 的可观测性建设要点**

- **追踪优先**：以平台原生 Trace 为主干，确保一次业务跨越多个函数、跨消息队列、跨外部依赖时上下文不丢失（追踪标识随事件负载透传并自动注入下游调用）；这是 Serverless 场景**唯一可靠的跨边界串联手段**。
- **指标体系六类**：调用量与并发数、错误率与限流率、执行时长分布（**必须看 P50 / P95 / P99，不得只看均值**）、冷启动次数与初始化时长、**保温实例复用率**（反映冷启动治理成效）、成本指标（单位业务成本、预置实例常驻时长占比）。
- **日志体系**：结构化 + 追踪标识关联 + 字段白名单 + 脱敏 + 集中采集 + 长留存；日志写入本地文件不可用（实例回收即丢）。
- **告警与 SLO**：为核心函数定义 SLI（如"99% 的推送在触发后 30 秒内进入发送通道"）与 SLO，配合错误预算；**冷启动占比、实例复用率、队列积压深度**应作为独立告警维度（它们是容量与成本的先行指标）。
- **平台绑定风险的可观测对策**：采集逻辑尽量下沉到业务侧埋点（不依赖厂商专有的可观测产品），指标暴露为开放格式（如 Prometheus 拉取格式），保证未来更换平台时观测数据可迁移。
- **异常与混沌**：定期做故障注入（模拟下游超时、限流、部分实例不可用、消息重复投递），验证超时、重试、熔断、降级、幂等是否真的生效——**Serverless 场景的"自动扩容"会掩盖依赖侧故障，必须用混沌工程验证隔离能力**。

**（4）架构决策记录（ADR）**

**标题**：某省"一网通办"外围能力采用 FaaS + 常驻容器混合架构的架构决策

- **背景与问题陈述**：推送与材料处理存在峰谷比 25 倍、闲置资源浪费明显、运维人力紧张；同时核心审批链路对状态一致性与事务性要求高，需要保留常驻服务。需要在"全量常驻""全量 FaaS""混合"三者中决策，并解决供应商锁定与国产化适配的后续迁移问题。
- **决策依据（事实与约束）**：① 峰谷比实测 25 倍，忙时 2 小时完成当日 80% 推送量；② 平峰 CPU 利用率 4%，按常驻配置存在大量闲置；③ 推送与 OCR 无强状态、事件驱动特征明显；④ 审批主链路有严格顺序与事务一致性要求；⑤ 运维团队 6 人（其中 4 人用于日常运维）；⑥ 等保三级对执行身份、日志留存、敏感信息有明确整改要求；⑦ 明年须完成国产化数据库与中间件适配；⑧ 预算上限与单位推送成本目标。
- **候选方案**：方案 A 全量常驻微服务（扩容及时性差、闲置成本高、发布重）；方案 B 全量 FaaS（核心链路状态与事务难以承载、长任务受限、锁定风险最高）；方案 C 混合架构（外围能力函数化 + 核心链路常驻 + 事件总线解耦）；方案 D 常驻 + 独立工作流引擎（可满足核心链路，但外围能力闲置问题未解决）。
- **质量属性权衡**（按优先级排序）：

| 质量属性 | 方案 A | 方案 B | 方案 C | 方案 D |
|---|---|---|---|---|
| 峰值承载及时性 | 差（需提前扩容） | 优（瞬时扩缩） | 优 | 中 |
| 稳态成本 | 高（按峰值配常驻） | 低 | 低（外围）/中（核心） | 中高 |
| 状态与事务一致性 | 优 | 差 | 优（核心链路） | 优 |
| 运维复杂度 | 中高（需手工扩缩） | 中（平台托管但需可观测与配额治理） | 中 | 高 |
| 厂商锁定风险 | 低 | 高 | 中（可通过开放格式缓解） | 中 |
| 国产化适配难度 | 低 | 高 | 中 | 中 |
| 端到端时延确定性 | 优（无冷启动） | 差（冷启动） | 分域不同 | 优 |
| 可观测与排障难度 | 中 | 高（链路跨函数） | 中高 | 中 |

- **决策结论**：采用**方案 C 混合架构**。外围能力（推送、OCR、抽取、脱敏、通知模板）函数化并置于事件总线之上；核心审批与认证保留常驻微服务；决策依据是"按业务特征切分"而非"技术偏好统一"。
- **验证指标（明确什么情况下认为决策错了）**：① 推送高峰 P95 响应 < 800 毫秒且 99% 消息在截止前送达；② 冷启动请求占比 < 10%；③ 单位推送成本较原方案下降 ≥ 40%；④ 核心审批链路事务一致性零异常；⑤ 等保三条整改项 100% 闭环且通过复测；⑥ 国产化适配后核心功能回归通过率 100%，且事件 Schema 与接口规范保持不变。若连续两个月冷启动占比 > 30%、或成本未降反升 > 10%、或出现跨函数级联故障未被及时隔离，则启动复审并考虑把关键路径函数回退为常驻服务。
- **替代方案与后果**：不采用全量 FaaS 的理由是核心链路的状态与事务要求；不采用纯常驻的理由是峰谷比与闲置成本；不采用方案 D 的理由是未解决外围能力闲置问题。接受的后果是：需要维护"事件契约 + 两种运行时形态"两套规范，运维团队需补充函数式开发与云原生可观测能力培训。

**（5）供应商锁定规避与国产化适配路径**

- **接口与契约标准化**：事件 Schema 用开放标准定义并版本化，**不让任何厂商专有字段进入契约**；对外 API 用 OpenAPI 描述；所有云服务调用封装在统一的"平台适配层"（适配器模式）之后，业务代码只依赖内部抽象接口。
- **运行时可移植**：容器化交付 + 镜像与函数产物双形态准备（同一份业务逻辑既能打包成镜像，也能打包成函数包），配合 Knative / OpenFaaS 等开放运行时实现"一套代码、多云可跑"。
- **避免专有存储与专有消息格式**：数据库访问通过标准 SQL / ORM 抽象，不使用云厂商专有存储特性作为核心依赖；消息格式统一为自描述 JSON / Protobuf，不用专有序列化；日志与指标导出为开放格式并可自建采集。
- **身份与密钥中立**：密钥不写入代码或镜像，使用标准密钥接口读取，在切换平台时只需替换密钥后端实现；避免绑定厂商 IAM 模型，建立平台内部统一身份层。
- **分阶段国产化适配路径**：第一阶段（1—2 个月）——完成接口抽象层与依赖清单盘点，识别所有云厂商专有依赖并逐项列出替代方案；第二阶段（2—4 个月）——在测试环境完成国产化数据库与消息队列的适配改造，采用双写与影子流量验证数据一致性，业务逻辑零改动为验收标准；第三阶段（4—5 个月）——生产环境按模块灰度切换，每批次保留旧链路回退窗口，以流量比例与错误率作为放量门槛；第四阶段——完成旧链路下线与依赖清理。
- **关键约束**：**国产化替换过程中不改变事件 Schema 与对外接口规范**（这是保证可迁移性的底线），任何需要变更契约的替换需求一律先做兼容性评估与版本升级；**迁移过程中不得以"临时改造"绕过抽象层**，否则抽象层会在压力下被腐蚀，锁定风险反而加深。
- **持续治理**：建立架构决策委员会与 ADR 制度，每季度做一次锁定度体检（统计专有 API 调用占比、专有中间件使用数、开放格式覆盖率），设定"专有依赖占比逐年下降"的目标并纳入技术债管理。

## 踩分要点

1. **判别题必须逐项给出理由**，不能只写"适合/不适合"。每个能力都要扣到"触发方式、峰谷比、状态依赖、时延敏感度、任务时长"中的具体特征，这是阅卷按点给分的基础。
2. **"无服务器"不等于"没有服务器"**：答题时必须点明是"运维责任转移给平台方"，服务器由平台托管但物理上依然存在，这是概念题的判分点。
3. **混合架构是标准答案形态**：不要写"全量 FaaS"或"全量常驻"，正确答案是"按业务特征切分"，并明确划出常驻层（核心主流程、认证、事务一致性）与函数层（推送、OCR、脱敏、Webhook）的边界。
4. **事件总线的三个职责要写全**：削峰填谷、重试与死信、多订阅者广播。只写"解耦"会丢分。
5. **冷启动必须分段**：平台冷启动 / 运行时冷启动 / 应用冷启动 / 连接建立。只写"用预置并发"而不分段定位，丢"分析过程"分。
6. **预置并发与代码身形的适用场景与代价要成对出现**：预置并发 = 用钱买时间、常驻计费、只适合关键路径少量函数；代码瘦身 = 不额外花钱、降本、适合所有函数。结论句"代码瘦身是基础盘，预置并发是尖峰武器"是加分句。
7. **幂等键的来源必须写对**：业务主键 + 事件标识组合，**严禁随机 UUID**。这是高频踩坑点。
8. **"恰好一次"不可保证**：正确表述是"至少一次投递 + 幂等/状态机实现业务效果恰好一次"，能写出来是加分项。
9. **死信队列、重试分类（可重试/不可重试）、补偿优先于回滚** 三点缺一不可。
10. **状态机表达流程**：材料处理的每个状态迁移都要落库并带时间戳，才能解决"处理到一半状态丢失"，并能还原完整流转链路。
11. **执行角色最小化**必须写到"资源级权限"而不是"账户级"，并把"管理类高危操作移出函数运行时"作为要点——这是等保整改题的采分核心。
12. **日志三条**：集中采集不留本地（实例回收即丢）、留存期限与合规对齐、完整性与防删（审计账号与业务账号分离）。
13. **敏感信息**：默认不记录请求体与响应体、字段白名单、统一脱敏在日志层实现、堆栈异常过滤、Trace 属性同样脱敏。**"日志 SDK 统一实现脱敏而非依赖开发自觉"是高分表述**。
14. **责任共担答题模板**：控制项 → 责任方 → 技术措施 → 证据材料 → 整改闭环。**"平台做过等保不等于应用过了等保"** 必须写出来。
15. **成本模型要含"调用次数放大因子 K"和"预置实例常驻成本"**，并按负载曲线给结论（峰谷比大 → FaaS 省；平稳高水位 → 常驻省）。
16. **成本优化要落到可执行动作**：合并碎函数、传引用不传数据、依赖瘦身、按曲线选内存规格、配额与预算告警。
17. **可观测性**：以平台原生 Trace 为主干；执行时长看 P95/P99 不看均值；冷启动占比与实例复用率作为独立指标；日志脱敏与集中采集。
18. **ADR 四要素必须齐**：决策依据（事实数据）、候选方案（≥3 个且含被否方案）、质量属性权衡（带优先级排序的表格）、验证指标（**含"什么情况下决策错了"的反向阈值**）。缺验证指标是常见失分点。
19. **锁定规避的落地抓手**：统一适配层、开放标准契约（事件 Schema 不含厂商专有字段）、开放格式日志与指标、密钥后端可替换、数据库与消息不依赖专有特性。
20. **国产化路径要给阶段性时间与验收标准**（双写、影子流量、灰度、回退窗口），并写明底线约束"不改变事件 Schema 与对外接口规范"。
21. **禁止用临时改造绕过抽象层**，否则抽象层被腐蚀、锁定加深——这是有经验的答法。
22. **量化目标**：全文要出现可度量的指标（峰值 P95 < 800 毫秒、冷启动占比 < 10%、单位推送成本下降 ≥ 40%、推送及时率 99% 以上），不能只有定性描述。
23. **答案结构**：每个问题先给结论性判断，再给"分点展开 + 表格 + 分阶段路线"，最后可加一句总结。阅卷时间有限，结论前置能提高得分效率。
24. **常见失分**：把 Serverless 说成"不需要运维"（错，责任转移不是消失）；把幂等说成"用消息队列保证不重复"（错，MQ 通常是至少一次投递）；把冷启动全部归因于"平台慢"（错，必须分段）；把预置并发说成"越多越好"（错，常驻计费）。

## 记忆口诀

1. **无服务器三形态**：FaaS 交代码，BaaS 交数据，SaaS 交配置——**责任从管操作系统一路降到管配置，但应用层安全责任一分不减**。
2. **判据六条口诀**：事件触发、峰谷比高、任务短、能拆分、有空闲、不怕迁——**六条全中才上 FaaS，缺一就要慎重**。
3. **冷启动四段口诀**：**平台分配、运行时启、依赖加载、连接建**——先测四段占比，再定优化方向，**别把时间花在只占 5% 的环节**。
4. **运行时冷启动头号元凶**：**JVM 启动**——分层编译加类共享，能砍一大半。
5. **应用冷启动三宗罪**：**连接重连、密钥重读、依赖加载**——单例化、缓存化、延迟加载，各治一宗。
6. **预置并发本质口诀**：**用钱买时间，常驻计费，只给关键**——长尾函数开了就是浪费。
7. **代码瘦身本质口诀**：**不花钱还降本，人人可用**——基础盘永远是代码，不是预置。
8. **组合结论句**：**代码瘦身是基础盘，预置并发是尖峰武器**。
9. **幂等键口诀**：**业务主键 + 事件标识，绝不随机 UUID**——随机键一生成，幂等当场失效。
10. **恰好一次口诀**：**至少一次投递 + 幂等状态机 = 效果恰好一次**——分布式做不到消息恰好一次。
11. **状态三铁律**：**函数无状态、状态外置、状态机表达**——别把进度存在某个函数的内存里。
12. **失败三件套**：**重试有上限、失败进死信、跨域用补偿**——回滚在 Serverless 里几乎不可能。
13. **死信两入口**：**人工重放 + 自动重放**——重放也必须走幂等，否则重放一次错一次。
14. **事件信封八要素**：**事件 ID、类型、版本、负载、时间、来源、追踪、幂等键**。
15. **契约演进三步**：**生产者双发、消费者迁移、旧版下线**——破坏性变更必发新版本。
16. **敏感数据最小化**：**事件里放引用不放全文**——总线不是数据泄露面。
17. **执行角色口诀**：**读、写、管三角色分离，管理权移出运行时**——最小权限要到资源级，不能到账户级。
18. **密钥铁律**：**代码不写、镜像不烘、明文不存、临时凭证自动轮**。
19. **日志三不**：**不写本地文件、不记请求响应、不存完整敏感值**——本地文件随实例回收即丢。
20. **日志留存口诀**：**热层快查、冷层长存、审计只增不改**——账号分离防删痕。
21. **脱敏落点**：**脱敏统一放日志输出层，不靠开发自觉**——靠自觉的规范必然破。
22. **异常治理**：**堆栈会带参数，异常要过滤截断**——对外只回错误码与追踪号。
23. **Trace 脱敏**：**追踪标签同样受管**——别把敏感字段直接塞进链路标签。
24. **等保金句**：**平台过了等保，不等于应用过了等保**——应用层控制项逐条自查举证。
25. **举证四列**：**控制项、责任方、措施、证据**——没证据的自查等于没做。
26. **责任边界**：**平台管设施与底座，用户管代码与数据**——责任共担是分界，不是免责。
27. **配额三闸**：**并发上限、超时上限、调用上限**——防止被刷爆配额与费用。
28. **成本三要素**：**次数、内存、时长**——内存翻倍时长翻长，费用近乎四倍。
29. **放大因子 K**：**一次业务触发 K 个函数，成本就乘 K**——函数切太碎是隐形浪费。
30. **数据搬运**：**传引用不传数据**——大对象放存储，事件里只放键。
31. **选型口诀**：**峰谷比大用函数，平稳高水位用常驻**——按负载曲线选，不按时髦选。
32. **敏感因子**：**次数与搬运是成本大头**——优先治理这两项。
33. **观测主干**：**平台原生 Trace 为主，业务埋点为辅**——跨函数串链只能靠上下文透传。
34. **时长看分位**：**只看均值会骗人**——P95 / P99 加冷启动单独维度才看得清。
35. **两个先行指标**：**冷启动占比、实例复用率**——它们是容量与成本的领先信号。
36. **混沌验证**：**自动扩容会掩盖依赖故障**——必须注入超时、限流、重复投递来验证隔离能力。
37. **ADR 四要素**：**依据、候选、权衡、验证**——缺"验证指标"就是没做完决策。
38. **反向阈值**：**写清什么情况下决策错了**——如冷启动占比 > 30% 即启动复审。
39. **锁定四抓手**：**适配层、开放契约、开放格式、可换密钥**——别让专有字段进契约。
40. **国产化底线**：**迁移不改事件 Schema 与对外接口**——这是可迁移性的底线。
41. **反腐蚀口诀**：**不许绕过抽象层搞临时改造**——否则抽象层被腐蚀，锁定反而加深。
42. **锁定体检**：**每季统计专有 API 占比与开放格式覆盖率**——纳进技术债管理才有长效。
43. **核心五不变**：**强状态、强事务、强顺序、强长连接、强低延迟 → 不上 FaaS**——这是判断红线。
44. **事件总线三职**：**削峰填谷、重试死信、多方广播**——只写"解耦"要丢分。
45. **总收口**：**无服务器不是不用管，是管得更精准**——管事件、管状态、管失败、管成本。
