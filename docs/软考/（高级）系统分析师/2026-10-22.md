## 今日核心概念

### 1. 微服务架构与服务网格

定义：微服务架构是将单体应用按业务边界拆分为多个可独立部署、独立伸缩、独立演进的小型服务，通过轻量通信（HTTP/RPC、消息）协作；服务网格（Service Mesh）是在业务代码之外，把微服务的通信能力下沉到基础设施层统一处理。

关键要点：
- 拆分四原则：按业务能力（DDD 限界上下文）而非技术分层拆；每个服务独占自己的数据（数据库隔离，禁止跨库直连）；单一职责且自治（独立部署、独立扩容、独立数据库）；拆分粒度宁粗勿细（太小则运维成本指数上升）。
- 服务通信两模式：同步（REST/gRPC，请求-响应，简单但故障会级联传播，需超时+熔断+重试三件套）；异步（消息队列 Kafka/RocketMQ，最终一致，需处理幂等与重复消费）。
- 服务网格 Sidecar 模式：每个服务旁挂一个 Envoy/Sidecar 代理，业务代码零侵入。提供流量治理（负载均衡、熔断、重试、限流）、可观测性（统一指标/日志/链路）、mTLS 服务间加密、协议转换（HTTP↔gRPC）。
- 控制面 vs 数据面：控制面（Istio 控制面）下发路由规则、安全策略、遥测配置；数据面（Envoy）实际执行流量转发与策略。两者解耦是网格可扩展的关键。
- 网格三大能力面：流量管理（Routing、Traffic Splitting 灰度/蓝绿、Traffic Mirroring 影子流量）、安全（mTLS、AuthorizationPolicy、零信任）、可观测（Prometheus 指标聚合、Jaeger 链路追踪、Envoy 访问日志）。
- 副作用与代价：Sidecar 引入约 1~2ms 延迟、资源占用增加 20%~50%、运维复杂度显著上升、调试链路变长（需理解 Sidecar 行为）。**小规模应用用网格是负债不是资产**，通常 10 个以上服务、跨 3 个以上团队时收益才显现。
- 记忆口诀：「拆分按界不按层，数据独占不互访；网格下沉通信层，Istio 控面 Envoy 面；十服务以上才回本，小规模徒增运维钱」

### 2. 事件驱动架构与事件溯源

定义：事件驱动架构（EDA）以"领域事件"为核心，组件之间通过发布/订阅事件异步协作，发送方不关心谁在消费；事件溯源（Event Sourcing）以事件序列作为系统状态的唯一真相来源，状态由事件回放推导得出。

关键要点：
- 事件三要素：唯一标识（Event ID，全局唯一防重复）、时间戳（Occurred At，业务发生时间而非处理时间）、来源（Origin/Trace ID，链路追溯）。
- 事件溯源三形态：Event Sourcing（事件是唯一真相，状态由回放推导）、Event Store + Snapshot（存全部事件，定期打快照加速恢复）、Event Collaboration（事件仅用于通知，状态仍在库中）。**三者是渐进的，Event Collaboration 是最保守的起点**。
- 快照（Snapshot）策略：每 N 个事件或每 T 小时打一次；快照必须包含版本号与序号，回放时取"最近快照 + 后续事件"。快照损坏会导致整个聚合无法恢复，必须定期校验。
- 事件模式演进四要素（EventStorming）：事件名称用业务语言（过去时，如"订单已支付"）；事件不可变（Immutable）；事件版本化（新增字段而非修改）；事件与命令分离（命令可被拒绝，事件只记录已发生的事实）。
- 消息投递语义三档：At Most Once（可能丢，最快）、At Least Once（可能重，最常用，必须幂等）、Exactly Once（端到端难保证，通常靠幂等 + 事务性发件箱模拟）。
- 幂等三要素：全局唯一业务 ID（Event ID / 订单号）+ 去重存储（Redis SETNX 或 DB 唯一索引）+ 过期策略（TTL 与业务窗口匹配，如 7 天）。
- 顺序性问题：单分区保证分区内有序（Kafka Partition Key 按聚合 ID 哈希）；需要全局有序时只能单分区（吞吐受限），实践中通常接受"同一聚合内有序，跨聚合乱序"。
- 消息堆积治理：消费者组再均衡（Rebalance）、死信队列（DLQ）、消息保留期、消费进度追踪（offset / checkpoint）、批量消费与限流背压。
- 记忆口诀：「事件过去时、不可变、带版本；至多一次可能丢，至少一次必做幂等；同聚合内保有序，跨聚合接受乱序；溯源存事件+快照，协作发通知最保守」

### 3. 分布式事务与一致性保障

定义：分布式事务指一次业务操作跨越多个服务/数据库，需要保证整体原子性或最终一致性的机制集合。核心矛盾是 CAP：分布式系统必然存在分区（P），只能在一致性（C）与可用性（A）之间取舍。

关键要点：
- CAP 精确表述：网络分区发生时，必须在 C 与 A 之间二选一。BASE 是 CAP 的工程折中（基本可用 BA、软状态 S、最终一致 E）。
- 2PC（两阶段提交）：协调者→准备阶段（各参与者预提交、锁定资源）→ 提交阶段（全部成功则提交，否则回滚）。**致命缺陷：单点故障（协调者挂起则资源永久锁定）、阻塞（参与者持锁等待）、性能差（两轮网络往返）。仅适用于单资源管理器场景**。
- TCC（Try-Confirm-Cancel）：Try 阶段预留资源、Confirm 阶段确认消费、Cancel 阶段释放。**不依赖全局锁，性能好，适合强一致场景**。适用前提：每个服务都要实现三个方法、必须能实现"资源预留"语义、隔离性要求高（通过业务查询做补偿对账）。
- Saga：长事务拆分为多个本地事务 + 补偿动作。支持正向（无补偿，如通知类）和反向（补偿型，如扣款→退款）两种模式。**适合长流程、跨外部机构、无法预留资源的场景**。
- 本地消息表（可靠消息最终一致）：业务操作与消息写入同一本地事务，轮询任务扫描未发送消息重投 → 收到 MQ 确认后标记已发送。**解决"本地事务成功但消息发送失败"的核心矛盾，是金融、订单场景最常用方案**。
- Seata AT 模式：全局事务 + undo_log 自动生成反向补偿 SQL，要求每张业务表必须有 undo_log 表，且受限于单库单事务，无法跨库。
- 可靠投递三件套（必须同时具备）：生产端可靠性（本地消息表/事务消息）、Broker 端可靠性（多副本、持久化、同步刷盘）、消费端可靠性（手动 ACK + 幂等处理）。**任何一环缺失都会丢消息或重复处理**。
- 常见场景选型：单库多表 → 本地事务；多库强一致 → TCC；长流程可补偿 → Saga；异步最终一致 → 本地消息表 / RocketMQ 事务消息。
- 记忆口诀：「2PC 阻塞有单点，TCC 预留性能佳；Saga 长流程可补偿，消息表解最终一致；可靠投递三件套：生产可靠+Broker 持久+消费幂等」

### 4. API 网关与服务治理

定义：API 网关是所有外部请求的统一入口，承担路由转发、认证鉴权、限流熔断、协议转换、监控日志等横切能力；服务治理是围绕服务注册、发现、配置、健康检查的一整套基础设施。

关键要点：
- 网关核心职责六项：路由（Path/Header 规则、负载均衡）、认证（JWT/OAuth2/统一登录、黑白名单）、限流（QPS、并发、IP 维度，令牌桶/漏桶/滑动窗口）、熔断降级（Sentinel/Hystrix）、协议转换（HTTP↔gRPC/WebSocket、Dubbo→HTTP）、可观测（统一埋点、访问日志、Trace 透传）。
- 网关 vs 注册中心 vs 配置中心：网关管**南北向**流量（外部→内部），注册中心管**东西向**服务发现（Nacos/Eureka/Consul），配置中心管动态配置（Nacos/Apollo），三者职责不同不要混为一谈。
- 服务注册与发现：客户端发现（Dubbo 主流，消费者直连各实例，性能好但调用方重）、服务端发现（K8s Service/Consul，调用方只需调 LB，K8s 生态主流）。K8s 里不再需要 Eureka，CoreDNS 直接承担发现职责。
- 负载均衡四策略：轮询（Round Robin，默认，均衡但无感知）、加权轮询（按后端能力）、最少活跃调用（自动避开慢节点）、一致性哈希（会话保持）。
- 熔断三态：关闭（正常放行）→ 打开（失败率超阈值，快失败不调下游）→ 半开（放少量请求试探，成功则关闭、失败则打开）。熔断粒度可以是接口级、实例级、服务级。
- 限流四算法：固定窗口（简单但临界问题）、滑动窗口（平滑，无临界）、漏桶（恒定速率出水，强行整形）、令牌桶（恒定速率生成令牌，允许突发，**最常用**）。
- 熔断与限流的区别：**限流防的是"量太大"，熔断防的是"对方已经挂了"，前者主动按配额拒，后者被动因失败率触发。两者必须配套使用**。
- 灰度发布三种路径：网关层按用户/Header 规则路由（成本最低）、服务网格 Traffic Splitting（金丝雀逐步放量）、双注册双订阅（Dubbo/注册中心权重调整）。三者可组合，先小流量灰度验证再全量。
- 记忆口诀：「网关南北向，注册东西向；限流防量大、熔断防已挂；灰度先切量，验证再放量」

### 5. 分布式系统可观测性三支柱与 SRE

定义：可观测性是通过系统外部输出（Metrics、Logs、Traces）推断系统内部状态的能力，区别于"监控"（监控已知问题的告警）；SRE（Site Reliability Engineering）是以软件工程方法论运营生产系统，用服务水平目标（SLO）而非"零故障"作为工程目标。

关键要点：
- 三支柱分工：Metrics（聚合数值、时序数据库 Prometheus，成本低、告警主渠道）、Logs（离散事件、ELK/Loki，排查根因、审计溯源）、Traces（请求链路、Jaeger/SkyWalking/Sentinel，定位跨服务瓶颈）。三者通过 Trace ID / Service Name / Metric Label 关联。
- 黄金三指标（Google SRE）：延迟（Latency，成功请求耗时分位值 + 失败请求分位值分开看）、流量（Traffic，QPS）、错误率（Errors，返回非预期响应的比例）。**告警应基于 SLO 燃尽率，而非单纯的 CPU/内存阈值**。
- SLI/SLO/SLA：SLI 是服务级别指标（"99% 请求延迟 < 300ms"）、SLO 是目标（"可用性 99.9%"）、SLA 是对外承诺（带违约赔偿）。**SLO 定得比 SLA 严，如 SLA 99.5% 则 SLO 定 99.8%**，留出缓冲避免违约。
- 错误预算（Error Budget）：(1 − SLO) × 总请求数，可用于"消费"。预算耗尽即触发政策——暂停功能发布、优先修稳定性问题。**这是 SRE 最重要的一招：把稳定性争议从"要不要延期"变成"预算还剩多少"**。
- 常见 SLO：可用性（成功请求/总请求）、延迟（满足延迟阈值的请求比例）、吞吐量、正确性（返回正确结果的比例）。
- 分布式追踪原理：Trace 由多个 Span 组成树，Span 携带 traceId/spanId/parentSpanId/timestamp。跨进程传播靠 W3C Trace Context 头或 B3 头；异步场景需显式传递消息属性。
- 采样策略：头部采样（按 Trace ID 哈希决定是否采集，实现简单但可能漏掉关键 Trace）、尾部采样（等 Trace 结束后按错误/延迟决定保留，精准但需内存缓存）、混合采样（保留全部错误 + 1% 正常）。
- 卡夫纳树四类错误：延迟（Latency，常见，需容忍重试）、故障（Fault，罕见但致命，需快失败+降级）、饥饿（Starvation，队列/连接池被挤占，需限流隔离）、蔓延（Cascading，依赖耗尽导致连锁，需熔断+舱壁）。
- 记忆口诀：「三支柱 Metric Log Trace；黄金三指标延迟流量错误率；SLO 严于 SLA，错误预算花；四类错误延迟故障饥饿蔓延」

## 案例分析题

**题目**：某市"一网通办"平台升级项目，采用微服务架构，包含用户中心、事项管理、审批引擎、电子证照、材料流转、支付结算、物流查询、对接引擎共 8 个服务，上线后出现以下严重问题：

1. **性能坍塌**：上线初期日均请求仅 3 万次，系统尚可承载。但每逢月初"医保年度报销"办理高峰，QPS 瞬间从 200 飙升至 3500，持续约 4 小时，期间 60% 请求超时。事后分析发现：审批引擎在高峰时段串行调用 5 个下游服务（日志查询、规则引擎、证照核验、信用核查、消息推送），单请求需 2.3 秒；数据库单表数据量已超 3 亿行，审批记录表无分区、无索引优化，全表扫描耗时 8 秒。

2. **数据不一致**：电子证照模块出现多个下游委办局系统各自调用的场景。某次"营业执照"更新时，平台侧显示新信息，委办局侧仍是旧数据，持续 3 天未被发现。分析发现材料流转服务与对接引擎之间存在"消息发送成功但本地事务回滚"的场景，导致消息发出后对应业务数据被回滚，但下游系统已经消费并更新了自己的库。

3. **雪崩式故障**：某天下午 15:20，对接引擎调用某省级委办局接口超时（对方系统缓慢）。对接引擎未设置超时时间，默认等待 30 秒，导致其工作线程池在 30 分钟内被占满（200 个线程全被阻塞）；随后依赖对接引擎的审批引擎、电子证照服务也相继响应变慢，最终整个平台在 15:50 开始不可用。恢复用了 3 小时。

4. **版本不一致导致功能异常**：对接引擎三个月内连续发布 7 个版本，不同部门调用的是不同版本的接口，导致"事项申报"功能在委办局侧可用、在市民端上报错。排查耗时 5 天，最终发现是各委办局对接方未及时同步版本信息。

5. **架构问题**：项目初期部署时未部署服务网格，所有跨服务调用均为代码内 Feign 直连。开发组发现日志分散在 8 个服务的本地磁盘，排查一次跨服务问题需要登录 8 台服务器手工 grep，平均耗时 2 小时。日志中大量敏感信息（身份证号、手机号）未脱敏。

6. **运维困境**：项目组配置了熔断功能，但熔断阈值设置过于宽松（失败率 90% 才熔断），实际故障时几乎没有触发；限流功能仅在网关上配置了一层，应用服务层未做保护，导致限流形同虚设。

**问题：**
1. 分析该项目在架构设计、微服务拆分、分布式事务、可观测性四个方面的核心问题。
2. 针对问题 1 的性能坍塌，提出具体的优化方案。
3. 针对问题 2 的数据不一致，设计数据一致性保障方案。
4. 针对问题 3 的雪崩式故障，设计完整的容错方案。
5. 针对问题 4 与问题 5，设计服务治理与可观测性改进方案。
6. 针对问题 6，说明熔断与限流参数应如何正确设置，并给出熔断降级策略设计原则。

**参考答案：**

**1. 核心问题分析**

- **架构设计层面**：（1）缺少服务网格与统一流量治理层，跨服务调用为代码内 Feign 直连，无法集中治理；（2）未做全链路可观测性建设，日志分散、无 Trace ID 贯通、敏感信息未脱敏；（3）未采用异步解耦，审批引擎串行调用 5 个下游服务，链路耦合过紧，单点慢即全链路阻塞；（4）缺少舱壁隔离与降级预案，各服务共享资源池。
- **微服务拆分层面**：（1）8 个服务职责边界不清，对接引擎同时承担协议转换、鉴权、转发、重试、限流等多项职责，形成"超级服务"；（2）未考虑数据隔离，对接引擎成为多个业务线共用的数据通道，容易成为单点；（3）服务粒度与团队规模不匹配，8 个服务由一个团队维护，运维复杂度超过收益。
- **分布式事务层面**：（1）未引入可靠消息机制，消息发送与本地事务未绑定，存在"消息已发但事务回滚"的不一致窗口；（2）缺少幂等设计，消息重复消费会导致重复更新下游数据；（3）无对账补偿机制，下游数据不一致无自动发现与修复手段；（4）未明确数据权威源，同一数据（营业执照）在多系统各自维护，无单一可信来源。
- **可观测性层面**：（1）无统一 Trace ID，无法追踪一次请求的完整链路；（2）日志未集中采集，排查跨服务问题需人工登录多台服务器；（3）关键指标（QPS、P99 延迟、错误率、线程池水位）无监控告警，故障发生时无法快速定位；（4）日志中身份证号、手机号未脱敏，存在合规风险。

**2. 性能坍塌优化方案**

- **链路异步化**：审批引擎的 5 个下游调用中，日志查询、消息推送可改为异步（发 MQ 后立即返回），规则引擎、证照核验、信用核查为强依赖需保留同步但并行化（CompletableFuture 并发调用，聚合等待）。**并行化后可将 2.3 秒降至约 0.8 秒**（取决于最慢的下游）。
- **数据库优化**（优先级最高）：
  - 审批记录表按月分区（12 个月），历史数据归档到历史表；
  - 建立覆盖索引：`(applicant_id, status, created_at)`、`(item_code, submit_time)`；
  - 避免 SELECT *，只查询必要字段；
  - 引入读写分离，写库只写、读流量走从库；
  - 连接池调优：最大连接数、超时时间配置，避免高峰打满。
- **缓存与限流**：规则引擎规则、证照核验结果引入本地缓存 + Redis 二级缓存，TTL 设为 5~30 分钟，显著减少下游调用；对审批入口按"事项类型 + 区县 + 时间窗"做配额限流，高峰期削峰。
- **异步削峰**：受理请求后立即返回"受理成功+受理编号"，审批实际处理通过 MQ 异步执行，前端轮询或推送进度。**这是政务系统高峰期最有效的削峰手段**。
- **压测验证**：改造后需做全链路压测，模拟峰值 5000 QPS，验证优化效果并建立容量基线。

**3. 数据一致性保障方案**

- **确定权威数据源（SoR）**：营业执照等证照信息的唯一可信来源应为"电子证照库"，对接引擎只做转发不做数据维护，所有下游以证照库为准。明确"一数一源、一源多用"。
- **引入本地消息表（可靠消息最终一致）**：对接引擎接收请求时，在同一本地事务中同时：① 更新本地状态为"待同步"；② 向消息表插入一条待发送消息。事务提交后由定时任务扫描未发送消息投递 MQ，投递成功后标记已发送。**彻底解决"消息发出但事务回滚"问题**。
- **消费端幂等**：下游消费者按消息中的全局唯一事件 ID 去重（Redis SETNX + 数据库唯一索引双保险）；业务更新使用"乐观锁 + 版本号"或"条件更新（WHERE version = ?）"防止并发覆盖。
- **对账补偿机制**：每日定时对平台侧与委办局侧数据做全量/增量对账（按主键 + 更新时间比对），发现差异自动生成差异工单并触发补偿修复；对账结果纳入监控告警。
- **状态机管理**：为每条对接同步记录维护状态机（初始→待同步→已同步→已确认→异常），状态流转留痕；连续处于异常状态超过 N 小时自动告警并人工介入。
- **消息可靠性三件套**：生产端（本地消息表）、Broker 端（多副本+持久化+同步刷盘）、消费端（手动 ACK + 幂等）。三件套必须同时具备。
- **明确时序要求**：接受"最终一致"，但设定时限 SLA——正常情况 5 分钟内完成同步，异常情况 30 分钟内告警人工介入。

**4. 雪崩式故障容错方案**

- **根因分析**（三个放大器）：
  - **无超时设置**：默认 30 秒等待，导致线程长时间占用；
  - **无隔离**：所有请求共享同一线程池，下游慢导致线程池耗尽；
  - **无熔断**：持续失败仍不断重试，形成自我强化的资源消耗。
- **超时设置（三层递减）**：连接超时 2 秒、读超时 3 秒（下游接口）、整体调用超时 5 秒。**必须短于上游的 SLA**，留出重试与降级的时间余量。
- **熔断器配置**：对接第三方接口必须熔断。失败率阈值 50%、慢调用阈值（RT > 1 秒）占比 50%、最小请求数 20、熔断持续时间 30 秒。熔断后进入 OPEN 状态直接快失败。
- **舱壁隔离（舱壁模式）**：按"调用方业务域"划分独立线程池/信号量（如事项申报池、证照查询池、进度查询池），每个池有独立配额。**下游变慢时只影响对应池，不会拖垮全部**。这是防雪崩最关键的一招。
- **熔断降级策略**：
  - 对**查询类**接口：熔断期间返回本地缓存数据或"系统繁忙，请稍后重试"友好提示；
  - 对**写入类**接口：熔断期间入本地消息队列暂存，恢复后补发，并返回"已受理"；
  - 对**查询进度类**接口：熔断期间返回默认值（受理中状态）；
  - **禁止所有接口都返回异常**——不同业务场景降级结果完全不同，必须分类设计。
- **重试策略**：只在读操作上重试，最多重试 1~2 次，指数退避（1s、2s），**写操作禁止自动重试**（除非有幂等键）。无幂等保证的重试会造成重复提交。
- **限流分层**：网关层全局 QPS 限流 + 应用层按接口维度限流（第三方接口单独设较小阈值，如 50 QPS），保护本地资源不被拖垮。
- **熔断演练**：上线前用故障注入（Chaos Engineering）主动打挂省级接口，验证熔断是否真的触发、降级是否生效、恢复是否正常。

**5. 服务治理与可观测性改进方案**

- **针对问题 4（版本不一致）**：
  - 引入 **API 版本化机制**：对接接口路径带版本号（`/api/v1/xxx`、`/api/v2/xxx`），新旧版本并行运行，各委办局按自身节奏迁移，禁止直接覆盖式发布；
  - 建立**对接方台账系统**：记录每个委办局对接的接口版本、上线时间、负责人、联系方式，新接口发布时自动通知并跟进确认；
  - **契约测试**：用 Pact 或 OpenAPI 定义接口契约，CI 阶段自动验证接口兼容性，防止破坏性变更悄悄上线；
  - 对接引擎提供**版本兼容矩阵文档**，公开各版本生命周期与下线时间，给对接方留足迁移窗口。
- **针对问题 5（可观测性）**：
  - **引入服务网格（Istio）**：Sidecar 自动注入，所有跨服务通信经过 Envoy，实现集中流量治理与遥测采集，业务代码零侵入；
  - **统一日志规范**：所有服务输出 JSON 结构化日志，必须包含 `traceId`、`spanId`、`timestamp`、`serviceName`、`level` 五个字段；
  - **日志脱敏（合规硬要求）**：在 Logback/Log4j 中配置自定义 Layout 或 Filter，对身份证号（保留前 3 后 4）、手机号（中间 4 位掩码）、银行卡号、姓名统一脱敏，**在日志输出前完成，不依赖日志平台后处理**；
  - **集中日志采集**：Filebeat/Fluent Bit → Elasticsearch/Loki，替代人工登录 8 台服务器 grep；
  - **全链路追踪**：集成 OpenTelemetry 或 SkyWalking，Trace ID 跨服务透传（HTTP 头传递 + MQ 属性传递），一次请求可通过 Trace ID 完整还原；
  - **黄金三指标监控**：对每个服务监控 QPS、P99 延迟、错误率，配置多级告警（P0 电话/P1 短信/P2 企业微信）；
  - **链路拓扑可视化**：通过 SkyWalking 或 Jaeger 自动绘制服务调用拓扑图，异常服务节点高亮，便于快速定位瓶颈。
- **价值量化**：改造后跨服务问题排查时间应从 2 小时降至 10 分钟以内，日志检索从人工 grep 变为秒级查询。

**6. 熔断与限流参数设置原则**

- **熔断阈值设置错误的危害**：本项目设置为"失败率 90% 才熔断"意味着——在失败率 0%~90% 期间，系统会**持续调用已经故障的下游**，每一个请求都要消耗 30 秒超时，200 个线程在 30 分钟内全部耗尽。**熔断阈值的本质是"在造成雪崩之前主动放弃"，设置过高等于没设置**。
- **熔断参数配置原则**：
  - **失败率阈值**：一般设置 50%，快速响应下游异常；对持续高负载但健康的下游可适当放宽到 70%；**不要设 90%**；
  - **慢调用比例阈值**：RT 超过 1 秒的调用占比超 50% 触发（部分依赖缓慢但未失败的情况同样致命）；
  - **最小请求数**：20（样本太小时比率统计无意义，比如 1 次失败就是 100% 失败率，会误触发熔断）；
  - **熔断持续时间**：30 秒，熔断后进入半开态放少量请求试探，成功则恢复；
  - **熔断粒度**：优先用**方法级/接口级**而非实例级，减少误伤。
  - **第三方外部依赖必须熔断**，无商量余地；内部强依赖要谨慎，避免形成级联熔断。
- **限流分层原则**：
  - **限流防"量太大"，熔断防"已挂掉"，两者不可互相替代**。只有熔断没有限流，下游恢复时会瞬间被涌入流量再次打垮；只有限流没有熔断，下游已挂时仍会持续消耗本地资源；
  - 限流应在**三层同时部署**：网关层（全局 QPS 保护）、应用层（接口维度业务配额）、数据库层（连接池 + 慢查询阈值）；
  - 第三方接口需单独设较低阈值（如 50 QPS），防止本平台流量打爆对方；
  - 限流算法优先令牌桶（允许一定突发，更贴合真实业务波峰）。
- **熔断降级策略设计原则**：
  - **分类设计**：读接口可降级为缓存/默认值，写接口可降级为入队暂存，进度查询可返回保守状态。**禁止一刀切全部返回异常**；
  - **兜底优先于报错**：只要业务允许，宁可返回不精确但可用的结果，也不要直接 5xx；
  - **降级结果对用户友好**：返回明确提示（如"系统繁忙，正在处理中，请稍后查询"）而非堆栈异常；
  - **降级可开关**：降级逻辑通过配置中心（Nacos）动态控制，支持不发版调整；
  - **降级也是监控对象**：熔断触发次数、降级次数应作为核心监控指标，异常升高说明系统正在"带伤运行"，需立即介入。

**踩分要点：**
- 第1问须从架构设计、微服务拆分、分布式事务、可观测性四个维度作答，每维度至少 3 条具体问题。
- 第2问须包含链路异步化/并行化、数据库分区+索引、缓存、异步削峰、压测验证五项；数据库优化必须写明具体索引和分区方案。
- 第3问须明确权威数据源、本地消息表、消费端幂等、对账补偿、状态机五要素，并写清"消息已发但事务回滚"的解法。
- 第4问须先做根因分析（无超时/无隔离/无熔断三放大器），再给超时三层递减、熔断四参数、舱壁隔离、分类降级、重试限制、分层限流、故障演练七项措施。
- 第5问须包含 API 版本化+dPACT 契约测试+对接台账解决版本问题，以及服务网格+结构化日志+日志脱敏+集中采集+全链路追踪+黄金三指标解决可观测性问题；**日志脱敏必须写明"在输出前完成"**。
- 第6问须指出"90% 阈值等于没设置"这一致命性、熔断四参数具体数值、分层限流三层、以及降级分类设计原则。

## 记忆口诀

**微服务与网格**
拆分四原则：按界不按层、数据独占不互访、粒度宁粗勿细、小团队别拆细
网格：Istio 控面 Envoy 数据面、Sidecar 加 1~2ms 延迟、十服务以上才回本

**事件驱动**
事件三要素：EventID+OccurredAt+TraceID
事件四要素：过去时、不可变、带版本、与命令分离
投递语义：至多一次可能丢、至少一次必幂等、精确一次靠事务
溯源三形态：Event Sourcing 极致 / Event Store+Shootshot 折中 / Event Collaboration 最保守
顺序性：同聚合内保有序（Partition Key=聚合ID）、跨聚合接受乱序

**分布式事务**
2PC：协调者单点 + 参与者阻塞 + 两轮网络
TCC：Try 预留 + Confirm 确认 + Cancel 释放、性能好但需每服务实现三方法
Saga：正向无补偿 + 反向补偿、适合长流程跨机构
本地消息表：本地事务写业务+写消息、定时任务补投、解"已发但回滚"
可靠投递三件套：生产可靠 + Broker 持久 + 消费幂等

**网关与治理**
网关南北向（外部→内部）、注册中心东西向（服务发现）、配置中心管动态配置
限流四算法：固定/滑动/漏桶/令牌桶（令牌桶最常用）
熔断三态：关闭→打开（快失败）→半开（试探恢复）
熔断 vs 限流：限流防量大、熔断防已挂，配套使用
灰度三路径：网关规则 / 网格 Traffic Splitting / 双注册双订阅

**可观测性与 SRE**
三支柱：Metrics（聚合告警）+ Logs（根因审计）+ Traces（链路定位）
黄金三指标：延迟（分位值）+ 流量（QPS）+ 错误率
SLI<SLO<SLA：SLO 要严于 SLA 留缓冲
错误预算：(1−SLO)×总请求数，耗尽即冻结发布
四类错误：延迟 + 故障 + 饥饿 + 蔓延
采样：头部（哈希决策）/ 尾部（结束后按错误延迟决策）/ 混合
