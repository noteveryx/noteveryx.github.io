## 今日核心概念

### 1. 领域驱动设计与战略建模
定义：领域驱动设计是以业务领域为建模中心，通过限界上下文、通用语言、聚合根、领域事件和上下文映射，将业务知识显式映射到软件模型的体系。
关键要点：
- 战略设计阶段输出限界上下文和上下文映射图，明确核心域、支撑域和通用域。
- 战术设计阶段以聚合为单位管理一致性边界，聚合根是唯一入口。
- 通用语言要求业务方、架构师、开发、测试使用同一套词汇。
- 上下文映射类型包括合作关系、共享内核、客户-供应商、防腐层、开放主机服务和发布语言。
- 领域驱动要求持续重构模型，建立事件风暴、用例分析和模型评审机制。

### 2. 整洁架构与六边形架构
定义：整洁架构与六边形架构是同源思想，将业务核心与外部依赖解耦，通过依赖倒置和端口适配器模式让业务规则独立于框架、数据库、界面和外部服务的体系。
关键要点：
- 分层由内向外分为实体、用例、接口适配和框架与驱动，越靠内越稳定。
- 业务核心不依赖任何外部技术细节，所有依赖指向核心。
- 六边形架构通过端口定义业务能力，由适配器接入具体技术。
- 整洁架构强调跨边界数据传输和跨边界原则，避免泄露领域模型。
- 适合复杂业务核心、长期演进、需多端复用和高可测试性的系统。

### 3. 中台架构与能力沉淀
定义：中台架构是把通用业务能力、数据能力、技术能力抽象为可复用、可编排、可治理的服务集合，为前台业务快速创新提供共享底盘的体系。
关键要点：
- 中台分为业务中台、数据中台、技术中台和 AI 中台，必须明确职责边界。
- 能力中心建设遵循识别、抽象、标准化、平台化、运营化五步。
- 中台必须配套契约管理、版本管理、SLA、限流、计量和计费机制。
- 反模式包括中台过度抽象、缺乏前台需求支撑、运营机制缺失和组织割裂。
- 落地需业务驱动、组织保障、平台支撑和度量闭环，避免技术中台空心化。

### 4. API 设计与接口治理
定义：API 设计与接口治理是对外和对内接口的协议、风格、版本、安全、限流、监控和生命周期进行全流程规范管理与持续优化的体系。
关键要点：
- API 设计原则包括面向资源、分层命名、显式语义、幂等控制和错误码一致。
- 接口风格包括 REST、gRPC、GraphQL、WebHook 和事件流，需按场景选型。
- 版本管理必须显式声明、向后兼容、阶段废弃，避免隐式破坏。
- 治理维度包括契约测试、流量控制、安全认证、限流熔断、监控告警和文档门户。
- 内部 API 同样需规范化，避免形成内部黑盒与强耦合。

### 5. 架构决策记录与技术债管理
定义：架构决策记录是用结构化文档对关键架构决策的背景、选项、结论、后果和约束进行留痕的实践，技术债管理是对系统演进过程中的次优选择进行识别、评估、还债和预防的体系。
关键要点：
- ADR 至少包含背景、选项、决策、后果四个部分，编号唯一且不可篡改。
- 关键决策包括技术选型、部署形态、存储选型、安全模型、集成方式。
- 技术债按影响与还债成本排序，纳入迭代计划，避免隐性累积。
- 债主必须明确，重要决策可建立架构委员会或评审机制。
- 决策记录应进入知识库与代码仓同源管理，与架构图、ADR 和代码相互追溯。

## 案例分析题

**题目**：某省人社厅"民生一网通办"系统已运行六年，承载就业、社保、人才、劳监、调解五大业务，年访问量 1.2 亿次。当前面临以下突出问题：

1. 业务高度耦合，五大业务共用同一数据库和同一应用包，每次新业务上线需整体发布，发布窗口超过 6 小时。
2. 业务规则散落在代码各处，规则变更需开发人员手工修改并随发布上线，业务部门无法自助调整。
3. 与公安、税务、银行、医保、教育等 8 个外部系统对接，接口协议不统一，部分链路已无文档可查。
4. 数据统计和报表生成占用夜间资源 70%，白天高峰期报表卡顿导致业务响应慢。
5. 全省 14 个地市存在个性化业务需求，硬编码分支导致代码腐化，新人难以接手。
6. 中台概念已提出两年，但未形成清晰的能力中心，前台业务仍重复建设。
7. 系统可用性指标仅 99.5%，年度故障时间超过 4 小时，影响群众办事体验。
8. 业务方要求 18 个月内完成中台化与云原生化，并支撑未来三年的业务扩展。

请回答：
1. 对该系统进行领域驱动战略建模，划分限界上下文并给出上下文映射关系。
2. 设计中台化与云原生化融合演进方案，涵盖能力中心、技术平台、组织保障和度量体系。
3. 给出业务规则外置与低代码落地思路，包括规则引擎、流程引擎、表单引擎和灰度上线机制。
4. 设计统一的 API 治理与外部对接平台，覆盖协议适配、契约测试、限流熔断和监控告警。
5. 制定技术债治理与架构决策记录体系，给出优先级评估、还债计划与 ADR 落地路径。

**参考答案**：

1. 领域驱动战略建模：
- 通过事件风暴梳理五大业务的事件、命令、聚合，输出统一语言词典。
- 划定限界上下文：就业服务、社保服务、人才服务、劳监调解、身份认证、支付结算、消息中心、文件中心、报表中心。
- 上下文映射：身份认证和消息中心作为通用域，对所有业务提供共享能力；报表中心作为支撑域通过发布语言和共享内核与各业务集成；支付结算作为支撑域通过防腐层与外部银行对接；劳监调解与就业服务是合作关系；人才服务与社保服务通过开放主机服务发布接口。
- 核心域为就业服务和社保服务，作为中台优先沉淀能力。
- 输出领域模型评审、模型维护、持续重构机制，避免模型腐化。

2. 中台化与云原生化融合演进：
- 第一阶段：搭建统一技术中台，包括容器云、CI/CD、镜像仓库、配置中心、注册中心、API 网关和可观测性平台。
- 第二阶段：构建身份、消息、文件、报表、规则、流程六大能力中心，对外提供标准化服务。
- 第三阶段：业务前台以轻应用方式构建，按业务域拆分为可独立部署的微服务，共享技术中台和能力中台。
- 第四阶段：完成数据库按业务域分库分表和读写分离，历史数据迁移通过双写与对账保证一致性。
- 组织保障上建立业务架构师、技术架构师、平台架构师分工机制，配套业务中台运营团队。
- 度量体系覆盖复用度、调用量、SLA、业务价值、可用性、变更频次和缺陷率。

3. 业务规则外置与低代码落地：
- 引入可视化规则引擎，业务人员通过规则配置页管理参数化规则和决策表。
- 引入流程引擎承载业务审批、调度和补偿，支持 BPMN 标准并对接组织机构与角色。
- 引入表单引擎支撑前台动态表单生成与数据收集。
- 规则和流程必须先在预生产环境灰度运行，配套版本管理、回滚和审计。
- 低代码平台必须具备权限管理、版本管理、灰度发布和监控告警能力。
- 关键业务仍需保留代码开发通道，避免平台能力空心化。

4. API 治理与外部对接平台：
- 协议适配层统一 REST、gRPC、WebService、WebHook、文件交换等多种协议。
- 统一接口规范：包括命名、版本、错误码、签名、限流和幂等要求。
- 外部系统接入通过 API 网关统一出口，配合认证、授权、加密、防重放和黑白名单。
- 建立契约测试体系，开发期做契约校验，运行时做接口断言。
- 限流熔断按业务优先级分级，核心交易链路优先保障。
- 监控告警覆盖接口成功率、RT、QPS、异常分布和下游依赖健康度。
- 全部接口进入统一门户，配套文档、示例代码、SDK 和测试沙箱。

5. 技术债治理与架构决策：
- 按影响面、还债成本、风险和战略重要性四维度评估技术债优先级。
- 输出技术债登记册，纳入迭代版本，每个版本必须偿还 20% 的高优先级债。
- 建立 ADR 制度，关键决策按背景、选项、决策、后果留痕并版本化管理。
- 重大决策由架构委员会评审，配套组织规范和责任追究。
- ADR 与代码仓、文档库、架构图相互关联，避免决策与实现脱节。
- 定期做架构健康度评估，覆盖耦合度、复杂度、可测试性、可观测性和团队成熟度。

**踩分要点**：
- 第1问必须输出统一语言、限界上下文、上下文映射、核心域与支撑域，不能只画架构图。
- 第2问要写清技术中台、能力中心、业务前台、组织保障和度量五个关键点。
- 第3问必须覆盖规则引擎、流程引擎、表单引擎、灰度发布和代码兜底，不能只说“做低代码”。
- 第4问必须写明协议适配、规范、网关、契约测试、限流熔断和监控告警。
- 第5问要写明技术债评估维度、登记册、ADR 制度、架构委员会和健康度评估。

## 记忆口诀

**领域驱动口诀**：通用语言必须同，限界上下文划边界；战略战术两阶段，事件风暴起模型。

**整洁架构口诀**：实体用例在内圈，接口适配往外延；依赖倒置指核心，业务技术两分离。

**中台落地口诀**：业务数据技术 AI，四类中台各司职；能力中心五步走，运营度量是根基。

**API 治理口诀**：协议规范先立约，契约测试守边界；网关限流熔断齐，监控告警不可缺。

**技术债口诀**：四维评估排优先，登记入迭代偿还；ADR 决策留痕迹，架构健康常度量。
