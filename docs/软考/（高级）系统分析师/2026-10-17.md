## 今日核心概念
### 1. 软件需求分类与层次

定义：软件需求是从用户视角与系统视角对系统功能、性能、约束的完整描述，按层次划分为业务需求、用户需求、系统需求（功能需求+非功能需求）三级，是需求工程的基础骨架。

关键要点：

1. **业务需求（Business Requirement）**：组织或客户的高层次目标，关注"为什么做"，由出资方提出，对应问题域分析。
2. **用户需求（User Requirement）**：用户使用系统完成的具体任务，关注"做什么"，以用户视角描述，通常以用例形式表达。
3. **系统需求（System Requirement）**：开发者视角的详细规格，关注"怎样实现"，细分为功能需求（行为）与非功能需求（质量属性）。
4. **非功能需求五大类**：性能（响应时间、吞吐量、并发数）、可用性（MTBF/MTTR/可用率）、安全性（机密性、完整性、不可否认性）、可维护性（可修改、可扩展、可移植）、易用性（学习成本、操作效率）。
5. **需求层次映射**：业务需求 → 用户需求 → 系统需求，越往下越具体、可度量、可验证。
6. **需求分类辅助法**：FURPS+ 模型（F 功能、U 易用性、R 可靠性、P 性能、S 可支持性），加号补充设计约束、实现接口、物理需求等。

### 2. 需求获取方法与技术

定义：需求获取是收集、分析、确认干系人需求的过程，常用技术包括面谈、问卷、原型、观察、焦点小组、联合应用开发（JAD）、需求研讨会等，是需求工程的入口环节。

关键要点：

1. **传统方法**：面谈（一对一深入）、问卷调查（一对多采样）、观察（实地跟岗）、文档分析（研究现有系统与业务文档）。
2. **协同方法**：焦点小组（多人互动讨论）、联合应用开发 JAD（客户+开发+设计师集中研讨会）、需求研讨会（需求工作坊）。
3. **原型法**：抛弃型原型（验证需求后丢弃）、演化型原型（逐步演化为最终系统），降低需求误解风险。
4. **头脑风暴与 KJ 法**：生成发散想法，再用亲和图法（KJ 法）归类整理，提炼核心需求。
5. **用例与用户故事**：从用户视角描述系统行为，"作为一个[角色]，我想要[功能]，以便于[价值]"。
6. **取舍原则**：根据项目规模、干系人数、可获得性选择组合方法，关键干系人深度面谈+群体工作坊+原型验证是经典组合。

### 3. 需求分析与建模

定义：需求分析是对获取的需求进行梳理、分解、抽象与建模的过程，核心是构建系统的分析模型，明确"做什么"，输出数据流图（DFD）、E-R 图、用例图、状态转换图等模型。

关键要点：

1. **数据流图（DFD）四要素**：外部实体、加工、数据存储、数据流。从顶向下逐层分解（顶层 DFD → 0 层 → 1 层 → 2 层），保持父图子图平衡（父图某加工的输入输出与子图一致）。
2. **E-R 图三要素**：实体（矩形）、属性（椭圆）、联系（菱形）。联系基数 1:1、1:N、M:N，弱实体用双矩形，识别联系用双菱形。
3. **用例图建模**：识别 Actor（人/外部系统）、识别用例（动词短语）、划分系统边界、定义关系（关联/泛化/包含/扩展）。
4. **状态转换图**：描述对象生命周期内状态变化，四要素（初态、终态、状态、转换），事件触发状态迁移，可派生为状态迁移表。
5. **分析模型三视角**：功能视角（DFD）、数据视角（E-R）、行为视角（时序图/状态图），三者互为补充。
6. **数据字典**：对 DFD 中所有元素（加工名、数据流、数据存储）给出严格定义，是模型无歧义的基础。

### 4. 需求验证与需求规格说明书（SRS）

定义：需求验证是确认需求的正确性、完整性、一致性、可追踪性、可验证性的过程，核心产出物是软件需求规格说明书（SRS），是后续开发与验收的根本基准。

关键要点：

1. **需求验证四性**：正确性（反映真实需求）、完整性（覆盖全部需求）、一致性（无矛盾冲突）、可验证性（可设计测试用例验证）。
2. **常用验证技术**：评审（同行评审、走查、桌面检查）、原型演示、需求测试（开发 acceptance test）、形式化方法（Z 语言、VDM）。
3. **评审分级**：正式评审（会议评审）、技术评审（非正式同行）、走查（开发讲解、记录员记录）、管理层评审（立项/里程碑）。
4. **SRS 标准（IEEE 830）**：引言、总体描述、具体需求（功能+非功能）、附录、索引。明确范围、定义、缩写、参考文献、需求优先级与稳定性。
5. **需求追踪矩阵（RTM）**：需求 ↔ 设计 ↔ 编码 ↔ 测试，双向追踪（正向 + 反向），确保每条需求被实现、每段代码有需求来源。
6. **变更控制**：所有需求变更必须经过变更控制委员会（CCB）评审、影响分析、批准/拒绝决策，避免范围蔓延。

### 5. 需求管理与需求变更控制

定义：需求管理贯穿软件全生命周期，重点是建立需求基线、追踪需求状态、控制需求变更，是保障项目范围、时间、成本可控的核心机制。

关键要点：

1. **需求基线（Baseline）**：经评审通过的需求规格说明书，是后续变更控制的参照基准，变更必须走变更控制流程。
2. **需求状态机**：建议 → 批准 → 已实现 → 已验证 → 删除 / 拒绝 / 推迟，状态可视化追踪。
3. **需求优先级技术**：MoSCoW（Must/Should/Could/Won't）、Kano 模型（基本型/期望型/兴奋型）、加权评分法，价值-复杂度矩阵决策。
4. **变更请求（CR）**：变更申请人、变更描述、影响分析（范围/进度/成本/质量）、CCB 评审、批准/拒绝决策。
5. **范围蔓延（Scope Creep）**：未受控的需求扩展，是项目失败主因之一，须以基线 + 变更控制双管齐下。
6. **干系人参与**：持续让关键干系人参与需求评审，确保需求理解一致、变更影响透明。

## 案例分析题

**题目**：

某市政府拟建设"智慧政务一网通办"综合服务平台，整合涉及民生、企业服务、不动产登记、医保社保等 12 个核心委办局的 480 项政务事项，实现"群众/企业办事只进一扇门，最多跑一次"。项目总投资 1.2 亿元，工期 18 个月。

需求调研阶段，系统分析师团队采用了如下做法：

（1）联合 12 个委办局负责人召开 2 天需求研讨会（JAD），梳理出业务需求清单；
（2）针对办件高频事项（如新生儿出生登记、企业开办），到办事大厅跟岗 1 周观察办事流程；
（3）面向企业群众发放电子问卷，回收 3200 份，分析高频痛点（材料重复提交 78%、跨部门跑动 5.5 次、办结时限平均 12 个工作日）。
（4）开发 1.0 版抛弃型原型，与办件人验证界面交互；
（5）完成 SRS 评审后建立需求基线，需求追踪矩阵（RTM）覆盖 480 项政务事项，从需求到测试用例双向可追。

请回答：

**问题 1**：请识别本项目中的业务需求、用户需求、系统需求各举 2 个示例，并指出业务需求、用户需求、系统需求三者之间的层次关系。

**问题 2**：需求获取阶段运用了哪几种需求获取技术？并指出每种技术对应的适用场景。

**问题 3**：本项目构建了哪些分析模型？这些模型如何互补？请说明理由。

**问题 4**：SRS 通过评审后建立需求基线，需求变更控制应如何开展？若新增"电子证照统一管理"需求，描述完整的变更控制流程。

**参考答案**：

**问题 1：需求层次示例**

（1）业务需求示例（组织高层次目标）：
- 实现"一网通办"，将分散在 12 个委办局的 480 项政务事项集中化办理，提升政务服务效率与满意度。
- 落实国家"放管服"改革要求，优化营商环境，办事环节、时限、跑动次数显著压减。

（2）用户需求示例（用户视角）：
- 企业用户：在一个窗口完成企业开办全部手续（含营业执照、税务登记、银行开户、社保登记等），最多跑 1 次、办结时限不超过 3 个工作日。
- 群众用户：新生儿出生登记仅需在医院或政务大厅一次性提交，材料免重复提交，结果可邮寄或电子证照下载。

（3）系统需求示例：
- 功能需求：支持 480 项政务事项的在线预约、材料预审、跨部门并联审批、办结通知、电子证照生成与下载。
- 非功能需求：单日最大办件量 50 万，并发用户数 5000，平均响应时间 < 2 秒，可用率 ≥ 99.9%，符合等保三级安全要求。

层次关系：业务需求（为什么做）→ 用户需求（做什么，由用户视角描述）→ 系统需求（怎样实现，开发者视角详细规格）。业务需求自上而下分解为多个用户需求，每个用户需求进一步细化为可度量的系统功能需求与非功能需求。

**问题 2：需求获取技术识别与适用场景**

- **JAD 联合应用开发研讨会**：多人多角色（12 个委办局）协同获取需求，适合跨部门、跨利益方的复杂系统，效率高、共识快。
- **观察法（跟岗）**：针对高频具体业务流程（新生儿登记、企业开办），深入一线还原真实场景，适合业务复杂、用户难以清晰表述的场景。
- **问卷调查**：覆盖广泛用户群体（企业、群众），量化分析痛点，适合大规模干系人采样与优先级决策（材料重复提交率 78% 等量化结论）。
- **原型法（抛弃型原型）**：可视化界面与交互，降低需求理解偏差，适合界面交互复杂、用户难以描述的"软需求"。

**问题 3：分析模型构建与互补**

本项目应构建以下分析模型：

1. **数据流图（DFD）**：自顶向下分解"一网通办"的总业务流程，从顶层（群众/企业提交申请 → 政务平台 → 委办局协同办理 → 结果反馈）逐步分解至每个事项子图，刻画"做什么"和数据流动。
2. **E-R 图**：建模政务事项、申请人、证照、办件结果、电子证照、材料清单等实体及联系，支撑数据库设计。
3. **用例图**：12 类用户角色（如个人办事者、企业办事员、委办局审批员）、480 个用例（含办件、查询、统计等），明确系统边界。
4. **状态转换图**：刻画办件生命周期状态（受理 → 预审 → 受理 → 在办 → 办结 → 归档），便于驱动工作流引擎。

互补理由：
- **DFD 回答"做什么"**：流程与数据流向；
- **E-R 回答"涉及什么数据"**：静态结构与持久化；
- **用例图回答"谁是用户、提供哪些功能"**：系统边界与功能划分；
- **状态图回答"对象如何演变"**：动态行为与控制流。

四种视角互为补充，构成"功能—数据—行为—边界"完整的需求视图。

**问题 4：需求变更控制流程**

需求变更控制机制：

1. **变更请求提出**：业务部门或产品经理提出"电子证照统一管理"变更请求（CR），填写变更申请表（变更描述、动机、紧急度）。
2. **影响分析**：系统分析师团队评估变更影响——
   - 范围影响：新增电子证照生成模块、证照库、证照核验接口；
   - 进度影响：需新增 60 人天开发、30 天集成测试；
   - 成本影响：增加约 80 万（含硬件、第三方核验对接费用）；
   - 质量影响：影响办件结果可追溯、等保合规要求；
   - 风险影响：电子证照法理效力需明确、需对接国务院电子证照库标准。
3. **CCB 评审**：变更控制委员会（业务方+技术负责人+架构师+测试负责人+财务）评审影响分析报告，决定批准/拒绝/推迟。
4. **变更实施**：批准后更新 SRS 与 RTM，相关设计文档同步更新，按变更基线重新规划迭代，进入开发。
5. **验证确认**：完成开发后由干系人验收，回归测试原 480 项事项不受影响，将新功能纳入基线 v2.0，关闭变更请求。

变更控制关键：所有变更必须走流程，影响分析透明披露，CCB 集体决策，防止范围蔓延；变更后必须重新建立基线。

## 记忆口诀

1. **需求三层级**：业务需求（为什么）→ 用户需求（做什么）→ 系统需求（怎样做），自顶向下分解、逐步细化。

2. **非功能五大类**：性（性能）、可（可用性）、安（安全）、维（可维护）、易（易用），FURPS+ 助记。

3. **需求获取技术组合**：JAD（多方协同）+ 观察（深入一线）+ 问卷（广覆盖）+ 原型（视觉化），四种互补。

4. **DFD 四要素**：外（外部实体）、加（加工）、存（数据存储）、流（数据流），逐层分解注意父图子图平衡。

5. **E-R 图三要素**：实（实体矩形）、属（属性椭圆）、联（联系菱形），基数 1:1/1:N/M:N，弱实体双矩形。

6. **SRS 四大特性**：正（正确）、完（完整）、一（一致）、验（可验证），加追踪性五件齐全。

7. **需求追踪矩阵（RTM）**：需求 ↔ 设计 ↔ 编码 ↔ 测试，正向反向双追溯，每条需求落实处、每段代码有根源。

8. **需求状态机**：建议 → 批准 → 实现 → 验证 → 关闭 / 拒绝 / 推迟，全程留痕可审计。

9. **需求优先级 MoSCoW**：Must（必须有）、Should（应该有）、Could（可以有）、Won't（暂不要），价值-复杂度决策。

10. **CCB 变更五步曲**：提出 → 影响分析 → CCB 评审 → 实施 → 验证，所有变更走流程、影响分析透明化、范围蔓延早遏制。

11. **FURPS+ 模型**：F 功能 / U 易用性 / R 可靠性 / P 性能 / S 可支持性，+ 号含设计约束、实现接口、物理需求。

12. **用户故事三要素**：角色（As a...）+ 目标（I want to...）+ 价值（So that...），从用户视角描述需求。
