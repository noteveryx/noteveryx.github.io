# （高级）系统分析师 · 第55次学习（2026-10-23）

**主题**：遗留系统现代化 —— 绞杀者模式、遗留系统改造决策矩阵与数据迁移工程

---

## 今日核心概念

### 1. 遗留系统的本质定义

**遗留系统（Legacy System）不是"老旧的系统"，而是"仍在运行、承载核心业务、且难以修改的系统"。**

三个要件缺一不可：
1. **仍在运行**（不是已下线的历史系统）
2. **承载核心业务**（不是边缘工具）
3. **难以修改**（不是"我们不想改"而是客观上改不动）

**关键认知**：一个用 COBOL 写在 1985 年、至今每天还在跑的系统叫遗留系统；一个上周刚用 Java 写的、代码没人看懂、没有任何文档、每次改动都要停机的系统，**同样是遗留系统**。技术新旧不是判据，**可维护性**才是。

### 2. 遗留系统的四大特征

| 特征 | 表现 | 后果 |
|---|---|---|
| **技术陈旧** | COBOL/Fortran/老式VB、单机部署、专用硬件 | 人才断层，无法招聘 |
| **文档缺失** | 无需求文档、无设计文档、只有源码 | 改一行要读三万行代码 |
| **架构僵化** | 单体巨石、紧耦合、修改影响面不可预测 | 改 A 崩 B |
| **数据锁定** | 数据结构混乱、字段含义靠口口相传 | 迁移即灾难 |

### 3. 遗留系统现代化四大策略

#### 策略一：绞杀者模式（Strangler Fig Pattern）

由 Martin Fowler 提出，源自**绞杀榕**（澳洲榕树，气根缠绕宿主树生长，宿主死后榕树独立成树）。

**核心机制**：

```
[客户端] → [门面/路由层 Facade] → ┬→ [新系统 A]
                                        ├→ [新系统 B]
                                        └→ [遗留系统]
```

- 在遗留系统前面加一层**路由/门面（Facade）**
- 新功能一律建在新系统里
- 老功能通过门面转发到遗留系统
- 随着迁移推进，路由规则逐步把流量从"遗留"挪到"新"
- 最终遗留系统流量归零，可以关停

**适用前提**：功能边界可切分、请求可在门面层识别并路由。**若所有功能共享同一套数据且互相调用，绞杀者模式会退化成"门面变成第二个遗留系统"。**

#### 策略二：防腐层（Anti-Corruption Layer，ACL）

Martin Fowler 另一模式，解决**新系统对接老系统**的问题。

- 防腐层是一个**翻译层**，把遗留系统的丑陋模型翻译成新系统的干净模型
- **防止"泄漏"（Leakage）**：遗留系统的糟糕设计不能渗透进新系统
- **防止"同化"（Corruption）**：新系统不能为了图省事，直接用遗留系统的数据模型和接口

**适用场景**：遗留系统无法改造（黑盒、只提供接口）、且新系统需要长期共存。

#### 策略三：修修补补（Patch and Let Die）

- 对**价值低、风险高**的遗留系统，只做必要的安全补丁，**任其自然死亡**
- 不再投入重构，**规划替代品**
- 适用：业务价值已萎缩、替代方案成熟

#### 策略四：大爆炸式重写（Big Bang Rewrite）

- 一次性用全新系统替换全部功能
- 理论上最干净，实践中最危险

**大爆炸的致命缺陷**：
1. **双倍维护成本**：重写期间新老系统并行，团队分裂、维护两套
2. **需求冻结悖论**：业务部门不愿在重写期间配合做需求调研，导致交付时才发现功能缺失
3. **一次性风险**：项目失败则业务停摆，无退路
4. **历史经验丢失**：老系统的"怪异行为"往往是踩坑换来的，新系统一旦照搬"设计"而不知其原因，就会重蹈覆辙

**结论**：大爆炸适用于"**系统本身没有业务价值、只是在维持一个必须存在的东西**"（如合规要求必须有的系统），而**不适用于核心业务系统**。

### 4. 遗留系统改造决策矩阵

| 业务价值 | 技术状况 | 改造策略 | 说明 |
|---|---|---|---|
| **高** | **差**（陈旧、文档缺失） | 绞杀者 + 防腐层，分模块渐进 | 主流路径，边改造边产生价值 |
| **高** | **中**（技术不算新但可维护） | 局部重构 + 渐进替换 | 成本最低 |
| **高** | **好**（技术新但业务耦合紧） | 架构改造（解耦），保留技术栈 | 动架构不动技术 |
| **低** | **差** | 修修补补 + 规划替代 | 不投入 |
| **低** | **好** | 保留运行，不做变更 | 冻结 |

**决策的三条原则**：
1. **按业务价值排序，不按技术新旧排序**——先改业务最痛的那块
2. **按模块切分，不按技术层切分**——按层切分会导致"半新半旧"的组件，排查问题时找不到归属
3. **每个切片都要能独立产生价值**——否则改造期间无法向业务方证明 ROI，改造会中途失去支持

### 5. 数据迁移工程（本节是考试重点中的重点）

#### 5.1 数据迁移的六个步骤

1. **数据剖析（Profiling）**：源数据的质量、分布、一致性分析。**没有剖析就不要谈迁移**
2. **映射设计（Mapping）**：源字段 → 目标字段的映射表，含转换规则、默认值、异常处理
3. **数据清洗（Cleaning）**：处理缺失、重复、格式不一致、编码不统一
4. **转换（Transformation）**：业务逻辑转换（如"性别：1/2/0" → "男/女/未知"）
5. **装载（Loading）**：全量装载 / 增量装载 / 双写
6. **验证（Validation）**：记录数对账、金额对账、业务抽样验证、参照完整性检查

#### 5.2 数据清洗的六类典型问题

| 问题类型 | 典型表现 | 处理方法 |
|---|---|---|
| **缺失值** | 关键字段为空、非关键字段为空 | 关键字段：拒收/补默认值/人工补录；非关键：留空 |
| **重复记录** | 完全重复、无主键重复 | 按业务主键去重，完全重复直接合并 |
| **格式不一致** | 日期"2026/1/1"与"20260101"、手机号带区号 | 统一格式函数 + 异常隔离 |
| **编码不统一** | "北京市"与"北京"、"110101"与"110101000000" | 建立标准码表，做映射 |
| **逻辑冲突** | 出生日期晚于入职日期、结束日期早于开始日期 | 业务规则校验 + 分级处理 |
| **冗余与不一致** | 同一实体在多表重复存储且不一致 | 单一数据源 + 主数据管理 |

**关键原则**：**清洗规则必须业务确认，不能由技术单方面决定。**"性别字段 0 到底是什么意思""状态码 9 是作废还是待审核"，技术部门猜不出来。

#### 5.3 迁移策略三种

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **一次性全量** | 停机、导全量、验完切换 | 简单、无双写一致性问题 | 停机窗口长，风险集中 | 小系统、低变更频率 |
| **增量同步 + 割接** | 双跑一段时间，最后割接 | 停机窗口短 | 需要 CDC/定时增量 | 大多数生产系统 |
| **双写（Dual Write）** | 新老系统同时写 | 无停机 | **双写不一致风险极高**，需对账补偿 | 特定场景，需强对账 |

**双写的三大风险**：
1. 写入成功但对侧失败 → 数据不一致
2. 顺序错乱（事务边界不同）→ 状态机错乱
3. 补偿逻辑本身就是新的 bug 源

**因此双写必须有配套的对账机制与补偿机制，且对账周期至少覆盖一个完整业务周期（如订单的全生命周期）。**

#### 5.4 数据验证的三层

1. **数量层**：源表行数 = 目标表行数（按映射关系加权计算，如"1 个订单 → 1 订单 + 2 个订单项"）
2. **金额层**：总金额、税额、折扣分别对账，允许千分之几的舍入误差
3. **业务层**：抽样 20-50 条做端到端业务验证（从订单到报表能算对），以及**分布一致性**（年龄段分布、区域分布是否与源一致）

**分布一致性是最容易发现问题的一层**：数量对、金额对，但年龄分布偏了，说明有隐性过滤条件丢失。

## 三个常考陷阱

### 陷阱一：认为"技术旧 = 必须重写"

**错。** 判断依据是"**改的成本 vs 改的价值**"，不是技术新旧。很多遗留系统的真正问题是**没有文档、没有人懂**，而不是用了 COBOL。解决"没人懂"的成本远低于重写。

更危险的是"**沉没成本谬误**"：因为投了很多钱在这套系统上，所以要继续投。但过去投入的成本已经是沉没成本，与"是否继续投入"无关。

### 陷阱二：绞杀者模式被误用为"万能解法"

绞杀者模式的**隐藏前提**是"**功能可切分 + 门面能路由**"。三个前提不满足时，绞杀者模式会失败：

1. 功能高度耦合（改 A 必然改 B）→ 无法切分
2. 请求无法在门面识别（一个请求触发大量内部交互）→ 无法路由
3. 数据共享同一套且无清晰归属 → 新旧系统都改同一张表，产生写冲突

**绞杀者模式的本质是"把重构工作按时间切片"，不是"把重构工作变简单"。** 如果一个变更本身需要牵一发动全身，切片也救不了。

### 陷阱三：数据迁移只验证"数量"和"金额"

**只对数量和金额是最常见的偷懒。** 数据迁移中，**数量对、金额对，但业务错乱**是高频事故：

- 时间字段时区偏移（原本东八区的时间被当成 UTC）
- 状态码映射错误（"已完成"映射成"已取消"）
- ID 映射关系断裂（外键指向错了但恰好有同号 ID，所以"看起来对"）

**因此必须做业务层验证，尤其是分布一致性与端到端链路验证。**

## 案例分析题

### 案例 1 — 遗留系统改造与数据迁移

**题干**：某市医保局现有"结算系统"是 2009 年建设的，用 Delphi 开发，Oracle 数据库，单体部署，无源码管理，无设计文档。原开发公司已倒闭。该系统每日处理 12 万笔结算业务，年度医保基金拨付 47 亿元。系统计算逻辑复杂，涉及起付线、封顶线、目录范围、违规扣减等规则，业务人员多次手工核对仍不敢完全相信系统结果。局方提出"三年内完成国产化替代，全面重构为新系统"。

**现状调查**发现：

- 系统**没有源码管理**，仅有一份编译后的 EXE 和数据库脚本
- 有一位退休返聘的老专家能看懂部分计算逻辑，但不愿接受"知识转移"的访谈安排，理由是"我走了你们也学不会"
- 数据库中 `HIS_ITEM` 表有 8 万条记录，其中 1.2 万条 `ITEM_NAME` 字段为空，且这些记录均被 15 万条明细表引用
- 明细表 `HIS_DETAIL` 中有 30 万条记录，其中 5% 的 `BIRTH_DATE` 是"19000101"
- 局方要求新系统必须"零停机"上线

**问题**：
1. 该项目最关键的前置工作是什么？请按优先级列出三项。
2. 请用遗留系统改造决策矩阵分析该系统应采取的策略。
3. 针对"退休老专家不愿知识转移"，项目经理应如何应对？
4. 针对 `BIRTH_DATE` 为 19000101 的 5% 记录，迁移时应如何处理？给出你的处理方案。
5. "零停机上线"在数据迁移上如何实现？给出技术方案，并说明其主要风险。

**参考答案**：

**问题 1 — 三项最关键前置工作**：

1. **业务规则逆向梳理与知识抢救（最高优先级）**。这是**唯一有时效性的工作**——老专家一旦真正离开，规则就永久丢失。每一条起付线、封顶线、违规扣减规则，都必须沉淀为可测试的规则文档或可执行的规则用例。这一步**必须在写一行新代码之前完成**，且**不能靠技术团队猜**。
2. **数据剖析与质量评估**。8 万条 ITEM_NAME 为空、30 万条 BIRTH_DATE 为 19000101，说明数据质量严重不达标。必须先统计**全量问题的规模与分布**（不止这两张表），形成数据质量基线报告，作为迁移工作量估算的依据。
3. **现有系统行为基线建立（黑盒特征测试）**。通过历史数据回放 + 结果比对，建立"现有系统对同一输入产生什么输出"的基线。这是后续验证新系统正确性的**唯一裁判标准**。

**顺序不可颠倒**：老专家的知识一旦丢失，项目没有任何补救措施；而数据剖析可以在专家还在时并行进行。

**问题 2 — 决策矩阵应用**：

| 业务价值 | 技术状况 | 判定 |
|---|---|---|
| 高（医保基金拨付 47 亿，核心业务） | 差（Delphi、无文档、原厂商倒闭、无人可维护） | → **绞杀者 + 防腐层 + 数据迁移，分模块渐进** |

**结论**：应采用**绞杀者模式 + 防腐层**的组合，**明确反对大爆炸式重写**。

理由：
- 业务价值极高，**绝不能承受大爆炸失败导致业务停摆的风险**
- 计算逻辑复杂（起付线、封顶线、目录范围、违规扣减），但**可按业务域切分**（门诊结算、住院结算、异地结算、DRG 支付是相对独立的域），具备绞杀者模式的前提
- 无源码（"无源码管理"意味着只有编译产物），**必须通过防腐层做黑盒对接**，而非重新实现后再替换

**分阶段建议**：
- 第一阶段（6-12 个月）：防腐层上线 + 规则引擎化 + 数据质量治理，**不换主流程**
- 第二阶段（12-24 个月）：先切**异地结算**（复杂度最低、外部依赖最强），验证整链路
- 第三阶段（24-36 个月）：切住院结算 → 门诊结算 → DRG

**问题 3 — 应对老专家不愿知识转移**：

**第一步：理解动机，不要急于说服。** 老专家说"我走了你们也学穷"，这话有两层含义：一是担心失去不可替代性而被动退出，二是真的认为无法教会。这种判断通常是**有依据的**——他见过太多"访谈完就扔一边"的先例。

**第二步：解决激励与安全感问题（关键）**。
- 转为**顾问角色**而非"被替代者"：新系统的规则引擎设计、验收标准制定，由他署名负责，给足尊重与决策权
- **利益绑定**：咨询费按规则覆盖率与里程碑付款，而非按时间计费；或约定新系统上线后的运维顾问角色
- 明确"**不会因为你离开而降低对你的评价**"，把他的顾虑从"组织风险"转为"专业声誉"

**第三步：改变知识转移的方式，不要只靠访谈**。
- **强制他出题而不是答题**：让他出 200 道"刁钻案例题"（含边界值、异常场景），团队作答，他只做"对/错+为什么"。这比让他讲解更能引出隐性知识
- **录屏而非录音**：要求他**在真实系统上演算一遍**（打开数据库、写 SQL、比对结果、解释为什么），全程录屏。这个过程包含大量"我认为是这样"的口头知识
- **结对工作**：让他和新人**一起**改一段真实逻辑，而非他讲新人听

**第四步：制度性保障**。
- 将规则文档纳入**代码评审流程**，让规则成为可评审的资产而非个人记忆
- 设置**知识交接的验收标准**（规则覆盖率 ≥ 95% 且通过黑盒回归测试），与咨询费挂钩

**关键认知**：这不是技术问题，是**激励设计问题**。把老专家当成"必须被榨取知识的资源"是最失败的姿态。

**问题 4 — BIRTH_DATE 为 19000101 的 5% 记录**：

**第一步：先判定业务含义，不要动手改**。19000101 可能有多种含义：技术默认值、历史录入遗留、真实但不可知、隐私脱敏。**必须先查清楚这 5% 数据的业务归属**（是哪类患者、按时间分布、按机构分布），分布本身就是重要线索——如果集中在某个年份录入，很可能只是技术默认值。

**处理方案（按优先级）**：

1. **先查源系统与其他数据源**：医保参保人员库、个人参保档案、身份证号（可反推出生日期）。**如果能从身份证号可靠推出出生日期，就直接补齐，这是最优解**。
2. **无法补齐的，按业务影响分流**：
   - **影响待遇计算的**（起付线常与年龄挂钩、部分疾病有年龄限制）：**单独隔离，不参与自动计算**，转人工核档，在 30 个工作日内补录；在此之前该记录按"待核档"状态，不发放也不追回
   - **仅用于统计报表的**：在数据仓库层做映射处理（映射为"未知"档），**不要污染业务库**
3. **建立数据质量标记位**：新增字段 `BIRTH_DATE_VALID`（1=已核实、0=未核实），并在所有下游使用处强制判断。**绝不能默默地把 NULL 当成 1900 年去计算年龄**。
4. **在迁移验收中显式列出**：这 5% 记录（1.5 万条）的处理状态必须作为迁移验收报告的独立条目，向业务方交代。

**三个必须避免的做法**：
- ❌ 直接把 19000101 改成 1900-01-01 并当作真实数据使用 → 老年患者年龄巨大，可能触发错误的高龄待遇
- ❌ 直接设为 NULL → 下游计算可能 NPE 或按最小年龄处理
- ❌ 直接丢弃这 5% → 金额对账必然不平，且这些患者可能是重点保障对象

**关键原则**：**脏数据处理的第一步永远是"识别"，不是"清洗"。**

**问题 5 — 零停机上线方案与风险**：

**技术方案：增量同步 + 割接（Cutover）**

```
阶段一【影子运行 T-90 天】
  旧系统：唯一权威源，正常处理业务
  CDC 增量同步：旧库 → 新库（基于日志捕获，秒级延迟）
  新系统：同步数据 + 影子计算，不返回结果给业务
  每日对账：新旧结算结果逐笔比对，差异率必须 < 0.01% 且全部可解释

阶段二【双跑核验 T-30 天】
  新系统开始承接部分只读查询与报表
  结算仍以旧系统为准，新系统结果仅供核对
  差异清单逐条归因：是规则差异还是缺陷（规则差异需确认新规则更优）

阶段三【割接 T 日】
  T-1 日 23:00 停止旧系统新增业务，做最终增量同步（通常 < 5 分钟）
  校验：新库关键表行数、金额、状态机总量三方对账（源库=新库=报表）
  对账通过 → 22:00 切换流量路由（旧域名/接口指向新系统）
  22:30–23:00 保留旧系统"待命可回滚"状态
  23:00 正式启用新系统

阶段四【回滚预案 T 日 + 7 天】
  割接后 7 天内保留回滚能力：
  - 旧系统数据库保持只读快照可恢复
  - 新系统产生的业务数据可反向同步回旧库
  - 回滚触发条件预定义（如割接后 2 小时内出现 P1 问题）
```

**主要风险**：

1. **规则差异被误判为"新系统 bug"（最高风险）**。旧系统的怪异行为往往是历史踩坑的结果。**必须在影子运行阶段逐条确认：差异是"旧系统错了"还是"我们理解错了规则"。** 判断依据是业务文件与政策规定，**不能以旧系统输出为准**。
2. **最终增量同步窗口超预期**。5 万笔在途事务的同步可能远超 5 分钟。**必须先在演练环境全流程压测一次，用实测数据而非估算来定割接时间。**
3. **双写/同步链路的单点故障**。CDC 通道中断会导致新库数据滞后。**必须有心跳监测 + 滞后告警 + 断点续传能力。**
4. **回滚不可行**。如果割接后新系统已产生只有新系统认识的新业务（如新政策项），反向同步旧系统会失败。**因此"可回滚窗口"必须限定在"新系统未产生不可回迁业务"之前**，通常不超过 7 天。
5. **历史数据迁移遗漏关联**。DEPT 表有 15 万条引用空 ITEM_NAME 的记录，割接前若未清理或未做映射，**新系统的报表与对账模块会直接崩溃**。数据质量治理必须**先于**割接完成，不能并行。

## 记忆口诀

- 口诀 1：**遗留三要件**——还在跑、扛核心、改不动。技术新旧不是判据。
- 口诀 2：**四大策略**——绞杀者渐进、防腐层翻译、修补等死、大爆炸慎用。
- 口诀 3：**绞杀者三前提**——功能可切分、门面可路由、数据有归属。
- 口诀 4：**防腐层防两件事**——防泄漏（脏模型渗入新系统）、防同化（新系统迁就老接口）。
- 口诀 5：**大爆炸四宗罪**——双倍成本、需求冻结、一次风险、经验丢失。
- 口诀 6：**迁移六步**——剖析、映射、清洗、转换、装载、验证。
- 口诀 7：**清洗六类病**——缺失、重复、格式、编码、逻辑冲突、冗余。
- 口诀 8：**验证三层**——数量对账、金额对账、业务分布与端到端。
- 口诀 9：**双写必带对账**——双写 = 一致性风险 + 补偿逻辑，必须配套。
- 口诀 10：**影子运行再割接**——T-90 影子对账、T-30 双跑、T 日割接、7 天可回滚。

## 补充：今日新增的架构判断（面试可直接用）

**问：为什么绞杀者模式比大爆炸更常用？**
答：三个层面——① 风险层面，大爆炸是"一次定生死"，失败则业务停摆；绞杀者每一步都能独立验证，失败可局部回滚。② 认知层面，大爆炸要求在设计阶段就理解全部业务，绞杀者允许"先做出一个切片，用真实的用户反馈来完善对业务的理解"。③ 组织层面，大爆炸往往伴随组织对立（老系统团队 vs 新系统团队），绞杀者是渐进的，冲突可被管理。

**问：绞杀者模式什么时候会失败？**
答：当**变更无法隔离**时。典型信号：每次改动都需要同时修改多个模块、需求本身横跨整个系统、共享数据库表被新旧系统共同读写且无归属划分。这时绞杀者只是把重构工作按时间切片，切不掉耦合的本质，等于用更长的工期做一次大爆炸，且中途不能停。
