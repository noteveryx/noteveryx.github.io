## 今日核心概念

### 1. 管道-过滤器架构风格（Pipe-Filter）

定义：管道-过滤器风格把处理过程分解为一系列独立的处理单元（过滤器），数据像水一样以流的形式从一个单元流向下一个单元，每个过滤器读取输入流、处理、写出输出流，系统控制流由管道的连接关系隐式给出，不存在中央控制组件。过滤器之间只通过数据格式（记录结构）耦合，而不由调用关系耦合。

关键要点：

- **核心特征**：数据流驱动的顺序处理；过滤器独立封装、单一职责；过滤器之间通过数据格式契约解耦；增删过滤器不改变整体结构。
- **适用条件**：处理流程可清晰切分为稳定的阶段；数据在流水线中持续变形（采集→清洗→转换→校验→入库）；各阶段可由不同团队并行开发。
- **典型代表**：Unix 管道、编译器（词法→语法→语义→代码生成）、ETL/ELT 数据管道、日志采集与指标计算流水线、日志归一化管道。
- **两大优势**：过滤器可独立复用与替换（同一数据源可接不同后端）；可独立测试（单过滤器单元测试 + 管道级集成测试）。
- **四大固有缺陷**：① 过滤器内部多批次处理会引入上下文切换与序列化开销；② 每个过滤器的数据格式转换成本累加，最慢过滤器决定整体吞吐（瓶颈效应）；③ 异常处理困难——任一环节失败需定义统一的回滚/补偿语义；④ 缺乏全局控制流，难以表达复杂条件分支与回溯（数据驱动模型正是为解决该缺陷而生）。
- **性能要点**：应尽量在管道内部保持同一数据格式直传，仅在必要边界做转换；过滤器之间用批量（chunk）而非单条传递；避免将昂贵的正则、加密放在管道串行主干上（可拆支管道并行后汇聚）。
- **架构取舍**：管道-过滤器提高可修改性与可测试性，但牺牲了全局编排能力与一致性控制力；用于"数据流水线"环节是最佳实践，用于"复杂业务决策"环节则需补充编排层。

### 2. 微内核架构风格与插件化契约

定义：微内核（Microkernel，又称插件化架构）风格将系统划分为一个稳定的核心（Core）和一组可插拔的功能模块（Plugin）。核心只实现最基础的能力并对外暴露一组稳定、明确的扩展点（接口/契约），具体业务功能以插件形式在运行期装入，通过扩展点调用，无需修改核心代码即可增加新功能。宏内核（Monolithic Kernel）则把尽可能多的服务下沉到内核态，微内核把服务上移到用户态，以进程隔离换取可靠性。

关键要点：

- **核心职责最小化**：核心负责插件注册与生命周期管理、插件间通信、配置与路由、公共服务（日志、缓存、事务）；业务规则一律留在插件内。
- **扩展点设计三要素**：① 接口契约的**粒度**（过粗则僵化、过细则组合爆炸）；② 契约的**版本兼容性**（向后兼容优先，破坏性变更必须升主版本号并提供并行适配层）；③ 插件的**注册与发现机制**（配置化注册中心 + 依赖注入）。
- **六大优势**：功能可独立开发与发布（上线周期从"改主程序"缩短为"上线一个包"）；故障隔离（插件崩溃不拖垮核心）；定制化交付（不同部门/地区加载不同插件组合）；可替换（同一扩展点可有多个实现）；可测（插件可独立压测）；可灰度。
- **四大风险**：① 插件契约一旦发布难以更改，契约设计失误代价极高；② 插件间跨进程/跨容器通信的序列化开销与延迟；③ 插件版本冲突与依赖地狱（需依赖收敛策略）；④ 核心与插件的调试链路变长，定位问题需跨边界追踪。
- **政务审批场景适配**：把审批规则（受理条件、审批环节、时限计算）做成规则插件，规则变更走"插件灰度→校验→全量"流程，核心审批引擎不变，实现"规则可配置、引擎不改造"。
- **与产品化架构的边界**：微内核强调"核心稳定、插件可换"，与 SaaS 多租户、容器化部署结合时表现为"同一内核 + 不同插件包"的交付形态；插件隔离强度决定可用性高低（进程隔离 > 线程隔离）。

### 3. 事件驱动架构（EDA）与事件溯源、CQRS

定义：事件驱动架构以"事件"（业务事实的不可变通知）作为组件之间通信的媒介，生产者只声明"发生了什么"并发布事件，不感知消费者是谁；消费者订阅感兴趣的事件并独立处理，从而在时间与空间上双重解耦。事件溯源（Event Sourcing）把事件本身作为系统状态的唯一事实源，当前状态由事件序列重放重建；CQRS（命令查询职责分离）把改变状态的命令侧与读取状态的查询侧分离成两套模型。

关键要点：

- **两类事件要分清**：**事件通知**（Event Notification，只携带事件标识与关键字段，接收方可能回查）与**事件携带状态传输**（Event Carried State Transfer，携带完整状态快照，减少回查）；大规模场景推荐后者 + 定期快照，避免"事件风暴 + 回查风暴"。
- **三大典型模式**：① 事件通知（解耦订阅）；② 事件溯源（以事件序列为唯一事实源，天然具备完整审计链，可回放、可重建状态）；③ CQRS（命令侧保证不变量，查询侧按需建模，写读分离、各自优化）。
- **四大优势**：生产消费彻底解耦；异步削峰，系统具备"最终一致"特性；事件溯源天然满足审计与追溯要求（不可变事件链 + 哈希链可防篡改）；可回放重放，支持数据修正与"时间旅行查询"。
- **五大风险与对策**：① **最终一致性**——对账与补偿（定时对账 + 人工兜底）；② **重复投递**——消费端幂等（业务唯一键 + 去重表 + 状态机判重）；③ **消息乱序**——按业务实体键分区（同一办件的事件落到同一分区）+ 序列号校验 + 乱序缓冲；④ **事件模式演进**——事件版本号 + 只增字段不改语义 + 消费者容忍未知字段 + 契约测试；⑤ **调试困难**——提供事件回放器、链路 ID 贯穿、事件溯源可视化时间线。
- **消息中间件选型要点**：Kafka 面向高吞吐日志型事件流、保证分区有序；RocketMQ 支持事务消息、延迟消息、顺序消息，适合业务事务一致性；RabbitMQ 灵活路由、复杂分发规则； Pulsar 存算分离、多租户。
- **可靠投递语义**：至少一次（at-least-once）+ 消费幂等是工程上最常用组合；严格一次（exactly-once）依赖端到端事务或幂等写入，业务层仍必须做幂等兜底。

### 4. 系统集成模式与集成中间件

定义：系统集成模式是不同系统之间建立数据或控制流转关系的结构性约定；集成中间件（ESB、消息中间件、数据集成平台）为集成提供协议转换、格式转换、路由分发、编排与监控等公共能力，使异构系统无需点对点耦合即可互联。

关键要点：

- **五类基础集成机制**：① 文件传输（批量、低频、可审计，适合离线交换与遗留对接）；② 共享数据库（成本最低但耦合最重，破坏性 schema 变更会引发连锁故障，仅适合稳定共享目录）；③ 消息传递（异步、解耦、可重放，适合事件与任务分发）；④ 远程过程调用（同步、低延迟、强耦合，适合查询类调用）；⑤ REST/HTTP 服务（契约化、跨组织、生态成熟，适合对外服务开放）。
- **三层集成视角**：**数据集成**（ETL/数据交换，解决"数据要能拿到"）；**控制集成**（API 编排/工作流，解决"动作要能协同"）；**业务集成**（流程贯通，解决"业务要能闭环"）。成熟度路径：数据集成 → 控制集成 → 业务集成。
- **ESB 的双面性**：价值在于统一协议转换、集中管控、可视化编排、复用企业级能力；风险在于总线成为单点故障与性能瓶颈、编排逻辑沉淀成"总线垃圾场"、排障链路变长、演进时难以拆分。判断原则：**跨组织、异构协议、需统一管控的集成走总线；域内高频调用、同质协议的调用走轻量网关/直连**。
- **集成契约治理**：接口版本策略（URL 版本 vs 请求头版本 vs 契约版本）、向后兼容规则（新增可选字段、禁止删改必填字段）、限流熔断降级、幂等与防重放、链路追踪 ID 贯穿、SLA 与错误码规范。
- **政务数据共享的现实约束**：共享交换必须解决"数据质量不达标""权责不清""重复建设""安全问题"四类根因；技术上要用可信交换节点、目录服务、数据血缘与质量稽核兜底，而非仅靠接口对接。

### 5. 4+1 视图与架构决策记录（ADR）

定义：4+1 视图（4+1 View Model）由 Kruchten 提出，用多个互补视图描述同一系统架构：逻辑视图（功能分解与抽象）、进程视图（并发与通信）、开发视图（代码组织与依赖）、物理视图（部署与运行映射），加 1 个贯穿性场景（scenarios）作为验证各视图一致性的检验标准。架构决策记录（Architecture Decision Record，ADR）以轻量文本逐条固化架构决策的上下文、结论、备选方案与后果，形成可追溯的决策链。

关键要点：

- **四视图职责划分**：逻辑视图回答"系统由哪些抽象构件组成"；进程视图回答"运行时如何并发与通信"；开发视图回答"源码如何组织与构建"；物理视图回答"构件部署到什么硬件与网络节点"。四者通过场景串联，场景变化会牵动视图联动。
- **视图与视点（Viewpoint）**：ADD（架构描述方法）中"视图（View）= 视点（Viewpoint）+ 模型（Model）"，不同利益方关注不同视点（用户、开发、运维、安全），视点差异是视图分裂的根因。
- **架构描述文档（ADD 产物）**：架构概览、视图、视点说明、模型、视图间关联（映射表）、模型间关联、设计约束与决策依据。
- **ADR 四要素 + 四状态**：背景（Context）、决策（Decision）、备选与后果（Alternatives/Consequences）、状态（提议中/已采纳/已废弃/被取代）；可追溯"为什么当时这么选"，避免后人重复讨论与推翻决策。
- **决策与质量属性的耦合**：每个架构决策都应关联它试图改善的质量属性（性能/可用性/安全/可修改性/易用性/可测试性）及权衡成本；无质量属性依据的架构决策属于"无主张的架构"。
- **治理落地**：ADR 入库并纳入设计评审；架构评审（ATAM/ARID）按节奏（每重大版本或每季度）运行；架构符合性检查纳入 CI（依赖规则、接口契约测试、事件模式兼容性测试）。

## 案例分析题

**题目**：

某省政务服务一体化平台（"一网通办"）已运行 5 年，接入 40 个省级部门、1200 余项政务事项，日均办件 12 万件，峰值并发 3000。近一年暴露出四类问题：

1. 各部门共享数据格式严重不统一（如企业基本信息字段名、编码规则、证照类型各不相同），数据清洗依赖人工编写脚本，脚本散落在运维个人电脑中，错误无法追溯。
2. 审批规则（受理条件、审批环节、时限计算、特殊情形）统一硬编码在主程序中，任何一条规则调整都需要修改主程序并停机发布，规则上线平均周期 15 天，现场经常出现"系统停着发版、窗口无法收件"的情况。
3. 办件状态变更无法完整追溯（哪一步、什么时间、由谁、依据什么材料做了变更），上级稽核、信访核查、审计检查均需人工调取日志还原，单次核查平均耗时 2 天，且曾发生日志被误删无法还原的情况。
4. 跨部门状态变更（如"受理通过→已转件至下一环节"）通过定时轮询对方系统数据库表实现，通知延迟最长 6 小时，遇对方系统维护则直接丢失；对外 API 支撑能力不足，部分高频接口直接连库查询，数据库压力大时接口整体不可用。

该省拟启动平台重构（保留现有对外服务与办件数据，采用渐进式改造，不允许全量停机切换）。项目组提出方案：建设"数据共享加工管道"、将审批规则改造为"可插拔规则组件"、引入"事件总线"驱动跨部门流转与全量审计、并为对外接口增加统一网关。

请回答以下问题：

**问题 1**：该方案中的"数据共享加工管道""可插拔规则组件""事件总线"分别对应哪种架构风格/架构机制？说明选择依据，并指出每种选择在重构场景下可能引入的 2 项主要风险及应对措施。

**问题 2**：平台需要与 40 个部门系统对接，涉及批量数据交换、办件状态实时通知、跨系统审批结果查询、以及新开发的小时级时效查询接口。请为这四类场景分别选择集成模式，并说明企业服务总线（ESB）在本项目中应当"用"还是"不用"，给出判断理由。

**问题 3**：项目组拟对"办件状态"采用事件溯源与 CQRS，请判断该选择的适用性，说明事件存储与读模型的设计要点，并逐一给出应对"重复投递、消息乱序、事件模式演进、最终一致性"四类风险的具体技术措施。

**问题 4**：请用 4+1 视图的视角给出该重构后系统的架构描述要点（至少覆盖逻辑视图、进程视图、部署视图三个视图的要素），并结合本题场景做 3 组质量属性权衡分析（指出敏感点、权衡点与代价）。

**问题 5**：针对 40 个部门的规则组件与事件模式并存演进，给出基于架构决策记录（ADR）的治理方案与分阶段演进路线图，并给出 3 项可度量的架构治理指标。

**参考答案**：

**问题 1 参考答案**

（1）"数据共享加工管道" → 管道-过滤器（Pipe-Filter）架构风格。
选择依据：数据从各部门汇聚后，需经历"格式归一→编码映射→质量校验→主键匹配→入库/分发"等阶段清晰的连续加工，阶段边界稳定且可由不同团队并行建设，符合管道-过滤器"数据流顺序驱动、过滤器独立可复用可替换"的适用条件；现有散落脚本本质上是人工拼装的过滤器链，管道化后可纳入版本管理、统一调度与监控。
主要风险与应对：
- 风险①：过滤器逐段格式转换开销累加，且最慢环节决定整条管道吞吐。应对：管道内保持同一中间格式直传，仅在部门边界做一次转换；批量传输（chunk 批处理）替代逐条；对慢环节拆分并行支管道后汇聚；对关键转换环节加缓存与结果复用。
- 风险②：某一过滤器异常导致下游数据不完整且难以定位。应对：管道作业统一编排调度（可观测、可重试）；失败环节支持幂等重跑与位点（checkpoint）续跑；输出侧加"完整性校验 + 对账"关卡；每个环节埋点并与统一追踪 ID 绑定。

（2）"可插拔规则组件" → 微内核（插件化）架构风格，核心引擎 + 规则插件 + 稳定扩展点契约。
选择依据：需求变化最频繁、最需独立发布的恰是审批规则，而核心审批流程引擎是稳定不变的部分。插件化后规则变更由"改主程序 + 停机发布"变为"发布插件 + 灰度切流"，直接命中规则上线周期 15 天与窗口无法收件的痛点；不同部门可加载各自规则插件组合，天然支持定制化交付与灰度。
主要风险与应对：
- 风险①：扩展点契约一旦发布难以更改，规则形态多样化后被迫往核心里塞特例，演变为"内核膨胀"。应对：契约先做"最小可用 + 可扩展"设计，优先用配置化规则描述（决策表/DSL）+ 插件承载复杂逻辑的双层方案；建立契约评审机制与契约测试用例库；契约只允许"新增可选能力"，禁止破坏性变更，破坏性变更须升主版本并保留并行适配层。
- 风险②：插件间与核心间通信开销、版本冲突与排障链路变长。应对：插件按部门/业务域隔离部署（容器化，进程级隔离）以获得故障隔离收益；插件依赖统一版本收敛与镜像仓库管理；插件调用统一走带追踪 ID 的服务契约，出现问题可按"插件+版本+办件号"秒级定位；单插件异常熔断降级为默认规则，避免拖垮核心。

（3）"事件总线" → 事件驱动架构（EDA）机制，配套事件溯源与 CQRS。
选择依据：跨部门状态变更属于典型的"事实广播 + 多方响应"场景，生产者不应知道消费者是谁；轮询数据库表的方案既有延迟（最长 6 小时）又丢失通知、且直连他方数据库破坏数据所有权。改为事件发布订阅后，延迟可降到秒级、通知可靠投递、且新增消费方零成本接入，直接解决"通知延迟/丢失"和"直连他方库"两个问题；同时不可变事件链为问题 3 的全量审计提供天然底座。
主要风险与应对：
- 风险①：最终一致性导致跨部门状态短暂不一致，且异常时数据错乱难发现。应对：引入定时对账任务（双方按业务主键+状态+时间戳对账，差异告警并生成补偿工单）；对关键流程设置"超时未收到回执则自动升级/人工介入"的状态机；对外接口对未收敛状态返回明确的处理中标识而非错误。
- 风险②：消息乱序与重复投递导致状态机错乱（如已办结后又收到受理事件）。应对：以业务实体键（办件号）作为分区键保证同实体有序；消费端引入幂等表与状态机合法性校验，非法序事件丢弃并告警；对全局状态采用版本号/时间戳单调比较。

**问题 2 参考答案**

四类场景的集成模式选型：

| 场景 | 推荐集成模式 | 理由 |
|---|---|---|
| 批量数据交换（部门基础库、证照库同步） | 文件传输 / 批量数据接口 | 数据量大、时效要求相对宽松、非实时；文件传输成本低、可审计、可重放，天然适配定时批处理与人工核对场景 |
| 办件状态实时通知（转件、办结、退回） | 消息传递（事件发布订阅） | 要求秒级、可靠、不丢；生产者无需知道消费者，天然支持多部门/多系统同时订阅，失败可重投 |
| 跨系统审批结果查询 | 远程过程调用 / 同步服务调用（带超时熔断） | 查询是请求-响应语义，需即时返回结果；同步调用链路短、语义清晰，但必须设超时、降级与本地缓存，防止级联阻塞 |
| 新开发的小时级时效查询接口 | RESTful API + 网关统一发布 | 接口形态标准化、生态成熟、跨组织开放门槛低；配合网关做限流、鉴权、缓存、灰度，小时级时效在网关缓存与数据同步链路中即可满足 |

关于 ESB 的判断：**采用"轻量网关 + 有限 ESB"的混合策略，而不是把全部集成收敛到一条重型总线**。
理由：① 本项目存在明显的域划分（部门域、办件域、认证域、消息域），40 个部门的异构协议适配确实需要统一转换与管控，这部分用 ESB/集成平台承载合理；② 但高频查询（跨系统审批结果查询）与核心流程内部调用若全部走总线，会把总线变成单点瓶颈与延迟来源，且总线编排逻辑会不断沉淀为难以拆解的"垃圾场"；③ 因此建议：对外统一发布与协议转换用 API 网关，跨域异步事件走消息中间件而非总线同步转发，强一致的低频批量用文件/批量接口，ESB 仅保留在需要协议适配与复杂编排的集成场景。
配套措施：ESB 与网关均做多实例部署与限流熔断；每个集成点标注"域归属+协议+时效要求"，按上述四分类归档，禁止跨域随意直连。

**问题 3 参考答案**

适用性判断：**部分适用，需限定边界**。
- 适用部分：办件状态变更属于"不可逆、需留痕、需还原"的核心业务事实，且稽核与信访核查是刚性的审计需求，事件溯源能天然提供"完整可回放的变更链"，价值很高；同时办件详情查询读多写少、查询形态复杂多样（多条件组合、关联视图），CQRS 分离后可独立建模，收益明显。
- 不宜全面套用的部分：并非所有数据都需事件溯源。部门基础库、字典、附件元数据等若全部事件化，会带来存储膨胀、查询复杂化与运维成本剧增（收益递减）。建议：仅对**办件状态机相关事件**做事件溯源，参考数据采用"快照+变更日志"即可。
- 额外提示：事件溯源不等于加密不可篡改。若监管要求防篡改，还需叠加哈希链/签名与外部可信存证（如只追加存储、第三方时间戳），否则事件仍可能被有权限者删除。

设计要点：
- **事件存储**：选支持按业务实体键有序追加写入与按实体键/时间范围高效检索的存储（典型为消息日志型存储或具备多版本模型的数据库 + 事件表 + 乐观锁版本号）；事件不可变、以追加写为主，事件体含：事件 ID、全局序列号、实体 ID（办件号）、实体版本、事件类型、事件时间戳、来源、操作人/角色、关联材料引用、业务关键载荷、Schema 版本号。
- **事件模式演进**：事件携带 `schemaVersion`；演进只允许新增可选字段、禁止修改既有字段语义；消费者解析时容忍未知字段；破坏性变更采用"新事件类型 + 双写过渡期"；配套事件契约测试（Schema 注册与兼容性校验纳入 CI）。
- **读模型（查询侧）**：按查询场景建多套读模型（如办件概览读模型、部门待办读模型、时间线读模型、统计读模型），由事件消费者异步构建；读模型允许冗余存储与反范式化，不承担业务不变量校验；读模型可随时按事件重放重建，重建走旁路，不影响在线查询。

四类风险的具体技术措施：

| 风险 | 具体措施 |
|---|---|
| 重复投递 | 消费端幂等：以事件 ID 建去重表（唯一索引），重复即丢弃；业务侧再以"实体版本号单调递增"二次校验；状态机显式定义"仅接受合法前置状态的迁移"，非法迁移拒绝并告警；数据库写入与去重记录同事务提交 |
| 消息乱序 | 生产端按实体 ID（办件号）分区发送，保证同实体分区有序；消费端记录已处理的最大实体版本号，收到更低版本直接丢弃并落"乱序缓冲/异常表"人工核查；跨实体不保证有序，业务逻辑不得依赖全局顺序；必要处使用逻辑时钟/版本号而非时间戳判序 |
| 事件模式演进 | 事件体统一含 schemaVersion；语义化版本管理，破坏性变更升主版本并保留旧版本处理器一段过渡期（双写 + 双读）；字段只增不删不改语义；消费者忽略未知字段、缺失可选字段走默认值；契约兼容性检查纳入 CI 与发布卡点；建立事件目录（注册中心）公示 |
| 最终一致性 | 明确一致性边界：单实体内部强一致（同一分区有序 + 版本号校验），跨实体/跨部门最终一致；建立定时对账（按实体主键 + 状态 + 时间窗双向比对）与差异告警工单；对超时未回执的流程定义自动升级与人工兜底；对外接口以"处理中/待同步"明确返回而非报错；对一致性要求极高的关键动作（如资金、证照核验）不依赖事件，走同步调用 + 补偿 |

**问题 4 参考答案**

4+1 视角的架构描述要点：

- **逻辑视图**：构件划分为"渠道与展现层（Web 门户、移动端、窗口端、自助机）、接入与网关层（API 网关、认证鉴权、限流熔断）、办件核心域（受理、流程引擎、规则引擎插件宿主、状态机、办件服务）、集成域（数据共享加工管道、批量交换、事件总线/消息中间件、ESB）、支撑域（用户与组织、证照与印章、支付与送达、附件与电子材料）、数据域（主数据、读模型库、事件存储、检索与报表）、平台运维域（配置中心、注册中心、监控与追踪、作业调度、审计与日志）"；核心抽象构件为"办件（Aggregate）""流程定义""规则插件""事件"四类。
- **进程视图**：并发与通信——网关多实例 + 无状态；办件服务按办件号哈希分区做水平扩展（保证同办件串行）；规则插件以独立容器/进程组部署，由插件宿主统一加载与管理，插件间以 RPC/事件通信；数据管道由调度器编排的作业组并行执行，按部门维度分片；事件总线多 Broker 多副本，按实体键分区保证局部有序；同步调用设置超时与熔断，避免级联阻塞。
- **开发视图**：按限界上下文分包（channel/ gateway/ casework/ rule-engine/ integration/ data-platform/ platform-ops），域间只允许通过契约交互；规则插件与事件模式分别独立版本线（语义化版本 + 契约仓库）；构建流水线分层：域内单测 → 契约测试（接口 + 事件模式兼容性）→ 架构符合性检查（依赖方向规则）→ 集成测试 → 性能与故障注入；事件模式与接口契约纳入版本库并随代码评审。
- **物理视图（部署视图）**：公有云政务云上多可用区部署；接入层双活 + 弹性伸缩；办件服务无状态多副本 + 负载均衡；规则插件按部门集群部署（可独立扩缩容）；消息中间件 3 副本跨机架部署；事件存储与读模型库主备 + 只读副本，读模型库走物理/逻辑只读分离；数据管道作业在计算集群分区执行；统一日志与指标接入监控平台，全链路追踪 ID 贯穿；数据库分库分表按办件号路由。
- **场景（贯穿性）**：以"一件事一次办结"场景作为一致性验证基准，贯穿逻辑、进程、开发、物理四视图，检验任一环节变更是否引发全视图联动调整。

三组质量属性权衡分析：

| 权衡组 | 敏感点 | 权衡点 | 代价 |
|---|---|---|---|
| 性能 vs 可修改性 | 管道过滤器的串行转换与格式转换开销；插件跨进程调用的序列化开销；写模型强一致校验 | 引入批量直传与同格式传递、插件进程隔离、读模型异步化（最终一致换吞吐） | 放弃部分强一致能力；运维复杂度（插件版本、追踪）上升；数据存在短暂不一致窗口 |
| 可用性 vs 性能 | 事件总线多副本与分区顺序保证、插件故障隔离带来的资源冗余 | 用多副本、跨可用区部署、插件熔断降级、读写分离与只读副本兜底 | 资源成本上升（至少 1.5~2 倍常态开销）、写入延迟略增、运维与切换复杂度提高 |
| 可修改性 vs 安全/一致性 | 插件契约与事件模式的开放性（可扩展） | 契约版本化 + 只增字段 + 契约测试 + 事件哈希链与只追加审计存储 + 敏感操作强制同步校验 | 演进节奏变慢（契约评审耗时）、存储成本上升（事件与版本双份）、兼容层需要维护 |

补充敏感点提示：安全方面的高敏感点是"事件总线与日志中敏感信息明文留存""插件可绕过核心直接访问数据""对外网关鉴权粒度"，对策分别是字段级脱敏与加密、插件权限最小化与数据访问走统一服务、网关统一认证鉴权 + 敏感接口二次鉴权。

**问题 5 参考答案**

ADR 治理方案：

- **决策记录项与必备要素**：每条 ADR 记录 编号、标题、日期、状态（提议/已采纳/废弃/被取代）、背景、决策内容、备选方案及否决理由、影响与后果、关联的质量属性与架构评审记录、责任人、关联需求或变更单号。ADR 入库到架构决策库并纳入代码仓库（与代码同源、随版本演进），重大决策必须通过架构评审（ATAM/ARID）后由架构委员会签署。
- **决策分级**：一类决策（核心边界、事件语义、数据权威源、插件契约主版本）需委员会评审并冻结；��类决策（单个插件实现、读模型建模细节）由域架构师决定；三级决策（实现选型、参数配置）由团队自行决定，避免评审过载。
- **契约治理**：插件契约与事件模式分别建立"契约目录 + 兼容性矩阵"，明确哪些是稳定区（禁止变更）、哪些是可演进区（遵循只增不改语义）；对外事件提供版本策略与消费者反馈渠道，破坏性变更需提前一个版本周期公告并提供迁移窗口；契约变更自动触发下游回归测试，未通过则阻断发布。
- **与组织流程的绑定**：ADR 与需求变更（CR）、发布、故障复盘三者挂钩——重大故障复盘必须产出 ADR（记录当时决策与后续修正），形成"决策可回溯、教训可复用"的闭环。

分阶段演进路线图（不允许全量停机，采用绞杀者式渐进替换）：

- **第一阶段（0~3 个月）——止血与并行**：建成统一事件总线与只追加事件存储，开辟"事件旁路"，对办件状态变更双写（老流程写库 + 新通道发事件），不改主流程；完成 40 个部门现状接口与数据质量摸底，形成数据字典与映射表；落地 ADR 机制与架构决策库、契约目录；建立全链路追踪与统一日志。
- **第二阶段（3~9 个月）——管道化与插件化**：把散落清洗脚本收敛为数据共享加工管道（分批迁移，先迁 2 个数据量最大的部门做样板），管道调度、校验、对账、位点续跑能力齐备；把"高频变更的审批规则"首批改造为插件（选择规则最复杂的 2 类事项试点），核心引擎保持稳定并发布插件契约 v1.0；灰度策略按办件号哈希分流，出现异常秒级回切老逻辑。
- **第三阶段（9~18 个月）——读写分离与事件溯源**：办件状态机正式切换为事件溯源 + CQRS（读模型异步构建，查询侧全部切到读模型），跨部门流转由轮询改事件订阅，通知时延从小时级降到秒级；对外网关统一收口，治理解耦直连数据库的高频接口，全部改走网关 + 缓存 + 只读副本；剩余部门数据管道与规则插件全量迁移。
- **第四阶段（18~24 个月）——治理与优化**：事件模式与插件契约进入稳定期，仅允许兼容演进；建立自动化架构符合性检查与混沌演练（插件故障、Broker 故障、数据库主备切换）；按需做多活（同城双活）改造；沉淀《架构规约》《事件规范》《插件开发指南》三份制度性文档。

3 项可度量的架构治理指标：
1. **事件化覆盖率** = 已通过事件总线流转的跨部门状态变更笔数 / 全部跨部门状态变更笔数，目标：第三阶段末 ≥ 95%，并同步监控端到端通知时延 P95 ≤ 5 秒。
2. **规则变更交付周期** = 审批规则从提出到上线的平均时长（含灰度），目标：由 15 天压缩至 ≤ 2 个工作日；配套指标：规则插件化率（插件承载的规则条数 / 规则总条数）≥ 80%。
3. **架构合规与稳定性**：① 越级访问/直连库事件数归零（网关调用占比 ≥ 95%，直连数据库的跨系统调用 = 0）；② 契约兼容性检查阻断的破坏性变更数量与总破坏性变更尝试数之比（目标 100% 被拦截）；③ 因架构原因引发的高等级故障与回滚次数（月度 ≤ 1 次），并以架构决策记录覆盖率（重大决策有 ADR 的比例 = 100%）作为过程性指标。

**踩分要点**：

1. 架构风格识别必须落到"风格名称 + 适用依据 + 风险对策"三段式，只答名称不答依据与风险，最高得一半分。
2. 管道-过滤器的核心得分点必考：过滤器独立可复用、数据流顺序、**最慢过滤器决定整体吞吐**、格式转换开销累加、缺乏全局控制流（数据驱动模型用于补救）。
3. 微内核得分点必考：核心最小化、扩展点稳定契约、插件独立发布/灰度/故障隔离；必答"契约难以变更"与"IPC 开销/版本冲突"两项风险。
4. 事件驱动得分点必考：**解耦（时间+空间）、异步削峰、最终一致性、不可变事件链天然审计**；必须出现"事件溯源""CQRS"术语并说明二者区别（前者以事件为唯一事实源，后者读写职责分离）。
5. 事件溯源不等于天然防篡改：审计防篡改需叠加哈希链/签名/只追加存储，漏答该点扣分。
6. 幂等三件套要写全：**事件 ID 去重表 + 实体版本号单调校验 + 状态机合法性校验**，且去重与业务写入同事务。
7. 乱序处理标准答法：按业务实体键分区保证局部有序 + 消费端版本号丢弃低版本 + 跨实体不保序（不要写"全局有序"）。
8. 集成模式必须与场景逐一对应（批量→文件、异步通知→消息、同步查询→RPC、对外开放→REST），并能说明为何共享数据库只适合稳定目录。
9. ESB 判断题给分点：答"不引入"不给理由不得分；高分答法是"按域/协议/时效分类分层，ESB 只用于跨组织异构协议适配与复杂编排，高频同域调用走轻量网关或直连"，并点明总线单点与"垃圾场"风险。
10. 4+1 视图答题必须逐视图给出要素（逻辑看构件、进程看并发与通信、开发看源码组织与依赖、物理看部署节点），漏掉"场景贯穿校验"扣分。
11. 质量属性权衡必须按"敏感点—权衡点—代价"三要素写，只写"要平衡性能和安全"不得分；代价必须具体化（如成本上升、延迟增加、一致性下降、运维复杂度上升）。
12. 渐进式改造必须体现"不停机"约束：给出并行双写 → 灰度切流 → 回切预案 → 全量切换的阶段路线，且每阶段有可度量里程碑。
13. ADR 治理答案要点：状态机（提议/采纳/废弃/被取代）、背景-决策-备选-后果四要素、分级评审避免过载、与需求变更和故障复盘挂钩、契约兼容性矩阵与稳定区/演进区划分。
14. 指标必须可度量：有分母、有时间窗、有目标值，典型为覆盖率、交付周期、时延 P95、阻断率，而非"加强治理""提升质量"这类空话。
15. 通用扣分点：出现具体公司/产品名、出现无依据的新技术名词、把消息队列说成"数据库表轮询的替代缓存"、混淆"最终一致性"与"强一致"、方案违反题目"不允许全量停机"约束。

## 记忆口诀

**管道-过滤器**
1. 数据流着走，过滤器牵手；格式是契约，顺序是自由。
2. 最慢一环定吞吐，逐段转换成本堆。
3. 管道胜在可复用、可测试、可并行；输在无全局控、无回滚语义。
4. 数据驱动模型补短板，流程难写要靠它。

**微内核与插件**
5. 核心要小要稳，插件要活要新；扩展点一改全线崩。
6. 插件四利：独立发布、故障隔离、定制交付、可灰度。
7. 插件四险：契约难改、跨进程开销、版本冲突、链路变长。
8. 规则可配、引擎不造——这是政务审批最好的一招。

**事件驱动与溯源**
9. 生产只管喊事实，消费只管订阅听；空间时间双解耦。
10. 事件通知带引子，携带状态带全貌；事件风暴要慎用。
11. 溯源唯一事实源，CQRS读写分家；重放可回溯，天然审计佳。
12. 至少一次最常用，消费幂等是命门：去重表+版本号+状态机。
13. 同实体按键分区保序，跨实体不保序，版本号低者丢弃。
14. 模式演进只增不改语义，破坏性变更双写过渡期。

**集成模式与ESB**
15. 批量走文件，异步走消息，同步走RPC，对外走REST。
16. 共享数据库耦合最重，稳定目录才敢用。
17. ESB价值在适配管控，风险在单点与垃圾场。
18. 高频同域直连，跨组织异构进总线。

**4+1视图与ADR**
19. 逻辑看构件，进程看并发，开发看依赖，物理看部署，场景来贯穿。
20. 视图等于视点加模型，视角不同视图必分裂。
21. ADR四要素：背景、决策、备选、后果；四状态：提议、采纳、废弃、取代。
22. 决策必须挂质量属性，无主张的架构是耍流氓。

**质量属性权衡**
23. 权衡三要素：敏感点、权衡点、代价；只喊"平衡"不得分。
24. 性能换一致，可改换成本，可用换钱，安全换流程。
25. 渐进改造四步：双写并行、灰度切流、可秒回切、全量收口。

**综合路线**
26. 管道治数据，插件治规则，事件治流转，溯源治审计，网关治接口。
27. 先旁路后切换，先试点后全量，先契约后实现。
28. 架构不停机，治理不停手，指标不停量。
