## 今日核心概念

### 1. 词法分析（Lexical Analysis）与正规式到有限自动机的构造

定义：词法分析是编译过程的第一阶段，负责把**字符流**扫描并切分为**单词序列（Token 流）**，是"字符世界"到"记号世界"的转换层。它本身不做语义判断，只回答"这是什么记号"。

关键要点：

- **词法单元三要素**：记号种别（Token Type，如 IDENTIFIER、INTEGER、OP）、属性值（Attribute，如变量名、整数值）、位置信息（行列号，用于错误定位与源码映射）。缺了位置信息，编译期报错就退化成"某某某行出错"这种无用提示。
- **正规式（Regular Expression）到自动机的四步构造**：①用正规式描述记号的词法结构（正规式三大基本运算：并、连接、闭包）；②用 Thompson 构造法把正规式递归转换为**非确定有限自动机（NFA）**；③用子集构造法（状态子集法）把 NFA 转换为**确定有限自动机（DFA）**；④用 Hopcroft 分区细化算法做 **DFA 最小化**，消除冗余状态后生成状态转移表。这一条链是"正则表达式引擎"与"词法分析器"的技术同源点。
- **为什么要转成 DFA**：直接用 NFA 匹配需要**回溯**（失败后换路径重试），最坏情况出现指数级回溯（"病态正则" ReDoS）；DFA 对同一输入串的判定是确定且线性的，天然免疫 ReDoS。工业级正则库（RE2）拒绝回溯即出于此因。
- **关键字消歧策略**：关键字在词法上与普通标识符同形，因此采用"**先按标识符规则识别，再查关键字表升级种别**"的两步法，而不是在转移表中为每个关键字单设分支。
- **最长向前匹配（最大匹配）原则**：同时匹配多条规则时取**长度最长**者；长度相同再按**声明优先级**裁决；若同长度同优先级则报词法冲突（scanner conflict），必须显式消解而不是靠运气。
- **词法错误处理**：非法字符、字符串未闭合、数值格式非法（如 `1.2.3`）、注释未闭合。原则是**报最长的可疑记号**并精确给出起止位置，遵循"最接近源程序的一处错误"原则，不做过度恢复。
- **词法分析的边界判定**：只有**上下文无关**的模式适合词法层。括号嵌套配对、算术表达式优先级这类需要上下文的信息**不可能**用正规式表达——这是词法分析的固有局限，也是必须上到语法分析层的原因。
- **工程映射**：规则引擎中"字段名识别、字面量识别、运算符识别"是词法层；低代码平台的表达式编辑器（如 Excel 公式、报表条件）其底层多为"词法 + 递归下降解析 + 解释执行"；日志采集的 grok 语法、SQL 解析器的第一遍都是词法分析。

### 2. 语法分析（Syntax Analysis）与上下文无关文法

定义：语法分析依据**上下文无关文法（CFG）**，把 Token 流构造成**语法树/抽象语法树（AST）**，回答"这些记号在结构上如何组织"。文法形式定义为四元组 G = (V_N, V_T, P, S)：非终结符集、终结符集、产生式集合、开始符号。

关键要点：

- **两个核心动作**：**推导（derivation）**——把开始符号逐步展开成句子；**归约（reduction）**——自底向上把句子折叠回开始符号。语法分析器要么走"自顶向下展开"，要么走"自底向上折叠"。
- **自顶向下递归下降（Recursive Descent）**：为每个非终结符写一个递归函数，对每个选择做 LL(1) 判定（依据 **FIRST 集**与 **FOLLOW 集**判断输入符号能否跟随），必要时查**预测分析表**。优点是手写直观、易于插入语义动作、错误定位精确；缺点是**不能直接处理左递归**（`E → T + E | T` 这类必须先改写），且对公共前缀要额外处理。
- **自底向上 LR 分析**：以"移进—归约"为核心，通过**规范归约**把输入串折叠。能力由弱到强依次为 **LR(0) → SLR(1) → LALR(1) → LR(1)**：LR(0) 识别能力最弱但实现最易，LR(1) 能力最强但状态数爆炸，LALR(1) 是工业界主力（Yacc/Bison 默认）。优点是能处理左递归、识别能力强；缺点是手写困难、错误信息不友好。
- **优先级与结合性声明**：Yacc/Bison 的 `%left`、`%right`、`%nonassoc` 声明**在文法层面消解二义性**，其做法是**自动改写文法**——对同一层的多个运算符生成一条公共的产生式链，再对终结符设置优先级，冲突时按优先级比较、结合性决定归约方向。这比手写"分层子文法"更简洁。
- **左递归改写**：直接左递归 `A → Aα | β` 改写为 `A → βA'`、`A' → αA' | ε`；间接左递归通过引入新非终结符消除。LL 解析器必须做此改写，LR 解析器不需要。
- **抽象语法树（AST）**：只保留语法骨架、丢弃具体语法细节（如括号、优先级推导中间节点），节点带类型与位置，是后续语义分析与优化的直接输入。AST 比语法树小一个数量级，是工程上传递"结构"的标准形式。
- **文法能力边界**：正规式只能表达**正则语言**（无计数、无嵌套配对）；上下文无关文法能表达**嵌套结构**（如表达式的括号配对、嵌套的 if-else）；上下文有关文法才能表达"类型必须匹配"这类语义约束——而后者不在语法分析层解决，交给**语义分析**。**语法分析解决"结构对不对"，语义分析解决"类型与含义对不对"**，这是本章最重要的分层。
- **错误恢复策略**：**同步恢复（panic mode）**最常用——遇错后跳到同步集合中的某个记号继续解析；另有**错误节点（error node）**与**短语级恢复**。原则是：语法错误尽量**多报**（一个错误后面往往藏着更多），**语义错误必须少报且报准**。

### 3. 语义分析与类型系统（Semantic Analysis）

定义：语义分析在语法树构造完成后，对程序做**上下文相关的合法性检查**并生成**带类型信息的中间表示**。它解决语法分析无力处理的三类问题：类型一致性、名字可见性、控制流合法性。

关键要点：

- **三项核心检查**：①**类型检查**（operand 类型是否满足运算符要求、实参与形参是否匹配、赋值两侧是否兼容）；②**作用域与名字解析**（名字在当前作用域链上是否可见、是否重复定义）；③**控制流检查**（不可达语句、break/continue 是否有合法目标、case 是否穷尽）。
- **符号表（Symbol Table）**：名字到属性的映射容器，是语义分析的核心数据结构。采用**层次化作用域**（词法作用域）与**栈式管理**（进入作用域压栈、离开弹栈），查找采用**哈希表**；需记录实体的种类、类型、层次、存储位置（偏移量）、大小与对齐信息。
- **类型系统的四个维度**：**静态类型 vs 动态类型**（检查时机）、**强类型 vs 弱类型**（是否允许隐式转换）、**名义型 vs 结构型**（类型同一性依据名字还是结构）、**多态**（子类型替换、重载、泛型）。工程上静态 + 强 + 名义型 + 子类型多态是最常见组合，Java/C#/TypeScript 均属此类。
- **类型格与子类型**：类型系统可用偏序关系表达"类型兼容"（如 int <: number <: any），据此支持**子类型多态**与**最小公共父类型**求取；协变与逆变决定容器类型（数组、函数参数）的替换规则。
- **属性文法与语法制导翻译**：把语义规则附着到文法产生式上，属性分**综合属性**（自底向上传递，如类型）与**继承属性**（自顶向下传递，如作用域环境）；属性依赖构成**有向无环图**，按拓扑序求值。实现上常用**树遍历（tree walking）**——在 AST 上走一遍，边走边做类型检查并生成 IR。
- **隐式转换的三条红线**：数值提升（byte→int）、扩大转换（int→long，丢精度但合法）、窄化转换（long→int，**必须显式且加告警**）。工程规则是"隐式只允许安全转换"。
- **编译期拦截的工程价值**：把"运行期才发现"的问题（字段名拼错、类型不匹配、参数个数不对）提前到"构建期就报错"，本质是**用类型系统换掉一部分测试成本**。这也是"规则配置错误在批处理时才暴露、导致 1.7 万条办件错判"这类事故的直接对策。
- **错误分级**：词法错误 → 语法错误 → 语义错误 → 逻辑错误。编译器只能拦前三类；逻辑错误（写对语法类型但业务语义错）必须靠业务规则校验、属性测试与人工评审兜底——**不要指望编译器解决业务正确性**。

### 4. 中间表示（IR）与基于数据流分析的代码优化

定义：中间表示是介于源程序与目标代码之间的**抽象机器程序**，是对源程序语义的等价重写。优化在 IR 上进行而非在源程序或机器码上进行，是编译器工程化的核心分界线。

关键要点：

- **IR 的五种常见形态**：**语法树/表达式树**（贴近源程序）、**DAG（有向无环图）**（公共子表达式的天然表达）、**三地址码**（四元式/三元式/指令表，每条指令最多三个操作数，形如 `x = y op z`，逼近目标机又不失通用性）、**SSA（静态单赋值）**（每个变量只赋值一次，天然phi节点，简化常量传播）、**字节码/虚拟指令集**（JVM、LLVM IR、WASM）。**三地址码 + SSA** 是现代工业编译器的默认选择。
- **数据流分析（Data-Flow Analysis）**：在基本块（Basic Block）组成的控制流图上，对程序点上的数据流事实做**不动点迭代**求解。经典问题包括**到达定义（reaching definitions）**、**可用表达式（available expressions）**、**活跃变量（live variables）**、**常量传播（constant propagation）**、**支配树（dominator tree）**。每种分析对应一个"格（lattice）+ 传递函数 + 边界条件"的三要素框架。
- **基于数据流的优化清单**：常量折叠与常量传播、公共子表达式消除（CSE）、复制传播、死代码消除、**循环不变量外提（loop-invariant code motion）**、强度削弱、循环展开与向量化、内联（inlining）、**分支重排与短路求值**。优化的合法性依据是**语义等价变换**——任何一条优化都必须能用等价关系证明不改变可观察行为。
- **机器无关优化 vs 机器相关优化**：前者只依赖语言语义（如常量折叠），在 IR 层做；后者依赖目标机器特性（寄存器分配、指令选择、指令调度、流水线填充），在后端做。**分层是保持可移植性的关键**。
- **指令选择、寄存器分配、指令调度**是后端三大任务：指令选择把 IR 模式匹配到机器指令（树覆盖法/树翻译法）；寄存器分配用活跃区间构造**干涉图**，再用**图着色**（K 近似最优）分配物理寄存器，装不下就溢出到栈；指令调度在依赖约束允许下重排指令以填满流水线空泡、减少停顿。
- **优化的代价是编译时间**：优化越多编译越慢、生成的代码可能越小更快，但"编译耗时"是真实成本。工业界的取舍是**分层优化 + 按目标场景选择档位**（AOT 优化激进、JIT 保守、热路径深度优化）。
- **现代映射**：JIT 的**分层编译**（解释 → C1 快速编译 → C2 深度优化）、**去优化（deoptimization）**、基于性能剖析的优化（PGO）、逃逸分析驱动的栈上分配；以及**规则/表达式引擎**中"规则 DSL → AST/IR → 解释执行或 JIT 编译"的完整编译器管线。

### 5. 目标代码生成与执行模式选择

定义：目标代码生成把优化后的 IR 翻译为可执行形式（机器码、字节码、中间代码），并决定代码在**何时、由谁**执行——这决定了系统的启动延迟、峰值吞吐、部署形态与回滚难度。

关键要点：

- **三种执行模式对比**：
  - **纯解释执行**：启动几乎零延迟、调试与热更新最灵活；但运行吞吐低，且每次求值都要重新遍历语法树，**工作量与调用次数成正比**——这正是"规则引擎每次求值都重新解析"性能崩塌的根因。
  - **纯预编译（AOT）**：运行最快、启动快（可直接加载机器码）；但编译在部署前完成，无法针对运行时数据特化，且**每次规则变更都要重新走完整发布流程**。
  - **混合模式（字节码 + JIT）**：先编译为与平台无关的字节码，运行时由虚拟机解释执行并对热点路径 JIT 编译。兼得"部署快、可移植、可运行时特化"，代价是引入 JIT 编译器复杂度与代码缓存管理成本。
- **"一次编译、多处执行"的关键设计**：**目标无关 IR + 多后端**。前端（词法/语法/语义）只做一次，IR 是稳定契约，各目标平台（x86、ARM、国产 CPU、GPU）各自实现后端。这是编译器实现**国产化多平台适配**的标准答案——换平台只换后端，不动前端与规则资产。
- **代码缓存与版本一致性**：JIT 代码以 IR 版本 + 运行时版本为键缓存；**规则变更必须使旧缓存失效**，否则会出现"新规则跑旧字节码"的诡异不一致。缓存失效策略（版本号、哈希、失效回调）属于架构必备项，不是优化项。
- **可调试性与生产安全的平衡**：线上开启 JIT 需保留**去优化与回退到解释器**的能力，否则一个激进的优化 bug 会让整个进程无法恢复；同时必须保留**代码级追踪与编译耗时埋点**。
- **编译式架构的收益与代价**：收益是把"重复解释"摊销为"一次编译"，把运行期错误前移到构建期，获得可复用的规则产物与可回滚的版本；代价是引入了编译器复杂度、构建期反馈变慢、规则变更要走编译-发布链路。因此**不是所有场景都该上编译式**——规则数量少、变更极频繁、单次执行量小的场景，解释执行更划算。
- **广泛存在性**：SQL 的查询优化器本质上就是编译器（SQL 文本 → 解析 → 重写 → 优化 → 执行计划 → 执行），规则引擎的 RETE 网络是另一种 IR + 编译技术，浏览器的 JIT、数据库的查询计划缓存、大模型的算子融合与图优化（TVM/OneDNN）同属一脉。**掌握编译原理等于掌握了一类通用的性能与正确性工程手段**。

## 案例分析题

**题目**：

某市"城市大脑"政务数据共享与政策兑现平台上线三年后暴露出一批结构性问题。该平台有一层自研的**策略规则引擎**，用于对全市 120 万条企业办件做政策匹配与补贴档位判定。规则由业务人员以 JSON/字符串表达式配置，形如：

```json
{ "when": { "and": [ { "field": "applicantType", "op": "==", "value": "ENTERPRISE" },
                     { "field": "registeredCapital", "op": ">", "value": 5000000 },
                     { "field": "taxTotal3Y", "op": ">=", "value": 1200000 } ] },
  "then": { "subsidyLevel": "A" } }
```

当前实现方式是：把规则表达式**解析成树结构并常驻内存**，每次对一条办件求值时遍历该树。现存问题如下：

1. **性能**：单批次 120 万条办件的规则判定总耗时 38 分钟，且耗时随数据量近似线性增长，夜间批处理窗口（23:00—06:00）被占满，无法容纳第二批次。
2. **正确性**：规则中的**字段名、类型、运算符是否适用**全部在运行期才被发现。某次上线中业务人员把 `registeredCapital` 误写为 `registerdCapital`，另有配置把 `>` 误写为 `>=`，两者均未被任何机制拦截，直到夜间批处理跑完才发现，导致 **1.7 万条办件补贴档位错发**，且其中部分已进入拨付流程，事后回溯与追回成本极高。

| 阶段 | 输入 | 输出产物 | 关键动作 |
| --- | --- | --- | --- |
| ① 词法分析 | 规则 DSL 源文本（字符流） | Token 流（种别+属性+位置） | 识别关键字、标识符、字段名、字面量、运算符、括号、标点 |

| ③ 语义分析 | AST + 符号表 + 类型环境 | 带类型标注的 AST / IR | 类型检查、作用域解析、字段存在性与类型校验、生成中间表示 |

**（2）编译式优于解释式的原因**

- **摊销收益**：解释式每次求值都要重新遍历规则树，1 万条规则 × 120 万条办件的重复遍历成本 ∝ 规则规模 × 数据量；编译式把规则结构分析一次性完成，运行期只剩"取值 + 判定"，成本从 O(规则规模) 降为 O(参与判定的条件数)，且不随规则总数线性放大。
- **前移正确性**：类型与字段存在性在编译期一次性全量校验，把"运行期才发现、且已产生业务后果"的缺陷模式彻底消除（对应问题 2）。
- **可优化**：只有形成 IR 才能做数据流分析驱动的优化（常量折叠、CSE、条件重排），解释式在树上直接优化要么做不了要么会破坏语义。
- **可复用与可版本化**：IR/字节码可缓存、可比对、可做语义等价性回归（对应问题 4）。
- **代价**：引入编译器复杂度、构建期变长、规则变更需重编译，因此必须配套增量编译与缓存机制。

**（4）正规式 → 自动机构造链**

① **正规式描述**：如标识符 `ident = [A-Za-z_][A-Za-z0-9_]*`，用基本正规式（并、连接、闭包）组合而成；
② **Thompson 构造**：递归地把正规式转换为 NFA 片段，每个运算对应固定的状态数（并引入 ε 转移），全式合成后以唯一初态和终止态封装；
③ **子集构造（确定化）**：DFA 的每个状态是 NFA 状态的一个**子集**，按 ε-闭包求可达子集，构造 DFA 转移函数；
④ **最小化（Hopcroft 分区细化）**：初始按"接受/非接受"划分等价类，反复按后继可区分性细化，直到不动点；
⑤ **生成代码**：最小 DFA 的状态转移表可直接写成词法分析器的 `switch` 分派表；状态数过大时用**状态分裂 + 哈希压缩**降低内存。

**（5）消歧与裁决**

- **关键字与标识符同形**：采用"**最大匹配识别为 IDENTIFIER，再查关键字表升级种别**"的两步法。理由是关键字在词法上就是标识符，若在转移表中单设分支，会导致 `andrew` 被误切为 `and` + `rew`。
- **多条规则同时匹配**：遵循**最长向前匹配**为主、**声明优先级**为辅；若两规则匹配长度相同且优先级相同，视为**词法冲突**，必须在 DSL 定义阶段显式消解（如规定 `>=` 优先于 `>` `=` 的分解），而不是依赖实现顺序。
- **字段名与标识符**：不做词法层区分，统一识别为 IDENTIFIER，在**语义分析阶段**查字段字典决定其是"字段引用"还是"变量引用"，从而把"字段不存在/类型不匹配"这类问题**留到语义分析**统一报错。

**问题 2 参考答案**

**（1）选型结论**

**建议采用递归下降（LL）为主、LR 为辅**，理由：

- 该 DSL 语法规则数量有限、结构清晰（字段—运算符—值的三元结构 + 逻辑连接的递归组合），LL(1) 足以覆盖；
- 递归下降**手写成本低、语义动作插入点直观**，规则引擎的业务人员与运维需要能读懂解析器代码以支持排障与二次开发；
- 递归下降的**错误定位精确**（能在具体产生式处直接报错并给出期望记号集合），对问题 2 中"配置错误必须当场拦截"的要求更友好；
- 若后续 DSL 扩展到复杂优先级表达式或引入上下文约束（如"同一 and 链中字段类型必须一致"），LR 的识别能力更强，可保留 LR 作为备选演进路径；
- 无论哪种方案，**歧义都必须用优先级声明或分层子文法在文法层面消除**，绝不能留给实现时的偶然行为。

**（2）CFG（分层子文法写法，含优先级与结合性）**

```
rule          := "{" "when" ":" expr "," "then" ":" action "}"
expr          := orExpr
orExpr        := andExpr { "or" andExpr }
andExpr       := notExpr { "and" notExpr }
notExpr       := "not" notExpr | comparison
comparison    := additive [ REL_OP additive ]
additive      := term { ("+"|"-") term }
term          := factor { ("*"|"/") factor }
factor        := NUMBER | STRING | BOOL | "(" expr ")" | FIELD
action        := "{" IDENTIFIER ":" value "}"
value         := NUMBER | STRING | BOOL
```

**优先级与结合性处理**：上述写法用**分层子文法**隐含实现了优先级——`or` 最低、`and` 次之、比较、再到算术、最后因子；`and`/`or` **左结合**（用 `{ }` 循环实现左递归式展开），算术加减与乘除同样左结合。若改用 **Yacc/Bison 的优先级声明**（`%left OR`、`%left AND`、`%left EQ NE`、`%left LT LE GT GE`、`%left PLUS MINUS`、`%left STAR SLASH`），编译器会自动改写文法并按优先级/结合性消解冲突，代价是错误信息不如手写递归下降友好。

**（3）左递归处理（若选 LL）**

递归下降不能直接处理左递归（`expr → expr "+" term`），必须改写为**右递归 + 列表**形式（上面文法中的 `{ }` 循环即等价于改写：把左递归拆为"收集项"和"处理项"两层）。若使用单条右递归产生式 `additive → term "+" additive | term`，则需注意**结合性会翻转**——右递归天然右结合，因此加减乘除必须显式改写以保持左结合，否则 `10-3-2` 的结果会从 5 变成 9。

**（4）为什么正则表达式不能解析该 DSL**

正则表达式只能描述**正则语言**，其识别能力等价于有限自动机，**不具备计数与嵌套配对能力**。本 DSL 中：
- 括号必须**嵌套配对**（`and (a>1 or (b<2 and c==3))`）——正则无法保证括号正确嵌套，强行用正则匹配必然在深层嵌套或出现多余括号时错误截断或错误接受；
- 存在**多级优先级**（not > 比较 > and > or > 算术），正则无法表达"哪一段先结合"的语义；
- 正则只能做**字符串模式匹配**，无法建立**结构化语法树**，也就无法做类型检查与优化。

结论：正则只能承担**词法层**（识别记号）与**简单条件抽取**（如提取单个 `field op value`），完整解析必须用上下文无关文法。

**（5）语法错误恢复策略与原则**

- **策略**：采用**同步恢复（panic mode）**——检测到错误后，跳过输入记号直到落入某个**同步集合**（如 `,`、`)`、`}`、关键字 `then`）再继续解析；同时在 AST 上插入**错误节点**占位，使后续语义分析不至于崩溃。
- **原则一（语法层多报）**：语法错误往往成片出现，应一次性报告多处错误而非遇错即停，便于业务人员一次改完。
- **原则二（语义层少报准报）**：类型错误、字段缺失等语义错误必须精确定位到具体节点与列号，避免语义级"洪水式"误报淹没真正的问题。
- **原则三（不吞错误）**：恢复过程中不得把错误节点静默当作合法节点参与优化或代码生成；任何含错误节点的规则在编译期即被**拒绝发布**，并保留错误明细供展示。
- **原则四（错误分级提示）**：警告（可疑但可编译，如疑似笔误的字段名、隐式窄化转换）、错误（阻断编译）两级，便于在配置体验与严格性之间取舍。

**问题 3 参考答案**

**（1）类型系统设计**

- **类型分类**：
  - 基础类型：`Int`（整数）、`Decimal`（金额/高精度，**金额类规则必须禁用浮点**）、`String`、`Bool`、`DateTime`；
  - 复合类型：结构体/对象类型（规则内的嵌套对象）、数组/集合类型；
  - 特殊类型：`Any`/`Unknown`（用于模板变量等未定型场景，**必须显式标注且在语义分析期收敛**，否则等于放弃类型检查）。
- **运算符适用类型规则**（举例）：`==`/`!=` 允许任意相同类型或双方均为可空类型；`>`/`>=`/`<`/`<=` 允许数值类型之间或 `DateTime` 之间，**不允许 String 与数值比较**（配置中出现即为错）；`+` 对数值是加法、对 String 是拼接（需显式 `concat` 避免歧义）；`and`/`or`/`not` 仅允许 Bool。
- **隐式转换边界**：只允许**安全提升**（`Int → Decimal`、`Int → Float`），且提升方向单一不可逆；**禁止隐式窄化**（`Decimal → Int` 必须显式并附警告）；`String ↔ 数值` 一律禁止隐式转换，必须显式 `parse`/`toString`；布尔不参与任何隐式转换。

**（2）作用域与名字解析**

- **作用域层次**：全局（平台级内置函数与常量） → 规则集 → 单条规则 → 条件节点 → 表达式节点；采用**词法作用域**与**栈式符号表**，进入节点压栈、退出弹栈。
- **名字解析流程**：①在当前作用域查 → ②逐级向外层作用域查 → ③命中则记录其定义层级（供类型检查与后续优化使用）→ ④全局仍未命中则报**未定义名字**错误。
- **符号表条目内容**：名字、种类（字段/变量/函数/常量）、类型、定义位置（行列）、作用域层级、存储位置信息。

**（3）三类语义检查**

- **类型检查**：运算符两侧类型是否满足规则；比较双方是否同族；布尔上下文（`and` 的操作数）是否确为 Bool；动作值类型与目标字段类型是否兼容；模板变量替换后的实际类型是否与使用点匹配。
- **名字可见性检查**：字段是否存在（查平台字段元数据字典）；字段是否在当前业务域内可见；是否重复定义；是否使用了已下线字段。
- **控制流合法性检查**：逻辑连接结构是否完整（`and` 链不得有悬空操作数）；条件表达式是否有返回值；动作块是否为空或存在未知键；`not` 是否缺少操作数。
- **补充检查（配置一致性）**：字段名拼写近似检测（编辑距离/前缀匹配）——把"未定义字段"升级为"疑似笔误，是否想输入 xxx"，直接命中问题 2 中的 `registerdCapital` 类错误。

**（4）属性文法与语法制导翻译的实现路径**

- **属性定义**：每个 AST 节点带**类型属性**（综合属性，自底向上由子节点计算）与**环境属性**（继承属性，自顶向下传递当前作用域符号表）。
- **遍历过程**（树遍历式语法制导翻译）：
  1. 进入节点时压入作用域、建立环境；
  2. 自顶向下解析表达式节点，先解析操作数再解析运算符（保证后缀式遍历顺序）；
  3. 自底向上归约每个节点：取子节点类型 → 查运算符适用类型表 → 推导结果类型（必要时做安全提升并记录提升信息）→ 把节点翻译成 IR 三元式并追加到 IR 列表；
  4. 退出节点时弹栈。
- **两处配置错误的拦截点**：`registerdCapital` 在**名字可见性检查**处即报"未定义字段，疑似笔误"；`>` 与 `>=` 的差异不属类型问题，而由**语法与语义联合校验**保证——编译器为每个比较运算标注其**精确语义（严格大于 / 大于等于）**，并在动作生成阶段把该语义**固化为字节码指令**，杜绝"配置语义在执行时被重新解释"的可能；同时对"金额档位边界"这类关键比较，附加**边界值规则**（如阈值 5000000 与 5000001 两个用例）做**编译期告警**，提示该字段在边界上敏感。

**（5）中间表示生成与编译期拦截的产出物**

IR 生成后形成"**规则可编译清单**"：每条规则对应一个编译单元，包含类型化 IR、校验结论、告警列表、编译产物哈希。CI 流水线以该清单为门禁：**编译失败（错误级）→ 阻断规则发布**；**告警级 → 需业务负责人签字确认**。这样把问题 2 的两类事故从事后发现（已拨付 1.7 万条）转为事前阻断（发布前 0 条流出）。

**问题 4 参考答案**

**（1）IR 形态选型**

**结论：以 SSA 形式的三地址码作为主 IR，编译生成平台无关字节码作为目标产物；AST 仅作为前端中间结构保留。**

- **AST**：贴近源程序，适合语法/语义分析阶段，但冗余多、优化能力弱，仅保留用于错误定位与调试。
- **DAG**：能表达公共子表达式，但控制流显式化困难，且变量定义不唯一，不适合做数据流分析。
- **三地址码**：每条指令最多三个操作数（`x = y op z`），控制流显式化（标签与跳转），可线性化、易于做数据流分析，且对规则这种"表达式求值型"负载天然贴合——**所有规则最终都归约为布尔表达式求值**。
- **SSA**：每个变量只赋值一次，配合**支配树**与 **φ 节点**处理控制流汇合，使常量传播与全局值编号等优化实现大幅简化；生成代码质量优于普通三地址码。
- **字节码**：作为最终目标产物，兼作"目标无关 IR"的一部分：既是 JIT 的输入，也是跨平台（x86 / 国产 CPU）的统一执行格式，一份字节码多处运行。
- **放弃纯语法树作为主 IR**：它无法支撑后续的常量折叠、CSE 与条件重排。

**（2）基于数据流分析的优化清单（≥6 项）**

| 优化项 | 依赖的数据流事实 | 在规则引擎中的具体形态 |
| --- | --- | --- |
| 常量传播与常量折叠 | 到达定义 + 常量传播分析 | 字面量阈值参与比较时，预计算为常量比较；`5000000 > 0` 恒真直接消去 |
| 公共子表达式消除（CSE） | 可用表达式分析 | 同一字段被多个条件引用时，只取一次值存临时量 |
| 复制传播 | 到达定义 | 临时量复制到另一变量后，后续引用统一替换，消除冗余赋值 |
| 死代码消除 | 活跃变量分析 | 布尔表达式中恒假分支后的条件永不求值，删除之；无用赋值删除 |
| 循环不变量外提 | 循环结构 + 不变量分析 | 批量循环中与单条办件无关的常量条件外提 |
| 条件重排（短路化） | 控制流 + 代价估计 | 把**选择性高、代价低**的条件前置，把恒真/恒假条件折叠 |
| 分支预测提示 | 静态概率估计 | 对"申请类型 == 企业"这类高选择性条件优先求值 |
| 死分支消除（结合常量传播） | 常量传播 | 条件恒真时只保留 then 分支；恒假时整条规则直接短路为不匹配 |
| 表达式强度削弱 | 代数等价 | 阈值比较改写为等价更省的运算形式（在有数值语义时需谨慎，涉及金额精度） |
| 字段访问去重（提升为临时量） | 可用表达式分析 | 同一字段多次访问合并为一次读取 |

**（3）条件重排与短路求值的等价性论证**

- **等价性来源**：布尔合取 `A ∧ B` 在**无副作用**且**操作数无异常**（不抛错、不改变状态）的前提下满足**交换律与结合律**，因此重排 `A ∧ B → B ∧ A` 不改变求值结果。
- **前提条件必须显式校验**：①所有条件为**纯函数**（只读取不可变输入，不写外部状态）——若某条件含"调用外部服务"或"累加计数"，交换律不成立，编译器必须**拒绝重排**并在编译期报错；②求值**无副作用且无异常**；③**类型一致**——短路返回类型必须是统一的 Bool，不能出现"前项返回 Bool、后项返回非 Bool"的混合类型；④涉及**空值/越界**时需定义确定的求值语义（是否短路求值应与平台语义一致并在文档中固化，否则重排会改变异常暴露时机）。
- **求值顺序的工程含义**：在有副作用或异常的场景下必须**显式声明求值顺序**，禁止依赖编译器默认行为——这是 DSL 规范中必须写死的一条。

**（4）优化收益度量指标（≥4 项）**

1. **字节码指令数/字节码体积**：单条规则平均字节码条数、优化前后对比（降幅 %）。
2. **单条办件规则判定平均耗时（纳秒/微秒）**：优化前后 P50/P95/P99 三档对比。
3. **批次总吞吐（条/秒）与批处理窗口占用率**：120 万条从 38 分钟降至多少分钟，夜间窗口占用率降至多少。
4. **条件短路命中率**：命中最早短路条件即返回的比例（衡量条件重排与选择性优化的直接效果）。
5. **字段访问次数下降幅度**：优化后每条办件的字段读取次数（原 N 次 → 优化后 M 次），与 I/O 与反序列化开销的关联。
6. **JIT 编译耗时与代码缓存命中率**：优化层级提升带来的编译时间成本，以及缓存命中率（未命中即触发重新编译的次数）。
7. **内存占用峰值**：规则集全部编译产物常驻内存的字节数与 GC 压力。
8. **语义等价性校验通过率**：优化前后在**全量历史办件样本**上判定结果完全一致的占比（**必须为 100%**，任一不一致即视为优化引入缺陷）。

**（5）优化与编译耗时的取舍**

- **分层策略**：默认档只做"零风险优化"（常量折叠、CSE、死代码删除），编译快；**高精度档**再加条件重排与更激进的变换，需额外的代价估计与静态证明。
- **增量编译**：以单条规则为编译单元，依赖字段元数据版本 + 规则内容哈希，未变更规则直接复用缓存产物，把"全量重编译"降为"增量重编译"。
- **构建期与运行期分离**：全量优化在 CI 阶段完成并把产物作为**版本化发布物**入库，运行期只做必要的 JIT 热点优化。
- **度量口径**：优化收益是**一次性的、持续的**（每次运行都省），编译成本是**一次性的、可摊销的**（N 次运行后即回本）——因此当规则执行量足够大时，激进优化的期望收益为正；决策阈值可用"编译耗时增量 × 执行次数 > 运行期节省"来判断。

**问题 5 参考答案**

**（1）三种执行模式六维对比**

| 维度 | 纯解释执行 | 纯预编译（AOT） | 字节码 + JIT 混合 |
| --- | --- | --- | --- |
| 启动延迟 | 最低（无构建期） | 低（产物直接可用，但需提前构建） | 中（首次解释执行，热点逐步 JIT） |
| 峰值吞吐 | 低（每次求值重复遍历） | 最高 | 高（热点路径可接近 AOT） |
| 规则变更时效 | 最快（改完即生效，但需重解析） | 最差（必须走完整构建与发布流程） | 中（可增量编译新规则，热替换字节码） |
| 部署形态 | 单一制品，跨平台最易 | 每个平台一份制品（多平台需分别构建） | 一份平台无关字节码 + 各平台虚拟机 |
| 可调试性 | 最好（栈帧清晰，可单步） | 中（需符号信息） | 中偏难（需处理去优化与栈展开） |
| 国产化适配 | 前端与后端都在运行时，换平台需重写 | 需为国产 CPU 各编译一份 | **只需国产平台实现一个字节码虚拟机/JIT 后端** |

**选型建议**：采用**混合模式**。理由：①该场景执行量巨大（120 万条 × 3000 条规则），摊销后编译成本可忽略，且吞吐收益显著；②规则口径变更频繁（业务政策驱动），需要比纯 AOT 更快的变更生效路径；③国产化与 x86 双平台部署，字节码 + 多后端是唯一能"前端一次、后端两套"的方案；④3000 条规则的编译可在 CI 中**全量离线完成并入库**，运行时只做热点 JIT，因此启动延迟问题被大幅缓解。

**（2）"目标无关 IR + 多后端"支撑双平台适配**

- **前端唯一**：词法/语法/语义分析只实现一次，产出**平台无关的 IR/字节码**，这是稳定契约。
- **后端可插拔**：分别为 x86 与国产 CPU 实现后端（或采用"IR → 平台字节码"的轻量后端），后端只做指令选择、寄存器分配与调度，不触碰语义。
- **运行时隔离**：用一个**小型字节码虚拟机**（可自研，约数千行）在两个平台上各跑一份，规避对特定运行时 JIT 的依赖——这直接解掉问题 5 中"换平台即重写"的死结。
- **必须补齐的工程项**：①字节码版本与虚拟机的**兼容性承诺**（字节码版本号 + 虚拟机向后兼容矩阵）；②调试信息与源码映射（保证线上报错可定位回规则源码位置）；③两个平台的**结果一致性验证**（同一批历史办件，两个平台的判定结果必须逐条一致，作为发版门禁）。
- **不推荐**为省事直接做双份 AOT：规则资产的唯一性会被破坏（两份构建产物可能不一致），且国产化适配要重做全链路。

**（3）规则版本变更时的代码缓存失效**

- **缓存键设计**：缓存键 = `hash(规则内容) + 规则DSL版本号 + 字段元数据版本号 + 目标平台标识 + 优化档位 + 虚拟机版本号`。任一项变化即自然失效，**避免依赖手工清理**。
- **主动失效**：规则发布/下线/字段元数据变更时，发布事件广播"失效通知"，按规则 ID 精准清除缓存条目；保留"内容哈希 + 依赖表"以支持**依赖级失效**（字段字典变更 → 只失效引用该字段的规则）。
- **防线一（唯一真源）**：源码 DSL 是唯一权威资产，字节码是**可再生构建产物**；任何时候字节码与源码不一致，**一律以源码为准并触发重编译**，字节码绝不作为业务真相。
- **防线二（构建期签名）**：编译产物附"源内容哈希 + 编译期配置指纹 + 构建签名"，运行期加载时校验，不一致直接拒绝加载并降级到解释执行或旧版本（**不允许静默使用不匹配产物**）。
- **防线三（灰度并存）**：新旧规则版本在灰度期**并存运行**，按办件分流；比对两版判定结果，差异超过阈值即自动回滚并告警——这同时解决了"新规则跑旧字节码"的检测问题：只要存在版本错配，判定差异一定会暴露。
- **防线四（版本写痕）**：每次判定结果记录所用规则版本号与编译产物哈希，写入办件审计日志，使任何"结果异常"都可回溯到确切的规则版本与产物。

**（4）对问题 1～5 的逐条治理**

**问题 1（性能）**
- 治理效果：编译一次、多次复用，运行期成本从"遍历整棵规则树"降为"取值 + 若干次比较"；批次耗时预期从 38 分钟下降到分钟级甚至更短，夜间窗口可容纳多批次。
- 遗留风险：规则集全量编译产物常驻内存带来的内存压力；极端规则（上千个条件的组合）仍会放大单条判定成本。
- 验证方式：历史 120 万条办件**回放压测**，对比优化前后总耗时与 P99 单条耗时；连续 3 个批次稳定在窗口内。

**问题 2（正确性）**
- 治理效果：字段不存在、字段名疑似笔误、类型不匹配、比较运算符语义歧义全部在**编译期**阻断；已发的 1.7 万条错判属于存量，需通过"字段元数据 + 规则历史版本"回溯定位受影响办件并人工复核，这是**存量治理而非新架构能自动解决**的部分。
- 遗留风险：编译器无法判断"阈值 5000000 本身是否符合业务口径"——业务语义错误（如把含税当不含税）仍需业务规则校验与人工评审。
- 验证方式：①构造含 5 类错误的历史配置样本，要求 100% 被编译期拦截并给出可读错误；②**回放全部历史办件样本**，对比新旧判定结果，差异清单逐条由业务确认，形成迁移期差异台账。

**问题 3（安全）**
- 治理效果：**取消任意代码执行**——DSL 不提供反射、IO、任意函数调用能力；模板变量只允许从**白名单上下文**取值；资源耗尽通过"**表达式深度与节点数上限 + 求值步数上限 + 超时中断 + 栈深度限制**"多重闸门控制；DSL 结构本身由文法约束，不可能构造出病态嵌套。
- 遗留风险：白名单上下文取值若来源不当仍可能泄露敏感数据；深度/步数上限过紧会误伤复杂合法规则。
- 验证方式：①红队用例集（注入、超深嵌套、超大范围扫描、循环构造）全部被拦截且不影响宿主进程；②越权取值用例 100% 拒绝；③压测下超时闸门生效且宿主线程池不被拖垮。

**问题 4（回归）**
- 治理效果：编译产物（IR/字节码）可**逐条比对**、可存版本、可算哈希；结合**语义等价性回归**（新旧规则在历史样本上判定一致率必须 100%）把人工比对变为自动化比对；配合"字段元数据依赖图"可做**影响面分析**（改一个字段，精确列出受影响规则并自动触发重编译与回归）。
- 遗留风险：样本覆盖不足时等价性结论会失真；规则数量增长后全量回归耗时上升。
- 验证方式：①规则发布流水线自动产出"受影响规则清单 + 回归差异报告"；②回归耗时与人工比对耗时对比（预期从 11 人天降至小时级）；③等价性校验通过率 100% 作为发布门禁。

**问题 5（国产化适配）**
- 治理效果：前端与 IR 只做一次，国产 CPU 侧只需实现字节码虚拟机/后端；**规则资产与构建流水线完全平台无关**。
- 遗留风险：两个平台的浮点/数值语义差异可能造成边界结果不同（金额类必须用定点 Decimal 并明确舍入规则）；国产 CPU 上的 JIT 性能需实测，可能需要针对该平台调整优化档位。
- 验证方式：双平台**同批办件逐条结果一致性测试**（要求 100% 一致）；国产平台批量吞吐与时延基线测试；平台迁移工时对比（预期从"重写"降为"实现一个后端"）。

**（5）至少 3 项可量化验证指标（汇总）**
1. 120 万条批次总耗时：从 38 分钟降至 **≤ 5 分钟**（夜间窗口占用率 ≤ 30%）。
2. 规则编译期拦截率：注入的 5 类错误配置 **100% 拦截**，且存量错判类缺陷**新增为 0**。
3. 新旧规则语义等价率：历史全量样本回放一致率 **100%**，差异清单业务确认闭环率 100%。
4. 规则发布平均工时：从 11 人天降至 **≤ 1 人天**（自动化回归 + 影响面分析）。
5. 双平台判定一致性：**100%**；国产平台吞吐达 x86 平台的 **≥ 80%**。
6. 安全红队用例拦截率 **100%**，单条规则求值超时上限生效且宿主无资源异常。

**踩分要点**：

1. **编译六阶段必须写全且产物对应准确**：词法（Token 流）、语法（AST）、语义（带类型 AST/IR）、中间表示（IR/三地址码）、优化（优化后 IR）、目标代码（字节码/机器码）——缺一阶段或阶段产物写错即失分。
2. **必须明确回答"编译式 vs 解释式"**：核心得分点是**摊销收益**（一次编译多次复用，消除"每次求值重复遍历"）与**错误前移**（类型与字段校验从运行期前移到编译期）；只说"编译更快"不够。
3. **词法记号表不少于 8 类且需区分关键字、标识符、字段、字面量、运算符、括号、标点、注释、EOF**；缺"位置信息（行列）"这一要素要扣分。
4. **"正规式 → NFA → DFA → 最小化"四步链必须完整**，并能说明**DFA 消除回溯、避免 ReDoS**这一工程动因。
5. **关键字消歧必须答"先按标识符识别再查表升级"**，答成"在文法里区分"属错误（关键字与标识符在**词法层**同形）。
6. **最长向前匹配 + 声明优先级 + 同等优先级报词法冲突**三点要答全。
7. **LL 与 LR 选型必须给出理由**（识读成本、错误定位、可扩展性），只做结论不写理由按半对计分。
8. **文法必须体现优先级与结合性**：分层子文法或 `%left/%right` 优先级声明二选其一，并明确左结合；用右递归却声称保持左结合会被判错。
9. **必须指出"正则不能解析该 DSL"的理由是语言能力问题（无法嵌套配对、无优先级、无法建树）**，答"正则效率低"不得分。
10. **语法错误恢复要答"同步恢复 + 错误节点"，并区分"语法层多报、语义层准报"**，这是常见踩分点。
11. **类型系统要给隐式转换边界**：只允许安全提升、禁止隐式窄化、禁止字符串与数值隐式互转、金额禁用浮点——答"允许隐式转换"直接失分。
12. **语义三类检查（类型、名字可见性、控制流）要分别落到具体规则上**（如"字段是否存在且拼写是否可疑"），并要体现**用类型系统换测试成本**的工程判断。
13. **属性文法与语法制导翻译要答出"综合属性自底向上、继承属性自顶向下、树遍历实现"**，只提名词不给机制按半对计分。
14. **`registerdCapital` 与 `>`/`>=` 两类错误必须分开处理**：前者靠名字解析与疑似笔误提示，后者靠**比较运算语义在编译期固化为指令 + 边界值告警**，把两者混为一谈扣分。
15. **IR 选型必须给结论并说明理由**：推荐"SSA 形式三地址码 + 平台无关字节码"，只列 IR 形态不作选择不得分。
16. **优化清单不少于 6 项，且每项要挂上依赖的数据流事实**（可用表达式、活跃变量、到达定义、常量传播、支配树）——只列优化名不给数据流依据按半数计分。
17. **条件重排的等价性论证必须写出前提**：纯函数、无副作用与异常、类型统一；并指出含副作用时必须拒绝重排。只答"因为逻辑与满足交换律"不写前提扣分。
18. **优化收益度量给 4 项以上量化指标**，且必须包含"批次总耗时/窗口占用率"与"语义等价率 100%"这两项业务级指标。
19. **三模式对比必须覆盖六个指定维度**并给出选型结论；仅做优缺点罗列而无结论不得分。
20. **国产化适配的答案落在"前端一次 + 多后端 + 字节码虚拟机"，并补齐字节码版本兼容与双平台一致性验证**；答"再编译一份"属未答到点子上。
21. **缓存失效要答"内容哈希 + 依赖元数据版本 + 主动失效事件 + 加载时签名校验 + 灰度并存比对"**，其中"唯一真源是源码、字节码可再生"这一条是核心得分点。
22. **逐条治理部分必须写"治理效果 / 遗留风险 / 验证方式"三要素**，尤其要指出**存量 1.7 万条错判不能靠新架构自动解决**、**业务口径错误编译器管不了**——这两句是区分高级与中级答卷的关键。
23. **至少给出 3 项可量化的最终验证指标**（如批次耗时 ≤5 分钟、拦截率 100%、等价率 100%、发布工时 ≤1 人天、双平台一致性 100%）。
24. **全文不出现"编译器万能"式表述**：需明确成本（编译期变长、构建链路复杂、变更需重编译），并说明"规则少且变更极频繁的场景解释式更划算"，体现技术选型的权衡意识。

## 记忆口诀

**编译管线**
1. 编译六阶：词、语、义、中、优、目——产物是 Token、AST、带类型 IR、优化 IR、目标码。
2. 词法切记号，语法搭骨架，语义定类型，中表示抽象，优化提效率，后端落地成。
3. 编译管的是"一次投入、多次摊销"，解释管的是"每次重来、处处从零"。

**词法分析**
4. 正则描述 → NFA → DFA → 最小化，这条链是词法分析的标准流水线。
5. Thompson 造 NFA，子集法定 DFA，Hopcroft 做最小化，三步走完出转移表。
6. DFA 不回溯，NFA 会回溯；回溯最坏指数级，ReDoS 由此而来。
7. 关键字与标识符同形：先按标识符认，再查关键字表升级种别。
8. 匹配最长优先，长度相同看优先级，再同优先级就是词法冲突。
9. 词法三要素：种别、属性、位置；位置不给，报错等于白报。
10. 正规式能匹配不能嵌套——括号配对、优先级这类问题，词法层无解。
11. 词法错误只报最长的可疑记号，不做过度恢复。

**语法分析**
12. 文法四元组：非终结、终结、产生式、开始符号。
13. 自顶向下看 FIRST 和 FOLLOW，能往下走才走；自底向上做移进归约。
14. LR 能力阶梯：LR0 → SLR1 → LALR1 → LR1，逐级增强，状态数也逐级爆炸。
15. 递归下降不能带左递归，右递归一用结合性就翻，移减乘除得改写。
16. 二义性三招：优先级声明、分层子文法、左递归改写。
17. 优先级用 %left/%right 声明，编译器自动改文法，冲突自然消。
18. 正则语言不能数括号，CFG 能嵌套不能查类型，语义分析管类型。
19. AST 只留骨架不要推导痕迹，比语法树小一个量级，才是传递结构的标准件。
20. 语法层多报错，语义层报准，错误恢复要同步集合 + 错误节点。

**语义分析**
21. 语义三查：类型查、名字查、控制流查。
22. 符号表是层次栈，查找逐层向外，作用域靠压栈弹栈管。
23. 静态强类型名义型，Java C# TypeScript 都属这一型。
24. 隐式只许安全提升，禁止隐式窄化，字符串与数值必须显式转。
25. 金额计算禁用浮点，要用定点 Decimal，精度问题不能靠运气。
26. 综合属性自底向上传，继承属性自顶向下传，属性依赖图按拓扑求值。
27. 树遍历就是土办法语法制导翻译，边走边标类型边生成 IR。
28. 编译期拦住的是词法语法语义三类错，业务口径错误编译器管不了。
29. 把运行期才暴露的错挪到构建期，就是拿类型系统换测试成本。

**中间表示与优化**
30. IR 五形态：树、DAG、三地址码、SSA、字节码；主 IR 选 SSA 三地址码。
31. 三地址码一句不超过三个操作数，x = y op z，逼近机器又不绑机器。
32. SSA 一变量只赋一次值，配支配树和 φ 节点，常量传播一下就通。
33. 数据流四要素：格、传递函数、边界条件、不动点迭代。
34. 到达定义、可用表达式、活跃变量、常量传播、支配树，五把主力分析尺。
35. 常量折叠靠常量传播，CSE 靠可用表达式，死代码靠活跃变量。
36. 机器无关优化在 IR 层，机器相关优化在后端；分层才可移植。
37. 短路求值把选择性高的前置，恒真恒假的条件直接折叠掉。
38. 条件重排三前提：纯函数、无副作用无异常、类型统一。
39. 有副作用就别重排——编译器必须拒绝，而不是默默给个顺序。
40. 优化等价三性：语义等价必须能证明，证明不了就别上。
41. 度量优化四指标：耗时、吞吐、短路命中、字节码体积；等价率必须 100%。
42. 优化是一次投入多次省，编译是一次投入一次花；执行量够大就值得激进。

**目标代码与执行模式**
43. 后端三大件：指令选择、寄存器分配、指令调度。
44. 寄存器分配走干涉图加图着色，染不上色就溢出到栈。
45. 指令调度在依赖允许下重排，把流水线空泡填满、少停顿。
46. 解释启动快跑得慢，AOT 跑得快改起来难，混合模式两头占。
47. 一次编译多处执行：前端唯一，IR 稳定，后端可插拔。
48. 换平台只换后端，不动前端，不动规则资产——这才是国产化的正解。
49. 字节码版本要和虚拟机版本绑死，向后兼容矩阵是发布必需品。
50. 缓存键五要素：内容哈希、DSL 版本、元数据版本、平台、优化档。
51. 唯一真源永远是源码，字节码只是可再生的构建产物。
52. 加载时校验签名，签名不符一律拒绝加载，绝不静默用旧产物。
53. 灰度期新旧并存跑，比对差异超阈值就自动回滚。
54. 每次判定写下规则版本号与产物哈希，异常才能回溯到确切版本。
55. 编译器不是万能钥匙：规则少、变更频、单次量小的场景，解释式更划算。
