## 今日核心概念

### 1. 系统架构评估方法 ATAM 与 SAAM
定义：架构权衡分析法（ATAM）与软件架构分析法（SAAM）是用结构化场景驱动方式评估软件架构质量属性的工程方法，是系统分析师论文与案例的常考内容。

关键要点：
- ATAM 四阶段九步骤：参与人介绍（Stakeholders/Presenters）、业务动机介绍（业务目标+质量属性场景）、架构介绍（架构视图/约束/模式）、质量属性效用树（QA Utility Tree）、分析架构方法（风险点/敏感点/权衡点/非风险点）、得出结论（场景优先级+风险决策）
- ATAM 核心概念：质量属性（性能/可用性/安全/可修改性/易用性/可测试性六大类）、场景（Stimulus/Response/Environment 三元组）、效用树（层次化质量属性→场景→优先级）
- ATAM 风险点（Risk）：架构决策可能对某个质量属性产生负面影响；非风险点（Non-risk）：架构决策对该质量属性无害；敏感点（Sensitivity point）：某质量属性对某个架构参数值敏感；权衡点（Trade-off point）：影响至少两个质量属性且需要平衡
- SAAM 是 ATAM 的前身，基于场景评估架构，关注变更场景的可支持性
- CBAM（成本效益分析法）是 ATAM 的延续，引入经济性决策
- 评估输出：质量属性效用树、风险登记表、决策建议书

### 2. 软件架构风格与分布式通信模式
定义：架构风格是软件系统高层组织的通用模式，规定组件类型、连接件类型、交互模式与约束；分布式通信模式是微服务与云原生架构下的服务间协作机制。

关键要点：
- 经典架构风格：管道-过滤器（Pipe-Filter，如编译器）、分层架构（Layered，如 MVC/三层架构）、客户端-服务器（C/S）、浏览器-服务器（B/S）、事件驱动（EDA，发布订阅）、微服务（Microservices，面向服务+独立部署）
- 微服务九大特性：独立部署、技术异构、去中心化数据存储、自动化部署、智能端点与哑管道、轻量级通信（HTTP/REST/gRPC）、领域驱动设计、容错设计、演进式设计
- 服务间通信三大模式：同步调用（REST/gRPC/Thrift）、异步消息（Kafka/RocketMQ/RabbitMQ）、事件驱动（EDA，发布订阅）
- 服务发现三种方式：客户端发现（Eureka + Ribbon）、服务端发现（K8s Service + DNS）、注册中心（Consul/Nacos）
- API 网关职责：路由转发、统一鉴权、限流熔断、协议转换、灰度发布、监控埋点；与中心化服务治理不同，网关侧重入口控制
- 服务网格 Service Mesh：Sidecar 模式（Envoy）将通信能力下沉到基础设施层，业务代码零侵入；Istio/Linkerd 为代表

### 3. 软件可靠性与容错设计
定义：软件可靠性是系统在规定条件下、规定时间内完成规定功能的能力；容错设计是通过冗余、检测、恢复机制使系统在故障发生时仍能维持服务的技术体系。

关键要点：
- 可靠性度量指标：MTTF（平均无故障时间）、MTTR（平均修复时间）、MTBF（平均故障间隔 = MTTF+MTTR）、可用性 Availability = MTTF/(MTTF+MTTR) = 1/(1+MTTR/MTTF)；"5 个 9" 表示 99.999% 可用性
- 软件可靠性模型：Jelinski-Moranda、Littlewood-Verrall、Musa-Okumoto、Goel-Okumoto（NHPP 非齐次泊松过程），预测软件失效行为
- 容错设计四大策略：冗余（Redundancy，硬件N+1/软件多副本）、检测（Detection，心跳/超时/校验和）、隔离（Isolation，故障域划分/舱壁模式/Bulkhead）、恢复（Recovery，重启/降级/熔断/限流）
- 数据复制三大模式：同步复制（强一致性能差）、异步复制（性能高可能丢数据）、半同步复制（折中）
- 故障转移（Failover）策略：主动-主动（Active-Active）、主动-被动（Active-Passive，热备/温备/冷备）
- 分布式系统八种谬误（Fallacies of Distributed Computing）：网络可靠、延迟为零、带宽无限、网络安全、拓扑不变、单一管理员、传输成本为零、网络同质——设计时必须警惕的认知陷阱

### 4. 信息安全体系与等级保护
定义：信息安全体系是覆盖机密性、完整性、可用性的综合防护框架；等级保护是中国《网络安全法》规定的强制性安全分级制度，是政务与重点行业信息系统的合规基线。

关键要点：
- 信息安全三要素 CIA：机密性 Confidentiality（加密/访问控制）、完整性 Integrity（哈希/数字签名）、可用性 Availability（容灾/备份）；扩展五要素加入 真实性 Authenticity、不可否认性 Non-repudiation
- 安全防护五道防线：物理安全（门禁/监控/防火）、网络安全（防火墙/IDS/IPS/VPN/WAF）、主机安全（补丁/加固/基线）、应用安全（OWASP Top 10/代码审计/SQL注入/XSS/CSRF）、数据安全（加密/脱敏/备份/分类分级）
- OWASP Top 10（2021 版）：A01 访问控制失效、A02 加密失败、A03 注入（SQL/命令/XXE）、A04 不安全设计、A05 安全配置错误、A06 易受攻击和过时的组件、A07 识别和认证失败、A08 软件和数据完整性故障、A09 安全日志和监控失败、A10 服务端请求伪造 SSRF
- 等级保护 2.0（GB/T 22239-2019）：五级保护对象（用户自主保护/系统审计保护/安全标记保护/结构化保护/访问验证保护），三级为政务系统标配
- 等保 2.0 五项技术要求：安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心；五项管理要求：安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理
- 密码学三件套：对称加密（AES/DES/3DES，加解密同密钥性能高）、非对称加密（RSA/ECC/SM2，加解密不同密钥用于密钥协商/签名）、哈希算法（MD5/SHA-1 已不安全/SHA-256/SM3，完整性校验）
- 数字签名与数字信封：数字签名（私钥签名公钥验证，不可否认+完整性）、数字信封（用对称密钥加密数据再用接收方公钥加密对称密钥，结合加密与签名）
- PKI 公钥基础设施：CA 证书颁发机构 + RA 注册机构 + 证书 + CRL/OCSP 吊销列表；HTTPS = HTTP + TLS（SSL 已淘汰）握手过程四次交互

### 5. 系统运行与维护管理
定义：系统运行与维护是软件生命周期中时间占比最长的阶段（占比 70% 以上），涵盖从系统上线到退役全过程的运维保障、持续改进与变更管控。

关键要点：
- 运维四类活动：改正性维护（Corrective，修复缺陷，占比 20%）、适应性维护（Adaptive，适应环境变化 25%）、完善性维护（Perfective，功能增强 50%）、预防性维护（Preventive，主动改进 5%）
- ITSM 框架：ITIL 4 服务管理四大维度（组织与人员/信息与技术/价值流与流程/合作伙伴与供应商）、服务价值系统 SVS、34 个最佳实践
- ITIL 4 服务管理实践：事件管理（Incident）、问题管理（Problem）、变更管理（Change）、发布管理（Release）、配置管理（CMDB）、服务台（Service Desk）、服务水平管理（SLA/SLO/SLI）、可用性管理、容量管理、连续性管理、信息安全管理
- 变更管理 CAB/ECAB：CAB 变更顾问委员会（周例会评审标准变更）、ECAB 紧急变更顾问委员会（紧急变更 24h 内响应）；变更类型：标准变更（预授权）、正常变更（CAB 评审）、紧急变更（ECAB 速批）
- CMDB 配置管理数据库：CI 配置项（服务器/应用/数据库/网络/文档）、CI 关系（运行于/连接于/依赖）、联邦式 CMDB（多源整合）
- 运维监控黄金三指标：USE 方法（Utilization 利用率/Saturation 饱和度/Errors 错误率，资源视角）、RED 方法（Rate 请求率/Errors 错误数/Duration 时延，服务视角）、Google 四黄金信号（Latency/Errors/Traffic/Saturation）
- AIOps 智能运维：异常检测（时序预测+统计阈值）、根因分析（RCA，调用链+日志聚类）、告警收敛（事件合并+降噪）、容量预测（机器学习预测资源）
- SLA 99.99% = 月宕机 ≤ 4.32 分钟、99.999% = 月宕机 ≤ 25.9 秒

## 案例分析题
**题目**：
某省级政务云平台承载社保、医保、公积金等 12 个核心业务系统，采用微服务架构部署在 K8s 集群中（3 主节点 + 12 工作节点），日均 API 调用量 2.3 亿次。近期发生以下问题：
(1) 某次医保接口调用链路过长（涉及 7 个微服务），导致 P99 响应时间达 4.8 秒，超过 SLA 约定的 1 秒；
(2) 上线新版本"电子社保卡"时，部分用户出现"数据未同步"导致重复报销风险；
(3) 等保测评发现系统未实现完整的访问控制与审计日志，存在合规风险；
(4) 凌晨 3 点 K8s 主节点故障导致 30 分钟服务不可用，业务部门投诉。
作为系统分析师，请针对以上问题提出架构优化方案。

**参考答案**：

一、性能问题（P99=4.8s 超标）
1. 调用链分析：通过 SkyWalking/Pinpoint 全链路追踪识别 7 个微服务中的慢服务节点，重点优化数据库访问与远程调用
2. 异步化解耦：非核心链路（如通知/审计/日志）改为 MQ 异步处理，缩短主链路耗时
3. 引入缓存层：Redis 缓存热点数据（如参保人基本信息），降低数据库压力，TTL 随机化避免雪崩
4. 数据预加载/预计算：常用查询结果提前计算并缓存到 Redis 或 CDN
5. 数据库优化：分库分表（按地市拆分）、读写分离、SQL 优化、索引优化
6. 同步改异步：部分非关键路径改造为事件驱动架构
7. 服务网格治理：Istio + Envoy 实现超时控制、熔断、限流，避免慢调用拖垮全链路

二、数据一致性问题（电子社保卡同步失败）
1. 分布式事务方案选型：
   - 强一致场景（资金扣减）：采用 TCC（Try-Confirm-Cancel）或 Seata AT 模式保证强一致
   - 最终一致场景（数据同步）：采用本地消息表 + MQ 可靠消息 + 幂等消费
   - 大事务拆分：Saga 模式（长事务拆分+补偿子事务）
2. 数据双写一致性：采用 Binlog 监听（Canal/Debezium）异步同步 + 失败重试 + 人工补偿
3. 幂等性设计：所有写入操作携带业务唯一键，通过唯一索引或 Redis 去重表防重
4. 补偿机制：定时任务对账补偿 + 异常告警人工介入

三、安全合规问题（等保测评）
1. 访问控制：实施 RBAC（基于角色）+ ABAC（基于属性）双层权限模型，最小权限原则
2. 统一身份认证：OAuth 2.0 + JWT 令牌 + CAS 单点登录，密码策略（复杂度/定期更换/多因子认证 MFA）
3. 审计日志：所有 API 调用、数据库操作、管理操作记录审计日志，日志保留 ≥ 180 天，防篡改（哈希链或区块链存证）
4. 数据加密：传输层 HTTPS/TLS 1.2+、敏感字段 AES 加密存储、密码 bcrypt/Argon2 哈希
5. 等保三级要求落实：安全区域边界（防火墙/WAF/IDS）、安全计算环境（主机加固/漏洞扫描/补丁管理）、安全管理中心（集中管控/态势感知）
6. 渗透测试与代码审计：上线前安全测试，定期第三方测评

四、高可用问题（主节点故障 30 分钟不可用）
1. K8s 高可用：3 主节点跨可用区部署（不同机房/不同交换机），etcd 集群 5 节点 Raft 选举
2. 多活架构：同城双活（两个数据中心同时对外服务）+ 异地灾备（异步复制，RPO ≤ 5 分钟、RTO ≤ 30 分钟）
3. 数据库高可用：MySQL MGR 组复制（自动故障转移 ≤ 30 秒）/ OceanBase 三地五中心
4. 故障演练：Chaos Engineering（Chaos Monkey/ChaosBlade）定期注入故障验证容灾
5. 故障检测与自愈：K8s liveness/readiness 探针 + 自动重启 + HPA 自动扩缩容
6. 应急预案：分级故障响应（P0-P4）+ 故障演练手册 + 7×24 值班

五、综合改进
1. 监控告警体系：Prometheus + Grafana（指标）+ Loki/ELK（日志）+ SkyWalking（链路）+ Alertmanager（告警）
2. AIOps 智能运维：异常检测、根因分析、告警收敛、容量预测
3. DevOps 流水线：GitLab CI + Argo CD 自动化部署 + 灰度发布 + 一键回滚
4. 容量管理：压测常态化（全链路压测影子表）、容量规划、弹性伸缩
5. 运维手册：Runbook 标准化、值班 SOP、故障复盘机制（Postmortem）

**踩分要点**：
- 性能优化要点：缓存+异步+分库分表+熔断限流+服务网格，缺一不可
- 一致性要点：分清强一致/最终一致场景，给出 TCC/Seata/本地消息表/Saga 具体方案
- 安全合规要点：等保三级五项技术+五项管理必须答全，访问控制+审计+加密是核心
- 高可用要点：跨可用区部署+多活+容灾+故障演练+RTO/RPO 定义
- 综合能力：体现监控/告警/CI-CD/AIOps 体系化运维思维
