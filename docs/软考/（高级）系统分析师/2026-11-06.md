## 今日核心概念

### 1. 容器化基础与 OCI 运行时规范

**定义**：容器化是通过 namespace（视图隔离）、cgroups（资源限制与计量）、联合文件系统（overlayfs 分层只读镜像）把应用及其全部运行依赖打包为不可变镜像（OCI Image Spec），再由容器运行时（containerd / CRI-O）通过标准 CRI 接口交给编排器调度执行的轻量虚拟化技术。它共享宿主机内核，隔离边界在用户态，密度远高于虚拟机但安全边界弱于硬件虚拟化。

**关键要点**：
- **三重隔离机制**：namespaces（pid / net / mnt / uts / ipc / user，负责"看不见"）、cgroups（cpu / memory / io，负责"用不了"）、overlayfs（分层只读 + 可写层，负责"改不了"）。
- **镜像与容器的区别**：镜像是不可变的分层制品（manifest + config + 层 tar），容器是镜像的运行实例（增加可写层、命名空间、运行时配置）。**tag 是可变指针，digest（sha256）才是不可变引用**。
- **OCI 三大规范**：Runtime Spec（运行时配置）、Image Spec（镜像格式）、Distribution Spec（仓库分发协议）；**CRI** 是 kubelet 与运行时之间的接口标准，Docker 已退出 CRI 主实现，containerd / CRI-O 为主流。
- **镜像分层与联合文件系统**：每层只读、叠加挂载，写时复制（CoW），删除文件在容器内只是白障标记（UnionFS 语义），这一特性直接决定了镜像瘦身与"层缓存命中率"的价值。
- **与虚拟机的对比**：虚拟机启动分钟级、GB 级镜像、内核级隔离；容器启动秒级、MB 级镜像、共享内核。容器安全必须依赖 **capability 裁剪 + seccomp + AppArmor/SELinux + user namespace 降权 + 只读根文件系统**。
- **国产化适配要点**：multi-arch manifest（amd64 / arm64 / 鲲鹏）、基础镜像离线内网仓库、依赖源替换（麒麟 / 统信 yum 与 deb 源）、跨架构二进制（Java 需架构无关的 JRE 或提供 arm64 包）、镜像签名与漏洞基线扫描。

### 2. Kubernetes 架构与声明式编排的控制循环

**定义**：Kubernetes 是以"声明式 API + 控制器协调循环（Reconcile）"为核心的开源容器编排系统：用户只提交期望状态（Object 或 CRD），控制器持续比对实际状态与期望状态并驱动系统收敛（Convergence）；调度器负责把 Pod 绑定到合适节点，kubelet 通过 CRI 拉起容器并上报状态。

**关键要点**：
- **控制平面六组件**：kube-apiserver（唯一入口，认证/鉴权/准入/聚合）、etcd（唯一权威状态存储）、kube-scheduler（打分与绑定）、kube-controller-manager（各类控制器循环）、cloud-controller-manager、kubelet（节点代理）。
- **声明式 vs 命令式**：只写"要什么"（spec），不写"怎么做"；**幂等性是控制循环成立的前提**，同一期望状态反复 apply 结果一致。
- **Reconcile 控制循环**：观测（Observe）→ 求差异（Diff）→ 制定计划（Plan）→ 执行（Act）→ 再次观测。差异本身就是"事件源"，所以 Kubernetes 不依赖外部事件驱动也能自愈，声明式是自愈的前提。
- **API 对象三要素**：metadata（name / namespace / labels / annotations）、spec（期望状态）、status（实际状态）。**控制器只允许写 status，不允许改 spec**——保证期望状态只能由用户或上层控制器修改。
- **扩展机制四条线**：CRD + Operator（声明式扩展 API 与领域控制器）、Admission Webhook（Mutating 改写 / Validating 校验）、Scheduler Framework（扩展打分与过滤）、Ingress / Gateway API（七层流量）。
- **Operator 模式**：把特定领域知识（数据库、消息队列、中间件）封装成"自定义控制器 + 自定义资源"，用声明式 API 管理有状态软件的生命周期，取代大量脚本化运维。

### 3. 工作负载模型与有状态服务编排

**定义**：Kubernetes 为不同工作负载语义提供不同编排模型：Deployment 管理无状态服务的多副本与滚动更新，StatefulSet 为每个副本提供稳定网络标识与有序启停并绑定独占存储，DaemonSet 保证每个节点一份代理，Job / CronJob 面向一次性与周期任务，ConfigMap / Secret 管理配置与密钥。

**关键要点**：
- **Deployment**：副本数由 ReplicaSet 维持；滚动更新由 `maxSurge`（可超出的新副本数）与 `maxUnavailable`（可不可用的旧副本数）两个旋钮控制；配合 `readinessProbe` 实现"先就绪再切流"。
- **StatefulSet**：Pod 名称含序号（web-0 / web-1），提供稳定 DNS（`web-0.web.headless-svc`）、**OrderedReady 有序启停**、稳定存储（每副本独立 PVC）、**按序滚动更新**（从序号大到小逐个替换）。适合数据库、消息队列等有状态中间件。
- **DaemonSet**：节点代理型负载（日志采集、监控 Agent、CNI 插件、存储驱动），随节点增减自动伸缩，无需副本数概念。
- **Job / CronJob**：Job 负责一次性任务至多成功 N 次；CronJob 按 Cron 表达式周期调度，涉及时区、并发策略（Forbid / Allow / Replace）与错过补跑策略。
- **配置与密钥分离**：ConfigMap 存非敏感配置，Secret 存敏感配置（**默认仅 base64 编码，不是加密**，必须配合 KMS 加密插件或外部密钥管理如 Vault，并关闭 etcd 明文存储）。
- **存储三件套**：PV（集群级存储资源）/ PVC（命名空间级使用声明）/ StorageClass（动态供给模板）；访问模式 RWO / ROX / RWX；StatefulSet 用 `volumeClaimTemplates` 为每个副本生成专属 PVC，**不能共享 PVC**。
- **服务网络与发现**：Pod 网络扁平互通由 CNI 插件实现；Service 通过 kube-proxy（iptables / eBPF 模式）做四层负载均衡；Ingress 做七层路由与域名分发；CoreDNS 提供集群内 DNS 解析与服务发现；NetworkPolicy 做网络层面的隔离（默认放通，需显式定义白名单）。
- **自愈三探针**：startupProbe（启动慢的应用，避免启动期被误杀）、livenessProbe（存活判断，失败则重启容器）、readinessProbe（就绪判断，失败则从 Service 摘除但不重启）。三探针语义必须分开，混用是生产事故高发点。

### 4. 弹性伸缩、资源配额与 QoS 治理

**定义**：资源治理是通过 requests（调度依据）、limits（运行上限）、QoS 等级、PriorityClass 优先级、资源配额（ResourceQuota / LimitRange）把集群资源分配秩序化，避免超卖引发级联驱逐与 OOM，实现"忙时扩得开、闲时收得住、核心服务不被牺牲"。

**关键要点**：
- **requests 与 limits 的分工**：requests 决定"能不能调度到这里"（按 requests 预留资源），limits 决定"最多能吃多少"。**CPU 超限被限流（Throttle），内存超限被 OOMKilled（进程被直接杀死，无优雅退出机会）**，两者后果完全不同。
- **QoS 三档（优先级从高到低）**：Guaranteed（requests = limits 且 CPU 与内存都设置）/ Burstable（默认档，requests < limits）/ BestEffort（完全未设）。**节点资源不足时按 QoS 从低到高依次驱逐**，因此线上核心服务必须保证 Guaranteed。
- **优先级与抢占**：PriorityClass 定义优先级；抢占（Preemption）按优先级驱逐低优先级 Pod 为高优先级腾出资源，但被抢占者若使用 Guaranteed 且设置了 PDB 会更安全。
- **HPA 三类指标**：资源型（CPU / 内存利用率，**必须有 requests 作为分母，否则指标失真**）、自定义指标（Prometheus 中的队列长度等业务指标）、外部指标（消息队列积压量）。**选错指标是 HPA 振荡的主因**：瓶颈在数据库时，扩容应用只会让数据库更堵，指标不降反而触发更多扩容。
- **纵向 vs 横向 vs 集群级**：VPA 调整单 Pod 的 requests/limits（与 HPA 同 Pod 上互斥）、HPA 调整副本数、Cluster Autoscaler 调整节点数；**正确顺序是 HPA 先扩 Pod → 调度器放不下 → Cluster Autoscaler 扩节点**；Karpenter 则按 Pod 规格做节点碎化与整合，替代 CA。
- **超卖与排队**：CPU 可超卖（时间片复用），内存不可超卖；超卖比过高时 CPU 争抢使单请求延迟显著上升，形成"应用层排队"，与虚拟机时代的性能问题同源。
- **资源配额与限制**：ResourceQuota 约束命名空间总量（CPU、内存、Pod 数、对象数），LimitRange 为未声明 requests/limits 的 Pod 注入默认值——**没有 LimitRange，命名空间里的 Pod 默认落在 BestEffort，是驱逐首杀对象**。

### 5. DevOps 持续交付与软件供应链安全

**定义**：DevOps 以"小批量、高频次、自动化、可观测、可回滚"为原则打通开发与运维：CI 负责构建、测试、安全扫描与制品入库，CD 负责按环境晋级发布；GitOps 进一步把环境的期望状态纳入版本控制，由控制器持续调谐（Sync）与漂移检测（Drift Detection），实现"Git 是唯一事实源"。

**关键要点**：
- **流水线即代码**：Pipeline as Code 与 IaC 同等重要，流水线变更必须走评审与版本化，否则流水线本身成为攻击入口。
- **质量门禁（Quality Gate）**：单元测试覆盖率、代码扫描、依赖漏洞、镜像扫描不达标即阻断合并或阻断晋级，且阈值应分级（阻断 / 告警）。
- **一次构建多环境晋级**（build once, promote many）：**制品不可变**，同一镜像 digest 从测试环境晋级到生产环境，杜绝"每个环境各编一次"导致的环境漂移。
- **制品标识**：使用 `image@sha256:digest` 而非可变 tag；配合 Harbor 等制品库的保留策略、复制策略与扫描结果存储。
- **供应链安全五件套**：SBOM（软件物料清单，列出全部依赖）、镜像签名与准入验证（cosign / Notary，在准入阶段验证签名）、漏洞扫描与基线、依赖来源治理（私有源、白名单）、最小化镜像（无 shell、无多余包，减少攻击面）。
- **GitOps 机制**：期望状态声明在 Git 中，控制器比集群实际状态并自动纠偏（自愈），提供漂移检测告警与一键回滚（版本回退即 Git revert）；权限模型收敛为集群内的 GitOps 控制器持有最小权限。
- **发布策略三选一**：滚动更新（资源开销小、切换慢）、蓝绿（切换瞬时、需双倍资源、回滚最快）、金丝雀（按比例放量、需指标自动判停）。
- **配置与密钥治理**：配置分环境管理（Helm values / Kustomize overlay），密钥不入 Git（External Secrets / KMS），镜像中不烘焙环境配置。
- **DORA 四指标**：部署频率、变更前置时间（Lead Time for Changes）、变更失败率、平均恢复时间（MTTR），是持续交付成效的量化标尺。

3. 回滚依赖从备份包人工恢复，平均耗时 45 分钟，平均每月发生 2 次；
4. 上季度发生 3 次整机故障（单节点网卡驱动异常导致服务级雪崩），跨节点故障定位困难；
5. 领导要求 3 个月内完成容器化改造，同步适配国产化环境（鲲鹏 ARM 64 + 麒麟 V10 + 统信 UOS），并支持两地三中心容灾与常态化灰度发布。

**参考答案**：

### 问题 1 答案：容器化改造方案

**（1）三重隔离机制设计**
- **namespaces**：每个容器独立 pid、net、mnt、uts、ipc 命名空间；net namespace 配合 CNI 插件实现 Pod 内多容器共享网络与 Pod 间扁平互通；user namespace 配合 capability 裁剪实现非 root 运行。
- **cgroups v2**：为每个容器限制 CPU 份额（权重）、内存上限（hard limit）、IO 权重，并作为资源计量与 QoS 判定依据；内存上限设置要留出运行时开销余量。
- **overlayfs 分层**：基础镜像层（发行版 + JRE）只读共享，业务镜像层只写应用制品，运行层承载日志与临时文件；**日志必须落 stdout/stderr 由日志采集器收集，禁止写入容器可写层**（否则容器重建即丢日志且撑爆磁盘）。
- **安全基线**：非 root 用户运行、只读根文件系统（readOnlyRootFilesystem）、禁止特权容器、seccomp 默认拒绝、禁止 hostNetwork / hostPID（确需使用须安全评审）、镜像来源仅允许内网受信仓库、镜像须通过漏洞扫描与签名验证。

**（2）多架构镜像与国产化适配**
- **构建方式**：在同一 Dockerfile 基础上用 buildx 跨架构构建，产出 multi-arch manifest（`linux/amd64`、`linux/arm64`），由 manifest list 统一索引；也可采用 CI 多节点并行构建后 push 并合并 manifest。
- **基础镜像**：使用鲲鹏 + 麒麟 V10 / 统信 UOS 对应的 arm64 基础镜像，并在内网私有仓库按 `项目/镜像/标签-arch` 组织；**离线环境下需预先完成 apt/yum 源替换与依赖预热**。
- **语言与依赖**：Java 应用需确认 JDK 的 arm64 版本可用（优先使用架构无关的 JRE 或提供 arm64 构建）；原生依赖（加密库、OCR、签章控件、数据库驱动）必须提供 arm64 版本，否则需在 arm64 环境重新编译或改用纯 Java 实现。
- **验证与回流**：arm64 镜像须在真机（鲲鹏）上完成功能、性能与兼容性回归，不能只在 x86 上通过"能跑"判定；建立 x86 与 arm64 双构建流水线与差异清单。

### 问题 2 答案：工作负载选型与发布策略

| 模块 | 工作负载 | 理由 |
|---|---|---|
| 统一认证服务 | Deployment（多副本 + HPA） | 无状态、多实例水平扩展；需高可用与弹性；配合会话外置（Redis）与负载均衡 |
| 办件流程引擎 | Deployment（无状态副本）+ 流程状态持久化到数据库；如需单点串行则用 Deployment + 分布式锁 | 流程引擎应尽量无状态化，把流程状态、节点流转记录落入 MySQL，靠乐观锁保证一致性，避免用 StatefulSet 带来的耦合 |
| 消息通知服务 | Deployment（消费者组，多副本） | 消费 RocketMQ 天然多副本；需保证同消息不重复处理（幂等键），扩缩容不影响消息顺序保证范围 |
| 定时对账批处理任务 | CronJob（并发策略 Forbid 或 Allow，配合分片） | 周期性一次性任务，任务完成即退出，无需常驻副本；大任务用分片参数并行，避免单实例超时 |
| 数据库 / Redis / RocketMQ / MinIO | StatefulSet + volumeClaimTemplates（或有状态中间件 Operator） | 需要稳定网络标识、有序启停、独占持久卷 |
| 日志与监控采集 | DaemonSet | 每节点一份 |

**滚动更新与回滚策略**
- 滚动更新：`maxSurge=1`、`maxUnavailable=0`（核心服务）保证任何时刻有足量可用副本；配合 `readinessProbe` 就绪后再切流、`minReadySeconds` 防止刚就绪即被切流抖动。
- 回滚：`kubectl rollout undo` 基于 Deployment 的 revision 历史回退到上一版本；前提是**镜像不可变、tag 唯一、每版本一个 digest**（推荐用 `image@sha256:...`），否则回滚可能拉到已被覆盖的镜像。
- 灰度：核心服务采用金丝雀（先 5% 流量 → 观察 DORA 指标与错误率 → 全量），配合 Argo Rollouts 或 Nginx Ingress 权重切分。
- **为何不能"直接改 Pod 镜像"回滚**：Pod 是控制器调谐出来的，Deployment 的 ReplicaSet 会把任何偏离 spec 的改动视为"漂移"并强制恢复，新 Pod 拉起后又变回新镜像，回滚失效；正确做法是**修改控制器期望状态（spec）**（回退镜像字段或 rollout undo），由控制器收敛出旧版本实例。
- 额外约束：PodDisruptionBudget 保证节点排空期间最小可用副本；优雅终止配置 `terminationGracePeriodSeconds` + preStop 钩子，保证在途请求处理完毕，避免发布即报错。

### 问题 3 答案：资源治理与弹性伸缩

**（1）资源治理**
- 为每个服务设定 **requests 与 limits**：requests 按 P95 用量 + 20% 余量设定，作为调度与 HPA 基准；limits 对内存设置硬上限（预留 15% 运行时开销），对 CPU 设置为 requests 的 2—3 倍以允许短时突发。
- **核心服务（认证、流程引擎）必须为 Guaranteed 档**（requests = limits，CPU 与内存均设）；普通服务为 Burstable；批处理类可为 BestEffort 但需明确接受被驱逐。
- 设置 **PriorityClass**：核心在线服务最高，通知服务次之，批处理最低；配合 **PodDisruptionBudget** 保护核心服务副本不被随意驱逐。
- 命名空间级设置 **ResourceQuota**（CPU/内存/Pod 数上限）与 **LimitRange**（为未声明的 Pod 注入默认 requests/limits，防止新服务默认落入 BestEffort）。
- 为队列型负载（RocketMQ 消费、通知发送）配置合适的 JVM 堆上限与容器内存上限匹配，避免堆外内存被 OOM 杀死（`-Xmx` 应小于容器 limit 且留出元空间与线程栈余量）。

**（2）弹性伸缩**
- **HPA**：核心服务按 CPU 利用率扩容；同时对"消息积压量""待处理办件数"等自定义业务指标做扩容，避免业务量涨但 CPU 不涨（I/O 密集型）时无法扩容。
- **Cluster Autoscaler**：节点级扩缩，与 HPA 配合（先 HPA 扩 Pod，再由 CA 扩节点）；考虑采用 Karpenter 做节点整合，降低碎片化成本。
- **定时预扩容**：针对 9:00—11:00 固定高峰，采用定时策略（如 8:30 预扩到基线 2 倍）比纯 HPA 更稳，避免指标滞后导致的扩容不及时。
- **成本治理**：闲时通过 HPA 缩容到最小副本 + 节点自动回收 + Spot/竞价实例承担可中断负载（批处理与非核心服务），实现"闲时收得住"。

**（3）HPA 选型不当的问题分析**
- **CPU 利用率对 I/O 密集型服务失真**：认证与流程引擎大量时间在等待数据库与外部接口，CPU 只有 20% 但请求已积压；以 CPU 为指标则不扩容，反而在高峰持续超时。
- **分母缺失导致指标失真**：未设 requests 时 CPU 利用率按节点核数或实际使用计算，指标不稳定，易触发振荡式扩缩（Scale-Up 后负载下降触发缩容，缩容后又积压，形成"呼吸式"抖动），并造成大量 Pod 创建销毁与连接风暴。
- **扩了瓶颈不降**：瓶颈在 MySQL 或 Redis 时，扩容应用只会让数据库并发连接激增，排队更长，甚至连接池打满触发雪崩——**扩容必须先定位瓶颈层次（应用/中间件/数据库/网络）**。
- **无稳定窗口导致震荡**：缺少 stabilizationWindow 与冷却期，指标抖动引发连续伸缩，进一步加剧数据库压力。
- **结论**：HPA 只解决"应用层横向扩容"，无法解决数据库与外部依赖瓶颈，必须配合限流、熔断、缓存、异步化与数据库连接池治理。

### 问题 4 答案：故障根因判别与处置

**（1）Pod 长期 Pending**
- 判别：`kubectl describe pod` 查看 Events，重点看 FailedScheduling 原因（Insufficient CPU / Insufficient memory / node(s) had untolerated taint / pod has unbound immediate PersistentVolumeClaims / node affinity conflict）。
- 处置：核对 requests 是否设置过大（相对于节点可分配量）；检查节点污点与容忍、亲和性/反亲和性约束；检查 PVC 是否已绑定（StorageClass 供给失败、拓扑约束）；检查配额（ResourceQuota）是否耗尽。根本对策：合理设置 requests、配额扩容、调度约束松绑、增加节点。

**（2）CrashLoopBackOff**
- 判别：`kubectl logs --previous` 看上一次容器日志；区分"启动即崩"（配置缺失、数据库连接失败、密钥未注入、镜像与架构不匹配导致 Illegal instruction）与"运行一段时间崩"（OOM、依赖不可用）。
- 处置：核对环境配置与 Secret 是否注入；核对数据库/中间件地址与网络策略；核对镜像架构与节点架构是否一致；将日志落 stdout 便于采集；完善启动自检与依赖就绪探针。

**（3）OOMKilled**
- 判别：`describe` 中 `Reason: OOMKilled`；对比容器 limit 与进程实际占用；区分**容器内存不足**（limit 过小，含 JVM 堆外、线程栈、直接内存）与**JVM 堆溢出**（日志出现 OutOfMemoryError）。
- 处置：调大内存 limit 并同步提高 `-Xmx`（堆占容器内存约 70%—75%，其余留给元空间、线程栈、直接缓冲）；排查内存泄漏（缓存无上限、集合持续增长、流未关闭、监听器未注销）；对已确认的内存上限使用 `requests = limits` 保障不被打扰；避免在容器内 swap。

**（4）ImagePullBackOff**
- 判别：核对仓库地址、凭据 Secret 是否存在且有效、镜像 tag/digest 是否存在、节点到仓库网络是否可达、证书与私有 CA 信任是否配置；多架构 manifest 是否包含目标架构。
- 处置：修复凭据与网络策略（NetworkPolicy 放通仓库）、导入内部 CA、更新镜像版本或架构、重启拉取；同时用 `imagePullPolicy: IfNotPresent` 配合预拉取与本地缓存，避免每次重启都拉取；批量恢复时用滚动重启分批推进，避免全量同时失败引发雪崩。

**（5）就绪探针配置不当导致雪崩**
- 典型错误：就绪探针指向的依赖（数据库、Redis）在高峰超时，导致 readiness 失败 → 实例被从 Service 摘除 → 剩余实例负载更重 → 更多实例探针失败 → **全部实例被摘除 → 流量无后端 → 全站不可用**，即"探针放大故障"。
- 处置：立即回滚发布或临时放宽探针；恢复后修正探针设计。
- **三类探针配置原则**：
  - **startupProbe**：启动慢的应用用它兜底（配宽松失败阈值），启动完成前 liveness/readiness 不生效，避免启动期误杀；
  - **livenessProbe**：只检查"进程还活着"这类不依赖外部服务的轻量条件，**绝不把数据库、下游接口写进 liveness**，否则外部依赖抖动会引发全量重启；
  - **readinessProbe**：可包含关键依赖，但必须设置 `failureThreshold × periodSeconds` 的容忍窗口大于依赖抖动时间，并配合 `initialDelaySeconds` 与 `timeoutSeconds`；探针要轻量、避免探针本身压垮下游（可用缓存或独立健康检查端点）。
  - 通用原则：探针结果进入 Service 端点剔除有"抖动"风险，因此须结合熔断、限流与最小可用副本数（`minAvailable`）共同设计。

### 问题 5 答案：持续交付与供应链安全

**（1）流水线门禁**
- 流水线即代码，纳入代码仓并走评审；阶段划分：提交检查（格式、Lint、单元测试、覆盖率阈值）→ 依赖与 SAST 扫描 → 构建镜像并生成 SBOM → 镜像漏洞扫描 → 集成/回归测试 → 签名与推送仓库 → 部署测试环境 → 冒烟 → 审批门禁 → 生产发布。
- **门禁分级**：覆盖率跌破基线、SAST 高危问题、镜像 Critical/High 漏洞 → 阻断流水线；中低危 → 告警并生成工单限期修复；紧急修复通道需双人审批并留痕。

**（2）制品晋级**
- **一次构建多环境晋级**：测试、预发布、生产使用同一 digest 制品，环境差异只体现在外部配置（ConfigMap / 环境变量 / Secret）；
- 制品标识使用 digest，`image@sha256:...`，禁止生产直接使用 `latest` 等可变 tag；
- 生产环境 `imagePullPolicy: Always` 配合 digest 固化（等效于不可变），并对生产仓库启用签名准入；
- 制品库启用保留策略、复制策略与扫描结果持久化，保留可追溯的发布审计记录。

**（3）GitOps**
- 环境期望状态以 Git 为唯一事实源（Deployment / Service / Ingress / HPA 等 manifest 或 Helm chart + Kustomize overlay），由 Argo CD / Flux 持续调谐：检测集群实际状态与 Git 的差异并自动纠偏（自愈），提供漂移告警与版本回退；
- 生产变更走 Git PR 评审 → 合并 → 自动同步，变更记录天然可审计；
- 权限收敛：集群侧只由 GitOps 控制器持有必要权限；人员不直连生产集群改配置，杜绝"改了没人知道"；
- 密钥不进入 Git，使用 External Secrets / KMS 由外部密钥源同步注入。

**（4）镜像签名与准入验证**
- 使用 cosign / Notary 对镜像 digest 签名，私钥存放于 KMS 或 HSM，禁止进入仓库与 CI 明文变量；
- 在 Kubernetes 准入控制阶段配置验证策略（Validating Admission Policy / Kyverno / Sigstore policy-controller），**只允许通过签名验证且来源受信的镜像创建 Pod**，未签名或签名不符直接拒绝；
- 关联 SBOM 与镜像 digest，出现漏洞时可精确圈定受影响 Pod 并批量处置。

**（5）度量与闭环**
- 以 DORA 四指标（部署频率、变更前置时间、变更失败率、平均恢复时间）度量交付效能，配合变更失败回滚率、平均回滚耗时等本地指标；发布后以错误率、P99 延迟、饱和度等指标驱动金丝雀自动判停与回滚。

## 踩分要点

1. **问题 1 必须答出容器三重隔离**：namespaces（视图隔离）、cgroups（资源限制与计量）、联合文件系统/overlayfs（分层与写时复制），三者缺一即为踩分点；只答"轻量虚拟化、启动快"不得分。
2. 区分**镜像与容器**：镜像是只读不可变分层制品，容器是其运行实例；tag 可变、digest 不可变，这一点直接支撑后续回滚与供应链论证。
3. 提到 **OCI 规范（Runtime/Image/Distribution）与 CRI**，说明 Docker 已非 CRI 主实现、containerd/CRI-O 为主流，体现技术判断的时效性。
4. **日志必须走 stdout/stderr 采集，禁止写容器可写层**，否则容器重建丢日志并占满磁盘——这是生产落地常见扣分点。
5. 容器安全基线要点：**非 root、只读根文件系统、禁特权、seccomp/AppArmor、capability 裁剪、镜像受信来源与漏洞扫描**，答出 4 项以上。
6. **多架构构建答出 multi-arch manifest（manifest list）** 而非"打两个 tag"；并指出原生依赖（加密库、OCR、签章控件、数据库驱动）需 arm64 版本，否则需重编译。
7. 国产化适配要有**内网私有仓库 + 离线依赖预热 + 鲲鹏真机回归**三个动作，仅说"支持国产化"不得分。
8. **工作负载选型理由要点**：认证/通知→Deployment 多副本无状态；流程引擎→状态外置 + Deployment（用分布式锁/乐观锁而非 StatefulSet 强耦合）；批处理→CronJob（并发策略 + 分片）；有状态中间件→StatefulSet + volumeClaimTemplates；采集→DaemonSet。答"全部用 Deployment"或"全部用 StatefulSet"直接扣分。
9. **回滚必须答出 rollout undo / 回退 spec**，并解释"直接改 Pod 会被控制器调谐回新镜像"——这是区分背书与理解的关键得分点。
10. 滚动更新参数 `maxSurge` / `maxUnavailable`、就绪探针门控、`minReadySeconds`、`PodDisruptionBudget`、`terminationGracePeriodSeconds` 答出 2 项以上。
11. 资源治理必须给出 **requests（调度与 HPA 基准）/ limits（运行上限）/ CPU 超限限流 vs 内存超限 OOMKilled** 的差异；只说"配好 requests/limits"不得分。
12. 答出 **QoS 三档与优先级（Guaranteed > Burstable > BestEffort）** 及"节点资源不足时按此顺序驱逐"；并点明 **LimitRange** 防止新 Pod 默认落入 BestEffort。
13. 弹性答出 **HPA（资源/自定义/外部三类指标）+ Cluster Autosigner（正确写法 Cluster Autoscaler）+ 定时预扩容 + 成本治理（Spot/竞价）** 两项以上。
14. **HPA 选型不当必须答出至少两个具体危害**：CPU 指标对 I/O 密集型失真、无 requests 时指标分母不稳导致振荡扩容、瓶颈在数据库时扩容无效反致连接池打满、缺少稳定窗口导致抖动放大。
15. 四类故障的**根因判别手段要写出观察点**：describe 看 Events/FailedScheduling、logs --previous、OOMKilled 原因字段、镜像仓库凭据与架构匹配；只写"重启 Pod"不得分。
16. **就绪探针雪崩的机制链必须写完整**：依赖超时 → readiness 失败 → 摘除 → 剩余负载更重 → 更多失败 → 全摘 → 雪崩；并给出"liveness 绝不含外部依赖、readiness 设容忍窗口"的原则。
17. 持续交付答出 **Quality Gate 分级（阻断/告警）+ 一次构建多环境晋级 + digest 引用 + SBOM + 签名与准入验证 + DORA 四指标** 中至少 4 项。
18. **GitOps 要点**：Git 为唯一事实源、控制器调谐与自愈、漂移检测告警、PR 评审即变更审批、密钥不入 Git、权限收敛到控制器。
19. 全题**不建议出现"提升性能、加强管理、加强运维"类空话**，每条措施须落到可执行动作（参数名、机制名、工具名）。
20. 结构化表达：**每问先给结论/清单，再给理由**，分点编号，与案例给定事实（12 台虚拟机、12% CPU、4 小时发布、45 分钟回滚、国产化环境、两地三中心）逐一挂钩。

## 记忆口诀

**一、容器三重隔离**
- 「名 c 组 叠」——namespaces 看不见、cgroups 用不了、overlayfs 改不了。
- 「视 资 层」：namespace 管视图，cgroup 管资源，unionfs 管分层。
- 「镜像只读容器活，tag 会变 digest 锁」。

**二、OCI 与 CRI**
- 「三规范一接口」：Runtime、Image、Distribution，接口就是 CRI。
- 「Docker 退场，containerd 登场」。

**三、控制平面**
- 「api etcd 调控云 kubelet」——apiserver、etcd、scheduler、controller-manager、cloud-controller、kubelet。
- 「只写期望，不管实现；spec 期望，status 实际；控制器只写 status」。
- 「观测、求差、计划、执行、再观测」——五步协调循环。
- 「声明式四板斧」：CRD+Operator、Admission Webhook、Scheduler Framework、Ingress/Gateway。

**四、工作负载选型**
- 「无状态 Deployment，有状态 StatefulSet，走节点 DaemonSet，做一次 Job，周期 CronJob」。
- 「StatefulSet 三宝」：稳定标识、有序启停、独占 PVC。
- 「PV 集群、PVC 命名空间、SC 模板，RWX 才共享，RWO 单写」。
- 「ConfigMap 配、Secret 密，Secret 只是 base64 不是加密」。
- 「四层 Service、七层 Ingress、DNS 发现、NP 隔离」。

**五、三探针**
- 「启动用 startup、活着用 liveness、能干活用 readiness」。
- 「liveness 绝不含外部依赖，readiness 可以但要有容忍窗口」。
- 「摘完更忙、更忙更摘、最后全摘——就是雪崩链」。

**六、资源治理**
- 「requests 定调度，limits 定上限」。
- 「CPU 超限是限流，内存超限是绞杀（OOMKilled）」。
- 「三档 QoS：保底 > 弹性 > 无保」——Guaranteed、Burstable、BestEffort。
- 「驱逐从低到高：先无保、再弹性、最后保底」。
- 「没 LimitRange，新 Pod 直接掉进无保档」。

**七、弹性伸缩**
- 「HPA 三指标：资源、自定义、外部」。
- 「没有 requests，CPU 指标就是分母不稳」。
- 「I/O 忙，CPU 闲，扩容不动，瓶颈在库」。
- 「先 HPA 扩 Pod，再 CA 扩节点」——顺序不能反。
- 「VPA 管单 Pod，HPA 管副本，CA 管节点」。

**八、发布与回滚**
- 「滚动看 surge 和 unavailable，就绪才切流」。
- 「回滚靠改 spec，不靠改 Pod，控制器会把你改回去」。
- 「rollout undo 靠 revision，revision 靠 digest 唯一」。
- 「PDB 护住最小可用，优雅终止配 preStop」。

**九、持续交付与供应链**
- 「流水线即代码，门禁分级阻断，SBOM 签名准入，digest 一次构建多环境晋级」。
- 「Git 是唯一事实源，调谐自愈加漂移告警，PR 即审批，密钥不入 Git」。
- 「DORA 四指标：频率、前置时间、失败率、恢复时间」。

**十、故障速记**
- 「Pending 看 Events 和调度失败，OOM 看 reason 字段，崩循环看上一次日志」。
- 「拉不下来查凭据查架构查网络，批量恢复要滚动重启」。
- 「JVM 堆只占容器内存七成，剩下给元空间和线程栈」。
