## 今日核心概念

### 1. 信息系统需求分析方法
定义：信息系统需求分析是通过结构化方法识别、获取、组织、分析、验证用户与业务需求的过程，是系统分析师的核心技能与考试重点。

关键要点：
- 需求层次三层：业务需求（Business Requirements，高层目标）、用户需求（User Requirements，用户视角）、系统需求（System Requirements，功能+非功能+约束）
- 功能需求 vs 非功能需求：功能需求（做什么，系统行为）、非功能需求（做得怎么样，质量属性：性能/可用性/安全/可维护性/可移植性）
- 需求获取五大技术：访谈（结构化+半结构化+非结构化）、问卷调查、原型演示、观察法、焦点小组；联合应用计划 JAD 会议加速需求获取
- 需求分析三大模型：数据模型（E-R图，实体+属性+关系）、功能模型（DFD数据流图，加工+数据流+数据存储+外部实体）、行为模型（状态转换图STD，时序+状态+事件）
- 需求描述三件套：用户故事（As a...I want...So that...）、用例图（Actor+Use Case+关系）、UML活动图
- 需求优先级排序：MoSCoW（Must/Should/Could/Won't）、Kano模型（基本/期望/兴奋型）、加权评分法
- 需求验证四指标：正确性（Correctness）、完整性（Completeness）、一致性（Consistency）、可追溯性（Traceability）
- 需求变更管理：变更请求CR → 影响分析 → CCB评审 → 决策（批准/拒绝/延期）→ 基线更新 → 通知相关方；需求基线化是范围控制的核心
- 需求追溯矩阵RTM：需求↔设计↔代码↔测试用例双向追溯，确保需求全覆盖

### 2. 面向对象分析与设计 UML
定义：面向对象分析（OOA）是基于对象/类/继承/封装/多态等机制识别业务实体与行为的方法；UML是面向对象建模的标准图形化语言。

关键要点：
- 面向对象四大机制：抽象（Abstraction，提取共性）、封装（Encapsulation，信息隐藏）、继承（Inheritance，子类复用父类）、多态（Polymorphism，接口多种实现）
- UML 2.5 14种图：静态图（用例图、类图、对象图、组件图、部署图、包图）+ 动态图（活动图、状态机图、序列图、通信图、时序图、组合结构图、交互概览图）
- 四大关系：关联（Association，A-B）+ 聚合（Aggregation，整体-部分可独立）+ 组合（Composition，整体-部分同生命周期）+ 泛化（Generalization，继承）+ 实现（Realization，类-接口）+ 依赖（Dependency，使用）
- 类图核心要素：类名+属性+方法；可见性（+public/-private/#protected/~package）；类间关系用不同线条表示
- 用例图三要素：参与者Actor（人/外部系统）、用例Use Case（功能单元）、关系（包含include、扩展extend、泛化generalize）
- 序列图四要素：对象（lifeline生命线）、消息（同步/异步/返回）、激活条activation、控制焦点focus of control
- 状态机图五要素：状态、转移、事件、动作、守卫条件；与活动图区别（状态机是对象状态变迁，活动是业务流程）
- 活动图：动作+控制流+决策+分叉/汇合+泳道（按角色分工）；用于业务流程建模
- 设计原则 SOLID：单一职责SRP、开闭OCP、里氏替换LSP、接口隔离ISP、依赖倒置DIP
- 设计模式三大类：创建型（单例/工厂/建造者/原型）、结构型（适配器/装饰器/代理/外观/桥接）、行为型（策略/观察者/责任链/状态/命令）

### 3. 数据库分析与数据建模
定义：数据库分析是从业务需求出发识别数据实体、属性、关系并构建数据模型的过程，是系统分析师分析与设计阶段的核心工作。

关键要点：
- 三层数据建模：概念模型（E-R图，与DBMS无关）、逻辑模型（关系模型，表结构）、物理模型（具体DBMS实现，含索引/分区）
- E-R图四要素：实体（矩形）、属性（椭圆）、关系（菱形）、连线；派生属性（虚线椭圆）、多值属性（双椭圆）、主键（下划线）
- 关系类型：一对一1:1、一对多1:N、多对多M:N（M:N需引入关联实体分解）
- 关系完整性：实体完整性（主键非空唯一）、参照完整性（外键引用有效）、用户自定义完整性（业务规则）
- 范式理论六阶：1NF（原子性）、2NF（消除部分依赖）、3NF（消除传递依赖）、BCNF（每个决定因素含候选键）、4NF（消除非平凡多值依赖）、5NF（消除连接依赖）
- 逻辑设计步骤：E-R图 → 关系模式转换（实体转表、属性转字段、M:N转关联表）→ 范式化优化 → 反范式权衡（性能优先）
- 物理设计要点：索引设计（B+树/哈希/位图/全文索引）、分区策略（水平/垂直/范围/哈希/列表）、存储引擎选择（InnoDB/MyISAM/RocksDB）
- 数据迁移策略：双写过渡+灰度切换+回滚预案；CDC（Change Data Capture，binlog监听）实现准实时同步
- 数据治理要点：主数据管理MDM、元数据管理、数据血缘、数据质量（完整性/准确性/一致性/及时性）

### 4. 系统架构设计模式与分布式架构
定义：系统架构设计模式是解决特定架构问题的可复用方案；分布式架构是面向大规模、高并发、高可用场景的系统组织方式。

关键要点：
- 分布式系统CAP三选二：一致性Consistency（所有节点同一时刻看到相同数据）、可用性Availability（每个请求都得到响应）、分区容错性Partition tolerance（网络分区仍能运行）
- CAP实战选择：P是必选项（分布式无法避免网络故障），故实际在C（CP系统：HBase/Redis Cluster/ZooKeeper）与A（AP系统：Cassandra/Eureka/CouchDB）间权衡
- BASE理论：基本可用BA（允许损失部分功能）、软状态S（中间态）、最终一致E（收敛一致）
- 共识算法三剑客：Paxos（最经典难懂）、Raft（易懂，Leader+Follower+Candidate）、ZAB（ZooKeeper专用）
- 分布式事务解决方案：两阶段提交2PC（强一致但阻塞）、三阶段提交3PC（改进2PC）、TCC（Try-Confirm-Cancel，业务侵入）、Saga（长事务拆分+补偿）、Seata AT模式（自动补偿）、本地消息表（最终一致）
- 分布式锁三大实现：Redis（SETNX+过期时间，Redisson看门狗）、ZooKeeper（临时顺序节点）、数据库（唯一索引）
- 分布式ID生成方案：UUID（无序）、Snowflake雪花算法（1位符号+41位时间戳+10位机器+12位序列）、Leaf号段模式（美团）、Redis INCR
- 负载均衡四层：DNS轮询（地理级别）、Nginx/LVS（四层TCP/UDP）、HAProxy（TCP+HTTP）、Spring Cloud Ribbon（七层客户端）
- 微服务架构模式：API网关、服务注册发现、配置中心、熔断限流、分布式链路追踪、分布式日志、统一监控告警
- 缓存三大问题：缓存穿透（布隆过滤器/空值缓存）、缓存击穿（分布式锁/逻辑过期）、缓存雪崩（TTL随机化/熔断降级/多级缓存）

### 5. 系统测试方法与质量保证
定义：系统测试是通过系统化方法验证信息系统功能、性能、安全、兼容性等是否满足需求的过程；质量保证是建立过程规范确保交付物符合标准的体系。

关键要点：
- 测试级别五层：单元测试（Unit，开发者+白盒）、集成测试（Integration，模块间接口）、系统测试（System，端到端功能）、验收测试（Acceptance，用户参与）、回归测试（Regression，修复后验证未破坏既有功能）
- 测试类型八类：功能测试、性能测试（负载/压力/容量/并发）、安全测试、兼容性测试、易用性测试、可靠性测试、本地化测试、探索性测试
- 测试方法三件套：黑盒测试（等价类划分/边界值分析/因果图/场景法）、白盒测试（语句覆盖/分支覆盖/路径覆盖/条件覆盖）、灰盒测试（结合内外）
- 测试覆盖率指标：语句覆盖（最低）、分支覆盖、条件覆盖、路径覆盖（最严）；MC/DC覆盖（航空DO-178B要求）
- 性能测试四件套：负载测试（Load，逐步加压找到最优负载点）、压力测试（Stress，超过设计极限验证系统崩溃点）、容量测试（Volume，大数据量）、并发测试（Concurrency，多用户同时操作）
- 性能指标三件套：响应时间（Response Time，含平均/P95/P99）、吞吐量（TPS/QPS/RPS）、资源利用率（CPU/内存/磁盘IO/网络）
- 测试用例设计八大法：等价类划分、边界值分析、因果图、判定表、正交实验、场景法、错误猜测、状态转换测试
- 测试管理流程：测试计划→测试用例设计→测试环境搭建→测试执行→缺陷管理→测试报告
- 缺陷生命周期：New → Assigned → Open → Fixed → Verified → Closed（或Reopen）
- 自动化测试金字塔：UI测试（少，慢，10%）+ API/接口测试（中，30%）+ 单元测试（多，快，60%）；测试金字塔指导自动化投入比例
- TDD测试驱动开发：红（写失败测试）→ 绿（写最小实现通过）→ 重构（优化代码）；BDD行为驱动开发（Given-When-Then）
- 持续测试DevOps：CI中自动化测试+CD中持续验证+生产环境灰度测试+监控告警

## 案例分析题

**题目**：
某省卫健委启动"互联网+医疗健康"项目，建设省级互联网医院平台，覆盖预约挂号、在线问诊、电子处方、药品配送、医保结算五大核心业务。系统要求日均承接50万次问诊请求，峰值QPS达5000，核心业务可用性99.99%（年宕机≤52分钟）。系统涉及省卫健委、25家三甲医院、120家连锁药店、医保系统、药品监管平台等多家外部系统对接。

项目立项时存在问题：
1. 业务需求变更频繁（每周新增需求5-8项），需求文档永远处于"草稿"状态；
2. 五大业务由5个不同厂商分别承建，无统一架构，技术栈差异大（Java/Node.js/Python/.NET混用）；
3. 各业务数据库分散（MySQL/Oracle/PostgreSQL/MongoDB混用），数据标准不统一；
4. 系统集成商各自对接外部系统，已对接的5家三甲医院接口风格各异，重复建设严重；
5. 系统安全等级保护要求三级，但未做安全架构设计。

请作为系统分析师回答：
(1) 请从需求工程、架构治理、数据治理三个维度分析本项目当前存在的主要问题；
(2) 请设计系统的总体技术架构（含前端/后端/数据/集成/安全五大层面），重点说明微服务拆分策略、数据一致性方案、高可用容灾设计；
(3) 请给出针对需求频繁变更的应对策略与变更控制流程。

**参考答案**：

问题一：三维度问题分析

一、需求工程维度：
1. 需求管理失控：无统一需求管理工具（应使用 Jira/DOORS/CodeBeamer），需求无优先级、无基线、无版本控制
2. 需求获取混乱：5个厂商各自调研，需求重复且冲突，未做统一利益相关方分析与用户画像
3. 需求变更失控：每周5-8项变更无评审流程，需求蔓延（Scope Creep）导致范围基准失效
4. 需求验证缺位：未建立需求追溯矩阵（RTM），无法验证需求实现覆盖率
5. 需求文档失序："草稿"状态说明缺乏变更控制与版本基线化机制

二、架构治理维度：
1. 无统一架构规划：5个厂商5种技术栈，无架构评审委员会（ARB），技术决策各自为政
2. 微服务边界不清：未基于业务能力做领域驱动设计（DDD），服务拆分随意，可能出现"分布式单体"反模式
3. 接口标准缺失：与三甲医院集成无统一API规范（应采用RESTful+OpenAPI 3.0/HL7 FHIR医疗信息标准）
4. 架构文档缺失：无架构决策记录（ADR）、无4+1视图、无技术雷达、无ADR变更流程
5. 安全架构缺位：等保三级未做安全架构设计（应含身份认证/访问控制/数据加密/审计日志/安全运营）

三、数据治理维度：
1. 数据标准不统一：四种数据库混用，无主数据管理（MDM）；医院、患者、药品等主数据无统一编码
2. 数据孤岛严重：5厂商各建数据库，无统一数据视图；患者在多个系统中ID不一致
3. 数据质量无保障：无数据质量度量（完整性/准确性/一致性/及时性）；脏数据导致业务异常
4. 数据共享缺失：无数据共享协议（应建立数据资产目录+数据交换平台+隐私计算）
5. 元数据管理缺失：无元数据管理平台，无法追溯数据血缘；合规审计困难

问题二：总体技术架构设计

一、前端层架构：
1. 统一门户：基于 Vue3 + 微前端（qiankun/wujie）统一用户入口，子应用独立部署
2. 多端适配：H5（移动端）+ 小程序（微信/支付宝）+ 原生App（iOS/Android）+ Web管理后台
3. 体验优化：CDN静态资源加速 + 图片懒加载 + 骨架屏 + SSR服务端渲染（Nuxt.js）
4. 统一UI规范：基于 Ant Design Mobile / Vant 设计语言，统一视觉与交互

二、后端层架构：
1. 微服务拆分策略（基于 DDD 领域驱动设计）：
   - 预约挂号服务（预约领域）
   - 在线问诊服务（问诊领域，含IM音视频）
   - 电子处方服务（处方领域）
   - 药品配送服务（药品领域）
   - 医保结算服务（医保领域）
   - 用户中心（认证/授权/患者主索引EMPI）
   - 医院对接服务（统一对接25家三甲医院）
   - 药店对接服务（统一对接120家连锁药店）
   - 支付中心（聚合支付）
   - 消息中心（统一通知）
2. 技术栈统一：Spring Boot 3.x + Spring Cloud Alibaba（Nacos+Sentinel+Seata）
3. 服务通信：内部 gRPC（高性能）+ 外部 RESTful（标准化）；同步调用与异步事件混合
4. 服务治理：Nacos注册中心 + Sentinel限流熔断 + Seata分布式事务 + SkyWalking链路追踪
5. API网关：Spring Cloud Gateway（路由+鉴权+限流+灰度+协议转换）

三、数据层架构：
1. 存储策略：
   - MySQL 8.0（业务主库，InnoDB集群MGR）
   - TiDB（OLAP分析、海量历史问诊）
   - Redis Cluster（缓存/会话/排行榜）
   - Elasticsearch（医嘱/病历全文检索）
   - MongoDB（问诊病历文档，灵活Schema）
   - ClickHouse（运营分析报表）
   - OSS/MinIO（影像文件、PDF处方）
2. 数据一致性方案：
   - 强一致（资金/医保结算）：Seata AT 模式 + TCC（医保结算）
   - 最终一致（处方/订单同步）：本地消息表 + RocketMQ 可靠消息
   - 大事务（在线问诊+处方+配送）：Saga 模式 + 补偿子事务
   - 跨院数据：CA签授+数据脱敏+数据使用审批
3. 分库分表：按患者ID哈希分256库×16表（4096表）；历史数据按月份归档到TiDB
4. 数据治理：
   - 主数据管理（EMPI患者主索引+医院+药品+医生主数据）
   - 数据资产目录（基于 Apache Atlas）
   - 数据血缘（基于 Apache DolphinScheduler）
   - 数据质量监控（完整性/准确性/一致性SLA ≥99.9%）
   - 数据脱敏（身份证/手机号/病历敏感字段）

四、集成层架构：
1. API网关：统一对外入口（路由+鉴权+限流+协议转换+监控）
2. 适配器模式：每个外部系统一个适配器（Adapter），屏蔽接口差异
   - 三甲医院适配器（HL7 FHIR/REST/SOAP适配）
   - 药店适配器（统一订单推送API）
   - 医保系统适配器（医保专网+签名验签）
   - 药品监管平台适配器（处方上传监管API）
3. 消息总线：Apache RocketMQ（异步解耦+削峰填谷+可靠投递）
4. 数据同步：Canal监听binlog + DataX全量同步 + Flink实时计算
5. 标准规范：RESTful + OpenAPI 3.0 + HL7 FHIR（医疗信息国际标准）+ 卫健委《全民健康信息平台数据集》

五、安全架构（等保三级）：
1. 身份认证：OAuth 2.0 + JWT + CAS单点登录 + 实名认证（公安一所）+ CA数字证书
2. 访问控制：RBAC（角色）+ ABAC（属性）双层；最小权限原则；动态鉴权
3. 数据加密：传输 TLS 1.3 + 存储 AES-256/SM4国密 + 密码 bcrypt/Argon2
4. 审计日志：全操作留痕（API调用/数据库操作/管理操作），保留 ≥180天，防篡改
5. 防护体系：WAF（Web应用防火墙）+ IDS/IPS（入侵检测）+ 防DDOS + 主机安全 + 容器安全
6. 安全运营：漏洞扫描（每月）+ 渗透测试（每季度）+ 代码审计（每次发布）+ 应急响应预案

六、高可用容灾设计：
1. 多活架构：同城双活（两个数据中心Active-Active）+ 异地灾备（异步复制）
2. RTO ≤ 30分钟，RPO ≤ 5分钟
3. K8s集群高可用：3主节点跨可用区部署，etcd 5节点Raft选举
4. 数据库高可用：MySQL MGR组复制（自动故障转移 ≤30秒）+ TiDB三副本
5. 多级缓存：Caffeine本地（纳秒）+ Redis分布式（毫秒）+ DB持久化；99.99%命中率
6. 熔断降级：Sentinel熔断器（错误率/慢调用/异常数三策略）+ 服务降级开关
7. 限流策略：Sentinel令牌桶/漏桶/滑动窗口；QPS限流 + 并发限流 + 关联限流

问题三：需求变更应对策略与控制流程

一、需求工程基础建设：
1. 需求管理工具：部署 Jira/DOings/Polarion 统一管理，建立需求池（Product Backlog）
2. 需求基线化：每个里程碑前完成需求基线 Freeze，基线后变更必经变更控制
3. 需求分层模型：业务需求BR → 用户需求UR → 功能需求FR → 非功能需求NFR，逐层细化
4. 需求追溯矩阵：建立 RTM（需求↔设计↔代码↔测试用例双向追溯）
5. 需求评审制度：需求评审会议（业务方+架构师+测试+开发四方签字）

二、需求变更控制流程（CCB五步法）：
1. 变更申请：任何人提交变更请求CR（含变更原因+影响范围+紧急程度）
2. 影响分析：项目经理+架构师+测试经理+业务代表四方评估
   - 进度影响：是否影响关键路径
   - 成本影响：是否超出预算10%阈值
   - 范围影响：是否触及范围基准
   - 质量影响：是否引入技术债务
   - 风险影响：是否带来新风险
3. CCB评审：变更控制委员会（CTO+产品总监+架构师+测试经理+业务代表）集体决策
   - 批准（含实施计划）
   - 拒绝（书面说明理由）
   - 延期（排入下个迭代）
   - 分级处理：紧急变更走快速通道（24小时内ECAB），标准变更周例会评审
4. 变更实施：依据CCB决策执行，更新需求基线+设计文档+测试用例
5. 验证与回归：测试团队验证变更正确性+影响范围回归测试，关闭CR

三、敏捷需求管理实践：
1. 用户故事地图（User Story Map）：按业务价值排序需求
2. MoSCoW 优先级：Must（必须有）/Should（应该有）/Could（可以有）/Won't（不会有）
3. Sprint迭代：2-4周一个迭代，每个迭代交付可用增量
4. Backlog Grooming：每迭代前梳理需求池，估算故事点
5. DoD完成定义：代码评审+单元测试≥70%+接口测试+UAT+部署预发

四、需求冻结与版本管理：
1. 需求冻结三阶段：
   - 软冻结（迭代前2周）：仅接受P0/P1紧急变更
   - 硬冻结（迭代前1周）：所有变更需PBG批准
   - 发布冻结（上线前）：仅接受线上Bug修复
2. 需求版本控制：基线化需求版本（v1.0/v2.0），变更记录可追溯
3. 需求变更度量：变更率（变更数/总需求数）、变更提前期（Lead Time）、变更拒绝率

五、需求相关方协同：
1. RACI矩阵：明确业务方A、产品经理R、技术R、测试C、其他I
2. 需求评审会议：周需求评审会、月度产品规划会
3. 沟通渠道：钉钉/企业微信即时沟通 + 周报/月报 + 季度业务评审
4. 期望管理：避免"范围镀金"（Scope Gold Plating），所有需求必须有业务价值论证

**踩分要点**：
- 问题一必须从需求工程（管理/获取/变更/验证/文档5点）+架构治理（规划/服务/接口/文档/安全5点）+数据治理（标准/孤岛/质量/共享/元数据5点）三维度诊断
- 问题二必须包含前端（微前端+多端）+后端（10+微服务+DDD拆分+Sentinel/Seata/SkyWalking）+数据（MySQL/TiDB/Redis/ES/MongoDB多模+一致性方案）+集成（适配器+HL7 FHIR+API网关+消息总线）+安全（等保三级+加密+审计）+高可用（多活+RTO/RPO+K8s+熔断限流）六层架构
- 问题三必须包含CCB五步变更流程（申请→分析→评审→实施→验证）+敏捷需求实践（MoSCoW/Sprint/Backlog/DoD）+需求冻结三阶段（软/硬/发布冻结）
- 关键数字：5000 QPS、99.99%可用性、52分钟宕机、25家三甲、120家药店、50万日问诊、256库×16表=4096表、180天审计日志、10%成本阈值、30分钟RTO/5分钟RPO
- 技术栈要点：Spring Cloud Alibaba全家桶（Nacos+Sentinel+Seata）+RocketMQ+TiDB+Redis Cluster+Elasticsearch+SkyWalking+HL7 FHIR
