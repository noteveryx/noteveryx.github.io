## 今日核心概念

### 1. 软件架构评估方法
定义：软件架构评估方法是基于质量属性场景、敏感点、权衡点和风险点，对候选架构进行系统性审查，验证其是否满足业务、质量、约束和演化要求的分析方法集合。
关键要点：
- 评估应围绕可用性、性能、安全性、可维护性、可扩展性、可移植性和互操作性七大质量属性展开。
- 常用方法包括 ATAM 架构权衡分析法、SAAM 场景分析、CBAM 成本效益分析和 ARID 主动评审中间设计。
- ATAM 通过场景生成、属性模型、点分析和风险分析四阶段识别关键风险与非风险决策。
- 敏感点是影响单一质量属性的决策，权衡点是影响多个质量属性且彼此冲突的决策。
- 评估结论必须输出风险、敏感点、权衡点和行动计划，并以业务可理解的语言输出。

### 2. 微服务架构治理
定义：微服务架构治理是为大量独立部署、版本迭代和团队自治的微服务制定统一的开发、部署、运行、接口、容错和演进规则，并以平台化方式持续保障其有序运行的体系。
关键要点：
- 治理维度包括服务契约、服务拆分粒度、版本兼容、注册发现、流量调度、容错策略和可观测性。
- 服务间通信优先采用同步 REST 或 gRPC，异步采用消息队列，必须显式声明接口契约、错误码和超时。
- 服务拆分应按业务边界进行，反对按技术层或数据库表拆分，避免分布式单体。
- 平台层应提供统一注册中心、配置中心、网关、监控、日志、告警、灰度和回滚能力。
- 治理必须包含技术雷达、API 规范、安全规范、SLO 指标和团队契约，避免治理失控。

### 3. 事件驱动架构与异步消息
定义：事件驱动架构是以事件为业务流转基本单位，通过发布订阅、消息队列、流处理和事件溯源实现服务解耦、流程编排和数据回溯的体系。
关键要点：
- 事件分为命令事件、领域事件、集成事件三种，命名应使用过去时并明确业务语义。
- 消息中间件至少要保证分区顺序、至少一次投递和幂等处理，必要时引入事务性消息。
- 事件溯源只追加事件流，状态由事件回放计算获得，便于审计和回溯，但需要良好的快照策略。
- 异步链路必须显式定义超时、重试、补偿、死信和最大重试次数，避免雪崩。
- 适合订单、计费、对账、风控和数据同步等需要解耦或回溯的场景。

### 4. 分布式事务与一致性
定义：分布式事务与一致性是跨多个服务、数据库或地区节点执行一组操作时，如何保障业务结果最终正确、可回滚、可补偿和可观测的体系。
关键要点：
- 强一致性方案包括两阶段提交、三阶段提交，但会损失可用性和性能。
- 弱一致性方案包括本地消息表、可靠消息、最大努力通知、Saga 长事务和 TCC 补偿事务。
- Saga 是把分布式事务拆为本地事务加补偿事务，通过协调器驱动并保证可观测。
- TCC 采用 Try-Confirm-Cancel 三阶段，适合核心金融与库存扣减，但实现复杂。
- 一致性必须配套幂等设计、对账机制、监控告警和最终一致性监控窗口。

### 5. 云原生架构与可观测性
定义：云原生架构是基于容器、服务网格、不可变基础设施和自动化运维构建的弹性应用形态，可观测性是对其运行过程进行指标、日志、链路追踪和事件全景感知的能力集合。
关键要点：
- 云原生以容器为最小交付单位，以 Kubernetes 为调度核心，强调声明式 API 和终态一致。
- 微服务网格将通信、熔断、限流、灰度、安全等能力下放到边车，与业务解耦。
- 可观测性三大支柱是 Metrics、Logs、Traces，必须有统一标识、统一时基和上下文传递。
- 监控不只是看指标，应覆盖 SLO/SLI、错误预算、用户体验和业务指标。
- 不可变基础设施要求构建一次、部署多次，禁止就地变更，提升一致性与回滚能力。

## 案例分析题

**题目**：某大型电商平台"星河电商"计划从单体架构演进为云原生分布式架构，以支撑大促期间十倍流量增长和未来三年的业务扩展。原系统为 J2EE 单体，订单、库存、营销、支付、财务五大模块集中部署，MySQL 主库压力极大，业务痛点如下：

1. 大促期间订单提交、库存扣减、营销优惠计算和支付确认链路长，单一环节故障即导致全链路失败。
2. 订单与库存跨库事务频繁，强耦合导致并发能力受限。
3. 营销规则频繁调整，每次上线需重启整个应用，发布窗口长，风险高。
4. 支付与财务对接复杂，存在重复支付、对账延迟和资金串户风险。
5. 监控只覆盖主机层，无法定位慢 SQL、慢接口、慢调用链和异常事件。
6. 测试团队无法模拟大促十倍流量，性能瓶颈难以提前发现。
7. 数据中心仅有一个，无法提供机房级灾备。
8. 管理层要求三年内完成改造，且要求大促期间业务零中断。

请回答：
1. 对该平台进行架构评估，明确质量属性场景、敏感点、权衡点和主要风险。
2. 设计云原生演进架构，说明服务拆分、消息驱动、网关、注册中心和可观测性平台的建设思路。
3. 给出分布式事务与一致性方案，覆盖订单、库存、营销和支付对账等关键路径。
4. 设计可观测性与混沌工程体系，说明 Metrics、Logs、Traces 和演练的落地方法。
5. 制定大促十倍流量下的弹性伸缩、多活容灾和应急回退方案。

**参考答案**：

1. 架构评估结果：
- 核心场景：大促下单链路、库存扣减、营销计算、支付确认、对账和报表查询。
- 质量属性：以可用性、性能、可扩展性、安全性、可观测性为重点，兼顾可维护性与合规性。
- 敏感点：数据库连接池、缓存命中率、营销规则计算路径、支付回调幂等。
- 权衡点：强一致与高可用、低耦合与运维复杂度、性能改造成本与业务连续性。
- 主要风险：单体硬拆、微服务粒度过细、分布式事务滥用、灰度缺失导致线上事故。
- 评估结论：采用基于 ATAM 的多轮评估，明确不可接受的属性退化并形成风险登记表。

2. 云原生演进架构：
- 第一阶段：搭建容器云平台、镜像仓库、CI/CD、配置中心、注册中心、API 网关和可观测性平台，作为整体底座。
- 第二阶段：按业务域拆分服务，订单、库存、营销、支付、财务、用户、商品独立成服务并独立部署。
- 第三阶段：将营销规则外置到规则引擎或低代码平台，实现规则热更新。
- 第四阶段：引入消息总线，把订单事件、营销事件、库存事件、支付事件通过 Kafka/RocketMQ 异步化。
- 第五阶段：构建微服务网格，统一熔断、限流、灰度、安全和路由。
- 数据层采用读写分离、分库分表、冷热数据分层，并建设跨机房双活。
- 整体架构具备声明式交付、不可变基础设施、自动化发布和监控告警能力。

3. 分布式事务与一致性方案：
- 订单与库存采用 Saga + 补偿事务，扣减与回滚由本地事务和补偿操作保证。
- 营销优惠采用最终一致性，在订单确认后异步清算，营销账和订单账日终对账。
- 支付采用 TCC 模式，Try 阶段冻结金额，Confirm 阶段实际入账，Cancel 阶段释放冻结。
- 财务对账采用事件溯源 + 日终批量对账，资金流向全链路可追溯。
- 所有外部接口必须幂等并带唯一业务号，关键操作全部上消息总线。
- 一致性方案配套全量对账、增量对账、异常告警、补偿执行和差异修补。

4. 可观测性与混沌工程：
- 三大支柱：Metrics 覆盖 QPS、RT、错误率、并发、可用度、SLO；Logs 统一格式与上下文；Traces 覆盖调用链与慢节点。
- 统一以 traceId、userId、orderId 为标识串联，方便跨服务跨系统定位。
- 监控告警分级：核心交易链路五秒告警，批量业务分钟级告警。
- 混沌工程按周开展演练，注入故障包括节点宕机、网络抖动、依赖超时、缓存击穿和数据库主从延迟。
- 演练结束输出改进清单，纳入下一迭代计划，避免演练走过场。
- 应急看板需覆盖核心交易链路、资源水位、依赖健康度、消息积压和告警分布。

5. 弹性与容灾方案：
- 弹性伸缩采用 HPA + 定时扩缩 + 流量预测，订单、库存、营销在大促前提前扩容并预热。
- 多活方案采用同城主备 + 异地灾备，数据库通过 binlog + 中间件实现双向同步，流量通过 DNS 和网关分级调度。
- 应急回退按分级执行：服务级回滚到上一版本；链路级通过降级开关跳过非核心功能；机房级通过切流量到备机房恢复。
- 大促前完成全链路压测、容量评估、限流阈值设定、降级清单和应急预案演练。
- 大促期间维持双人值守、灰度发布暂停和变更窗口冻结，重大事故按预案执行。

**踩分要点**：
- 第1问必须输出质量场景、敏感点、权衡点和风险表，不能只列属性名。
- 第2问要写清服务拆分、消息驱动、网关、可观测性和不可变基础设施五个关键点。
- 第3问必须覆盖 Saga、TCC、最终一致性、幂等和对账机制，不能只写两阶段提交。
- 第4问必须写出 Metrics、Logs、Traces 三支柱与混沌工程的具体落地，不能只写“做监控”。
- 第5问要写明容量评估、扩容、多活切换、降级、回退、变更窗口与值守机制。

## 记忆口诀
**架构评估口诀**：场景驱动找风险，敏感权衡要分清；ATAM 四阶段走，输出风险给业务。

**服务拆分口诀**：业务边界拆服务，不按技术不按表；分布式单体要避免，单一职责最关键。

**事件驱动口诀**：事件过去时命名，分区幂等保顺序；异步链路明超时，补偿死信必设计。

**分布式事务口诀**：Saga 拆本地加补偿，TCC 三阶段保一致；幂等对账告警必做，最终一致性也可行。

**可观测性口诀**：指标日志加链路，三柱必备统一 ID；混沌演练勤练兵，故障画像早预防。
