## 今日核心概念

### 1. 存储引擎内核结构：Buffer Pool、WAL 与 Checkpoint

定义：存储引擎（Storage Engine）是数据库管理系统中直接负责数据在磁盘与内存之间存取的核心模块，决定了数据的物理组织方式、并发控制的粒度以及持久化策略。上层的 SQL 解析、优化器、执行器都建立在它之上，存储引擎的性能特征往往决定了整个数据库的性能天花板。

关键要点：
- **三大核心结构**：Buffer Pool（缓冲池，缓存数据页与索引页）、WAL（预写日志 Write-Ahead Log）、Page/Block（磁盘上的最小读写单位）；此外还有事务元数据（Transaction Table、锁管理器）
- **读写路径完全不对称**：
  - 读路径：先查 Buffer Pool → 命中直接返回；未命中则从磁盘读入并 pin 住该页（pin 表示禁止被淘汰），使用结束后 unpin
  - 写路径：先写 WAL 并按配置刷盘（WAL 协议：提交事务前其 WAL 必须落盘，这是持久性的保证），数据页允许延迟刷盘
- **WAL 协议的威力**：只要 WAL 落盘，即使数据页未刷盘崩溃，重启后也能靠重放 WAL 恢复出已提交数据。这把"每次写都要落盘"降级为"顺序写日志 + 延迟批量刷脏页"，把随机 IO 变成了顺序 IO
- **Buffer Pool 淘汰策略**：简单 LRU 存在**扫描污染**问题——一次全表扫描会把大量冷页全部装入缓冲池，把热点页挤出去。解法是 **LRU-K**（统计每个页被访问的历史次数，K 次以上的才进入主 LRU）或扫描敏感策略（中间位置插入）
- **Checkpoint 的两个作用**：① 把脏页批量刷盘；② 截断已不再需要的 WAL（否则 WAL 无限增长，恢复时间不可控）。**锐利 Checkpoint（Sharp Checkpoint）** 会把所有脏页集中刷盘造成 IO 毛刺，**模糊 Checkpoint（Fuzzy Checkpoint）** 把刷盘分散到平时，平滑但需要更多磁盘空间
- **后台线程矩阵**：page cleaner（后台刷脏页）、checkpointer（触发 Checkpoint）、log writer（写 WAL 缓冲）、log flusher（刷 WAL 盘）、purge（清理 MVCC 旧版本）、stats 线程（收集统计信息）。**DBA 调优的本质，多是调整这些线程的并发度与节奏**
- **IO 放大的主要来源**：脏页集中刷盘（尖刺）、随机写、Compaction 与前台读写争抢同一块盘。**存储引擎调优的第一原则是把前台读写的 IO 与后台整理的 IO 隔离到不同设备或不同队列**

### 2. LSM-Tree 与 B+Tree：读放大、写放大与空间放大的三角权衡

定义：两种主流存储引擎的数据组织方式。B+Tree 采用**原地更新**（In-place Update），页面写满就地分裂；LSM-Tree 采用**追加写 + 后台合并**（Log-Structured Merge Tree），数据先写入内存表，再顺序刷写为不可变的 SSTable 文件，后台再逐层归并。

关键要点：
- **B+Tree 的取舍**：读放大低（一次树形查找直达叶子页）、写放大高（随机 IO、页分裂与合并、页内部分空间浪费）。适合**读多写少、事务型、强一致**场景，是传统 OLTP 的默认选择
- **LSM-Tree 的取舍**：写吞吐极高（顺序追加写 + WAL）、读放大（查询要依次检查多层 SSTable）、空间放大（多版本共存、压实前数据冗余）。适合**写密集、日志流、时序、监控埋点**场景
- **三大放大问题**（LSM 的本质矛盾）：
  - **写放大**：Compaction 把数据从下层搬到上层又从上层合并到新层，同一份数据被反复重写。经验倍数：Leveled 约 10~50 倍，Tiered 接近 1
  - **读放大**：一次逻辑读要查多个 SSTable，每层都可能命中
  - **空间放大**：多版本 + 未压实的多份副本共存，磁盘占用远超逻辑数据量
- **LSM 的关键组件**：WAL（崩溃恢复）、MemTable（内存写缓冲，决定写入延迟）、SSTable（不可变磁盘文件，含 Block、Block Index、Filter 三部分）、Compaction 线程池
- **两种 Compaction 策略的取舍**：
  - **Leveled（分层）**：每层多个 SSTable 之间**有序且不重叠**，每层总大小约为上一层的 10 倍。每层有序范围可被上层 Block 覆盖 → 读放大小，但相同 key 的多个版本可能分散在多层 → 写放大大
  - **Tiered（分层堆叠）**：同层 SSTable 之间**有序但不合并**，每层内部文件有序、层间范围重叠。新数据直接进入新层 → 写放大接近 1，但一次读可能要打开同层的多个文件 → 读放大大
- **工程折中**：多数生产系统用**混合策略**——热数据用 Leveled（保证读性能），冷数据用 Tiered（降低空间与写放大），或对超大表单独指定 Tiered
- **典型实现**：RocksDB、LevelDB（基础实现）、TiKV、Cassandra、ClickHouse 的 MergeTree（变体）、OceanBase、TiDB 的 TiKV 层。**国产化数据库如 OceanBase、TiDB、GaussDB 在信创场景中大量采用类 LSM 或混合引擎**

### 3. Bloom Filter 与索引加速机制

定义：Bloom Filter 是一种概率型位图数据结构，用多个哈希函数把元素映射到位数组的若干位置上。它不能告诉你"这个元素一定在集合里"，但可以极快地告诉你"这个元素一定不在集合里"。

关键要点：
- **两个关键性质**：**无假阴性**（说"不在"则一定不在）、**有假阳性**（说"可能在"，实际可能不在）。**误判率 ≈ (1 - e^(-kn/m))^k**，其中 m 为位数组长度、n 为元素个数、k 为哈希函数个数；最优 k = (m/n)·ln2
- **在 LSM 中的核心作用**：查询时先查每个 SSTable 的 Bloom Filter，若确定"不在"就直接跳过该文件，**避免昂贵的磁盘 IO**。这是 LSM 抗读放大的第一道防线，也是 LSM 能与 B+Tree 匹敌的关键
- **代价**：① 每个 SSTable 需维护一份 Bloom Filter，占内存；② 假阳性会导致"以为在、实际不在"，仍需读盘验证，造成额外 IO
- **限制**：标准 Bloom Filter **不支持删除**（置位后无法复位）。需要删除能力要用 Counting Bloom Filter、Cuckoo Filter 或引用计数方案
- **其他索引加速技术**：
  - **Zone Map / Min-Max 索引**：列存引擎中为每个数据块记录列的最小值与最大值，查询时直接跳过不可能命中的块。ClickHouse、Apache Doris 广泛使用
  - **位图索引**：适合低基数列的等值/范围过滤
  - **前缀索引 / 倒排索引**：全文检索场景
  - **稀疏索引**：数据块稀疏存储，块内再逐行二分
- **维度选择的权衡**：列存适合**扫描型分析**（少读大量列数据），行存适合**点查与事务**。混合理想是"行存存索引 + 列存存数据"（如 ClickHouse 的 ReplacingMergeTree 部分场景、腾讯云 TDSQL-C 的行列存转换）

### 4. 存储引擎调优与性能诊断方法论

定义：以可观测指标为依据，定位存储引擎内部瓶颈并通过参数调优与结构优化提升系统性能的一整套方法论。

关键要点：
- **必须建立的核心观测指标**（缺一项就会出现盲区）：
  - Buffer Pool 命中率、脏页比例、后台刷脏速率
  - WAL 写入速率、**Checkpoint LSN 距离**（距上次 Checkpoint 已累积的 WAL 字节数，直接决定崩溃恢复时间与刷脏压力）
  - **Compaction 积压量**：L0 文件数、SSTable 总数、待压实字节数、Compaction 任务排队时长
  - 磁盘 IO 利用率与 **await（平均等待时间）**、IO 队列深度
  - 读放大倍数：实际 SSTable 打开次数 / 逻辑查询数
- **症状—根因速查对照**：
  - 写入毛刺、周期性延迟尖刺、CPU 不高但延迟高 → **Checkpoint 尖峰或 Compaction 与前台争抢 IO**
  - 读延迟上升而 CPU 与 IO 均不高 → **读放大**（层数过多、Bloom Filter 内存不足或误判率偏高）
  - 磁盘写满 → 写放大 + 空间放大 + TTL 未真正回收数据
  - 长时间事务伴随 purge 变慢、版本链过长 → 长事务阻塞 MVCC 清理
- **调优手段清单**（按优先级）：
  1. **IO 隔离**：WAL 单独一块盘（顺序写对时延极敏感），Compaction 限流（`background_io_rate_limit`）避免抢占前台带宽
  2. **扩大 Buffer Pool**，使活跃数据集常驻内存；配合 LRU-K 抗扫描污染
  3. **调整 Compaction 触发阈值**：L0 文件数阈值降低 → 写放大上升、读放大下降；反之亦然
  4. **冷热分层**：热数据 Leveled、冷数据 Tiered 或下沉对象存储（冷备 + 分层存储降低成本）
  5. **启用分区级优化**（如 ClickHouse 按日期分区且查询带分区裁剪）
  6. **批量写入优化**：批量提交、避免超大事务、避免索引过度膨胀
- **纪律性原则**：先定 SLO（明确的 P99 延迟与吞吐目标），再测量定位，再**单变量**调参，再复测，最后灰度上线。**任何没有基线数据的"优化"都是玄学**
- **典型流程**：基准压测（sysbench / 自研业务流量回放）→ 火焰图与内核指标采集 → 瓶颈定位 → 调参或结构改造 → 回归压测 → 影子流量验证 → 分批上线

### 5. 分片键选择与数据倾斜治理

定义：在分库分表或分布式数据库中，选择合适的分片键（Partition/Shard Key），使数据量与访问流量在各分片间均匀分布、并让高频查询能够被高效路由的策略。

关键要点：
- **分片键选择三原则**：
  1. **覆盖高频查询条件**——能携带分片键的查询可直达单片，避免跨片扫描或广播查询
  2. **数据量均衡**——避免某一片成为"超级分片"
  3. **避免写热点**——避免单调递增的键（自增 ID、时间戳）导致写入全部落在同一分片的新尾页
- **典型事故模式**：
  - 用**自增 ID 或时间戳**做分片键 → 数据与写入持续向最新一片倾斜，形成写热点；且历史查询跨片
  - **行政区划分片**看似均衡，实则各区县办件量差异巨大（且"全市一网通办"会把查询变成跨市扇出）
  - 应用双写迁移期，新旧片数据倾斜，旧片承担读、新片承担写，两者负载严重不均
- **热点治理手段**：
  - **分片键打散**：把一个业务键映射到多个虚拟分片（Virtual Shard），再对虚拟分片做哈希路由，使物理分片负载均衡
  - **随机化 / 哈希后缀**：在键后追加哈希后缀打散顺序写，但会牺牲范围查询
  - **映射表（集中路由）**：单独一张映射表记录 key → 分片，支持迁移与再平衡
  - **读写分离 + 多副本**：读流量由多副本分担，缓解热点分片的读压力
- **跨片查询四类策略**：
  1. **绑定查询**：分片键在查询条件中，直接路由单片
  2. **广播表**：小而稳定的字典表冗余到每个分片，任意分片本地可查
  3. **异写索引**：建立"索引表 → 目标分片"的二级索引，先查索引再取数（分布式数据库 2.0 能力）
  4. **全局聚合表**：跨片查询结果上卷为汇总表，牺牲实时性换性能（本质是 CQRS 读写分离思想）
- **与 CAP 的边界**：**分片是水平扩展手段，本身不解决一致性问题**。跨片事务仍需 2PC / TCC / 可靠消息最终一致；分片粒度变细会放大跨片协调成本，不是越细越好
- **渐进式改造路径**：分片键错误时不可"一键改键"，需双写 → 数据回填 → 校验 → 切读 → 停旧写 → 清理，且必须支持双读比对与流量灰度

## 案例分析题

**题目**：某市"一网通办"平台数据库迁移与性能退化综合分析

**背景材料**

某市统一政务服务平台包含统一身份认证、电子证照、42 个政务事项、办件库与好差评等模块，年办件量约 380 万件，日均在线用户 4 万余人，接入 58 个部门单位。原数据库为 MySQL 8.0（InnoDB 引擎）单主 2 从架构，读写分离，主库 8 核 32G、企业级 SSD；2026 年 3 月为满足信创与扩容要求，迁移至采用类 LSM 引擎的国产分布式数据库，采用 3 分片 × 2 副本架构，每分片 16 核 64G。

迁移后前三个月运行平稳，自 2026 年 6 月下旬起出现以下问题：

**现象一**：每天 14:00—16:00 办件提交接口 P99 响应时间由 120ms 上升至 2.4s，错误率由 0.3% 升至 4.7%；同期节点 CPU 使用率仅 30%~35%，磁盘 IO 利用率却达 95%，磁盘 await 最高冲到 780ms。

**现象二**：运维排查发现，每日 14 点起 L0 层 SSTable 文件数快速攀升至 500 个以上，Compaction 任务大量积压，待压实数据量峰值达 2TB，Compaction 队列排队时长超过 40 分钟。

**现象三**：6 月底统一身份认证模块接入市级 APP，查询 QPS 由 8000 升至 15000（近 2 倍），但数据库 CPU 几乎没有上升，仅 30% 升至 38%，而认证查询 P99 由 15ms 升至 78ms，缓存命中率由 96% 跌至 62%。

**现象四**：7 月 8 日完成 200 万条历史办件数据批量补录后，管理层报表"按区县统计办件量"查询超时，且抽查发现报表数据仅包含主分片数据，另有约 1/3 数据缺失。

**现象五**：7 月 20 日多名窗口人员反映"个别办件详情查询不到"，运维排查发现该平台分片键为"办件编号"，但窗口人员日常查询多以身份证号为主键条件，且部分查询未带租户或区划过滤条件。

**参考答案**：

### 问题 1 — 分析现象一、现象二的根因，并给出存储引擎层调优方案

**根因分析：**

现象一与现象二本质是**同一个因果链**：批量写入 → L0 快速膨胀 → Compaction 积压 → 后台合并抢占磁盘 IO → 前台读写被排队阻塞 → 响应时间尖刺。

具体机理：

1. **写放大导致磁盘 IO 饱和**：LSM 引擎的每次写入，先写 WAL、再写 MemTable、刷为 L0 的 SSTable，随后被反复 Compaction 归并到上层。若底层存储是 B+Tree 式原地更新，理论上"一次用户提交 → 一次数据页写"；而在 LSM 下，一个 380 万件/年、含多索引的表，单条写入在生命周期内可能被搬移 10~50 次（Leveled 典型写放大倍数），导致磁盘写 IO 放大一个数量级。14:00—16:00 是业务高峰（窗口补录、批量报送集中），写入集中触发大量 L0 产生，Compaction 无法及时完成。

2. **Compaction 与前台读写争抢同一 IO 通道**：Compaction 是持续的大流量读写任务，且读写混合；当前架构未做 IO 隔离，Compaction 一旦启动便占满 IO 带宽，导致前台请求在 IO 队列中排队——这正是"CPU 只有 30% 但 await 高达 780ms"的直接原因（典型的 **CPU 空闲但 IO 饱和** 现象，说明瓶颈在 IO 而不在 CPU）。

3. **Checkpoint 与刷脏的叠加**：迁移初期参数未按 3 倍于原单机的数据量重新调优，Buffer Pool 偏小、WAL 与数据同盘、Checkpoint 阈值过小，导致脏页集中刷盘，与 Compaction 叠加形成"雪崩式"IO 尖刺。

4. **历史数据补录加剧问题**（问题 4 的诱因）：200 万条批量导入使得 L0 与上层各级的 key 区间重叠度极高，Compaction 需要处理大量同 key 多版本数据，工作量与占用带宽急剧上升。

**存储引擎层调优方案（按优先级，应至少答出 4 项并说明取舍）：**

1. **IO 隔离与限流（优先级最高，直接止血）**
   - 将 WAL 单独部署到独立的高吞吐设备（WAL 是顺序小写，单独放置可保证 fsync 时延稳定，避免与 Compaction 争抢）；
   - 对 Compaction 设置后台 IO 限速（如 `background_io_rate_limit`），并与前台读写分离队列，保证 Compaction 只能"吃"空闲带宽，不得饿死前台；
   - 为 Compaction 单独规划容量配额，避免待压实数据堆积至 TB 级。

2. **Buffer Pool 扩容与结构优化**
   - 按活跃数据集重新规划 Buffer Pool（LSM 是"读少写多"场景，索引页与热数据块常驻内存可显著降低读放大）；
   - 采用 LRU-K 策略防止批量导入与报表扫描造成扫描污染；
   - 调整脏页比例上限（`max_background_write_ratio`）与后台刷脏线程数，把刷脏从"尖峰"摊平为"涓流"。

3. **Compaction 策略分级调整**
   - 对大表与写热点表改用 **Tiered Compaction**（或混合策略：热数据 Leveled、冷数据 Tiered），把写放大从 10~50 倍压到接近 1，代价是读放大上升，因此必须配合第 4 项；
   - 调整 L0 触发阈值（降低阈值会提前压实、降低读放大但提高写放大；提高阈值反之），需依据"读多写少则降低阈值"的业务特征取舍；
   - 排查是否存在**范围删除未生效**（TTL 未真正回收、Compaction 未推进到最底层）导致的磁盘水位虚高。

4. **索引加速降低读放大**
   - 提高 Bloom Filter 的每键位数（bits_per_key）与布隆过滤器缓存内存占比，降低假阳性率，减少无效磁盘读取；
   - 启用 Zone Map / Min-Max 索引（若产品支持），使报表类范围查询可跳过无关数据块；
   - 评估是否关闭或延迟部分低价值二级索引：政务场景中大量查询走"身份证号 + 办件编号"，部分历史索引可能长期不被命中，**删除低效索引同时降低写放大与空间放大**——这是 LSM 场景最容易被忽视的优化点。

5. **业务侧协同（架构层）**
   - 历史补录改为**离线批量导入通道**（直接写入底层 SSTable 文件或走专门的批量导入接口），绕开实时写入链路，避免与在线业务争抢 L0；
   - 读写分离读副本承担报表与统计类查询，避免大范围扫描进入主分片；
   - 对高频写接口做批量合并（同一办件的多字段更新合并为一次提交）。

**必须点出的结论**：调优不是"调参数"那么简单，**参数调优能削峰、限流、提速，但无法消除 LSM 的结构性写放大**。若业务持续高频写入，应同步评估"按业务维度分区 + 分区级独立 Compaction"或"冷热数据分层下沉对象存储"，把架构手段与参数手段结合。

### 问题 2 — 分析现象三"CPU 未上升但读延迟上升、缓存命中率骤降"的根因并给出治理手段

**根因分析：**

现象三的四个数字必须串起来读：**QPS 翻倍 → CPU 几乎不变 → 读延迟上升 5 倍 → 缓存命中率从 96% 跌到 62%**。这不是"机器不够"，而是**读放大被放大后的典型表征**。

1. **读放大机制**：LSM 引擎的一次逻辑读，要依次检查多层 SSTable。当查询命中的 key 分布在多层（同一 key 的多个版本分散在 L0、L1、L2…）时，一次逻辑读要打开多个文件、多次预读与页查找。前台 QPS 从 8000 涨到 15000 后，**逻辑读被读放大系数放大**，实际磁盘读次数成倍增长，磁盘 IO 迅速饱和，IO 队列排队导致 P99 从 15ms 涨到 78ms。

2. **缓存命中率为何暴跌**：LSM 的数据分布在多份 SSTable 中且不可变，缓存以"文件 + 偏移"为粒度，**同一份业务数据在多层各有一份副本**。Compaction 期间，新文件不断生成、旧文件不断失效，缓存中的旧块持续失效；同时写入压力增大导致新版本数据不断落到新文件，缓存的工作集被"版本 churn"冲刷。命中率从 96% 掉到 62%，本质是**缓存空间被写放大带来的多版本数据挤占**，而不是缓存本身出了问题。

3. **CPU 未上升的解释**：LSM 的读路径是 IO 密集型而非 CPU 密集型，大量时间消耗在磁盘等待与文件打开上，处于 IO 等待态的线程不计入 CPU 使用率。所以"CPU 30%"恰恰说明**瓶颈在 IO 带宽与并发度，而不是算力**——这也再次印证问题 1 的调优方向。

4. **还需警惕的次生因素**：统一身份认证是高读低写场景，**完全可用缓存扛住**。缓存命中率跌到 62% 说明缓存层本身可能存在容量不足、Key 设计与淘汰策略不合理、或缓存与数据库的**双写一致性**在压力下失效（缓存击穿到数据库形成雪崩）。这一点必须写入分析，否则治理方案会不完整。

**治理手段：**

1. **存储引擎层**：提高 Bloom Filter 精度（bits_per_key）与内存配额、降低假阳性率；调整 Compaction 策略降低层数（Leveled 化在读多场景更优）；对认证表按"身份证号"等查询键做**哈希分片/分区**，使同一查询落在单片，避免跨片扇出。

2. **缓存层**：扩容缓存至活跃数据集的 1.2~1.5 倍；把身份认证这种读多写少的模块**独立出小集群或独立读副本**，隔离其他业务的写与 Compaction 干扰；对热点 Key 采用本地缓存（Caffeine/进程内 Caffeine + Redis 两级）降低回源压力。

3. **读写分离与流量治理**：认证查询全部走只读副本；报表与统计查询走独立分析集群或列存引擎（把 OLTP 与 OLAP 混在同一套 LSM 上是典型误配）。

4. **请求侧**：对认证接口做**接口合并与结果缓存**（同一身份证号短时间多次查询直接命中缓存），并加上**单飞（single-flight）防击穿**，避免热点 Key 失效瞬间并发打穿。

5. **监控补齐**：新增"**逻辑读放大系数**""Bloom Filter 假阳性率""Compaction 积压量""缓存命中率分模块统计"四项指标告警——当前监控只有 CPU、内存、磁盘使用率这类基础指标，是本次问题"运维发现得晚"的根本原因。

### 问题 3 — 分析现象四（报表数据缺失）的原因并给出正确做法

**原因分析：**

1. **直接原因**：报表统计逻辑直接对**主分片**或某个分片执行 `SELECT count(*), county FROM ... GROUP BY county`。分片键是"办件编号"，区县是普通字段，因此按区县的统计必然跨片；只查单片，自然只得到该分片数据，**约 1/3 数据缺失**（3 分片取 1 片）。

2. **更隐蔽的原因**：报表查询未做**分布式下推**，全量数据被拉回到应用层或单一计算节点再做 GROUP BY，数据量大时直接超时。这与"数据缺失"叠加，形成"既慢又不全"的双重故障。

3. **架构层根因**：**分片键选错**。分片键"办件编号"与最高频的分析维度"区县"完全正交，意味着**所有按区县、按身份证号、按时间的查询天然跨片**。这是分片设计最典型的失误：分片键不是随便选的字段，选错之后，所有非分片键维度的高频查询都要付出跨片代价。

**正确做法：**

1. **建立二级索引（异写索引）**：为"区县 + 时间"、"身份证号"建立索引表（索引项 → 目标分片与主键），查询先走索引表定位分片与记录，再并行路由到目标分片取数。这正是分布式数据库 2.0 的核心能力，也是分片键选错后的标准补救手段。
2. **广播表**：把"区县代码表""部门表""事项目录表"等小而稳定的字典表冗余到每个分片，使本地可完成维度翻译与关联，无需跨片。
3. **读写分离与汇总表**：统计类报表应走**只读副本 + 预聚合汇总表**。按"区县 + 月份"建立汇总表，通过增量事件或定时任务维护，报表查询退化为单表单表查询，毫秒级返回。**这是政务报表类需求的正解——牺牲实时性，换取查询性能与正确性**。
4. ** OLAP 引擎分流**：将分析类查询迁移到列存分析引擎（数据通过 Binlog/CDC 同步），OLTP 只承担事务写入。
5. **分片键改造的评估**：正确的分片键应是与高频查询条件一致的业务键（如"区县 + 办件编号"复合分片键）。但**分片键改造不能一改了之**，需双写 → 回填 → 双读比对 → 切读 → 停旧写 → 清理的完整链路，且必须伴随数据一致性校验与流量灰度，应作为独立的数据迁移项目立项，并给出停机窗口、回滚方案与校验脚本要求。

### 问题 4 — 分析现象五并提出治理方案

**原因分析：**

1. **分片键未覆盖高频查询条件**：分片键为"办件编号"，而窗口人员的日常查询以**身份证号**为主条件，因此这类查询必须**广播到全部分片**（3 分片）后再聚合。随着办件量增长到 380 万件，单次广播查询代价极高，极易超时；同时分片键的分布性不均也会带来数据倾斜。

2. **"查询不到"的四种可能根因**（须区分，不能一概而论）：
   - **路由错误**：查询条件未携带分片键，驱动层未做广播而误判为单片路由，导致只查了一片；
   - **数据未回填或未同步**：历史补录数据写到了未纳入索引的分区，形成"数据在库、查不到"的错觉；
   - **租户/区划过滤条件缺失**：题目提到"部分查询未带租户或区划过滤条件"，在多租户分片下，缺少租户上下文会导致路由到错误分片或跨租户数据越权可见（后者是**安全缺陷**，不只是性能问题）；
   - **最终一致性延迟**：写入已落到某分片，但查询走了另一副本且复制存在延迟。
3. **未带过滤条件的查询是双重风险**：既是性能风险（无法路由、无边界扫描），也是**数据权限风险**。政务平台中，按"办件编号"直接定位单条记录看似安全，但在无租户校验时，一旦编号可预测或接口未做归属校验，就可能造成越权访问他部门/他人的办件信息，这在等保测评与安全审计中属于必须整改项。

**治理方案：**

1. **查询路由治理**：在数据访问层统一收口，强制查询条件包含分片键或可路由键；无法路由的查询走**异步广播查询接口**并做结果合并，同时设置超时与结果数量上限，避免拖垮集群。
2. **建立反向索引**：为身份证号建立二级索引（身份证号 → 分片 + 办件编号），使高频查询同样能做到一次路由。
3. **租户与权限强校验**：所有查询强制携带租户/区划上下文，服务端依据登录身份注入过滤条件（**信任边界放在服务端，不依赖前端传参**），并在网关或数据访问层做越权拦截；补齐"未带条件查询"的默认拒绝策略与审计日志。
4. **数据完整性校验**：对补录数据做全量对账（分片级行数、主键集合、校验和），把"数据在库但查不到"与"数据根本不在库"区分开；建立分片路由的正确性用例（路由命中分片 = 期望分片）。
5. **查询性能兜底**：对超大结果集强制分页与上限；对全表统计类需求统一走汇总表与列存分析链路。

### 问题 5 — 综合：给出一份存储引擎与数据库层的整体改进路线

**参考答案：**

**第一阶段（1 个月内，止血）**
1. WAL 独立盘 + Compaction 限流 + Buffer Pool 扩容 + Checkpoint 参数重调；
2. 建立七项核心监控：Checkpoint LSN 距离、L0 文件数、Compaction 积压量、逻辑读放大系数、Bloom 假阳性率、缓存命中率（分模块）、磁盘 await；
3. 报表与统计查询切至只读副本，禁止在主分片做大范围扫描；
4. 历史补录改走离线批量通道。

**第二阶段（1~3 个月，治本）**
1. 大表与冷数据切换 Tiered 或混合 Compaction 策略，评估清理低价值索引；
2. 建立二级索引（区县+时间、身份证号），广播表改造；
3. 报表体系重建：读副本 + 预聚合汇总表 + 列存分析引擎分流；
4. 查询路由与租户权限强校验落地，补齐越权风险整改。

**第三阶段（3~6 个月，架构演进）**
1. 分片键改造立项评估（复合分片键 区县+办件编号），按双写→回填→双读比对→切读→清理推进；
2. 冷热数据分层，冷数据下沉对象存储并接统一查询接口；
3. 建立数据库可观测体系与容量模型（数据量增长率、Compaction 带宽预算、IO 容量预测），把容量规划从"出故障再扩容"变为"按增长率提前扩容"。

**贯穿全程的三条纪律**
- 每次调优必须有 SLO 与基线数据，改动必须单变量、必须压测与灰度；
- 涉及数据一致性的改造（分片键改造、双写迁移）必须有校验脚本与回滚方案；
- 涉及权限的改造（租户过滤）必须先于性能优化完成，安全项不可让位于性能项。

---

**踩分要点**：

1. **现象一必须点明"CPU 低 + IO 饱和 + await 高"= IO 瓶颈而非算力瓶颈**，这是全题的判断起点；只答"加机器""升配"不得分。
2. **必须写清 LSM 的写放大链条**：一次业务写入 → WAL + MemTable + L0 + 多次 Compaction 搬移，用倍数（Leveled 10~50 倍 / Tiered≈1）体现深度。
3. **调优方案必须区分"参数止血"与"结构治本"**，并至少覆盖：WAL 隔离、Compaction 限流、Buffer Pool 与 LRU-K、Compaction 策略切换（Leveled/Tiered 取舍）、Bloom Filter 与 Zone Map、批量导入旁路。**只列"调参数"而无取舍分析，最多一半分**。
4. **现象三的因果链不可跳过**：QPS 翻倍 → 读放大 → 磁盘读次数成倍 → 队列排队 → P99 上升；同时必须解释**缓存命中率跌到 62% 的机制**（多版本 churn 冲刷缓存 + 缓存空间被挤占），并识别出"认证接口本应靠缓存扛住"这一被忽略的结构问题。**只答"扩容缓存"是最低档答案**。
5. **现象四必须识别出"分片键与查询维度正交"这一根因**，并给出二级索引/广播表/汇总表/列存分流四条出路；同时指出**报表查询未做分布式下推**导致全量拉回。
6. **现象五必须把"查询不到"拆成多种根因**（路由错误、数据未同步、过滤条件缺失、复制延迟），并**明确点出"未带租户条件"属于越权访问风险而非仅性能问题**——这是拉开分数档次的点。
7. **分片键改造要给出渐进路径**（双写→回填→双读比对→切读→清理）并要求回滚与校验脚本，不得直接答"改用身份证号分片"。
8. **最后问必须给出分阶段路线图**，区分 1 个月内止血、1~3 个月治本、3~6 个月架构演进，并落到监控指标清单与容量模型。
9. **通用扣分点**：出现"加机器、升配、优化代码"这类空泛表述而无具体参数名与机制；把 LSM 与 B+Tree 的读写特性张冠李戴；只谈不谈取舍（Leveled/Tiered、隔离级别、Compaction 阈值调整都会带来代价）。
10. **加分表现**：能点出"Compaction 与前台争 IO 是分布式数据库最典型的隐性瓶颈""OLTP 与 OLAP 混部是架构误配""长事务会阻塞 purge 造成版本链膨胀"等资深判断。
