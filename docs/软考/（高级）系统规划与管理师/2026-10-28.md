# （高级）系统规划与管理师 · 第68次学习（2026-10-28）

**主题**：信息化战略实施与标准化体系 —— 战略落地、信息化规划编制、标准化与知识产权、绩效评价

---

## 今日核心概念

### 1. 信息化战略与战略实施

定义：信息化战略是组织在信息化领域的长远目标与总体方略，回答"要建设什么、建成什么样、怎么建成"三个问题。战略实施是将战略意图转化为可执行行动的过程。

关键要点：
- **信息化战略与业务战略的关系**：信息化战略必须**支撑业务战略**，不能脱离业务谈信息化。常见三种关系：支撑型（信息化支撑业务战略落地）、驱动型（信息化引领业务变革）、一体型（战略同步规划）
- **战略实施的四个层次**：战略共识 → 战略解码 → 战略举措落地 → 战略评估与调整
- **战略解码（Strategic Decomposition）**：把战略主题分解为可衡量的战略目标（Objective），再分解为关键绩效指标（KPI）、关键举措（Initiative），最后分解到部门级责任目标。核心工具是**战略地图与平衡计分卡**
- **平衡计分卡四维度**：财务、客户、内部流程、学习与成长。四维度必须平衡——只盯财务指标会导致短期行为，只盯学习成长会失去方向
- **战略举措的分解工具**：OGSM（目标-策略-衡量-行动）、BSC + 战略地图、KPI 分解树（鱼骨图）
- **信息化的战略实施需要"一把手工程"**：IT 战略无法由 CIO 单独推动，必须进入组织最高决策层的议程
- **常见失败模式**：
  1. 战略与业务两张皮——IT 部门自说自话，做的都是自己擅长的项目
  2. 战略停留在 PPT——没有解码到举措与责任，形成不了预算与考核
  3. 战略没有取舍——什么都想做，最后什么都没做成

### 2. 信息化规划的编制方法

定义：信息化规划是组织信息化的纲领性文件，规定信息化的总体目标、架构蓝图、重点任务、实施路径与保障措施。

关键要点：
- **规划编制的六项原则**：全局性、先进性、实用性、经济性、开放性、可扩展性
- **规划的三层结构**：总体目标（愿景与目标）→ 架构蓝图（应用架构、数据架构、技术架构、安全架构）→ 重点任务与实施计划
- **规划与战略的关系**：战略回答"为什么做、做什么"，规划回答"怎么做、做什么、什么时候做完"。**规划是战略在信息化领域的具体化，不是战略的附庸**
- **规划的编制流程**：现状调研与差距分析 → 需求分析 → 愿景与目标设计 → 架构设计 → 重点任务分解 → 实施计划与路线图 → 投资估算与效益分析 → 评审发布
- **现状调研的常用方法**：
  - 业务访谈与问卷（识别业务痛点）
  - 系统清单与资产梳理（识别重复建设）
  - **应用架构成熟度评估**（识别整合机会）
  - 数据流与数据标准调研
  - 竞品与同行对标
- **差距分析的两种类型**：
  - **现状与目标的差距**（该做什么还没做）
  - **各系统之间的差距**（系统间不协同、重复建设）——**后者往往更重要，是整合的主要依据**
- **实施路线图的表达**：按"近期（1年内）夯实基础、中期（2-3年）重点突破、远期（3-5年）整体提升"三阶段划分，配套里程碑与量化指标
- **规划与预算的刚性约束**：规划中的每一个重点任务都应有对应的预算科目与资金来源，否则规划只是愿望清单
- **规划的动态性**：规划不是一次写完就锁定的文件，需设**年度滚动修订机制**，一般 3 年一修、每年调整

### 3. 标准化体系与标准化战略

定义：标准化是为在一定范围内获得最佳秩序，对活动及其结果规定共同规则、准则或要求的过程。在信息化领域，标准化是消除"烟囱"、实现互联互通的制度基础。

关键要点：
- **标准化的三大功能**：**简化**（减少复杂性，降低成本）、**沟通**（统一语言，消除歧义）、**互换**（不同厂商产品可互联）
- **国际标准组织**：ISO（国际标准化组织）、IEC（国际电工委员会）、ITU（国际电信联盟）、IEEE（电气电子工程师学会）
- **我国标准体系**：
  - **国家标准 GB/T**（推荐性，"/T"表示推荐）——强制性为 GB
  - **行业标准**（如行业主管部门发布的行业标准代号）
  - **地方标准**（DB）
  - **团体标准**（社会团体发布）
  - **企业标准**
- **信息化领域的常用国家标准**：
  - GB/T 22239 系列（网络安全等级保护基本要求）
  - GB/T 8567（计算机软件文档编制规范）
  - GB/T 19001（质量管理体系，等同采用 ISO 9001）
  - GB/T 34960 系列（信息安全技术 政务信息共享 数据安全技术要求）
  - GB/T 23020 等（信息化和工业化融合相关）
- **标准化的实施路径**：制定 → 宣贯培训 → 试点验证 → 全面推广 → 检查评估 → 修订
- **标准化的常见困境**：
  1. **标准滞后于技术**——标准制定周期长于技术迭代周期，导致"标准过时"
  2. **标准与需求脱节**——标准制定者与使用者分离，标准不落地
  3. **标准执行走样**——有标准不执行，或执行时打折扣
  4. **标准过多过细**——企业陷入"标准合规"的文档负担，反而影响效率
- **解决路径**：建立**标准动态维护机制**（设置标准复审周期，如 3-5 年）、**实施反馈闭环**（执行中发现问题及时修订）、**标准与考核挂钩**（把标准符合性纳入项目验收与审计）
- **信息化的标准化不等于"一刀切"**：标准化统一的是**接口、数据格式、流程、编码**，不是统一所有技术选型

### 4. 知识产权与信息化中的合规

定义：知识产权是权利人依法就特定客体享有的专有权利。在信息化项目中，涉及开源软件合规、软件著作权、专利侵权等关键风险。

关键要点：
- **知识产权四大类型**：
  - **著作权（版权）**：保护表达形式，**软件代码、文档、界面设计**均受保护，自动产生（作者享有著作权，无需登记）
  - **专利权**：保护技术方案，需申请授予，期限 20 年（发明）
  - **商标权**：保护标识，用于区分商品或服务来源
  - **商业秘密**：保护技术信息与经营信息，**须采取保密措施**才能构成
- **软件著作权登记**：中国实行登记制，登记后可获得《计算机软件著作权登记证书》。**登记不是权利产生的前提，但具有法律证据效力**，是项目验收、知识产权申报的常见材料
- **开源软件合规（核心风险点）**：
  - **开源 ≠ 免费商用**。不同开源许可证对使用、修改、分发的限制不同
  - **许可证类型与义务**：
    - GPL / AGPL：**传染性最强**，衍生作品须同样开源；AGPL 进一步覆盖网络服务场景
    - LGPL：动态链接通常可以，静态链接需提供源码与可重新链接能力
    - MIT / BSD / Apache 2.0：宽松型，基本无分发义务，Apache 2.0 额外包含专利授权与变更声明要求
    - MPL 2.0：文件级弱传染
  - **合规动作**：建立**开源软件清单（SBOM）**、许可证扫描（自动化工具接入 CI）、法务审核、**标注义务的落实**（版权声明、许可证文本随产品分发）
  - **典型违约后果**：法院判令停止侵权、赔偿损失、公开道歉；政府项目还涉及**审计问责与信用记录**
- **职务发明与成果归属**：信息化项目中自主开发形成的软件，其著作权归属依劳动合同与保密协议约定，**必须在合同中明确约定归属与奖励**，否则纠纷时适用"法人作品"推定
- **项目全周期的知识产权管理**：
  - 立项阶段：明确知识产权策略（自研、采购、开源的比例）
  - 采购阶段：合同中约定知识产权归属与侵权担保条款
  - 实施阶段：过程文档与源码版本留痕
  - 验收阶段：软件著作权登记、交付物清单核对
  - 运维阶段：许可合规年度审计
- **数据合规相关**：数据知识产权、数据流通交易合规等是新增热点领域

### 5. 信息化项目的绩效评价

定义：信息化项目绩效评价是对项目目标达成情况、实施过程质量与效益实现程度的综合判断，为后续改进与决策提供依据。

关键要点：
- **评价的三个维度**：**效果评价**（做成了没有、目标达成度）、**效率评价**（成本投入产出比）、**效益评价**（对组织的长期影响）
- **评价方法的演进**：
  - 财务评价法：净现值（NPV）、内部收益率（IRR）、投资回收期、效益费用比。**财务法难以反映无形效益与战略价值**
  - **成本效益分析**：适合公共项目的经济合理性分析
  - **后评价法**：项目结束后的系统性回顾，对后续项目最有价值
- **项目后评价的四个维度**：
  1. **目标评价**：目标是否合理、是否达成
  2. **实施过程评价**：过程是否规范、效率如何
  3. **效益评价**：效益是否实现、是否可持续
  4. **影响评价**：对组织战略、流程、能力的长期影响
- **后评价的方法组合**：**逻辑框架法（前后对比）** + **项目前后对比** + **横向对比（同类项目）** + **有无对比（对照组）**
- **评价指标设计原则**：
  - **可量化优先**，避免"满意度高"这类不可测指标
  - 区分**产出指标**（Output，交付了什么）与**效果指标**（Outcome，改变了什么）
  - 指标要与规划中的目标指标对齐，形成"目标—指标—评价"的贯通
- **常见问题**：
  1. **只评不闭环**——评价做完没有反馈到下一轮规划，评价沦为形式
  2. **重产出轻效果**——交付了系统不等于改变了业务
  3. **数据不可信**——项目期数据为自我填报，缺乏独立核验
- **改进方向**：建立**评价结果应用机制**（评价结论作为下一年度预算分配、项目立项排序、供应商评价的依据），让评价真正产生约束力

### 6. 信息系统审计与合规治理

定义：信息系统审计是独立地对信息系统的控制机制、运行状况与合规性进行评价的活动，是治理闭环的"最后一双眼睛"。

关键要点：
- **审计与内部控制的区别**：内部控制是"自己管自己"，审计是"独立评价别人"（独立性是审计的核心特征）
- **信息系统审计的常见目标**：财务信息的可靠性与完整性、系统的可用性与效率、合规性、系统安全与隐私保护、内部控制的有效性
- **审计类型**：
  - **控制测试**：测试内部控制是否有效运行
  - **实质性测试**：直接验证数据与业务的真实性
- **审计依据**：国际标准 ISACA 的 CISA、中国的《企业内部控制基本规范》、《信息系统审计准则》、等级保护测评要求
- **审计的常见发现类型**：
  1. **权限管理类**——账号共用、越权授权、离职账号未回收、超级管理员滥用
  2. **变更管理类**——变更未经审批、测试不充分、无回滚方案
  3. **日志与监控类**——关键操作无日志、日志未集中留存、日志可被删除
  4. **数据安全类**——数据未分级分类、备份未验证、个人信息超范围使用
  5. **文档与制度类**——制度缺失或未及时更新、实际操作与制度不符
- **审计的落地要点**：
  - **以制度为基准**——审计什么，取决于制度怎么写。**没有制度，审计无从下手**
  - **以证据为支撑**——抽样检查、穿行测试、系统日志提取，**结论必须有可核查的证据链**
  - **以整改闭环为目的**——发现问题 → 定级 → 明确责任人与时限 → 复查验证
- **合规治理的框架支撑**：网络安全等级保护、密码应用安全性评估（密评）、数据安全、个人信息保护等构成合规要求的外部约束，**审计是验证是否满足这些约束的手段**

### 7. 信息化项目的知识管理与经验沉淀

定义：知识管理是组织对知识的获取、创造、共享、应用与保留的系统性管理。在信息化项目中，经验沉淀直接决定后续项目的效率。

关键要点：
- **知识的分类**：显性知识（文档、流程、代码）与人隐性知识（经验、直觉、技能）。**信息化项目最大的知识资产往往是隐性知识**
- **项目知识管理的主要活动**：知识识别、知识获取、知识共享、知识应用、知识保留
- **经验沉淀的载体**：
  - **模板库**：把重复性的工作固化为模板（方案模板、测试用例模板、验收清单）
  - **案例库**：成功与失败案例都要入库，**失败案例的价值往往更高**
  - **检查清单（Checklist）**：把专家经验转化为可执行的操作步骤，降低对个人能力的依赖
- **复盘机制**：项目结束后组织复盘会，对照原计划与实际情况，分析差异与根因，形成改进项并跟踪
- **失败的常见原因**：
  1. **无复盘机制**——项目结束即散伙，经验随人走
  2. **只记成功不记失败**——失败案例被视为"污点"，不愿记录
  3. **知识不结构化**——只写大段总结，没有可复用的清单与模板
  4. **缺乏落地场景**——知识入库后无人查阅，与没有一样
- **让知识复用的三个关键设计**：
  - **可检索**——分类清晰、命名规范、全文检索
  - **可复用**——以模板和清单形式呈现，而非叙述性总结
  - **有入口**——融入日常工作流，开发人员在写方案时能被提示"参考某某模板"

## 三个常考陷阱

### 陷阱一：把"信息化规划"写成"项目列表"

**错误表述**：规划正文由几十个拟建项目的名称、描述、预算构成。

**为什么错**：项目列表是规划的**输出**，不是规划的**本体**。一份只有项目清单的规划，缺少三个关键要素：
1. **没有现状差距分析**——不知道现状是什么，就不知道为什么要建这些项目
2. **没有架构蓝图**——项目之间各建各的，最终形成一堆烟囱，正是规划要解决的问题
3. **没有实施路径与优先级依据**——不知道先做什么、后做什么、为什么

从"项目列表"到"真正的规划"，中间的桥梁是：**愿景与目标 → 架构蓝图 → 重点任务 → 项目组合 → 实施路线图**。

**正确表述**：规划的最小完整形态是"**一份差距分析、一张架构蓝图、一组重点任务、一条实施路线图**"。判断一份规划是否合格，看它能否回答"为什么建、建成什么样、先建什么"三个问题。

### 陷阱二：认为"标准化会拖慢信息化速度"

**错误表述**：标准制定流程长、审批多，会妨碍信息化的快速响应，应该少做标准。

**为什么错**：这是把"标准化成本"与"标准化收益"错误对比。标准化的收益是**长期的、累积的、规模化的**：
1. **消除重复建设**——没有统一的数据编码与接口标准，20 个系统就要对接 20 种口径，后续每一次数据共享都要重新开发
2. **降低集成成本**——统一接口规范后，新系统接入是"照着做"，而不是"逆向猜"
3. **提升人员流动的抗性**——人员轮岗时，标准是"岗位知识"的载体
4. **规避方向性返工**——技术路线定错、系统无法互联的返工成本，远高于制定标准的成本

而所谓"标准拖慢速度"，多半是标准本身有问题：**标准滞后于技术、标准与需求脱节、标准执行走样**。这是标准质量与维护机制的问题，不是标准化的必然代价。

**正确表述**：标准化的正确取向是"**少而精、快而准**"——减少标准数量、提高标准质量、建立快速修订机制。用"制定得慢"来否定标准化，是把手段的缺陷当成了目的的缺陷。

### 陷阱三：把"信息化项目的效益"等同于"系统建成上线"

**错误表述**：项目按时上线、通过验收、用户能登录使用，就说明项目成功了，效益已经实现。

**为什么错**：验收通过衡量的是**交付物**，效益实现是**业务变化**，两者之间存在明显落差：
1. **建成不等于会用**——系统上线但业务人员仍用线下方式，信息孤岛只是搬到了线上
2. **会用不等于有效**——业务在系统上走了，但审批时长未缩短、错误率未下降、群众办事体验未改善
3. **短期有效不等于长期有效**——系统硬推行政流程，一年后大家绕过系统回到线下，系统成为"摆设"
4. **有形效益不等于全部效益**——政务信息化大量效益是无形的（能力提升、风险降低、决策科学化），财务法算不出来

**正确表述**：信息化项目的成功判断必须区分三个层次：**交付层**（是否按质按量建成）→ **使用层**（是否真正被业务采用、替代了原有线下方式）→ **效果层**（业务指标是否改善、组织能力是否提升）。项目绩效评价必须覆盖这三层，而不能止步于验收。

## 案例分析题

### 案例 1 — 某市"十四五"信息化规划落空与"十五五"规划编制

**背景材料**

某市为推进政务信息化建设，2021 年编制了《"十四五"政务信息化规划》，规划提出到 2025 年建成"一网通办"体系、"一网统管"体系，实现全市政务数据共享，事项"一网通办"率达到 100%，并规划了 47 个重点建设项目，总投资 18.6 亿元。

**规划编制过程**

规划编制历时 4 个月，征求了 32 个部门意见，进行了 3 轮专家论证，最终形成文本共 12 万字。规划正文第 6 章为"重点任务与项目"，以表格形式列出了 47 个项目的名称、建设单位、起止年份、投资额和预期目标。

**执行情况**

到 2025 年底的实际执行情况：
- 47 个项目中，完成并通过验收 29 个，延期 11 个，取消 7 个
- 已建成系统共 34 个，其中市本级 12 个、区县级 22 个
- 数据共享方面：规划要求市级部门数据"应享尽享"，实际完成 118 类数据共享，覆盖 32 个部门。规划目标为"2025 年底前实现市级部门数据共享率达到 100%"，实际为 72%
- "一网通办"事项：规划目标 100%，实际 68.6%
- 总投资完成 14.2 亿元，剩余 4.4 亿元因资金调整未落实
- 系统上线后使用率：12 个市本级系统中，3 个系统月活跃使用率低于 20%，其中 2 个已被同部门另一系统替代但未及时下线

**项目后评价发现的问题**

2026 年 3 月，该市委托第三方开展"十四五"信息化规划实施后评价，报告指出：
- 29 个已验收项目中，**只有 6 个项目的验收材料中包含了可量化的效益指标**，其余 23 个的验收材料主要为功能清单与截图
- 多个项目的实际使用部门在访谈中表示"系统确实比原来的方式麻烦"，尤其是需要跨部门流转的环节
- 部分已建系统之间存在功能重叠，评价组统计到至少 9 处功能重复
- 规划编制过程中形成的现状调研材料显示，当时全市已有各类政务系统 62 个，但规划正文未对这 62 个系统的现状做出完整梳理，未提出整合清单

**"十五五"规划编制启动**

2026 年 4 月，该市启动《"十五五"政务信息化规划》编制工作。规划组提出的编制思路是：
1. 全面梳理全市在建和已建系统，形成系统资产台账
2. 围绕"数据共享"和"事项整合"两条主线设计重点任务
3. 对所有项目提出明确的量化目标和可验证的效益指标
4. 编制完成后开展后评价，作为下一轮规划的输入

规划组在编制说明中提出一个尖锐问题：**"十五五"规划中，如何避免重蹈"十四五"的老路——规划与执行两张皮？**

---

### 问题 1 — 针对"十四五"规划的执行问题，分析规划编制中存在的缺陷

**参考答案：**

**缺陷一：规划文本以项目列表为主体，缺少架构蓝图与差距分析**

从题中信息可以直接看出两处结构性缺失：

其一，**未对现状做出完整梳理**。规划编制时全市已有 62 个政务系统，但规划正文未做梳理、未提整合清单。结果是：规划在既没有弄清"手里有什么"的情况下就规划"要建什么"，导致 47 个项目中有 7 个被取消、9 处功能重复、2 个系统上线后即被同部门另一系统替代。**这是典型的"重复建设"**——重复建设的根源不在执行，而在规划阶段缺少现状资产梳理。

其二，**缺少架构蓝图**。没有统一的应用架构与集成架构，各部门项目建设时各自确定技术路线与对接方式，结果是 34 个系统"各自为政"，共享率仅 72%、"一网通办"仅 68.6%。**规划本应解决的最大问题（消除烟囱），恰恰因为规划中没有架构设计而落空。**

**缺陷二：目标设定不可验证，缺乏可度量的过程指标**

规划目标"数据共享率 100%"、"一网通办率 100%"这类指标看似明确，实则不可验证：
1. **口径未定义**——"数据共享率"的分母是什么？是应共享数据目录条数，还是部门自有数据条数？"一网通办"是指可网上办理，还是实际通过网厅办理？口径不清导致验收时无法客观判定
2. **只有终态目标，没有过程指标**——100% 是个终局数字，无法作为年度考核依据，也无法在进度落后时及时预警
3. **缺少约束性配套**——没有把共享率拆解到各部门的责任指标，没有对应的考核机制

结果是数据共享率停在 72%，而**没有任何一方被追责**——目标无法度量，就无法管理。

**缺陷三：目标与项目之间缺乏逻辑映射**

47 个项目与规划目标之间看不出对应关系。规划没有回答"47 个项目中，每一个如何支撑'数据共享'或'一网通办'目标"。这导致：
- 项目优先级排序缺乏依据（按部门报送顺序？按投资额？无法判断）
- 项目完成后无法判定其目标贡献度
- 项目取消或延期时，无法判断目标是否仍可达成

**缺陷四：投资与效益的匹配关系缺失**

规划总投资 18.6 亿元，但未说明这些投资分别支撑哪个目标、预期产生什么效益、效益如何测量。执行结果中 29 个项目只有 6 个有可量化的效益指标，**说明效益论证在立项与验收环节就已失效，而非执行阶段才失效**。

**缺陷五：缺少实施路线图与动态修订机制**

规划只有项目起止年份，没有阶段划分（近期夯基础、中期重点突破、远期整体提升）、里程碑与年度目标。从执行结果看，11 个项目延期、7 个取消，说明规划缺乏对外部环境变化（预算调整、需求变化、技术演进）的应对机制——**规划是一份静态文件，而执行是一个动态过程**。

**缺陷六：需求获取环节存在"部门报送"式偏差**

后评价中多个部门反映系统"比原来的方式麻烦"，尤其是跨部门流转环节。这说明需求在规划编制阶段未被真正验证：规划的编制过程是"征求 32 个部门意见"，属于**自下而上的部门视角**，缺乏从**业务流程和用户视角**的横向梳理。**部门视角天然偏好本部门职能完整，跨部门流程的便捷性天然受损**。

**缺陷七：缺少信息化规划与业务规划的衔接**

规划通篇是信息化建设内容，未见与全市业务规划（政务服务事项标准、监管流程优化、基层减负）的映射。而"一网通办"率低、"系统比原来麻烦"的根本原因，正是信息化没有伴随业务流程的同步优化——**用系统去固化未优化的流程，只会把低效固化下来**。

### 问题 2 — 针对后评价发现的验收与使用问题，提出改进方案

**参考答案：**

**一、建立以"效果"为核心的验收指标体系**

**问题诊断**：29 个项目中只有 6 个有可量化效益指标，验收实质退化为"功能是否按设计实现"的检查，**只验交付物不验效果**。

**改进方案**：

**第一，验收指标分三层设计**

| 层次 | 指标类型 | 示例 | 权重建议 |
|---|---|---|---|
| 交付层 | 功能完成度、缺陷密度、性能达标率 | 需求实现率 ≥95%、严重缺陷为零 | 30% |
| 使用层 | 活跃用户数、业务替代率、流程线上化率 | 上线 6 个月内月活用户占目标用户 ≥70%、原线下流程关闭率 100% | 30% |
| 效果层 | 业务指标改善、用户满意度、成本节约 | 审批时限缩短 ≥30%、人工工作量减少 ≥20%、群众满意度 ≥90% | 40% |

**关键**：**效果层指标必须在立项时（可研与实施方案中）就确定**，而不是验收时再定。验收时补指标必然导致"凑数"。

**第二，项目立项即锁定"效益承诺书"**

- 可研阶段明确 3-5 条可量化的效益指标，写入项目合同与验收标准
- 效益指标的**测量方法、数据来源、测量责任人**同时确定，避免验收时扯皮
- 建立**效益基线**：立项时记录现状指标值（如审批平均时长 5 个工作日），作为对比基准

**第三，验收流程改造**

- **延长观察期**：系统上线后设置 3-6 个月试运行期，试运行期结束才做最终验收，试运行期内**只允许部分验收款支付**
- **分期验收**：按里程碑分阶段验收，如"一期上线验收 + 二期效益达标验收"，尾款与效益指标挂钩
- **引入独立核验**：第三方或审计部门对效益指标进行抽验，避免建设单位自评

**二、破解"系统建了但没人用"的困境**

**问题诊断**：12 个市本级系统中 3 个月活使用率低于 20%，说明**系统交付与业务采纳之间存在断裂**。

**改进方案**：

**第一，需求侧的根本修正——流程先行**

- 项目立项前必须完成**业务流程再造**，明确哪些环节取消、哪些环节合并、哪些环节线上化
- **系统不得增加手工填报环节**。凡是新系统增加的录入字段，必须有明确的复用来源或法定必要性
- 对跨部门流转环节做专项优化：统一入口、统一材料复用、状态可查

**第二，采用推行策略**

- **试点先行**：先在 2-3 个典型部门或区县试点，跑通后推广，避免"全市一次性上线"带来的培训与适应断层
- **培训与考核同步**：培训不是"上线前讲一次"，要嵌入日常业务，并纳入使用方的考核
- **领导带头用**：单位主要负责人作为系统第一使用者，形成自上而下的推动力

**第三，推行阻力识别与破除**

- 阻力来源要分类识别：**能力型**（不会用）→ 培训与辅助；**习惯型**（习惯线下）→ 制度强制与流程闭环；**利益型**（线下留痕有利于某环节）→ 需从制度上消除；**信任型**（担心数据被比对问责）→ 明确数据使用边界
- **建立反馈闭环**：用户意见的收集、处理、反馈要有台账，让用户看到"提了有用"

**第四，低活跃系统的处置**

- 对月活低于 20% 的系统启动**退出评估**：确认是推广不力还是功能定位错误
- 与功能重叠的系统**合并下线**，避免"僵尸系统"持续占用资源并制造数据不一致
- **下线要有流程**：数据归档、接口清理、账号回收、公告告知，防止"系统没了但数据还在"留下隐患

**三、把后评价结果真正用起来（闭环机制）**

**问题诊断**：后评价若不产生约束，就是一次昂贵的自我批评。

**改进方案**：

- **后评价结论作为下一轮项目立项的硬约束**：同类项目若上次未达成效益指标，本次需说明改进措施与依据
- **后评价结论纳入供应商评价**：连续两个项目效益不达标的供应商，在后续采购中扣分或限制参与
- **后评价发现的问题形成整改台账**，明确责任部门、责任人、整改时限，由规划主管部门跟踪销号
- **建立"规划—实施—评价—修订"的正式循环**：评价结论作为规划修订的强制输入，这正是该市"十五五"规划编制思路中已明确的方向，应固化为制度

### 问题 3 — 针对"十五五"规划编制，回答"如何避免规划与执行两张皮"

**参考答案：**

"规划与执行两张皮"的根源在于：**规划作为一份静态文件，独立于执行过程；执行的信息不回流规划，执行的偏差也不触发规划调整。**因此破题的关键不是"把规划写得更细"，而是**让规划与执行形成闭环**。

**一、在规划结构上建立"目标—举措—项目—指标"的贯通链条**

这是解决两张皮的第一道防线。规划不能只有项目列表，必须做到每个项目都能向上追溯到目标、每个目标都能向下分解到项目：

- **目标层**：3-5 个可量化的总体目标，每个目标有明确口径定义与基线值
- **举措层**：每个目标分解为 2-4 项战略举措，举措描述"做什么"而非"建什么系统"
- **项目层**：举措落为具体项目，每个项目标注"支撑哪项举措、贡献哪个目标指标"
- **指标层**：每个目标配 3-5 个指标，标注责任部门、测量方式、年度目标值
- **追溯检验**：规划评审时，随机抽取任一目标，应能逐层追溯到项目；任一项目，应能向上追溯到目标。**追溯不通即为规划缺陷**

**二、在编制方法上引入"自上而下 + 自下而上"的双向校验**

- **自上而下**：从全市业务战略与群众需求出发，先定目标与举措，再往下推导项目。**必须从业务流程和用户视角出发，而非从部门职能出发**——这是 34 个系统建好却不好用的根本教训
- **自下而上**：从系统资产台账出发，识别重复建设、可整合、可下线的部分
- **双向校验的检验标准**：自上而下的项目清单与自下而上的资产清单**必须交叉比对**，凡与既有系统功能重复的，必须论证整合方案或明确下线计划后方可立项

**三、在编制内容上强制包含"整合清单"与"退出机制"**

- 规划中必须有一张**系统整合清单**：明确哪些现有系统合并、哪些改造、哪些下线、保留多久
- 规划中必须明确**下线机制**：功能重叠系统的识别标准、决策程序、时限要求。**没有下线机制的规划，只会不断叠加**
- 从"十四五"的教训看，2 个系统上线后被同部门另一系统替代却未及时下线，说明**下线是最难的部分**，必须在规划阶段就设定规则

**四、在目标设定上采用"口径先行 + 过程指标"**

- **口径先行**：每一个目标指标必须先写清定义、计算公式、数据来源、统计范围、测量频率。**口径不清的目标等于没有目标**
- **过程指标 + 终态指标配套**：终态目标（如共享率 100%）指导方向，过程指标（如"每季度完成 XX 类数据目录梳理与标准编制"，"上半年完成 20 个系统的整合下线"）用于年度考核与预警
- **目标值要留出弹性区间**：给出基准值与目标值两档，避免因外部因素（如预算调整）导致目标刚性失真后无人负责

**五、在执行环节建立"规划跟踪 + 偏差触发"的动态机制**

- **定期跟踪**：季度调度、半年评估、年度调整——与该市招标筛查任务的调度机制可以复用同一套节奏
- **偏差触发规则**：明确规定何种偏差必须触发什么动作。例如：关键指标完成率低于 70% 时自动启动专项评估并向市政府报告；单个项目延期超过 3 个月自动触发变更审查；年度投资完成率低于 85% 时启动规划整体复核
- **滚动修订机制**：明确规划年度调整的权力与流程——**哪些内容可由规划主管部门调整（项目排序、资源配置），哪些必须报市政府批准（总体目标、投资总额）**。不划清这个界限，规划一遇问题就只能整体推翻重来，或者干脆不动

**六、引入独立评估与第三方后评价**

- 规划实施中期（第三年）开展**中期评估**，不等到规划期末才发现全部落空
- 规划期末开展**第三方后评价**，评估机构与规划编制单位分离
- 评估结论作为下一轮规划的强制输入，并作为预算安排的重要依据

**七、把规划从"文本"变成"平台"**

技术层面的支撑手段：用信息化手段承载规划，形成**规划任务管理平台**：
- 目标、举措、项目、指标、责任人、进度、效益实测值在同一平台关联
- 指标数据自动采集（从各业务系统取数），**避免靠人工填报数据**
- 偏差自动预警并推送至责任人
- 规划调整通过平台留痕，版本可追溯

这既提升了管理效率，也**让规划从一次性文档变成持续运行的机制**——这是解决"两张皮"最根本的手段。

**八、明确"规划的生命在于执行"的责任机制**

- 规划经市政府批准后，**规划中的目标分解为责任部门的年度绩效指标**，纳入考核
- 责任部门的主要领导对目标负责，形成刚性约束
- 规划主管部门具备**建议调整与通报批评**的职权
- 同时要防止走向另一个极端——**目标定得过高导致层层造假**。因此目标值必须基于历史数据测算，且留有合理弹性

**总结**：避免两张皮需要三件事同时成立——
1. **结构上贯通**（目标-举措-项目-指标可双向追溯）
2. **方法上双向**（自上而下的业务视角 + 自下而上的资产视角交叉校验）
3. **机制上闭环**（跟踪、偏差触发、滚动修订、评估反馈）

**其中第三点最关键**。前两点靠编制质量，第三点靠制度保障。**没有制度保障的规划，本质上仍是一份期望文件。**
