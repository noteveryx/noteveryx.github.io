## 今日核心概念

### 1. 信息系统运行维护的 SLA 与运维考核体系

定义：SLA（Service Level Agreement，服务级别协议）是服务提供方与客户之间就服务质量指标、责任边界、违约处理达成的法律约束正式协议；运维考核体系是将 SLA 指标转化为可度量、可追责、可改进的日常管理机制。

关键要点：
- **SLA 三层结构**：**业务层 SLA**（面向最终用户的服务可用性与响应承诺，如"市民办事系统可用性 99.9%"）、**系统层 SLA**（面向技术组件的服务水平，如"数据库响应时间 P95 < 2s"）、**第三方 SLA**（面向外部供应商的支撑承诺，如"云厂商网络可用性 99.99%"）。**三层必须逐级分解，下层指标之和支撑上层承诺**。
- **OLA（Operational Level Agreement，运营级别协议）**：内部各技术团队之间的服务承诺，用于对齐内部责任。如"网络组承诺 30 分钟内响应应用组的网络类工单"。**OLA 是 SLA 的内部支撑，无 OLA 则 SLA 无保障**。
- **SLA 核心指标六类**：**可用性**（Availability）、**响应时间**（Response Time，首次响应）、**解决时间**（Resolution Time，从报障到恢复）、**服务时间窗口**（Service Window，7×24 或 5×8）、**服务交付量**（如工单处理量）、**质量指标**（如一次解决率 FCR、满意度）。
- **可用性计算公式**：可用性 = (总服务时间 − 不可用时间) ÷ 总服务时间 × 100%。**"不可用"的认定标准必须在 SLA 中明确定义**（如"连续 3 次调用失败即判定不可用"、"单次超过 30 秒视为不可用"），否则违约判定扯皮。
- **可用性等级与年停机时间换算**：

| 可用性 | 年不可用时间 | 故障容忍 |
|---|---|---|
| 99% | 3.65 天 | 每周可停 4 小时 |
| 99.5% | 1.83 天 | — |
| 99.9% | 8.76 小时 | 每月可停 43 分钟 |
| 99.95% | 4.38 小时 | — |
| 99.99% | 52.6 分钟 | 每月可停 2.2 分钟 |
| 99.999% | 5.26 分钟 | 每周可停 6 秒 |

- **SLO 与 SLA 的关系**：**SLO（内部目标）应严于 SLA（对外承诺）**，如 SLA 承诺 99.9%，内部 SLO 定 99.95%，留出缓冲避免违约。
- **运维考核七指标**（可作为月度考核表）：① 可用性达成率；② 响应及时率（首次响应在 SLA 时限内）；③ 解决及时率（解决时长在 SLA 时限内）；④ 一次解决率 FCR；⑤ 工单闭环率与超期工单数；⑥ 用户满意度（CSAT/NPS）；⑦ 重大故障数（M1/M2 级）。
- **违约与考核处理**：SLA 违约金通常采用"按比例扣减服务费"方式（如可用性每低于 0.1% 扣减月度服务费 5%，扣减上限 30%）；连续 3 个月违约可要求整改、扣减费用或解除合同。**扣减上限必须写入合同**，避免无限责任。
- **运维服务报告机制**：**月度服务报告**（各项指标达成情况、未达标项说明、改进计划、趋势分析）+ **季度服务评审会**（深度复盘 + 改进项确认）+ **年度服务回顾**（整体评价与 SLA 续签）。**报告必须数据可溯源**，人工估算的数据在争议时不可采信。
- 记忆口诀：「SLA 三层业务系统三方，OLA 是内部支撑；可用性=(总-不可用)/总，不可用定义先写清；99.9 年停 8.76 时，99.99 只有 52 分；SLO 严于 SLA 留缓冲，扣减上限必须定」

### 2. 运维事件与问题管理深度实践

定义：事件管理（Incident Management）目标是**尽快恢复服务**、降低业务中断影响；问题管理（Problem Management）目标是**找出事件根本原因并消除**，防止同类事件重复发生。两者是"救火"与"防火"的关系。

关键要点：
- **事件管理六步**：① **事件记录**（服务台统一受理，建立工单，记录时间线）；② **分类与优先级判定**（影响范围与紧急度双维度）；③ **初步诊断与一线解决**；④ **升级**（功能性升级转二线/三线，层次性升级申请管理权限或资源）；⑤ **解决与恢复**；⑥ **关闭与知识沉淀**（关闭前必须判断是否可沉淀为知识条目）。
- **事件优先级矩阵（影响 × 紧急度）**：

| | 紧急（立即处理） | 不紧急（可排期） |
|---|---|---|
| **影响大**（核心业务中断/多用户受影响） | P1 紧急 | P2 高 |
| **影响小**（单用户/非核心功能） | P3 中 | P4 低 |

- **升级三原则**：① **明确升级触发条件**（如 P1 事件 30 分钟未恢复自动升级）；② **明确各级响应时限**（一线 15 分钟、二线 30 分钟、三线 1 小时）；③ **升级不等于甩锅**（升级后原责任人仍需跟踪至关闭）。
- **重大事件（Major Incident）管理**：指定**重大事件经理（Incident Commander）**、建立专用沟通渠道（应急群/专线）、定时向干系人通报（每 30 分钟一次，即使无进展也要通报）、启动应急预案、事后 5 个工作日内完成**复盘报告**（Post-Incident Review）。**"无进展也要通报"是常被违反但极其重要的规则**——干系人最焦虑的不是坏消息，而是不确定。
- **问题管理四步**：① **问题识别**（触发条件：同一类事件 30 天内发生 ≥3 次、单个 P2 以上事件、重大事件复盘发现潜在根因、人工提出）；② **根因分析**（5Why 连问、鱼骨图六维人机料法环测、KT 法）；③ **变通方案与已知错误登记**（Workaround 临时绕行、Known Error 已知但未根治的错误）；④ **永久解决方案**（通过变更管理实施，实施后关闭问题单并观察是否复发）。
- **根因分析五问法示例**（数据库连接池溢出 47 次）：为什么溢出？→ 连接未释放 → 某批查询未关闭 Statement → 代码缺少 try-with-resources → 无代码规范与门禁检查 → **根因是开发规范与静态扫描门禁缺失**。**永久方案不是"重启服务"，而是"整改代码 + 引入静态扫描门禁 + 参数调优 + 连接泄漏监控告警"**。
- **变通方案 vs 永久方案**：变通方案是**快速恢复业务**的临时手段（重启、扩容、切换、限流），**不解决根因**，必须登记为已知错误并推动永久方案；永久方案须走变更管理实施。**只有变通没有永久方案，问题管理就是白做**。
- **知识库建设三分类**：**操作手册**（How-to，正常操作指引）、**故障处置卡片**（SOP/应急预案，按错误码或现象索引）、**常见问题 FAQ**（图文并茂，面向最终用户）。来源：事件关闭、问题解决、变更实施、项目交付均须沉淀；设知识审核人定期评审有效性。
- **重复性事件率是运维成熟度的核心指标**：目标应从当前的 60%+ 降到 30% 以下，**这个指标的改善才是问题管理真正见效的标志**。
- 记忆口诀：「事件救火求快恢复，问题防火求除根因；一个问题关闭多个事件；五问法连追到根因，变通恢复永久根治；P1 重大事件必通报，没进展也要按时报；重复事件率降下来才算真管用」

### 3. 运维变更管理与配置管理（CMDB）深度实践

定义：变更管理（Change Management）是对 IT 基础设施与服务的变更进行评估、授权、计划、实施、验证与回顾的全过程管理；配置管理（Configuration Management）维护配置项（CI）及其关系的准确信息，是变更影响分析与故障定位的基础。

关键要点：
- **变更管理七步**：① **提出变更申请（RFC）**（明确变更内容、原因、影响范围、实施窗口、验证方法、回滚方案）；② **分类与分级**；③ **评估**（技术可行性、业务影响、风险等级、资源需求、依赖影响、回滚可行性）；④ **授权**（CAB 审批 / ECAB 紧急审批 / 标准变更预授权）；⑤ **计划与准备**（确认窗口、备份数据与配置、准备回滚脚本、通知相关方）；⑥ **实施与验证**（实施后立即做功能 + 性能 + 业务链路验证，全程有人值守观察至少一个业务高峰）；⑦ **关闭与回顾**（更新 CMDB、记录结果、评估目标达成、重大变更复盘）。
- **变更三类型**：**标准变更**（预授权的低风险高频操作，如密码重置、日志清理、白名单添加，走快速通道，事后登记）、**常规变更**（需 CAB 评估，走完整流程）、**紧急变更**（重大故障修复，ECAB 30 分钟内快速审批，但**必须事后补全记录并复盘**）。**紧急变更不能免除记录义务**。
- **变更分级四级**：一级（重大，影响多系统/架构级，需 CAB + 高层批准，安排在业务低峰期，实施前必须演练）、二级（重要，影响单一核心系统，需 CAB 审批，必须有回滚方案）、三级（一般，影响非核心系统，运维负责人审批）、四级（标准，预授权 SOP 操作，事后登记）。
- **变更三条铁律**：① **没有回滚方案的变更不得实施**；② **生产环境禁止直接改**（必须走发布流程，配置变更也需审批）；③ **变更必须同步更新 CMDB**，否则 CMDB 失真将导致后续故障定位困难。
- **回滚方案要求**：明确回滚触发条件、回滚步骤、回滚耗时、回滚责任人。**"回滚需要 2 小时"和"回滚需要 5 分钟"是两种完全不同的风险等级**，应急能力应按后者设计。
- **CMDB 四类配置项**：硬件（服务器、存储、网络设备）、软件（操作系统、中间件、应用、数据库）、文档（架构图、手册、SLA 协议）、环境与合约（机柜、机房、IP 地址段、供方合约）。
- **CMDB 六步建设路径**：① **界定范围与分级**（不追求一次全量，按"关键业务优先"分批，首批纳入支撑核心业务的服务器、数据库、中间件、核心应用及其依赖，约 500~800 个 CI）；② **设计数据模型**（CI 类型 + 关系类型：依赖、部署于、连接、使用、支撑；每个 CI 记录负责人、位置、版本、生命周期、SLA 等级）；③ **数据采集与初始化**（自动发现工具如网络扫描、Agent 采集、云 API + 人工核对）；④ **嵌入变更流程（最关键）**——**变更关闭前必须完成 CMDB 更新，否则变更单无法关闭**；⑤ **定期校正与审计**（自动发现每周比对一次，输出准确率报告，目标 ≥95%；每季度配置审计抽样核对实物与记录）；⑥ **明确组织责任**（配置管理员 + 各域配置责任人，"谁变更、谁更新"）。
- **CMDB 的三个核心用途**：**故障影响分析**（改这个 CI 会影响谁）、**变更影响评估**（提前识别受影响服务）、**资产盘点与审计取证**。**这三点是 CMDB 价值的全部来源，如果没人用，CMDB 就会沦为没人维护的死数据**。
- 记忆口诀：「变更七步申请评批计验关；标准常规紧急三分，四级变更按风险；三条铁律：无回滚不实施、生产不直改、变完必更 CMDB；CMDB 六步定范围建模型采数据联变更用审计设专人；价值三用途：故障影响、变更评估、资产审计」

### 4. 运维可用性管理与连续性保障

定义：可用性管理是确保 IT 服务按约定目标持续运行、并主动管理可用性风险的活动集合；连续性保障（Business Continuity）是灾难发生后维持关键业务运行的完整能力体系，涵盖容灾、备份、应急预案与业务连续性计划。

关键要点：
- **可用性三段公式**：可用性 = MTBF ÷ (MTBF + MTTR)。**MTTR 越短、MTBF 越长，可用性越高**。提升可用性的杠杆只有三个：**提高 MTBF**（减少故障次数）、**缩短 MTTR**（加快恢复）、**缩小影响面**（故障不扩散）。
- **MTTR 构成拆解**（用于缩短）：**发现时间**（监控告警是否及时，秒级告警优于人工发现）、**响应时间**（值班人员多久介入）、**定位时间**（是否有 CMDB 和链路追踪，通常占 MTTR 的 40%~60%）、**恢复时间**（是否有预案、能否自动化恢复、是否需人工操作）。**定位时间最长，是优化重点**。
- **提升可用性五手段**：① **冗余**（消除单点：双机热备、多副本、跨机房）；② **容错**（故障自动切换：自动 failover、健康检查 + 自动摘除）；③ **主动预防**（容量管理、补丁管理、监控预警、变更评审）；④ **隔离**（舱壁、资源池、限流，防故障扩散）；⑤ **演练**（定期故障演练，验证冗余与切换真实有效）。
- **故障恢复能力分级**：**冷备**（数据 + 备机，需手动恢复，RTO 小时级）、**温备**（数据同步，备机待启动，RTO 分钟到小时级）、**热备/双活**（实时同步，随时可切，RTO 分钟级以内）。**选型取决于 RTO/RPO 要求与成本约束**。
- **RTO 与 RPO 权衡**：RTO 越短、RPO 越小（如 RPO=0 同步复制），成本越高（需要专线、高规格设备）。**必须在成本与可用性目标之间找平衡点**，政务类核心系统通常接受同步复制的高成本，非核心用异步。
- **单点故障排查清单**：数据库（主库是否单点）、中间件（MQ 是否单节点）、网络（是否单出口/单运营商线路）、电源（是否单路供电）、机房（是否单机房）、DNS（是否单域名服务器）、证书（是否即将到期）、**人员（是否只有一人会某项操作，属"人的单点"）**。**人的单点最容易被忽略，也最难在技术层面解决**。
- **业务连续性计划（BCP）五要素**：**业务影响分析（BIA）**（识别关键业务与最大可容忍中断时间）、**风险评估**、**恢复策略**（灾难恢复流程）、**演练计划**、**维护与审查**。**BIA 是 BCP 的前提**，不分析关键业务就无法确定恢复优先级。
- **应急预案六要素**：**触发条件**（什么情况下启动，量化指标）、**响应团队**（谁指挥、谁执行、谁联络）、**处置步骤**（按序执行的 checklist）、**资源准备**（备件、备用环境、第三方联系方式）、**对外沟通**（通知干系人的渠道与话术）、**恢复与总结**（恢复确认、复盘改进）。
- **预案最大的失效原因**：**写在文档里但没人演练**。**每半年演练一次恢复预案，每季度演练一次应急响应流程**是最低要求。
- 记忆口诀：「可用性=MTBF/(MTBF+MTTR)，三杠杆：多不坏、快恢复、不扩散；MTTR 四段发现响应定位恢复，定位最长是重点；五手段冗余容错预防隔离演练；人的单点最难防；BIA 是 BCP 前提；预案不演练等于没有」

### 5. 运维外包与服务商管理

定义：运维外包是将部分或全部运维服务委托给第三方服务商，通过合同（外包合同 / UC 支撑合同 / SOW）约定服务范围、质量标准、考核机制与责任边界，实现专业能力与资源的外部获取。

关键要点：
- **外包三类型**：**整体外包**（全部运维交由一家，权责清晰但风险集中）、**部分外包**（基础运维外包、核心系统自运维，平衡成本与控制力）、**混合模式**（日常运维外包 + 核心系统/架构/安全自控）。**政务与关键业务系统推荐混合模式**——核心数据、架构决策、安全防护不能外包。
- **SOW（Statement of Work，工作说明书）**：明确服务范围（做什么/不做什么）、服务时间、交付物清单、人员要求（资质、数量、驻场比例）、响应与解决时限、考核指标、**服务边界与例外情形**、变更流程。**SOW 写不清，后续争议无解**。
- **UC（Underlying Contract，支撑合同）**：与上层 SLA 配套，用于向第三方供应商购买服务以支撑 SLA 达成。**SLA 承诺必须能通过 UC 向上传导**，否则等于凭空承诺。
- **服务商选择五维度**：**技术能力**（同类项目经验、资质证书如 ITSS、信息安全资质）、**服务能力**（响应速度、驻场能力、备件保障）、**价格**（不只是报价低，要看全生命周期成本与隐性成本）、**信誉与案例**（客户评价、同行业口碑、历史履约）、**风险**（财务稳定性、人员稳定性、是否有外包商转包）。
- **人员管理要求**：**关键岗位人员更换须经甲方书面同意**、**人员到岗率考核**（如驻场要求 5×8、关键时段需在岗）、**背景审查**（涉及政务数据的岗位需签保密协议）、**交接管理**（人员离职时须完整交接并经甲方确认）。
- **挂靠与转包风险**：部分服务商为压低成本，实际由个人或小团队挂靠资质承接，或层层转包。**识别方法**：核对实际运维人员是否与服务商劳动合同一致（可在社保记录中验证）、社保缴纳人数与报价规模是否匹配。**核心业务系统应要求"人岗合一"，不接受挂靠**。
- **外包考核四维**：**服务质量**（SLA 达成率、缺陷率）、**响应速度**（到场时间、工单响应）、**人员稳定**（人员流动率、关键岗位到岗率）、**协作配合**（问题配合度、文档提供及时性、报告质量）。
- **外包的风险控制四条**：① **权限分离**（外包人员只授予完成工作所需的最小权限，不授予生产环境 root、不授予数据库超级管理员）；② **操作留痕**（所有操作经堡垒机审计、关键操作双人复核）；③ **数据不出域**（敏感数据不出境、不外包，涉及个人信息的处理须符合个保法要求）；④ **可替换性**（合同中保留更换服务商的权利、不锁定长期独家）。
- **成本核算**：外包总成本 = 服务费 + 管理成本（甲方投入的管理人力）+ 风险成本（故障导致的业务损失 + 应急处置成本）+ 切换成本（更换服务商的迁移成本）。**只看服务费的低价外包，往往总成本更高**。
- 记忆口诀：「外包三型整体/部分/混合，核心系统不外包；SOW 定范围 UC 传承诺，SLA 必须能向上传；选服务商看技术服务价格信誉风险五维；挂靠识别看社保人岗合一；外包四控：权限分离、操作留痕、数据不出域、保留可替换；总成本还要算管理与切换成本」

## 案例分析题

**题目**：某市政务云运维中心负责全市 68 个市级政务系统的运行维护，运维团队 26 人，服务内容包括基础设施、数据库、中间件、网络、安全、应用支撑六类运维。原运维模式存在以下问题，后经运维体系重构：

（1）**事件管理混乱**：某月监测发现全市政务系统月均事件 1.8 万件，其中**重复性事件（同类问题反复发生）占比 62%**。日常处理中，**约 40% 的事件通过电话或微信群直接处理，未走工单系统**，导致事件记录缺失、无法统计、无法分析规律。同一类"数据库连接池溢出"事件半年内发生 47 次，每次均由值班人员重启应用解决，从未启动问题管理。

（2）**SLA 考核形同虚设**：年初与各委办局签订 SLA，承诺核心系统可用性 99.9%、P1 事件 30 分钟响应、4 小时解决。但中心**无自动化的可用性统计手段**，服务报告全部靠人工估算。一次 P1 事件（某社保系统不可用 6 小时 20 分钟）发生后，委办局要求按 SLA 扣减服务费并出具不可用时间认定依据，双方僵持 3 周。**因无监控数据，中心最终被迫让步扣减费用 2.8 万元。**

（3）**变更失控**：某次开发人员为解决数据同步慢的问题，**直接在生产环境修改了数据库连接池参数并重启服务，未提交任何变更申请**。修改后 10 分钟内，5 个关联系统相继连接失败，**业务中断 3 小时 40 分钟**，恢复过程中因无人知道原来的参数值，只能从备份中还原，损失严重。事后追责发现，该开发人员入职 8 个月，从未接受过变更管理培训。

（4）**CMDB 形同虚设**：中心曾投入 3 个月建设 CMDB，录入服务器 320 台、网络设备 86 台。但**应用系统之间的依赖关系完全没有录入**，设备变更后也无更新。一年后评估，CMDB 准确率仅 51%。运维人员反馈："查配置项还不如直接 ssh 上去看。"运维主管承认："没人用，就没人维护，最后就放弃了。"

（5）**外包管理失控**：中心将 12 个非核心系统的日常运维外包给某服务商，合同约定驻场 2 人。但实际长期只有 1 人，且频繁更换（6 个月内更换 4 人）。**2026 年 4 月审计发现，该服务商的 2 名运维人员与 5 名运维人员同时在另一家中标项目中任职，存在违规兼职；且部分核心数据库操作未通过堡垒机审计，存在操作不可追溯风险。**此外，服务商用 X 月未通过正式工单系统，直接操作生产环境，涉及 17 次。

（6）**应急能力缺失**：中心从未开展过故障演练。某次机房空调故障导致核心机房温度升高，运维人员按纸质预案操作，但**预案中的应急联系人是两年前的离职人员，电话全部失效**，最终通过翻纸质档案才找到现任负责人，延误 40 分钟。同年某次数据库故障，因无 CMDB 依赖关系，无法快速判断影响范围，**通知下游系统排查耗时 3 小时**。

**问题：**
1. 针对问题（1），分析事件管理存在的问题，并设计符合问题管理与知识管理要求的改进方案。
2. 针对问题（2），说明 SLA 违约认定的关键前置条件是什么，设计自动化度量与考核机制。
3. 针对问题（3），分析变更失控的根本原因，设计变更管理流程与变更管控铁律。
4. 针对问题（4），分析 CMDB 建设失败的根本原因，给出 CMDB 的价值实现路径与六步建设方案。
5. 针对问题（5），指出外包管理的合规风险并给出处置方案。
6. 针对问题（6），设计应急预案与演练体系，并针对通知下游系统耗时 3 小时的问题给出改进方案。
7. 针对本中心整体情况，给出运维体系重构的总体路线图（分阶段、可落地）。

**参考答案：**

**1. 事件与问题管理改进方案**

**存在的问题：**

- **服务台缺位**：40% 事件通过电话/微信直接处理，无统一受理入口（SPOC 缺失），事件不记录、不统计、不分析。
- **问题管理完全缺位**：62% 重复性事件反映存在大量已知根因未根治，"47 次连接池溢出"是典型——每次都重启解决，从未追问根因。
- **事件无分级**：无优先级判定机制，所有事件走同一处理路径，导致高优先级事件得不到优先响应。
- **无升级机制**：一线解决不了时无明确升级路径与时限，容易"卡住"。
- **无重大事件管理**：重大事件无专职指挥、无定期通报、无复盘。
- **知识库缺失**：每次事件都是新问题，人走经验走，知识无法沉淀。

**改进方案：**

**第一步：建立服务台与统一受理入口（SPOC）**

- 设立**统一服务台**：统一服务热线 + 统一邮箱 + 统一工单系统 + 自助门户，**所有运维请求必须经此入口**。
- **技术手段强制**：① 生产环境运维操作**全部经堡垒机**，未开工单的账号无生产环境权限；② 应用变更通道统一在工单系统中，代码部署必须关联工单号；③ 将"工单登记率"纳入运维人员月度考核（目标 100%）。
- 服务台分层：**5×8 现场服务台** + **7×24 值班热线**（重大故障场景）；一线人员负责受理、分类分级、初步诊断、一线可解决项直接解决（目标 FCR ≥ 60%）。
- **自助服务分流**：建设知识库与自助门户（密码重置、工单进度查询、服务目录申请、服务状态查询），分流低价值工单。

**第二步：事件分级与升级机制**

采用**影响 × 紧急度**双维度矩阵：

| 优先级 | 定义 | 响应时限 | 解决时限 |
|---|---|---|---|
| P1 紧急 | 核心业务系统不可用，影响多委办局业务办理 | 15 分钟 | 4 小时（建立重大事件小组，每 30 分钟通报） |
| P2 高 | 单一重要系统不可用或有临时绕行方案 | 30 分钟 | 8 小时 |
| P3 中 | 一般功能异常，业务可继续 | 2 小时 | 3 个工作日 |
| P4 低 | 咨询类、请求类、外观性问题 | 1 个工作日 | 约定时限内 |

- **升级双机制**：**功能性升级**（一线→二线专业组→三线厂商/研发，按技术能力横向转派）；**层次性升级**（P1/P2 自动上报中心领导与相关委办局联系人；P1 超 2 小时未恢复上报主管，超 4 小时上报分管领导并启动应急预案）。
- **重大事件管理**：指定重大事件经理、建立专用沟通群、**定时通报（即使无进展也要通报）**、恢复后 5 个工作日内完成复盘报告（时间线、根因、影响、改进项）。

**第三步：启动问题管理（针对 62% 重复性事件）**

- **问题识别触发规则（自动化）**：① 同一类事件 **30 天内发生 ≥3 次**自动生成问题单；② 任一 P1/P2 事件自动生成问题单；③ 重大事件复盘发现的根因自动生成问题单；④ 支持人工提出。
- **根因分析（以"连接池溢出 47 次"为例）**：
  - 5Why 追问：为什么连接池溢出？→ 连接未释放 → 某批查询未关闭 Statement → 代码缺少 try-with-resources → **无代码规范与静态扫描门禁**；
  - 六维排查（人机料法环测）：代码缺陷（人/法）、连接池配置不合理（机/料）、SQL 执行效率低（料）、缺少监控告警（法）、无自动化巡检（环）。
  - **根因定论：开发规范缺失 + 无静态扫描门禁 + 连接泄漏监控缺失**。
- **变通方案与已知错误登记**：短期内提供"连接池溢出先扩容再重启"等变通方案，并将问题登记为**已知错误（Known Error）**，录入知识库供一线快速处置。
- **永久解决方案（走变更管理）**：整改存量代码 + 引入静态扫描门禁（SonarQube 检查未关闭资源）+ 调整连接池参数 + 上线连接泄漏监控告警。**实施后关闭问题单并观察 30 天，确认未复发**。

**第四步：建设知识库与经验沉淀**

- **三类内容**：① 操作手册（How-to）；② 故障处置卡片（按错误码/现象索引的 SOP）；③ 常见问题 FAQ（面向业务人员）。
- **沉淀机制**：**事件关闭前必须判断是否可沉淀为知识条目**（强制项）；问题解决、变更实施、项目交付均须沉淀。
- **知识审核**：设知识审核人（资深二线工程师），每季度评审有效性，过期条目下架。
- **知识联动**：工单受理时系统自动推荐相似知识条目（降低一线处理难度）；将知识贡献（有效条目数、被引用次数）纳入绩效加分。
- **度量指标**：知识复用率、自助解决率、**同类事件重复发生率（目标从 62% 降至 30% 以下）**。

**2. SLA 违约认定前置条件与自动化度量机制**

**违约认定的关键前置条件（本案僵持的根本原因）：**

- **可用性必须可量化测量**：SLA 违约认定的第一步是"证明确实没达标"，而"证明"的唯一有效方式是**监控系统自动采集的原始数据**。本案无自动化统计手段，意味着中心**在争议中天然处于举证不能的劣势**。
- **"不可用"的定义必须明确且可测量**：
  - 判定标准：如"连续 3 次调用失败"、"单次请求超过 30 秒"、"健康检查连续 2 个探测周期失败"；
  - **计划内停机窗口是否计入不可用时间**（须在 SLA 中明确排除）；
  - **不可抗力/第三方依赖导致的不可用如何认定**（如省级平台故障导致的不可用，是否计为承运方违约）；
  - **判定主体**：以承运方监控系统数据为准，还是以第三方监测为准。
- **责任归属规则**：必须区分**承运方原因**（自身系统故障）、**甲方原因**（业务方操作失误、变更需求）、**第三方原因**（云厂商、网络运营商、上级平台）。**不同原因的处理方式不同（违约扣款 vs 不计违约 vs 免责）**。
- **测量口径与数据留存**：采样频率（建议 1 分钟）、数据来源、留存期限（不少于 SLA 有效期）、**双方均可访问的原始数据查询入口**。

**自动化度量与考核机制设计：**

**第一步：建设可用性监控（技术底座）**

- 部署 **APM + 综合监控平台**（Zabbix/Prometheus + SkyWalking/听云 + 日志平台）：
  - **拨测探针**：对每个核心业务入口每 1 分钟发起探测（不只是探活，须走真实业务链路），记录成功率与响应时间；
  - **端到端可用性**：以"业务办理成功率"而非"进程存活率"为准；
  - **数据留存**：原始监控数据留存不少于 12 个月，满足争议追溯需要。
- **服务台系统打通**：工单系统、监控系统、配置管理系统（CMDB）三者打通，事件自动关联到具体 CI。

**第二步：SLA 指标自动计算**

在监控平台建立 SLA 计算看板（按月自动生成）：

| 指标 | 计算方式 | 数据来源 |
|---|---|---|
| 可用性 | (服务时间 − 不可用时间)/ 服务时间 | 拨测探针 + 告警记录 |
| 响应及时率 | 响应时长 ≤ SLA 时限的事件数 / 总事件数 | 工单系统时间戳 |
| 解决及时率 | 解决时长 ≤ SLA 时限的事件数 / 总事件数 | 工单系统时间戳 |
| 一次解决率 FCR | 一线直接关闭的事件数 / 总事件数 | 工单系统 |
| 重大故障数 | P1 事件数 | 工单系统 + 告警 |
| 满意度 | 关闭后回访评分均值 | 工单系统回访 |

**数据不可人工修改**：指标数据由系统自动生成，运维中心内部无权修改，确保对外披露数据的可信性。**这是避免"扯皮"的根本手段——用自动化数据取代人工估算**。

**第三步：服务报告与考核机制**

- **月度服务报告**（系统自动生成 + 人工补充分析）：各项指标达成情况、未达标项原因分析、改进计划、趋势对比；**报告数据直接引用监控看板，不可手工修改数字**。
- **季度服务评审会**：与各委办局共同复盘 SLA 达成、澄清争议、确认改进项。
- **考核与违约处理**：
  - 扣减规则前置写入 SLA：如"可用性每低于承诺值 0.1% 扣减月度服务费 5%，扣减上限 30%"；
  - **连续 3 个月违约**触发整改流程，整改不力可扣减费用或解除合同；
  - 委办局满意度纳入考核，避免"指标达标但体验差"。
- **争议处理机制预设**：建立争议受理窗口（指定专人对接）、争议处理时限（如 5 个工作日内答复）、争议升级路径；**争议期间以监控原始数据为准，不以口头承诺为准**。

**3. 变更管理流程与铁律**

**根本原因分析（四层）：**

- **管理层面：无变更管理流程落地。** 流程可能存在于制度文件中，但未嵌入技术管控手段，**依赖人员自觉，必然失效**。
- **技术层面：无强制技术管控。** 生产环境可被直接修改，说明：① 堡垒机未强制；② 生产权限授予过宽（开发人员有生产写权限）；③ 配置变更无审批流卡点；④ 无变更窗口限制。
- **人员层面：培训缺失。** 该开发人员入职 8 个月未接受变更管理培训，说明**新员工上岗培训体系存在漏洞**，且未考核变更管理知识。
- **流程层面：变更风险未分级。** 若数据库参数变更被识别为高风险操作，必须走完整流程 + 备份 + 回滚预案 + 演练，就不会出现此次事故。

**变更管理流程（七步）：**

1. **提出变更申请（RFC）**：任何生产环境变更（配置、代码、数据库、网络、参数）必须提交书面申请，内容含变更内容、原因、影响范围、实施窗口、验证方法、**回滚方案**。
2. **分类与分级**：按标准/常规/紧急三类，按影响与风险分四级。
3. **变更评估**：评估技术可行性、业务影响、风险等级、资源需求、**依赖影响（结合 CMDB 分析受影响的 CI 与上下游系统）**、回滚可行性。
4. **变更授权**：常规变更由 CAB（变更咨询委员会，含运维负责人、开发负责人、安全负责人、业务代表）审批；标准变更预授权；**紧急变更由 ECAB 30 分钟内快速审批**。
5. **变更计划与准备**：确认变更窗口（核心系统仅允许 0:00–4:00）、备份数据与配置、**准备回滚脚本并验证可用**、通知相关方。
6. **变更实施与验证**：按方案实施 → 实施后立即验证（功能 + 性能 + 关键业务链路）→ 全程有人值守，**观察至少一个业务高峰周期**。
7. **变更关闭与回顾**：更新 CMDB、记录结果（成功/失败/回滚）、评估目标达成、**重大变更须复盘**。

**变更分级标准：**

| 级别 | 定义 | 审批 | 窗口与演练 |
|---|---|---|---|
| 一级 重大 | 影响多系统或架构调整、回滚难度高 | CAB + 高层批准 | 业务低峰期/节假日，**实施前必须演练** |
| 二级 重要 | 影响单一核心系统、可能中断服务 | CAB 审批 | 标准窗口，**必须有回滚方案** |
| 三级 一般 | 影响非核心系统或局部功能 | 运维负责人审批 | 常规窗口，登记备案 |
| 四级 标准 | 预授权低风险标准化操作 | 免审批，按 SOP 执行 | 事后登记 |

**变更管控四条铁律（技术强制，非仅制度）：**

1. **无回滚方案不实施**：工单系统中变更申请无回滚方案字段则无法提交，CAB 审批时不通过则无法排期。
2. **生产环境不直改**：
   - 堡垒机强制登录，**未关联工单号的操作无法登录生产环境**（技术卡点，非口头约束）；
   - 生产环境权限最小化，**开发人员不授予生产写权限**，需要时走临时授权（限时、留痕）；
   - 数据库修改必须通过审批后的工单执行，禁止本地客户端直连生产库。
3. **变更窗口外不做一二级变更**：技术层面在窗口外限制生产变更通道；数据库参数类变更强制在窗口内。
4. **变完必须更新 CMDB**：变更单中"CMDB 更新"为必填项，未更新则变更单无法关闭。

**配套管理措施：**

- **变更成功率与回滚率纳入考核**（目标成功率 ≥95%，回滚率过高说明变更质量差）。
- **新员工上岗必修变更管理培训**（纳入入职培训清单并考核）。
- **变更窗口日历公开**（每月提前公布，便于业务方安排）。
- **紧急变更必须事后补全记录并在 5 个工作日内复盘**（防止紧急通道被滥用）。

**4. CMDB 建设失败原因与价值实现路径**

**根本原因（三条，核心是最后一条）：**

- **范围过大、目标不清**：试图一次性建成"全量完整"的 CMDB，投入 3 个月录入 400 多台设备就停了。CMDB 是**持续运营的资产，不是一次性工程**，一次性全量必败。
- **脱离运维工作流**：CMDB 独立于工单与变更流程之外，运维人员日常操作不需要查 CMDB，**自然不会维护它**。准确率 51% 的根因是"录入后无人更新"。
- **价值未被证明（最根本）**：运维主管一句"没人用就没人维护"点破了本质。**CMDB 若不能嵌入高频运维场景（故障定位、变更影响评估），就只是一张没人看的资产表**。缺的是"用起来"的理由，不是"录全"的功夫。

**价值实现路径（先证明价值，再补数据）：**

- **切入点选择：从高频刚需场景切入，而非追求完整性。**先做"故障影响分析"和"变更影响评估"两个场景——**这两个场景每天都在发生，CMDB 的价值能被直接感知**。
- **让运维人员在工作中"顺手"维护**：① 变更单中增加"选择受影响 CI 并自动更新关联关系"的步骤（自动化采集而非手工录入）；② 故障工单关闭时系统自动记录本次涉及的 CI，**把维护工作嵌进已有流程，不新增动作**。
- **用准确率而非数量考核**：CMDB 的 KPI 应是"故障定位平均耗时""变更影响分析准确率"，**不是"录入了多少条 CI"**。
- **先覆盖核心再做全量**：首批只做支撑核心业务的关键链条（如认证服务 → 数据库 → 缓存 → 网关，约 100~200 个 CI），**做到 95% 准确率并被日常使用后，再逐步扩展**。

**CMDB 六步建设方案（按序执行）：**

1. **界定范围与分级**：按业务重要性分级，**首批只纳入支撑核心业务（认证、支付、审批主流程）的服务器、数据库、中间件、核心应用及其直接依赖，约 500~800 个 CI**；明确不在本期的范围（测试环境、非核心系统），避免范围蔓延。
2. **设计数据模型**：定义 CI 类型（硬件/软件/文档/环境合约）与关系类型（依赖、部署于、连接、使用、支撑）；每个 CI 必填字段：名称、类型、责任人、位置、版本号、生命周期状态、SLA 等级、关联合同。**关系数据比 CI 数据更重要**——本案的致命问题正是"应用之间依赖关系完全没有录入"。
3. **数据采集与初始化**：① 自动发现（网络扫描、Agent 采集、云 API 拉取资源清单）获取硬件与云资源；② 人工核对补充**应用间依赖关系**（通过调用链分析、服务清单梳理、开发者访谈）；③ 首次导入后立即做一次完整性评审，确认核心链条无缺失。
4. **嵌入变更流程（最关键一步）**：**变更单中"CMDB 更新"设为必填项，未更新则变更单无法关闭**；提供自动化采集接口（如部署后自动同步服务 IP、端口、依赖），减少手工负担；**这是保证 CMDB 长期准确的唯一有效机制**。
5. **定期校正与审计**：① 每周运行自动发现与 CMDB 现有数据比对，输出差异报告并指派责任人修正（目标准确率 ≥95%）；② 每季度开展配置审计，抽样核对实物与记录（尤其高价值 CI 如核心数据库）；③ 每次重大故障后复盘 CMDB 是否支撑了快速定位。
6. **明确组织责任**：设立**配置管理员**（专职或兼职岗），各域设**配置责任人**；明确"**谁变更、谁更新**"原则；将 CMDB 准确率纳入运维团队季度考核；配置管理员有权拒绝未更新 CMDB 的变更单关闭。

**5. 外包管理合规风险与处置方案**

**识别出的合规风险（四类）：**

- **人员违规兼职风险**：审计发现服务商 2 名运维人员同时在另一家中标项目任职。这意味着① 同一批人员在多个项目间分配精力，**驻场承诺无法兑现**（合同约定 2 人实际长期 1 人）；② 存在**潜在的利益冲突与信息隔离风险**，涉密政务数据在多个项目间流转可能失控。
- **操作不可追溯风险**：部分核心数据库操作未通过堡垒机审计。**这是最严重的合规缺陷**——核心数据操作无留痕，一旦发生数据被篡改或泄露事件，无法追责，违反《网络安全法》日志留存要求与等保 2.0 的审计要求（审计日志留存不少于 6 个月）。
- **绕过工单直接操作生产环境**：X 月内 17 次直接操作生产环境，未走正式工单系统。这既规避了变更管控（无审批、无回滚、无记录），也使 SLA 数据失真（事件未登记，导致响应及时率统计失真）。
- **资质与实际履约不符**：合同承诺 2 人驻场、6 个月换 4 人，**实际到岗率仅 50%**，属于**未按合同履约**，业主方可据此主张违约金或解除合同。

**处置方案（五步）：**

- **第一步：立即止损（24 小时内）**
  - **冻结违规人员操作权限**：立即暂停上述 2 名违规兼职人员在政务云生产环境的全部权限，要求服务商提交书面说明与整改承诺；
  - **强制堡垒机接入**：立即关闭所有服务商的直连通道，**所有生产操作必须经堡垒机 + 工单双认证**，无工单号无法登录；
  - **开展全量审计**：对服务商近 6 个月所有生产环境操作做完整审计回溯，重点核查核心数据库操作、数据导出、权限变更三类高风险行为，识别是否存在未授权操作或数据外传。

- **第二步：合规性核查与责任认定**
  - 核查服务商与另一项目的中标合同，确认是否存在违反招标投标法第三十二条（**同一单位或个人不得同时在同一项目中承担两个标段；也不得以他人名义投标或允许他人以本企业名义投标**）或构成**挂靠出借资质**的情形；
  - 若认定为**出借资质/违规转包**，依据《招标投标法》第五十八 条与合同约定，业主方有权**解除合同并追究违约责任、索赔损失**；
  - 明确违规人员在本项目中的具体操作记录，评估数据安全影响，必要时按规定向主管部门报告。

- **第三步：合同处置**
  - 依据合同违约条款（驻场人数不足、未经审批操作生产环境）发出**书面整改通知**，要求限期整改；
  - 若整改不到位或存在继续违规，**依据合同约定解除合同**，并按"服务费扣减 + 违约赔偿"方式处理；
  - 追究已发生的实际损失（因无审计导致的排查成本、因操作失误导致的业务损失）；
  - **重新招标或启用备选服务商**，过渡期由中心人员临时接管 12 个系统的运维。

- **第四步：新服务商重新准入（治本）**
  - **资质核查**：要求提供 ITSS 等资质证书原件，通过住建部四库一平台核验资质真实性与有效期；**要求提供社保缴纳证明，核对投标人员是否为本单位在职员工**（本案的核心教训）；
  - **人员锁定**：关键岗位人员名单在合同中列明，**更换须经甲方书面同意**，人员到岗率纳入月度考核（低于 90% 扣减服务费）；
  - **技术管控强制写入合同**：① 生产环境必须经堡垒机 + 工单双通道；② 禁止本地客户端直连生产数据库；③ 核心数据库操作须双人复核；④ 全部操作日志留存不少于 6 个月并可随时提供给业主审计；
  - **违约与退出条款**：明确挂靠、转包、违规兼职为**禁止性违约**，业主方有权立即解除合同且不支付违约金；保留更换服务商的权利，不锁定长期独家。

- **第五步：完善外包管理制度**
  - 建立**外包服务商风险台账**（资质、履约、违规记录、风险等级），每半年复评；
  - 建立**外包人员合规承诺机制**（无兼职、无利益冲突、保密协议、违规处罚条款）；
  - **权限最小化原则落地**：外包人员只授予完成工作所需的最小权限，不授予 root 与数据库超级管理员，**核心数据访问须逐次审批**；
  - **定期审计**：每季度对服务商开展合规审计，重点核查人员稳定性、操作留痕、数据安全。

**6. 应急预案与演练体系设计**

**现有预案的失效原因：**

- **联系人失效**：预案中应急联系人是两年前离职人员，说明**预案未随人员变动更新**。预案的有效期本质上是"到下次修订为止"，人员离职、机构调整、联系方式变化都应触发预案修订。
- **无演练**：从未演练意味着预案中的流程、联系方式、备份数据可用性、资源准备均未经验证。**未演练的预案不能证明其有效，只能证明其存在**。

**应急预案体系设计（六要素全覆盖）：**

- **触发条件（量化）**：明确到什么程度启动预案。如"核心机房温度连续 5 分钟超过 35℃"、"核心系统连续 10 分钟不可用"、"数据库主库故障超过 15 分钟未恢复"。**模糊的触发条件会导致该启动时不敢启动、不该启动时乱启动**。
- **响应团队（角色明确）**：设立**应急指挥（1 人，中心负责人）、技术处置组（2~3 人，资深运维）、业务联络人（1~2 人，对接委办局）、记录员（1 人）**；每个角色设 A/B 角（A 角为主、B 角为备份），**A/B 角名单每月核对在岗状态**。
- **处置步骤（checklist 化）**：把处置动作拆成可勾选的清单，每步明确操作人、验证方法、预期结果。**关键动作前置化**（如"切备用电源"而非"处理供电问题"）。
- **资源准备**：备用设备清单（服务器、交换机、存储、电源）、备件库存位置、备用机房/容灾环境可用性、**第三方联系方式（云厂商、运营商、设备厂商售后）并每季度验证有效性**。
- **对外沟通**：明确通知渠道（应急群、电话、短信）、**通知对象清单**（委办局联系人、上级主管部门）、**通报频次**（P1 每 30 分钟通报一次，即使无进展）、通报模板（当前状态、影响范围、已采取措施、下次通报时间）。
- **恢复与总结**：恢复确认标准（业务验证通过 + 业务方确认）、复盘报告要求（时间线、根因、影响、改进项、责任人、完成时限）。

**演练体系设计：**

- **演练类型四层**：
  - **桌面推演**（季度级）：不实际动手，只走流程讨论，检验预案逻辑与角色分工；成本最低，可发现流程漏洞；
  - **模拟演练**（半年级）：模拟场景但不真正破坏（如模拟"数据库故障"但用测试环境），检验响应速度与协调能力；
  - **技术演练**（半年级）：实际执行部分技术动作（如手动切换主备、恢复备份），检验技术可行性；
  - **实战演练**（年度级）：在预发环境完整注入故障（如断电、断网、删库），全流程验证，**这是唯一能真正发现问题的演练方式**。
- **演练计划**：年度演练日历（明确每季度做什么）、场景清单（覆盖机房故障、数据库故障、网络中断、外部依赖不可用、数据恢复、人员缺位六类）、**每次演练必须有评估表**（目标达成度、问题清单、改进项与责任人）。
- **演练纪律**：**演练必须真实**（不可提前"走过场"）；演练前必须验证回滚方案；**演练后 5 个工作日内出复盘报告并跟踪改进项闭环**；**改进项未闭环的，下一年度演练优先级提升**。
- **预案维护机制**：**触发式修订**（人员变动、机构调整、架构变更、演练发现漏洞时立即修订）+ **定期评审**（每半年评审一次，修订后重新发布并回收旧版本，确保现场用的是最新版）。

**针对"通知下游系统排查耗时 3 小时"的改进：**

根因是**无 CMDB 依赖关系，数据库故障时无法快速判断哪些下游系统受影响**。改进措施：

- **第一步：补全核心系统依赖关系（本项最优先）**：立即梳理核心数据库的**直接调用方与间接调用方**（通过应用配置文件中的数据源配置、日志中的连接记录、开发者访谈三路交叉确认），形成"数据库 → 应用 → 下游接口"的完整依赖链，第一阶段先覆盖核心业务（认证、审批、支付）。
- **第二步：建立依赖关系可视化**：引入 CMDB 的关系模型，用拓扑图展示"某数据库故障会影响哪些应用、哪些业务"。**故障发生后，值班人员直接查图，5 分钟内确定影响范围**，替代原来的人工逐个询问。
- **第三步：故障影响自动分析**：在监控平台配置告警联动规则——**数据库告警触发时，自动按依赖图列出受影响的上下游系统清单**，并通过工单系统自动向各系统责任人推送"请检查本系统是否受影响"的通知（**从"人找人"变为"系统找人"**）。
- **第四步：影响确认与升级**：各下游系统责任人收到通知后 30 分钟内反馈"受影响/不受影响"，超时未反馈自动升级至其上级。这样**通知与确认的耗时从 3 小时压缩到 30 分钟以内**。
- **第五步：常态化维护**：依赖关系纳入 CMDB 六步建设（第 2 步设计模型、第 4 步嵌入变更流程），并每季度做一次依赖关系复核（架构调整后依赖必然变化，**依赖图不更新等于失效**）。

**7. 运维体系重构总体路线图（四阶段，18 个月）**

**阶段一：止血与建制度（第 1–3 月）— 先让"错的事做不出来"**

- 强制技术卡点上线：堡垒机 + 工单双通道（**不改流程，先卡住最危险的动作**）；
- 外包违规处置与合同清理（完成第五问的处置方案）；
- 建立变更管理七步流程与四级分级（**先流程后系统**）；
- 明确不可抗力判定标准、"不可用"定义、扣减规则等 SLA 前置条款，完成与委办局的 SLA 补充协议签署；
- **阶段目标**：生产环境直接操作降为 0，SLA 争议有据可依。

**阶段二：建能力（第 4–9 月）— 让"该做的事有工具支撑"**

- 部署可用性监控与拨测探针（**解决 SLA 无法举证的根本问题**），SLA 看板上线；
- 部署工单系统 + 服务台，统一受理入口，**强制工单登记率纳入考核**；
- 事件分级、升级机制、重大事件管理流程落地并演练一次；
- CMDB 第一批建设（核心链条 500~800 个 CI，重点是**应用间依赖关系**），准确率目标 ≥90%；
- 应急预案体系重写并完成一次桌面推演；
- **阶段目标**：SLA 指标全部自动可取、工单登记率 ≥95%、CMDB 首批可用。

**阶段三：转闭环（第 10–15 月）— 让"问题被根治"**

- 问题管理正式运行：触发规则自动化（同事件 30 天内 ≥3 次自动建单），**重复性事件率从 62% 降至 30% 以下**；
- 知识库上线并与工单联动（受理时推荐相似知识），一线自助解决率提升；
- CMDB 嵌入变更流程（**变完必更新成为技术强制**），依赖图可视化，故障影响自动分析上线；
- CMDB 准确率提升至 ≥95%，覆盖范围扩展至全部核心系统；
- 完成两次技术演练（数据库故障切换、机房断电）；
- **阶段目标**：问题管理产生实效，重复事件率达标，故障定位与影响分析耗时下降 70% 以上。

**阶段四：上水平（第 16–18 月）— 让"能力可持续"**

- 引入 ITSM 成熟度评估，对照标准识别差距并持续改进；
- 建立运维知识库与经验教训库（OPA），**新人上手周期从 2–3 个月降至 2 周以内**；
- 关键岗位"人的单点"治理（AB 角、交叉培训、值班轮换）；
- 成本与服务价值度量体系（单位事件成本、SLA 达成趋势、满意度趋势纳入管理层看板）；
- 完成一次实战演练与年度服务评审，输出次年改进计划。
- **阶段目标**：运维从"救火"转向"预防"，形成可持续改进机制。

**路线图的三条执行原则：**

1. **技术卡点优先于制度约束**：每一条管理要求都应有对应的技术强制手段（未开工单无权限、未更新 CMDB 无法关闭变更单），**纯制度约束在运维场景下必然失效**。
2. **先证明价值再补数据**：CMDB、知识库等资产都从高频刚需场景切入，**用"故障定位更快""影响分析更准"证明价值，而不是用"录入了多少条"**。
3. **指标驱动而非任务驱动**：每个阶段设定可量化的阶段目标（工单登记率、CMDB 准确率、重复事件率、SLA 达标率），**每季度对照复盘，未达标则调整而非掩盖**。

**踩分要点：**
- 第 1 问须覆盖服务台缺位、问题管理缺位、无分级、无升级、无重大事件管理、知识库缺失六项问题，改进方案须含 SPOC 建设、P1~P4 分级矩阵、双升级机制、问题识别触发规则、5Why 根因分析实例、三类知识库。
- 第 2 问须明确"可用性必须可量化测量、不可用定义、责任归属、数据留存"四个前置条件，度量机制须强调**数据由系统自动生成、内部无权修改**。
- 第 3 问须从管理/技术/人员/流程四层分析根因，四条铁律必须写成**技术强制手段**而非制度条文（如"未关联工单号无法登录生产环境"）。
- 第 4 问须指出根本原因是"价值未被证明、脱离工作流"，六步方案须强调**第 4 步嵌入变更流程是长期准确的唯一有效机制**。
- 第 5 问须识别人员违规兼职、操作不可追溯、绕过工单、资质履约不符四类风险，处置须覆盖止损、核查认定、合同处置、重新准入、制度完善五步，并写明**社保缴纳证明核验**这一具体手段。
- 第 6 问须覆盖预案六要素、四层演练、预案维护机制；影响分析改进须写出**依赖关系补全 + 可视化 + 自动推送 + 30 分钟确认时限**的具体设计。
- 第 7 问须分四阶段给出可落地的路线图，每阶段有量化目标，并提炼三条执行原则。

## 记忆口诀

**SLA 与考核**
SLA 三层：业务层（对用户）/ 系统层（对组件）/ 第三方（对供应商）
OLA 是内部承诺，SLA 的内部支撑
可用性 = (服务时间 − 不可用时间) / 服务时间
不可用定义必须先写清，否则违约扯皮
99.9 年停 8.76 小时 / 99.99 年停 52.6 分钟 / 99.999 年停 5.26 分钟
SLO 严于 SLA 留缓冲；扣减上限必须写进合同
考核七指标：可用性、响应及时、解决及时、FCR、闭环率、满意度、重大故障数

**事件与问题**
事件救火求快恢复，问题防火求除根因
优先级 = 影响 × 紧急度，P1~P4 四级
升级双机制：功能性（转技术组）+ 层次性（要权限资源）
重大事件五要素：定指挥、建群、定时通报（无进展也报）、启动预案、五日内复盘
问题触发：同事件 30 天内 ≥3 次自动建单
五问法连追根因；变通恢复 + 永久根治两套方案
知识库三类：操作手册 / 处置卡片 / FAQ；事件关闭前必须判断可否沉淀
重复事件率 62% → 30% 以下，是问题管理见效的标志

**变更与配置**
变更七步：申请 → 分类分级 → 评估 → 授权 → 计划 → 实施验证 → 关闭回顾
三类型：标准（预授权）/ 常规（CAB）/ 紧急（ECAB，事后补记录）
四级：重大 / 重要 / 一般 / 标准，窗口与演练要求不同
四条铁律：无回滚不实施、生产不直改、窗口外不做一二级、变完必更 CMDB
CMDB 六步：定范围 → 建模型 → 采数据 → 联变更 → 用审计 → 设专人
**嵌入变更流程是长期准确的唯一有效机制**
CMDB 价值三用途：故障影响分析 / 变更影响评估 / 资产审计

**可用性与连续性**
可用性 = MTBF / (MTBF + MTTR)
三杠杆：多不坏（MTBF↑）、快恢复（MTTR↓）、不扩散（隔离）
MTTR 四段：发现 / 响应 / 定位 / 恢复；定位最长是重点
五手段：冗余、容错、预防、隔离、演练
恢复分级：冷备（小时）→ 温备（分钟）→ 热备双活（秒级）
BIA 是 BCP 的前提；预案六要素；不演练的预案等于没有预案
单点排查别忘"人的单点"——最难防也最重要

**外包管理**
三类型：整体 / 部分 / 混合；核心系统不外包
SOW 定范围，UC 向上传承诺；SLA 必须能通过 UC 传导
选服务商五维：技术 / 服务 / 价格 / 信誉 / 风险
挂靠识别：查社保缴纳，人岗合一
四控：权限分离 / 操作留痕 / 数据不出域 / 保留可替换
总成本 = 服务费 + 管理成本 + 风险成本 + 切换成本
