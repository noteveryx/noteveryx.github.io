## 今日核心概念

### 1. 性能指标体系与SLO（服务级别目标）

定义：性能指标体系是对系统运行效率与服务质量进行量化描述的一组度量约定；SLO（Service Level Objective，服务级别目标）是面向使用者可感知体验的、可内部量化考核的性能目标值，是把技术指标翻译为服务质量承诺的桥梁。

关键要点：
- **四大类核心指标**：
  - 响应时间（RT）：端到端耗时，常用**平均值**与**百分位**（P90/P95/P99）双重刻画。**平均值会掩盖长尾**，对外承诺必须用 P95/P99，不能只报平均。
  - 吞吐量（Throughput）：单位时间完成的请求数/事务数（TPS、QPS），反映系统处理能力上限。
  - 并发数（Concurrency）：同时在途的请求数/在线用户数，与吞吐量共同构成负载模型。
  - 错误率（Error Rate）：失败请求占比，区分应用错误（4xx/5xx）、超时错误、依赖服务错误。
- **资源类辅助指标**：CPU 利用率、内存使用率与换页率、磁盘 I/O 利用率与 IOPS/吞吐、网络带宽与重传率、连接池占用数、线程池/队列长度、GC 频率与停顿时长。资源利用率**不能单独作为性能结论**，高利用率未必是瓶颈，低利用率也可能存在串行等待。
- **指标分层**：端到端（用户感知）→ 服务/接口层 → 组件层（应用、数据库、中间件）→ 资源层（主机、网络、存储）。分层目的是**定位问题落在哪一层**，避免"一上来就加服务器"。
- **SLO 与 SLA 的关系**：SLA 是对外合同承诺（有法律约束、含罚则），SLO 是内部目标（通常严于 SLA，如 SLA 99.95% 对应 SLO 99.99%，留出缓冲）。**SLO 是 SLA 的前置指标**，SLO 达成则 SLA 大概率达成。
- **三个"9"法则**：99% ≈ 每年 3.65 天不可用；99.9% ≈ 8.76 小时；99.99% ≈ 52.56 分钟；99.999% ≈ 5.26 分钟。计算式：` downtime = 365 × 24 × (1 - 可用性) `。
- **性能相关 SLA 与罚则**：政务与行业客户通常约定核心接口的 P99 响应时间上限、错误率上限、高峰期可用性下限，并约定**未达标的扣款比例**（常见按月服务费的百分比扣减，封顶比例需在合同中明确）。
- **性能目标必须写明测量口径**：统计时间窗（1 分钟/5 分钟）、样本范围（是否含探针、爬虫、压测流量）、是否剔除异常值、测量点位置（客户端 / 网关 / 应用侧），否则不同团队报出的数字无法对账。
- **性能预算（Performance Budget）**：将端到端响应时间拆解到各层（网关、鉴权、业务服务、数据库、缓存、第三方调用），每层分配额度并作为开发与评审约束，防止"每层都说自己不慢"。

### 2. 性能测试方法与压测模型

定义：性能测试是在特定负载条件下，通过模拟真实或放大的业务请求，采集系统响应与资源指标，评估系统性能是否满足目标并暴露瓶颈点的测试活动。

关键要点：
- **性能测试五种类型**：
  - 基准测试（Baseline）：单用户或小负载，获取各接口的性能基准值，用于对比与回归。
  - 负载测试（Load）：在**预期业务量**下验证是否满足 SLO，负载量一般取预估峰值的 1.0～1.5 倍。
  - 压力测试（Stress）：**逐步加压直到系统崩溃**，找出**极限值**与瓶颈点、失效模式及恢复能力。
  - 稳定性测试（Soak/Endurance）：在中等负载下长时间运行（数小时至数天），暴露内存泄漏、句柄泄漏、日志膨胀、缓存雪崩等**慢性病**。
  - 容量测试（Capacity）：找出在 SLO 约束下的**最大承载用户数/吞吐量**，作为扩容与采购依据。
- **负载模型三要素**：并发用户数、请求到达率（是否等效 Poisson 到达）、思考时间（Think Time，决定压力形态）。
  - **加压模型**：等量等速（阶梯加压）、梯度加压（每 5 分钟加 10% 并发）、峰值脉冲（模拟开闸放水、秒杀、批量任务）、浸泡（7×24）。
  - 政务与行业系统的高峰画像常见：**年初集中申报、医保集中缴费、学费/报名季、季度报表叠加夜间批处理**，压测场景应按真实业务日历设计，而不是只测均匀流量。
- **压测实施七步**：明确业务模型与 SLO → 选择工具（JMeter / Locust / Gatling / k6 / 阿里云PTS）→ 准备压测数据与账号（**注意数据分布要贴近生产，须做脱敏并禁止使用真实敏感数据**）→ 环境确认（配置、拓扑、版本、数据量与生产等比）→ 脚本编排与参数关联 → 执行与监控 → 结果分析与调优复测。
- **关键纪律**：
  - **生产环境压测必须走影子流量/流量镜像**（复制真实请求到影子环境），**禁止在生产直接施压**，除非有完整隔离与熔断预案。
  - 数据量必须**等比放大**（1% 生产数据量压不出索引问题），否则压测结论无效。
  - **缓存预热**与**冷启动**两种场景都要测；含自动扩容的系统必须验证"扩容生效前的降级表现"。
  - 压测结论要包含**瓶颈定位结论**，而不只是"并发到多少开始慢"。
- **测试结果判据**：以 SLO 为红线，不以"没报错"为通过；核心接口 P95/P99 达标、无错误率突增、无资源打满、扩容后性能线性回升。

### 3. 分层瓶颈定位与性能调优

定义：瓶颈定位是自上而下按层次逐级排除、找到限制系统整体吞吐的那个最慢环节的过程；性能调优是针对已确认瓶颈，通过代码、数据、架构、参数、系统配置等手段提升系统性能并通过复测验证的工程活动。

关键要点：
- **分层定位顺序（自上而下，从慢的地方往依赖倒查）**：浏览器/客户端 → 接入层（CDN、负载均衡、网关）→ 应用层（代码逻辑、线程池、锁、GC）→ 中间件（缓存、消息队列、注册中心）→ 数据库（SQL、索引、锁、连接池、慢查询）→ 操作系统（CPU、内存、I/O、网络栈参数） → 物理环境（磁盘、带宽、机柜温度）。
  - **黄金判据：延迟在哪里增长，压力就加在哪一层。** 若 P99 上升而下游依赖调用耗时不变，则问题在本层及之前。
- **常用工具链**：
  - 应用侧：APM 探针（SkyWalking、Elastic APM、阿里 ARMS）、链路追踪 TraceId 贯通、火焰图（Flame Graph）定位热点方法、Arthas/VisualVM/async-profiler 分析线程与 GC、Profiler 找 CPU 与内存热点。
  - 数据库侧：慢查询日志、`EXPLAIN` 执行计划、索引与统计信息、锁等待与死锁图、`performance_schema`/动态性能视图、连接池监控（最大连接数、活跃/空闲连接、超时数）。
  - 系统侧：`top`/`iostat`/`vmstat`/`sar`/`netstat`/`ss`/`free`/`perf`、火焰图、慢日志与内核参数（ulimit、tcp_tw_reuse、somaxconn、文件句柄）。
- **数据库与缓存常见瓶颈**：
  - **慢 SQL**：全表扫描、无索引、索引失效（函数包裹字段、隐式类型转换、前导通配符）、`ORDER BY`/`GROUP BY` 未利用索引产生临时表与排序、大分页 `LIMIT 1000000,20`（可用延迟关联/游标改写）。
  - **锁与并发**：热点行更新、行锁升级表锁、死锁、元数据锁（DDL 阻塞）、长事务持有锁。
  - **连接池**：池过小导致排队等待（表现为接口 RT 上升但 CPU 空闲），池过大打满数据库连接（`max_connections` 耗尽导致其他应用连不上）。
  - **缓存三坑**：**穿透**（查不存在的 key，请求直达库）→ 布隆过滤器/空值缓存；**击穿**（热点 key 过期瞬间大量并发回源）→ 互斥重建/逻辑过期/热点永不过期；**雪崩**（大量 key 同时过期或缓存集群宕机）→ 过期时间加随机抖动/多级缓存/限流降级。
  - **大事务与批量操作**：无分批提交、单事务处理百万行导致锁表与 undo 膨胀，需分批（每批 1000～5000）+ 间隔 + 幂等续跑。
- **应用与运行时调优**：接口聚合与批量化（N+1 查询合并）、异步化与消息队列削峰、缓存预计算、本地缓存（防击穿）、连接池与线程池参数整定、GC 参数与堆内存调整（JVM 堆建议初始=最大避免抖动）、JIT 预热、序列化与压缩、避免同步阻塞 IO。
- **架构级手段**（调优无解时上升一层）：读写分离、分库分表与数据分区、单元化与多活、异步化与最终一致、缓存与计算分离、限流降级与熔断、水平扩容（无状态化是前提）。
- **调优闭环**：**基线采集 → 假设 → 单变量验证 → 复测对比 → 留档（调优前后对照表）**。**禁止多变量同时改**，否则无法归因；每次调优必须复测并把数据写进台账。
- **常见反模式**：凭感觉调参数不采数据、看平均响应时间不看 P99、只看应用不看数据库与内核、压测数据量太小、上线前不回归性能基线、把调优当"一次做完"。

### 4. 容量规划与弹性伸缩

定义：容量规划是基于当前负载、资源消耗与业务增长预测，在满足 SLO 的前提下测算所需资源总量并规划扩容节奏的技术活动；弹性伸缩是资源随负载自动增减的机制。

关键要点：
- **容量规划五步**：
  1. **业务量预测**：确定规划期内的用户数、业务笔数、峰值系数（峰值/均值）、季节性与事件驱动增量（集中申报、普查、换届）。
  2. **单位资源消耗模型**：`所需资源 = (业务量 × 单位业务资源消耗) / 目标利用率`；对数据库常用 `连接数 = 峰值QPS × 平均响应时间(s)`（Little 定律），对应用常用 `实例数 = 峰值QPS / 单实例压测吞吐 × 冗余系数`。
  3. **冗余与安全裕度**：生产环境资源水位长期运行在 **30%～60%**（CPU/内存不超过 70%），保留突发与故障切换空间；**单点（无冗余）资源必须按 N+1 规划**，即故障一个节点仍能承载峰值。
  4. **扩容触发与节奏**：设置阈值（水位 + 持续时长 + 连续次数，防抖动）、预热期、扩容冷却时间、批量上限与成本上限；区分**垂直扩容**（单机加配，升配简单但上限低、有停机风险）与**水平扩容**（加副本/加节点，需无状态化与会话外置）。
  5. **滚动验证**：扩容方案上线后用压测回归验证"扩容后性能线性回升"和"扩容过程中的服务连续性"。
- **容量类型**：计算资源（CPU/内存/GPU）、存储资源（容量与 IOPS 双向规划，**性能与容量是两套账**）、网络资源（带宽与连接数）、数据库连接与实例规格、许可证与授权数量（常被忽视，成为扩容的隐性瓶颈）。
- **关键指标**：容量水位（资源利用率）、冗余度、扩容周期（从触发到就绪的时间）、单位成本（如"每万笔业务成本"）、容量满足率（当前可承载峰值 / 预测峰值）。
- **弹性伸缩策略**：
  - 定时伸缩（按业务日历预知峰值，如每月 1 日、季度末）——**可预知场景首选**。
  - 阈值伸缩（按 CPU/内存/QPS 队列长度）——需设置冷却时间与连续满足次数。
  - 预测伸缩（基于历史曲线预测未来负载）——适合规律性强的政务业务。
  - **优先级与降级链**：资源不足时先扩缓存与只读副本，再扩应用实例，再启用降级接口，最后限流。
- **与业务高峰的匹配**：政务系统峰值集中且陡峭，**必须按真实日历预置容量并做"高峰前置扩容"**（在高峰前 N 小时完成扩容并预热），而不是等指标告警再扩（扩容通常有数分钟到数十分钟延迟，扛不住陡增）。
- **容量风险清单**：单点无冗余、扩容依赖人工审批耗时、许可证/预算未预留、存储 IOPS 增长未纳入、数据库单表增长未做分区规划、上下游依赖未做自身容量对齐（上游扩容把压力推给下游）。

### 5. 自动化运维与AIOps自愈闭环

定义：自动化运维是以脚本、编排与平台能力替代人工重复操作与判断的运维方式；AIOps 是运用机器学习与智能算法，对运维全链路数据（指标、日志、链路、事件、工单）进行采集、关联、预测与自动处置，以提升运维效率与稳定性的实践体系。

关键要点：
- **自动化三要素**：**触发条件（事件/指标）→ 决策逻辑（规则/策略/模型）→ 执行动作（脚本/工单/切流/扩容）**，缺一不可；**只有触发没有决策的是告警，只有决策没有动作的是报表**。
- **四类典型场景**：
  - 自动扩缩容（阈值/预测触发，扩副本、切流、预热）
  - 故障自愈（进程自动拉起、磁盘自动清理、连接池自动重置、缓存预热）
  - 巡检自动化（基线核查、配置合规比对、日志巡检、容量预测报表）
  - 变更自动化（流水线部署、配置即代码、灰度发布与自动回滚）
- **基础设施即代码（IaC）与配置即代码（GitOps）**：基础设施与配置用声明式文件版本化管理，变更通过版本库合并、评审、灰度、回滚，避免"登录服务器手工改"造成的不可追溯；**配置文件必须版本化，变更必须可回滚**。
- **AIOps 能力三层次**：**数据层**（多源数据采集、统一时序库与日志库、数据质量与标签体系）→ **算法层**（异常检测、告警收敛与聚类、根因定位与关联分析、变更事件关联、容量预测）→ **执行层**（自愈动作编排、告警降噪与优先级、工单自动派发与知识库推荐）。
- **告警治理**：**告警风暴是运维事故的第一诱因**。治理手段包括告警分级（P1～P4）、同源去重与聚合、阈值动态化与基线化、告警收敛（一次根因只出一条主告警）、通知渠道分级（电话/短信/即时通讯）、**每条告警必须绑定处置预案（Runbook），无预案的告警应降级为报表**。
- **变更与性能/容量的耦合**：**任何可能影响性能的变更（版本升级、扩容、参数调整、数据库变更、流量切换）都必须纳入性能回归与容量校验**，变更是性能劣化的第一嫌疑。
- **自动化风险控制**：动作分级（只读 → 低风险 → 高风险）、**高风险动作必须人工确认与二次校验**、设置熔断与"自动化停止开关"、动作回滚预案、执行留痕与可审计、防止自动化风暴（单次自动动作幅度限制与频率限制）。
- **与日常运维的关系**：自动化不是替代流程，而是**把"标准动作标准化、把非标动作提级处理"**，遗留非标问题清单本身就是自动化路线图。

## 案例分析题

**题目**：

某市"城市民生服务一体化平台"承载全市 86 万实名用户，日均业务办理 42 万笔，峰值出现在每年 11 月至次年 1 月的集中参保缴费期，峰值并发用户 1.2 万，峰值请求速率 3800 次/秒。

平台于当年 3 月完成"国产化迁移与中间件升级"改造，改造后 9 月起平台性能持续劣化：

- 9 月起监控看板显示核心交易接口平均响应时间由 0.8 秒升至 1.9 秒，P99 由 2.1 秒升至 6.8 秒，11 月 21 日 21:40 至 23:10 期间全站卡顿，P99 一度达到 34 秒，错误率升至 6.3%。
- 故障期间客服工单 3700 单，人工重试 8000 余次，12345 热线收到相关投诉 640 件。
- 平台 12 台应用服务器（8 核 16G）CPU 峰值利用率 91%、内存 94%，但磁盘 I/O 利用率仅 18%、网络带宽利用率 12%。
- 核心业务库为单库单表架构，订单主表数据量 8.2 亿行且持续增长，未做分区；DBA 反馈近三个月未清理过慢查询日志，上季度新增 4 个业务模块的批量作业与夜间报表作业时间重叠。
- 平台运维团队共 6 人，自改造以来未做过任何压测；监控仅有 CPU、内存、磁盘三项主机级指标，无慢查询视图、无 APM 探针、无链路追踪；告警规则 47 条，2026 年 9 月单月触发 3127 条，实际有效告警不足 30 条，其余均为阈值抖动与重复告警。
- 服务合同约定：核心接口可用性不低于 99.9%，高峰时段（每年 11 月至次年 1 月）P99 响应时间不超过 3 秒，未达标按月扣减运维服务费的 20%，单月扣款上限为当月服务费的 50%。9 月至 11 月已累计扣款 43 万元。
- 市政府已安排专项预算 680 万元，要求在 12 月 1 日集中参保缴费高峰前完成整改并验证有效。

**问题**：

1. 请指出该平台在性能管理方面存在的缺陷，按严重程度排序并说明判断依据。
2. 请设计针对该平台的性能指标体系与可观测性建设方案。
3. 请设计性能测试方案，说明测试类型、负载模型、环境与数据准备的关键要求。
4. 请针对已识别的瓶颈给出分层调优措施清单，并说明调优验证方法。
5. 请给出该平台的容量规划与弹性伸缩方案（要求覆盖 12 月高峰）。
6. 请设计性能与容量问题的长期治理闭环，包括告警治理、变更管控、演练与考核机制。

**参考答案**：

**一、缺陷排序与判断依据**

按严重程度从高到低排序如下：

1. **无压测与无性能基线（最严重）**：中间件升级、国产化迁移属于重大架构变更，未做任何压测即上线，等于把"是否满足 SLO"交给生产环境用真实业务做试验。判据是升级后 9 月起指标持续劣化且运维方无任何对比基线，无法定位是改造引入还是业务自然增长。

2. **可观测性缺失**：仅有 CPU/内存/磁盘三项主机级指标，无慢查询视图、无 APM、无链路追踪。判据是 CPU 91%、内存 94% 而磁盘 I/O 仅 18%、带宽仅 12%——**资源利用率结构异常说明瓶颈不在磁盘与网络，而在 CPU 密集的等待（锁、GC、阻塞）与应用逻辑**，而恰恰这类问题在无 APM 与慢 SQL 分析的情况下不可见。

3. **数据库架构与治理失效（当前故障的主要技术根因）**：单库单表 8.2 亿行、无分区、无慢查询清理、四模块批量作业与夜间报表作业时间重叠。判据是 P99 34 秒伴随错误率 6.3% 呈"雪崩式"突变，符合锁等待/长事务导致的批量阻塞特征，而非容量不足的渐进式劣化。

4. **容量与弹性机制缺失**：无任何自动或人工的容量水位管理，扩容依赖被动响应；且业务峰值陡峭（集中参保缴费期），按告警再扩容必然来不及。

5. **SLA 罚则已触发且损失扩大**：99.9% 可用性对应全年不可用 8.76 小时，9—11 月单次 90 分钟卡顿加分散超时已造成 640 件投诉、43 万元扣款，且合同高峰期 P99≤3 秒的硬约束使 6.8 秒与 34 秒均为违约。

6. **告警体系失效**：3127 条告警中有效不足 30 条，说明阈值静态、缺少收敛与分级，真实故障被噪音淹没，同时无效告警消耗值班人力。

7. **值班与应急机制不足**：故障期人工重试 8000 余次说明缺少自动重试与降级限流能力，且 3700 单工单与 640 件热线投诉反映出对外沟通与用户安抚预案缺位。

8. **业务增长未纳入容量规划**：8.2 亿行主表持续增长无分区规划，批量作业叠加无窗口管理，长期风险大于短期故障。

**二、性能指标体系与可观测性建设方案**

1. **指标分层建库**：
   - 端到端层：用户侧成功率、P99 时延、关键流程完成率（如"参保缴费成功提交率"）。
   - 接口层：按接口分组统计 RT 的 P50/P95/P99、QPS、错误率（区分 5xx、超时、依赖失败）。
   - 组件层：应用线程池活跃数/队列长度、JVM GC 次数与停顿时长、连接池活跃/空闲/等待数；数据库 QPS、活跃连接、慢 SQL 数量与平均耗时、锁等待次数、复制延迟、主从切换次数。
   - 资源层：CPU、内存与换页、磁盘 I/O 与 IOPS/await、网络带宽与重传率、队列长度。
   - 缓存层：命中率、热点 key 访问量、回源 QPS、连接数、内存占用。
   - 依赖层：第三方接口（短信、支付、身份认证）成功率与超时率。

2. **口径统一**：所有指标统一 1 分钟与 5 分钟两个窗口，剔除压测、爬虫、探针流量；测量点同时在网关侧与应用侧埋点；**对外承诺只用网关侧 P95/P99**，防止口径套利。

3. **三支柱技术栈**：指标（Prometheus/InfluxDB 类时序库）、日志（含 TraceId 的结构化日志，ELK/Loki 类）、链路（SkyWalking 或同类 APM 探针，TraceId 贯通网关→应用→数据库→外部依赖），并强制**日志、指标、链路用同一 TraceId 关联**，实现"一次点击可下钻"。

4. **慢查询常态化治理**：开启慢查询日志（阈值 1 秒）与动态性能视图，建设慢 SQL 看板与 TOP 榜，纳管到日巡检；配合代码评审关卡，禁止无索引查询上线。

5. **告警重构**：47 条规则重构为分级体系——P1（可用性受损、核心接口错误率>2%）走电话值班，P2（性能劣化趋势）走即时通讯与工单，P3（容量与水位）走日报；加同源去重、5 分钟窗口聚合与风暴抑制，**目标月告警量降至 300 条以内、有效率提升至 70% 以上**。

6. **基线与预算**：建立各核心接口的性能基线（改造前后可比）与性能预算表，把 P99 上限拆到各层作为开发与上线约束。

**三、性能测试方案**

1. **测试类型组合**：
   - 基准测试：单用户测各核心接口基准值，作为回归对比基准。
   - 负载测试：按峰值 1.2 万并发、3800 QPS 的 1.0～1.5 倍施压，验证是否满足 P99≤3 秒、错误率≤0.5%。
   - 压力测试：阶梯加压至 1.5～2.0 倍负载，定位极限值与瓶颈，验证熔断限流是否按设计生效。
   - 稳定性测试：中等负载连续 72 小时，覆盖 4 个批量作业与报表作业周期，查内存泄漏与日志膨胀。
   - 容量测试：确定满足 SLO 的最大并发用户数与最大 TPS，输出容量基线表。
   - 回归测试：每次版本上线前跑核心接口基准+负载组合。

2. **负载模型（按真实业务日历，不做均匀流量）**：
   - 峰值脉冲：模拟 9:00 开闸放水式集中涌入，30 秒内从 10% 爬升至 100% 峰值。
   - 阶梯加压：每 5 分钟增加 10% 并发，直至 P99 突破 3 秒或错误率超 0.5%。
   - 混合场景：查询类占 70%、写入类占 20%、批量与报表类占 10%，与生产日志比例一致。
   - 浸泡场景：叠加夜间批处理与报表作业，验证任务隔离与队列削峰效果。
   - 故障场景：模拟数据库主从切换、缓存集群抖动、下游第三方超时，验证降级与熔断。

3. **环境与数据准备的关键要求**：
   - 生产同构：压测环境拓扑、机型、CPU 架构（国产化环境）、中间件版本、数据库版本与参数必须与生产一致；配置核查表逐项签字确认。
   - 数据等比：按生产数据量的 **20%～30%** 建库并保证数据分布（时间跨度、热点客户、状态分布）一致，否则索引与统计信息问题暴露不出来；数据必须**脱敏**或使用合成数据，严禁将真实个人信息、参保数据直接用于压测。
   - 账号与链路：按真实比例分配不同角色账号，覆盖登录态、鉴权、支付等完整链路，不做"绕过登录"的空转压测。
   - 隔离与安全：压测流量必须与生产流量物理或逻辑隔离、具备一键熔断开关；生产环境压测仅允许影子流量（复制真实请求至影子环境），**禁止在生产直接施压**。

4. **判据与产出**：以 SLO 为红线，输出《性能测试报告》《容量基线表》《瓶颈清单与调优建议》，报告须含"限流降级是否按设计生效""扩容后性能是否线性回升"两项结论。

**四、分层调优措施清单与验证方法**

1. **数据库层（最高优先级）**：
   - 8.2 亿行订单主表按创建时间做**分区**（或按用户/机构分片），并制定归档与冷数据迁移策略，历史数据转入历史库或列存。
   - 补齐缺失索引，重点覆盖高频查询条件与排序字段；对无法用索引的查询改写 SQL，禁用 `SELECT *`。
   - 慢查询治理：全量清理存量慢 SQL 并逐条归因；对本月新增慢 SQL 实行日通报、周复盘、纳入考核。
   - 批量作业改造：分批提交（每批 2000～5000 行）+ 批次间隔 + 幂等断点续跑 + **错峰调度**（四模块批量作业与夜间报表错开，作业窗口申请与审批留痕）。
   - 事务治理：缩短长事务，拆分大事务，业务高峰期禁止大批量数据修正类操作。
   - 连接池：按数据库 `max_connections` 与应用实例数倒推各实例池上限，避免池过大打满数据库连接；池过小导致的排队要以"等待获取连接耗时"指标区分，不与慢查询混淆。

2. **应用与运行时层**：
   - 用 APM 火焰图定位 CPU 热点，消除热点方法与重复计算；对批量循环内的数据库访问做批量化与合并（N+1 治理）。
   - 线程池与连接池整定：核心线程数按 CPU 核数与任务类型分池隔离，队列长度设置上限并配置拒绝策略（快速失败优于无限排队）。
   - JVM 调优：初始堆与最大堆一致避免动态扩缩抖动，设置合理的年轻代比例与 GC 策略，控制 Full GC；核查 GC 日志确认停顿是否与 P99 尖刺重合。
   - 缓存治理：命中率纳入监控，热点 key 单点加固与本地缓存，缓存预热在流量进入前完成。
   - 引入**熔断、限流、降级、异步化与消息队列削峰**：写请求高峰进入 MQ 异步落库，核心查询与支付链路优先保障，非核心功能（历史报表导出、消息推送）高峰期主动降级。

3. **接入与流量层**：
   - 负载均衡开启会话保持与健康检查，对已劣化节点及时摘除，避免把流量打到慢节点。
   - 对静态资源与热点数据做 CDN 缓存，缩短链路长度。
   - 入口限流：按接口与用户维度设置配额，超限返回友好提示而非拖垮后端。

4. **架构层（数据库与应用调优无解时）**：
   - 读热点分离：读多写少的查询走只读副本或缓存；写集中的核心表评估分库分表。
   - 高峰削峰：批量写入与集中提交改为削峰队列 + 限速消费。
   - 无状态化改造与水平扩容：为 12 月高峰的临时扩容预留能力。

5. **调优验证方法（关键）**：
   - **单变量原则**：每次只改一项并复测，通过对比表归因，禁用多变量同改。
   - 复测链路：修复后重跑基准测试 → 负载测试 → 峰值脉冲场景 → 72 小时稳定性测试，四项全过才算通过。
   - 留档：形成《调优前后对照表》（场景、指标、调优前、调优后、结论），作为验收证据与后续回归基线。
   - 灰度验证：先在预生产环境复现 21:40—23:10 的流量曲线（尖峰+批量作业重叠）验证，再上生产低峰期灰度放量。

**五、容量规划与弹性伸缩方案**

1. **业务量预测**：以 11 月—次年 1 月集中参保缴费期为规划窗口，峰值并发 1.2 万、峰值 3800 QPS 为基准，按 **1.5 倍**（5700 QPS）作为 12 月高峰设计容量，并叠加 20% 故障冗余（单节点故障后仍能承载峰值）。

2. **资源测算**：
   - 应用层：实例数 = 峰值 QPS ÷ 单实例压测吞吐（以压测后单实例承载 600 QPS 为例）≈ 8 实例，压测复核后定稿；再加 2 台热备，共 10 台。
   - 数据库层：按 Little 定律估算连接数 = 5700 QPS × 平均响应 0.1 秒 ≈ 570 并发连接，按实例 600 连接上限配置读写分离与连接池限额；存储按年均增长 40% 规划，容量与 IOPS 双向核算。
   - 缓存层：按热点数据与并发估算内存，规划命中率 95% 以上，配置双节点热备。
   - 带宽与许可证：带宽按峰值流量 1.5 倍预留；中间件、数据库、监控探针授权数量同步核增。

3. **水位与冗余标准**：CPU/内存生产长期水位控制在 30%～60%，不超过 70%；关键资源 N+1 冗余；建立容量台账（当前水位、预测峰值、扩容阈值、扩容周期）。

4. **扩容触发与节奏**：
   - **定时伸缩为主**：按业务日历在 11 月 25 日、12 月 1 日、12 月 15 日、1 月 5 日四个节点预扩容并完成预热，**高峰前 24 小时完成扩到位**，不等告警。
   - **阈值伸缩为辅**：CPU 连续 5 分钟 >65%、队列长度持续 >80% 时自动扩副本，设 30 分钟冷却时间与单次扩副本上限，防止抖动。
   - **预测伸缩**：基于近三年同期曲线做高峰预测，11 月上旬完成模型校准。
   - 数据库：主从延迟 >30 秒或连接数 >70% 触发只读副本流量切分；必要时对历史查询走历史库。

5. **降级链（资源不足时的顺序）**：扩缓存与只读副本 → 扩应用副本 → 停用非核心功能（批量导出、复杂报表、消息推送）→ 接口级限流 → 排队与预约化处理。

6. **12 月高峰前的验证节奏**：11 月 20 日前完成调优与压测复测；11 月 25 日完成全链路演练（真实峰值曲线 + 故障注入 + 降级演练）；12 月 1 日进入高峰后每日复盘容量水位与性能指标，必要时按预案二次扩容；1 月 5 日后按容量台账输出年度容量规划报告。

**六、长期治理闭环**

1. **告警治理（3 个月专项）**：告警分级 P1—P4；同源去重与 5 分钟窗口聚合；阈值从静态改为基线动态；**每条 P1/P2 告警必须绑定 Runbook**，无预案降级为日报；目标月告警量 <300 条、有效率 >70%、误报率 <20%。

2. **变更管控**：建立变更分级（标准/一般/重大），重大变更（中间件升级、数据库版本、架构调整、流量切换）**强制压测与性能回归**；变更前评估性能影响面并更新性能预算；变更窗口避开业务高峰与批处理窗口；保留回滚预案并验证可回滚；上线后 72 小时性能专项观察。

3. **性能基线与回归常态化**：核心接口基线纳入版本库，每次上线自动跑基准+负载回归，性能劣化超过阈值（如同比劣化 20%）阻断发布；每月出具《性能健康报告》（P99 趋势、慢 SQL TOP、缓存命中率、资源水位、容量满足率）。

4. **演练机制**：季度性能压测演练（至少含一次峰值脉冲与一次故障注入）；年度容量演练（验证扩容通道、预热时长、人员到位）；每次演练形成问题清单并跟踪闭环，演练不达预期需提交专项整改。

5. **作业与窗口管理**：建立批处理作业台账与调度日历，明确作业窗口、并发上限、超时与失败重跑策略；夜间批处理与报表错峰；高峰季节（11 月—次年 1 月）冻结非必要批处理与大表变更。

6. **组织与考核**：明确运维团队职责分工（数据库、中间件、应用、监控、值班）并配备 7×24 值班；将"慢 SQL 存量下降""告警有效率""压测覆盖率""SLO 达成率"纳入运维方考核与合同扣款条款联动；运维团队 6 人对 12 台服务器+单库8.2亿行的现状明显不足，须补充 DBA 与中间件岗位或引入专业外包支持。

7. **用户沟通与应急**：建立系统公告与短信/公众号的降级公告模板，重大故障时主动告知用户绕行方案（线下渠道、错峰办理），减少热线投诉；建立故障复盘模板（时间线、根因、改进项、责任人、时限）。

## 记忆口诀

**一、指标四把尺**
响应时间看分位，平均会骗人要用 P99；吞吐看 TPS，并发看在线；错误要分五、超时、依赖；SLO 在内、SLA 在外，外紧内松留缓冲。

**二、三个九要会算**
三六五天九成九，八七六时九九九，五二五六分五九；可用性公式 365×24×(1-可用率)，莫把 SLA 与 SLO 混。

**三、压测五型**
基准摸底、负载达标、压极限、泡稳定、测容量；峰值按业务日历，别拿均匀流糊弄；数据要等比、账号要真实、生产只做影子。

**四、定位分层口诀**
上到下逐层倒查：端到端 → 接入 → 应用 → 中间件 → 数据库 → 系统 → 物理；延迟涨在哪层，压力就加在哪层；CPU 忙内存高而磁盘闲，多半是锁与 GC。

**五、缓存三坑**
穿透查不存在（空值+布隆）；击穿热点过期（互斥重建+逻辑过期）；雪崩集体到期（随机抖动+多级缓存）。别把击穿当穿透治。

**六、容量五步**
预测业务量、算单位消耗、留三到六成冗余（N+1）、设阈值与节奏、滚动验证；高峰前置扩容，别等告警再扩；垂直扩容简单有上限，水平扩容必须先无状态。

**七、调优闭环**
基线 → 假设 → 单变量 → 复测 → 留档；一次只改一项，否则无法归因；调优无解上升一层：异步、削峰、读写分离、分库分表、限流降级。

**八、自动化三要素**
触发 + 决策 + 动作，缺一即废；只触发无决策是告警，只决策无动作是报表。告警风暴是第一事故源：分级、去重、收敛、配预案，无预案降级为日报。

**九、变更铁律**
重大变更必压测，性能回归必做；高峰与大表变更必冻结；变更必须可回滚、可追溯；性能劣化的头号嫌疑永远是变更。

**十、治理闭环**
建基线、定分级、清慢查、治告警、常演练、严变更、有人有责有考核；SLO 达成率进合同，演练不达标要整改。
