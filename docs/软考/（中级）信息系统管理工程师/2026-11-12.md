## 今日核心概念

### 1. 遗留系统的四种处置策略与绞杀者模式

定义：遗留系统是指在长期运行中承担核心业务、但其技术栈、数据结构、架构形态与当前主流技术规范严重脱节的既有信息系统。遗留系统管理的第一性决策不是"要不要改造"，而是"以何种方式处置"，其本质是在技术债利息、业务连续性风险与改造投入之间做路径选择。

四种处置策略及适用条件：
1. **维持**：不改变核心，仅做缺陷修复与安全加固。适用于业务稳定、系统规模小、改造预算不足、且依赖的外围系统多。
2. **改造**：保持外部接口与行为不变，重构内部实现（分层解耦、代码清理、数据库结构优化）。适用于业务逻辑正确但代码质量差、测试缺失的场景。
3. **替换**：重新实现功能并切换，遗留系统退役。适用于业务模型已发生根本变化、原技术栈无人可维护、且具备完整需求规格与历史数据可迁移。
4. **退役**：业务本身已消失或已被其他渠道替代，关停系统并处置数据与硬件。

绞杀者模式：在遗留系统外围建立新系统，以"门面 + 路由"方式按业务能力逐个接管，每接管一块即废弃对应旧模块，最终旧系统自然枯竭而非一次性大爆炸替换。其三种变体：绞杀者（外围包裹逐块剥离）、防腐层（防腐层适配新模型与旧模型）、分支抽象（对外统一抽象、对内适配多版本）。

关键要点：
- 绞杀者模式的核心价值是**把"高风险大爆炸切换"变成"低风险连续交付"**，与 11-10 的灰度发布思路同源，但应用在架构替换层面。
- 选型判据三问：业务需求是否仍稳定（否→替换或退役）；原技术栈是否还有可维护人力（否→替换）；是否具备可迁移的历史数据与可复用的需求规格（否→维持）。
- 遗留系统最危险的不是旧，而是"无人知晓的依赖"——隐性接口、报表取数、批处理、对外共享文件、运维脚本，必须在改造前做依赖测绘。
- 中级教材考点常把遗留系统处置与系统迁移、系统更新改造、集成接口三类问题混在一起考，答题时须先明确"处置策略—迁移方式—集成接口"三个层次，再逐一对应。

### 2. 信创迁移的兼容性适配矩阵

定义：兼容性适配矩阵是以"原技术栈 → 目标技术栈"为主键、以"操作系统、数据库、中间件、运行时、芯片架构、外设与驱动、终端与浏览器、第三方接口"为维度，系统登记每一处技术替换点的**不兼容类型、改造方式、验证结论与责任方**的工程台账。它是信创改造中唯一能防止"漏项"的管控工具。

典型技术栈映射：
- 处理器架构：x86 → 麒麟（飞腾/鲲鹏 ARM64）、统信（龙芯 LoongArch）
- 操作系统：Windows Server 2008/2012 → 银河麒麟（Kylin V10）、统信 UOS（服务器版）
- 数据库：Oracle/SQL Server/DB2 → 达梦 DM、人大金仓 KingBase、OceanBase、TDSQL
- 中间件：WebLogic/WebSphere/Tomcat + Oracle WAS → 东方通 TongWeb / 金蝶 Apusic / 宝兰德 BES
- 运行时：.NET Framework → .NET 8（跨平台）、Java 8 → Java 17（支持国产 CPU 与国密）
- 报表与办公：水晶报表/FineReport → 国产报表中间件；Office 宏 → 文档中心国产化适配
- 浏览器与终端：IE/旧版 Chrome → 奇安信浏览器、红莲花、360 政企版

六类典型不兼容与改造手法：
1. **指令集与二进制不兼容**：原生扩展（Oracle 空间扩展、Oracle OCI 驱动）需替换为达梦/金仓对应驱动；商业中间件按 CPU 重新编译。
2. **数据库语法与编程模型不兼容**：PL/SQL 包、存储过程、触发器、游标、自定义函数、`ROWNUM`、隐式游标、序列与触发器组合、层级查询 `CONNECT BY`、`NVL`/`DECODE`、日期函数 `ADD_MONTHS`、外键与索引组织方式差异，须做逐语句改写与等价性证明。
3. **字符集与排序规则不兼容**：GBK/GB2312 → UTF-8（注意 Oracle 空字符等价于 NULL）、大小写敏感差异、全角半角与拼音排序差异，直接影响中文排序、模糊查询与唯一约束。
4. **中间件与运行时差异**：容器默认不支持 Session 粘性、类加载隔离、JDBC 驱动包名、连接池参数、事务边界与超时参数差异。
5. **外设与驱动不兼容**：打印机、扫描仪、高拍仪、CA 证书 UKey、读卡器、税控设备的国产化驱动缺失，或旧驱动在新国产内核上无法加载。
6. **第三方接口与许可不兼容**：外部系统（统一身份认证、电子签章、短信、地图、支付）SDK 依赖 x86 原生库或闭源中间件；商业软件许可不支持国产环境。

关键要点：
- 适配矩阵的最小列集为：**业务系统 / 技术组件 / 原方案 / 目标方案 / 兼容等级 / 改造工作量 / 责任方 / 验证状态**；兼容等级建议四档：完全兼容、改造后兼容、需替换、暂不支持。
- "暂不支持"项必须在改造启动前形成清单并给出**业务影响与临时替代方案**，否则将成为割接当天的爆炸点。
- 适配矩阵必须配套**国产化测试环境**（同架构 CPU + 同版本操作系统 + 目标数据库），且测试环境版本需与生产基线一致，否则矩阵结论不可迁移。
- 常见丢分点：把"驱动安装成功"等同于"业务兼容"，忽略事务语义、并发行为、排序规则、性能特征四类**隐性不兼容**。

### 3. 双轨并行与切量灰度

定义：双轨并行是指在割接窗口内，新旧系统同时对生产业务提供服务，通过只读影子比对、双写双读、对照回放等手段验证新系统正确性，再按预设阶梯逐步切流、最终停旧系统的一种割接组织方式。其本质是**用可回退性换取割接确定性**。

三种并行模式及其适用：
1. **影子流量（Shadow / Dark Traffic）**：生产请求复制一份打到新系统，新系统只计算不返回。适用于读多写少、验证响应内容与性能基线的场景；对写操作需在影子侧回放或事务回滚。
2. **双写双读（Dual Write & Read）**：旧系统为主、新系统为辅，写操作同时落两库（或由旧系统写、新系统只读），定期比对两侧结果。适用于数据模型变化大、需要持续累积验证样本的场景；须解决"双写失败如何补偿"的问题。
3. **对照回放（Replay / Verification）**：抽取历史生产数据在双侧重放，比对输出结果与关键中间状态。适用于批处理、报表、计算类逻辑的正确性验证。

切量阶梯（示例）：影子比对 → 1%（内部员工或试点窗口）→ 5% → 20% → 50% → 100%，每一档设置**最小观察窗口**（建议不少于 3 个完整业务日周期，覆盖月结、批量、对账等低频路径）与**回切阈值**（错误率、响应时延 P95、业务量偏差、对账差异率）。

回切决策树：触发任一硬阈值即执行回切（回切耗时目标 < 15 分钟）→ 定位失败档位 → 冻结切量并保留现场快照 → 缺陷修复后重新从最低档位爬坡，禁止跳档。

关键要点：
- 切量前必须完成**四件准备**：旧系统冻结变更（进入维护冻结期）、回切脚本与数据补偿脚本演练通过、数据双向校验通过、监控大盘与告警就位。
- 灰度人群选择原则：先内部账号、再低风险业务线（查询类）、再高价值低风险用户、最后全量；高风险写操作（支付、注销、审批）应放到最后一档或采用"双写不切读"策略。
- 数据一致性的核对粒度要分三层：总量级（行数、金额合计）、主键级抽样、关键字段级全量或分桶比对；仅比对行数是典型的伪验证。
- 停旧（Cutover 完成）后仍需保留一段**并行回退窗口**（如 30 天），此期间旧系统数据只读留存并禁止物理销毁。

### 4. 改造验证与验收标准

定义：改造验证是指以"业务功能正确、兼容稳定、性能不退化、数据一致、安全合规、文档齐备"六条主线，用可度量指标判定信创改造是否达到切换条件的正式活动；验收标准则是这些指标的具体阈值与举证材料清单。

六条验证主线与举证要求：
1. **功能正确性**：以历史业务用例（建议按业务发生频次与金额分级抽取）回归执行，通过率不低于 99.5%，关键资金与权限类流程 100% 通过；举证为回归测试报告与缺陷闭环清单。
2. **兼容性**：操作系统、数据库、中间件、终端、浏览器、外设、第三方接口的兼容性矩阵 100% 有结论；举证为适配矩阵终版与国产化测试报告。
3. **性能不退化**：关键交易类接口响应时间 P95 不高于原系统 110%，吞吐量不低于原系统 90%，批处理窗口不超时；举证为迁移前后同负载压测对比报告。
4. **数据一致性**：核心表行数、主键唯一性、金额合计、状态分布四项比对差异率为 0；举证为数据校验脚本输出与抽样人工复核记录。
5. **安全合规**：漏洞扫描无高危与中危遗留、账号权限矩阵无越权项、日志留存满足等保要求；举证为扫描报告、权限矩阵、审计日志抽查记录。
6. **文档与交接齐备**：需求说明书、概要与详细设计、数据库设计说明书、部署手册、运维手册、应急预案、培训记录；举证为文档清单与签收记录。

验收组织要点：成立由业务方、技术方、运维方、安全方组成的验收组（不少于 5 人且为单数）；先初验（功能与集成），再试运行（连续 15~30 天并出具运行报告），最后终验；终验须有第三方检测机构出具的**软件测评与信创适配认证报告**；不合格项形成整改台账并闭环复验后方可终验。

关键要点：
- 试运行期是发现"低频路径缺陷"的唯一窗口（对账、月结、批量、年度切换、跨年结转），跳过试运行直接终验是高风险做法。
- 验收不是文档工作而是**证据工作**：每条标准都必须有可核查的证据出处（报告编号、截图、日志位置、签认单）。
- 常见丢分点：只写"完成测试"不写通过率与门槛值；只写"性能满足要求"不写对比基准与劣化容差；整改台账无闭环证据。

### 5. 改造工程治理与知识转移

定义：改造工程治理是指在信创迁移这类长周期、高风险工程中，通过组织机制、范围控制、依赖治理与知识沉淀，保证改造过程可控、可审计、可交接的管理体系。其关键在于"人走知识不走"。

治理机制要点：
1. **范围冻结与变更控制**：改造启动前冻结功能范围，形成基线清单；新增需求一律走变更评审并评估对割接窗口的影响。
2. **依赖治理**：建立软件物料清单（SBOM），登记全部第三方组件、版本与许可证；高危漏洞与许可证冲突须在割接前清零或出具风险接受说明。
3. **组织与职责**：设改造总负责人、架构组、数据迁移组、测试验证组、割接指挥组（割接窗口内唯一指挥链）；割接实行"一令一执行、操作双人复核、逐项打勾确认"。
4. **知识转移与能力建设**：原厂退出前完成源码与文档交接、运维手册编写、原厂支持过渡期约定；运维团队按目标技术栈完成培训与认证，割接后 30 天内实行"原厂与新团队并行值守"。
5. **遗留系统处置**：停旧后按保留期只读归档，历史数据按数据安全法与档案管理要求处置（到期安全销毁并出具销毁记录），硬件与许可按资产流程回收。

关键要点：
- 割接方案必须具备**可执行性三要素**：逐步骤操作手册（含命令与参数）、回切脚本（经演练）、每一步的判定标准与责任人。
- 割接窗口选择遵循"业务低峰 + 避开月结月季末 + 避开重大活动保障期 + 预留回切缓冲时间"四条准则。
- 治理视角的高频失分点：把改造当成纯技术任务，忽视"文档、培训、应急、审计"四项软件资产化义务。
- 中级教材常把"系统更新与改造、系统迁移与退役、系统集成接口"三块合并命题，答题时先给方案选择依据，再给实施步骤，最后给验证与保障，三段式缺一不可。

## 案例分析题

**题目**：

某市人力资源和社会保障局建设"智慧人社一体化平台"，原有五套系统（就业登记、社保补贴申领、人才档案管理、职称评审、劳动关系监察）分别部署在两台 Windows Server 2008 R8 服务器上，技术栈为 .NET Framework 4.6 + SQL Server 2008 R2 + IIS 7.5，其中两套系统使用 SQL Server 报表服务生成打印报表，一套对接省厅 CA 数字证书，一套使用旧版水晶报表控件。数据库累计约 1.6TB，单表最大 8200 万行。系统日均访问量 12 万人次，月末有补贴批量审核与社保代缴批处理任务。

该市被列入省级信创改造试点，要求 8 个月内完成整体迁移至"麒麟 V10（飞腾 ARM64）+ 达梦数据库 DM8 + 东方通 TongWeb"的国产化环境，预算 2860 万元（其中软件开发 1580 万、适配与测试 480 万、硬件与许可 620 万、迁移实施 120 万、风险预留 60 万），且明确"改造期间不得中断对外服务"。前期需求调研发现：核心业务规则文档缺失，5 套系统共 340 个存量功能点中仅 128 个有书面说明；改造预算中未安排运维人员培训费用；割接窗口只批准了一个 6 小时的夜间窗口。

项目实施过程中暴露的问题：

1. 改造启动第 2 个月，团队才通过代码扫描发现，补贴申领系统中 47 个存储过程使用了 SQL Server 特有语法（含 `ROWNUM` 分页、`ISNULL` 与空串比较、`GETDATE()` 触发器生成序列、`CONNECT BY` 层级查询），另有 38 处硬编码日期格式 `'yyyy-MM-dd'` 的字符串拼接，数据库字符集为 GBK，而达梦默认 UTF-8 并区分空串与 NULL。首轮迁移测试中，补贴审批列表按"申请日期升序 + 姓名拼音升序"的排序结果与原系统完全不一致，涉及 210 万条历史数据的排序校验不通过。
2. 统信与麒麟双版本操作系统路线在第 3 个月仍未确定，导致适配矩阵无法冻结、国产化测试环境只能按单一方案搭建，第 6 个月路线确认为麒麟 + 达梦后，此前在另一分支上完成的 37 处驱动改造全部返工，返工导致割接准备时间被压缩至 23 天。
3. 性能对比显示，新平台在压测中关键交易接口 P95 由原系统 820 毫秒上升至 1180 毫秒（劣化 44%），批处理窗口由 4.5 小时延长至 7.2 小时（超窗口 2.7 小时），其中批处理劣化主因是达梦未开启列存/并行度配置且存储只有机械盘。
4. 割接前 10 天，项目组提出采用"影子流量比对 3 天 + 全量切换"的方案，未编写回切脚本，也未做数据一致性核对。因开发人员对达梦 `MERGE` 语法不熟悉，两套系统采用双写方案时同步程序连续 3 晚失败，共产生 412 条数据不一致。
5. 试运行期结束后，运维部门反馈：新平台所需数据库、中间件、国密改造的技术人员共需 9 人，现有 4 人且均无国产化平台运维经验，原厂支持将在项目验收后 6 个月终止。
6. 验收时专家组提出：缺少信创适配认证报告与第三方软件测评报告，且 340 个功能点中 61 个为"用户口头描述即认定通过"，无书面用例与执行记录。

请回答以下问题：

1. 指出该项目在改造组织与技术路线上存在的**主要缺陷**（不少于 8 项），并按严重程度排序，指出其中会导致割接失败或数据损失的**致命缺陷**。
2. 针对该项目的**兼容性适配问题**，设计一份"国产化兼容性适配矩阵"的结构（列出必备列）与三条关键缺陷（字符集/排序、SQL 语法、迁移时机）的**具体改造措施**。
3. 设计该项目的**数据迁移方案**：说明迁移步骤、字符集与空串 NULL 处理、迁移前后数据校验方法，并给出批次迁移与回滚策略。
4. 设计**双轨并行与切量方案**：给出并行模式选择、灰度阶梯与每一档的观察窗口与回切阈值、回切决策流程与回切时间要求，并说明为什么"影子流量 3 天 + 全量切换"不合格。

**问题 1：主要缺陷与致命缺陷**

按严重程度排序的缺陷清单（括号内为后果）：

1. **需求与业务规则文档缺失，改造范围无基线**（340 个功能点仅 128 个有书面说明，改造即"照着代码猜需求"，缺陷不可避免且验收无据）
2. **未安排运维人员培训费用与能力建设预算**（割接后无人能接管，验收即交付终结，项目失败）
3. **技术路线（操作系统/数据库分支）长期不定，适配矩阵无法冻结**（37 处驱动改造返工，割接准备仅剩 23 天，风险不可控）
4. **未编写回切脚本、未做数据一致性核对即定割接方案**（一次失败即不可逆，无法在 6 小时窗口内回退）
5. **双写同步程序连续失败未及时熔断，累积 412 条数据不一致**（已产生实际数据损失，且无对账与补偿机制）
6. **性能验收门槛缺失，劣化 44% 与批处理超窗未设量化拦截**（割接后必然触发用户投诉与业务中断）
7. **验收证据链不完整**：缺信创适配认证报告、缺第三方测评报告、61 个功能点无书面用例与执行记录（终验不具备条件，涉嫌验收失真）
8. **割接窗口仅批准 6 小时，与切量阶梯和回切缓冲需求严重冲突**（灰度与回切无时间空间）
9. **批处理与在线交易未做资源隔离与错峰规划**（批处理 7.2 小时挤占在线资源，是性能劣化的重要成因）
10. **原厂支持退出安排在验收后 6 个月，但无过渡期并行值守与源码文档交接**（知识断档）
11. **字符集与空串语义问题未在方案阶段识别**（210 万条数据排序校验不通过，直接导致上线即失败）
12. **预算结构失衡**：软件开发 1580 万占比 55%，而适配测试 480 万、迁移实施仅 120 万，风险预留 60 万占 2.1%，明显低于高风险改造项目的经验区间（8%~10%）

其中致命缺陷（直接导致割接失败或数据不可逆损失）为第 1、2、3、4、5 项：
- 第 1 项使"功能正确性"无从判定，任何割接都缺少可信基线；
- 第 2 项使项目在验收即失去持续运行能力；
- 第 3 项使适配与测试时间被系统性压缩，验证充分性无法保障；
- 第 4 项使失败不可回退，6 小时窗口内一次故障即造成长时间业务中断；
- 第 5 项已在产生实际数据不一致，且缺乏发现与补偿机制，数据损失会随双写持续扩大。

**问题 2：适配矩阵结构与三条关键缺陷改造措施**

适配矩阵必备列（每行 = 一个技术替换点）：
业务系统 | 组件类别 | 原方案（含版本） | 目标方案（含版本） | 兼容等级（四档：完全兼容/改造后兼容/需替换/暂不支持） | 不兼容类型（六类之一） | 具体改造措施 | 工作量（人天） | 责任方 | 验证方式 | 验证结论 | 状态

配套要求：矩阵须与"国产化测试环境基线"绑定，环境版本与生产一致；"暂不支持"项须有业务影响说明与临时替代方案；矩阵须版本受控，每次路线变更即冻结新版本并重算受影响条目。

三条关键缺陷改造措施：
1. **字符集与排序缺陷**：
   - 统一以 UTF-8（带 BOM 不使用，库表统一字符集与排序规则）为全链路基准，逐字段核查源库 GBK 到 UTF-8 的转换，对含生僻字、历史乱码、emoji 的字段做专项抽样；
   - 空串与 NULL 语义统一：在迁移 ETL 层显式定义映射规则（源库空串 → 目标库空串或 NULL 二选一并全库一致），并在应用层禁用"空串等价 NULL"的隐式比较，全部改为显式 `IS NULL` 判断；
   - 排序不一致根因是"拼音排序依赖操作系统 locale"与"大小写敏感差异"，解决方式：在排序列上建显式排序键（存储名称首字母编码列或统一 GBK 排序键列），应用侧按排序键排序，禁止依赖数据库默认 collation 排序；这样可保证跨库跨环境排序结果完全一致；
   - 验证：抽取 210 万条全量按"申请日期+排序键"重排，与原系统输出逐行比对，差异必须为 0。
2. **SQL 语法缺陷**：
   - 建立"SQL 语法映射表 + 兼容改造规范"，逐条给出源语法与目标语法的等价改写：`ROWNUM` 分页改写为带排序键的 `LIMIT/OFFSET` 或窗口函数 `ROW_NUMBER() OVER (ORDER BY ...)`；`ISNULL` 改写为 `NVL/IFNULL`；`GETDATE()` 统一改为数据库参数化取当前时间（应用侧传参，避免库间函数差异）；`CONNECT BY` 层级查询改写为递归 CTE（`WITH ... AS`）或应用侧一次性拉取后在内存中构树；序列+触发器生成主键改为目标库序列 + 应用侧取号；
   - 对 47 个存储过程逐个产出"原逻辑说明 → 改写后代码 → 等价性证明（边界值、NULL 值、并发下的一致性）→ 单元测试用例"四件套，由数据库负责人 + 业务负责人双签；
   - 38 处硬编码日期字符串拼接全部改为参数化日期类型传入，杜绝隐式格式转换；
   - 语法扫描工具在流水线中设为强制门禁，命中未改造语法即阻断构建。
3. **迁移时机缺陷（路线迟定导致返工）**：
   - 立即执行路线冻结评审：由市局、集成商、原厂、设备方共同签署《国产化技术路线基线确认书》，明确操作系统版本、数据库版本、中间件版本、CPU 型号，并作为合同与验收依据；
   - 路线未冻结前，只允许开展与平台无关的工作（需求梳理与文档补齐、代码梳理、语法映射表编制、测试用例设计），禁止投入适配编码与硬件到货，防止再生产沉没成本；
   - 建立变更代价评估机制：任何路线变更须出具"影响条目数 × 平均改造工时 + 回归测试工时 + 割接窗口影响"的量化评估，触发阈值（如影响条目超过矩阵 10% 或割接准备期不足 45 天）即上报变更控制委员会决策；
   - 设置里程碑门禁：路线冻结（第 0 阶段出口）、适配矩阵冻结（第 1 阶段出口）、测试通过（第 2 阶段出口）、割接演练通过（第 3 阶段出口），四道门禁不通过不得进入下一阶段。

**问题 3：数据迁移方案**

迁移步骤：
1. 全量数据画像与清洗（重复主键、孤儿记录、非法字符、超长字段、GBK 乱码字符统计）；
2. 源库到目标库的**对象映射与转换**（表结构、字段类型、默认值、索引、约束、序列、视图、存储过程、报表模板），形成《对象转换对照表》；
3. 全量迁移演练（同一套 ETL 脚本在演练环境跑通并计时，验证窗口可容纳）；
4. 生产全量迁移（停写窗口内完成，或采用 CDC 增量追平）；
5. 增量追平与切换（若采用不停写方案：先全量后 CDC，最后停旧写、反向追平、校验后切读）；
6. 双轨比对与灰度切量；
7. 旧系统只读归档，30 天后按保留策略处置。

字符集与空串 NULL 处理：
- 迁移链路统一以 UTF-8 编码读写，中间不经过任何隐式转码工具；ETL 明确指定源/目标字符集并禁止依赖操作系统默认编码；
- 源库空串与 NULL 的映射规则统一取"源空串 → 目标空串"或"→ NULL"，二选一并写入《迁移规则说明》，应用侧同步改造比较逻辑；
- 对 38 处日期字符串拼接与所有金额字段按目标库类型显式转换（金额统一 DECIMAL 定点数，禁用浮点）；
- 中文拼音排序依赖的目标库需显式指定排序规则并建立排序键列。

迁移前后数据校验方法（四层递进）：
- 第一层 总量级：各表行数、金额合计（SUM 分币种分方向）、状态分布计数，三项差异率为 0；
- 第二层 主键级：全量主键集合双向差集（源减目标、目标减源）均为空集；
- 第三层 关键字段级：分桶抽样（按主键哈希分 100 桶，每桶抽 1%，合计不少于 30 万行）逐字段比对，或对资金类、状态类字段做全量比对；
- 第四层 业务逻辑级：对账（总账-明细）、结转、批量结果等做业务口径复核。

批次迁移与回滚策略：
- 按业务域分批（人才档案 → 职称评审 → 就业登记 → 监察 → 社保补贴），每批独立可验证、独立可回滚；禁止跨业务域事务；
- 每批迁移前对源数据做只读快照（备份并记录校验和），作为回滚数据源；
- 回滚机制：切换失败即停写新库、用快照恢复源库至切换时点一致状态、回切读流量至旧系统；前提是**旧系统在观察窗口内保持可启动且禁止变更**（本次割接须在停旧前完成旧库可回退验证，即"停旧演练"一次）；
- 批次判据：上一批次通过四级校验且观察期内无新增不一致，方可启动下一批次。

**问题 4：双轨并行与切量方案**

并行模式选择：
- 主体采用 **影子流量 + 双写双读**：读请求按比例复制至新系统只计算不返回（首批比例 5%），比对响应体关键字段与耗时分位；写操作由旧系统主导，新系统异步双写并每日对账；
- 对**批处理与报表**采用 **对照回放**：抽取近 3 个月历史批处理输入数据在双侧重放，比对输出结果与行数、金额合计；报表以"同一份数据在双侧生成 PDF 后做结构与数值比对"；
- 关键写操作（补贴发放、审批结论、证书编号生成）初期采用"旧系统单写 + 新系统只读"，避免双写不一致直接造成资金与权益差错。

灰度阶梯与观察窗口、回切阈值（建议值）：
- 阶梯：内部员工账号（1%）→ 试点窗口/低风险查询业务（5%）→ 20% → 50% → 100%
- 每一档最小观察窗口：不少于 3 个完整业务日，且必须覆盖一次月末批处理或一次对账周期
- 回切硬阈值（任一触发即回切）：新系统错误率 > 0.5%；P95 时延 > 原系统 130%；双写日对账差异率 > 0.01%（即 100 万笔中超过 100 笔不一致）；核心交易量与旧系统同期偏差 > 2%；关键功能用例失败 ≥ 1 项
- 回切时间要求：**回切动作须在 15 分钟内完成**（演练证明，含流量切回、数据回滚或补偿、状态核验）；因此回切脚本必须为自动化脚本，且在割接前至少演练 2 次

回切决策流程：
触发硬阈值 → 割接指挥组决策（授权人单一，负责放行/回切，不接受"现场讨论"）→ 立即冻结切量并关闭新系统写入口 → 执行回切脚本 → 验证旧系统恢复（功能用例 + 流量指标 + 对账）→ 保留现场快照与日志 → 根因分析与修复 → 重新从 1% 档位爬坡，禁止跳档。

"影子流量 3 天 + 全量切换"不合格的原因（至少答出 5 条）：
1. 无阶梯切量，一次性 100% 切换，故障影响面等于全量用户；
2. 无回切脚本与回切演练，失败不可逆，6 小时窗口内无法在合理时间恢复；
3. 无数据一致性核对方案，412 条不一致未被及时发现与补偿；
4. 3 天观察窗口无法覆盖月末批处理与对账等低频路径，正是本项目批处理已劣化 2.7 小时的场景；
5. 未设置分档回切阈值与决策授权人，事故时无人有权拍板；
6. 未安排停旧前的"旧系统可回退验证"，割接一旦失败，旧系统本身状态不确定；
7. 6 小时窗口与"影子 3 天 + 全量切换"自相矛盾：影子比对 3 天消耗窗口时间，全量切换后已无回退时间余量。

**问题 5：性能调优方案与验收性能门槛**

调优方案（分四层，按见效顺序）：
1. **数据库层（首要，主因在存储与并行度）**：
   - 存储改为分布式存储或高转速 SSD（原机械盘为批处理劣化主因），IOPS 提升目标 ≥ 5 倍；
   - 达梦开启列存表/列分区（分区表按日期或机构分区，单表 8200 万行按分区裁剪）、调整并行度与缓冲池、开启执行计划监控；
   - 对高频统计类查询建立物化汇总表或物化视图，批处理中的"全表扫描+反复聚合"改为增量汇总；
   - 批处理 SQL 逐条做执行计划分析（重点：全表连接无索引、函数作用在索引列导致索引失效、`CONNECT BY` 改递归 CTE 后未加 hint）；
   - 批处理改写为"分片并行 + 断点续跑"（按机构或时间片切分，单片事务幂等，支持中断续跑），把 7.2 小时压缩为可接受窗口。
2. **应用层**：
   - 消除 N+1 查询与无索引外键关联，关键接口 SQL 治理（Top SQL 清单逐条优化）；
   - 引入连接池参数调优、批量读写改批量接口、大字段异步加载；
   - 引入本地缓存与结果缓存（可结合 11-11 的缓存治理口径）。
3. **资源隔离层**：
   - 在线交易与批处理分时错峰（批处理窗口从低峰提前至 01:00 起，避开在线高峰）；必要时独立实例或独立存储资源池；
   - 设置批处理资源配额上限，防止批处理挤占在线连接池与 CPU（可配资源组与并发度上限）。
4. **容量与观测层**：
   - 压测基线化：按真实业务配比（在线 80%、批处理 20%）构造混合负载，输出 P50/P95/P99、吞吐、批处理时长三项；
   - 上线后按批处理分片耗时、总时长、失败分片数设置告警。

验收性能门槛（建议写入合同与验收标准）：
- 关键交易接口 P95 ≤ 原系统 820 毫秒 × 1.10 = 902 毫秒（即劣化不超过 10%），P99 ≤ 1500 毫秒；
- 吞吐量 ≥ 原系统的 90%；
- 错误率 ≤ 0.1%；
- 批处理总时长 ≤ 原系统 4.5 小时 × 1.10 = 4.95 小时（即不超过 4 小时 57 分），且单分片失败可断点续跑、整体成功率 ≥ 99.9%；
- 压测通过标准：连续 3 轮压测结果偏差 ≤ 5%，峰值 1.5 倍负载下 P95 劣化 ≤ 15%；
- 监控告警上线并通过一次真实告警演练（告警触发、通知、处置、闭环四步留痕）。

**问题 6：验收方案**

验收组织：
- 成立验收组：组长由市局分管领导担任，成员含业务处室负责人 2 名、技术负责人 1 名、运维负责人 1 名、安全负责人 1 名、外部专家 1 名，合计不少于 5 人且为单数；监理单位列席但不代替验收组；
- 设立三个独立检查口：业务口（功能符合性）、技术口（性能与兼容）、合规口（安全、文档、第三方报告）；三方任一不通过则不得进入下一环节；
- 财务与资产口核对预算执行、资产登记、原厂支持与质保条款。

验收流程（三阶段）：
1. **初验**：在准生产环境完成功能回归、兼容性验证、性能对比初测、数据一致性校验，出具《初验报告》与整改台账；初验不通过不得进入试运行；
2. **试运行**：连续 15~30 天正式环境运行（至少覆盖一个完整月结与对账周期），出具《试运行报告》（含可用性、事件统计、缺陷清单、业务部门签字确认）；
3. **终验**：审查全部证据材料与整改闭环，出具终验结论。终验前必须取得：第三方软件测评机构出具的《软件测试报告》与《信创适配认证报告》，以及监理单位的《监理总结报告》。

必须提交的证据材料清单：
- 需求规格说明书（补齐 340 个功能点后）、概要设计、详细设计、数据库设计说明书（对象转换对照表）、部署手册、运维手册（含日常巡检表、故障处置手册、应急预案与演练记录）、用户操作手册；
- 适配矩阵终版与逐项验证记录；国产化测试环境说明；
- 功能回归测试报告（含 340 个功能点的用例与执行记录、缺陷闭环清单）、性能对比压测报告（迁移前后同负载）、数据迁移校验报告（四层校验输出）、双轨比对报告与对账台账、割接方案与回切脚本演练记录、割接实施记录；
- 安全类：漏洞扫描报告、权限矩阵、审计日志抽查记录、密码应用安全性评估（密评）结论；
- 培训记录与考核结果、原厂支持终止前的源码与文档交接单；
- 预算执行情况表、资产登记与许可清单。

"61 个口头认定通过"功能点的处理：
1. 逐条回溯：由业务经办人 + 业务处室负责人共同确认每个功能点的业务规则描述，形成书面功能说明与验收用例（含前置条件、操作步骤、预期结果、判定规则），**不认可只凭口头认定的通过结论**；
2. 补测：按功能点类型分级补测——资金发放类、权限控制类、状态流转类 100% 补测并留存执行记录；查询展示类、报表打印类按不少于 30% 抽样补测，剩余功能点至少完成端到端演示并录制演示证据；
3. 回溯历史数据影响：61 个功能点若涉及历史数据展示或金额计算，须一并核对其数据在迁移后的正确性，纳入数据校验第二至第四层；
4. 缺陷闭环：补测发现缺陷全部登记闭环，未闭环的功能点不得标记通过；
5. 结论：本批 61 个功能点应判定为"验收证据不足、暂缓通过"，整改与补测完成并经业务签字后随《功能点补充确认书》一并提交终验组复核；终验报告中须单列该项，不得以"已口头认定"计入通过率。

**问题 7：运维交接与知识转移方案**

1. **人员能力建设**：
   - 现状缺口 9 人（数据库 3、中间件 2、国密改造 2、监控与告警 2），现有 4 人无国产平台经验——差距 5 人且技能维度不匹配；方案为"外部引入 + 内部转岗 + 厂商托管"三管齐下：引入具备国产数据库运维认证人员 2 人、中间件 1 人；内部 4 人 3 个月内完成认证培训；国密改造岗位 2 人由具备国密合规经验方补齐；
   - 培训计划：分四批（数据库 DM8、东方通 TongWeb、麒麟 V10、监控与故障处置），每批不少于 40 学时并有实操考核，考核通过率 100% 方可上岗；
   - 知识库沉淀：把割接手册、常见故障处置、双写对账操作、批处理分片续跑、应急预案全部转为标准作业程序（SOP），纳入运维知识库并指定唯一责任人维护；
   - 预算调整：从软件开发 1580 万与风险预留 60 万中调剂不低于 120 万用于培训、认证与知识库建设（本次预算缺口是明确缺陷）。
2. **原厂退出衔接**：
   - 明确原厂支持终止时点（验收后 6 个月）与交接前置条件（源码、部署脚本、配置基线、账号与密钥清单、运维手册、已知问题清单全部移交并经我方验证通过）；
   - 设置 3 个月并行值守期：原厂与新团队共同值班，原厂处理我方独立无法处置的事件不超过 20%（超出即说明能力未建成）；
   - 过渡期退出判据：连续 30 天 P1 事件由新团队独立闭环率 ≥ 90%，核心系统无未移交的知识盲区，遗留待办清单清零。
3. **遗留系统处置**：
   - 旧系统停机后进入 30 天只读归档期，禁止物理删除；
   - 归档内容：数据库全量备份 + 校验和、配置与脚本、源码或安装介质（如有）、运维与业务文档、原厂合同与许可；
   - 数据处置：按数据安全法与档案管理规定分类保管，涉及个人信息的按保留期到期安全销毁（不可恢复），出具《数据销毁记录》并由业务、安全、运维三方签认；
   - 硬件与许可：服务器、存储、网络设备按资产流程回收或再分配；数据库与中间件许可按迁移后实际用量重新授权，避免重复付费；
   - 到期后编写《旧系统退役报告》（退役时间、数据去向、资产去向、遗留风险）。
4. **文档沉淀与知识资产化**：
   - 建立"改造资产包"：需求、设计、测试、割接、运维、应急、交接全套文档纳入知识库统一管理（配置管理基线 + 版本编号 + 密级标注）；
   - 每类运维场景形成标准作业程序与检查单（日常巡检、月度补丁、季度应急演练、年度演练等），配套责任人与频次；
   - 复盘：项目结束组织一次经验教训复盘，形成《信创改造复盘报告》，纳入单位知识资产。

## 踩分要点

1. **先给处置策略再给实施步骤**：题目问"如何改造"，答题必须先明确是"维持/改造/替换/退役"哪一条路径或绞杀者模式，再展开迁移与灰度，否则层次错乱。
2. **兼容性适配矩阵必答列**：业务系统、组件类别、原方案、目标方案、兼容等级、不兼容类型、改造措施、工作量、责任方、验证方式与结论——列不全即丢分。
3. **字符集与排序问题必须答到根因**：不是"改成 UTF-8"就完事，必须点出"拼音排序依赖操作系统 locale / 依赖默认 collation"，并给出"建立显式排序键列、应用侧按排序键排序"这一可落地措施；空串与 NULL 语义必须明确"二选一并全库一致 + 应用侧禁用隐式比较"。
4. **SQL 语法必须给等价改写**：ROWNUM→窗口函数、ISNULL→NVL、GETDATE→参数化、CONNECT BY→递归 CTE、序列触发器→目标库序列，每条都要写改写后形态，只说"语法不兼容需改造"不得分。
5. **回切必须给时间指标**：15 分钟内完成回切 + 回切脚本须演练 2 次 + 回切授权单点，这是区分"有方案"与"无方案"的关键分水岭。
6. **灰度阶梯必须给观察窗口与硬阈值**：阶梯（1%→5%→20%→50%→100%）、观察窗口 ≥ 3 个完整业务日且覆盖月结、阈值（错误率 > 0.5%、P95 > 130%、对账差异率 > 0.01%、交易量偏差 > 2%、关键用例失败 ≥ 1）——五个阈值缺一扣分。
7. **性能劣化必带对比基准与容差**：劣化 44% 必须对照原系统 820 毫秒给出目标 902 毫秒（+10%），批处理 4.5 小时对应 4.95 小时；不能只写"优化性能"。
8. **数据校验答四层递进**：总量级（行数/金额/状态）、主键级（双向差集）、关键字段级（分桶抽样或全量）、业务逻辑级（对账结转）——只答"核对数据一致"必丢分。
9. **验收证据思维**：每个标准都要有出处（报告编号、签认单、截图、日志位置）；"完成测试"不算，"通过率 99.5% + 报告编号 + 缺陷闭环清零"才算。
10. **口头认定的功能点要敢于判"暂缓通过"**：并给出补文档 + 分级补测 + 回溯历史数据 + 缺陷闭环 + 单列提交的完整处置，这正是本题区分高级与中级答卷的关键点。
11. **运维交接要写人、钱、时间三要素**：9 人缺口如何补、120 万培训预算从哪出、原厂 6 个月后退出如何衔接（3 个月并行值守 + 30 天独立闭环率 90%）。
12. **分阶段路径必带量化出口标准**：每个阶段给里程碑、交付物、可量化的验收阈值（功能点覆盖率、扫描命中数、比对差异数、回切分钟数、对账差异率），只写"完成改造"不合格。
13. **预算结构分析要提一句**：适配测试与迁移实施占比偏低、风险预留 2.1% 低于 8%~10% 经验区间，体现成本意识。
14. **全篇主线一致**：所有措施均围绕"降低割接风险、保证数据可回退、确保项目可持续运行"三条主线，不要写成技术科普。

## 记忆口诀

**口诀一：遗留系统四把刀**
维持改造换退役，绞杀模式外围包；防腐适配新模型，分支抽象统一口；隐性依赖先测绘，路线不明不动刀。

**口诀二：信创适配六类坑**
指令原生要重编，语法方言逐句改；字符排序建键列，空串空值语义定；中间运行时参数差，外设驱动最易缺；第三方接口与许可，暂不支持早澄清。

**口诀三：迁移校验四层楼**
总量行数金额对，主键差集双向推；关键字段分桶抽，业务对账结转校；四层差异零为准，口头说我一律不。

**口诀四：灰度切量五步走**
影子比对不上返，试点一档先小跑；五二五一逐级放，三日观察含月结；阈值触发即回切，十五分钟必须到；回切演练两次过，从头再爬不跳档。

**口诀五：性能三指标要记牢**
P95 不超一成，吞吐保住九成；批处理十一成内，错误千分之一顶；压测三轮差不超五，压垮一成半以内。

**口诀六：验收证据三不要**
不要口头认通过，不要只写已完成，不要空说无问题；每条标准有出处，签字报告才是据。

**口诀七：交接三件事**
人会了才能接，九人缺口要补齐；十二万培训费，技能得配证书；原厂退出设过渡，三月并行三十天；旧机只读满月再，销毁记录要签全。

**口诀八：阶段出口要量化**
P0 需求与路线定，P1 适配与性能平，P2 演练回切证，P3 切量交接稳；每阶段带交付物，量化阈值不放过。
