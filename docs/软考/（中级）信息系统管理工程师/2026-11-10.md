## 今日核心概念

### 1. 软件配置管理（SCM）三大要素与配置项全生命周期

定义：软件配置管理是用配置管理的方法和工具，对软件产品的全部配置项（Configuration Item，CI）进行识别、版本控制、变更控制、状态记录与配置审计，从而保证产品在整个生命周期内的**完整性、一致性、可追溯性、可复现性**。SCM 的核心是回答三个问题：**现在交付的到底是哪个版本（标识）、它由什么组成（版本）、它为什么变成这样（变更与审计）**。

关键要点：

1. **SCM 三大核心要素（考试高频）**：
   - **版本控制（Version Control）**：对配置项的每一次修改赋予唯一标识（版本号），保留全部历史，支持差异比较（diff）、回退（revert/restore）、分支（branch）与合并（merge）。解决"改了什么、谁改的、能不能退回去"。
   - **变更控制（Change Control）**：对配置项的变更施加申请—评估—审批—实施—验证—记录的全流程控制，确保变更经过授权、可追溯、可回退。解决"该不该改、谁批的、改完有没有验证"。
   - **状态记录（Status Accounting）**：记录每个配置项在任一时刻的状态（草稿/评审中/已批准/已发布/作废）与对应版本，形成配置状态报告与配置项清单。解决"现在系统里跑的是哪一版、依据什么在运行"。
   - 补充：**配置标识（Configuration Identification）** 是前提，**配置审计（Configuration Audit）** 是保障。四者合称 SCM 的基本活动。

2. **配置项识别与命名规范**：
   - 纳入管理的不只是源码：源代码、脚本、编译与打包配置、依赖清单（依赖锁定文件）、数据库脚本与迁移文件、接口契约文档、设计文档、测试用例与测试数据、部署编排文件、镜像与制品、运维配置模板、第三方许可清单。
   - 命名规则三要素：**类型前缀 + 模块 + 版本 + 状态**，例如 `PAY-GATEWAY-v3.2.0-REL`。禁止出现"最终版""新版""最新""test""新建文本文档"等无语义命名。
   - **基线（Baseline）** 是在某一时刻经正式评审批准、作为后续工作基础的一组配置项的集合，一经建立只能通过正式变更控制修改。典型三类基线：
     - **功能基线（Functional Baseline, FCA 对应）**：需求与设计确定后形成的基线，回答"做什么"。
     - **分配基线（Allocated Baseline, PCA 对应）**：任务分配与责任落实后形成，回答"谁来做"。
     - **产品基线（Product Baseline）**：配置项组装成产品、交付或安装到目标运行环境时形成，回答"交付什么"。
   - **基线化（Baselining）** 的实质是"冻结 + 挂账"：把一组配置项的版本号固定、登记入册，此后任何修改都必须走变更流程并产生新基线。

3. **CMDB（配置管理数据库）与配置审计**：
   - CMDB 存放 CI 的属性、关系与状态，是配置管理与运维管理（CMDB 驱动变更、自动化运维、影响分析）的共同底座；中级教材中它同时出现在「ITSM 配置管理」与「ITIL 实践」两处，需注意两者关系：**ITSM 的配置管理是流程视角，CMDB 是数据视角**。
   - **配置审计**分两类：
     - **功能配置审计（FCA）**：核查配置项是否满足需求与设计规格的一致性，**审计"做对了吗"**，一般在验收前进行。
     - **物理配置审计（PCA）**：核查交付物与配置记录（版本、数量、状态）是否一致，**审计"交付全了吗、是不是同一版"**，一般在上线前进行。
   - 未通过配置审计不得进入下一阶段，这是防止"开发库直接当生产用"的第一道闸门。

4. **易错辨析（务必分清）**：
   - 配置管理 ≠ 文档管理：文档管理关注"文字资料"，配置管理关注"可交付物的版本与状态"，文档本身也是配置项之一。
   - 配置管理 ≠ 变更管理：变更是配置管理的一部分，配置管理还包含标识、版本、状态与审计。
   - 配置库（受控库）≠ 代码托管平台全量：受控库只存放**已通过评审与验证**的基线版本，开发库中的中间产物不得进入受控库。

### 2. 配置库结构、版本控制原理与分支策略

定义：配置库是按配置项状态划分的分层存储空间，通过"库分层 + 基线推进"实现配置项从开发到生产的受控流转；版本控制是记录配置项全部历史版本的技术机制，分支策略则是团队在并行开发与集成分成之间的取舍规则。

关键要点：

1. **三类配置库（传统配置库模型）**：
   - **开发库（Dynamic Library）**：开发人员自由使用，可存放中间产物、临时文件；变更频繁，无严格评审；**严禁直接被生产环境使用**。
   - **受控库（Controlled Library）**：存放通过评审与测试、达到基线要求的配置项；变更需经变更控制流程审批；是集成与测试的输入。
   - **产品库（Static/Product Library）**：存放最终发布版本，仅在发布时由配置管理员从受控库复制生成；**任何改动都是新版本发布动作**，不允许直接修改。
   - 现代实践中三者常由分支策略替代（主干即产品库语义、特性分支即受控库语义），但**理念完全一致**，答题时应能双向映射。

2. **版本控制核心操作与术语**：
   - **签出（Checkout）/ 签入（Check-in）**：签出取得可写副本，签入提交修改；集中式版本库有锁定（Lock）机制防止并发覆盖，分布式版本库（Git）用"提交（Commit）—合并（Merge）"取代锁定。
   - **分支（Branch）**：从某基线派生出的并行开发线，用于隔离特性开发与缺陷修复。
   - **合并（Merge）**：将分支修改并回主干，冲突必须**人工解决并评审**，禁止自动"ours/theirs"一刀切。
   - **标签（Tag）**：指向特定提交的可读名称，用于标识一次发布（`release-v3.2.0`），**发布后标签不可移动**（不可变）。
   - **提交（Commit）** 的重要性提交信息规范：`类型(模块): 摘要 + 关联需求号/缺陷号 + 变更原因`。**提交信息与需求编号的关联是审计追溯的最小单元**。
   - **差异比较（Diff）**、**三方合并（Three-way merge）**：合并基线、当前分支、目标分支三个版本，是理解冲突成因的关键。

3. **分支策略三大模型**：
   - **主干开发（Trunk-based）**：所有开发直接提交主干，配合特性开关（Feature Flag）控制发布可见性，发布频率高、贴近主干开发。适合持续交付、团队规模适中、有自动化测试保障的团队。
   - **Git Flow**：长期分支（main/develop）+ 特性（feature）+ 发布（release）+ 热修（hotfix）多类分支，阶段清晰、适合有明确发布版本的传统交付；但分支合并成本高、发布周期长。
   - **环境分支（Environment Branch）**：按环境（开发/测试/预生产/生产）建分支，改动从低环境流向高环境，合规审计友好，但易产生大量合并冲突。
   - **选型判据**：交付频率要求高 + 自动化测试完善 → 主干开发；多版本长期并行维护 + 强流程管控 → Git Flow；强合规审计、变更评审为强约束的行业 → 环境分支或受控库模型。**在案例中给出选择并说明理由，是高频采分点。**

4. **版本号规范（SemVer 语义化版本）与版本标识**：
   - **主版本号.次版本号.修订号**：`MAJOR.MINOR.PATCH`。
     - **MAJOR**：不兼容的 API 变更（如从 v2 升级 v3，需业务系统改造）。
     - **MINOR**：向后兼容的新功能。
     - **PATCH**：向后兼容的缺陷修复。
   - 版本后缀标记预发布与构建：`1.4.0-alpha.1`（内部测试）、`1.4.0-rc.2`（候选发布）、`1.4.0+build.20261110`（构建元数据）。
   - **企业内网应用与政务系统**可简化为 `大版本.小版本.修订号`，但**必须明文规定"哪些变更允许升哪一段"**，否则版本号失去管理意义。
   - **配置项标识（CIV）与版本号不是一回事**：CIV 用于唯一标识一个配置项（如 `PAY-GATEWAY`），版本号标识该项的某一状态；二者组合才构成"某项的某版"。

5. **常见配置管理失效的典型症状（背下来做案例诊断锚点）**：
   - 同一环境不同机器代码版本不一致（部署未统一来源）。
   - 无法回答"线上跑的到底是哪次提交"（未打标签、未记录版本）。
   - 上一可用版本被覆盖，无法回退（制品库无保留策略、历史包被清理）。
   - 开发人员本地直接改生产配置绕过流程（配置即代码未落地）。
   - 数据库变更脚本与代码版本不对应（迁移文件未纳入版本控制）。
   - 合并冲突由开发私自"全部保留自己版本"处理（无评审、无审计）。

### 3. 持续集成与持续交付（CI/CD）流水线与质量门禁

定义：持续集成（Continuous Integration，CI）是指开发人员频繁将代码变更合并到主干，每次合并都通过**自动化构建与测试**来验证；持续交付（Continuous Delivery，CD）在此基础上进一步保证**任何时刻主干上的版本都能被可靠地、一键地部署到生产环境**，交付成为团队的日常动作而非项目末尾的事件。

关键要点：

1. **CI/CD 流水线标准阶段（八段流水线模型）**：
   - **代码检出（Checkout）**：按标签或提交号检出，保证可复现。
   - **依赖安装（Dependency Install）**：依赖清单锁定文件必须入库，防止"今天能装明天装不上"。
   - **静态检查（Static Analysis）**：代码规范、潜在缺陷、许可证合规扫描（开源组件许可证与 CVE 漏洞扫描）。
   - **单元测试（Unit Test）**：覆盖率门槛、失败即阻断。
   - **构建打包（Build & Package）**：产出不可变制品（镜像/安装包），**制品一旦生成不再修改**，以摘要哈希标识。
   - **集成测试（Integration & E2E）**：接口联调、数据库迁移验证、端到端用例。
   - **安全扫描（SAST/DAST/依赖漏洞）**：与流水线绑定，阻断高危。
   - **部署与验证（Deploy & Verify）**：部署到目标环境并执行冒烟验证。
   - 全链路原则：**流水线即代码（Pipeline as Code）**，流水线定义文件与业务代码一并版本化、评审、变更，任何人不得在界面上手工改流水线。

2. **质量门禁（Quality Gate）**：
   - 定义：门禁是流水线上的**准入判定点**，未达标即阻断流水线、不得进入下一环节与下一环境，**不允许"先合入后补救"**。
   - 典型门禁项与建议阈值：单元测试覆盖率 ≥ 60%（核心模块 ≥ 80%）、静态检查零严重告警、依赖无高危 CVE、开源许可证无冲突、代码评审通过人数 ≥ 2 且至少 1 人非作者、集成测试通过率 100%、性能基准劣化幅度 ≤ 10%、数据库迁移脚本可正向执行且可回滚。
   - **门禁阈值必须写在代码库里并随代码演进**，一次只调一个变量并记录原因；**随意放宽阈值以让流水线"变绿"是配置管理失效的典型表现**。
   - **例外通道（Break-glass）**：紧急修复允许绕过部分门禁，但必须记录审批人、原因、绕过项，并**在下一个工作日内补齐完整回归与评审**——这是"紧急上线占比过高"的制度出口，也是案例题的常见采分点。

3. **制品与环境管理**：
   - **制品库（Artifact Repository）**：保存所有不可变制品，**同一版本号对应唯一哈希**，禁止"同号覆盖"（同号必同物）。
   - **保留策略**：至少保留最近 N 个版本与全部生产发布过的版本（生产版本永久保留或按合规年限保留），确保**任意历史生产版本可随时取回**——这是回滚能力的物理前提。
   - **四类环境职责**：开发（开发自测）→ 测试（功能与集成测试）→ 预生产（贴近生产的配置与数据，用于演练与验收）→ 生产。**原则：配置一致、路径一致、版本唯一**；严禁在生产环境做测试性修改。

4. **CI/CD 与运维、变更、测试的接口**：
   - CI/CD 是**自动化的变更实施手段**，不替代变更管理：**流水线跑通不等于获批上线**，生产发布仍需走变更评审与窗口管理。
   - 流水线承担回归测试与性能基准，是"变更质量守门人"；与配置审计（PCA/FCA）配合，构成交付前的最后一道防线。
   - **度量指标**：变更前置时间（Lead Time for Changes）、部署频率、变更失败率、平均恢复时长、流水线通过率、门禁阻断次数、缺陷逃逸率。**这四项 DORA 指标是中级教材「IT 运维/服务度量」的常见考点。**

5. **与中级教材「信息系统运行维护」章节的接口**：
   - 运维侧最常见的配置管理诉求是"**环境一致性**"（开发能跑通的东西，生产一定能跑通），本质是用**自动化 + 不可变制品 + 声明式配置**消除手工漂移。
   - 常见故障归因：手工改配置导致的漂移、版本混用、依赖版本漂移、密钥与配置混放（密钥必须外置到密钥管理服务，不得入库）。

### 4. 发布管理：发布类型、发布流程、灰度与回滚

定义：发布管理（Release Management）是对配置项从受控库经审批、构建、验证、部署到生产环境并对用户生效的全过程管理，目标是在**可追溯、可回滚、不中断或少中断**的前提下把变更安全地交付给用户。

关键要点：

1. **发布类型四分类**：
   - **重大版本发布（Major Release）**：功能与架构变化大，需完整测试周期与上线方案，通常安排在业务低谷窗口。
   - **增量发布（Incremental Release）**：分批逐步放量，风险可控。
   - **紧急发布（Emergency/Hotfix Release）**：为修复影响生产的高危缺陷，未经完整回归即上线，**必须事后补审补测**。
   - **补丁发布（Patch Release）**：仅修复缺陷，范围小、影响可控，但仍需回归与回滚预案。
   - 配套还有**打补丁（Hot Patching）**：不停机在线替换程序文件，适用于高可用集群，需验证会话与连接不中断。

2. **标准发布流程（八步）**：
   - ① 需求/缺陷登记并纳入版本计划（版本内容冻结，形成发布范围清单）。
   - ② 开发与自测完成，提交合并请求（MR/PR），通过代码评审。
   - ③ 流水线自动构建与测试，产出不可变制品并打版本标签。
   - ④ 部署到测试环境完成系统测试与回归，形成测试报告。
   - ⑤ 部署到预生产环境做演练、性能压测、数据迁移验证与业务确认。
   - ⑥ 发布评审（发布申请、影响分析、风险评估、回滚预案审核、窗口与值班安排），经授权人批准。
   - ⑦ 正式部署与上线验证（冒烟测试、关键业务点检、监控看板值守）。
   - ⑧ 发布确认与归档（发布记录、更新配置状态与基线、更新用户文档、关闭发布单）。
   - **贯穿全程的三条底线**：有记录、可回滚、不越权（未审批不上生产）。

3. **灰度发布与蓝绿、金丝雀**：
   - **金丝雀发布**：先向少量用户/少量流量开放，观察指标后逐步扩大范围；**核心判据是设定观察窗口与回滚阈值**（如错误率 > 1% 或 P99 劣化 > 20% 自动回滚）。
   - **蓝绿发布**：准备蓝（现网）与绿（新版本）两套环境，切换流量后绿承接；**回滚即切回蓝**，秒级恢复，代价是双份资源成本。
   - **A/B 测试**：用于效果验证而非发布风险管理，目标不同，切勿混淆。
   - **滚动发布**：逐批替换实例，适合无状态服务；**有状态服务需先处理会话粘滞与数据兼容**。

4. **回滚机制与不可回滚场景**：
   - **回滚三要素**：可回滚的制品（历史版本仍在制品库）、可回滚的数据库结构、可回滚的配置与数据。
   - **数据库变更最易导致"不可回滚"**：新增非空列带默认值尚可回滚；**删除列、修改列类型、重命名表**在生产已写入新数据后往往无法回退。因此规范要求：**采用"扩展—迁移—收缩"三步（加新列→双写与回填→确认稳定后再删旧列）**，保证任一时刻可退；**破坏性变更必须走专项评审**。
   - **不可逆变更清单**（一旦执行即不可回退，必须双人复核 + 数据备份 + 灰度 + 专项审批）：数据删除、字段类型变更、表重命名、接口契约不兼容变更、消息队列结构变更、证书与密钥轮换、第三方接口下线。
   - **回滚失败的三种典型原因**：上一个可用制品已被覆盖；数据库脚本未配套反向脚本；回滚时依赖的外部系统状态已变（如已发短信、已扣款、已推送到下游）。

5. **发布窗口与冻结期**：
   - 高峰期（年末考核、医保结算季、招生季）、重大活动与节假日期间执行**变更冻结**；紧急事项走例外审批并事后复盘。
   - 发布窗口须同步安排：值班人员到位、监控看板值守、回滚决策人在线、第三方（云厂商、支付、短信）协同时间。

6. **移动端与多端发布的特殊问题**：
   - 移动端存在**版本碎片化与强制更新**问题：强制更新会导致低版本用户直接不可用，需评估存量用户最低版本、灰度节奏与"仅提示不强制"的过渡期。
   - **签名与包体一致性**：应用签名不一致会导致安装失败或覆盖安装失败；最低系统版本要求提高会造成部分设备"变砖"式不可用。
   - **包体大小与下发灰度**、**热修复（热补丁）**的合规与安全边界需在发布方案中说明。

### 5. 配置管理的组织职责、制度与度量体系

定义：配置管理的落地依赖明确的**角色分工**（配置管理员、开发、测试、运维、质量保证、发布审批人）、**制度文件**（配置管理计划、变更管理办法、发布管理制度、命名与版本规范）与**度量指标**三者到位，工具只是承载。

关键要点：

1. **角色与职责（考试高频）**：
   - **配置管理员（CMO）**：制定并维护配置管理计划，识别配置项与基线，管理配置库与配置状态，组织配置审计，保管配置记录；**对配置项的完整性负责，不对代码质量负责**。
   - **开发人员**：按规范提交变更、编写单元测试、维护版本与提交信息、配合评审与审计。
   - **测试人员**：验证配置项功能与性能，出具测试报告，确认基线可发布。
   - **运维人员**：按发布方案实施部署、执行配置项落地、维护环境一致性、保留操作日志。
   - **质量保证（QA）**：独立审计配置管理过程合规性，**不承担具体配置操作**（独立性是审计有效的前提）。
   - **发布审批人/变更控制委员会（CAB）**：批准或否决发布与重大变更，对风险与回滚方案负责。
   - **配置项负责人（CI Owner）**：负责某一配置项的标识、版本、变更与状态维护。

2. **必备制度文件清单（案例题"还缺什么"的答题模板）**：
   - 配置管理计划（配置项清单、命名与版本规范、库结构与权限、基线点、工具与职责、审计安排）。
   - 变更管理办法（含分级审批矩阵、紧急通道与后补审时限）。
   - 发布管理制度（发布流程八步、发布窗口与冻结期、灰度与回滚要求、发布记录模板）。
   - 代码评审规范（评审人资格、最少人数、检查清单、禁止自审自批）。
   - 制品与版本库保留策略、账号权限与离职交接制度（含外包人员权限回收）。
   - 第三方/外包代码与开源组件治理（许可证清单、SBOM、漏洞扫描）。

3. **度量指标体系（十条常用指标及目标方向）**：
   - 变更成功率、变更失败率、变更前置时间、部署频率、平均恢复时间（MTTR）、缺陷逃逸率、流水线通过率与时长、门禁阻断次数、配置审计不符合项数、制品版本可回溯率（历史生产版本可取回比例）。
   - **目标设定原则**：基线先行（先测现状再定目标）、单一维度先行（一次改一类指标）、指标与激励挂钩（否则数据造假）、**负向指标必须配正向指标防止指标驱动行为**（如只看"变更失败率低"会压制变更频次，导致"什么都不敢改"）。
   - **DORA 四指标**（部署频率、变更前置时间、变更失败率、平均恢复时间）是中级教材新版本新增考点，务必掌握其含义与"高绩效团队四项全优"的表现。

4. **外包与多团队协作场景的高风险点**：
   - 外包团队账号权限随人员流动未及时回收；代码仓库权限与合同期不匹配。
   - 多团队并行开发缺少分支与合并规范，造成**合并地狱**（主干长期冲突、集成频率下降）。
   - 各团队各自维护部署脚本与配置模板，导致**生产环境路径与配置不一致**。
   - 交付物仅交源代码不交构建脚本与依赖清单，接手方无法复现构建——**构建可复现性是配置管理的底线检验**。

5. **配置管理的价值链定位**：
   - 对**开发侧**：减少集成地狱、缺陷可追溯、变更可定位。
   - 对**测试侧**：回归范围可控、缺陷复现可重现。
   - 对**运维侧**：环境一致、版本可查、回滚可执行、故障定位时间缩短。
   - 对**审计与监管**：满足等保测评、行业监管对"版本可追溯、变更可审计"的要求，也是信息系统管理工程师岗位的核心职责之一。

## 案例分析题

**题目**：

某市政务服务管理局建设"一网通办"移动端应用（含统一身份认证、跨省通办、医保电子凭证调取、公积金查询、惠企政策直达五个模块），由 1 家本体单位运维团队（6 人）与 3 家外包开发公司（共 47 人）混合开发。系统系统自 2025 年 3 月上线以来累计发布 43 次，平均每两周一次。近期现状如下：

**一、代码与版本管理**
- 3 家外包公司各建 1 个代码仓库（共 3 个），本体运维团队另用 1 个版本库管理配置脚本，**四套库互不联通**，无统一主干与分支策略；各供应商每周合并一次，冲突平均 47 处/次，平均解决耗时 6.5 小时，集成节奏被迫压缩。
- **代码评审执行率 0%**，提交者自行合并（自审自批占比 100%）。
- 无语义化版本规范，版本号由开发手写，取值形如 `v1.2`、`最新版`、`测试版`；**无法回答"线上跑的是哪次提交"**。
- 制品由开发组长本地打包后上传服务器，**无制品库**；同一版本号被重复覆盖 3 次，**上一个可用安装包已无法取回**；2026 年 8 月 21 日回滚时因取不到旧包失败，故障持续 6.8 小时。

**二、构建、测试与流水线**
- 无 CI/CD 平台，**全流程人工**：编译、打包、测试、上传均手工执行，单次回归测试需 3 个工作日，测试通过率仅 61%（含 23% 用例长期跳过）。
- 无覆盖率门槛、无静态检查、无依赖漏洞扫描、无开源许可证扫描。
- 37 个第三方组件未纳入版本控制与台账管理，扫描发现 **6 个存在高危 CVE**、**8 个为 GPL 协议且未做合规审查**。

**三、数据库变更**
- 14 次发布中 **9 次由开发手工执行 SQL**，无迁移脚本、未纳入版本控制、无正向/反向脚本。
- 2026 年 8 月 21 日发布中删除 `T_CREDIT_BALANCE.OLD_AMOUNT` 字段并清空历史数据，触发回滚失败，**医保电子凭证调取失败 42 次**、公积金查询错误 1.3 万次，局方已向服务对象致歉并扣减承建方当月考核款 12 万元。

**四、发布与回滚**
- 全部为**全量直接发布，无灰度**；近 6 个月 2 次发布引发生产故障（4 月 12 日 30% 用户反馈"查不到公积金"；8 月 21 日服务中断 6.8 小时）。
- **紧急发布 11 次，其中仅 3 次做了事后回归测试**，8 次属"先上线、后补测"。
- 2026 年 6 月一次将移动端最低系统版本从 Android 8 提升至 Android 10，**未做存量用户评估**，约 12% 用户应用无法启动使用，投诉 2100 余件。

**五、权限与外包治理**
- 外包人员离场后**保留账号 9 个**未回收，其中 3 个仍可登录生产环境查看敏感信息；外包团队持有生产配置文件的写权限。
- 权限无季度复核机制，无操作审计留存；无代码仓库、制品库、云资源的操作审计。

**六、度量和合规**
- 近 6 个月发布 43 次，平均故障恢复 6.8 小时，缺陷逃逸至生产 87 个；未开展配置审计。
- 等保测评中"版本可追溯、变更可审计"条款被判为不符合项，需限期整改；局方已批准 180 万元专项整改预算（配置管理平台与流水线建设 96 万、制品库与制品迁移 18 万、权限治理与第三方组件合规整改 26 万、外部咨询与培训 40 万）。

1. 指出该项目在软件配置管理、版本控制与发布管理方面存在的**主要问题**（至少列出 8 项，按严重程度排序并说明后果）。

**二、统一代码库与分支策略方案**

1. **代码库统一**：建立**单一主干仓库**（1 个主仓库 + 3 个子模块/前端后端分仓），3 家外包公司的代码全部纳入本局版本库；配置脚本、数据库迁移脚本、流水线定义、部署编排文件**同库或同组受控**。权限模型：外包团队对主干只具备**推送权（Push）**，无直推主干权，一律走合并请求。
2. **分支策略选择**：采用 **主干开发（Trunk-based）+ 特性开关（Feature Flag）** 为主，辅以**短期热修分支**。
   - **选择理由**：本系统模块多、迭代频繁（两周一版）、需求来自政策变化，交付速度优先；同时"医保凭证调取""公积金查询"等核心模块可用特性开关做到"代码合入即默认关闭、验证通过再开启"，把发布决策从"合代码"推迟到"开开关"，是降低发布风险的关键手段。
   - **不选 Git Flow 的理由**：其多类长期分支与本项目"两周一迭代 + 5 个模块并行"不匹配，会显著拉长集成分支存活期、制造合并冲突，与本次"集成地狱"现状叠加恶化。
   - **不选环境分支为唯一策略的理由**：按环境建分支会产生大量环境间合并冲突，且与"环境配置一致"目标相悖；环境一致性应靠配置即代码 + 声明式部署实现，而非靠分支区分环境。
   - **保留例外**：涉及 Android 最低版本、签名证书、协议不兼容的重大变更，走**发布分支（release-x.y）**，从该分支回合主干。
3. **分支保护与合并规则**：主干禁止直推；合并请求须 **≥2 人评审通过且至少 1 人非作者**；合并必须线性化（禁用自审自批、禁用自动合并）；冲突必须人工解决并由第二人复核；主干合并后自动触发全量流水线，**流水线不绿不得发布**。
4. **版本号规范（SemVer 语义化版本）**：
   - 格式 `MAJOR.MINOR.PATCH[-预发布标识][+构建号]`，例如 `3.4.1-rc.2+build.20261110`。
   - MAJOR：接口契约不兼容变更（需客户端配合改造，如医保凭证调取协议调整）——例如 `2.0.0 → 3.0.0`。
   - MINOR：向后兼容的新功能（新增"惠企政策直达"模块）——例如 `3.3.0 → 3.4.0`。
   - PATCH：向后兼容的缺陷修复与安全补丁——例如 `3.4.0 → 3.4.1`。
   - 预发布标识：`alpha`（内部联调）、`beta`（测试环境验收）、`rc`（候选发布，须通过预生产演练）；正式发布去掉预发布标识。
   - 构建号取提交短哈希（`+build.a1b2c3d`），保证**同一版本号唯一对应唯一制品哈希**。
   - **与配置项标识分离**：`APP-GOV-SERV` 为配置项标识，版本号标识其状态，二者组合构成"某项某版"。
   - **附加规则**：版本号一经发布即**不可复用、不可修改**；已发布版本永久保留在制品库；数据库迁移脚本按版本号顺序编号（`V3_4_1__drop_old_amount.sql`），与版本号一一对应。

**三、CI/CD 流水线与质量门禁方案**

1. **流水线八阶段**：
   - ① 代码检出（按标签或提交哈希，锁定提交，禁止拉取最新分支）
   - ② 依赖安装（依赖锁定文件入库，私有仓库镜像源，校验哈希）
   - ③ 静态检查 + 开源许可证与 SBOM 生成
   - ④ 单元测试 + 覆盖率统计
   - ⑤ 构建打包（产出不可变镜像/安装包，以摘要哈希标识，一次构建多次复用）
   - ⑥ 集成测试 + 数据库迁移正向/反向脚本验证（**迁移脚本必须在空库与生产快照副本上各跑一遍**）
   - ⑦ 安全扫描（SAST + 依赖 CVE 扫描）
   - ⑧ 部署测试环境 + 冒烟与性能基准 → 生成测试报告与发布候选包
   - 流水线定义采用**流水线即代码**，与业务代码同库评审、任何人不得在界面手工改动。
2. **质量门禁指标（≥6 项，均写入代码库并随代码演进）**：
   - 单元测试覆盖率 **≥ 70%**（核心模块：医保凭证调取、公积金查询 **≥ 85%**），且**新增代码覆盖率不低于 80%**（防止"改一行拉低整体"）。
   - 静态检查 **0 个严重级**问题（阻断级 + 警告级双阈值，严重为 0、警告 ≤ 5 且有整改单）。
   - **依赖高危 CVE = 0**，中危 CVE ≤ 3 且有豁免说明与整改期限；GPL 等传染性协议组件 **0 个进入发布制品**，确需使用须经法务书面审查并提供商业授权或替换为 MIT/Apache-2.0 等兼容协议。
   - **代码评审通过人数 ≥ 2**，其中至少 1 人为非本模块作者；评审记录须含检查清单勾选。
   - 集成测试通过率 **100%**，**跳过用例数 = 0**（针对现 23% 长期跳过用例，须全部补齐或书面批准并设置到期日）。
   - **数据库迁移脚本验证通过**（正向可执行 + 反向可回退 + 生产快照副本验证通过），破坏性变更（删列、改类型、重命名）**强制专项评审 + 双人复核**。
   - 性能基准相对基线劣化 **≤ 10%**，超出即阻断。
   - 制品扫描无恶意代码/后门告警，SBOM 完整率 100%。
3. **例外通道（Break-glass）**：仅限影响生产的 P0/P1 安全或资金类缺陷；须记录审批人、原因、绕过项与回滚方案；**T+1 工作日内补齐完整回归与双人评审**；**每月统计例外通道使用次数，超过 2 次即启动根因分析**（防止例外常态化）。
4. **发布候选制品管理**：通过全部门禁的制品自动入库并打 `release-x.y.z-rc.n` 标签；**生产发布只能从制品库取件，禁止现场编译打包**。

**四、发布管理与回滚方案**

1. **发布流程八步固化**：版本计划与范围冻结 → 开发自测 → 合并请求评审 → 流水线构建产出不可变制品 → 测试环境系统测试与回归 → 预生产演练（压测 + 迁移验证 + 业务确认）→ 发布评审（影响分析、风险评级、回滚预案、窗口与值班、授权人批准） → 正式部署与冒烟验证 → 发布确认归档（发布记录、基线更新、配置状态更新、用户文档更新、发布单关闭）。
2. **灰度发布方案**：核心模块（医保电子凭证调取、公积金查询）采用**金丝雀 + 滚动**组合。
   - 灰度维度：先内部账号 → 再 1% 用户 → 5% → 20% → 50% → 100%，每级**观察窗口不少于 30 分钟**（覆盖业务高峰时段的巡检要点）。
   - **自动回滚阈值（示例）**：错误率 > 1%、核心接口 P99 劣化 > 20%、崩溃率 > 0.5%、客诉量 10 分钟内 > 20 件，任一触发即自动回滚并通知发布负责人。
   - 保留**蓝绿双环境**：医保凭证等强一致场景在蓝绿两套环境各部署一份，回滚即切回，秒级恢复，代价为双份资源（约 +35% 计算资源，需在 180 万预算内核算）。
3. **针对"强制更新致 12% 用户不可用"的改进**：
   - **强制更新前置评估**：涉及最低系统版本、权限模型、硬件要求的变更，须先做**存量设备与系统版本分布盘点**（当前 Android 8 及以下占比 12.4%），出具兼容性报告与影响面清单，经发布评审后方可实施。
   - **分级推送策略**：设置**过渡期双版本并行**（老版本继续可用 2 个发布周期），仅在灰度观察指标达标后再提示强制；提供**网页端与小程序端兜底通道**，避免"不可用即无法办事"。
   - **存量用户豁免与降级方案**：对无法升级设备提供功能裁剪版（如仅保留查询类功能），并保留 3 个月的兼容维护承诺。
   - **强制弹窗合规提示**：明确告知不兼容原因、替代路径与截止时间，留存用户确认记录备查。
   - **发布后 72 小时专项值守**，监控崩溃率、启动成功率、差评率三项指标，出现劣化立即停止后续放量。
4. **针对"删字段致不可回滚"的改进（核心）**：
   - **数据库变更全面脚本化并纳入版本控制**：所有 DDL/DML 一律以版本化迁移脚本提交（编号与版本号一一对应），禁止任何手工执行 SQL；**执行主体由流水线统一调度**（迁移任务作为流水线阶段自动执行）。
   - **强制"扩展—迁移—收缩"三步法（Expand-Migrate-Contract）**：
     - 扩展：新增字段/新表/新索引，与旧结构并存（新字段可空或带默认值）。
     - 迁移：应用双写，新旧字段同步写入，进行历史数据回填并校验一致性。
     - 收缩：确认新字段数据完整、**观测期不少于 2 个发布周期**且无回滚需求后，再删除旧字段。
   - **破坏性变更清单**（数据删除、字段类型变更、表重命名、接口契约不兼容、消息结构变更、证书密钥轮换、第三方接口下线）**禁止进入常规发布**，必须走**专项变更评审 + 双人复核 + 数据备份 + 灰度 + 专项审批**六项动作。
   - **数据保护前置**：每次发布前对涉及的数据表做**快照备份并验证可恢复**（每月至少一次真实恢复演练，RPO ≤ 15 分钟、RTO ≤ 2 小时）；迁移前后做**数据比对校验**（行数、金额汇总校验和、抽样明细比对），校验不通过即中止发布。
   - **历史数据清理分离**：8-21 的"清空历史数据"这类动作**不得与结构变更同批发布**，须独立窗口、独立审批、独立回滚方案，且**先备份后执行、执行后立即校验**。
   - **建立"不可回滚变更清单台账"**：登记每一项不可逆变更的内容、执行人、审批人、时间、校验结论，作为审计证据。
5. **回滚三要素与回滚失败防线**：可回滚制品（历史生产版本**永久保留**，禁止同号覆盖）、可回滚数据（迁移反向脚本 + 快照备份）、可回滚配置（配置即代码，变更随版本发布）。**每次发布前必须做一次"回滚可行性验证"**（在预生产实际演练一次回滚，记录耗时），回滚不可行则不允许发布。
6. **发布窗口与冻结**：明确每月 25 日至次月 5 日为高峰冻结期（医保结算周期），冻结期只允许 P0/P1 紧急修复；节假日与重大活动期间同样冻结。

**五、组织、角色、权限、制度保障措施**

1. **组织与角色**：
   - 设立**配置管理委员会**（CAB）：由局信息中心主任任主任，成员含本体运维负责人、3 家外包项目经理、质量保证（QA，独立于开发与运维）、业务处室代表；**审批重大变更、发布申请、破坏性变更、例外通道**。
   - 明确**配置管理员（CMO）**：由本体运维团队专职 1 人担任（不兼任开发），负责配置管理计划、配置项识别与基线、代码库与制品库管理、配置审计组织、发布记录归档。
   - **CI 负责人**：每个配置项（5 个功能模块 + 数据库 + 部署编排）各设 1 名配置项负责人，对该项的版本与状态负责。
   - **QA 独立性**：QA 不参与开发与部署操作，只做过程审计与配置审计，保证审计有效性。
   - **开发人员、测试人员、运维人员、发布审批人**职责按第 5 节概念表落地，写入《配置管理计划》。
2. **权限治理（重点整改项）**：
   - **立即清理 9 个离职外包账号**，回收生产环境访问；建立**账号生命周期台账**（入职开通、岗位变更调整、离职 T+1 回收），与合同期限联动。
   - 外包人员**取消生产配置文件写权限**，生产配置一律通过流水线由流水线账号发布，实现"人能提代码不能改生产"。
   - 权限**季度复核**（每季度末由配置管理员出清单，CAB 审批），外包合同到期自动触发权限冻结。
   - **操作审计全留痕**：代码仓库、制品库、云资源、数据库、配置中心的操作日志集中留存不少于 6 个月（满足等保审计要求）。
   - 落实**最小权限与职责分离**：开发不能自批合并，开发不能操作生产环境（紧急情况走 Break-glass 并全程录像留痕）。
3. **制度文件**（本次须一次性建立 7 份）：
   - 《配置管理计划》（配置项清单与命名规范、库结构与权限、基线点、审计安排）
   - 《代码评审规范》（评审人资格、最少人数、检查清单、禁止自审自批）
   - 《变更管理办法》（分级审批矩阵、Break-glass 通道与 T+1 补审时限）
   - 《发布管理制度》（八步流程、灰度与回滚要求、窗口与冻结期、发布记录模板）
   - 《版本号与制品库管理规范》（SemVer 规则、制品保留策略、同号同物原则）
   - 《数据库变更管理规范》（脚本化、三步法、破坏性变更六项动作、校验要求）
   - 《第三方组件与开源合规管理办法》（SBOM、CVE 扫描、许可证审查、禁止 GPL 进入发布制品）
4. **外包专项治理**：
   - **交付物清单强制化**：每家外包交付时必须提交源码、构建脚本、依赖锁定文件、数据库迁移脚本、部署编排文件、流水线定义、SBOM、测试用例与测试报告、运维手册；**缺项不予验收**，并写入合同条款与验收标准。
   - **构建可复现性验证**：随机指定一家外包，在干净环境按其提交的构建脚本重跑，要求**产出制品哈希一致或差异可解释**，否则整改。
   - **统一流水线强制接入**：外包项目必须接入本局流水线，禁止自建流水线与手工打包；接入情况纳入季度供应商评价。
   - **供应商评价与退出机制**：按交付准时率、缺陷密度、评审一次通过率、回滚配合度、账号合规率打分，连续 2 个季度不合格启动整改或退出；**避免"多方各自维护、各自打包"的局面**。
   - **人员流动报备**：外包团队人员变更须 T+1 报备并同步调整权限，核心岗位设 AB 角，禁止"单点人员依赖"。
   - **知识产权与源码归属**：合同明确所有代码、脚本、文档、SBOM 归本局所有，源码托管平台账号归本局，外包人员仅有受控访问权，**合同到期可无缝接管**。

**六、度量指标体系与分阶段整改路径**

1. **度量指标体系（10 项，含目标值与基线对比）**：

| 指标 | 现状 | 阶段目标 | 口径说明 |
|---|---|---|---|
| 配置审计不符合项数 | 未开展 | 季度 0 项 | 每季度 FCA + PCA 各 1 次 |
| 版本可追溯率（线上版本可定位到提交哈希） | 0% | 100% | 制品标签与提交号一一对应 |
| 历史生产版本可取回率 | 0% | 100% | 制品库永久保留策略生效 |

| 代码评审覆盖率（合并请求经 ≥2 人评审） | 0% | 100% | 合并请求日志统计 |
| 变更前置时间（提交到上线） | 未知，约 14 天 | ≤ 5 个工作日 | 目标内交付占比 |
| 变更失败率 | 未统计 | ≤ 15% | 需回滚或引发故障的发布占比 |

   - **目标设定原则**：先测基线再定目标；负向指标（失败率）必须配正向指标（交付频次、变更前置时间），防止"为降失败率而不敢变更"。
2. **分阶段实施路径**：

- **P0 阶段（0—1 个月，止血与合规整改）**
  - 交付物：账号清理报告（9 个账号回收清单）、生产配置写权限收回说明、版本号临时规范（统一 SemVer，禁用"最新版"类命名）、历史生产版本盘点与制品补录清单、《紧急发布补充回归制度》与 T+1 补审模板、第三方组件台账与 6 个高危 CVE 处置计划（3 个升级、2 个替换、1 个下线）、8 个 GPL 组件合规审查结论（替换或商业授权）、遗留 23% 跳过用例的补齐或书面豁免清单。
  - 周期：30 天。
  - 验收标志：等保"版本可追溯、变更可审计"条款初评通过；离场人员账号清零；高危 CVE 闭环率 100%。
- **P1 阶段（1—3 个月，工具链落地）**
  - 交付物：统一代码仓库与分支保护规则、代码评审规范落地（强制 ≥2 人评审）、CI/CD 流水线八阶段上线（含覆盖率门槛与门禁）、制品库与保留策略（历史生产版本永久保留）、语义化版本规范发布、数据库迁移脚本化改造（先补齐历史 9 次手工 SQL 的脚本回填）、Break-glass 通道与台账。
  - 周期：60 天。
  - 验收标志：连续 4 次发布全部由流水线产出制品且全部通过门禁；回滚演练实测 ≤ 30 分钟且成功；版本可追溯率 100%。
- **P2 阶段（3—6 个月，发布治理与灰度化）**
  - 交付物：发布管理制度与八步流程固化、发布评审模板、预生产环境建成并投用、灰度（5%→20%→50%→100%）方案与自动回滚阈值上线、蓝绿双环境切换方案、移动端最低版本变更的存量评估与分级推送机制、数据库"扩展—迁移—收缩"三步法规范与破坏性变更六项动作。
  - 周期：90 天。
  - 验收标志：至少 2 次生产发布完成完整灰度并有灰度报告；零不可逆变更未走专项评审；移动端版本升级不再出现存量用户不可用事件。
- **P3 阶段（6—12 个月，度量化与持续改进）**
  - 交付物：10 项指标看板（DORA 四指标 + 质量与审计指标）上线、季度配置审计（FCA + PCA）常态化、季度供应商评价与退出机制运行、《配置管理计划》年度评审与修订、经验教训库与知识转移（关键岗位 AB 角、每家外包至少 2 名持证工程师）建设。
  - 周期：180 天（持续运行）。
  - 验收标志：变更失败率 ≤ 15%、MTTR ≤ 1 小时、缺陷逃逸率 ≤ 10%、季度审计不符合项 0 项、连续 2 个季度供应商评分达标。

## 记忆口诀

**一、SCM 三大要素**
版本控制管"改了啥"，变更控制管"该不该改"，状态记录管"现在是哪版"；标识是前提，审计是保障。

**二、配置库三分**
开发库自由干，受控库评审进，产品库发布定；开发库的东西绝不能上生产。

**三、基线三道关**
功能基线定"做什么"，分配基线定"谁来做"，产品基线定"交付啥"；基线一立只能改不能动，改动必须走变更。

**四、配置审计两问**
FCA 查"做对没"（对需求对设计），PCA 查"交付全没"（对版本对数量）；审不过不许往下走。

**五、分支策略三选**
主干开发配特性开关，交付快靠开关放；Git Flow 版本清但分支长；环境分支审计好但冲突多。选型看交付频率、自动化水平、合规要求三条线。

**六、版本号三段**
主版本不兼容，次版本加功能，修订号修缺陷；预发布 alpha-beta-rc，正式发布去后缀；同号必同物，发过的号永不改。

**七、流水线八段**
检出、依赖、检查、单测、打包、集成、安全、部署；流水线即代码，界面上不准手改。

**八、门禁六条硬线**
覆盖率卡核心、新人改码也卡、严重漏洞零容忍、传染协议禁入制品、评审两人一外审、集成用例不许跳；放宽阈值等于毁门禁，紧急绕过要留痕次日补测。

**九、发布八步走**
范围冻结、自测评审、流水线打包、测试环境回归、预生产演练、发布评审批准、上线冒烟确认、归档更新基线。三条底线：有记录、可回滚、不越权。

**十、灰度四阈值**
错误率超百分之一、P99 劣化超两成、崩溃率超零点五、客诉十分钟超二十件；任一触发就回滚。灰度顺序：内部、百分之一、百分之五、两成、五成、全量。

**十一、数据库三步法**
先扩展、再迁移、后收缩；观测不足两个周期不许删；删列改名清数据一律不可逆，专项评审加双人复核加备份加灰度。手工 SQL 是回滚失败的头号根因。

**十二、回滚三要素**
旧制品还在、旧脚本能退、旧配置可还原；发布前不演练回滚就不许发布。版本号覆盖等于自杀。

**十三、强推升级四必做**
存量盘点要准、过渡期要留、网页端要兜、观察要久；最低版本提升前先看用户手里都是什么机器。

**十四、度量与治理**
版本可追溯率、可取回率、评审覆盖率、门禁通过率、失败率、逃逸率、恢复时长、例外次数；负向指标必须配正向指标，否则就是"什么都不敢改"。外包交付物不交脚本和 SBOM 就不予验收，账号离场 T+1 必回收。
