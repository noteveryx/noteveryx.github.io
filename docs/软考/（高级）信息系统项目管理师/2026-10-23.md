**主题**：项目管理绩效域与度量体系 —— OKR/KPI、绩效测量基线与管理绩效的闭环

---

## 今日核心概念

### 1. 项目管理绩效域（Performance Domains）

定义：项目管理绩效域是**项目管理的六大类管理关注方向**，它不按"知识领域"（进度、成本、质量）切分，而按"**要达成的目标**"切分，每个绩效域下挂若干具体目标，共同构成"项目管理原则—绩效域—任务"的层次结构。

**八大绩效域与 12 条原则的对应关系**：

| 绩效域 | 对应原则 | 该域要解决的问题 |
|---|---|---|
| **干系人** | 干系人导向、干系人参与 | 谁是干系人、怎么让他们参与且高效 |
| **团队** | 团队协作、团队领导、团队发展 | 怎么把人变成团队 |
| **开发方法与生命周期** | 裁剪、适应与韧性、交付增量价值 | 用什么过程交付 |
| **规划** | 领导力、生命周期、系统思考 | 怎么定目标与路径 |
| **项目工作** | 交付价值、聚焦、交付成果 | 怎么把事做出来 |
| **交付** | 交付成果、适应与韧性、质量 | 怎么把成果交出去且被接受 |
| **测量** | 衡量、完整性、透明、协作 | 怎么知道做得怎么样 |
| **不确定性** | 风险、韧性、适应与韧性 | 怎么应对变化 |

**关键认知**：绩效域之间**不是并列的平行关系，而是"干系人—团队—过程—规划—执行—交付—测量—应对不确定性"的闭环**。测量绩效域的输出会反过来修正规划绩效域的输入。

### 2. 项目管理原则的八大含义（PMBOK 第七版）

1. **成为勤勉、尊重和关心他人的管理者**——项目管理首先是"人"的职业
2. **营造协作的团队环境**——团队环境由项目经理负责营造，不是天生的
3. **有效地让干系人参与**——参与不是通知，"参与"要求投入
4. **聚焦团队工作**——团队工作 ≠ 团队合作（teamwork vs team working）：前者强调集体氛围，后者强调个体贡献的汇总
5. **聚焦增值交付**——一切活动都要问"对交付的价值有什么用"
6. **识别、评估和响应系统交互**——项目是更大的系统的一部分
7. **展示领导力**——领导力 ≠ 管理：管理是"计划、组织、控制"，领导力是"引领、影响、激发"
8. **支持团队绩效与恰当的裁剪**——裁剪不是偷懒，是"用刚好够的过程"

### 3. 度量体系：KPI、OKR 与度量基准

**KPI（关键绩效指标）**：**事后衡量型**，衡量已经发生的绩效，适合考核。

- 特点：**滞后性**、**可比较性**、**易被博弈**
- 典型：项目按时交付率、缺陷密度、变更成功率、预算偏差率
- 陷阱：单一 KPI 会诱导"指标造假"（Goodhart 定律：一旦某个指标成为目标，它就不再是好指标）

**OKR（目标与关键结果）**：**事前引导型 + 事后验证型**，先定"要到哪里"，再用可量化的关键结果验证。

- O（Objective）= 定性目标，回答"我们想达成什么"
- KR（Key Result）= 定量结果，回答"怎么知道达成了"
- KR 的三种类型：**数值型**（如"可用性提升到 99.95%"）、**里程碑型**（如"完成全部 12 个合规项审计"）、**二元型**（如"通过等保三级测评"）

**两者的关键差别**：

| 维度 | KPI | OKR |
|---|---|---|
| 时间取向 | 事后 | 事前+事后 |
| 导向 | 考核与问责 | 对齐与牵引 |
| 数值 | 通常是达成固定值 | 通常是"上下限+挑战值"双值 |
| 完成度 | 100% 才算达成 | 70% 达成即算健康 |
| 数量 | 少而精（3-5 个） | O 不超过 3 个，每个 O 下 2-4 个 KR |

**PMBOK 第七版的做法**：把"OKR 用于引导交付目标"+"KPI 用于事后度量绩效"，**两者不是替代关系**。项目管理中 OKR 回答"我们要交付什么价值"，KPI 回答"这次交付做得好不好"。

### 4. 度量与报告：度量基准与绩效报告的差异

- **度量（Measurement）**：产生关于项目状态的信息，通常由 PM 本人收集，成本低、细节多、可频繁进行（每日/每周）
- **度量基准（Measuring Baseline）**：度量数据经过分析后形成的**已批准基准**，用于后续偏差对比（PMBOK 中"度量基准"是 PMBOK 第六版的概念，第七版弱化但仍保留）
- **报告（Reporting）**：把度量结果加工成**面向特定受众**的信息，需要加工、解释、给建议，成本高、面向外部（治理委员会、投资人）

**核心差异一句话**：**度量是"取数"，报告是"讲故事"。取数不需要判断，讲故事必须判断。**

### 5. 挣值度量与绩效度量的衔接

项目管理中度量管理的落地工具仍是**挣值分析（EVM）**：

- **偏差（Variance）**：SV = EV − PV，CV = EV − AC。**偏差回答"我们偏了多少"**
- **绩效指数（Index）**：SPI = EV / PV，CPI = EV / AC。**指数回答"偏得有多严重"（比率可跨项目比较）**
- **完成预测（Forecasting）**：EAC 的五种算法

**PMBOK 第七版的"进展"概念与 EVM 的关系**：**EVM 是度量绩效的量化手段，"进展（Progress）"是它的管理延伸**——EVM 只告诉你偏差，要做成"进展报告"，还需要包含：未来预测、需要的决策、决策的责任人。

## 三个常考陷阱

### 陷阱一：把"团队工作"和"团队合作"混为一谈

- **团队工作（Team Working）**：个体技能、协作执行、交付成果。**项目更关心这个。**
- **团队合作（Teamwork）**：社交互动、建立关系、处理冲突。**是团队工作的必要条件，但不是充分条件。**

**项目越紧急，越需要"团队工作"；项目越复杂，越需要"团队合作"。** 团队合作做不好，团队工作必然做不好；但团队合作做得很好、团队工作做不好，项目依然会失败。

### 陷阱二：以为 OKR 是"目标管理"，KPI 是"绩效考核"，二者可随意替换

**错**。OKR 的 KR 里，很多是**里程碑型、二元型**（如"完成等保三级备案"），这类 KR **无法承担考核功能**——因为它要么完成要么没完成，没有中间刻度，无法区分"努力程度"与"结果"。

如果把里程碑型 KR 直接当考核指标，会出现"**为了完成里程碑而降低质量**"的博弈行为。

**正确做法**：OKR 用于牵引与对齐，KPI 用于考核；**两者之间要有映射关系**（哪些 KR 支撑哪些 KPI），但不要直接等同。

### 陷阱三：把"度量"当成"报告"，报告又当成"绩效评价"

三者严格区分：

| | 度量 | 报告 | 绩效评价 |
|---|---|---|---|
| 输入 | 项目数据 | 度量结果 | 报告 + 干系人反馈 + 环境 |
| 目的 | 知道状态 | 让特定人做出决策 | 判定团队/个人绩效 |
| 受众 | 项目内部 | 治理层/干系人 | 人力资源/管理者 |
| 频率 | 高（每日/每周） | 中（每周/每月） | 低（季度/项目结束） |
| 责任人 | PM | PM | 直属领导/HR/PMO |

**只有绩效评价才可以用于人事决策。** 把度量结果直接用于处罚，是项目管理中常见的重大失误——因为度量只有事实，没有解释。

## 案例分析题

### 案例 1（2026 年真题改编）— 绩效域与度量

**题干**：某市政务服务局启动"一网通办"平台二期项目，任命小张为项目经理。项目进入执行阶段后，小张发现：

1. 上级要求"年底前完成全市 42 个高频事项的上线"，小张把这些事项分解到团队，并给每人定了"O1：完成本人负责事项接入；KR1：12 月 15 日前上线；KR2：可用性不低于 99.9%"。
2. 团队会上，有成员提出"可用性 99.9%"做不出，因为第三方短信通道的服务水平只有 99.5%。小张认为这是第三方的问题，把 KR2 改成了"99.5%"。
3. 每月例会，小张只汇报"本月完成事项数"和"累计缺陷数"两个数据。局长问"为什么二期比一期慢"，小张答"因为二期需求变更多"。会议结束。
4. 项目结束后，局里对二期团队做绩效评价，评价依据是"是否完成全部 KR"。结果：8 人中 3 人 KR 未完成，被扣绩效；2 人虽 KR 未完成但投入工时最高，被认定为"尽力"给予表扬。

**问题**：
1. 指出小张在目标设定中存在的两个问题。
2. 小张修改 KR2 的做法是否正确？为什么？
3. 小张的月度报告存在什么问题？应如何改进？
4. 局里的绩效评价存在什么问题？应如何改进？

**参考答案**：

**问题 1 的两个问题**：
- **问题①：O 与 KR 混杂**。小张的"O1：完成本人负责事项接入"实质上是**任务（Task）而非目标（Objective）**。OKR 的 O 应当是定性的、鼓舞性的、方向性的表述（"让市民办事像网购一样便捷"），而不是把 KR 反过来当 O。正确的做法是：O 写方向，KR 写"事项上线数 ≥ 42""高频事项一次办成率 ≥ 85%"等结果。
- **问题②：KR 缺少挑战值**。PMBOK 与 OKR 实践都强调 **KR 应设置基线值与挑战值双档**（如"上线事项 ≥ 42 个（挑战 50 个）"）。只有单一数值，团队达成 42 个即算"完全成功"，无法体现牵引作用，且配合第 4 问的绩效评价，会强化"及格即满分"的导向。

**问题 2**：**不正确**。
- 首先，**KR 是目标，目标是团队和自己协商确定的，不是被外部压力单方面修改的**。第三方服务水平不达标，应当通过**变更控制流程**（提出变更 → 影响分析 → CCB 审批）来调整，而不是项目经理在团队会上直接改数字。
- 其次，"99.5% 是第三方的问题"这个归因**技术上不成立**。系统的可用性是**串行链路的乘积**：若短信通道只是其中一个环节，前置网关、本地队列、重试机制是否足以将失败次数掩盖住？**正确的做法是做依赖链路分析（MTBF 分解），而不是把端到端指标等于最弱环节**。
- 更重要的是：**可用性目标是"系统级目标"，必须有系统性手段支撑**（多通道冗余、失败降级为短信替代方案、重试与熔断），而不是把目标数字下调到"能交付"为止。这是典型的**"指标向下对齐"**，而非"能力向上建设"。

**问题 3**：**存在"有数据无结论、有事实无分析"的问题**。
- 只报两个数，**没有基准对比**（"完成事项数 18 个"——相对计划 21 个是超前还是滞后？没有计划值就无法判断）
- 没有偏差分析（"二期比一期慢"的归因"需求变更多"是**现象而非原因**，未给出变更数量、变更来源、变更对进度的影响量级、已批准的变更占多少比例）
- 没有结论与建议（未说明"是否需要采取纠偏措施、需要谁做什么决定"）

**改进**：月度报告应包含四部分——
1. **进展度量**（SPI/CPI 等与计划的对比，说明状态而非仅数据）
2. **偏差根因**（分层分析：外部依赖/内部管理/范围蔓延/质量返工）
3. **未来预测**（EAC、完工时间预测、风险敞口）
4. **待决策事项**（明确提出"请治理委员会在 X 月 X 日前决定是否调整上线批次"，并给出备选方案）

**问题 4**：**存在两个严重问题**。
- **问题①：把 OKR 直接当绩效评价依据，指标类型错配**。KR 中含**里程碑型（二元型）** KR（如"12 月 15 日前上线"），这类 KR 只反映结果、不反映可控的努力与质量投入。里程碑未达成的原因可能是第三方延期（不可控）、也可能是团队投入不足（可控），**两者被同等对待，是评价公平性的致命伤**。
- **问题②：出现"投入工时最高"与"未完成 KR"同时获得表扬的评价**，说明评价标准**自相矛盾**，会让团队导向"刷工时"而非"交付价值"，直接违背"聚焦增值交付"原则。

**改进**：
- 建立 **OKR—KPI 映射表**：哪些 KR 是牵引性的、哪些 KPI 是考核性的，只有可量化、有基线、团队可控的 KPI 才进考核
- 引入**可控性归因**：把未达成原因按"内部可控 / 内部部分可控 / 外部不可控"分类，外部不可控因素从考核中剥离，改用**协作贡献度**评价（如协调第三方、推动变更审批的次数与效果）
- 引入**绩效分布约束**：强制分布（如 20/70/10），避免"人人满分"
- 用**过程成熟度指标**补结果指标：需求澄清轮次、缺陷逃逸率、变更响应时长、代码/文档评审参与度

## 记忆口诀

- 口诀 1：**八大绩效域**——干系人、团队、开发方法与生命周期、规划、项目工作、交付、测量、不确定性。
- 口诀 2：**八原则起手**——勤勉关爱、协作环境、有效参与、聚焦团队工作、聚焦增值交付、系统交互、领导力、支持裁剪。
- 口诀 3：**团队工作 ≠ 团队合作**——前者要结果（项目看这个），后者要关系（是前提不是结论）。
- 口诀 4：**KPI 事后、OKR 事前后**——KPI 滞后可考核，OKR 事前牵引+事后验证。
- 口诀 5：**OKR 双值制**——基线值 + 挑战值，70% 达成即算健康。
- 口诀 6：**度量取数、报告讲故事、评价判人**——只有评价能用于人事，度量不能。
- 口诀 7：**偏差看绝对、指数看相对**——SV/CV 看"差多少"，SPI/CPI 看"差得有多严重、能不能跨项目比"。
- 口诀 8：**指标不可下调、目标只可变更**——要降目标走 CCB，不能在团队会上口头改。
