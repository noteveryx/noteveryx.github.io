# （高级）信息系统项目管理师 · 第62次学习

## 今日核心概念

### 1. 项目人力资源管理（五过程 + 塔克曼五阶段）
定义：项目人力资源管理是通过规划、估算、组建、建设、释放五个过程，获取项目所需的人力资源并充分发挥其作用的过程，核心产出是具备技能与能力、职责清晰、彼此信任的高效团队。
关键要点：
- 五过程：规划人力资源管理（规划过程组）→ 估算活动资源（规划过程组）→ 组建团队（实施过程组）→ 建设团队（实施过程组）→ 释放团队资源（实施过程组）。
- 责任分配矩阵（RAM）：事业环境因素（组织架构图、团队文化、可用资源）＋ 组织过程资产（模板、过去经验教训）；工具为词典式 RACI：R执行、A批准（唯一）、C咨询、I知会。
- 塔克曼阶梯五阶段（Tuckman's Ladder）：形成期（相互独立、客气试探）→ 震荡期（冲突显现、争夺控制权）→ 规范期（协同配合、建立默契）→ 成熟期（高效产出、互补短板）→ 解散期（团队释放、经验沉淀）。
- 激励五理论：马斯洛需求层次（生理—安全—社交—尊重—自我实现）、赫茨伯格双因素（保健因素消除不满、激励因素带来满意）、麦格雷戈 X 理论—Y 理论（X 需监督控制、Y 需授权自主）、期望理论（激励力＝效价×期望值）、麦克斯伯格、阿德Transactional（康德—帕金森定律）。
- 冲突解决五策略（按从低到高强度排序）：撤退回避、缓和迁就、妥协调解、强迫指挥、合作解决问题；**合作/协作是最彻底、最正面的策略，最彻底应对时建立长期信任**。项目经理先引导个人冲突、再引导集体冲突。
- 团队建设活动：塔克曼五阶段对应五类建设活动——公认现状（外向了不起）、暴露差异（向内）、建立信任（自由与脆弱）、群体规范（共同目标）、共庆成功（集体主义）；工具含认可与奖励（认可成果、行为、成长三层次）、团队建设活动、集中培训。
- 虚拟团队与文化差异：跨地域/跨文化团队须关注时区、语言、沟通风格、个人隐私与工作习惯，E/I 沟通模型中虚拟团队更依赖书面异步沟通，风险是信息延迟与误解。
- 裁减人员（遣散）管理：按 HR 制度与法律程序执行，**PM 无权单方面辞退团队成员，须由有权者（项目经理主管、HR）处理**，项目经理只提供事实与证据。

### 2. 项目配置管理（四活动 + 基线三类型）
定义：项目配置管理是管理项目配置项变更、控制配置项版本与状态、确保产品与文档一致性与可追溯性的过程，目的是让任何时刻都能回答"现在做的是什么、为什么这样做、是否与批准一致"。
关键要点：
- 四大活动：**配置识别 → 配置状态记录（记账） → 配置审计（核实） → 配置控制（变更控制）**，四者构成闭环。
- 配置标识：识别配置项（CI）并编号命名；配置项八大类：基准类、计划类、需求类、设计类、代码类、测试类、运行环境类、文档类（标准常记"源程序、需求文档、设计文档、测试计划、项目管理计划、合同/协议、项目章程、运行环境"）。
- 版本号规则：通常为**主版本号.次版本号.修订号**；第一部分表示重大变更（架构级），第二部分表示次要变更（增量功能），第三部分表示纠正（错误修复）。
- 三大基准（后两个属于范围基准与进度基准，需整体变更控制）：
  - **功能基准**：产品/服务功能范围——对应 WBS 工作绩效数据与可交付成果；
  - **进度基准（进度基准）**：经批准的进度网络图＋活动清单＋资源清单＋资源日历＋工作绩效数据，用于计算 SV/SPI/EAC；
  - **范围基准**：包含 WBS＋WBS词典＋范围说明书，经过正式批准，只能通过整体变更控制变更。
- 配置审计：分为**功能配置审计（ FCA）**——审计交付成果性能、接口、与需求的一致性；**物理配置审计（ PCA）**——审计配置项实物/文档的版本、介质、标识、数量、状态是否与记录一致。PCA 常由 QA 独立完成。
- 变更控制：任何配置项变更必须提出**变更请求（CR）→ 变更控制委员会（CCB）审查批准/否决 → 实施 → 验证 → 更新基线与状态记录**；**未批准的变更不得实施，紧急变更事后必须补齐记录**。

### 3. 项目量化管理（统计控制与随机化）
定义：项目量化管理（QM）是把数据分析、项目管理技术与知识整合到量化管理与决策中的过程，用于评估趋势、预测结果、做出判断与优化，支持不确定性决策。
关键要点：
- 过程：规划量化管理→开展数据与需求分析（规划过程组）→实施定量分析（实施过程组：敏感性分析、决策树分析、模拟分析、优化分析）→实施统计控制（监控过程组，含核查、控制图）。
- 统计控制七步：定义量化项目规划模型及数据需求（含变异与异常值处理）→ 选择统计控制方法（常用控制图、抽样调查）→ 实施统计控制（计算变量均值、偏差、标准差）→ 监测偏差并查找根因（抽查、假设检验）→ 核查结果（是否在预测容差范围内）→ 制定纠偏措施 → 实施与记录。
- 抽样调查：当总体数量过大、破坏性测试昂贵或时间受限时采用；常用方法有**简单随机抽样、分层抽样、系统抽样、整群抽样**，分层抽样可保证各子层代表性。
- 核查（验证）：核查前应先识别**问题原因**（分析、例外分析），因为收集的数据必须正确测量才能核查；核查结果**不应作为绩效评价依据**，而**流程改进**才可用绩效数据评价。
- 数据分析技术：核查（准确性分析）、回归分析、假设检验、敏感性分析、蒙特卡洛模拟、优化分析；注意**绩效报告数据可比性**四项定性分析：数据质量、基准持续性、测量一致性、整体一致性。
- 大数定律失效（奥卡姆剃刀）：历史数据不足以预测非线性、突变行为时，大数定律失效；泰勒定律揭示"发展过程是连续渐进的"，但牛顿定律主导的机械思维解决不了社会复杂问题，需用**交叉跳慰（费米估算/自上而下估算）**等方法辅助。

### 4. 项目绩效评价与绩效报告
定义：项目绩效评价是依据项目绩效测量基准与实际结果比较，分析绩效好坏、偏差原因并采取纠偏的监控过程；绩效报告是向干系人沟通绩效结果的正式文档，取代了旧版"状态报告"的叫法。
关键要点：
- 绩效测量基准：**范围基准（工作绩效数据与工作绩效信息）＋ 进度基准＋ 成本基准**的组合，是绩效评价的唯一衡量尺子。
- 工作绩效数据（WPD）→ 收集整合；工作绩效信息（WPI）→ 分析汇总；工作绩效报告（WPR）→ 沟通发布，三者属于"监控过程组 2.4 监督工作绩效"。
- 绩效报告包含内容：总体进展概述；宏观效益与微观效益分析；绩效数据（PV/EV/AC、CV/SV、SPI/CPI 等）；预测（EAC/VAC/ETC/TCPI）；关键风险与问题；建议与决策请求。
- **挣值指数判读**：
  - CV>0、SPI<1 → **成本超支、进度落后**（低效/拖延型，最需关注）；
  - CV<0、SPI>1 → **成本节约、进度提前**（可能为赶工超员，需防质量滑坡）；
  - CV>0、SPI>1 → 成本节约且进度提前（最优）；
  - CV<0、SPI<0 → 成本超支且进度落后（最差，须强力纠偏）。
- **EAC/VAC/TCPI 三公式**：
  - EAC = BAC/CPI（偏差将持续时，默认公式）；
  - EAC = AC +（BAC−EV）＝BAC（当前偏差视为偶然，一次性偏差）；
  - EAC = AC +（BAC−EV）/（CPI×SPI）＝AC + ETC/（CPI×SPI）（偏差受双重影响，成本与进度共同）；
  - ETC = EAC − AC；VAC = BAC − EAC；TCPI =（BAC−EV）/（BAC−AC）（剩余工作应达到的成本绩效）。
- 绩效基准与实际值的**趋势分析**：偏差是否持续扩大（PV−EV 缺口扩大即"缺口"，对应成本超支趋势）、关键路径漂移识别，避免"只做偏差分析不做趋势分析"。

### 5. 项目收尾管理与经验教训
定义：项目收尾是完成并正式结束项目或阶段的过程，包括合同收尾与行政收尾（管理收尾），标志项目转入运营并释放资源。
关键要点：
- 项目收尾包括：项目收尾（含合同收尾、行政收尾）、项目总结、评估与审计、移交运营、项目解散——五项属"实施过程组 4.1～4.5 结束项目或阶段"，含**项目总结、项目评估（审计）、项目移交运营、项目解散**。
- 合同收尾：逐项完成合同条款核对与验收，取得**客户正式验收/完工证明**，办理**行政结算**与尾款支付（保留质保金），解除合同义务。
- 行政收尾：完成并归档全部项目文档、移交运营与资产、释放团队与设施、进行经验教训总结、通知干系人项目正式关闭、更新组织过程资产库。
- 经验教训（Lessons Learned）：过程资产库包括**历史信息与经验教训知识库**（经验总结、绩效历史、项目收尾报告、验收历史、正式评估、团队解散总结）与**组织过程资产中心**（流程模板、模板、度量标准、标准作业程序）；经验教训须在项目**全过程持续记录**、收尾时汇总。
- OPA 三类：历史信息与经验教训知识库（明细+汇总）、组织过程资产中心、方法与实践。**过程改进是终止阶段的活动（OCL 是收尾工具）**；经验教训可分**可估计（正常）与不可估计（异常）**两类，异常必须分析根因。
- 效益实现度量与后评估不属于项目收尾范围，而属于**运营/项目后评价阶段**（可选做，但项目经理有责任提供数据）。

## 案例分析题

**题目**：

某市属事业单位"一体化政务服务平台二期"项目于2026年3月立项，由中标承建方组建团队开发，计划工期14个月，总预算（BAC）1000万元。3个月后，项目经理老周向管理层汇报：项目持续推进，但实际支出已达920万元，而经核算完成的工作量仅相当于原计划的78%。管理层要求项目团队提交分析说明与后续纠偏方案。事后检查发现：

1. 项目启动后，老周为赶进度，从公司其它项目借调了6名核心开发人员，其中有3人在借调期间向原公司提交了离职申请；同时3个月试用期刚满的老周即转为正式项目经理。
2. 二期需求不断增加（如新增"跨部门数据共享交换"模块），但客户并未正式提出变更申请，开发组直接开始编码；老周口头同意新需求，未走变更流程。
3. 项目组文档混乱：需求文档有v1、v1.1、v1.0、v2多个版本，管理员无法说明"当前基准是哪个"；配置管理员同时负责10个项目的配置管理，被询问时答"我这边没登记"，也无从核对实际交付物版本。
4. 试运行阶段发现一个核心功能模块存在功能缺陷，质量部对已交付物进行了功能配置审计，指出交付物与需求规格说明存在3处不一致，且未验证接口的性能指标。
5. 项目结项时，建设单位以"接口文档未移交、系统运维手册缺失"为由拒绝出具验收报告，尾款300万元无法支付。

已知：PV（计划价值）=1000万元，EV（挣值）=780万元，AC（实际成本）=920万元，BAC=1000万元。

**问题**：
1. 指出该项目在人力资源管理方面存在的问题并给出改进措施。
2. 指出该项目在配置管理方面存在的问题并给出改进措施。
3. 依据挣值数据，计算 CV、SV、CPI、SPI、EAC、ETC、VAC、TCPI，分析项目当前绩效状况。
4. 指出项目结尾存在的问题并给出纠正措施。

**参考答案**：

### 问题1：人力资源管理问题与改进措施

存在的问题：
1. 人员借调管理缺失：未按人力资源计划招募与获取，采用临时借调方式补齐核心开发人员，导致人员流动与质量风险，且未在人力资源计划中安排备份（替补人员）。
2. 团队组建阶段判断失当：项目启动即处于**形成期**，成员彼此生疏、工作习惯差异大，此时最需要加强磨合与培训，而非立即冲刺赶进度。
3. 领导力与激励不足：老周以"赶进度"为目标，未与成员建立共同目标与信任，未针对优秀成员开展认可与奖励，团队处于**震荡期**（冲突与控制权争夺）而非规范/成熟期。
4. 任职资格与经验管理不足：3个月即转正式项目经理，可能**过度信任**（Over Trust）缺乏项目经验的人员；缺少对成员能力、经验、可用时间的评估，也缺少指导与培训。
5. 未实施"释放团队资源"管理：借调人员未明确归还与交接安排。

改进措施：
1. 重新编制人力资源管理计划：明确各阶段（尤其建设期）所需人力资源的类型、技能、可用工时，明确项目班子成员职责（RAM/RACI 矩阵），制定招募与借调审批流程。
2. 按塔克曼五阶段推进团队建设：形成期通过公认现状、暴露差异活动增进了解；震荡期主动引导冲突并达成共识；规范期建立团队规范与共同目标；成熟期授权并充分授权；解散期组织总结与资源释放。
3. 强化激励与认可：针对优秀团队成员与个人采用**认可与奖励**，具体可包括认可成果（集体与个人）、认可行为（团队合作、分享知识）、认可成长（培训与提升）；结合需求层次与双因素理论，为核心成员提供成长机会、授权与晋升通道。
4. 开展指导、培训与团队能力建设：针对新加入成员进行技术与项目管理培训，采取"指导"（一对一）方式帮助新成员融入；对高级项目人员需防止骄傲自满引发冲突，及时沟通。
5. 优化项目经理任命与授权：应评估项目经理任职资质（经验、专业能力、领导力），在转正前完成独立带组能力评估；项目经理需在项目章程授权范围内行使权力，超越权限事项向高层寻求支持。
6. 制定人员遣散与释放方案：项目终止或人员借调结束时，按 HR 制度办理释放与交接，做好工作交接单与文档归档。

### 问题2：配置管理问题与改进措施

存在的问题：
1. 缺少配置管理计划：未制定配置管理计划，未明确配置项识别规则、版本命名规则与变更控制流程。
2. 配置标识混乱：需求文档版本出现 v1.1、v1.0 并存，说明**未执行统一的版本递增与标识规则**（主版本号.次版本号.修订号）。
3. 配置状态记录缺失：配置管理员"没登记"，说明**配置状态记录（记账）活动未落实**，无配置项清单、无状态与版本历史。
4. 配置控制失效：客户新增需求直接编码、老周口头同意，**未走变更申请与 CCB 审批流程**，属于"未批准的变更即实施"。
5. 职责与资源冲突：1名配置管理员兼管10个项目，**不满足配置管理"专人专职、职责单一"的要求**，且缺乏独立性保障。
6. 配置审计执行不完整且被误解：质量部仅做功能配置审计，**未做物理配置审计**，且把"核查结果"直接当作绩效评价依据（核查结果不应作为绩效评价依据）。

改进措施：
1. 制定配置管理计划：明确配置项八大类识别标准、版本号规则（主版本.次版本.修订号）、变更控制与审计流程、配置库与权限管理。
2. 建立配置项清单并统一编号命名：编制**配置管理计划与配置项清单**，明确各配置项唯一标识与存放位置，配置状态记录"谁在何时提交了什么、什么状态、什么版本"。
3. 严格变更控制：所有需求变更必须**提交变更请求（CR）→ CCB 审查评估（对范围、进度、成本、质量影响）→ 批准或否决 → 实施 → 验证 → 更新基线与状态记录**；紧急变更可先事后补齐记录。**严禁先干后补、越权口头同意**。
4. 配备专职配置管理员并保证可用工时：将配置管理职责独立于开发与测试，明确"**一项配置管理职责只能分配给一个人**（RACI 中 A 唯一）"；对兼管多项目的情况，增加工时保障或人员。
5. 规范配置审计：项目须同时开展**功能配置审计（FCA）**与**物理配置审计（PCA）**——FCA 验证交付成果与需求/性能的一致性，PCA 验证配置项实物与文档记录一致；应使用自动化工具比对差异清单并逐项纠正。
6. 正确使用核查结果：核查用于判断与建议改进，**不应直接作为对个人绩效评价的依据**，防止核查沦为追责工具而影响团队如实报告。

### 问题3：绩效计算与分析

计算过程：
1. CV = EV − AC = 780 − 920 = **−140 万元**（负偏差，成本超支）
2. SV = EV − PV = 780 − 1000 = **−220 万元**（负偏差，进度落后）
3. CPI = EV / AC = 780 / 920 ≈ **0.848**（小于1，成本效率低）
4. SPI = EV / PV = 780 / 1000 = **0.78**（小于1，进度效率低）
5. EAC = BAC / CPI = 1000 / 0.848 ≈ **1179.25 万元**
6. ETC = EAC − AC = 1179.25 − 920 ≈ **259.25 万元**
7. VAC = BAC − EAC = 1000 − 1179.25 ≈ **−179.25 万元**
8. TCPI =（BAC − EV）/（BAC − AC）=（1000 − 780）/（1000 − 920）= 220 / 80 = **2.75**

分析结论：
1. 项目处于**"成本超支 + 进度落后"的低效/拖延型偏差组合**（CV<0、SPI<1），是最需重点干预的偏差类型。
2. 进度仅完成计划的 78%，已用掉 92% 的预算，说明**成本绩效随进度一同恶化**（CPI≈0.848 明显低于 SPI≈0.78），典型的"边拖边烧钱"状态：人员借调、返工、变更失控叠加导致投入产出比严重失衡。
3. 按现有趋势预测，完工总成本约 **1179 万元**，将超预算 **约 179 万元**；剩余工作尚需投入约 **259 万元**。
4. 若按原预算 1000 万元干完且用完 AC=920，则剩余工作必须在 **TCPI=2.75** 的成本绩效下完成，即**每投入 1 元需产出 2.75 元价值**，在项目后半程几乎不可能实现——说明**在现有预算约束下项目必须做范围削减或申请追加预算**，否则目标不可达。
5. 偏差判断需结合**基准持续性、数据质量、测量一致性、整体一致性**四项定性分析，并做**趋势分析**（成本与进度指标是否持续恶化），不能仅凭单一时点数据下结论。

纠偏建议：优先分析根本原因（借调人员不稳定→返工；变更无控制→范围蔓延；文档无基线→重复开发），采取范围冻结与变更管控、范围蔓延剔除、赶工/快速跟进评估、缩减范围或申请预算变更（走整体变更控制）等组合措施。

### 问题4：项目收尾问题与纠正措施

存在的问题：
1. **交付物与文档不完整**：接口文档、运维手册未移交，属于行政收尾的文档移交缺失，导致无法支持运营。
2. **未完成合同收尾**：建设方拒绝出具验收报告，合同义务未终结，尾款 300 万元无法支付，形成商务纠纷。
3. **知识沉淀缺失**：项目中的配置管理、变更控制教训未形成经验教训记录，组织过程资产库未更新。

纠正措施：
1. 补充完善移交物：按合同与SOW 清单逐项核对，**补齐接口文档、运维手册、数据字典、部署与配置说明**，完成**知识转移与人员培训**，使建设单位具备独立运维能力。
2. 推进合同收尾：按**验收三阶段（初期验收/试运行验收/最终验收）**与验收标准组织整改复验；取得**客户正式验收/完工证明**；办理**行政结算**与尾款支付；如双方对范围有争议，按**争议解决三步（谈判→调解/仲裁→诉讼）**或合同约定方式处理。
3. 强化项目文档与过程资产沉淀：完成项目收尾报告与项目总结，将经验教训（尤其"无变更流程先干后补""配置项无登记"问题）写入**历史信息与经验教训知识库**，更新组织过程资产中心，为后续项目提供模板与度量标准。
4. 完成行政收尾：移交资产与账号权限、更新组织过程资产库、释放资源（遣散/释放团队资源）、通知全部干系人项目正式关闭。

## 踩分要点

- **五过程名称必须写全**：规划人力资源管理、估算活动资源、组建团队、建设团队、释放团队资源；答人力资源题时"过程"分与"措施"分各占一半，缺过程只写措施会丢分。
- **塔克曼五阶段顺序不能乱**：形成、震荡、规范、成熟、解散；常考"项目初期冲突多、后期效率高"的阶段判断题，以及"成熟期出现成员骄傲"对应"过度自信/骄傲自满"。
- **责任分配矩阵**：RACI 中 **A（批准）必须唯一**，是高频易错点；"词典式 RACI"为考试表述。
- **配置管理四活动顺序**：识别→记录→审计→控制；审计要区分 **FCA 与 PCA**，"物理配置审计"漏写必丢分。
- **三大基准别混**：功能基准（产品功能范围）、进度基准（进度网络图＋活动清单＋资源清单＋资源日历）、范围基准（WBS＋WBS词典＋范围说明书）；**范围基准＋进度基准＋成本基准共同构成绩效测量基准**，常在选择题中交叉考查。
- **版本号三段**：主版本（重大变更）·次版本（次要变更）·修订号（纠正），不要写成"版本号.日期"。
- **量化管理七步别跳步**：**核查前必须先识别问题原因（分析、例外分析）**，这是评分点；同时强调"核查结果不应作为绩效评价依据"。
- **挣值四算必考**：CV、SV、CPI、SPI 的公式与符号判断；EAC 三种公式适用场景（默认 BAC/CPI）；VAC 为负表示预计超支；**TCPI 越大说明剩余工作越难在预算内完成**，可用于判断"是否必须申请追加预算或削减范围"。
- **偏差组合判断**：CV<0 且 SPI<1 → 成本超支、进度落后（低效型）；CV>0 且 SPI<1 → 成本超支、进度提前（赶工超员型，防质量滑坡）。
- **收尾题**：合同收尾（验收、完工证明、行政结算、尾款）+ 行政收尾（文档归档、移交运营、释放资源、经验教训）两分必须都写；常考问"项目收尾包括哪些活动"，标准答：项目收尾、项目总结、项目评估与审计、项目移交运营、项目解散。
- **权限边界**：项目经理无权擅自辞退成员、无权越过 CCB 批准变更、无权未授权即对外签约；这类"越权"表述在案例中通常是踩分雷区。
