## 今日核心概念
### 1. 项目范围管理六过程
定义：项目范围管理是确保项目"做且只做"完成项目所需的全部工作的管理过程，覆盖产品范围与项目范围两层含义，是项目成功的基础与基准。
关键要点：
- 范围管理六大过程：规划范围管理→收集需求→定义范围→创建WBS→确认范围→控制范围。
- 产品范围：最终交付物所具备的特性与功能；项目范围：为交付产品而必须完成的工作。
- 范围基准由WBS、WBS词典、范围说明书三层构成，是成本/进度/质量三大基线的源头。
- 范围管理核心矛盾：范围蔓延（Scope Creep）vs 镀金（Gold Plating），前者未经变更控制，后者主动加戏。
- 范围管理与时间/成本/质量的关系：范围是"根"，其他三角是"果"，范围变则一切变。

### 2. 需求分类与需求跟踪矩阵
定义：需求是从用户视角对系统应具备功能与非功能特性的完整描述，是范围定义的输入与依据。
关键要点：
- 需求三层分类：业务需求（高层次战略目标）、用户需求（角色级使用场景）、功能需求+非功能需求（系统级实现细节）。
- 非功能需求六大类：性能、可靠性、可用性、安全性、可维护性、可移植性，简称"性可安维移"。
- SRS（软件需求规格说明书）应包含：功能需求、非功能需求、外部接口、约束条件四部分。
- RTM（需求跟踪矩阵）建立需求从提出→设计→实现→测试的全链路双向追溯，是范围控制核心工具。
- 需求优先级排序四象限：紧急重要、紧急不重要、重要不紧急、不紧急不重要；MoSCoW法则：Must/Should/Could/Won't。

### 3. WBS工作分解结构
定义：WBS是把项目可交付成果与项目工作逐层分解为更小、更易管理的单元所形成的层级结构，是范围管理的核心工具。
关键要点：
- WBS分解四大原则：100%原则（所有交付物纳入）、可交付成果导向、8/80原则（工作包40-80小时/4-8天）、责任明确原则。
- WBS分层结构：项目→阶段→可交付成果→工作包→活动→任务，主流层级为4-6层。
- WBS不是组织分解结构OBS，但二者通过WBS字典交叉对应形成责任矩阵（RAM/RACI）。
- WBS分解方法：自上而下（生命周期阶段驱动）、自下而上（头脑风暴归集）、类比模板（标准模板复用）。
- WBS工作包是范围、进度、成本、绩效测量的最小核算单元，可独立估算与控制。

### 4. 范围基准与范围控制
定义：范围基准是经过批准的WBS、WBS字典与范围说明书的总称，是项目执行的基线，控制范围就是监督范围基准的变更。
关键要点：
- 范围基准变更必经整体变更控制流程：申请→评审→CCB审批→实施→验证→归档。
- 范围控制核心产出：变更请求（CR）、变更日志、范围基准更新、经验教训。
- 范围确认 vs 范围控制：前者关注"可交付成果验收"，后者关注"范围基准的变更监控"，动词方向相反。
- 范围蔓延控制三道防线：基线锁定、变更控制委员会（CCB）把关、挣值分析预警。
- 范围确认可按里程碑分阶段进行，每阶段产生经验教训与最终交付物验收记录。

### 5. 范围管理高频踩坑点
定义：软考范围管理章节的高频失分点集中在术语混淆、过程顺序错位、WBS粒度失控与变更流程缺失四个维度。
关键要点：
- 易混术语：确认范围（Validate Scope）是干系人验收，控制范围（Control Scope）是过程监督；产品范围 vs 项目范围。
- 过程顺序：规划→收集需求→定义范围→创建WBS→确认范围→控制范围，6过程不可调换顺序。
- WBS粒度陷阱：过粗→失去管控意义；过细→估算成本剧增；按8/80原则与可交付成果导向双重把关。
- 变更流程高频考点：任何范围变更必须走整体变更控制流程（ICCP），CCB决策、配置管理系统留痕。
- 案例题陷阱：需求变更未走流程 = 范围蔓延；客户口头要求 = 无书面变更；完工后追加工 = 镀金（项目经理主动）。

## 案例分析题
**题目**：
某市政务服务平台项目（合同额800万，工期10个月）已进入第7个月，项目经理小李组织范围确认时发现：(1) 行政服务大厅窗口人员反映"排队叫号功能"频繁卡顿，要求增加"短信+微信公众号"双通道提醒，作为合同外新增功能；(2) 市大数据局新下发的《政务平台安全等保三级合规要求》要求补充"敏感数据脱敏+日志审计"模块，涉及20%功能扩展；(3) 团队内部分工程师私下为领导开发"个性化首页"功能，未走任何变更流程；(4) 已交付的电子证照模块存在10项缺陷，运维部门以"不属于本项目"为由拒绝验收，导致整体验收停滞。

问题：
1. 请指出上述四种情形分别属于范围管理的什么现象？应如何处理？
2. 请画出本项目WBS分解的顶层结构（至少6项可交付成果）。
3. 为防范范围蔓延，小李应建立哪些范围控制机制？请列出至少5项。
4. 若新增"短信+微信双通道提醒"需追加成本40万、工期1.5个月，请按变更控制流程给出完整处理步骤。

**参考答案**：
1. 四种情形判断与处理：
- 情形1（窗口人员新增提醒功能）：属于范围蔓延（Scope Creep）——未经变更控制的口头需求添加。处理：由小李书面记录窗口需求，提交整体变更控制流程，由CCB评估价值与可行性；无论批准与否，均需书面回复并归档，不直接答应。
- 情形2（等保合规新增）：属于外部强制变更（External Driven Change）——法规/政策更新导致的强制性范围调整。处理：因属合规强制要求，必须纳入范围，走紧急变更流程，先做影响分析（成本/进度）报CCB与甲方共同审批，可作为合同变更追加处理。
- 情形3（工程师私加个性化首页）：属于镀金（Gold Plating）——团队未授权擅自增加功能。处理：立即停止开发、撤除已部署代码、批评教育、纳入经验教训库；同时审视团队动机（领导要求？），引导走正式变更流程。
- 情形4（运维拒验收）：属于范围确认失败——可交付成果未通过干系人验收。处理：组织正式范围确认会议，先做缺陷修复再验收；运维部门作为验收干系人必须在初始干系人登记册中识别，并参与范围确认全过程；10项缺陷属质量问题（质量域），但影响范围验收，应协同质量经理按缺陷管理流程处理。
2. WBS顶层结构（按阶段+可交付成果双重分解）：
- 1. 项目管理
  - 1.1 项目章程与启动报告
  - 1.2 项目计划与基线
  - 1.3 监控与收尾报告
- 2. 需求分析与设计
  - 2.1 需求调研与SRS文档
  - 2.2 架构设计说明书
  - 2.3 详细设计与接口规范
- 3. 平台开发
  - 3.1 排队叫号子系统
  - 3.2 电子证照子系统
  - 3.3 业务办理子系统
  - 3.4 统一支付子系统
  - 3.5 数据交换子系统
- 4. 系统测试
  - 4.1 单元/集成/系统测试
  - 4.2 安全等保测评
  - 4.3 性能压测与UAT
- 5. 部署与上线
  - 5.1 政务云部署与配置
  - 5.2 数据迁移与切换
  - 5.3 上线试运行支持
- 6. 培训与交付
  - 6.1 用户操作手册与培训
  - 6.2 运维交接与SLA
  - 6.3 项目验收与结算
3. 范围控制机制至少5项：
- 建立并冻结范围基准（WBS+WBS字典+范围说明书），任何变更走整体变更控制流程（ICCP）。
- 设立变更控制委员会（CCB），明确成员、决策规则（投票/一致通过）与响应时限（5个工作日内）。
- 配置管理系统留痕（文档版本、变更日志、基线对比），所有变更请求CR与决策记录入配置库。
- 建立需求跟踪矩阵（RTM），实现需求→设计→编码→测试→验收的双向追溯，防止漏项与镀金。
- 范围确认分阶段进行（里程碑验收+最终验收双层），验收记录签字盖章归档。
- 挣值分析（PV/EV）预警范围蔓延：EV偏离PV过大时主动审查变更。
- 范围绩效审计与定期干系人沟通，防"秋后算账"。
4. 短信+微信双通道提醒新增功能的变更控制流程：
- 步骤1：识别变更——窗口人员提交书面需求（不口头承诺）。
- 步骤2：记录变更请求（CR）入变更日志，分类为"合同外增值"。
- 步骤3：影响分析（项目经理+业务分析师+架构师+估算师联合评估）：
  - 成本影响：+40万（短信网关接入3万+微信认证2万+开发20万+测试5万+运维10万）。
  - 工期影响：+1.5个月（开发1月+测试0.5月）。
  - 范围影响：与排队叫号子系统耦合，影响接口与联调。
  - 风险影响：短信服务商SLA风险、微信公众号接口限流风险。
- 步骤4：方案评审——组织CCB评审会（项目经理+客户代表+技术负责人+财务负责人），评审变更必要性、替代方案（如只做微信或只做短信）、性价比。
- 步骤5：CCB决策——批准/拒绝/推迟/部分批准（建议先做微信通道，短信通道后续评估）。
- 步骤6：合同变更——批准后与甲方签订补充协议，明确追加费用40万与工期延长至11.5个月。
- 步骤7：实施更新——更新范围基准、进度基准、成本基准；更新WBS与WBS字典；通知团队。
- 步骤8：实施验证——开发完成后组织专项测试与UAT，干系人验收签字。
- 步骤9：归档与经验教训——所有变更记录、影响分析、决策过程归档入配置库，经验教训入库复用。

**踩分要点**：
- 术语精准：范围蔓延（未经控制的追加）vs 镀金（团队擅自添加）vs 强制变更（外部法规驱动）三概念必区分。
- 流程完整：变更控制九步走（识别→记录→分析→评审→决策→合同→更新→实施→归档）缺一不可。
- WBS顶层：按"管理+阶段+可交付成果"三层组织，至少6项可交付成果对应范围基准。
- 范围确认 vs 范围控制：前者干系人验收，后者基线监督；运维拒验收属范围确认失败，不是范围控制。
- 强制变更处理：合规类变更必须接受，但走紧急变更流程并追加合同，不可私下消化。
- 干系人识别：窗口人员、运维部门必须在干系人登记册中并参与验收，避免"项目结束才出现"。

## 记忆口诀
- 范围管理六过程口诀：「规收定创确控」——规划范围、收集需求、定义范围、创建WBS、确认范围、控制范围。
- 范围基准三层口诀：「WBS+字典+说明书」——Work Breakdown Structure + WBS Dictionary + Scope Statement 缺一不可。
- WBS分解四大原则口诀：「百可八责」——100%原则、可交付成果导向、8/80原则（40-80小时）、责任明确。
- 范围蔓延 vs 镀金口诀：「蔓是被动（客户提）+镀是主动（团队加）」，都是失控，必须变更流程治。
- 范围管理高频踩坑口诀：「术语混、顺序乱、粒度偏、流程缺」四错位，变更九步走 + CCB是关键。
- WBS与OBS交叉口诀：「WBS管事，OBS管人，RAM矩阵交叉定责任」——RACI四角色贯穿。
- 范围确认与控制方向口诀：「确验收、控变更」——一个是客户验收交付物（动词朝向客户），一个是项目经理监督变更（动词朝向基线）。
