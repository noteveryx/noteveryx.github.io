# 2026-11-09 寓言故事 · 两支商队的路账

> 每天一个研究生水平概念，借一个故事让它在心里生根。

---

## 故事

青石峡南北两坡，各住着一支商队。两队世世代代记同一本《同行录》：谁在哪年哪月，跟谁同过一道路。全峡只有一条规矩——**只添，不涂**。

两队各有一本册子，各记各的。添行也有讲究：先在行首盖一枚小印作记号，比如"丁七印"，同一行盖同一个印。这样两队的册子上都可能出现"丁七印·张三与李四同行"，行数未必相同，印记相同。峡里人管这叫"一印一号，认印不认人"。

消息走峡索。索道横跨绝壁，绳长，绳上结着雾，雾一挡，话就绕远：常常该说的话半个月才到；偶尔绕了三圈才到；更邪门的是同一句话能到三遍——送绳的人手一滑，纸卷顺着风溜回原处，再送，再溜。

两队约定：**见到对方册子，就互相念。** 一个人念自己册上的行，另一个人拿笔在自己册上对，遇着"丁七印"合上了，就在自家那一行边点个红点。念完，交换册子，再念回来。

峡里人试过很多次。什么时候念、念几遍、先念哪队、念到一半下雨明天接着念——最后发现，两本册子总会一样。

后来有个新来的账房不服气，非要问个为什么。老账房掰着手指给他数：

**第一**，念多少遍都一样。一行盖了"丁七印"，念三遍它还是那一行，不会变成三行——因为认的是印，印认得就归一。

**第二**，谁先念谁后念都一样。峡里从来没人能保证两队谁先到，反正念完都是并在一处，谁先谁后不生差别。

**第三**，念到一半停手、隔三天再接着念，跟一口气念完，也一样。

三条合起来，念册这件事就有了个脾气：**怎么念都对得上**。于是两队彻底不必约时间，不必跑一趟请示谁，也不必推举什么主事——只要各自记各自的，随时相遇随时念，最后两本册子必定长成一本。

老账房讲到这里，话头一转，指着峡壁上的一块字："不过有一条，记死了，谁都别想破。"

峡壁上刻着："丁七·某年某月·张三误记于北坡，作废。"是北坡的账房自己来刻的。

新账房不懂："记错了，涂掉不就完了？"

老账房摆手："涂不得。"

他讲：北坡那页涂掉了"张三"两个字，南坡那页还没收到这个涂。南坡册子上还留着"张三同行"那一行。等两队再念，北坡说"这行没了"，南坡说"这行在"——本是芝麻大点事，结果两本册子永久地对不上。

"所以作废不是涂，是再添一行。"老账房敲了敲岩壁，"添一行说它不算，这行本身又是一个印、一行字，念的时候照样认得、照样归一。两本册子上都有它，就有一样。"

新账房想了想，还有个疑问："两个人同一天同一条路，一个在北坡记，一个在南坡记，各记各的，算不算打架？"

"那不打架。"老账房说，"两行都留着，都留着就一样。打架的从来不是这个。"

峡里这些年真正吃过亏的，是另一种：一队给一头骡子记了"左前腿有瘸"，另一队记"右前腿有瘸"。两边都说得清楚，谁也没说错，可凑到一块儿，事情就拧了。

老账房说："路账只能保证两本册子最后一样。管不了册上写的东西对不对。"

新账房又问："那非得写'只添不涂'？要是能涂，事情不是更干净？"

"能涂的账本，就不是这本账本了。"老账房说，"能涂，就意味着有一条消息得在别的册子上也生效。它什么时候生效？走索道，绕远、迟到、重复——你永远不知道对面涂没涂。这事没有答案，就不能要。"

峡口每年有一场大对账。遇山洪的时候，两队常跑散，册子各在一半人手手里。等他们重逢，有人念三天三夜，把两边册子从头对到尾，红点一样多，一行不差。有人手腕酸得抬不起来，说这三天值了——三年前，正是峡里这条规矩，让两队没打过一架。

## 这个故事在讲什么

**收敛数据类型（Convergent Replicated Data Type, CRDT）**：一种可以由多台机器各自独立修改、再把副本数据合并起来的数据类型。它的设计目标是：即使消息延迟、丢失、重复、乱序到达，各副本最终也会收敛到**完全相同的状态**——不需要中心节点、不需要全体表决、不需要时钟同步。

关键不在"怎么让数据一致"，而在"**状态长什么样**"。CRDT 把状态定义成一个可合并的代数结构（半格，join-semilattice），合并操作满足三条：

- **交换律**：merge(A, B) = merge(B, A)，谁先谁后无所谓；
- **结合律**：merge(merge(A, B), C) = merge(A, merge(B, C))，怎么分组都无所谓；
- **幂等律**：merge(A, A) = A，重复吸收，重复送达无害。

再加一条**单调性**：状态只增不减。真正的"删除"不是抹掉，而是补一条"此行作废"的记录，让作废本身也成为可增的元素。

**边界（与近邻概念划界）**：

- **不是共识算法**。Paxos/Raft 保证所有节点对"顺序与取值"达成一致，代价可能是阻塞等待；CRDT 放弃全局顺序，只要状态能收敛，代价是语义上可能同时保留矛盾。
- **不是操作转换（OT）**。OT（Google Docs 一路）靠变换函数让乱序编辑收敛；CRDT（Yjs、Figma 一路）直接改状态的表示方式，让合并本身可交换可幂等。
- **不等于"最终一致数据库"**。普通最终一致数据库在行级/键级合并时仍会冲突，需要应用层仲裁；CRDT 把收敛做进了类型定义本身。
- **不是"没冲突"**。它保证的是副本状态不分叉，不保证业务语义唯一。

**生活中的例子**：

1. 离线优先的待办 App：地铁里离线加了三件事，联网后同步，三端最终一致；
2. 协同编辑文档：多人同时敲同一段，最后文档收敛，但改动顺序可能被重排；
3. 多区域数据库复制：两个机房各写各的，跨城同步后数据合流；
4. 边缘节点/IoT 设备缓存配置：设备断网时自行改配置，复联后自动合并；
5. 多探针监控计数：十个采集点各加各的请求数，汇总时相加，重复上报不会把计数撑大；
6. 分布式部署的计数器（PN-Counter）、集合（OR-Set）、协作画布元素位置（2D-Grid）。

### 陷阱一：以为 CRDT "消除了冲突"

它消除的是**副本分歧**（divergence），不是**语义冲突**（conflict）。集合型 CRDT 里两人都加"张三"，合起来两条都在，并无矛盾；但"最后写入者获胜"寄存器在两个副本并发写入不同值时，必须靠时钟或版本号去猜谁赢——而时钟本身并不可靠。真正的业务矛盾（转角只能过一辆车、余额不能为负）CRDT 管不了，得靠应用层规则或换结构。

### 陷阱二：以为 CRDT 能替代共识

涉及唯一性约束（一个用户名只能存在一份）、权限、跨资源不变量（转账总额守恒）时，合并算不出唯一答案，必须引入中心或共识协议。共识擅长"全局定序"，CRDT 擅长"多主并发写"，两者解决的痛点不同，不是替代关系。

### 陷阱三：以为"只增"是万能免罪符

真正删除需要"墓碑"：墓碑必须带唯一标识，并且能跟随元素一同传播（OR-Set 用唯一标签 tag 来区分"删前加"与"删后加"），否则离线场景会出现已被删除的元素"复活"。墓碑不清理，状态还会无界膨胀。

### 陷阱四：以为合并就是"重放操作日志"

CRDT 的路线是**状态半格**，不是日志重放。日志重放要处理乱序与因果关系才能收敛（OT/因果重放一路），CRDT 用结构设计把顺序问题直接绕开。

### CRDT 的 5 层用途

1. **离线优先客户端**：本地先写、后合并，断网不阻塞，这是 CRDT 最原始的动机；
2. **多副本与多区域数据库**：把"跨城复制冲突"从运维难题降级成类型设计问题；
3. **协同编辑与共享白板**：文本、光标、图形元素的并发编辑与收敛；
4. **弱连接与边缘计算**：IoT、CDN 边缘、车载终端在不稳定网络下的状态同步；
5. **遥测与可观测性**：分布式计数器、采样聚合，天然容忍重复上报；
6. **账务类应用的局部使用**：只读视图、缓存层可以用 CRDT；核心账本仍倾向用带共识的账本系统。

## 故事里的隐喻，对应着什么

| 故事元素 | 学术对应 |
|---|---|
| 《同行录》 | 副本状态（replicated state） |
| 只添不涂 | 单调性 / 只增状态（grow-only） |
| 一行盖"丁七印" | 带唯一标识的原子元素（版本化 tag） |
| 添一行 | 生成新的不可变状态元素（op） |
| 互相念册子 | 状态合并（merge / join） |
| 念到合上就点红点 | 幂等：重复吸收，重复送达无害 |
| 谁先念都一样 | 交换律 |
| 念到一半停手再念 | 结合律 |
| 峡索绕远、迟到、送三遍 | 异步网络、at-least-once 投递、乱序 |
| 相遇才念，不必约时间 | 无协调（coordination-free） |
| 作废要另添一行而非涂改 | 墓碑 / add-wins 删除语义 |
| 两队不打架 | 收敛：副本状态最终一致 |
| 骡子左腿瘸 vs 右腿瘸 | 语义冲突：状态一致但事实矛盾，CRDT 不负责 |
| 没人能保证对面涂没涂 | 不可通约的不确定性，故必须放弃删除 |

## 一句话总结

> 把副本状态设计成"只往上长、且合并结果与顺序和次数都无关"的结构，网络再乱，最后也长成同一本账。

这就是 收敛数据类型（CRDT）。
