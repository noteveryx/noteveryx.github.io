# 2026-10-19 寓言故事 · 饭堂里那块"试吃布"

> 每天一个研究生水平概念，借一个故事让它在心里生根。

---

## 故事

赵家村有个大饭堂，每天正午十二点一到，二十桌人同时冲进来抢一只刚出炉的烤全羊。

规矩是老祖宗定的：每桌一次只准夹一筷羊，羊须切得均匀。问题也跟着来了。三十只手同时伸过去，羊左腿一会儿被张三扯走一块，右肘一会儿被李四挖走一片，最惨的是两个后生筷子撞在同一块羊排上，谁也拔不出来，羊排撕成两半，两桌都没吃好，还骂了一中午。

村长老赵蹲在灶台看了三天，画出两条半龙。

第二天起，饭堂门口多了一队小鬼。每桌进来领羊时，先派一只小鬼从灶房抱出一块雪白棉布——叫"试吃布"——往那头羊身上一盖。布外看不见羊在哪儿、布里看不见别桌人在干啥，那一桌的人在布下以为自己独占了整头羊，照夹不误。

夹完一筷肉，这一桌的人把筷子放下来，小鬼掀起布角看一眼：布下那一筷有没有跟别桌撞在同一块肉上？

没撞——小鬼掏出一只红印往那一筷上一盖，"戳"。这一筷就正式从羊身上切走，记到账上，别的桌再也拿不走。

撞了——小鬼一声哨，整桌的菜盘连带那筷肉"哗"地推回大锅重炖，那一桌的人红着脸把筷子缩回去，等下一轮再盖布重试。

半年下来，二十桌人再没打过架。村里又立了块新碑，三行字：

> 布下见真心。
> 盖戳才算数。
> 倒盘不亏心。

碑脚还刻了句谁也看不懂的话："布盖得越勤，撞得越少；筷子伸得越少，回锅越快。"村里人念了一遍，半懂不懂——但饭堂的羊，从此没人抢破皮。

## 这个故事在讲什么

### 定义

**软件事务内存（Software Transactional Memory，STM）** 是一种**并发编程抽象**。程序员把一段对共享内存的读写操作"包"进一个**事务（transaction）** 里：事务执行期间，所有读和写都落到一份**私有日志视图**上，看不见别人在动；事务结束时，运行时统一**验证**——若这一组操作与别人冲突（读了别人写过的旧值、或者两人写了同一份数据），整段事务**回滚（abort）** 作废重来；若无人冲突，**一次性原子提交（commit）**，对所有线程同时可见。

它的三大承诺：
1. **原子性（Atomicity）**：事务里所有写要么一起生效，要么一笔不写。
2. **隔离性（Isolation）**：事务内看不到别人的中间状态，仿佛独占内存。
3. **乐观并发（Optimistic Concurrency）**：不预先抢锁，先做完再说，撞了再退。

### 与近义词的边界

- **vs. 互斥锁（Mutex）**：锁是"先抢到再用"，**悲观**并发；STM 是"先用再算账"，**乐观**并发。前者抢不到就排队，后者抢完发现撞车就推倒重来。
- **vs. 数据库事务（DB Transaction）**：DB 事务是**硬盘粒度 + 持久化 + 复杂恢复**，STM 是**内存粒度 + 不持久化 + 单纯可见性**。两边都用"事务"这个词，但 STM 不写 redo log、不 flush 到磁盘。
- **vs. 消息队列（Message Queue）**：消息队列是**进程间异步协调**，任务落地后谁也不等谁；STM 是**线程间同步协调**，大家抢同一片内存，谁撞了谁退。
- **vs. 无锁编程（Lock-Free Programming）**：无锁用 CAS 自旋硬扛，程序员手写 retry 循环；STM 把 retry 循环交给运行时，程序员只写"正面"的事务体。

### 陷阱一：把 STM 当万能解药

STM 在**读多写少 + 冲突稀疏**的场景非常优雅（每条事务平均 < 5% 概率撞车时通常胜过锁）。但一进入**密集写、热点数据**（比如二十个线程同时往同一个计数器自增），回滚率爆表，性能可能比一把粗锁还烂十倍。STM 不是替代锁，是**互补**。

### 陷阱二：在事务里调用 IO

数据库事务有 XA / 两阶段提交之类的兜底，事务里的 IO 失败能回滚。STM 一般**禁止**事务里调用系统 IO，因为 IO 的副作用不可逆——你已经把邮件发出去了，事务回滚能撤回邮件吗？Haskell 的 STM 在类型层面直接拒绝事务里包 IO 操作。

### 陷阱三：锁里包事务、事务里包锁

锁里包事务——你用一把锁把整个事务保护起来，等于回到了悲观锁，乐观并发的优势全丢。事务里包锁——STM 验证时只看到"你写了哪些地址"，看不到锁的释放顺序，两个事务可能各持一把锁等对方回滚，**活锁（live-lock）或死锁**。

### 陷阱四：以为 STM 能解决 race condition 的逻辑错误

STM 保证"事务里读到的值在提交时一致"，不保证"你写的逻辑就一定对"。程序员自己写错事务边界（比如本该一起读的两个字段分两次事务读），STM 救不了你。

### STM 的 N 层用途

1. **多核 CPU 上的线程协作**：Haskell STM、Clojure STM、Java 的 Akka-STM、C++20 提案的 std::atomic 部分场景。
2. **数据库内核的内存结构**：VoltDB、Hekaton（SQL Server 的内存引擎）都用类似 STM 的乐观并发提交。
3. **分布式事务的客户端缓存**：Google Percolator 在 BigTable 之上用乐观事务实现跨行原子写。
4. **版本控制系统**：Git 的 `pull --rebase`、Mercurial 的 bookmark 冲突解，本质都是 STM 思想的"合并或回退"。
5. **机器学习参数服务器**：把每个 worker 的梯度更新当一个事务，PSERUNe 反复回滚冲突更新。
6. **区块链**：Optimistic Concurrency Control（OCC）是区块链"先打包后验证"思路的祖师爷，比特币区块的临时链与最终链没救。

## 故事里的隐喻，对应着什么

| 故事元素 | 学术对应 |
|---|---|
| 二十桌人同时抢一只羊 | 多核线程并发访问同一份共享数据结构 |
| 一桌进来领一次羊 | 一个事务（transaction） |
| 雪白"试吃布"盖在羊上 | 事务私有日志视图（local log / read-set + write-set） |
| 布下看不见别桌 | 隔离性（isolation） |
| 布掀开看一眼撞没撞 | 提交时验证（validation / commit check） |
| 撞车就推倒菜盘重炖 | 冲突回滚（abort + retry） |
| 不撞就盖红戳记账 | 原子提交（atomic commit） |
| 小鬼抱布、盖戳 | 事务管理器（TM, transaction manager） |
| 烤全羊本身 | 共享内存 / 共享数据结构 |
| 三行碑文 | STM 的三大保证 |
| 筷子伸得越少回锅越快 | 冲突率越低、事务越短，STM 越快 |
| 半年没打架 | 乐观并发假设成立时的稳态 |

## 一句话总结

> **布下见真心，盖戳才算数，倒盘不亏心——STM 是"先做后验、撞了重做、谁撞谁退"的内存事务抽象。**

这就是 **软件事务内存（Software Transactional Memory, STM）**。

## 记忆口诀

- 口诀 1：先盖布、后掀布——事务的两步：执行 + 验证提交。
- 口诀 2：撞车推倒重来——冲突回滚，别试图补救。
- 口诀 3：布下见真心——隔离性，事务内看不见外部中间态。
- 口诀 4：盖戳才算数——原子性，全做或全不做。
- 口诀 5：筷子伸得少、撞得少——事务粒度要小，热点数据要避开。
