# 2026-11-23 寓言故事 · 十二本抄账

> 每天一个研究生水平概念，借一个故事让它在心里生根。

---

## 故事

清河府有一间总档房，存着全府十二个衙门的田亩户籍正账。这正账金贵得很，谁要动一笔，都得请档房当众翻页、抄录、盖印，再一张张传示十二个衙门。折腾一趟半个月。

新来的掌书叫陆蘅。他上任头一件事，不是换锁，不是添柜，是把十二个衙门的人叫来，问：你们到底嫌什么？衙门们吵了三天，有人嫌慢，有人说写着写着别人一改，我这边就作废了。

陆蘅听完，回了一句：那就让你们各自看各自的那本。

他定了个"换账日"。每季月底，档房把正账整整抄成十二本副本，一本送一个衙门，编号盖印。从换账日起，副本在谁手里谁说了算，谁也改不了，谁也偷看不着别人那本。衙门要改自己账上的数，就在副本之外另写草纸，草纸只有本衙门自己看得见，外头谁也不知道这衙门此刻算成了什么样。

法子一推行，衙门的速度立刻上来了。十二家各看各的副本，互不遮挡；抄错个字也不至于当场翻脸。

头一年就出事。

清河县有两条渠，甲渠灌东田，乙渠灌西田，合起来用的是河里那份定数。秋里水紧，县衙派了两个书吏，各领一门差事：东田的赵书吏在草纸上写"甲渠用水上限减一斗"，西田的钱书吏写"乙渠用水上限减一斗"。两份草纸各写各的田，互不相干。档房排到谁先谁后都合了规，先后并进去都对得上，挑不出一处错。

直到渠口的水闸夜里被人关小了一格。第二天两片田的苗都旱了。查下来才知道：河里的水本来只够灌一片田，两边各减一斗，单看每一边都是"在自己那份里减了"，合起来却超了河。

老书吏捧着两份都合规的草纸叹气：规矩没破，两边都没撒谎，田还是旱了。

陆蘅把这事记进册子，给它取了个名字，叫"偏斜"。两条各自都合规的改动，合起来把一条总规矩捅穿了——因为它们动的是不同的对象，却受着同一条总量约束。

第二件事更闹。

南川县令嫌副本麻烦，嫌自己衙门总押着旧副本不还。档房说旧本子得烧掉，别处另抄新的。南川说：我这一烧，底下正在核的二十户账就全乱了。档房不敢烧。

于是旧本子一年年压着，越压越多。到第七年，档房三间屋子堆的全是纸，翻一个户籍得爬梯子去找。陆蘅的祖父留下一句话：看纸山不如看扔纸。

于是新规矩两条：一，谁的本子最迟什么时候必须还；二，逾期的本子当众作废，来年重新抄。

南川跳脚：作废了我的账怎么办？

陆蘅说：那你就照规矩重核一遍。你拖着不还，全府都得替你压着这座纸山。

有人说这规矩狠。可他们从没人听陆蘅说过第二句话：别以为抱着旧本子不还，你那份"能看见从前"的权利是白来的。

## 这个故事在讲什么

### 概念

**多版本并发控制（Multi-Version Concurrency Control, MVCC）**：一种并发控制的实现范式。写操作不去原地覆盖旧数据，而是生成一个**新版本**；多个版本在存储中长期并存；读操作不加锁、不等待，取一份**读视图（快照）**，只看到在快照时刻"已提交"的那些版本。事务提交时，新版本才对后续事务可见。

概念分两层，务必分开：

- **MVCC 是机制**：怎么让多个版本共存、怎么判定某个版本对某次读是否可见。
- **快照隔离（Snapshot Isolation, SI）是协议**：规定事务读哪一份快照、什么情况下两个事务冲突。最常见的组合是"MVCC + SI"，PostgreSQL、Oracle、MySQL InnoDB、TiDB、CockroachDB 都是这个组合。MVCC 也可以承载别的协议（可串行化快照隔离 SSI）。

### 3-5 个落地的例子

1. **PostgreSQL**：每条数据行都留着若干个行版本（老版本挪进 undo 表空间），每个事务启动时取一份快照，记录当时的"可见性规则"。Read Committed 是每条语句取一次新快照，Repeatable Read 是整个事务取一次快照。
2. **Oracle**：一条"一致读"在 undo 段里翻出属于你那一刻的旧版本给你看，全程不加锁。
3. **MySQL InnoDB**：靠 undo log 维护 read view，RR 隔离级别下 read view 在事务内固定。
4. **TiDB / CockroachDB**：MVCC 是事务模型的地基，key 里编码了时间戳（key 空间按时间分区），因此能支持时间点恢复、CDC 增量订阅。
5. **流批一体（Flink / Kafka changelog）**：读同一张表的不同时间点视图，本质也是 MVCC 版本在流式场景的延伸。

### 陷阱一：把 MVCC 当成"历史版本备份"

MVCC 的多版本是为了**并发可见性**，不是为"回滚到过去"。回滚是事务级的撤销操作（靠 undo log 回退自己的写），跟 MVCC 版本链完全是两套东西。MVCC 里的老版本通常在没人再需要它们之后被后台回收（PostgreSQL 叫 autovacuum/vacuum），它们不是给你做时间旅行用的档案。

### 陷阱二：以为用了 MVCC 就"没有并发问题"了

MVCC 只解决读写互斥问题，**写写冲突照样存在**，而且通常拖到提交那一刻才暴露。更关键的是：快照隔离下存在**写偏斜（write skew）**——两个事务改的是**不同的行**，读的是**同一个范围**，各自都通过了冲突检测，合起来却违反了总量约束。故事里那份甲渠、那份乙渠就是这个。修它要靠额外机制：SSI（可串行化快照隔离）、显式的谓词锁、唯一索引/外键约束、业务层串行化。

### 陷阱三：把"快照"当成全局一致读

快照只保证**同一个事务内部**多次读同一份数据看到同一个版本（可重复读），不保证跨事务之间构成一个可串行化的顺序。多个事务各拿各的快照，各看各的世界，这不矛盾。

### MVCC 的三层用途

1. **并发层**：读写互不阻塞。读不占锁、不等写；写不阻塞已在进行的读。高并发 OLTP 的基本盘。
2. **一致性层**：为每个事务提供稳定读视图，避免了脏读、不可重复读，还天然给出"语句级/事务级"两种可重复读粒度。
3. **工程层**：MVCC 版本 + 预写日志是**时间点恢复（PITR）**、**逻辑复制与 CDC**、**在线 DDL 期间不中断读写**、以及 HTAP 与流批一体的底座——一套版本结构同时被并发控制和运维复制复用。

### MVCC 与相邻概念的边界

- **vs 两阶段锁（2PL）**：2PL 靠加锁互斥，代价是阻塞与死锁；MVCC 靠版本多路，读写并行。两者可以混用。
- **vs 时间戳排序（TSO）**：TSO 是并发控制协议（按时间戳排序并检测），MVCC 是实现机制；MVCC 可以是 TSO 的载体，也可以承载 SI。
- **vs 乐观并发控制（OCC）**：OCC 是"冲突就回滚重试"的策略，MVCC 是"版本怎么存、怎么可见"的管理机制，两者常同时出现，不是同一层面的对立。
- **vs undo/redo 日志**：日志是持久化恢复用的；MVCC 版本是在线并发用的。PostgreSQL 把二者共用存储（同一套 WAL 加 undo 表空间），容易混为一谈，但职责不同。

## 故事里的隐喻，对应着什么

| 故事元素 | 学术对应 |
|---|---|
| 总档房的正账 | 共享数据库 / 存储引擎中的数据页 |
| 改一笔要传示十二个衙门 | 粗粒度锁、串行化写、阻塞式并发控制 |
| 换账日抄成十二本副本 | 快照 / 版本（MVCC 的多版本共存） |
| 副本锁住谁也改不了 | 快照读不修改数据，读不加锁 |
| 各衙门看不见别家那本 | 事务隔离：读视图互不可见 |
| 草纸（各衙门私写） | 事务私有写集 / 未提交版本（undo） |
| 并档 | 提交（commit）与新版本对后续事务可见 |
| 并档排队 | 提交序列化点、冲突检测时机 |
| 甲渠减一斗 / 乙渠减一斗 | 写偏斜（write skew）：写集不重叠，总量约束被破坏 |
| 两份草纸单看都合规 | 快照隔离不是可串行化 |
| 老书吏叹气"没撒谎田还是旱了" | 线性一致性破坏可由"都合规"的局部动作合成 |
| 旧副本烧不掉 | 长事务/长快照阻塞版本回收（vacuum 阻塞） |
| 档房三间屋子的纸山 | 版本膨胀、存储开销与扫描性能退化 |
| 归还期限与逾期作废 | 强制回收长快照；快照保护一致性，不保护无限期占有 |
| "看纸山不如看扔纸" | 回收策略优先于无限保留历史版本 |

## 一句话总结

> MVCC 就是让每个读者都站在自己那一刻的世界里看同一批账，写者永远往"未来"加新页，不涂改旧页。

这就是多版本并发控制。

---

## 记忆口诀

- 口诀 1：写者不涂改，只添新页；读者各看各的那一版。
- 口诀 2：读视图定"何时"，可见性规则定"看得见谁"。
- 口诀 3：脏读不重读有了，可重复读有了，可串行化还没有。
- 口诀 4：冲突到提交才报，写偏斜还得靠外力（SSI、谓词锁、约束）。
- 口诀 5：纸山要清，长事务要限；快照保一致，不保你永远占着旧账。
